# End-to-End Encrypted Workspaces

In an end-to-end encrypted workspace, conversations, files and agent output are decrypted only on devices you have authorized. Lody's servers relay and store the data, but only ever see ciphertext they cannot read.

<Callout type="warn">
If you lose every authorized device and have no recovery file or passkey, the workspace can never be opened again, and Lody cannot recover it. Set up a recovery file in the encryption console soon after you create the workspace.
</Callout>

## How content is encrypted

- Each workspace has a **workspace key**. Content is encrypted with it on your device before it is sent.
- Each authorized device has its own device keys, kept in the operating system's secure storage (for example the macOS Keychain). The workspace key is only ever delivered to authorized devices, encrypted.
- The server never receives the workspace key, so it can relay and store content but cannot read it.

## Signed records decide who is in

Inviting a member, approving a device, removing a member and transferring ownership are each written as a **signed record**, signed by a permitted member on their own device. Every device checks these records itself:

- A bad signature, a reordered history or an action someone was not allowed to take is rejected, and inviting and approving pause.
- The server only passes records along and cannot sign for anyone, so it cannot quietly add a member or a device.

You can read these records under **Security code & history** in the encryption console, for example "Jordan Lee joined the workspace (approved by Alex Chen)".

## Adding a new device

When a new device opens the encrypted workspace it sends a request automatically. Your authorized computer or phone shows an approval window; check that the numbers on both screens match and choose **Authorize**. The new device receives the key and opens the workspace. The server only relays the request and cannot approve it for you.

## Removing members and replacing the key

A removed member's devices lose access immediately and cannot see anything new. When you remove someone, also **replace the workspace key** so that an old device holding the old key cannot decrypt new content. History already downloaded to their devices cannot be taken back.

## Security code [#security-code]

The security code is a string of digits computed from the workspace's current member and authorization information. It lets you confirm that the members and devices you see are exactly what everyone else sees.

- If your code **matches** what other members, and your other devices, show, the workspace member and authorization information is consistent: nobody was shown a different record by the server.
- If it **differs**, both refresh and compare again (codes also differ when one side is out of date). If it still differs, do not invite or approve anyone, and tell the workspace owner.

To compare, open **Security code & history → Compare with a teammate** in the encryption console and scan the QR code on their screen, or read the groups of digits aloud. In person, on video or by phone all work; avoid sending the code only through Lody itself.

<Callout type="info">
A matching code proves you all see the same member and authorization records. It does not prove that someone is who they claim to be; make sure you are comparing with the teammate you know.
</Callout>

## Recovery

Under **Recovery** in the encryption console you can save a recovery file or add a supported passkey. If you lose every device, use them to open the workspace again on a new one. Keep the recovery file offline: anyone with both the file and your account can read your encrypted workspaces.

## Known limits

- In a browser, security depends on the code the Lody website serves not being tampered with. If that matters to you, use the desktop or mobile app.
- When the server is unreachable, your machines can keep working for a limited time with the member information they already confirmed; inviting, approving devices and replacing keys wait until you are back online.

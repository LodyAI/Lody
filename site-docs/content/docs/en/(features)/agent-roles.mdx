# Agent Roles

An **Agent Role** packages *how* you use an agent: the machine and
[Agent Config](/docs/agents) it runs on, the model and reasoning level, the permission mode, and an
optional default instruction. Give it an emoji and a name, and all of those choices become one click.

A role is not a new provider and not a running agent. It stores no API keys and no MCP selection —
those stay with the Agent Config.

## Create a role

Two entry points, one editor:

- **Settings** → **Agent Roles** → the `+` button.
- The **Role** row in the composer's run configuration → **New role with settings**. This one opens
  pre-filled with whatever you are about to run, which is the quickest way to keep a setup you just
  tuned.

Pick the machine and agent config, then the model, reasoning, and permission that agent publishes,
and optionally a default instruction. A new role is private to you until you turn on
**Share with workspace**.

## Use a role when starting a conversation

The composer's run configuration has a **Role** row above **Agent**, because a role answers every
row under it at once.

- On desktop, open the run-config button in the composer footer and hover **Role**: the list sits
  beside a panel that states exactly what the highlighted role runs.
- On mobile, open the run-config sheet; **Role** is the first row.

Pick one and the rows under it change to match. The composer footer then shows the role's emoji and
name, with its values beside it in smaller text. Roles you have actually started a chat with also
appear under **Recently used**.

**None** clears the name, not the configuration: the values a role set are yours now, so leaving the
role keeps them.

The footer names a role only while the configuration is still that role's. Change the model by hand
and the name disappears — the footer never claims a role that is not what will run.

A blank child tab inside another conversation follows these same new-conversation rules. Its machine
and working directory stay attached to the parent session, but its Role list includes every Role on
that machine, across agent types. Picking one switches the draft to the Role's agent config and
freezes its run configuration, instruction, and provenance when you send the first message.

## Use a role inside a conversation

Once a conversation has been created, it already runs an agent on a machine and a role cannot move
it there. So the **Role** row inside a conversation:

- offers only roles bound to an agent of the **same type**, whose model, reasoning, and permission
  values that agent understands, and
- applies only that run configuration — the role's default instruction is not added to a
  conversation already in progress.

Every row stays editable afterwards.

## Mention a role

Type `@` and pick a role under **Agent Roles** to ask the current agent to start a *new* conversation
with it:

```text
@code-reviewer check the diff on this branch and report anything that breaks
```

The new conversation starts on the role's machine and agent config with its model, reasoning,
permission, and default instruction already applied. What the role said at the moment you sent the
message is frozen into that request, so editing or deleting the role afterwards cannot change work
that was already accepted.

Which roles you can mention depends on where you are: a local project or a plain chat offers roles on
that same machine, while a GitHub project can also reach roles on your other authorized machines,
because the new conversation clones the repository itself. See [Mentions](/docs/mention) for the
other mention types.

## Sharing

A role is private until you share it. **Share with workspace** makes it visible, mentionable, and
runnable for every member. It still runs on its own machine, so members need access to that machine.

Private means other members cannot discover, mention, or run it through Lody. It is not encryption,
which is why a role stores no secrets in the first place.

## When a role cannot run

A role binds one machine and one agent config exactly, and never quietly substitutes another. If its
machine goes offline or its agent config is deleted, the role stays listed — in Settings and in the
picker — marked with the precise reason, and cannot be selected until you fix it.

Editing a role only affects later use. Conversations already started from it keep running as they
were.

# Scheduled tasks

A **scheduled task** sends a prompt at the times you choose, with the Agent, model, permission mode and project you picked. Every run is an ordinary chat: open it, keep talking, or stop it whenever you like.

Typical uses: summarize yesterday's merged commits every morning, check dependency advisories every weekday, draft the weekly report on Friday — or keep a manual task you run with one click when you need it.

For an overview of recurring coding workflows, see [Coding Agent Scheduler](/coding-agent-scheduler/).

## Where it runs

Scheduled tasks do not run in the cloud. **One of your own machines** owns each one:

- That machine runs the [Lody CLI](/docs/cli) (the desktop app starts it for you), on a version with schedule support.
- The editor reads times on **that machine's local time zone**; there is no zone picker. "Every day at 9:00" means 9:00 on that machine. If an older machine has not reported its time zone, the editor falls back to your viewing device's zone. Check **Next runs** before saving.
- If the machine is off, asleep, or the CLI is not running, nothing runs at that time. See [missed runs](#missed-runs) for what happens afterwards.

You can view and manage scheduled tasks on the web, desktop and phone, but only the owning machine executes them.

Calendar rules save an explicit time zone. A **Once** rule saves an absolute instant: changing the selected machine redisplays that same instant on its clock. Existing advanced cron rules retain their saved zone.

## Choose a coding agent

Schedules create ordinary Sessions with the selected [Agent Config](/docs/agents/). The setup routes include:

- **Codex** — select a configured Codex Agent on the execution machine
- **Claude Code** — select its Agent Config and available model and permission controls
- **Kimi Code** — use the managed Kimi Code provider and complete its sign-in
- **GLM over Claude Code** — use the GLM provider preset with its matching endpoint and credentials; this runs through Claude Code
- **DeepSeek Harness** — use the built-in Harness provider; this is separate from DeepSeek over Claude Code
- **Pi** — use the managed Pi provider on a supported machine; providers without a permission selector use their own execution policy

Credentials, model access, tools and dependencies must be ready on the owning machine. These are integration routes, not a claim that every model or permission setting has been tested with scheduled execution. Run a small manual task with your chosen configuration first. See the [Agent Config guide](/docs/agents/) for provider-specific requirements and limitations.

## Create a scheduled task

Open **Schedules** in the sidebar and choose **New schedule** (or search "New Schedule" in the command palette). The editor is shaped like the composer:

1. **Name and prompt** — what the Agent should do on each run.
2. **Agent, model and permission** — the same controls as the bottom of the composer. A new task starts with the machine and Agent you last used on the chat landing, and that Agent's remembered settings. No extra permission selection is required just to save a task, but remembered settings still need to pass runtime validation. Providers such as Pi that have no permission selector use their own execution policy.
3. **Machine, project, worktree** — the project is optional; without one, each run is a plain chat with the Agent and no repository is checked out.
4. **Send to** and **Trigger** — see below.

Anything missing is marked with an exclamation mark next to the control that fixes it. Saving returns you to the list.

## Triggers

- **On a schedule** — pick a rule under **Repeat**, then the time:
  - every day, every weekday, every week (choose days), every month (choose dates)
  - every few hours, every few minutes
  - once (a date and time)
- **Manual** — never runs by itself; it runs only when you press **Run now**. Handy for a prompt you reuse.

The editor lists the **Next runs** so you can check the rule. Times and dates are typed in.

## Prompts to try

Select the project these prompts should inspect. They are example instructions to adapt, not reports of completed runs.

### Check the configuration with a manual task

Choose **Manual**, **New chat each run**, and your Agent Config. Save this prompt, then press **Run now**:

> Read this project's README and package or build manifest. Return the project name, the documented test command, and any missing setup information. Do not edit files, install dependencies, or run the tests.

Open **Last run** and check that a chat started on the intended machine with the intended Agent. This checks that configuration for this task; it does not verify every future tool or permission request.

### Summarize recent repository work each morning

Choose **Every day at 9:00** and **New chat each run**:

> Inspect this project's local Git history for the last 24 hours. Summarize up to ten changes with commit hashes, group related changes, and list follow-up questions separately. If there are no commits in that period, say so. Report the branch inspected. Do not fetch, edit files, or publish anything.

This reads the checkout's available history. It does not promise that a local branch contains every newly merged remote commit.

### Review dependency advisories on weekdays

Choose **Every weekday at 10:00**:

> Read this project's dependency manifests and lockfiles. Check available official security advisories for the installed versions. Report the package, installed version, advisory link, and affected range for each match. If network access or a source is unavailable, say what you could not verify. Do not update dependencies or open a pull request.

The Agent needs the relevant files, network access and tools for that check. Review the first run before relying on it as a recurring report.

## Where runs go

- **New chat each run** (default) — every run starts its own chat.
- **One chat for this task** — every run is appended to the same chat, for tasks that build on earlier context. The chat is created on the first run; **Start a new chat** moves later runs to a fresh one.
- **An existing chat** — runs are appended to a chat you pick. That chat's Agent is used, and no separate project is chosen.

## Manage scheduled tasks

Each row in the list shows the name, frequency, next run and what it runs with:

- Timed rows have **Pause** / **Resume** right on the row; manual rows have **Run now**.
- Right-click a row to open it, run it now, pause or resume, open the **Last run**, or delete it (deleting asks first).
- Clicking a row slides its details in from the right: pause, run now and delete at the top, **Run history** at the bottom. Drag the divider to resize; click empty space in the list to close.

Only the creator can edit, pause or delete a scheduled task. Pausing stops future runs; chats already started must be cancelled on their own.

## Let an Agent set it up

Tell the Agent something like "check for dependency updates every weekday at 9am" and it drafts the name, prompt and rule, then shows a **Schedule this task?** card in the chat.

- The card uses the current conversation's Agent, permission mode, machine and project, and lists exactly what will be created.
- **Edit** lets you change the name, prompt and time rule right on the card.
- **Create** creates it; **Ignore** drops it. Once created the card can no longer be edited — change the task from the Schedules page.

A proposal stays pending until you press **Create**. The built-in schedule tools also let an Agent list, inspect and pause existing tasks. They do not let it directly create, edit or resume a task; use the schedule controls for those actions.

## Missed runs

With the editor's default missed-run policy, a task catches up **once** after the machine wakes or the CLI starts again, for the most recent missed time. It does not replay every missed slot. The run may still wait for the Agent or configuration to become available.

If the previous run is still going when the next one is due, the new run waits and starts once the previous one finishes; at most one run waits.

## FAQ

### A task says "Waiting for the schedule configuration to finish syncing"?

The owning machine has not received the latest configuration yet; for a few seconds after saving this is normal. If it stays, check that the machine is online and its CLI is up to date.

### Why can't I pick a machine?

Scheduled tasks run only on your own machines with a CLI that supports them. Update the Lody CLI on that machine.

### Will my computer wake up to run a task?

No. The CLI checks and runs tasks while the machine is awake; it does not wake a sleeping computer. After waking it catches up once, as described in [missed runs](#missed-runs).

### Why did a saved task fail before starting a chat?

One known case is tracked in [issue #1247](https://github.com/LodyAI/Lody/issues/1247#issuecomment-5986803074). A schedule with a saved `fast: "false"` option can fail before creating a Session when the capability probe used a model without a Fast option. The value can come from remembered chat settings even if you did not touch Fast in the schedule editor.

The creation path rejects that saved option, but the scheduler labels the failure `DISPATCH_UNAVAILABLE` and retries. The validation gap was still present in [source checked on October 5, 2026](https://github.com/LodyAI/Lody/blob/cd3f5b3ca969be5fa2e327744d449ffd802efe7b/apps/cli/src/commands/session.ts#L3099-L3105); this symptom does not mean the Agent itself is unavailable. Follow the issue for fix status. When reporting it, include the CLI version, selected Agent and model, and displayed error, without credentials or private prompts.

未処理の Issue キュー、いくつかのオープン中の PR、そして 3 つのリポジトリにまたがるかもしれないバグがあるとします。プライマリエージェントにキューを順番に処理させ、修正を Kimi に委任し、Codex にレビューを依頼して、結果を取りまとめさせたい場面です。

Lody では、こうした作業を 1 つの会話から整理・統括できます。コーディングエージェントは別のセッションを作成し、指示を送り、進捗を読み取ってフォローアップできます。また、エージェント同士でメッセージをやり取りすることも可能です。たとえば、レビュー担当が修正を書いているエージェントに指摘事項を送り、パッチの準備ができたら再レビューを依頼するといった連携が行えます。

このガイドでは、そのようなワークフローで**プライマリエージェントをオーケストレーターとして使う**方法を紹介します。掲載している例はご自身のリポジトリに合わせて調整できるプロンプト例であり、ベンチマーク結果や本番環境での実行記録ではありません。

<Callout title="どのページを見ればよいですか？">
  このガイドでは、1 つのオーケストレーション用エージェントを使う一連の流れを説明します。基盤となるツールについては [エージェントセッション制御](/ja/docs/session-orchestration) を、ご自身で複数のタスクを立ち上げる方法については [並列コーディングエージェント](/ja/docs/parallel-agents) をご覧ください。
</Callout>

## オーケストレーターの役割

オーケストレーターはタスク全体を把握します。対応が必要な項目、変更同士の依存関係、各パートの担当者、そしてまだ検証が残っている箇所を追跡します。他のエージェントは、それぞれの会話の中で範囲を絞ったタスクを実行します。

作業分担の一例は次のとおりです。

| 会話                   | 担当タスク                                                     | 返却される内容                                 |
| ---------------------- | -------------------------------------------------------------- | ---------------------------------------------- |
| プライマリエージェント | Issue と PR のキューを確認し、作業を割り当て、フォローアップする | 現在のステータス、依存関係、未解決の判断事項   |
| Kimi                   | 範囲を明確にした修正を実装する                                 | パッチ、コミット、検証結果                     |
| Codex                  | そのパッチをレビューする                                       | レビュー対象コミットに紐づく指摘事項           |
| Grok                   | 影響を受ける別のリポジトリを調査する                           | 調査結果とインターフェース変更の提案           |

これらの役割はこのタスクにおける一例にすぎません。役割を入れ替えたり、同じエージェントのインスタンスを複数使ったり、別の互換エージェントをワークスペースに参加させたりできます。Grok も、その役割に割り当てれば修正の実装、パッチのレビュー、他のセッションの調整を行えます。

Lody には、この作業をまとめるための[クロスセッションツール](/ja/docs/session-orchestration/)が用意されています。このガイドでは、プライマリエージェント、Kimi、Codex、Grok の各セッション間でそのツールを使用しており、エージェント固有のチーム機能には依存しません。

## ワークスペースを準備する

[マシンを Lody に接続](/ja/docs/quickstart/)し、使用したい[エージェント設定](/ja/docs/quickstart)がそのマシン上で利用できることを確認してください。対象マシンはオンラインである必要があり、エージェントには対象リポジトリおよび担当タスクに必要な GitHub ツールへのアクセス権が必要です。

以下の例では、調整役にプライマリエージェントを使い、個別の集中作業に Kimi、Codex、または Grok を使います。
調整用のプライマリエージェントセッションを開始し、確認対象のリポジトリ、PR、または Issue を伝えます。コードを編集するタスクにはそれぞれ専用の [Git ワークツリー](/ja/docs/worktrees/)を割り当て、並列で動くエージェントが独立した作業ディレクトリを持てるようにしてください。新しいワークツリーへのフォークはコミット済みの `HEAD` から開始されるため、別のディレクトリにある未コミットの変更は自動的には引き継がれません。

コードを変更する前に、まずキューの全体像を把握させるのが効果的です。

## 1. プライマリエージェントに PR と Issue をトリアージさせる

作業キューには重複した項目が含まれがちです。ある Issue にすでに対応する PR が出ていたり、2 つの PR が同じ問題を解決しようとしていたり、クライアント側の更新より先に SDK 側の変更をマージする必要があったりします。まずはコーディネーターにそれらの関係性を特定してもらいましょう。

```text
Lody のセッションツールを使ってこの作業を調整してください。

以下の PR と Issue を確認してください：[リンクを貼り付け]。
各項目について、影響を受けるリポジトリ、現在の状態、
既存の実装状況、他の項目との依存関係を特定してください。

そのうえで、独立して進められる修正は Kimi セッションに、レビューは Codex セッションに
委任してください。編集を伴うタスクにはそれぞれ別の worktree を割り当ててください。
各依頼には、対象 Issue、作業範囲、期待される動作、検証要件を含めてください。
すでにその作業を担当している既存セッションがある場合は再利用してください。

セッションのリンク、調査結果、そして私の判断が必要な事項をまとめて報告してください。
マージとデプロイは私自身が確認するので実行しないでください。
```

質の高い依頼は、受け取る側のエージェントがキュー全体を読み直さなくても作業に着手できるくらい具体的です。たとえば、「クライアントでの重複送信を修正すること。既存のリトライ動作は維持すること。バグを再現し、パッチを検証すること」のように記述します。別セッションが「例のバグ」の意味を知っていると期待せず、関連する Issue とリポジトリを明記してください。

また、コーディネーターは「タスクが完了した状態」と「変更がマージ可能な状態」を区別する必要があります。パッチ自体は書き終わっていても、レビューや依存先の完了、結合チェックがまだ残っている場合があるからです。

## 2. 複数リポジトリにまたがる修正を調整する

例として、「リクエストをリトライすると同じレコードが二重に作成される」というバグを考えてみましょう。クライアントがリトライを開始し、SDK がリクエストを組み立て、サーバーがそのリクエストを処理済みかどうかを判定します。

各リポジトリでの調査は同時に開始できます。実装に入る前に、エージェント同士で調査結果を突き合わせ、リポジトリ境界をまたぐ挙動について合意させておきましょう。

```text
リクエストのリトライ後に重複レコードが作成される問題について、
以下のリポジトリを横断して調査してください：
[クライアントリポジトリ]、[SDK リポジトリ]、[サーバーリポジトリ]。

クライアントに Kimi セッション、SDK に Codex セッション、サーバーに Grok
セッションを割り当ててください。リトライがどこで発生し、重複リクエストが
どのように処理されているかについて、エージェント間で調査結果を共有させてください。
依存関係のある変更を加える前に、リクエストの仕様（コントラクト）について合意させてください。

独立して進められる部分は並列で実装してください。各エージェントには、
コミット、実行したチェック、他リポジトリの変更への依存関係を報告させてください。

結果を取りまとめ、更新後の各コンポーネントを組み合わせた結合チェックを段取りしてください。
必要なマージ順と残っている未検証箇所を報告してください。
```

やり取りすべき重要なポイントは、たとえば「リクエスト識別子をクライアントと SDK のどちらが生成するか」「リトライ時にその識別子を保持するか」といった細かな仕様である場合もあります。その決定を他のセッションへ共有することで、全体の実装の足並みが揃います。

ワークツリーを分ければファイルの編集は衝突しません。しかし、リポジトリをまたぐ正しさは、各コンポーネントを実際に組み合わせて確認しなければ保証できません。3 つのテストスイートがそれぞれ単独で通ったとしても、クライアント、SDK、サーバーが同じ仕様に合意している証明にはならないためです。

## 3. エージェント間でレビューと修正のループを回す

パッチができたら、レビュー担当に正確な対象を指定します。レビュー中にもブランチが進む可能性があるため、リポジトリ、ベースコミット、確認対象のコミットを含めて伝えてください。

コーディネーターにそのやり取りを段取りさせるには、次のように指示します。

```text
Codex セッションに Kimi セッションのパッチをレビューさせてください。
まず、リポジトリ、ベースコミット、現在の head コミットを特定してください。
レビュー担当はファイルを編集せずに diff を確認し、可能であればファイル位置や
再現手順を含めた具体的な対応可能な指摘事項を実装セッションへ送ってください。

実装担当のエージェントには、それらの指摘を修正し、新しいコミットと
検証結果を返信させてください。その後、更新されたコミットをレビュー担当に確認させてください。

対応すべき指摘事項がなくなるか、レビューと修正を 2 ラウンド終えたら停止してください。
意見の相違やブロッカーがある場合は私に差し戻してください。
レビューしたコミットと未検証のまま残っている事項を要約してください。
```

また、「指摘事項を実装セッションに送り、対応を依頼してください」や「レビューセッションに最新のコミットを確認してもらってください」のように、エージェントから別の既存セッションへ直接連絡させることもできます。指示を書く際は、[セッションメンション](/ja/docs/mention/)を使って対象の会話を指定してください。

やり取りは双方向で行えます。実装エージェントがレビュー担当に指摘の意図を確認したり、レビュー担当が不足している再現手順を求めたりすることも可能です。どちらの会話も自分で開いてコンテキストを補足したり、指示を変更したりできます。

この例のラウンド上限は、あなたが与える指示の一部です。エージェント同士に意見の対立を延々と解決させようとするのではなく、未解決の作業を人間に戻す区切りを設ける役割があります。エージェントが「指摘事項なし」と報告することは有益な根拠になりますが、それでも diff と検証結果はご自身で確認する価値があります。

## 別の会話をメンションして作業をつなぐ

Lody の会話で `@` を入力して別の会話を選択すると、メッセージ内でその会話を参照できます。
そのうえで、現在のエージェントにそのセッションへ連絡させたり、調査結果をキャッチアップさせたり、新しいタスクを割り当てたりできます。これにより、チャット間でメッセージをコピーしなくても、エージェント同士が必要なコンテキストを直接交換できるようになります。

たとえば、`@` で SDK 調査用の会話を選択し、次のように依頼します。

```text
メンションしたセッションに、リクエストのリトライについて分かったことを尋ねてください。
こちら（クライアント側）の調査結果を送り、リクエスト識別子の仕様について合意したうえで、
その合意内容をもとに実装計画を更新してください。
```

あるいは、レビュー用の会話をメンションし、実装エージェントに最新のコミットと検証結果をそこへ送って再確認を依頼することもできます。メンションによって対象の会話を特定し、あなたの指示によって何を依頼・送信するかを伝えます。エージェントは各自の会話を独立して保ちながら、メッセージと参照可能なセッション履歴を通じて関連コンテキストをやり取りします。

## 複数のマシンとエージェントをまたいで連携する

連携に参加するセッションは、Lody に接続された別々のマシン上で実行できます。たとえば、ノート PC 上のプライマリエージェントが、ワークステーション上で SDK を作業している Kimi セッションと、リモート開発マシン上でサーバーを調査している Codex セッションを調整できます。

| マシン                 | エージェント           | 作業内容                                 |
| ---------------------- | ---------------------- | ---------------------------------------- |
| ノート PC              | プライマリエージェント | 調査の調整と結果の収集                   |
| ワークステーション     | Kimi                   | SDK の調査と修正                         |
| リモート開発マシン     | Codex                  | サーバーの調査と共通仕様のレビュー       |

1 台のマシン上のセッション同士と同様に、セッションメンションとメッセージを使って作業を連携させます。各エージェントは、それぞれの実行マシン上にあるリポジトリのチェックアウト、ツール、ランタイムを使用します。対象マシンがオンラインであり、必要なワークスペースへのアクセス権と互換性のあるエージェント設定が揃っている必要があります。

メッセージでは、調査結果、インターフェースに関する決定事項、コミット参照、レビュー依頼などをやり取りできます。変更を組み合わせてテストするには、結合チェックを行うマシンから該当するコミットや成果物を参照できるようにしてください。会話コンテキストをやり取りしても、未コミットのファイル自体は転送されません。

## 引き継ぎ情報を具体的に保つ

別々のセッションで作業するエージェントは、それぞれ独自の会話履歴を持っています。次のタスクに必要な情報は明示的に伝えてください。

- **実装前：** リポジトリ、Issue、作業範囲、期待される動作、関連するインターフェースの決定事項。
- **レビュー前：** ベースコミットと head コミット、パッチが対処している問題、すでに実行したチェック。
- **修正後：** 新しいコミット、対応した指摘事項、残っている制限事項。

こうした引き継ぎ情報は、人間がワークフローを把握するうえでも役立ちます。Lody では、[会話の横で diff を確認](/ja/docs/diff-viewer/)したり、作業を引き継ぐ必要があるチームメンバーに[セッションを共有](/ja/docs/session-handoff/)したりできます。チームによるアクセスは、マシンおよびプロジェクトの共有権限に従います。

## 1 つの Issue と 2 つのエージェントから始める

まずはご自身が内容を把握している Issue を 1 つ選びましょう。プライマリエージェントにそれを確認させ、範囲を絞った修正を Kimi または Codex に委任します。そこに別のレビュー用セッションを追加し、2 つのエージェントに指摘や調査結果をやり取りさせて、生成されたパッチをご自身で確認してみてください。

そのワークフローが有効だと感じたら、キュー全体や複数リポジトリにまたがるバグへと広げていきましょう。セッションの作成、メッセージの送信、進捗の確認、フォローアップという同じ操作で、どのケースにも対応できます。

[Lody を始める](/ja/docs/quickstart/)から環境を整え、[エージェントセッション制御](/ja/docs/session-orchestration/)を使って最初のタスクを組み立ててみましょう。

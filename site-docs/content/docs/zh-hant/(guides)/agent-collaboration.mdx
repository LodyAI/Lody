你手邊有一批待處理的 Issue 佇列、數個開啟中的 PR，還有一個可能涉及三個儲存庫的 bug。你希望由一個主 Agent 逐一梳理這些項目、將修復任務分派給 Kimi、請 Codex 進行審查，最後將結果彙整回來。

在 Lody 中，你可以從單一對話中統籌這整套工作。Coding Agent 可以建立其他工作階段、向它們發送指令、查看進度並持續追蹤。Agent 之間也能彼此傳送訊息：審查者可以將審查發現發送給負責實作修復的 Agent，而實作 Agent 在 patch 準備好後，也能再次請求審查。

本指南將說明如何**讓主 Agent 擔任工作流程的協調者（orchestrator）**。文中的範例皆為可依據你實際儲存庫調整的示範 prompt，並非基準測試結果或實際正式環境的執行紀錄。

## 協調者的職責

協調者負責掌握整體任務進度：哪些事項需要處理、哪些變更彼此相依、各部分由誰負責，以及還有哪些項目需要驗證。其他 Agent 則會在各自的對話中專注執行被指派的任務。

以下是一種可行的分工方式：

| 對話 | 分派任務 | 回傳內容 |
| ---- | -------- | -------- |
| 主 Agent | 檢視 Issue 與 PR 佇列、指派工作並追蹤進度 | 目前狀態、相依關係與待決事項 |
| Kimi | 實作範圍明確的修復 | patch、commit 與驗證結果 |
| Codex | 審查該 patch | 對應受審 commit 的審查發現 |
| Grok | 調查另一個受影響的儲存庫 | 調查結果與介面變更建議 |

這些角色配置是針對此任務的選擇。你可以互換角色、同時使用多個相同 Agent 的實例，或將其他相容的 Agent 加入工作區。只要在指派時指定，Grok 同樣可以實作修復、審查 patch，或協調其他工作階段。

Lody 提供了用來組織這類工作的[跨工作階段工具](/zh-hant/docs/session-orchestration/)。本指南透過這些工具跨主 Agent、Kimi、Codex 與 Grok 工作階段進行協作，而不依賴任何 Agent 本身的原生團隊功能。

## 設定工作區

請先[將機器連線至 Lody](/zh-hant/docs/quickstart/)，並確認你要使用的 [Agent 設定](/zh-hant/docs/quickstart)在該機器上皆可使用。目標機器必須保持線上狀態，且各個 Agent 需具備存取相關儲存庫及執行任務所需 GitHub 工具的權限。

以下範例由主 Agent 負責協調，並由 Kimi、Codex 或 Grok 負責執行具體任務。
先啟動一個主 Agent 工作階段來負責協調，告訴它需要檢視哪些儲存庫、PR 或 Issue。為需要編輯程式碼的任務分配各自的 [Git worktree](/zh-hant/docs/worktrees/)，讓平行運作的 Agent 擁有獨立的工作目錄。從分支建立的新 worktree 會以已提交的 `HEAD` 為起點；其他目錄中尚未提交的變更不會自動出現在該處。

在動手修改程式碼之前，第一項實用的任務是先釐清整個待辦佇列。

## 1. 讓主 Agent 梳理並分類 PR 與 Issue

待辦佇列中常會出現重疊的工作：某個 Issue 可能已經有對應的 PR、兩個 PR 可能在解決同一個問題，或者 SDK 的變更必須先合併，用戶端更新才能接續進行。先請協調者找出這些關聯性。

```text
使用 Lody 工作階段工具來協調這項工作。

檢視這些 PR 與 Issue：[貼上連結]。
針對每個項目，找出受影響的儲存庫、目前狀態、既有的實作進度，
以及與其他項目的相依關係。

接著，將可獨立執行的修復分派給 Kimi 工作階段，並將審查分派給 Codex 工作階段。
為每個編輯任務建立獨立的 worktree。在每項指派中寫明對應的 Issue、範圍、
預期行為與驗證要求。若已有工作階段正在負責某項工作，請重複使用該工作階段。

帶回所有工作階段連結、調查發現，以及任何需要我做決定的事項。
合併與部署請保留給我審查。
```

好的任務指派必須足夠具體，讓接收任務的 Agent 無需重新釐清整個佇列就能直接開始工作。例如：「修復用戶端重複送出的問題；保留既有的重試行為；重現該 bug 並驗證 patch。」請一併附上相關的 Issue 與儲存庫，不要假設其他工作階段知道「那個 bug」指的是什麼。

協調者也應區分「任務已完成」與「變更已就緒」。一個 patch 可能已經寫完，但審查、前置相依項目或整合檢查可能仍在等待中。

## 2. 協調跨儲存庫的修復

以一個示範性的 bug 為例：重試請求可能會建立兩筆相同的紀錄。用戶端負責發起重試，SDK 負責組裝請求，而伺服器端則負責判斷該請求是否已經處理過。

你可以同時在每個儲存庫啟動調查。在動手實作之前，先讓各個 Agent 比對調查結果，並針對跨儲存庫邊界的行為達成共識。

```text
跨這些儲存庫調查請求重試後產生重複紀錄的問題：
[用戶端儲存庫]、[SDK 儲存庫]、[伺服器端儲存庫]。

指派一個 Kimi 工作階段負責用戶端、一個 Codex 工作階段負責 SDK，以及一個 Grok
工作階段負責伺服器端。請這些 Agent 彼此交流重試發起的來源，
以及各層目前如何處理重複請求的調查發現。
在進行有相依關係的變更前，先讓它們就請求契約達成一致。

平行實作可獨立進行的部分。每個 Agent 都應回報其 commit、
執行的檢查項目，以及對其他儲存庫變更的相依關係。

彙整所有結果，並安排使用更新後元件一起進行整合檢查。
回報所需的合併順序與仍未補齊的驗證缺口。
```

需要溝通確認的關鍵可能只是個小細節：究竟是由用戶端還是 SDK 產生請求識別碼，以及重試時是否會保留同一個識別碼。將這項決定傳達給其他工作階段，能確保各方的實作保持一致。

獨立的 worktree 能隔離檔案編輯。然而跨儲存庫的正確性仍取決於將各元件放在一起驗證。三個儲存庫各自的測試套件都通過，本身並不足以證明用戶端、SDK 與伺服器端遵循的是同一套契約。

## 3. 在 Agent 之間執行審查與修復循環

當 patch 產出後，請提供給審查者一個精確的目標。由於審查期間分支可能持續推進，因此務必包含儲存庫、基準點與待檢視的 commit。

你可以請協調者安排這次交流：

```text
請一個 Codex 工作階段審查 Kimi 工作階段的 patch。
先確認儲存庫、基準 commit 與目前的 head commit。
審查者應以唯讀方式檢視 diff（不進行任何編輯），並將可執行的審查意見
發送給實作工作階段，盡可能附上檔案位置與重現方式。

請實作 Agent 修復這些意見指出的問題，並回覆新的 commit 與驗證結果。
接著讓審查者檢視該更新後的 commit。

當沒有剩餘的可執行審查意見，或完成兩輪審查與修復後即停止。
若出現意見分歧或阻礙，請帶回給我處理。
摘要說明已審查的 commit 以及任何仍未驗證的項目。
```

你也可以直接指示某個 Agent 聯繫另一個既有的工作階段：「將你的審查發現發送給實作工作階段並請它處理」，或「請審查工作階段檢查你最新的 commit」。撰寫指令時，可使用[工作階段提及](/zh-hant/docs/mention/)來指定目標對話。

雙方的交流是雙向的。實作 Agent 可以請審查者釐清某項審查意見；審查者也可以要求補充缺少的重現步驟。你可以隨時開啟任一方的對話來補充上下文或調整指派內容。

此範例中的輪數上限是你所下達指令的一部分，它能在 Agent 陷入重複爭論時，提供一個將未解決工作交回給你的節點。Agent 回報「未發現問題」雖是實用的參考依據，但實際的 diff 與驗證結果仍值得你親自檢視。

## 提及另一個對話以串聯工作

在 Lody 對話中輸入 `@` 並選取另一則對話，即可在你的訊息中引用它。
接著你可以請目前的 Agent 聯繫該工作階段、同步它的調查發現，或交付新的任務。
這讓 Agent 之間能直接交換所需的上下文，省去你在不同聊天視窗間來回複製訊息的麻煩。

例如，透過 `@` 選取負責 SDK 調查的對話，然後要求：

```text
詢問提及的工作階段針對請求重試有何發現。
將我們用戶端這邊的調查結果發送給它，就請求識別碼的行為達成共識，
並運用該共識來更新我們的實作計畫。
```

或者提及審查對話，請實作 Agent 將其最新的 commit 與驗證結果發送過去進行再次檢查。
「提及」負責標定目標對話，而你的指令則說明要請求或傳送哪些資訊。
Agent 會在保留各自獨立對話的同時，透過訊息與可存取的工作階段歷史記錄來交換相關上下文。

## 跨機器與跨 Agent 協作

參與協作的工作階段可以執行在連接至 Lody 的不同機器上。例如，筆電上的主 Agent 可以同時協調工作站上負責 SDK 的 Kimi 工作階段，以及遠端開發機器上調查伺服器端的 Codex 工作階段。

| 機器 | Agent | 工作內容 |
| ---- | ----- | -------- |
| 筆電 | 主 Agent | 協調調查並彙整結果 |
| 工作站 | Kimi | 調查並修復 SDK |
| 遠端開發機器 | Codex | 調查伺服器端並審查共用契約 |

就像在同一台機器上運作一樣，使用工作階段提及與訊息來串聯它們的工作。
每個 Agent 都會使用其執行機器上的儲存庫複本、工具與執行環境。
目標機器必須保持線上狀態，且具備必要的工作區存取權限與相容的 Agent 設定。

訊息可以傳遞調查發現、介面決定、commit 參照與審查請求。
若要將變更放在一起測試，請務必讓執行整合檢查的機器能取得對應的 commit 或構建產物；
交換對話上下文並不會傳輸尚未提交的檔案。

## 保持交接資訊具體明確

在不同工作階段中運作的 Agent 各自擁有獨立的對話歷史。請明確傳送下一個任務所需的資訊：

- **實作前：** 儲存庫、Issue、任務範圍、預期行為，以及相關的介面決定。
- **審查前：** 基準 commit 與 head commit、該 patch 所解決的問題，以及已執行的檢查。
- **修復後：** 新的 commit、它解決了哪些審查意見，以及任何仍存在的限制。

這些交接資訊也能讓團隊成員更容易追蹤工作進度。在 Lody 中，你可以[在對話旁檢視 diff](/zh-hant/docs/diff-viewer/)，也可以[將工作階段分享給需要接手工作的團隊成員](/zh-hant/docs/session-handoff/)。團隊存取權限則遵循機器與專案的共享權限設定。

## 從一個 Issue 與兩個 Agent 開始

先挑選一個你熟悉的 Issue，讓主 Agent 進行檢視，並將範圍明確的修復任務分派給 Kimi 或 Codex。接著新增一個獨立的審查工作階段，請兩個 Agent 互相交流審查與調查發現，最後再由你自己檢視產出的 patch。

當這套工作流程運作順暢後，就可以進一步擴展到整個待辦佇列，或是跨多個儲存庫的 bug。建立工作階段、發送訊息、檢視進度與後續追蹤——這些相同的操作就能支援上述每一種情境。

立即[開始使用 Lody](/zh-hant/docs/quickstart/)，並透過 [Agent 工作階段控制](/zh-hant/docs/session-orchestration/)來組織你的第一項指派任務。

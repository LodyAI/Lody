처리해야 할 이슈 대기열과 열려 있는 여러 개의 PR, 그리고 세 개의 리포지토리가 얽혀 있을지 모르는 버그가 있다고 가정해 보겠습니다. 메인 에이전트가 대기열을 차례로 처리하면서 수정 작업은 Kimi에 위임하고, Codex에게 리뷰를 요청한 뒤 결과를 취합해 오기를 원할 수 있습니다.

Lody에서는 이러한 작업을 하나의 대화 안에서 체계적으로 구성할 수 있습니다. 코딩 에이전트는 다른 세션을 생성하고, 지시 사항을 전달하며, 진행 상황을 확인하고 후속 조치를 취할 수 있습니다. 또한 에이전트끼리 직접 메시지를 주고받는 것도 가능합니다. 리뷰를 담당하는 에이전트가 수정을 작성하는 에이전트에게 리뷰 의견을 보내고, 수정 에이전트는 패치가 준비되면 다시 리뷰를 요청할 수 있습니다.

이 가이드에서는 이러한 워크플로에서 **메인 에이전트를 오케스트레이터로 활용**하는 방법을 설명합니다. 여기에 나온 예시는 여러분의 리포지토리에 맞게 변형해 사용할 수 있는 참고용 프롬프트이며, 벤치마크 결과나 실제 프로덕션 실행 기록은 아닙니다.

<Callout title="어떤 페이지를 보면 될까요?">

  세션 제어](/ko/docs/session-orchestration)를, 직접 여러 작업을 동시에 시작하는 방법은 [병렬 코딩
  에이전트](/ko/docs/parallel-agents)를 참고하세요.
</Callout>

## 오케스트레이터의 역할

오케스트레이터는 전체 작업을 총괄적으로 추적합니다. 어떤 항목에 주의가 필요한지, 변경 사항 간에 어떤 의존성이 있는지, 각 파트를 누가 담당하고 있는지, 아직 검증이 남은 부분은 무엇인지 파악합니다. 나머지 에이전트들은 각자의 대화에서 범위가 정해진 집중 작업을 수행합니다.

가능한 작업 분담 예시는 다음과 같습니다.

| 대화          | 담당 작업                                    | 반환 결과                             |
| ------------- | -------------------------------------------- | ------------------------------------- |
| 메인 에이전트 | 이슈 및 PR 대기열 확인, 작업 할당, 후속 조치 | 현재 상태, 의존성, 미결 의사결정 사항 |
| Kimi          | 범위가 지정된 수정 구현                      | 패치, 커밋, 검증 결과                 |
| Codex         | 해당 패치 리뷰                               | 리뷰한 커밋과 연결된 리뷰 의견        |
| Grok          | 영향을 받는 다른 리포지토리 조사             | 조사 결과 및 인터페이스 변경 제안     |

이러한 역할 배치는 이 작업에 맞춘 선택일 뿐입니다. 역할을 바꾸거나, 같은 에이전트의 인스턴스를 여러 개 사용하거나, 호환되는 다른 에이전트를 워크스페이스에 추가할 수도 있습니다. Grok 역시 해당 작업에 지정되면 수정을 구현하거나 패치를 리뷰하고 다른 세션을 조율할 수 있습니다.

Lody는 이러한 작업을 구성할 수 있는 [세션 간 도구](/ko/docs/session-orchestration/)를 제공합니다. 이 가이드는 메인 에이전트, Kimi, Codex, Grok 세션 전반에서 해당 도구를 활용하며, 특정 에이전트의 자체 팀 기능에 의존하지 않습니다.

## 워크스페이스 설정하기

[머신을 Lody에 연결](/ko/docs/quickstart/)하고 사용하려는 [에이전트 설정](/ko/docs/quickstart)이 해당 머신에서 사용 가능한지 확인하세요. 대상 머신은 온라인 상태여야 하며, 에이전트는 작업에 필요한 리포지토리와 GitHub 도구에 접근할 수 있어야 합니다.

아래 예시에서는 조율에 메인 에이전트를 사용하고, 집중 작업에는 Kimi, Codex 또는 Grok을 사용합니다.
조율을 담당할 메인 에이전트 세션을 시작하세요. 어떤 리포지토리, PR 또는 이슈를 살펴볼지 알려줍니다. 코드를 수정하는 작업에는 병렬 에이전트가 서로 독립된 작업 디렉터리를 사용할 수 있도록 각자 전용 [Git 워크트리](/ko/docs/worktrees/)를 할당하세요. 새 워크트리 분기는 커밋된 `HEAD`에서 시작되므로, 다른 디렉터리의 커밋되지 않은 변경 사항은 자동으로 반영되지 않습니다.

코드를 수정하기 전에 먼저 대기열의 전체 상황을 파악하도록 지시하는 것이 좋습니다.

## 1. 메인 에이전트에게 PR과 이슈 분류 맡기기

대기열에는 서로 겹치는 작업이 포함되어 있는 경우가 많습니다. 어떤 이슈에 이미 PR이 열려 있거나, 두 개의 PR이 같은 문제를 해결하고 있거나, 클라이언트 업데이트 전에 SDK 변경 사항이 먼저 병합되어야 할 수 있습니다. 먼저 조율 에이전트에게 이러한 관계를 파악하도록 요청하세요.

```text
Lody 세션 도구를 사용해 이 작업을 조율해 주세요.

다음 PR과 이슈를 확인해 주세요: [링크 붙여넣기].
각 항목에 대해 영향을 받는 리포지토리, 현재 상태,
기존 구현 작업 여부, 다른 항목과의 의존성을 파악해 주세요.

그런 다음 독립적으로 진행할 수 있는 수정 작업은 Kimi 세션에,
리뷰는 Codex 세션에 위임해 주세요. 각 편집 작업에는 별도의 워크트리를 할당하세요.
각 작업 할당 시 관련 이슈, 작업 범위, 예상 동작, 검증 요구 사항을 포함해 주세요.
이미 해당 작업을 맡고 있는 기존 세션이 있다면 그 세션을 재사용하세요.

세션 링크, 조사 결과, 그리고 제 결정이 필요한 사항을 정리해 가져와 주세요.
병합과 배포는 제가 검토한 뒤 진행할 수 있도록 남겨 두세요.
```

좋은 작업 할당은 전달받은 에이전트가 전체 대기열을 처음부터 다시 파악하지 않고도 바로 작업할 수 있을 만큼 구체적입니다. 예를 들어 "클라이언트의 중복 제출 문제를 수정하세요. 기존 재시도 동작은 유지하세요. 버그를 재현하고 패치를 검증하세요."처럼 작성합니다. 다른 세션이 "그 버그"가 무엇을 뜻하는지 알 거라고 가정하지 말고, 관련 이슈와 리포지토리를 함께 포함하세요.

조율 에이전트는 단순히 작업이 끝난 상태와 변경 사항이 준비된 상태를 구분해야 합니다. 패치 작성은 완료되었더라도 리뷰, 선행 의존성 또는 통합 확인이 아직 남아 있을 수 있습니다.

## 2. 여러 리포지토리에 걸친 수정 조율하기

예를 들어 요청을 재시도할 때 동일한 레코드가 두 번 생성되는 버그가 있다고 가정해 보겠습니다. 클라이언트가 재시도를 시작하고, SDK가 요청을 구성하며, 서버가 해당 요청이 이미 처리되었는지 판단합니다.

각 리포지토리에서 동시에 조사를 시작할 수 있습니다. 구현에 들어가기 전에 에이전트들이 조사 결과를 비교하고 리포지토리 경계를 넘나드는 동작에 합의하도록 하세요.

```text
요청 재시도 후 중복 레코드가 생성되는 문제를 다음 리포지토리들에서 조사해 주세요:
[클라이언트 리포지토리], [SDK 리포지토리], [서버 리포지토리].

클라이언트는 Kimi 세션에, SDK는 Codex 세션에, 서버는 Grok 세션에 할당해 주세요.
재시도가 어디서 시작되고 중복 요청이 어떻게 처리되는지에 대해
에이전트들이 조사 결과를 서로 공유하도록 하세요.
의존성이 있는 변경을 하기 전에 요청 계약(contract)에 합의하도록 하세요.

독립적인 부분은 병렬로 구현하세요. 각 에이전트는 자신의 커밋,
실행한 검사, 그리고 다른 리포지토리의 변경 사항에 대한 의존성을 보고해야 합니다.

결과를 취합해 업데이트된 컴포넌트들을 함께 사용하는 통합 확인을 진행해 주세요.
필요한 병합 순서와 아직 검증되지 않은 부분을 보고해 주세요.
```

핵심적인 협의 내용은 사소한 세부 사항일 수 있습니다. 예를 들어 클라이언트와 SDK 중 어느 쪽이 요청 식별자를 생성하는지, 그리고 재시도 시 해당 식별자를 유지하는지 여부입니다. 이 결정을 다른 세션에도 전달하면 각 구현이 어긋나지 않고 일관성을 유지할 수 있습니다.

워크트리를 분리하면 파일 편집 충돌은 막을 수 있지만, 여러 리포지토리에 걸친 정확성은 결국 컴포넌트를 함께 테스트해야 확인할 수 있습니다. 세 개의 테스트 스위트가 각자 통과하더라도 클라이언트, SDK, 서버가 동일한 계약에 맞게 동작한다는 사실까지 자동으로 보장되지는 않습니다.

## 3. 에이전트 간 리뷰 및 수정 루프 실행하기

패치가 만들어지면 리뷰어에게 정확한 대상을 지정해 주세요. 리뷰가 진행되는 동안에도 브랜치가 바뀔 수 있으므로 리포지토리, 기준(base) 커밋, 확인할 커밋을 함께 전달해야 합니다.

조율 에이전트에게 이 교환 과정을 다음과 같이 진행하도록 요청할 수 있습니다.

```text
Codex 세션에 Kimi 세션의 패치를 리뷰해 달라고 요청해 주세요.
먼저 리포지토리, 기준 커밋, 현재 head 커밋을 확인하세요.
리뷰어는 파일을 수정하지 않고 diff만 검토한 뒤, 가능하면 파일 위치와
재현 방법을 포함해 조치 가능한 리뷰 의견을 구현 세션으로 보내야 합니다.

구현 에이전트에게는 해당 의견을 반영해 수정하고 새 커밋과
검증 결과를 회신하도록 요청하세요. 그런 다음 리뷰어가 업데이트된 커밋을 다시 확인하게 하세요.

조치할 리뷰 의견이 더 이상 없거나 리뷰/수정 라운드를 두 번 진행하면 중단하세요.
의견 충돌이나 진행을 막는 문제가 있으면 제게 다시 가져와 주세요.
리뷰한 커밋과 아직 검증되지 않은 사항을 요약해 주세요.
```

에이전트에게 다른 기존 세션에 직접 연락하도록 지시할 수도 있습니다. 예를 들어 "조사 결과를 구현 세션에 보내 해결을 요청하세요" 또는 "리뷰 세션에 최신 커밋을 확인해 달라고 요청하세요"처럼 말하면 됩니다. 지시 사항을 작성할 때는 [세션 멘션](/ko/docs/mention/)을 사용해 대화를 지정하세요.

대화 교환은 양방향으로 이루어질 수 있습니다. 구현 에이전트가 리뷰어에게 의견의 의미를 명확히 묻거나, 리뷰어가 빠진 재현 방법을 요청할 수도 있습니다. 여러분이 직접 두 대화 중 어느 쪽이든 열어 맥락을 추가하거나 작업을 변경할 수도 있습니다.

이 예시의 라운드 제한은 사용자가 주는 지시 사항의 일부입니다. 에이전트들에게 의견 차이를 끝없이 해결하라고 반복 요청하는 대신, 해결되지 않은 작업을 사용자에게 돌려보낼 시점을 정해 두는 역할을 합니다. 에이전트가 이상 없음(no findings)을 보고하는 것도 유용한 근거가 되지만, diff와 검증 결과는 여전히 직접 확인하는 것이 좋습니다.

## 다른 대화를 멘션하여 작업 연결하기

Lody 대화에서 `@`를 입력하고 다른 대화를 선택하면 메시지에서 해당 대화를 참조할 수 있습니다.
그런 다음 현재 에이전트에게 그 세션에 연락하거나, 조사 결과를 공유받거나, 새 작업을 할당하도록 요청할 수 있습니다. 이렇게 하면 채팅창 사이를 오가며 메시지를 복사해 붙여넣지 않아도 에이전트들이 필요한 맥락을 직접 주고받을 수 있습니다.

예를 들어 `@`로 SDK 조사 대화를 선택한 뒤 다음과 같이 요청해 보세요.

```text
멘션한 세션에 요청 재시도에 대해 파악한 내용을 물어봐 주세요.
우리의 클라이언트 측 조사 결과를 전달하고, 요청 식별자 동작에 합의한 뒤,
그 합의 내용을 바탕으로 우리의 구현 계획을 업데이트해 주세요.
```

또는 리뷰 대화를 멘션하고 구현 에이전트에게 최신 커밋과 검증 결과를 그쪽으로 보내 재검토를 요청하게 할 수도 있습니다. 멘션은 대상 대화를 지정하고, 여러분의 지시문은 에이전트가 어떤 정보를 요청하거나 전달할지 알려 줍니다. 에이전트들은 각자의 대화를 유지한 채 메시지와 접근 가능한 세션 기록을 통해 관련 맥락을 교환합니다.

## 여러 머신과 에이전트에 걸쳐 협업하기

참여하는 세션들은 Lody에 연결된 서로 다른 머신에서 실행될 수 있습니다. 예를 들어 노트북의 메인 에이전트가 워크스테이션에서 SDK를 작업하는 Kimi 세션과 원격 개발 머신에서 서버를 조사하는 Codex 세션을 조율할 수 있습니다.

| 머신           | 에이전트      | 작업                        |
| -------------- | ------------- | --------------------------- |
| 노트북         | 메인 에이전트 | 조사 조율 및 결과 취합      |
| 워크스테이션   | Kimi          | SDK 조사 및 수정            |
| 원격 개발 머신 | Codex         | 서버 조사 및 공통 계약 리뷰 |

한 머신에서 세션을 다룰 때와 마찬가지로 세션 멘션과 메시지를 사용해 작업을 연결할 수 있습니다. 각 에이전트는 자신이 실행되는 머신에 있는 리포지토리 체크아웃, 도구, 런타임을 사용합니다. 대상 머신은 온라인 상태여야 하며, 필요한 워크스페이스 접근 권한과 호환되는 에이전트 설정을 갖추고 있어야 합니다.

메시지로는 조사 결과, 인터페이스 결정 사항, 커밋 참조, 리뷰 요청 등을 전달할 수 있습니다. 변경 사항을 함께 테스트하려면 해당 커밋이나 아티팩트를 통합 확인을 수행하는 머신에서 사용할 수 있도록 해야 합니다. 대화 맥락을 교환하더라도 커밋되지 않은 파일은 전송되지 않습니다.

## 작업 인계 내용은 구체적으로 작성하기

별도의 세션에서 작업하는 에이전트들은 각자의 대화 기록을 가지고 있습니다. 다음 작업에 필요한 정보는 명시적으로 전달하세요.

- **구현 전:** 리포지토리, 이슈, 작업 범위, 예상 동작, 관련 인터페이스 결정 사항.
- **리뷰 전:** 기준 커밋과 head 커밋, 패치가 해결하는 문제, 이미 실행한 검사.
- **수정 후:** 새 커밋, 반영된 리뷰 의견, 남아 있는 제한 사항.

이러한 인계 정보는 사람도 워크플로를 쉽게 따라갈 수 있게 해 줍니다. Lody에서는 [대화 옆에서 diff를 확인](/ko/docs/diff-viewer/)하고, 작업을 이어받아야 하는 팀원에게 [세션을 공유](/ko/docs/session-handoff/)할 수 있습니다. 팀 접근 권한은 머신 및 프로젝트 공유 권한을 따릅니다.

## 하나의 이슈와 두 개의 에이전트로 시작하기

먼저 내용을 잘 알고 있는 이슈 하나를 선택해 보세요. 메인 에이전트에게 이슈를 확인하게 한 뒤, 범위가 명확한 수정을 Kimi나 Codex에 위임하세요. 별도의 리뷰 세션을 추가해 두 에이전트가 결과를 주고받도록 하고, 생성된 패치를 직접 확인해 보세요.

이 워크플로가 유용하다는 것을 확인했다면 대기열 전체나 여러 리포지토리에 걸친 버그로 확장해 보세요. 세션 생성, 메시지 전송, 진행 상황 확인, 후속 조치라는 동일한 작업 방식으로 각 사례를 모두 처리할 수 있습니다.

[Lody 시작하기](/ko/docs/quickstart/)에서 환경을 준비하고, [에이전트 세션 제어](/ko/docs/session-orchestration/)를 활용해 첫 번째 작업을 구성해 보세요.

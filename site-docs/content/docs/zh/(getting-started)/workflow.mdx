# 工作流推荐

Lody 当前是采用 [GitHub 集成](/zh/docs/github) 和 [worktree](/zh/docs/worktrees) 作为基本的核心功能，所以推荐用户以此作为基本的工作流。

进行实践之前，请先完成 Lody 的[配置](/zh/docs/quickstart)。

## 需求划分

由于 Agent 的最大上下文限制，一般来说 vibe coding 开发多个并行的小功能的效果将优于一个复杂的大功能。当你进行开发之前请思考清楚原子功能划分，这样我们就可以利用到 worktree 的天然文件隔离的好处，进行并行地功能开发，从而节省开发时间和减少等待时间。

## 并行开发

划分好功能或修复需求之后，我们可以直接将一个功能或修复需求在主页对话框中描述给 Lody，当前的工作流的原则就是每个对话将对应一个功能或修复，也就是对应一个 PR。你可以启动任意数量的并行对话，这取决你的机器性能和你的上下文切换的疲惫程度。隔离 Worktree、混用 Agent、以及团队可见性，见[并行 Coding Agents](/zh/docs/parallel-agents)。

Lody 结束一轮对话之后会发送[推送](/zh/docs/notification)，点击推送将会跳转到对应会话，如果你对编码很熟悉，你可以直接点击下方的文件变更来确认结果。如果你不熟悉代码，你可以点击左侧 sidebar 对应会话下方的分支名进行复制。在你习惯的开发环境中切换到对应分支进行端到端的测试。

基本通过之后可以点击对话上方的创建 PR 按钮，Lody 将自动创建PR，描述完整的需求和实现方案。并且将对应的 PR 与当前的对话关联。你可以直接点击上方关联后的 PR 按钮跳转到 GitHub 的 PR 界面。

## AI Review 循环

如果你使用 Claude Code、Codex 或是 Devin 等，并将其关联到仓库中，他们将会对每个 PR 进行详细的 Review。收到对应的 Review 结果之后你可以直接在 Lody 中对话例如 `拉取PR评论，分析其正确性，正确就修复并且设为 resolved，否则评论理由`。 Lody 将自动拉取 PR 的所有评论，进行判断和修复，然后 push 修复 commit。这将被动触发（或者你手动 @ 触发）下一轮的 AI Review，循环直到没有明显的错误。

## 归档已完成的会话

当 PR 被合并，这意味着当前会话已经完成了它的职责，除非是又发现相关的 bug，否则我们不建议当前会话再继续进行其他功能的开发。你可以在 sidebar 中点击会话的[归档按钮](/zh/docs/session#归档会话)，将会话从列表中移除。

你也可以在 **设置**-**通用** 中开启自动归档，让已关联 PR 的会话在 PR merged 或 closed 后自动进入归档列表。

## 定期彻底删除会话

归档会移除会话的 worktree 工作目录，但对话历史和会话分支仍保留在 CLI 机器上。如需一并回收这部分空间，请定期在归档界面中彻底[删除会话](/zh/docs/session#删除会话)。

## 非 GitHub 项目

以上工作流最适合托管在 GitHub 的项目。对于非 GitHub 项目，可以将目录添加为[本地工作目录](/zh/docs/local-project)。本地项目仍支持对话、文件列表、diff 审阅、移动端访问和 Lody Preview，但不包含 GitHub PR 与 CI 自动化能力。

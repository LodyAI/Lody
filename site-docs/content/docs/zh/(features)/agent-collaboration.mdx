你手上有一批 Issue、几个待处理的 PR，还有一个可能涉及三个仓库的 bug。你希望 Claude Code 先过一遍这些工作，把修复交给 Kimi，让 Codex 审查，再把结果汇总回来。

在 Lody 中，你可以从一条对话组织这项工作。Coding Agent 能创建其他会话、发送指令、查看进度并跟进。Agent 之间也能互发消息：审查者可以把问题发给负责实现的 Agent，实现者修好后再请它检查。

这篇文章介绍如何让 **Claude Code 担任 orchestrator，统筹其他 Agent**。下面的提示词是可按自己仓库调整的示例，不是性能测试结果，也不是某次生产任务的实录。

## 负责统筹的 Agent 做什么

它跟进整体任务：哪些工作需要处理、改动之间有哪些依赖、每一部分由谁负责，以及还有什么需要验证。其他 Agent 则在各自的对话中完成具体分工。

一种分工方式是：

| 对话 | 任务 | 返回什么 |
| --- | --- | --- |
| Claude Code | 梳理 Issue 和 PR、分派工作、跟进结果 | 当前进度、依赖关系和待决定的问题 |
| Kimi | 实现范围明确的修复 | 补丁、提交和验证结果 |
| Codex | 审查补丁 | 对应具体提交的审查意见 |
| Grok | 调查另一个受影响的仓库 | 调查结果和接口修改建议 |

这些角色是针对当前任务的选择。你可以交换分工、使用同一种 Agent 的多个实例，或接入其他兼容的 Agent。Grok 也可以根据分工实现修复、审查补丁，或协调其他会话。

Lody 提供组织这些工作的[跨会话工具](/zh/docs/session-orchestration/)。本文通过这些工具协调 Claude Code、Kimi、Codex 和 Grok 会话，不涉及配置 Claude Code 原生 Agent Teams 功能。

## 准备工作区

先[把机器连接到 Lody](/zh/docs/quickstart/)，确认机器上有需要使用的 [Agent 配置](/zh/docs/agents/)。目标机器需要在线，Agent 需要具备访问目标仓库及执行任务所需 GitHub 工具的权限。

下面以 Claude Code 负责统筹、Kimi、Codex 或 Grok 执行具体任务为例。创建一条 Claude Code 会话负责统筹，告诉它要处理哪些仓库、PR 或 Issue。为修改代码的任务分配独立 [Git worktree](/zh/docs/worktrees/)，让并行 Agent 使用不同的工作目录。Fork 到新 worktree 时从已提交的 `HEAD` 开始，其他目录中的未提交修改不会自动带过去。

第一步可以先让它理解这批工作，再开始修改代码。

## 1. 让 Claude Code 梳理 PR 和 Issue

一批待办中经常存在重叠：某个 Issue 已经有对应 PR，两个 PR 解决的是同一个问题，或者客户端更新必须等 SDK 改动先合并。让负责统筹的 Agent 先找出这些关系。

```text
使用 Lody 会话工具协调这批工作。

检查这些 PR 和 Issue：[粘贴链接]。
对每一项说明受影响的仓库、当前状态、已有实现工作，以及与其他项的依赖关系。

然后将可独立执行的修复分派给 Kimi 会话，将审查分派给 Codex 会话。
每个编辑任务使用独立 worktree。在任务中写清 Issue、范围、预期行为和验证要求。
如果已有会话负责某项工作，优先复用。

汇总会话链接、发现的问题，以及需要我决定的事项。
合并和部署留给我审查。
```

好的分工能让接收任务的 Agent 直接开始工作，无需重新理解整批待办。例如：“修复客户端重复提交的问题，保留已有重试行为，复现 bug 并验证补丁。”同时附上对应的 Issue 和仓库，不要只写“修一下那个 bug”。

负责统筹的 Agent 还应区分“任务执行完毕”和“改动已经就绪”。补丁写完后，可能仍在等待审查、上游依赖或集成验证。

## 2. 协调跨仓库修复

假设遇到一个问题：请求重试后生成了重复记录。客户端发起重试，SDK 组装请求，服务端判断这个请求是否已经处理过。

你可以同时在三个仓库中启动调查。在修改代码前，先让几个 Agent 交流发现，确认跨仓库的行为约定。

```text
调查请求重试后产生重复记录的问题，涉及这些仓库：
[客户端仓库]、[SDK 仓库]、[服务端仓库]。

分别创建 Kimi 会话调查客户端、Codex 会话调查 SDK、Grok 会话调查服务端。
让 Agent 互相交流：
重试从哪里发起，各层目前如何处理重复请求。
先确认请求的接口约定，再修改有依赖关系的部分。

可独立实现的部分并行处理。每个 Agent 汇报提交、执行的检查，
以及对其他仓库改动的依赖。

汇总结果，安排使用更新后组件的集成检查。
说明需要的合并顺序和仍未验证的部分。
```

需要交换的信息可能很小，却会影响全部实现：请求标识由客户端还是 SDK 生成？重试时是否沿用同一个标识？把这些决定发给其他会话，才能让各方实现保持一致。

独立 worktree 可以隔离文件修改。跨仓库的正确性仍需把组件放在一起验证。三个仓库各自的测试通过，并不能单独证明客户端、SDK 和服务端遵守的是同一套约定。

## 3. 让 Agent 进行审查与修复循环

有了补丁后，给审查者一个明确的目标。审查过程中分支可能继续变化，因此需要说明仓库、基准提交和待审提交。

你可以让负责统筹的 Agent 安排这次交流：

```text
让一个 Codex 会话审查 Kimi 会话的补丁。
先确认仓库、基准提交和当前 head 提交。
审查者只读检查 diff，将可执行的意见发给实现会话，
尽量附上文件位置和复现方式。

让实现 Agent 修复这些问题，并回复新的提交和验证结果。
再让审查者检查更新后的提交。

没有剩余的可执行意见时结束，最多进行两轮审查与修复。
如果存在分歧或阻塞，交回给我。
汇总审查过的提交，以及仍未验证的部分。
```

你也可以直接让一个 Agent 联系已有会话：“把你的发现发给实现会话，请它处理”，或者“请审查会话检查你的最新提交”。输入指令时，可以通过[会话 mention](/zh/docs/mention/)明确指向哪一条对话。

消息可以双向流动。实现 Agent 可以请审查者解释某条意见，审查者也可以要求补充复现步骤。你可以打开任意一条会话，补充上下文或调整任务。

示例中的轮数上限属于你给出的指令。遇到未解决的分歧时，它提供了一个交回给人的结束条件。Agent 报告没有发现问题是一项参考，最终仍需查看 diff 和验证结果。

## 在对话里 @ 另一条对话，连接相关工作

在 Lody 对话中输入 `@`，选择另一条对话，就可以在消息中引用它。接着让当前 Agent 联系那个会话，了解已有发现，或给它分派新任务。这样，Agent 可以直接交流、快速同步工作所需的上下文，你不用在几个聊天窗口之间复制消息。

例如，通过 `@` 选中负责 SDK 调查的会话，然后说：

```text
问一下提到的会话，它对请求重试有什么发现。
把我们在客户端的调查结果发给它，确认请求标识的行为约定，
再根据双方确认的结果更新我们的实现计划。
```

也可以 `@` 审查会话，让实现 Agent 把最新提交和验证结果发过去，请对方再检查一次。会话引用明确了联系对象，指令则说明要询问或发送什么。Agent 通过消息和可读取的会话历史交换相关上下文，同时保留各自的对话。

## 跨机器、跨 Agent 协作

参与工作的会话可以运行在连接到 Lody 的不同机器上。例如，笔记本上的 Claude Code 负责统筹，工作站上的 Kimi 处理 SDK，远程开发机器上的 Codex 调查服务端。

| 机器 | Agent | 工作 |
| --- | --- | --- |
| 笔记本 | Claude Code | 统筹调查、汇总结果 |
| 工作站 | Kimi | 调查并修复 SDK |
| 远程开发机器 | Codex | 调查服务端、审查共同的接口约定 |

你可以像在同一台机器上操作一样，通过会话引用和消息连接这些工作。每个 Agent 使用所在执行机器上的仓库、工具和运行环境。目标机器需要在线，并具备必要的工作区访问权限和兼容的 Agent 配置。

消息可以传递调查结果、接口决定、提交信息和审查请求。需要把改动放在一起测试时，再把对应提交或产物提供给执行集成检查的机器；交流对话上下文不会搬运尚未提交的文件。

## 每次交接都带上具体信息

不同会话中的 Agent 有各自的对话历史。下一步需要的信息应该明确发送：

- **实现前：** 仓库、Issue、任务范围、预期行为，以及有关接口的决定。
- **审查前：** 基准提交、待审提交、补丁解决的问题，以及已经执行的检查。
- **修复后：** 新提交、对应解决了哪些意见，以及仍然存在的限制。

这些信息也让人更容易跟进。在 Lody 中，你可以在[对话旁查看 diff](/zh/docs/diff-viewer/)，也可以[把会话共享给同事](/zh/docs/session-handoff/)，由对方继续处理。团队访问遵循机器和项目的共享权限。

## 从一个 Issue 和两个 Agent 开始

选一个你熟悉的问题，让 Claude Code 调查，再将范围明确的修复委派给 Kimi 或 Codex。随后加一条独立审查会话，让两个 Agent 交换意见，最后自己检查补丁。

这套工作方式有用之后，再扩大到一批任务或涉及多个仓库的 bug。创建会话、发送消息、查看进度和跟进任务，这些操作可以用于上面的每一种场景。

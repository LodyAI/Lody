# Команды CLI

`lody` — это одновременно:

- локальный процесс среды выполнения, запускаемый с помощью `lody start` или `lody daemon start`
- одноразовый CLI для управления рабочими пространствами, репозиториями GitHub, сессиями, машинами и конфигурациями агентов

Если вы только начинаете работать с Lody, сначала прочтите [Быстрый старт](/ru/docs/quickstart), [Сессии](/ru/docs/session),
[Конфигурация агента](/ru/docs/quickstart) и [Типы сред выполнения CLI](/ru/docs/cli-runtimes).

## Справка и просмотр параметров

Встроенный вывод справки является основным источником информации о точных флагах и позиционных аргументах.

```bash
lody --help
lody session --help
lody session create --help
lody agent-config update --help
```

Используйте этот шаблон для любой команды:

| Область               | Команда                            |
| --------------------- | ---------------------------------- |
| Общий обзор           | `lody --help`                      |
| Группа команд         | `lody <group> --help`              |
| Конкретная подкоманда | `lody <group> <subcommand> --help` |

## Основные команды

| Команда       | Что делает                                             | Команда справки      |
| ------------- | ------------------------------------------------------ | -------------------- |
| `lody`        | Показывает общую справку и доступные команды           | `lody --help`        |
| `lody login`  | Выполняет вход в систему и регистрирует текущую машину | `lody login --help`  |
| `lody logout` | Очищает локальные учётные данные                       | `lody logout --help` |
| `lody start`  | Запускает Lody CLI в текущем терминале                 | `lody start --help`  |

Командам, которые обращаются к локальной среде выполнения напрямую, обычно требуется запущенный на
переднем плане процесс `lody start` или работающий в фоне `lody daemon start`:

- `lody session create`
- `lody session chat`
- `lody session cancel`
- `lody agent-config refresh-capabilities`

### Неинтерактивный вход с `--auth`

По умолчанию `lody login` запускает авторизацию устройства через браузер. На машинах без графического
интерфейса (CI-раннеры, удалённые серверы, контейнеры) можно обойтись без браузера, передав заранее
созданный CLI-токен:

```bash
lody login --auth <token>
lody start --auth <token>          # войти и запустить среду выполнения одним шагом
```

- `--auth <token>` выполняет аутентификацию с помощью **CLI token**, сгенерированного в разделе
  **Settings → Account → CLI Token** в десктопном или веб-приложении. Нажмите **Create token**,
  добавьте краткую заметку (например, `CI runner`, `home server`) и скопируйте токен перед
  закрытием диалогового окна — он показывается только один раз.
- Токены можно отозвать в любой момент на той же панели. Отзыв немедленно отключает все CLI,
  которые использовали этот токен.
- `--auth` принимает тот же флаг `--machine-name <name>`, что и интерактивный вход, поэтому вы
  можете переопределить имя хоста по умолчанию.
- Если флаг `--auth` не указан в `lody login`, команда переходит к интерактивной авторизации через
  устройство; если он не указан в `lody start` в окружении без активной сессии, среда выполнения
  предложит войти в систему отдельно.

Храните токен в защищённом месте (например, в менеджере секретов или в переменной окружения
`LODY_AUTH`). Он предоставляет такой же доступ к вашим рабочим пространствам, как и интерактивный вход.

## Продуктовая аналитика

Облачные клиенты (десктопное приложение, веб-версия, мобильное приложение и CLI) по умолчанию передают минимальные счётчики использования продукта и обезличенные сообщения об ошибках; это управляется единым переключателем на уровне аккаунта в разделе Settings → About → **Share app usage data**. Отключение этого параметра останавливает сбор данных в десктопном, веб- и мобильном приложениях, аккаунтной аналитике и авторизованных облачных процессах CLI.

Для любого облачного процесса CLI вы также можете задать в окружении переменную `LODY_DISABLE_USAGE_SHARING=1` (или `DO_NOT_TRACK=1`) как жёсткое локальное переопределение, чтобы аналитика оставалась отключённой.

В локальных сборках PostHog отключён. Когда в облачном CLI включена аналитика, он отправляет только минимальный набор зарегистрированных имён событий, время события, случайный идентификатор процесса, укрупнённые метаданные `platform` / `cli_type` / нормализованный встроенный `agent_type` (`other` для пользовательских агентов) и метаданные библиотеки без создания профилей пользователей. Автоматические ошибки содержат фиксированный тип и код. Аргументы команд, идентификаторы машин, пути к репозиториям, имена пользовательских агентов и тексты сообщений об ошибках в эти запросы не включаются.

## Режим демона

`lody daemon start` запускает Lody CLI в фоновом режиме и поддерживает его доступность для
десктопных, веб- и мобильных клиентов, не оставляя окно терминала открытым. Эта же команда
подключает удалённую машину: выполните её по SSH на сервере или другой рабочей станции, и эта
машина присоединится к вашему рабочему пространству.

Перед переходом в фоновый режим `lody daemon start` проверяет, удаётся ли подключиться к Lody и
выполнен ли вход на этой машине:

- Вход выполнен и сервис доступен: демон запускается.
- Вход не выполнен (или сохранённые учётные данные отклонены): команда запускает процесс
  авторизации устройства, открывает ссылку для входа в браузере (или выводит её в терминал, если
  браузера нет) и ждёт завершения входа, прежде чем перейти в режим демона. Без подключённого
  терминала — в CI или при запуске по SSH из скрипта — она не ждёт браузер, а завершается с ошибкой
  и просит выполнить `lody login` или передать `--auth <cli_token>`.
- Сервис Lody недоступен: команда завершается с ошибкой подключения вместо того, чтобы оставлять
  демон, который не может синхронизироваться. Передайте `--skip-auth-check`, чтобы запустить демон
  в любом случае, или `--auth <cli_token>` для неинтерактивного входа.

| Команда               | Что делает                                                  |
| --------------------- | ----------------------------------------------------------- |
| `lody daemon start`   | Запускает фоновый демон                                     |
| `lody daemon status`  | Показывает состояние среды, машины и подключения            |
| `lody daemon logs`    | Выводит последние логи (по умолчанию 50 строк)              |
| `lody daemon stop`    | Останавливает фоновый демон                                 |
| `lody daemon restart` | Останавливает демон, если он запущен, и запускает его снова |

Типичные примеры:

```bash
lody daemon start
lody daemon status
lody daemon logs --lines 100
lody daemon restart
lody daemon stop
```

Логи демона записываются в каталог `~/.lody/logs`. Используйте `lody daemon logs`, если запуск
завершается ошибкой или интерфейс не может связаться с CLI. Если во время отладки вам нужен живой
вывод на переднем плане, используйте вместо этого `lody start`.

## Команды рабочих пространств

Используйте команды для работы с рабочими пространствами, когда вам нужен точный ID или slug
рабочего пространства для последующих команд.

| Команда               | Что делает                                   | Команда справки              |
| --------------------- | -------------------------------------------- | ---------------------------- |
| `lody workspace list` | Выводит список доступных рабочих пространств | `lody workspace list --help` |

### workspace list

`lody workspace list` выводит таблицу со столбцами `ID`, `Name` и `Slug`. Используйте её перед
командами, которые принимают `--workspace <idOrSlug>`.

```bash
lody workspace list
lody workspace list --json
```

## Команды GitHub

Используйте команды GitHub, чтобы проверить, какие репозитории уже привязаны к рабочему
пространству в разделе Settings → GitHub.

| Команда            | Что делает                                                              | Команда справки           |
| ------------------ | ----------------------------------------------------------------------- | ------------------------- |
| `lody github list` | Выводит список репозиториев GitHub, привязанных к рабочему пространству | `lody github list --help` |

### github list

`lody github list` выводит репозитории, уже добавленные в рабочее пространство. Она не показывает
все репозитории, к которым есть доступ у GitHub App, а только те, которые в данный момент
привязаны к этому рабочему пространству.

```bash
lody github list --workspace my-team
lody github list --workspace my-team --json
```

Основные параметры:

- `--workspace <idOrSlug>` выбирает целевое рабочее пространство
- по умолчанию выводится читаемая таблица с ID репозитория, полным именем и видимостью
- `--json` возвращает структурированные данные о репозиториях для автоматизации

Точные флаги:

```bash
lody github list --help
```

## Команды проектов

Команды проектов управляют регистрациями локальных проектов, которые позже можно выбрать при
создании сессии.

| Команда                   | Что делает                                           | Команда справки              |
| ------------------------- | ---------------------------------------------------- | ---------------------------- |
| `lody project add [path]` | Регистрирует локальный каталог проекта               | `lody project add --help`    |
| `lody project list`       | Выводит список зарегистрированных локальных проектов | `lody project list --help`   |
| `lody project delete`     | Удаляет зарегистрированные локальные проекты         | `lody project delete --help` |

Без селекторов `lody project list` считывает проекты текущей машины через её локальный демон. Чтобы
просмотреть проекты, зарегистрированные на машине рабочего пространства, без запуска демона на
клиенте, используйте путь облачного каталога:

```bash
lody project list --workspace <id|slug|name> [--machine <id|name>] --json
```

Без `--machine` каталог рабочего пространства включает авторизованные локальные проекты на всех
машинах и подключённые репозитории GitHub. Используйте `--kind local` или `--kind github`, чтобы
выбрать один тип; `--machine` ограничивает результат локальными проектами на указанной машине.
`--catalog` выбирает каталог рабочего пространства без явного селектора рабочего пространства.
Удалённый вывод списка недоступен в локальной платформе с открытым исходным кодом, так как этот
режим не выполняет облачный ввод-вывод.

### Поиск ресурсов и пагинация

Списки машин, проектов, конфигураций агентов, ролей и MCP в рабочем пространстве по умолчанию
возвращают 20 записей. Используйте `--limit` (1–100), `--query` и `--cursor` с теми же фильтрами
или `--all-pages`. В формате JSON возвращаются поля `items`, `hasMore` и необязательное поле
`nextCursor`, а также псевдоним массива для конкретного ресурса. Это безопасные сводки: значения
подключения MCP и учётные данные запуска агента опускаются.

```bash
lody agent-role list --workspace my-team --all-pages --json
lody agent-role get ROLE_ID --workspace my-team --json
lody agent-config get AGENT_ID --workspace my-team --json
lody mcp list --workspace my-team --json
lody operation list --workspace my-team --session SESSION_ID --state active --json
lody session list --workspace my-team --query parser --machine-id MACHINE_ID --agent-config-id AGENT_ID --agent-role-id ROLE_ID
```

Подробные сведения о роли включают префикс промпта; списки сохраняют доступные для чтения
недоступные роли с указанием причин. Вывод списка операций читает хранилище текущей машины в
рамках запрашивающей сессии и аутентифицированного пользователя с флагами `--state`, `--limit` и
`--cursor`. Он не агрегирует хранилища других машин. Фильтр роли в сессии соответствует
происхождению при создании. Lody MCP предоставляет соответствующие доступные только для чтения
действия `lody_catalog` (`machines`, `projects`, `agent_configs`, `agent_roles`, `mcp_servers`) и
инструмент `lody_operation`.

Актуальные точные флаги всегда проверяйте во встроенной справке:

```bash
lody project add --help
lody project list --help
lody project delete --help
```

## Создание и обновление ролей агентов

CLI и MCP могут предложить новую роль или изменения для роли, которой вы владеете. Предложение
появляется в виде карточки проверки в активной беседе. Нажмите **Save** в Lody, чтобы применить
его, или отклоните карточку, чтобы оставить каталог без изменений. Успешная команда сообщает об
ожидающем подтверждения предложении, а не о сохранённой роли.

```bash
lody agent-role create --name "Reviewer" --description "Review code" \
  --prompt-prefix "Find actionable bugs" \
  --machine-id MACHINE_ID --agent-config-id CONFIG_ID --session SESSION_ID

lody agent-role update ROLE_ID --name "Code reviewer" \
  --description "" --prompt-prefix "Focus on correctness" --session SESSION_ID
```

| Параметр                 | Создание       | Обновление                        |
| ------------------------ | -------------- | --------------------------------- |
| `--name <name>`          | Обязательный   | Необязательный                    |
| `--description <text>`   | Необязательный | Необязательный; `""` очищает поле |
| `--prompt-prefix <text>` | Необязательный | Необязательный; `""` очищает поле |
| `--machine-id <id>`      | Обязательный   | Не поддерживается                 |
| `--agent-config-id <id>` | Обязательный   | Не поддерживается                 |

Для обновления требуется хотя бы одно поле. Пропущенные поля остаются без изменений. Новые роли
являются приватными и используют конфигурацию запуска по умолчанию привязанного агента. Модель,
разрешения, общий доступ и другие параметры можно изменить в редакторе ролей.

Используйте `--session` или задайте `LODY_SESSION_ID`, чтобы выбрать активную беседу, а также
`--workspace <id-or-slug>`, если рабочее пространство неоднозначно. При повторной попытке
передавайте тот же `--request-id <id>` с идентичными входными данными — результат вернёт статус
уже существующего предложения.

Также поддерживаются JSON-файлы:

```bash
lody agent-role create --file role.json --session SESSION_ID
lody agent-role update ROLE_ID --file patch.json --session SESSION_ID
```

Файл создания содержит поля `name`, `machineId`, `agentConfigId` и при необходимости `description`
и `promptPrefix`. Файл обновления содержит только изменённые поля `name`, `description` или
`promptPrefix`. Флаг `--file` нельзя сочетать с прямыми опциями полей роли. Для инструкций,
хранящихся в Markdown, передавайте `--prompt-prefix "$(cat reviewer.md)"`.

`role.json`:

```json
{
  "name": "Reviewer",
  "machineId": "MACHINE_ID",
  "agentConfigId": "CONFIG_ID",
  "description": "Review code",
  "promptPrefix": "Check correctness.\nReport actionable bugs."
}
```

`patch.json`:

```json
{
  "description": "",
  "promptPrefix": "Focus on correctness.\nExplain each finding."
}
```

Файлы должны содержать один JSON-объект в кодировке UTF-8 с ключами в формате camelCase,
показанными выше. Файл обновления представляет собой сам патч: не оборачивайте его в поле `patch`,
а ID роли передавайте как аргумент команды. Идентификаторы повторных попыток передавайте через
`--request-id`. В строках JSON для переноса строки используется `\n`; комментарии и завершающие
запятые в JSON недопустимы.

Все значения полей должны быть строками. Для создания обязательны `name`, `machineId` и
`agentConfigId`. Для обновления требуется хотя бы одно поддерживаемое поле. Пропущенные при
обновлении поля остаются без изменений; `""` очищает описание или инструкции, тогда как `null`
отклоняется. Имена должны быть непустыми, совместимыми с упоминаниями (`@`) и содержать не более
60 символов после обрезки пробелов; описания допускают до 140 кодовых точек Unicode; инструкции
допускают до 32 768 символов до обрезки пробелов. Идентификаторы машин и конфигураций должны быть
непустыми и содержать не более 128 символов после обрезки пробелов. Неподдерживаемые поля
отклоняются.

MCP предоставляет тот же сценарий подтверждения через действия `create` и `update` инструмента
`lody_agent_role`. Действие `create` принимает `requestId` и перечисленные выше поля создания;
`update` принимает `requestId`, `roleId` и объект `patch`, содержащий изменённые текстовые поля.
О том, как используются сохранённые роли, см. в разделе [Роли агентов](/ru/docs/agent-roles).

### Восстановление зависшего окна десктопного приложения

Если окно десктопного приложения перестало отвечать — или после перезапуска возвращается в то же
сломанное состояние — причиной может быть его локальный кэш, а до пункта **Settings → Clear cache**
добраться не удаётся. Запланируйте то же восстановление из терминала:

```bash
lody app reset-cache          # очистить восстанавливаемые кэши; сохранить вход в аккаунт
lody app reset-cache --hard   # удалить все локальные данные и выйти из аккаунта
lody app reset-cache --cancel # отменить любое из действий выше
```

Команда только записывает запрос; приложение применяет его при следующем запуске, поэтому
**полностью закройте десктопное приложение и откройте его снова**. При этом ничего никуда не
отправляется, и не требуется ни вход в систему, ни запущенный демон.

`lody app reset-cache` сохраняет ваш аккаунт, настройки и неотправленные черновики Shortcut и
заново загружает беседы из рабочего пространства. Используйте `--hard` только в том случае, если
приложение всё равно остаётся зависшим: этот флаг также удаляет текущую авторизованную сессию и
локальные параметры. Запрос, который так и не был применён, истекает через сутки.

## Команды сессий

Команды сессий — это основной способ работы с Lody вне веб-интерфейса.

Перед началом работы:

- для `session create`, `session chat` и `session cancel` на текущей машине должен быть запущен `lody start` или `lody daemon start`
- для `session list`, `history`, `observe`, `show`, `rename`, `archive`, `restore` и `delete` достаточно входа в систему и доступа к рабочему пространству
- используйте [`lody workspace list`](#команды-рабочих-пространств), если вам нужен ID или slug рабочего пространства
- `sessionId` можно передать позиционным аргументом или через `LODY_SESSION_ID`

| Подкоманда             | Что делает                                               | Нужна локальная среда | Команда справки               |
| ---------------------- | -------------------------------------------------------- | --------------------- | ----------------------------- |
| `lody session create`  | Создаёт новую сессию на текущей машине                   | Да                    | `lody session create --help`  |
| `lody session chat`    | Отправляет новый ход в существующую локальную сессию     | Да                    | `lody session chat --help`    |
| `lody session cancel`  | Отменяет выполняемый ход в локальной сессии              | Да                    | `lody session cancel --help`  |
| `lody session list`    | Выводит список сессий в рабочем пространстве             | Нет                   | `lody session list --help`    |
| `lody session history` | Читает видимую историю транскрипта                       | Нет                   | `lody session history --help` |
| `lody session observe` | Просматривает и отслеживает сохранённое состояние сессии | Нет                   | `lody session observe --help` |
| `lody session show`    | Показывает метаданные сессии                             | Нет                   | `lody session show --help`    |
| `lody session rename`  | Переименовывает сессию                                   | Нет                   | `lody session rename --help`  |
| `lody session archive` | Перемещает сессию из активного списка в архив            | Нет                   | `lody session archive --help` |
| `lody session restore` | Восстанавливает архивированную сессию                    | Нет                   | `lody session restore --help` |
| `lody session delete`  | Безвозвратно удаляет архивированную сессию               | Нет                   | `lody session delete --help`  |

### session create

Создаёт сессию, привязанную к репозиторию GitHub или зарегистрированному локальному проекту.

```bash
lody session create --workspace my-team --agent-config codex --repo owner/repo "Fix the failing test"
```

Основные параметры:

- `--workspace <idOrSlug>` выбирает целевое рабочее пространство
- `--agent-config <idOrName>` выбирает конфигурацию агента из раздела [Конфигурация агента](/ru/docs/quickstart)
- `--agent-role <idOrName>` создаёт сессию из роли агента в рабочем пространстве; машина, конфигурация агента и конфигурация запуска роли переопределяют `--machine`, `--agent`/`--agent-config`, `--mode`, `--model` и `--config-option` (в предупреждении перечисляются проигнорированные флаги)
- `--repo <owner/repo>` подключает репозиторий GitHub
- `--local-project <id|name|path>` подключает ранее зарегистрированный локальный проект
- `--repo` и `--local-project` взаимоисключающие
- `--branch <name>` выбирает начальную ветку
- `--mode <modeId>` и `--model <modelId>` переопределяют параметры ACP
- `--env KEY=VALUE` можно повторять; переменные сохраняются вместе с сессией для последующего возобновления
- текст промпта можно передать позиционным аргументом, через `--prompt`, `--prompt-file` или stdin

Точные флаги:

```bash
lody session create --help
```

### session chat

Отправляет следующий пользовательский ход в существующую сессию на текущей машине.

```bash
lody session chat <sessionId> "continue from the last patch"
LODY_SESSION_ID=<sessionId> lody session chat --prompt "continue from the last patch"
```

Основные параметры:

- `sessionId` можно передать позиционным аргументом или через `LODY_SESSION_ID`
- текст промпта можно передать позиционным аргументом, через `--prompt`, `--prompt-file` или stdin
- `--mode <modeId>` и `--model <modelId>` переопределяют параметры ACP для этого хода

Точные флаги:

```bash
lody session chat --help
```

### Входные вложения

И `create`, и `chat` принимают повторяемый флаг `--attach <path>`:

```bash
lody session create --machine remote --prompt "Analyze the data" --attach ./data.csv
lody session chat <sessionId> --prompt "Use this screenshot too" --attach ./screen.png
```

Пути считываются на машине, выполняющей команду, относительно её текущего каталога.
Все вложения должны завершить подготовку до отправки сообщения. Любая ошибка
прерывает отправку. Поддерживается до восьми непустых файлов размером до 100 МиБ каждый.
Поддерживаемые изображения в пределах ограничения на размер изображения сохраняют визуальный ввод;
более крупные изображения передаются как файлы. При наличии вложений текст необязателен.
`--prompt-file` по-прежнему считывает текст промпта. Повторный запуск автономной команды CLI
отправляет новое сообщение.

### session cancel

Отменяет выполняющийся в данный момент ход локальной сессии.

```bash
lody session cancel <sessionId>
```

Если отмена не удалась, команда завершается с ненулевым кодом выхода. Точные флаги:

```bash
lody session cancel --help
```

### session list

Выводит список сессий в рабочем пространстве. По умолчанию отображаются только активные сессии.

```bash
lody session list --workspace my-team
lody session list --workspace my-team --archived
lody session list --workspace my-team --all --limit 50 --json
```

Основные параметры:

- `--archived` показывает только архивированные сессии
- `--all` включает как активные, так и архивированные сессии
- `--limit <count>` ограничивает размер результата
- по умолчанию выводится читаемая таблица; `--json` возвращает структурированные данные

Точные флаги:

```bash
lody session list --help
```

### session history

Читает видимый транскрипт одной сессии. Эта команда намеренно скрывает внутренние рассуждения,
вызовы инструментов и другие элементы, не предназначенные для пользователя.

```bash
lody session history <sessionId> --limit 20
lody session history <sessionId> --all --reverse
lody session history <sessionId> --jsonl
```

Основные параметры:

- `--limit <count>` возвращает N самых новых видимых ходов
- `--all` возвращает весь видимый транскрипт
- `--reverse` выводит записи в порядке от новых к старым
- `--json` и `--jsonl` удобны для автоматизации

Точные флаги:

```bash
lody session history --help
```

### session observe

Подключается к существующей сессии без отправки задачи и без изменения статуса непрочитанности.
В настоящее время эта команда использует облачный вход и доступ к рабочему пространству;
подключение только к локальному демону не поддерживается.

```bash
lody session observe <sessionId> --json
lody session observe <sessionId> --jsonl --follow
lody session observe --workspace my-team --all --jsonl --follow
```

Без `--follow` команда выводит снимок состояния и завершает работу. Для режима отслеживания
требуется `--jsonl`. В отличие от `history --jsonl`, команда остаётся подключённой для получения
последующих ходов. Режим рабочего пространства требует одновременно `--workspace` и `--all`,
отклоняет позиционный ID сессии и игнорирует `LODY_SESSION_ID`.

События JSONL: `snapshot`, `ready`, `session.changed`, `turn.started`, `turn.finished` и
`session.removed`. Каждое успешное событие содержит `version: 1`, `streamId`, `sequence`,
`observedAt` (в миллисекундах Unix) и `workspaceId`. `turn.finished` включает идентификаторы
пользователя и необязательного ассистента, а также `outcome: completed | failed | canceled`.
Начальные снимки содержат `latestTurn`, чтобы итог быстрой задачи оставался доступным для чтения;
старые ходы повторно в виде событий не воспроизводятся.

Снимки сессий различают `source: persisted | metadata` и `freshness: synced | unavailable`.
Событие `ready` для рабочего пространства отмечает перечисление каталога, а не открытие каждой
комнаты истории: у сессий только с метаданными указано `state: unknown`. Исторические неактивные
комнаты остаются закрытыми; изменения только в их истории находятся вне области отслеживания
рабочего пространства. При необходимости подключайтесь к ним отдельно. Завершение требует
сохранённых сведений о ходе; состояния покоя по метаданным или потери присутствия (Presence)
недостаточно. `freshness` — это подтверждённое чтение, а не доказательство того, что агент в
данный момент находится в сети.

`sequence` упорядочивает события одного запущенного процесса и не может использоваться для
возобновления в другом процессе или гарантировать повторное воспроизведение. После перезапуска
сверьте снимки и историю. Обычный потоковый текст опускается. Структурированная диагностика
направляется в stderr; ошибки команд используют существующий формат ошибок CLI. Нажатие Ctrl+C
останавливает наблюдение без отмены выполнения.

```bash
lody session observe --help
```

## Команды машин

Используйте команды для работы с машинами, чтобы проверить, какие машины зарегистрированы в рабочем
пространстве и находятся ли они в сети.

| Команда             | Что делает                                  | Команда справки            |
| ------------------- | ------------------------------------------- | -------------------------- |
| `lody machine list` | Выводит список машин в рабочем пространстве | `lody machine list --help` |

### machine list

```bash
lody machine list --workspace my-team
lody machine list --workspace my-team --online-only
lody machine list --workspace my-team --json
lody machine list --workspace my-team --json --include-acp-capabilities
```

Таблица по умолчанию показывает идентификатор машины и её доступность. В JSON сохраняется поле
`onlineStatus: online | offline | unknown`; недоступный статус присутствия не сообщается как
`offline`. Флаги `--include-acp-capabilities` и `--include-agents` сохраняют прежний подробный
вывод и не могут сочетаться с флагами постраничного вывода и фильтрации каталога. Для получения
возможностей с пагинацией используйте `agent-config list/get`.

- по умолчанию отображаются как машины в сети, так и офлайн-машины
- используйте `--online-only`, чтобы отфильтровать список до машин с недавним heartbeat-сигналом
- `--json` по умолчанию опускает `acpCapabilities`, чтобы уменьшить размер полезной нагрузки
- передайте `--include-acp-capabilities`, если вам нужен кэш возможностей в выводе JSON

Это полезно перед выполнением `agent-config refresh-capabilities`.

Точные флаги:

```bash
lody machine list --help
```

## Команды конфигурации агентов

Команды конфигурации агентов во многом повторяют поведение веб-интерфейса из раздела [Конфигурация агента](/ru/docs/quickstart).

Перед началом работы:

- селекторы принимают ID или имя
- если несколько конфигураций или машин имеют одинаковое имя, CLI требует явный ID
- `refresh-capabilities` в настоящее время работает из CLI только на текущей машине

| Подкоманда                               | Что делает                                          | Команда справки                                 |
| ---------------------------------------- | --------------------------------------------------- | ----------------------------------------------- |
| `lody agent-config list`                 | Выводит список конфигураций в рабочем пространстве  | `lody agent-config list --help`                 |
| `lody agent-config show`                 | Показывает одну конфигурацию                        | `lody agent-config show --help`                 |
| `lody agent-config create`               | Создаёт новую конфигурацию                          | `lody agent-config create --help`               |
| `lody agent-config import-magpie`        | Импортирует локальных провайдеров Magpie            | `lody agent-config import-magpie --help`        |
| `lody agent-config update`               | Обновляет существующую конфигурацию                 | `lody agent-config update --help`               |
| `lody agent-config delete`               | Удаляет конфигурацию                                | `lody agent-config delete --help`               |
| `lody agent-config refresh-capabilities` | Обновляет поддерживаемые режимы, модели и параметры | `lody agent-config refresh-capabilities --help` |

### agent-config list

```bash
lody agent-config list --workspace my-team
```

Показывает идентификатор конфигурации, машину и доступность. Вывод JSON также включает тип агента,
описание и поддерживаемые параметры модели и запуска. Используйте `--machine`, `--query` и
пагинацию, чтобы сузить список.

### agent-config show

```bash
lody agent-config show <idOrName>
LODY_AGENT_CONFIG_ID=<id> lody agent-config show
```

Показывает поля конфигурации в человекочитаемом виде или в формате JSON.

### agent-config create

Создаёт конфигурацию для встроенной среды выполнения агента или среды из реестра.

```bash
lody agent-config create \
  --workspace my-team \
  --agent-type codex \
  --name "Codex Default" \
  --env OPENAI_API_KEY=... \
  --prompt "Always run tests before finishing"
```

Основные параметры:

- `--agent-type <type>` обязателен
- `claude` и `codex` обрабатываются как встроенные среды выполнения
- все остальные типы агентов обрабатываются как среды выполнения из реестра
- `--env KEY=VALUE` можно повторять
- `--env-file <path>` загружает переменные окружения из файла
- `--prompt` или `--prompt-file` задаёт префикс промпта по умолчанию

Точные флаги:

```bash
lody agent-config create --help
```

### agent-config import-magpie

Импортирует провайдеров Magpie на сервере, выполняющем команду, для всех поддерживаемых агентов
или выбранного подмножества:

```bash
lody agent-config import-magpie --workspace my-team --json
```

Подробности настройки, параметры и состояния результата см. в разделе [Подключение Magpie](/ru/docs/magpie).

### agent-config update

Обновляет конфигурацию на месте.

```bash
lody agent-config update <idOrName> --name "Codex CI"
lody agent-config update <idOrName> --env OPENAI_API_KEY=... --unset-env OLD_KEY
lody agent-config update <idOrName> --prompt ""
```

Основные параметры:

- `--name` обновляет отображаемое имя
- `--description ""` очищает описание
- `--env` и `--env-file` объединяют новые значения переменных окружения
- `--unset-env KEY` удаляет одну или несколько переменных окружения
- `--prompt ""` очищает префикс промпта по умолчанию

Точные флаги:

```bash
lody agent-config update --help
```

### agent-config delete

```bash
lody agent-config delete <idOrName>
```

Удаляет одну конфигурацию по ID или уникальному имени.

### agent-config refresh-capabilities

Обновляет кэш возможностей для одной конфигурации агента на текущей машине.

```bash
lody agent-config refresh-capabilities <idOrName> --workspace my-team
```

Используйте эту команду после:

- установки или обновления CLI-агента для программирования
- изменения окружения конфигурации агента
- обновления доступных моделей или режимов на машине

Основные параметры:

- `--machine <idOrName>` по умолчанию указывает на текущую машину
- выбранная машина должна быть в сети
- в настоящее время CLI отклоняет обновление на удалённой машине; используйте для этой команды текущую машину
- для автоматизации поддерживаются `--json` и `--jsonl`

Точные флаги:

```bash
lody agent-config refresh-capabilities --help
```

## Типичные примеры

```bash
# Найти нужный ID или slug рабочего пространства
lody workspace list

# Посмотреть репозитории GitHub, уже привязанные к этому рабочему пространству
lody github list --workspace my-team

# Посмотреть конфигурации агентов в этом рабочем пространстве
lody agent-config list --workspace my-team

# Запустить локальный демон в фоновом режиме
lody daemon start

# Режим переднего плана удобен для временной отладки
lody start

# Создать сессию в репозитории GitHub
lody session create \
  --workspace my-team \
  --agent-config codex \
  --repo owner/repo \
  "Fix the failing tests"

# Прочитать последние видимые ходы транскрипта
lody session history <sessionId> --limit 20

# Просмотреть машины и обновить возможности на текущей машине
lody machine list --workspace my-team --online-only
lody agent-config refresh-capabilities codex --workspace my-team
```

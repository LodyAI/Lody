# Desktop Onboarding

- Electron opens `/onboarding` in the primary product renderer. Do not add a second window, renderer entry, provider tree, or runtime lease for onboarding.
- The Electron main process owns the durable completion marker. Product navigation starts immediately alongside that write and never waits for its IPC; renderer storage owns only resumable phase and draft state, and is cleared after both product navigation and the completion IPC succeed.
- Build the flow from platform capabilities and the upfront `ArrivalProbe`: `['arrive', ...(cloudAccount ? ['account'] : []), ...(needsModel ? ['model'] : []), 'start']`. Local builds must not import or call cloud auth, workspace, or GitHub implementations.
- `ArrivalProbe` reads only Lody and Sorbet state in `<LodyDataDir>/sorbet` via headless `@sorbetai/control` (`credentials.list()`, `authentication.methods()`, and `providers.availableModels()`). Startup must never read login-shell environment variables (`$SHELL -ilc env`), probe external CLIs (`~/.claude*`, `~/.codex*`), or scan TCC-protected folders (`~/Documents`, `~/Desktop`, `~/Downloads`).
- External credential imports (`claude-code`, `codex`, `env`) run only after explicit user confirmation on that row. When a tool stores single-use rotating OAuth refresh tokens, never copy those tokens into Sorbet; explain that refreshing would sign out the original CLI and offer a one-click subscription OAuth sign-in instead.
- `ConnectModelSheet` and `BrowserAuthButton` are shared between Onboarding (`ModelScreen` and `StartScreen`) and `Settings -> Lody Agent`. Onboarding must never import lazy settings route modules (`@/components/harness/*` or `@/components/settings/*`) so deferred settings chunks stay out of the initial renderer bundle.
- Completed Account and Model decisions collapse into clickable chips in `OnboardingChipRail` without `"Step X of Y"` progress indicators. Clicking a chip revisits that step while keeping other chips intact; `Escape` returns to the previous editable step.
- `Arrive` plays the approved editorial illustrations from `intro-illustration-direction.md`, auto-advancing beats 1-3 unless hovered or `prefers-reduced-motion` is active, and keeps `ready-to-begin` on the continuous stage as `Account` swaps in on the left.
- `Account` auto-selects a single workspace and expands in-place only when multiple workspaces or workspace creation/slug repair are needed.
- `StartScreen` mounts the real `<ChatComposer>` (`#chat-prompt`). Project selection is optional and defaults to projectless conversation; recent repositories under `~/dev`, `~/code`, `~/Developer`, and `~/projects` are scanned lazily only when the Project popover opens, while `Open folder...` (`Cmd/Ctrl+O`) remains immediately interactive.
- Both sending the first task and `Explore first` (`先逛逛`) transition into the product without blocking on native completion persistence. When reduced motion is off and View Transitions are available, `[data-lody-composer-box]` morphs directly into the product composer.
- Desktop onboarding owns the app theme for its whole route lifetime: enter and reload in `light`, and restore the persisted source to `system` only after completion succeeds or the route unmounts.
- Every onboarding error path logs its underlying error to `console.error` while keeping user-facing inline messages free of raw error codes or secrets, and leaves recoverable actions retryable.
- Desktop onboarding analytics use the shared flow/step/operation/completion event contract and one anonymous session-scoped `flow_id`, hard-gated by the platform `telemetry` capability so OSS local emits nothing. Never send names, slugs, repository paths, prompts, API keys, or raw error messages. Completion analytics distinguish `completion_started`, `completion_succeeded`, and `flow_completed`; see [event semantics](../../../../../specs/onboarding-analytics.md).

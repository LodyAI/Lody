# Loro ephemeral presence 通道

Status: draft
Translation: current

[English](loro-ephemeral-presence-channel.md)

工作区通过一条独立于持久文档同步的 Loro ephemeral 通道发布在线状态：机器心跳、会话活跃状态，
以及"谁正在查看这个会话"。读取端只有在心跳的 `updatedAt` 处于时效窗口内时，才判定机器在线。
持久对话内容走自己的传输通道，不受下文任何内容影响。

## 该通道是一份在线状态预算，不是数据通路

ephemeral 通道面向最新状态。它不随文档流持久化，不重放历史；服务端可能只保留很小的实时转发
队列，并在订阅者过慢时直接断开，而不是缓冲每一次中间更新。因此通道上发布的一切都是可丢弃的，
发布的唯一理由是某个读取端此刻需要知道当前状态。

一个工作区只拥有一条 ephemeral 传输，机器心跳与该工作区内其他所有 ephemeral 写入方共用它。
发布严格串行：同一时刻只有一个更新在途，其余排在先进先出队列中；该队列不合并已被覆盖的条目、
不为心跳提供优先级，也没有长度上限。因此，产出速度超过网络排空速度的写入方，会在整个积压期间
延迟其后的每一个写入方，心跳也在其中。

这种延迟不只是变慢，而是破坏在线状态本身。心跳的时间戳在条目创建时取得，而非发送时取得，
所以等待超过时效窗口的条目送达时已经过期：读取端收到了它，却仍把机器判定为离线。在此期间
连接始终报告健康，因为一个能成功排空的积压并不是错误，于是没有任何重连或恢复路径会发现问题。

## 不变量

**只在 ephemeral 通道上发布小体积、低频率的在线状态。绝不在其上发布高频或大体积数据。**

对每一个 ephemeral 写入方，具体要求是：

- **速率有界。** 写入方由定时器、生命周期转换或用户可见的阶段变化驱动，绝不由流中的每个元素
  驱动。按 chunk、按 token、按击键、按帧、按循环迭代发布一律禁止，无论单条负载多小。当高频
  来源确实需要呈现时，必须在进入通道之前采样或限流到固定上限，使发布速率成为发布方的属性，
  而不是来源的属性。
- **体积有界。** 负载是形状固定的小记录，每个字段都在 `packages/shared/src/presence.ts` 中有
  schema 上限。无上限字符串、累积文本、文件内容、diff、对话记录、编码后的文档，以及随会话
  增长的集合，都不是在线状态，不属于这里。
- **仅最新状态。** 写入方在稳定的 key 下发布当前状态，并且必须容忍丢失所有中间值。任何读取端
  必须按序收到、或不能遗漏的内容，都是持久数据，属于文档传输通道。
- **不得饿死共享通道。** 由于共用一个队列，新增一个写入方就是在改变机器心跳的送达预算。新的
  ephemeral 写入方必须说明其最坏情况下的速率与负载大小，而不是典型值。

不符合上述边界的功能，不能靠压缩单条负载勉强塞进来。它要么属于持久文档传输通道，要么就留在
本地、完全不发布。

## 对读取端的影响

读取在线状态始终是一个三态问题。有新鲜心跳即在线；传输已同步但没有心跳即离线；传输未同步即
未知。读取端不得在传输未同步时报告"离线"，也不得把连接健康当作送达及时的证据 —— 本 Spec 所
要防止的故障，正是这两者同时成立。

三种状态必须一直保留到消费方，不得在中途被压平。只有明确的"离线"才可以阻塞工作或拒绝派发；
"未知"应当继续执行，并在自己的截止期限上失败，因为一个诚实的慢失败胜过一个迅速的错误失败。
对外报告在线状态的接口要携带状态本身而不是布尔值，使调用方能区分"已检查且确实不可用"与
"无法检查"。

## 证据

通道常量、负载 schema 与时效判定位于 `packages/shared/src/presence.ts`。工作区传输、它的两个
store 以及机器心跳定时器位于 `apps/cli/src/lib/loro/presence.ts`；会话活跃状态的唯一所有者是
`apps/cli/src/lib/loro/session-active-presence.ts`。读取端的解释逻辑位于
`packages/components/src/atoms/presence.ts`，CLI 侧位于 `apps/cli/src/commands/machine.ts`，
其 `onlineStatus` 字段让三种状态穿过 `--json` 到达调用方。`apps/cli/src/mcp/lody-mcp-server.ts`
中的派发守卫只在明确离线时阻塞；`apps/cli/src/commands/agent-config.ts` 采取同样立场。

串行队列、不做合并以及无上限重试预算，是 `@loro-dev/streams-crdt`（`EphemeralStreamCrdt`）的
实现细节，检查版本为 0.15.1。本仓库无法控制它们，因此该约束被表述为发布方的义务。

本 Spec 所防止的故障观测于 2026-09-20，记录在
[已驳回的 transient-reasoning note](../.agents/notes/rejected/bug-fix/2026-09-18-codex-transient-reasoning.zh.md)：
某个会话按 agent 推理 chunk 逐条发布 presence，三秒内产生 4,000 次写入，随后该工作区的机器被
读为离线，而对话同步始终正常。本 draft 记录的是期望约束，不构成"现有每个写入方都已在生产负载
下被测量过"的证据。

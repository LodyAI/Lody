# 邀请的信任来源：服务端投递与自己发送

Status: draft
Translation: current

[English](invitation-trust.md)

## 场景

管理员邀请同事加入加密工作区。受邀人需要知道“我加入的是哪个工作区”：工作区 ID、genesis 和一台背书设备的公钥。管理员需要知道“入账的是受邀人的设备”。[优先使用快照的工作区邀请](snapshot-join.zh.md#邀请的信任来源)要求这些信息经独立渠道送达。

邮件邀请不满足这一点。邮件由服务端发送，链接里的 genesis 和背书者公钥由服务端拼接，邀请 token 服务端也知道。服务端若不诚实，可以同时做两件事：

- 给受邀人一封指向自己伪造的工作区的邮件。受邀人以为加入了团队，写入的内容实际加密给了服务端。
- 用真实邀请的 token 抢先提交自己的密钥，被管理员的设备自动接纳，读到真实工作区的内容。

两边合起来，服务端可以在中间转发内容而不被察觉。邀请签名（自动接纳前的核验）不能阻止这件事：受邀人此时还没有任何可信的密钥可用来验证签名。

管理员自己复制并发送的链接没有第一个问题：链接在管理员设备上生成，genesis 和背书者公钥不经服务端。但服务端仍然知道 token，可以冒充受邀人提交申请，所以这类链接目前每次申请都要人工批准，而管理员看到的申请人邮箱和姓名同样来自服务端。

## 决定

**邀请按投递渠道分为两类，信任程度不同，界面如实区分；只有不经服务端的渠道才能在加入时建立双向信任。**

### 1. 邮件邀请：信任等同于服务端，直到核对

邮件邀请保留，自动接纳也保留（条件见白皮书 §4）。它的定位是方便，不是独立验证：

- 通过邮件加入的成员，在成员列表里标为“未核对”；受邀人自己的工作区也显示“尚未与团队成员核对”。
- 标记不限制任何功能。这与白皮书已有的原则一致：正常批准和机器校验完成后可先使用，人工核对可以稍后进行，但未核对必须如实显示。
- 邀请界面和白皮书写明：未经核对的邮件邀请，其安全性取决于服务端诚实。

### 2. 自己发送的链接：携带服务端不知道的秘密

管理员设备生成链接时，除 genesis、背书者公钥和 token 外，再生成一个 128 位随机秘密，只放在链接的 fragment 里，不上传。

- 受邀人的客户端用这个秘密对自己的加入申请计算认证码，随申请一起提交。
- 持有该秘密的管理员设备在签署接纳前验证认证码。验证通过说明：申请来自拿到这条链接的人，申请里的设备公钥没有被服务端替换。
- 验证通过的申请视为“已核对”，双方都不再显示未核对标记。
- 单人链接（只接纳一次）验证通过后可以自动接纳，不需要管理员再点一次。可多人使用的共享链接仍然逐个人工批准，因为拿到链接的人不止一个。
- 秘密只保存在生成链接的那台设备上。其他管理员设备看到这条申请时无法验证认证码，按未核对的申请走人工批准。

这条路径的保证取决于管理员发送链接所用的渠道不受服务端控制，例如团队已在用的聊天工具或当面扫码。

### 3. 事后核对

通过邮件加入、或由没有链接秘密的设备批准的成员，可以事后核对一次：受邀人和任意一位已核对的成员比对[安全码](whitepaper.zh.md)。安全码绑定 genesis、账本位置和权限状态摘要，因此一次比对同时发现两种攻击：工作区被替换（genesis 不同），或受邀人的设备被替换（状态里的设备公钥不同）。

- 比对成功后，双方的客户端各自在本地记录“已在该位置核对”，并清除对应的未核对标记。记录属于本地状态，不写入账本，也不上传。
- 比对失败必须明确告警，不自动选边，并提示联系管理员。

## 保证

- 经自己发送的单人链接加入时，不诚实的服务端既不能把受邀人引到别的工作区，也不能把自己的设备冒充成受邀人入账，前提是它看不到这条链接。
- 邮件邀请和未验证的申请始终带有可见的未核对状态，直到用户完成一次安全码核对。
- 不改变账本记录格式；链接秘密和认证码只存在于邀请链接和申请的传输数据中。

## 不保证

- **未核对期间。** 邮件邀请在核对之前不抵抗不诚实的服务端。标记只让这个状态可见，不能阻止攻击。
- **渠道本身。** 如果管理员把链接发到服务端也能读到的地方，第 2 节的保证不成立。
- **真人身份。** 认证码证明申请来自拿到链接的人，不证明那个人是谁。
- **多设备管理员。** 链接秘密不在管理员的设备之间同步；生成链接的设备离线时，其他设备只能人工批准。

## 已考虑的取舍

Owner 于 2026-11-11 在评审对话中同意以下方向；本 Spec 仍为 draft，以本修订的 PR 批准为准。

1. **未核对成员不受限。** 让未核对成员在核对前不能使用远程机器或只读，会把邮件邀请变成“加入后还要再做一步才能用”。只显示状态。
2. **邀请界面的默认项不变。** 邮件和复制链接并列，在复制链接旁标注“无需信任服务器”。
3. **单人链接验证通过后自动接纳。** 认证码已证明申请来自链接持有者，自动接纳不降低安全性，并省去一次点击。
4. **不弹窗提醒核对。** 只在成员页和工作区安全页显示状态，避免警告疲劳。

## 证据

- 邮件由服务端发送并拼接 genesis：私有后端的邀请邮件发送逻辑（本仓库无法引用）；公开侧 `packages/components/src/lib/e2ee-member-offer.ts` 从链接 fragment 读取这些字段。
- 链接在管理员设备上生成：`packages/components/src/components/settings/e2ee-team-settings.tsx` 的 `memberInvitationUrl(offer)`。
- 自动接纳前的邀请签名核验：`packages/e2ee-client/src/member.ts` 的 `verifyAutomaticMemberAdmission`（[#2549](https://github.com/LodyAI/Lody/pull/2549)，尚未合并）。
- 账号级配对已采用“秘密不发给服务端”的同类做法：[白皮书 §3](whitepaper.zh.md)。
- 安全码界面已存在，按位置记录核对结果尚未接入：[白皮书 §5.2](whitepaper.zh.md)。

## 1. 决定与范围

## 2. 两类实体与有效权限

### 2.1 用户身份

用户身份是成员与角色的主体，与登录会话、邮箱展示和物理设备分开，不为恢复另设用户根私钥。客户端 MUST 从可信账本验证用户与设备公钥的绑定，不能因为目录返回同一邮箱就替换已授权设备。恢复设备也是该用户的一个设备条目，不是更高一级身份。

在某个 Org 中，该身份对应一次成员资格及一个角色：Owner、Admin、Member 或 Guest。被移除后重新加入 MUST 获得新成员实例，旧设备凭证和旧请求不得因此复活。成员实例是内部防重放标识，不要求用户理解。

邮箱用于注册、联系和审批核对，MUST NOT 作为签名身份或最终权限来源。是否把邮箱写进永久账本不是本轮决定；建议仅在申请/账号展示中使用，账本绑定已确认的身份及公钥。

### 2.2 用户设备

每个设备有自己的签名和加密公钥、所属用户身份、设备标识及有效/已撤销状态。管理权限不按设备单独登记，由用户当前角色与设备种类推出：Owner/Admin 的有效个人设备可管理，机器与恢复设备永不管理（2026-09-24 确认）。设备类型为 personal、machine、recovery；机器和恢复设备都不是新的用户角色。设备批准记录可保存“谁批准了它”，但 MUST NOT 作为持续授权依赖。

例如电脑 A 批准手机 B，B 又批准电脑 C：撤销 A 后，B、C 继续有效；不能重新沿历史推导它们失权。若 A 被攻破并在撤销前成功登记了恶意设备 X，X 也不会自动消失，用户必须明确撤销 X；这是 D1 的取舍，而不是应在实现中偷偷恢复连带规则的理由。

### 2.3 每次操作都重新求权限

```text
设备签名有效
  且设备在该 Org 的当前账本中有效
  且设备绑定的用户成员资格有效
  且该用户当前角色和设备种类允许该操作及其目标
  → 才能执行状态转换
```

MUST 从前一可信状态（认证快照起点或其后已验证增量）得到角色，而不是使用设备加入时缓存的角色。Owner 把 Alice 从 Admin 降为 Member 后，Alice 的全部设备随用户角色降权，但设备本身不被删除。不按设备登记另一套管理开关；用户角色改变后按当前角色与设备种类重新求权限。机器无管理权，不设独立 Owner 管理密钥。

**已确认：**撤销设备仅修改当前 Org。未来可另加跨 Org 移除提示，首版不执行跨 Org 撤销。

## 3. 谁能签什么

下表给出角色规则及建议的签名组合。符号 D 为当前有效个人设备签名，R 为已登记的有效恢复设备签名，N 为新设备对绑定请求的持钥证明。签名不只覆盖操作名称，还覆盖目标、Org、成员实例和操作内容。

**已确认：**管理动作由获授权的有效个人设备 D 签署，按当前用户角色鉴权；不设独立管理密钥。R 只能恢复密钥及授权本人的新个人设备，不能直接管理 Org、写文档或执行命令；日常操作不解锁恢复秘密。

| 操作                            | 谁可批准                                             | 建议签名/证据                                     | 生效结果与拒绝条件                                                                                       |
| ------------------------------- | ---------------------------------------------------- | ------------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| 创建 Org                        | 创建者                                               | 一个创世操作绑定用户、首设备与首代承诺，由 D 签名 | 固定创立记录及唯一 Owner；不能接受服务端替换的创立身份                                                   |
| 接纳新成员                      | Owner 或 Admin                                       | 批准者 D；绑定用户与首设备公钥的签名申请          | 新身份成为 Member；不能借邀请直接授予 Admin；申请不得被换公钥/Org                                        |
| 移除成员并启用新 Epoch          | Owner                                                | D；同一记录包含移除、新代承诺及历史包             | 一次提交全部生效或全部不生效；排除目标成员全部设备与 R；不能直接移除当前 Owner                           |
| Guest/Member/Admin 角色调整     | Owner                                                | D                                                 | 指定用户角色改变，设备随之改变有效权限；不能借此转移 Owner                                               |
| 加入自己的设备                  | 该用户的有效设备；全设备丢失时走恢复                 | D+N；恢复用当前 R+N                               | 设备直接绑定该用户，不依赖批准设备后续是否存活；不能绑定到他人身份                                       |
| 撤销自己的设备                  | 本人有效个人设备；全实体端丢失先恢复新个人设备       | D                                                 | 只撤销明确目标；不要求目标在线、不按祖先关系要求额外根签名；仅当前 Org；Owner 撤后须仍有有效个人设备或 R |
| 登记自己的机器                  | 建议由当前前端设备的用户批准                         | 前端 D、机器 N、已确认的配对证据                  | 机器归属该用户及目标 Org；公钥确认前、凭一次性码或仅登录均不能登记                                       |
| 向有效设备发当前密钥            | 持有当前钥的有效个人或机器设备，含合格 Guest；不含 R | 发送设备签名、当前收件资格与公钥、信封            | 每次按已验证账本重查；发送能力不授予写内容、执行或管理权限                                               |
| 向自己的新设备/机器补发当前密钥 | 同上；不限于本人设备                                 | 已生效设备登记、当前收件资格及签名信封            | 目标须已入账，补发不扩大任何用户角色                                                                     |
| 生成新 Epoch                    | Owner 或 Admin                                       | D；绑定新代承诺和历史密钥包，每设备发钥独立       | 独立新密钥，只发有效接收者；换代不改变成员/角色/设备资格                                                 |
| 转移 Owner                      | 当前 Owner                                           | 当前 Owner 的有效个人设备单方签名                 | 唯一 Owner 原子切换；前任默认 Admin；接任者须为有效成员且有有效个人设备或 R；不要求其另签同意            |
| 登记/替换恢复设备 R             | 本人有效个人设备                                     | D、R 的持钥与绑定证明；具体字段待审               | 普通更换先验证新 R 再撤旧；已泄漏时优先撤销；均不复活失效成员                                            |

Admin 请求移除成员只是发给 Owner 的请求，不是已生效的移除。Member/Guest 不能邀请其他用户、升降角色或旋转 Org 密钥。Guest 只读，但其签名仍用于持钥和本人设备流程；其余角色可在 Org 授权范围内读写及请求机器执行。机器无管理权限，恢复设备的直接操作另受恢复用途限制。MUST 拒绝未知操作和没有明确授权规则的入口。

建议 Owner/Admin 对另一用户的单台设备没有额外、隐含的管理入口；已有“移除用户”和用户自助撤设备即可。若需要远程禁用他人单设备，应另行确认，不从“Owner 最高权限”自动生成所有可能的 API。

## 4. 线性账本怎么验证与提交

### 4.1 状态与记录

首次加入不强制从创世回放：验证已认证设备签署的完整权限快照，再逐条验证后续增量。快照签名同时绑定协议用途、预期 Org/创世、位置/head、实际完整状态与防重放事实；不能用快照内部自称的 Owner 身份建立签署者信任。签署者须为已独立认证、当前有效的 Owner/Admin 个人设备，机器和 R 不能背书。独立包已有入口；产品的持久化、信任材料及接入验收另见实施起点，不改变普通记录格式。

安全码核对同时覆盖实际状态和 head；同位置不一致告警，位置不同先同步或核对共同位置。邀请者+服务端合谋仍可能欺骗尚未独立核对的新人；与另一已认证诚实成员核对能发现分歧，不证明历史每步合法或全球最新。完整历史保留作可选审计和历史密钥；快照不能跳过起点之后的坏链或回滚。

从可信创立记录重放得到的状态包含：成员身份/实例/角色、设备绑定/状态、当前 Owner 配置、密钥代次及发布记录、已处理操作、已验证链头。设备创建来源是审计信息，不是权限树。

普通记录正文只包含上一条记录 hash、提交设备签名公钥和完整操作，附一个提交者签名；操作内部可包含其他持钥/同意证据。使用 DAG-CBOR 固定数组与原始字节，完整记录 hash 连接可信创世，不逐条重复 Org ID、序号或通用操作 ID。创世用一个操作登记初始成员和设备。每次换代直接携带新钥加密上一代钥的历史包；每设备密钥信封独立交付。

共同的验证顺序是：

1. 检查规范编码、版本和长度，确认 Org 与前驱。
2. 从前一状态找签名公钥，检查设备、成员和操作权限；新设备只能用自己的证明申请加入，不能自授权限。
3. 校验全部签名、目标绑定、申请/配对证明和防重放约束。
4. 计算下一状态，以所验证的流尾 CAS 追加。服务端准入与客户端重放 MUST 使用同一规则。
5. 读回验证已提交原文后报告生效；同一读取页 MUST 全部验证并原子保存，不能保存坏页的前半段和页尾。

CAS 冲突 MUST 刷新后重新验权。签名原文先持久保存，丢响应先查询并核对原操作，不能凭超时声称失败或重复授权。无效记录、历史缺口、未知格式 MUST 停止，不降级普通 append、不自动换创立记录。

### 4.2 用户确认与提交时序分开

加入申请、接受和机器持钥证明 SHOULD 绑定稳定的 Org、身份、公钥、目的和一次性请求，不绑定会频繁变化的普通链头；最终批准/提交包装再绑定当前链头。普通链头推进不要求用户重复扫码或再次点击接受；换目标、公钥或权限须重新确认。

已申请不等于已入账。B 的批准先 CAS 成功、Owner 后移除 B，则新成员保留；移除先成功，B 未提交的批准必须失败。设备 A 加入 B 先成功、随后撤销 A，则 B 也保留。新规则不回溯撤销过去合法的设备登记。

申请 ID、待处理与取消放外部系统（可用 Convex 表），不要求都入权限账本。最终接纳仍绑定获批用户、公钥和持钥证据，不能让表被篡改直接替换接收者。已入账不能通过取消表项回滚；已确定提交前可取消，进入提交后不能保证撤回；结果未知 MUST 先核对原始提交。后端协调的精确状态和申请有效期仍待细化，不能由服务端状态替代客户端验证，也不按今天的时间否定历史。

### 4.3 登记与秘密投递的边界

**建议提交顺序：用户确认 → 登记 CAS → 读回验证 → 发放 key package → 接收端验证并解密。**可以预生成仅本地保存的信封，但不能在登记前交给目标或放入它能读取的托管入口。密文对持有目标私钥的人就是可用秘密，不能因为“已加密”就提前公开。

发放与换代记录 MUST 绑定授权依据和准确的公钥。发送前重新确认目标资格和当前代次；已知撤权即停止发放。发送前后发生并发变更仍受既有 JWT/新鲜度假设及明确的密钥换代边界约束，不宣称与所有数据流同时截止。密钥投递失败不撤销已生效登记；界面显示“同步失败：端到端加密密钥分发失败”，恢复时核对相同目标后重试。

### 4.4 中心化投递与安装进度（2026-10-09 修订，待接入验收）

采用中心化持久信箱，每个当前有效设备分别获得由其加密公钥封装的当前代信封，允许错峰在线；R 同样保留信封。换代提交并验证、本地安装成功后安排全设备分发，新设备入账安排当前代补发，其他合格持钥设备可以补齐。任务必须跨重启恢复，覆盖已提交但尚未安排分发的情况。

服务器按 Org、代次、接收设备提供缺信封与缺安装报告两种列表。客户端逐项重新核对已验证账本中的资格、公钥和代次，网关也核验信封；列表和投递进度不授予权限。已有信封但接收者离线时继续保留，不反复重新生成；R 不要求即时安装报告。撤权或再次换代后停止旧任务并保留可查询结果。

接收设备验证、核对承诺、持久安装后提交设备签名报告，绑定用途、Org、代次、设备、承诺和精确安装来源；发布设备用已验证发布记录作为来源，不伪造收到的信封。报告持久重试并幂等，接收上下文须覆盖安装后尚未报告的崩溃窗口。报告不证明持续持钥或当前资格，丢钥、错误信封可请求修复；旧代报告不得推进新代状态。细节见[白皮书 §4.1](whitepaper.zh.md#41-中心化密钥投递与安装报告)。独立包已有协调器、索引契约和报告流程；真实云端存储、认证、调度、界面及完整接入验收仍待完成。

### 4.5 协议扩展与账本更替（2026-10-17 新增，待审）

账本 v1 在生产环境首次开放创建时冻结，此后永久可验证；冻结点、冻结范围与固定样例见[基础规范 · 格式兼容性](../e2ee-foundations.zh.md#格式兼容性)。第 9 节中的待定事项须在冻结前完成格式审查。v1 永久认识一种扩展记录：**能力声明**（操作标签 9），正文为严格递增、非零的 u32 能力码列表（1 至 16 项）。

- 只有 Owner 或 Admin 的有效个人设备 D 可以签署；机器、恢复设备、Member 和 Guest 一律拒绝。
- 只增不减，不能撤销。声明之后的记录才能使用对应的新操作；使用此前未声明能力的操作，与未知操作一样 MUST 拒绝。
- 客户端不支持某项已声明能力时，MUST 验证声明之前的全部记录，在声明处以“需要升级”停止，展示已验证部分；不得报告账本损坏，也不得跳过声明继续验证。
- 写入方和服务端 MUST 拒绝自己不支持的声明，因此一项能力只有在实现它的版本上线后才会出现在账本里。当前版本不支持任何能力。

需要更换密码套件或创世级参数时，不改写旧账本：新建一个带新创世记录的账本，在旧账本末尾通过一项能力追加指向新账本的链接记录，参照 MLS ReInit。链接记录的格式随那项能力一起定义。

## 5. 新人扫码申请与成员邀请

**已确认交互目标：一侧提出申请/邀请，另一侧确认；双方可错峰在线。**不把协议所需的后台签名变成无意义的第三次审批。

1. Owner/Admin 展示工作区二维码或链接。入口识别目标加密 Org；当前 workspace 是产品入口，不另创建 Team 或跨 Org 权限。
2. 新人扫码后注册/登录，客户端生成独立设备密钥并提交用户关联，提交邮箱、公钥和签名申请。已有身份复用已验证身份关联，不复用另一台设备私钥。
3. 前端向审批者展示 Org、新人邮箱/身份、公钥摘要及是否已额外核验。双方 MAY 通过线下或其他 IM 比对公开摘要，不交换私钥。
4. 当前 Owner/Admin 确认接纳为 Member，客户端在最新账本验权并提交加入。申请者自己的签名表示其加入意愿；不再要求其为无关链头变化确认一次。
5. 新人先验证上述快照及后续增量，确认本人已入账；合格持钥端验证入账后，将当前代 key package 加密给新人已登记的设备及已入账恢复设备。Admin 或其他合格持钥设备可发送，无需 Owner；收到并核验后才显示可访问内容。

已有账号的定向邀请沿用相同规则：签名邀请按对方公钥加密，对方确认即提供申请/接受证据，授权端后台完成提交和发钥。没有公钥的新用户先走注册申请，不向“仅有邮箱”的目标猜测公钥或提前发送 Org 密钥。Admin 发钥的前提是仍有权限且持有可用当前代；换代尚未完成时可继续按当前有效代发送；不得向已失权接收者发钥。

二维码是申请入口，不是自动加入凭证，也不含内容密钥。建议绑定 Org 创立摘要以便跨信道核对；从不可信网页获得二维码仍不能独立证明显示名称或真人身份。正常批准和自动检查完成后可先用，人工安全码核对可以稍后进行；机器配对的显式确认不因此取消。首次未额外核验 MUST 如实显示，不能打“已独立验证”标记。目录不能覆盖已固定公钥；密钥变化与核验提示的最终样式留给交互 review。

## 6. 机器接入：命令、位置与公钥确认

### 6.1 用户看到的流程

```text
前端选择 Org，生成连接命令
  → 用户在目标机器运行命令，领取/兑现一次性配对凭证
  → 机器生成密钥、回传公钥并证明持钥
  → 前端显示机器位置与公钥摘要；机器本地显示相同摘要
  → 用户核对，点击授权
  → 账本登记成功并验证
  → 前端按机器公钥发送 key package
  → 机器验签、验证登记与 Org，解密后完成连接
```

命令绑定当前 Org、前端设备及这次配对；机器公钥尚未知时不能声称已经绑定了目标机器身份。收到目标持钥证明并经用户确认后，才固定其公钥。命令名称和参数是工程定稿，不在这里提供尚不存在的可执行 CLI。

one-time auth key MUST 仅用于该配对会话，不能兑换普通账号的长期凭证、自动取得 Org 成员权或直接解密。建议不可猜测、短期有效、可取消，并在首次合法关联时绑定一台机器的准确公钥；原会话重试不得替换公钥或被另一台机器复用。仅窃取命令/一次性 key 不足以获批，仍需前端对目标摘要的显式确认。原始凭证不写账本、诊断日志或分析事件。

### 6.2 位置与身份是两项信息

前端 MUST 展示服务观察到的机器连接 IP 所对应的大致位置，供用户判断“这是否是我预期位置的机器”，不是拿用户自报的城市作为可信证据。地理信息 SHOULD 标为估算；VPN、中继或未知地址可能导致位置不同或不可识别，界面必须如实说明，不能编造精确地址。位置服务的选择、查询隐私与留存尚未定，不默认把原始 IP 交给新的第三方。

机器名称和 IP 位置是辅助提示。前端与机器本地 MUST 对同一完整公钥材料生成一致摘要；建议摘要同时绑定协议、Org 和配对会话，避免将另一会话的确认搬过来。用户看到的摘要与最终登记、加密用的公钥 MUST 完全一致。前端授权后不得替换目标；机器也 MUST 核验命令绑定的前端身份、签名和 Org，不能只信服务器说“已授权”。

设备授权的远程诱导风险可参考 [RFC 8628 §5.4](https://www.rfc-editor.org/rfc/rfc8628.html#section-5.4)：确认实际发起配对的设备很重要。这里仅借鉴该威胁分析，不宣称这个自定义配对/密钥流程已实现 OAuth Device Grant 或继承其安全保证。

### 6.3 授权后的权限

机器作为某个用户的设备进入 Org，建议归属生成命令并批准连接的用户，不能由服务端任意指定账号。key package 只包含获准内容所需密钥与核验上下文，MUST NOT 因为连接成功就带上其他设备私钥或恢复秘密。

“机器能解密”与“哪些人能让机器执行”不是同一决定。机器不能代表用户管理 Org；已确认 Owner/Admin/Member 可在 Org 授权范围内请求执行，Guest 只读，R 不能直接执行。首版沿用机器所有者共享给有执行权成员的现有方式；复杂逐成员/操作/目录配置与新隔离方案留待以后。请求指 Agent 开始一轮、远程保存文件、终端操作等机器操作，复用现有任务系统；结果未知先查固定请求编号，不自动重跑任意 shell。精确请求与目标绑定留到 API review；仍须验证设备/用户、Org、目标、参数、请求标识和期限，并持久去重，不能凭入组或解密成功跳过执行权限判断。

授权提交前取消、超时或公钥不符 MUST 不入账、不传钥；提交已发出时不能声称取消就已回滚，结果未知 MUST 先核对原记录。记录已成功、传钥失败可以恢复投递，不重新创建机器。仅有配对 key 不得自动授予权限；泄漏可能造成会话争抢/拒绝服务，用户可取消并创建新会话，仍须防止被诱导批准错误机器。

## 7. 备份、撤权与无法继续的情况

### 7.1 强推荐，不冒充已经备份

所有端及 Owner 首建/移交 MUST 允许用户明确确认风险后跳过恢复设置，不能阻断注册、加入或正常使用。恢复文件提供已选定的恢复库入口，验证可用的 Passkey PRF 可作为另一入口；首发入口清单与 PRF 支持范围仍须明确，不设置额外加密密码。建议给出“设置恢复方式”与“暂时跳过”，再说明所有设备丢失可能无法恢复旧加密数据；确认次数不在本稿写死。强推荐恢复方式或手机配对，Owner 全部设备与恢复材料丢失可能失去旧 Org 内容及管理入口，须明确提示。

选择设置时仍 MUST 回读并实际解锁云端恢复包，成功才报告“已备份”。跳过后只报告“尚未设置恢复”，可稍后补设；生成恢复设备公钥、收到密钥信封、配对完成都不等于已有可恢复副本。跳过不增加或削减 Org 角色。原型不能把备份摘要存在当成强制入组或持钥证明。

全部设备与恢复材料丢失后，旧秘密不保证可找回；账号和新 Org 仍可使用，旧 Org 需重新建立身份信任。Owner 没有剩余有效设备或恢复材料时不能承诺服务端接管；这项风险要在跳过时如实提示，而不是偷偷添加恢复后门。

### 7.2 恢复设备与完整恢复路径

每个用户在每个工作区 MUST 使用独立 R；同一用户在该工作区的多个实体设备复用其有效 R。恢复文件提供恢复库解锁材料，云端保存由客户端加密的各 R 私钥包，不持 R 私钥，也不能从文件预先生成未来工作区 R。

首次设置 MUST 完成客户端生成 R、解锁恢复库、加密上传私钥包与回读解密、由本人有效个人设备登记 R、给 R 保存当前代信封，以及实际验证该工作区能恢复。这些是完成条件；精确保存顺序、中断恢复与并发处理仍待格式定稿，不能据此假定整个流程原子完成。上传与账本登记是可恢复的多步流程，不承诺跨存储原子。普通换代只使用 R 公钥封装新钥，不要求打开恢复文件。Passkey PRF 可以是同一恢复库的另一入口；普通登录 Passkey 不是恢复能力，精确包装格式待定。

恢复时验证可信创世材料、账本及 R 当前资格，解开当前代信封并核对承诺，再沿历史包取得旧钥。新个人设备 C 生成独立密钥，由 R 授权并证明持钥，入账后使用 C 并清理临时 R 秘密。只有 R 有效且所需密文完整时才无需管理员在线。R 不能直接写内容、执行、管理或发钥；C 依据当前用户角色取得权限，不因恢复升权。

普通更换先验证新的再撤旧；确认泄漏时优先撤销。单个 R 泄漏影响该工作区，恢复库解锁材料连同对应密文泄漏可能影响所有已覆盖工作区。删除文件或更换入口不使已复制的 R 私钥失效，须分别替换受影响工作区的 R 并撤销、换代；部分失败要保留可继续的进度。撤 R 不连带撤它已批准的 C，应另外检查可疑设备。被移除后重新加入须新成员实例与新 R，不复用已退役公钥。

逐工作区显示恢复状态，旧验证时间不能冒充最新一代已测试；文件不是全部内容的离线备份。详细说明见[白皮书 §6](whitepaper.zh.md#6-备份与恢复)，恢复库字段、完整离线导出范围仍待定稿。

### 7.3 移除成员与自助撤销设备

Owner 移除成员 MUST 提前持久保存候选新钥和签名原文，以同一条记录、一次 CAS 同时移除成员并启用新代。服务端准入和客户端回放使用同一规则，失败不得只生效一半。新代接收者排除该成员全部个人设备、机器与 R。读回验证后异步发钥；投递不在该原子提交内。

未知结果核对并重试原字节；确认冲突后终结原尝试、刷新并重新验权，不能静默重签。提交前独立保存可恢复新钥的协议及其是否为 Beta 前提，仍待明确。

本人撤自己的设备不自动获得换代权，也不连带撤销其他设备。普通成员撤设备后标记需要换代，再由有权限的 Owner/Admin 换代，调度和等待处理仍需细化。等待期间诚实端暂停以旧钥加密新更新与快照；本地编辑可保留，已有密文仍按当前权限和宿主规则上传，旧代可读。

已知撤权立即拒绝后续授权操作；云访问与机器新执行仍遵守最多 15 分钟的总窗口，投影、凭证、缓存、长连接不能各自延长。JWT 无法收回旧钥，服务端也不能证明每份旧密文都在撤权前生成。没有跨内容流的原子截止保证。

## 8. Review 场景与实现边界

新增快照验收：错误签署者/Org、正确 head 搭配不受签名覆盖的状态、缺少必要字段、坏增量均失败；原邀请者自证不算独立核对；不同位置不误报分叉；同位置不同状态明确告警；双进程 R 恢复验证持久认证材料与增量，不临时要求管理员在线。历史包及旧承诺必须认证到接受状态，不能仅靠解密成功接受权限。恶意背书者亲自签署的结构合法虚假状态可能被接受，单凭验签不能识破；用独立核对发现其差异，不写成自动拒绝的承诺。旧全量测试不覆盖这些用例；10k/100ms 门槛已撤销，不是通过。

以下是应验证的可观察结果，不是本轮已运行测试：

| 场景                                        | 预期                                                       |
| ------------------------------------------- | ---------------------------------------------------------- |
| A 批准 B、B 批准 C，撤销 A                  | 仅 A 失效，B/C 有效；移除其用户才使该实例全部设备失效      |
| Admin 的一台设备被撤销                      | 用户角色及其他设备不变；撤设备不能偷偷变成降级用户         |
| Owner 将 Admin 降级，其另一设备随后批准新人 | 按提交时用户角色拒绝，不能使用设备加入时角色               |
| Owner 离线，Admin 批准已申请新人            | Admin 自己传当前密钥，能完成加入，不出现等待 Owner 发钥    |
| 新人申请后链头正常推进                      | 不要求重复接受；公钥/Org/权限改变则不能复用原确认          |
| 批准者撤权与接纳并发                        | 先成功的提交决定结果；后来撤销不连带取消已接纳用户/设备    |
| 手机没有备份并明确跳过                      | 继续使用，显示无恢复保障；不能伪报已备份或偷偷上传明文秘密 |
| 一次性命令被另一台机器拿到                  | 不自动获批；目标摘要不同必须重新由用户核对，不能继承原授权 |
| 配对后服务端替换机器公钥、Org 或前端身份    | 校验失败，不传钥、不登记；IP 相同不能覆盖失败              |
| 入账后传钥失败、客户端重启                  | 保留已生效登记，可核对后补发；不凭超时重复注册             |
| 成员/目标设备撤权后重放旧 key package       | 不恢复资格；不能承诺擦除已经泄漏的旧秘密                   |
| 全实体设备丢失、R 有效且收到当前代包        | 可恢复当前和历史钥并登记新个人设备，不依赖管理员此刻在线   |
| R 未入账、已撤销或缺最新密钥包              | 不宣称恢复成功，不绕过账本或凭空恢复新钥                   |
| R 批准 C 后撤销 R                           | C 保留，R 不能继续授权和接收新钥                           |
| Guest 恢复、R 直接发机器命令                | Guest 不升权；拒绝 R 的直接执行                            |
| 备份位置返回另一 R 或创世                   | 不接受替换；正确解密也不自动授予可信锚资格                 |

独立包与产品接入的状态分开记录，见实施起点。已有账本、Guest/R 和密钥分发基础能力，不能据此宣称本稿新增的原子移除、恢复库和全平台产品流程已完成。有限模型、形式化证明和真实服务验收也不互相替代。

## 9. 尚未定稿的范围

D01–D22 的方向已确定，包括逐工作区独立 R、Owner 单方移交、提交前可取消/提交后先对账、一次提交移除并换代。不得再把旧共用 R、双方签署移交或两次提交的成员移除当作当前方案。

仍需细化：恢复库与可信锚编码、可选离线导出、各平台私钥保存、新代钥独立备份及其发布门槛、自撤设备后的换代衔接、Beta 具体功能清单、Owner 丢失全部密钥后的账号注销规则，以及容量/申请期限/留存参数。复杂机器共享配置和本地内容额外加密已排除，不列为当前阻塞。

“没有备用设备”不是非法身份；“有解密密钥”不是管理权；“拿到一次性码”不是设备授权；“有签名”也不等于当前有权限。

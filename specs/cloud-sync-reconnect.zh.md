# 云端同步重连节奏

Status: draft
Translation: current

[English](cloud-sync-reconnect.md)

一台机器断网，或者它访问云端所经过的本地代理挂掉，两个小时都没人发现。这段时间
里，承载组织、成员与权限信息的云端控制面订阅（一条 WebSocket）始终连不上。此时
机器对用户的承诺其实很朴素：网络一恢复就尽快回来，在此之前保持安静。它对云端的
承诺也一样，因为同一个坏掉的共享代理背后，所有客户端会在同一时刻一起失败。

重试节奏就是这份承诺的全部。长时间故障中仍以固定间隔重试的客户端，和对着一个已经
挂掉的服务猛敲没有区别：上面那次两小时的故障产生了约 450 次连接尝试，从第一分钟
到最后一分钟都是每 8-24 秒一次。因此只要失败还在持续，重试间隔就必须继续增长，
上限以分钟而非秒计，并保留随机抖动，避免大量机器在恢复时彼此同步。

重试变慢不等于恢复变慢。之所以可以退到分钟级，是因为上限并不是唯一的回来方式：
当机器上的其他信号证明网络重新可用时——目前是内容同步数据面恢复健康——正在等待的
连接会立即发起，而不是把剩余的等待走完。这个信号很廉价，在传输不稳定时可能反复
抖动，所以它最多每分钟额外触发一次尝试；而一次故障中的第一个信号，也就是真正带来
恢复的那个，永远不会被丢弃。

恢复信号往往到达于"当下无事可释放"的时刻：客户端可能正睡在自己的两次重试之间，或者
已有一次尝试在途、且即将失败。这样的信号会被记住而不是被花掉——下一次连接尝试不必等
待期间被装上的那段延迟——并且只有真正跑过的尝试才算是对它的回答。否则，网络恰好在错误
时刻恢复的机器，就会一直等待一个健康传输永远不会再发出的第二个信号。

连上并不等于已经恢复。刚连上几秒就断掉的连接算作失败，退避继续增长；只有能稳定
保持的连接才会重置退避。控制面与内容同步面各自独立退避，互不拖累：两条连接常常
因为同样的原因失败，但各自依据自己的信号恢复。

未决：目前只有内容同步面提供上线信号，因此未接入内容同步的机器只能依赖上限本身。
这条连接之上的更高层重试（例如 PR 轮询的首次同步等待）仍保留各自的固定间隔，不在
本文范围内。

证据：上述故障来自机器本地的 CLI 日志（`~/.lody/logs`，2026-09-16 04:50-06:50
UTC），无法从本仓库复现。实现：`apps/cli/src/lib/cloud-sync-reconnect.ts`，在
`apps/cli/src/lib/cloud-cli-port.ts` 组装，由 `apps/cli/src/commands/start.ts`
接入上线信号；退避曲线、强制重连下限与稳定判定由
`apps/cli/src/lib/cloud-sync-reconnect.test.ts` 在假定时器下验证。上游客户端自身的
重试常量由本仓库查证，但不受本仓库控制。

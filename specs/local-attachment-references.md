# Direct local attachment references

Status: draft
Translation: current

[中文](local-attachment-references.zh.md)

## Decision

Same-desktop ordinary files are paths, not uploaded objects or registered capabilities.
A `local_attachment` carries the owning machine, absolute path and display metadata.
The original file stays where it is. Pathless or generated content is saved to a
persistent local attachment directory before sending, then follows the same path
representation. There is no ID-to-path registry, submission binding, resolve RPC or
inheritance operation. Resend, queueing and same-machine forks reuse the payload.

Absolute paths consequently become part of conversation content and its existing
synchronization. A path identifies a file; it does not grant permission to read it.
This revision replaces the earlier draft's opaque registration and per-turn
inheritance design. The trade-off is intentional: ordinary files have normal path
semantics, rather than a second attachment authorization and storage protocol.

## Preparation and execution

The shared preparation flow selects its route once. A known native machine
identity matching the target uses local preparation. Otherwise, clients use the
existing transfer route. A selected local route reports failure without silently
uploading ordinary files. Originals require no preparation RPC, copy or content
hash. Generated bytes are completely saved before the path is returned; failed
preparation preserves the draft. These files remain available for retry and history;
automatic reclamation is outside this change.

At actual execution, the host checks its machine identity, the existing requester
authority and the path's regular-file status. Ordinary paths are passed as encoded
ACP `file://` resource links. The Agent's sandbox remains its read boundary; a
selected path outside the working directory does not widen permissions. Missing,
unreadable and sandbox-denied files report errors. Original files are never modified
or deleted by attachment preparation, and their current contents are read at use
time. Symlinks are resolved at use time; no earlier target or bytes are frozen.

Prepared paths are not transferable to another machine by changing `machineId`.
Cross-machine resend or fork requires an explicit transferred replacement. Native
preview uses the existing file-resource boundary. Explicit downloads from another
device use the authenticated file RPC and its existing workspace path restrictions;
a local attachment does not exempt arbitrary host files from those restrictions.
Generated files outside allowed download roots may remain available only locally.
Sharing/export discloses omitted local content or refuses a complete attachment
export; it never uploads original paths implicitly.

## Images

Images remain image payloads. Same-desktop images with a source path use that file
directly; preparation does not copy it. Pathless images are saved once before
sending. Preview and Agent execution do not wait for cloud authentication or upload.
An authorized background uploader reads the local file, retries after connectivity
returns and resumes from durable metadata and receipts. Publication retains local
identity for offline reads. Receipts reconcile history, frozen inputs and queued
references, including messages written after upload completes. Remote targets retain
the existing image transfer route.

ACP receives visual image bytes and a resource link to the local file. Source edits
are visible to subsequent local reads and uploads; moving or deleting an unpublished
source makes it unavailable. Sending does not freeze the file contents. Preparation
and cleanup never modify or delete original files. Pathless image storage remains
subject to quota and is retained while frozen inputs may reference it. Protected
plaintext preparation remains unsupported. OSS composition remains local-only and
gains no cloud capability.

## Compatibility and evidence

New path references do not enter legacy file backfill. Existing transferred
`file`/`image` inputs retain their transport semantics. The removed opaque registry
format has no compatibility resolver; old references without a path are unavailable
and require reselection. Unsupported execution inputs must fail the complete
request rather than disappear during parsing. No attachment-specific version
preflight is added.

The implementation is owned by shared preparation, Electron's local file boundary,
`session-local-attachments.ts` for generated-file saving and actual reads, and
`message-handler.ts` for execution and image upload. The
[attachment lifecycle](../.agents/docs/cli-lib-session-files.md) explains the code.
Packaged-app offline/restart behavior and live cross-device image upload remain
manual acceptance requirements; this document does not claim they have passed.

# E2EE 控制账本与内容信封：第一阶段

Status: draft
Translation: pending

## 当前设计入口

更新后的完整类型、API 与对账设计见[独立权限账本设计](e2ee-ledger.zh.md)。
该稿采用精简单签记录，取代此前通用多签、逐条 OrgID/序号/操作 ID 的候选格式。
下文保留现有原型实现及内容信封说明，不是新格式定案；代码尚未迁移。
历史密钥方案也已更新：历史包直接随换代记录入账，每设备发钥仍独立；下文的
`HistoryPublisher` / `StreamsHistoryRemote` 独立历史流仅是待替换原型，不再是目标设计。
先完成独立包设计与验证，再恢复 Lody 接线。
恢复目标已改为独立账本中的恢复设备 R，复用设备登记、发钥及撤销；下文用户身份
私钥、恢复公钥及相关接口是旧原型，不应继续作为新恢复 API 的依据。

## 最新意图与原型差距

目标设计现已改为用户身份直接绑定设备，角色从用户读取；撤设备只撤明确目标，
不连带其曾批准的其他设备。Admin 可接纳普通成员并发当前密钥，不等 Owner；
生成新代由 Owner/Admin 负责。各端及 Owner 恢复强推荐，可以确认后跳过，不能以备份缺失阻断。
新人可扫码注册、提供邮箱/公钥并申请，由有权方确认；机器使用一次性配对和
前端对位置/公钥摘要的确认，才登记及传钥。位置只是辅助信息，不是密码学身份。

**已实现扁平设备权限与独立内容信封。** 已去掉父链、连带撤销和按祖先关系要求身份根的
分支；同一 Org 内有效个人设备可撤本人任一设备，角色始终从当前用户读取。
异步申请、Admin 发钥、可跳过备份和机器配对仍未接入。机器管理权已禁止，跨 Org
撤设备首版不做；不设独立管理签名，转让后前任默认 Admin。
内容层可对真实 CRDT 字节加密、签名并严格解包，已有 SDK 增量 provider，尚未接入应用的
快照来源证据、附件或机器执行路径，不能据此启用生产 E2EE。

## 使用场景与边界

管理员撤销 B 与 B 邀请 C 同时发生时，以同一控制流的 CAS 提交顺序决定权限。
邀请先提交则 C 保留；撤销先提交则旧邀请冲突，B 刷新后不能再提交邀请。
离线签名时间不改变顺序。这不是 DAG，也不使用 MLS。

本阶段实现可独立测试的签名 hash chain、提交驱动及显式选择的 Org 权限策略，
不改变现有产品行为。已确认首版仅 Owner 最终移除成员；Owner/Admin 均可完成内容换代；Admin 可
邀请普通成员，不能任命 Admin。所有用户可用有效个人设备撤销本人指定设备，
不连带其他设备。`ownerManagedTeamPolicy` 仍是显式选择，产品未自动启用；完整
恢复和 Epoch 协议仍未接入，这些范围确认不是对整份实验协议的批准。

产品边界已确认为新建加密 Org，不另引入 Team。现有 `team.ts`、`Team*`、
`ownerManagedTeamPolicy` 与 `lody-team-*` 是原型历史命名，不代表另一个产品层；
本轮将 Org genesis/action 签名域升为 v3，外层 control/v1、页级 journal/v2 及
Streams 分帧不变。旧 v1/v2 动作拒绝解码；旧创世数据在新版导出不同锚点，旧 journal
拒绝且原样保留，包含只有 pending 的情况。没有自动迁移、清空或重设信任锚点。

## 信任与验证

客户端从经过可信引入的 Org 创世摘要及初始状态重放账本。服务器不能单独替换
这个锚点。应用策略必须从上一个已验证状态查找设备公钥、成员实例和权限，校验
动作全部字段，并指定全部必需签名；设备权限与用户角色取交集，不设额外管理签名。
核心校验 Org、前驱、操作 ID 唯一性、规范编码及每个必需签名后才接受新状态。
未知操作、未知版本、缺失记录或无效签名必须停止，不能跳过坏记录继续授权。

一个操作的所有签名绑定完整事件及有序签名者 ID 列表。具体负载先由应用编码为
字节，再参与签名；核心不理解或加密负载。身份凭证和 Epoch 密钥不得以明文负载
发送。Org 动作已有规范编码和多签要求，尚未提供控制负载加密。

## 旧原型规范编码（实现记录，不是新格式定案）

线格式是无空白的 ASCII JSON 数组：

```text
event = ["lody-control/v1", genesisHash, previousHash, operationId,
         actor, memberInstance, device, kind, payloadHex]
wire = [event, [[signerId, signatureHex], ...]]
signingBytes = UTF8(JSON.stringify([event, sortedSignerIds]))
recordHash = SHA256(UTF8("lody-control-record/v1\0" + wire))
```

哈希和公钥为 32 字节，小写 hex；操作 ID 为 16 字节随机标识；Ed25519 签名为
64 字节。身份、实例、设备、动作和签名者 ID 使用 1–128 位 ASCII 字母、数字、
下划线或连字符。签名者 ID 严格升序且不重复，1–8 个。负载至多 64 KiB；记录
至多 140 KiB。解码后重新编码必须逐字节一致，拒绝空白、转义别名或多余字段。
签名与 SHA-256 使用 Web Crypto；私钥可以保持不可导出。验签统一使用固定版本
`@noble/ed25519@3.2.0` 的严格模式（`zip215: false`），SHA-512 使用平台
Web Crypto，不依赖各端原生 Ed25519 验签的宽松差异。所有签名公钥必须是规范
编码、非零素数阶子群点；签名 R 必须规范且属于该子群（允许单位元 R），S 小于
子群阶。曲线计算由库实现，算法不可用时失败、不回退。此配置严于库的严格模式
单独提供的检查：它另行排除混合阶公钥和 R。

## Org 权限策略

v3 在每台设备的签名登记中明确记录 `canManage`。它是控制账本操作的权限上限，
不是独立角色：有效权限还受用户当前角色约束。`false` 的个人设备仍可作为内容
接收者，但不能发控制操作或接受 Owner 移交。首版机器必须为 `false`；登记不能
缺省此字段，不能由角色或设备类型自动补上。普通个人设备由批准方明确授予
`true`；首次 Owner 设备必须能管理。机器命令调用者权限是另一个尚未接入的边界。
创世与移交不要求备份承诺；备份是否实际可恢复只能由恢复流程验证。
撤销只影响当前 Org，`requiresKeyRotation` 不阻塞合法设备按当前代次继续上传；
换代完成前旧持钥者若取得这类新密文仍可能解密，不能以 JWT 失效冒充密码学隔离。

`deriveTeamAnchor` 对公开创世数组计算 SHA-256，绑定协议、随机 nonce、Owner
身份/成员实例、恢复签名与解密公钥、首台个人设备的两把公钥与明确设备权限；不包含独立管理钥或备份
承诺。它验证签名公钥、字段格式与密钥用途分离，但不替代创立者身份核验或备份
解锁验证。加密公钥目前只做编码/去重检查；未来密钥封装层必须在释放秘密前执行
X25519/KEM 的有效性检查，不能把接收者列表视为已完成加密握手。
创世状态包含唯一 Owner、配置版本 0。设备及恢复接收者按 `(用户, 成员实例)`
归属；外部账号表不能直接修改这个状态。

所有动作都在前一已验证状态取操作者的有效个人设备公钥。Machine 可以成为
内容接收者，但不能发控制操作；设备须声明 canManage，角色不自动授予该能力。

| 动作             | 必需权限与签名                                                        | 状态变化                                           |
| ---------------- | --------------------------------------------------------------------- | -------------------------------------------------- |
| `member.add`     | Owner 或 Admin 的有效管理设备签名；新成员身份根和首台个人设备共同确认 | 只加入普通成员，使用未曾用过的成员实例             |
| `member.admit`   | 指定 Owner/Admin 的当前管理设备签名，加申请者独立身份及设备签名       | 异步申请批准为普通成员；消费一次性申请             |
| `member.cancel`  | 申请者设备对当前记录签名，加原申请的双签名                            | 只取消未消费的本人申请，不撤销已加入成员           |
| `member.remove`  | 当前 Owner 有效管理设备签名                                           | 删除目标实例全部设备及恢复资格，不能删除 Owner     |
| `member.role`    | 当前 Owner 有效管理设备签名                                           | 在 Admin/Member 间切换；不能借此改变 Owner         |
| `device.add`     | 本人的有效个人设备签名、新设备持钥证明                                | 直接绑定用户；批准设备仅留在签名历史中供审计       |
| `device.revoke`  | 本人的任一有效个人设备签名                                            | 只删除该成员实例的指定设备，保留其他设备及恢复资格 |
| `owner.transfer` | 当前 Owner 与接任者的有效管理设备签名                                 | 旧 Owner 降为 Admin，新 Owner 唯一生效，配置加一   |

`device.revoke` 仅作用于操作者本人的成员实例，不要求 Owner/Admin 角色或身份根签名；
仍需有效且 canManage=true 的个人设备签名。
已登记设备不依赖批准者之后是否有效；被攻破设备在撤权前登记的恶意设备也不会
自动消失，须另行明确撤销。两台本人设备并发互撤，先 CAS 成功者保留；另一条
旧头冲突，已撤设备即使重新签署新头也没有权限。无旧设备时走
尚未实现的恢复入口，不能只凭登录 token 撤销加密身份下的设备。

动作负载是小写 hex 编码的 ASCII 数组
`["lody-team-action/v3", actionTag, configVersionDecimal, ...fields]`，最多 4096
字节；版本号为无前导零的非负安全整数。字段顺序由 `team-codec.ts` 显式定义，
拒绝多余字段、别名及未知动作。外层 `kind` 使用 `team-member-add` 这样的
连字符形式；内部固定 tag 保留 `member.add`。每个动作必须匹配当前 Owner 配置。
`device.add` 的字段为 `[deviceId, signingKey, encryptionKey, kind, permission]`，`device.revoke`
为 `[deviceId]`，不再接收 `authorization` 分支字段。permission 只能是 `manage` 或 `none`，
对应 canManage 的 true/false。创世域为 `lody-team-genesis/v3`。

签名者 ID 是固定职责槽位，如 `actor-device`、`joining-identity`、
`new-device`、`accepting-device`，不是由消息
自行声明可信公钥。旧 `member.add` 和设备配对仍要求签署同一完整记录；
新增成员申请使用独立双签名，不因无关链头推进要求申请者重新确认。
首版要求异步接受：签名邀请按接收者公钥加密并托管，接收者稍后解密、验签并签名
接受；双方无需同时在线。邀请/接受绑定 Org、双方身份与邀请者实例、权限、设备
持钥证明、一次性标识及有效期；普通链头变化不要求用户重新确认。最终提交仍在
当前状态验权并 CAS，过期、重放或邀请者已失权则拒绝；入账前不发当前内容密钥。
批准的 Admin 可直接发信封，不等待 Owner；另获准换代，但不扩大成员管理权。
目前已实现独立申请及 `member.admit/cancel` 包装；加密托管、发钥及产品入口尚未接入。

独立申请为规范 ASCII JSON `[body, identitySignatureHex, deviceSignatureHex]`，
两份签名覆盖相同 body：`["lody-join-request/v1", genesis, requestId,
approverUser, approverInstance, expiresAtDecimalOrNone, memberAddPayload]`。
末字段复用 v3 `member.add` 的完整成员编码，内部配置固定为 0；不绑定可变链头。
requestId 为 16 字节随机值；外层 `member.admit/cancel` 各包含这个完整申请字符串，
仍受动作 4096 字节限制。申请只是持钥同意，账号与公钥的可信对应仍须核验。
批准时指定用户及成员实例须仍有邀请权限；换一台合法管理设备无需重做申请。
消费键为 `(申请身份签名公钥, requestId)`，批准或取消后不再复用；移除后加入
必须新实例、新申请。取消先提交阻止批准，批准先提交后取消不能撤销成员资格。

有效期无默认值，具体产品期限待确认；`null` 必须显式选择。若设置，到期时刻起
不得新批准，但已入账的成员不因申请过期失权。`assertJoinRequestFresh` 只提供
检查函数：可信后端必须在原子准入点检查时间，历史重放不能使用今天的时钟。
当前客户端和合成测试不证明生产已执行这条检查；申请签名也不等于传输已加密。

设备撤销保留该实例的设备 ID/密钥墓碑；不能换个 ID 重新使用已撤设备的钥匙。
移除成员后再邀请必须创建新实例并重新签署，原有用户身份/物理设备可以在显式
确认后沿用，但旧实例的签名和其他旧设备不会自动生效。设备 ID 在成员实例内解释。
没有独立管理密钥；转回原 Owner 也不能复用旧配置或旧签名。

移交不要求备份摘要；用户明确确认风险后可以跳过备份。选择设置时必须实际
验证恢复包才报告已备份，不以备份声明冒充持钥证明。只转移 Owner 不取消
前任的内容访问，也不清除未完成的换代要求。

成员或设备撤销置 `requiresKeyRotation=true`；Owner/Admin 的 `epoch.publish` 清除发布义务，
但不表示所有设备拿到密钥或所有同步通路已经切代。
`listTeamRecipients` 只列有效实例中的设备及恢复加密公钥，不发布密钥。
列表不是新鲜度证明，`requiresKeyRotation=false` 也不代表内容层已经就绪。
根身份单独恢复（没有任何旧设备）、根密钥轮换、Owner 灾难恢复和完整 Epoch 切换
属于后续协议；未知入口必须拒绝，不能复用普通加设备操作绕过。

## 内容信封（实验版）

### 恢复文件包装（独立实验格式）

恢复文件为规范 UTF-8 JSON `["lody-recovery-file/v1", backupIdHex16, keyHex32]`，
ID 与 32 字节密钥独立安全随机生成，文件至多 256 字节；不包含 URL、登录凭证或设备私钥。
备份头为 `["lody-recovery-backup/v1", backupId, expectedIdentityHash32, revisionDecimal]`。
其中身份指纹与材料版本由调用方独立提供，不从下载包自动接受；身份秘密的序列化及
恢复后公私钥校验仍由身份模块负责。1–2048 字节材料使用固定 XChaCha20-Poly1305，
每次新加密生成 24 字节 nonce，头作为 AAD；帧为 `u16be(header.length) || header || nonce || ciphertextAndTag`。
文件和对应密文足以离线解密，登录不是第二个密码学因子；旧版本预期值仍能打开旧包，
此层不证明最新、不恢复成员权限、不隐式替换身份。Electron 已接主进程原生文件
导出入口：新建而不覆盖，写入后同步并回读，只返回备份密文与公开定位信息。
文件重新选择现有原生入口，主进程有界读取并解密，验证公私钥配对及当前本地身份，
只返回公开匹配信息；不替换身份，不从待验证密文接受另一个身份指纹。
实际上传包回读、Passkey 和全丢失设备恢复尚未接入；不因本地
导出或纯加解密成功报告已备份。保存成功后后续失败可能保留尚无配套备份的文件。

用户身份材料另有规范数组 `["lody-user-identity-secret/v1", signingPublicHex32,
signingPkcs8Hex, encryptionPublicHex32, encryptionPkcs8Hex]`，至多 2048 字节，
各 PKCS8 至多 128 字节；不是设备包。身份指纹为
`SHA256(UTF8(JSON.stringify(["lody-user-identity/v1", signingPublicHex32, encryptionPublicHex32])))`。
恢复须核对独立预期指纹、严格签名持钥证明及 X25519 公私钥配对，不因 AEAD 成功
接受错误身份材料。返回私钥句柄不可导出；生成时为持久保管临时导出，不能宣称
硬件不可提取。Node 用户身份现有独立显式存储：包装、回读校验后原子保存，
加载失败不自动换钥；恢复仅能写空库，不覆盖已有身份。用户与设备数据库及系统
包装域分别隔离。Electron 已接显式 create/load IPC，主进程按账号和认证域绑定，
排队后和返回前复核会话，只返回公钥与指纹；不随登录自动创建用户身份。
云端备份、恢复 UI 及新设备账本授权仍未接入；
真实 SQLite/合成系统包装测试不等于真实系统密钥环或产品恢复验收。

内容与控制记录分别编码，不把文档字节塞进控制流。`ContentCipher` 接收显式
Org genesis、代次、逻辑资源 ID、用途、作者身份/成员实例/设备及 32 字节代次
密钥。用途区分 Loro/Flock 增量和快照、blob、presence、RPC 请求与响应；不是
transport URL。每次加密独立生成随机 16 字节消息 ID 和 24 字节 nonce。

```text
header = ASCII(JSON.stringify(["lody-content/v1", genesis, epochDecimal,
  resource, purpose, actor, memberInstance, device, messageIdHex]))
resourceKey = HKDF-SHA-256(epochKey, salt=UTF8("lody-content-hkdf/v1"),
  info=ASCII(JSON.stringify(["lody-content-key/v1", genesis, epochDecimal,
    resource, purpose])), length=32)
body = XChaCha20-Poly1305(resourceKey, nonce, plaintext, AAD=header)
unsigned = u16be(header.length) || header || nonce || body
frame = unsigned || Ed25519.Sign(deviceKey,
  UTF8("lody-content-signature/v1\0") || unsigned)
```

body 包含 16 字节认证 tag；末尾签名 64 字节。头部至多 4096 字节，明文至多
16 MiB；逻辑资源使用 1–1024 位可打印非空白 ASCII，作者标识沿用控制记录规则。
解码后必须能重新编码为相同头部，未知用途/版本、别名、额外字段、超限或截断
均拒绝；错误不回显输入片段，没有明文或其它密码套件后备。这是单帧内存限制，
不是已实现的大附件分块协议。重复发送保留完整原始 frame，不手工复用 nonce。

`open` MUST 匹配调用方期望的 Org/代次/资源/用途；公钥来自必需的应用策略，
不能取消息自报公钥。先验签，再派生密钥；异步密码操作后再次验权，随后无 await
地认证解密并返回。`seal` 同样在输出前复核签名和权限。输入在首次 await 前复制；
临时密钥和明文副本用后清零，但不承诺 JS/Web Crypto 的所有隐式副本可被擦除。

`inspectContent` 仅供选择已知代次密钥，结果未经认证。当前权限、历史作者规则、
代次资格和新鲜度由调用方策略负责；模块不导入 CRDT、不保存游标、不发网络请求。
同一合法 frame 可重复解密，机器持久去重和执行授权仍是上层必需边界。快照签名
只认证其发送者，不自动证明所含每一条 CRDT 操作的原始作者；来源证据与实际
应用接入仍待实现，不能用“当前成员”判断替代保留历史的授权规则。

可选 `streams-content` 入口已对接 streams-crdt 0.15.1 的增量 provider，固定房间的
资源、模型、作者和写代次；换代须排空并重建房间。provider header 为单字节 `1`，
sealed 为完整内容 frame，其加密明文为 `u16be(aad.length) || aad || 原始增量批次`。
aad 是 SDK 提供的精确上下文，至多 1024 字节；只调用一次生成函数，解密后逐字节
匹配才返回原始批次。按当前作者/资源计算封装预算，不突破 SDK 的 4096 字节上限。
接入须选 encrypted-only/encrypt；快照读写暂时明确拒绝，不能开启依赖快照/410
恢复的生产房间。增量批次签名也只证明发布者，不可替代机器命令的独立作者证据。
已使用真实 SDK 验证加密写入、Loro catchup、拒绝坏包不导入/不推进游标，以及
持久化失败后保留游标并重放；不是实际 Lody 运行时或生产后端验收。

## 代次密钥信封（实验版）

`KeyEnvelopeCipher` 已实现固定 HPKE Base X25519/HKDF-SHA-256/ChaCha20-Poly1305，
外层 Ed25519 验签复用严格配置。接口只接受一个 32 字节代次密钥，不自行选择或
保存秘密；调用方不得误传身份/恢复/管理私钥。使用固定 `@hpke/core@1.9.0` 与
`@hpke/chacha20poly1305@1.8.0`，不手写 KEM，不退回其它套件。

```text
header = ASCII(JSON.stringify(["lody-epoch-key/v1", genesis, epochDecimal,
  controlHead, senderUser, senderInstance, senderDevice,
  recipientKind, recipientUser, recipientInstance, recipientId]))
enc, ct = HPKE.Seal(recipientPublicKey, info="lody-epoch-key-hpke/v1",
  plaintext=epochKey32, AAD=header)
unsigned = u16be(header.length) || header || enc32 || ct48
frame = unsigned || Ed25519.Sign(senderDeviceKey,
  UTF8("lody-epoch-key-signature/v1\0") || unsigned)
```

header 至多 2048 字节，标识沿用控制格式；recipientKind 为 device 或 recovery。
接收方须精确匹配预期上下文，验证发送者签名和本地公钥后才执行 HPKE 解密。
发/收两侧的强制策略从已验证证据提供公钥，在异步密码计算后再次验权。
非规范 X25519 公钥别名拒绝，低阶密钥在 KEM 计算失败；无需导出接收者私钥。
该层没有联网、落盘或隐式恢复成员资格，当前头/接纳证据仍必须由应用核验。
不能仅靠 Admin 对任意 32 字节的签名决定当前代次，须执行下述承诺核对。
测试通过不表示邀请、恢复或机器发钥已接通。

`OrgKeyExchange` 已把上述信封接到实际 v3 账本策略。准备信封前后均追赶并验权，
发送内容必须符合当前最新代次承诺；Owner/Admin 管理设备可向有效接收者发钥，
普通成员仅可向自己的已登记设备/恢复身份复制，机器不能发钥。待换代不阻塞当前
代次准备；新代已发布则旧代不能继续准备为当前钥。

接收时 `readAtHead` 先完整验证至所见末尾，再提供信封对应的历史状态和当前状态；
不因早已找到目标头就跳过后续坏页。发件者按历史状态验权，收件者按当前状态验权；
解密后核对代次承诺并再次刷新，期间撤权拒绝返回。正常延迟交付不因发件者随后
降级或无关链头变化失效。强制注入的新鲜度/会话检查仍由应用实现，已知撤权或
登出须取消在途操作；两次读取不是密码学的“全球最新”证明。
该组合只返回待发送密文或临时验证密钥，不自动执行网络发送或运行时激活。
最终发送时仍须验权，不能把准备成功当成可长期使用的发送许可。
Node 接收端另有 `SqliteReceivedKeyStore`：保存原始 HPKE 信封而非明文密钥，
依赖已由设备身份存储安全保管的目标私钥。先验证再原子保存，保存后再次通过
`OrgKeyExchange` 复核；最终刷新失败可保留密文，但不报告接收完成。
重启时仍重新核验历史发送者、当前收件者与代次承诺，磁盘中的记录不授予权限。
同代首次验证的信封保留，重复加密不覆盖；错库、损坏数据和撤权失败而不自动重建。
这只是可选本地接收存储，不是丢失全部私钥后的恢复备份，也未接产品运行时或
离线权限缓存策略；数据库格式与限额见核心 README。

另有 `KeyDelivery` 与独立 `SqliteKeyDeliveryStore`：保留调用者随机生成的 16 字节
交付 ID，密文先落盘，再发；重启只重试原文，同 ID 换密文拒绝。每次尝试验证原
信封签名、历史接纳和双方当前资格；落盘后再刷新，不能使用旧准备结果长期发送。
代次已推进则拒绝继续发旧待发送包，由应用显式准备新的交付。发端只验签不能
证明 HPKE 明文内容，收件端仍须核对密钥承诺。写回执不算完成，读回相同密文才
记为 observed；这仅是远端观察，不代表收件人解锁或安装。实际网络准入、传输中
等待的凭证过期处理、UI 和真实后端仍未接入，不宣称此层完成 15 分钟撤权承诺。

`StreamsKeyDeliveryRemote` 已对接锁定 SDK，复用历史密文的长度前缀、交付 ID 和
有界扫描/CAS 实现，但使用独立预创建的密钥交付流，不与控制、文档或历史桥混用。
扫描结束后再次验权，才调用 CAS；不降级普通 append。已有合成 HTTP 对端配合
真实 SDK/SQLite/HPKE 的发送重启与接收恢复测试，包括扫描期间撤权不上传。
这不证明生产配置、SDK 获取凭证期间的过期处理或服务端 15 分钟窗口已落实。

### Owner 发布与接收端安装

新增实验动作 `epoch.publish(configVersion, epoch, commitment)`，编码为 v3 动作
数组后追加代次十进制和 32 字节承诺。当前 Owner/Admin 有效管理设备签名可提交；
代次从 0 连续增加，同 Org 不能复用承诺。客户端从已验证账本保留 `epochs` 映射，
不是使用服务器自报的“当前密钥”。此为新增动作，旧 reader 遇到未知动作停止；
既有动作、genesis 与 journal 编码不变，不把旧签名换含义。

承诺为 `SHA256(UTF8("lody-epoch-secret/v1\0") || genesis32 || epochKey32)`，
不含 epoch，使复用同一秘密产生相同承诺并被拒绝。换代者仍须安全随机生成独立
秘密；承诺不能证明生成过程、持久保存或实际分发已完成。发布与撤权/其它发布
竞争时按 CAS 决定，失败候选不得自动重签或复用。

`VerifiedEpochKeys` 只实现内存安装/读取/清空。安装前后核对已验证承诺和当前资格，
错误密钥不覆盖已有值；返回副本，每次读取重查资格。清空使等待中的安装失效，
不会在清空进行中的内存安装后异步装回。下述候选存储已提供独立原子落盘，
但运行时接线、历史桥发布、全部传输通路的排空和切代尚未实现，不能据此启用产品
或宣称未来内容已隔离。

### 发布驱动

发布提交部分已由独立 `EpochPublisher` 串起：调用方保留随机操作 ID 与预期 head，
新意图从验证后的 Owner/Admin 状态生成随机 32 字节密钥、签名，并通过受保护 store
原子保存候选/pending 后 CAS。已有意图查找保存的原文重试，不因 unsupported、
响应丢失或新 head 生成另一密钥。不同待提交意图、旧 head、换作者/换 head 复用
旧 ID 均拒绝。`resume()` 不需要签名私钥，仅提交观察到的原文；仍由驱动重新验证。
结果只含状态、原文、代次及验证快照，不含秘密；原始临时密钥在网络提交前清零。
这未接入 UI、下述历史桥发布、收件人发钥或传输切代，不是完整轮换控制器；
历史 committed 不授权发钥，也不自动授予发钥或切代权限。

### 逐代历史密钥桥

以下描述旧原型实现。目标改为[历史密钥随换代入账](e2ee-ledger.zh.md)，不再单独
发布历史桥或维护历史流；尚未迁移代码，也未用旧测试验证新格式。

`sealEpochHistory` 使用内容信封的独立用途 `epoch-history`，固定资源 ID
`previous-epoch-key`，以第 N 代密钥加密第 N−1 代的 32 字节密钥。N 必须大于 0，
不支持任意跳边或反向链接。用途和 N 已在内容头、密钥派生及签名中绑定；旧 reader
对新用途停止，不会解释为普通 blob。`importHistory` 需要已有 N 代密钥，验证解密后
再核对 N−1 代的账本承诺，成功才装入内存。不能因为发件人签名合法就接纳错误旧钥。

输入至多 4234 字节，解出的内容必须恰为 32 字节；失败不装入目标密钥，清空取消
在途恢复。调用方逐代提供历史桥，不暗中联网或遇到缺桥时跳过；历史作者应按对应
历史证据验证，不能因其后来撤权而一概拒绝旧桥。此处仍不负责安全持久化、云端发布
或可用性保证。真实三代 Loro 测试已验证仅从最新钥恢复历史，但不代表全端恢复完成。

独立 `HistoryPublisher` 已提供桥密文发布：只读核验换代记录确已入账，再验证桥签名、
当前钥与上一代钥的承诺。精确密文必须先落盘再上传；重启按操作 ID 重试，不重新
加密。同 ID 换密文拒绝，失败不删除原密文。只有远端读回完全相同的密文才返回
`observed`，回执不足以证明；读不到/读取失败为 `unknown`，不同密文报错。
历史作者验证仍由显式策略提供，不能一律要求历史作者目前仍活跃。
Node 可选 SQLite 历史 outbox 不存明文钥、不迁移旧 journal；具体格式见核心 README。
候选发布现已把桥、新代密钥密文与 pending 合为同一原子保存；N>0 时须先取得并
核对 N−1 密钥，随后封装桥，缺钥不能发布。重启从候选读取原桥给上传器重新核验。
SDK 历史传输端口已有 `StreamsHistoryRemote`，使用独立预建二进制流；每条编码为
`u32be(16+密文长度) || 操作ID16 || 密文`，只是路由包装，不能代替信封与账本验证。
完整有界扫描后 CAS，精确重复不追加，冲突拒绝；跨 HTTP 页重组，不推算游标。
扫描至多 16 MiB、4096 条/页，遇坏数据、缺历史或不支持 CAS 停止、不降级或跳过。
生产还需配置准入、凭证和 SDK 缓冲前限长/时限，未实际部署；发钥或通路激活未接，
不是完整换代流程；
`observed` 不保证永远可用、不授权发钥、不表示通路可激活。Owner 移交前后已收到
密钥的持久保管仍是必须补齐的部分。

## 提交、重试与持久化

设备身份另有显式的 Node `SqliteDeviceIdentityStore.create/load`：首次生成独立
Ed25519/X25519 密钥和随机设备 ID，经过系统包装往返检查并持久保存后才返回。
加载时核对账户绑定和公私钥配对；缺失、损坏或密钥环锁定报错，不偷偷生成替代
身份。返回私钥句柄不可导出；初次持久化需要临时导出，不承诺硬件不可提取或
进程内存完全擦除。Electron 设备包装复用安全后端检查，独立格式/用途隔离。
此为本机存储，不是云端备份、入组或恢复权限。Electron 主进程已接显式创建/加载
IPC，只返回设备 ID 和公钥；账号由主进程解析，期间账号切换则拒绝返回结果。
OSS 本地模式在访问云端登录前拒绝；注册引导 UI 和手机流程尚未验收。

桌面端新增显式选择的 `createElectronEpochProtection`，仅在主进程通过系统
`safeStorage` 包装单个代次密钥；不注册 IPC、不自动接入产品。加密内容绑定
genesis、代次及承诺，解包核对预期上下文和密钥承诺，未知格式/损坏/超限拒绝。
调用方仍须提供已验证承诺和当前授权，解包成功不证明权限或防止磁盘回滚。
登录模块开发用明文开关、加密不可用、Linux `basic_text`/未知后端均明确失败；
不修改现有登录行为，也不使用明文兜底。参见
[Electron 39.2.6 安全边界](https://github.com/electron/electron/blob/v39.2.6/docs/api/safe-storage.md)：
Windows DPAPI 不隔离同一用户的其它进程，Linux 随系统密钥环而异；不承诺抵御
已控制设备的攻击者。原生调用可能阻塞/弹系统授权，JS 字符串不保证内存擦除。
包装层已与下述独立持久层组合测试；macOS 开发态 Electron 39.5.1 的真实
safeStorage 已验证跨进程创建/恢复。签名安装包、锁定状态及 Windows/Linux 尚未验收，也不适用于
没有系统密钥环的云端 CLI。这些仍是后续接入门槛。

`SqliteEpochControlStore` 在一个 SQLite 行中原子保存账本和已包装候选，密钥不以
明文进入数据库。`withCandidate(wire, secret)` 先核对承诺和系统加解包往返，仅在
内存准备；返回的 store 交给现有提交驱动，验签验权后的 pending 保存同时写入两者，
之后才 CAS。缺候选、无法解包或磁盘拒写均阻止提交；未知结果保留原文及候选。
已观察到相同已提交原文时也保存所提供的候选。成功或冲突清 pending，但保留密文；
已存候选承诺不能换一个操作复用。恢复只通过当前已验证代次策略安装，不以磁盘
内容证明授权。没有自动清理、自动重签、防磁盘回滚或全端 keyring。
新增 `findCandidate(operationId)` 只返回未经验证的原文，供发布驱动重新核验；
保存和读取均拒绝候选操作 ID 重复，避免同一意图对应多份秘密。

它使用独立 `lody-epoch-journal/v2`（application ID `0x4c454b31`、schema 2），
编码为 `[format, encodedControlJournalV2, [[wire, wrappedHex, historyHexOrNull], ...]]`。
0 代必须无桥，后续代必须有匹配作用域的桥。旧候选 v1 数据库原样拒绝，不自动
迁移、删除或重建。存储只核验桥路由；发布者先核对旧钥再封装，上传器再次验签
并核对新旧钥承诺；`readHistory` 的磁盘密文不是权限证据。整行至多
16 MiB、4096 个候选、每个包装 1–4096 字节。旧普通 journal/v2 原样拒绝，不自动
迁移。两种存储共用原有 SQLite 持锁与同步写实现。真实签名、桌面包装逻辑、SQLite
拒写及子进程终止测试通过，不等于真实系统密钥环、断电、完整发布控制器或 AC7 验收。

```text
读取并验证完整前缀 → 重新鉴权 → 持久保存签名原文
    → 原子 CAS → 读回并验证 → 持久保存前缀 → 返回已提交
```

每个客户端保留完整的已验证页、每页的不透明流游标及一个待确认操作。页内没有
单独记录的服务端游标：必须全页验签验权成功，再一起保存记录和页尾，不能保存
坏页的有效前半段。之前完整保存的页不因后续失败回滚。存储适配器必须
跨实例、跨进程互斥，原子且持久地保存整份检查点。重启重放保存的记录，不接受
未经验证的权限缓存。写出前保存原文；丢失响应只能重试同一原文。相同操作 ID
但不同原文不得继承成功状态。CAS 冲突不自动重签；调用者重新决定是否继续，
涉及曾暴露的新代次密钥时必须丢弃候选密钥。

驱动不会仅凭 append 成功回执返回已提交，而要读回相同原文并验证。不能确定
结果时保留待确认操作并返回 `unknown`，不自动走普通 append。`committed`
只说明该操作存在于已验证前缀；此后的撤权仍有效，不能据此直接发放密钥。
只有不存在早先待确认请求，且适配器保证本次请求未被接纳时，才可返回
`unsupported` 并清理原文。早先请求可能仍在后台处理中；重试返回不支持 CAS
不能证明它不会提交，此时必须继续返回 `unknown` 并保留原文。

## 保证与尚未实现的部分

Node 端可显式选择 `SqliteControlStore`（Node ≥22.13）；它不进入通用包入口。
每个 Org 使用独立的本地账本文件，保存完整原文而非可信权限缓存。SQLite 排他
锁覆盖整个操作及网络等待；每次保存独立提交，之后操作失败不回滚已保存的原文。
锁竞争立即返回 `journal-busy`，不等待或抢过期锁；连接关闭或进程退出后释放。
页级 journal 使用格式及 schema v2；旧实验 v1 原样拒绝，不自动迁移、删除或重建。
损坏、未知版本或非本模块数据库也拒绝打开。事务句柄不能越过回调
生命周期使用。此原型的编码账本上限为 16 MiB，游标至多 1024 字符；超限保留旧检查点。
它有同步磁盘 IO，不应在 UI 线程运行；没有磁盘加密或私钥托管。

持久性依赖本地文件系统正确实现 SQLite 锁和同步写；不支持网络盘或运行中的
云同步数据库。应用必须提供私有目录，不得替换、重命名或删除使用中的数据库。
进程终止及 SQLite 拒写测试不等于断电、硬件故障或所有操作系统验收。

显式选择的 `StreamsControlStream` 已接入 `streams-client@0.7.0` 的 `read` 和
`appendCas`。一次 CAS 写一帧：四字节大端长度加原始规范 wire，类型为
`application/octet-stream`。HTTP 页可能切断一帧；适配器继续读取到完整边界，
再返回全部记录及最后一页的真实游标，不能推算页内偏移。调用者提供流地址、
凭证、预创建和准入机制，适配器不自动创建流或选择 Org 信任锚点。

驱动逐页追到 `upToDate` 才返回状态或提交 CAS；空页只能表示读到尾部。第一次
空读取可把保留起点 `-1` 规范为实际空流游标，后续不能用空页推进已保存位置。
一次追赶最多 4096 条、16 MiB 原文及 4096 页；适配器也限制单次组合读取的帧
字节和页数。超限、残帧、游标不前进、历史不可用均报错，不截断当最新。
第一阶段每次重放本地前缀，不提供快照压缩。SDK 在返回前已经缓冲 HTTP 响应体，
因此生产 transport 还须在缓冲前限制体积和请求时限，不能把此处限长当作内存保护。

CAS 不传 producer，不让 SDK 自动重试不确定写入；原文重试由持久 outbox 管理。
mismatch 返回冲突，其他 SDK 错误保留为不确定结果，并读回核对；不从普通 501
推断请求从未提交，不降级普通 append。测试运行真实 SDK 配合合成 HTTP 对端，
不证明生产后端已开启 CAS、集群读屏障或控制准入已就绪。

hash chain 能发现相对于本地锚点的篡改，却不能证明服务器没有隐瞒新记录或分叉。
全局新鲜性仍依赖后端完整、唯一的提交视图。独立控制入口须在 CAS 前验签验权，
普通文档凭证不得直接写控制链；客户端仍独立验证，坏链停在最后有效前缀，首版不修复。
首版不做跨数据流封存或密码学截止证明，改由可信服务端通过 JWT 控制云端准入。
签发/续签须核验 Org 成员实例、设备资格和持钥，不能只凭账号登录；旧 JWT 的
最坏残留窗口已确定为撤权记录成功提交后的 15 分钟，包含签发/投影延迟、时钟
容差、长连接与在途请求；各环节不得叠加窗口，到界限停止继续云端读写/流式交付
和机器新执行。缓存/派生凭证不延长原证明，已知撤权立即拒绝；JWT 参数与主动
失效属于满足总预算的实现选择。它不代替密钥换代、客户端验签验权或直连鉴权，
不证明每条旧消息早于撤权，也不保证 Owner 在此时限内完成换代或撤回既有副作用。
控制流准入、密钥封装、JWT 设备级撤销、
配对恢复和 Machine RPC 鉴权仍是启用生产 E2EE 前的门槛。
本阶段不提供前向安全、密码学安全证明或 Lean 证明。

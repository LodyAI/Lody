# 桌面通道执行

Status: draft
Translation: current

[English](desktop-channel-execution.md)

## 场景

云端桌面可提供独立安装的 Stable 与 Nightly 应用。用户退出一个再打开另一个来切换。
公开独立桌面继续保持 local-only，通道身份不能在该构建中启用云端行为。

## 身份与所有权

- 不同通道必须保留独立应用身份、协议处理器、桌面缓存和凭据。浏览器登录遵循
  [桌面登录契约](desktop-browser-login.zh.md)，返回发起应用。
- 受支持的云端桌面版本必须在两个启动顺序中互斥，包括 control-only 模式。失败方提示
  如何退出当前应用，不能杀死它、抢占执行所有权，或加载凭据/业务存储。
- 必须早于 ready 的 Electron 配置和早期启动事件订阅应先于异步所有权申请。
  门控期间收到的有效回调不能丢失。
- 同应用第二实例的转交必须与跨通道冲突分开处理。
- 桌面锁与本地 CLI Host 所有权职责不同。自身执行进程确认停止前，桌面必须持锁。
  停止失败必须阻止正常退出、报告失败并允许重试。
- 桌面崩溃不能留下持久化的残留桌面锁。
- 外部 daemon 不能静默替代 Nightly 内置执行层。不受支持的所有权必须给出可操作的
  拒绝提示，不能杀死外部进程。Nightly 在认证和业务初始化前取得共享执行 Host，
  即使已保存的偏好关闭本地 agent 也如此。Host 被占用时拒绝启动。
  Worker 停止/重启必须保留桌面的预约及 Supervisor 身份；control-only 模式停止
  Worker 执行和探测，但不释放 Host 所有权。
- 共享执行数据必须保持受支持 Stable 可读。桌面缓存隔离和进程互斥不能证明数据格式兼容。
- 必须明确支持哪些旧 Stable 版本。新的锁协议本身不能证明与不参与该协议的旧版本互斥。

## 诊断身份

桌面端与 Web 的「设置 → 关于」必须在「下载应用」下方提供「下载 Nightly 版本」，
打开对应语言的独立 `/download/nightly` 页面。普通下载页不嵌入 Nightly 下载。
独立页面必须在视觉上区分 Nightly，说明共用真实数据及手动切换方式，并仅使用完整
Nightly 清单内的不可变安装包链接。无效或不可用清单不得产生正式版回退或猜测地址。
清单和下载页必须说明已验证的最低正式版；该下限需要真实安装包兼容性证据，不能仅由版本比较推断。

发行 composition 注入构建身份时，关于页面、复制的崩溃报告和提交的问题报告必须记录
报告桌面的通道、版本和两个源码 revision。构建身份必须与远程机器日志明确区分，
不能扩展成对环境变量、账号或文件系统的采集。

## 证据与限制

`desktop-bootstrap.ts`、`index.ts` 与 `application.ts` 分别负责早期配置、所有权门控和
应用生命周期。启动 bundle 测试覆盖延迟导入边界与早期回调，租约测试覆盖竞争、崩溃释放和
退出失败。Host 冲突与 Supervisor 停止/重启测试覆盖执行预约；这些测试不证明打包后的
系统分发或旧版兼容。打包启动验收、
支持版本下限与共享数据兼容仍是推出通道前必须完成的事项。

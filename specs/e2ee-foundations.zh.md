# E2EE 基础模块边界

Status: draft
Translation: current

[English](e2ee-foundations.md)

客户端收到加密字节后，首先需要明确的格式，以及绑定到原本要打开的组织和文档的签名。
基础模块提供这一检查，但不启用加密工作区。

调用方提供独立可信的组织创世哈希、文档资源、密钥代次、用途和签名公钥。
不能因为字段出现在数据包或 URL 中就信任它。内容 v0 保持 `docEpoch = 0`，
拒绝不支持的版本和文档代次。更新帧字节排列不变：版本字节、u32be 组织代次、
u16be 文档代次、32 字节签名公钥、24 字节 nonce、密文及标签、64 字节签名。
文档上下文绑定创世哈希和资源；用途及可选外部绑定参与认证。
四种文档更新／快照用途共享密钥派生上下文，但不共享认证字节。

公有字节值复制输入输出。规范 CBOR 拒绝非规范编码、尾随数据和不支持的类型，
并限制总大小、嵌套深度和数组长度。严格 Ed25519 拒绝坏签名、非规范或带额外扭转分量的点、单位元公钥 A、单位元 nonce 点 R
以及 S ≥ L。纯实现和原生实现都先执行同样的前置检查，再验证签名方程，避免原生密码库
差异导致接受不同的记录集合。

签名有效只是一项前提。基础原语（`@lody/e2ee-core/protocol`）不验证当前成员身份、新鲜度、写权限、
快照历史或服务端接纳条件。独立 AEAD 原语使用 HKDF-SHA-256 派生绑定上下文的内容钥，
并按调用方提供的上下文、包头及外部绑定检查 XChaCha20-Poly1305 标签。
每次新加密必须取得 24 字节安全随机 nonce。标签有效本身不证明作者身份或权限。不提供签名、私钥导出、平台存储、传输或生产开关。
平台存钥和完整内容解密是后续工作。本草案不代表产品或全平台验收。

独立 HPKE 原语保留 Base X25519/HKDF-SHA-256/ChaCha20-Poly1305、
info `lody-e2ee/hpke-epoch/v1\0` 与账本规范四字段 AAD。只把 32 字节代次钥
封成 `enc32/ct48`，接收外部持有的设备密钥句柄，不提供投递或安装工作流。
封装必须取得宿主安全随机数；异步原生操作完成后清理临时副本，取消等待清理。
外层签名、当前双方资格与代次承诺仍由调用方验证；HPKE 有效不证明发送者身份。

## 实时 RPC 与 presence（M5 评审草案）

本节记录已定的实时方向：iroh 优先、加密 Streams RPC 回退、共用签名加密帧与持久
去重、账本绑定 machineId，以及机器自己取得执行权限新鲜度。owner 已选择这些行为
边界和 iroh 设备身份；**本次 Spec 修订仍是 draft**。下文已有的候选字节布局和上限
保持不变；这些决定不批准新账本编码，也不开启产品通道。机器接纳格式改动单独实施。
普通 RPC、文档 content v0 与 credential-binding/v1 不变。

### 共用内容帧

两通道每条消息都传一份完整 content v0：header39、nonce24、带 tag16 的密文、
signature64。传输字段不产生权限。复用 `deriveContentKey`，绑定钉住的 genesis、
当前 epoch、`docEpoch=0`、用途 7/8/9 和资源。请求与响应资源为 `rpc:<machineId>`，
presence 为 `presence:<roomId>`。建议 ID 使用 1..128 字节不含空白的可打印 ASCII，
前缀原样拼接，不做 URL 归一化；越界拒绝。一个 genesis 对应一个工作区，宿主另外核对
这个固定绑定。用途虽然不在包头里，仍受 content v0 认证。请求、响应、presence 与
文档密钥不能互换。本提议不使用额外 content additionalData。

建议正文采用固定字段，而不是外层 JSON。整数无符号、大端；u64 不得超过 2^53-1。
`text16` 是 u16 字节长度加严格 UTF-8；`bytes32` 是 u32 字节长度加原字节。分配前检查
截断、尾随字节、未知标签与上限。下列上限包含完整明文正文，content v0 另加 143 字节。
建议所有时间戳为非负 Unix UTC 毫秒，`now >= expiresAt` 即过期。presence 要求
`issuedAt <= now < expiresAt` 且 `0 < expiresAt - issuedAt <= 60_000`；本机时钟
不确定时不能继续复用。

| 用途       | 建议明文布局                                                                               | 建议上限                                 |
| ---------- | ------------------------------------------------------------------------------------------ | ---------------------------------------- |
| 8 请求     | `version:u8=0, requestId:16, expiresAt:u64, method:text16, params:bytes32`                 | 1 MiB；method 为 1..128 字节可打印 ASCII |
| 9 响应     | `version:u8=0, requestId:16, requestDigest:32, kind:u8, sequence:u32, payload:bytes32`     | 每帧 1 MiB                               |
| 7 presence | `version:u8=0, incarnation:16, sequence:u32, issuedAt:u64, expiresAt:u64, payload:bytes32` | 64 KiB；TTL 不超过 60 秒                 |

requestId 与 presence incarnation 由宿主安全随机生成 16 字节。请求签名者取 content
包头公钥。目标、genesis、epoch 与用途来自独立可信上下文，不从解码正文或 URL 建立。
params 为现有方法 codec 产生的原始 UTF-8 JSON，帧认证后按方法验证；计算摘要时不重新
序列化。JSON 内容不能选择方法、签名者、目标、ID 或期限。二进制方法输出须明确 codec，
不能隐式转换成 JSON。

建议响应 kind：0 progress、1 最终成功、2 最终错误。requestDigest 是**完整原签名加密
请求**的 SHA-256。每请求 sequence 从零严格递增；完全相同的重复帧忽略，相同序号不同
字节视为冲突。终态之后不再接受 progress；允许缺少中间 progress，但缺帧不产生成功。
成功／progress 使用该方法现有 UTF-8 JSON codec；错误 payload 为
`code:text16, detail:bytes32`，code 限 1..64 个 ASCII 字母、数字、`_` 或 `-`，detail
为明确允许的加密方法错误 DTO。原异常、路径、栈和 provider 输出留在相应可信宿主诊断
边界，除非明确属于该 DTO。响应发布失败不替换已保存的业务结果。

一个持久响应 owner **先原子保存每帧完整原签名密文及分配的序号，再发布**，重试原字节。
重启不得在已提交序号下重新加密 payload。未提交的封装不分配持久序号；提交结果不确定
时，先核实，再封装另一帧或发布。响应 outbox 不可用／无效时，另发经授权的结果查询，
不能编造另一份原响应。首版也不自动回收响应证据。

响应／progress 必须匹配调用方持久保存的原 ID／摘要、genesis、目标与 epoch，且由独立
绑定的目标设备在**当前仍有效**时签署。其他同工作区持钥成员不能冒充。请求过期禁止新
开始，不禁止交付／查询已保存结果。结果查询本身仍需认证与授权，知道 ID／摘要不授予
访问权。已有业务结果可包装成另一次结果查询请求的合法新响应；这不是为了重试而重新
加密或签署原请求。

### 机器绑定：采用账本接纳记录

机器 `AdmitDevice` 记录将精确产品 machineId 和设备签名公钥一起纳入批准个人设备的
账本签名。从本地已验证账本取得 `machineId → 签名公钥`，不能信任目录行、传输地址或
持有 epoch 钥。既有成员／账号和机器所有权／共享检查仍须保留；这项绑定不新增执行
权限。credential-binding/v1 不变，也不是 machineId 证明。不采用独立机器绑定证明。

同一工作区内，同一 machineId 最多绑定一台有效设备。该 machineId 更换公钥时，必须
在同一份签名账本记录内撤销旧公钥，竞争接纳不能产生两个有效目标。精确记录编码及
验证／向量变更归独立的机器接纳格式工作，本草案不选择它们的字节。没有 machineId 的
旧开发机器记录可以继续经授权的文档同步，但不能建立实时权限；不得从元数据猜绑定，
也不迁移或重签其历史记录。

### 权限新鲜度：机器自己经认证读取

已验证账本证明连续性，不证明远端刚返回了最新状态。token、请求时间、转发的证明或新
收到的帧均不建立执行新鲜度。宿主在新开始**和每次后续动作**前检查当前设备／成员角色
及既有机器所有权／共享规则。Guest／恢复设备不能执行；只读查询按读取权限检查。已知
撤销、epoch 变化、rotationRequired 或本地证据冲突立即阻断受影响发送与执行，覆盖两
通道和持久派发路径。

执行机器自己发起经认证的最新账本读取，网络前记录本机开始时间，验证到该次最新边界。
权限缓存仅在内存中存在，有效期最多是从该次读取开始计的 15 分钟剩余时间。缓存／转发
页不重开窗口；慢读取耗尽窗口就不授权。期限与请求期限及适用上游凭据期限取交集，并
预留时钟／停止操作余量。全局账号锁里不等网络。

执行新鲜度只在内存保存。重启后丢弃，必须联网、经认证重新核查最新账本，才接受新的
远程执行；本地 retained checkpoint 和 journal 时间戳不能恢复这份授权。进程内缓存遇
时钟回退或无法确定休眠／恢复耗时时失效并重新核查。各宿主选择并测试具体时钟、停止
余量和休眠检测，但不得突破时限。来源 checkpoint／原窗口可以保留为诊断证据，不能
形成新授权窗口。这不改变 journal 已单独接受的持久过期时钟下限行为。离线文档内容、
编辑和已保存结果仍可用；刷新失败在既有授权到期时阻断新的远程执行，不阻断无关本地
工作。已启动但结果不确定的操作，不因重新验证而自动重启。

### Iroh 身份与可信宿主边界

Iroh 复用工作区设备的 Ed25519 身份：EndpointId 就是该设备签名公钥。仅由可信宿主把
设备私钥交给 iroh；不导出给 renderer，也不提供任意签名 IPC。经 iroh 认证的对端仍须
通过共用帧、已验证机器绑定、当前成员／设备权限、新鲜度和执行 journal 检查；传输连接
不授予工作区权限。

启用复用前，须审查具体 iroh TLS 与 discovery 签名路径和账本／内容签名之间的域隔离；
身份方向已定不代表这项审计通过。原生 SDK、发现／中继配置和平台验收仍属实施工作。
iroh 不可用或连接很慢时，加密 Streams RPC 仍须使用同一原请求 ID／帧和同一个机器端
执行 claim 正常工作。

### 持久身份、结果查询与回收

发送前保存完整原签名密文和固定 ID；机器确认接收前将原件保存到两通道共用 journal。
逻辑身份为 `(genesis, workspace, targetMachineId, requestId)`，请求设备和原字节是
不可变属性。同身份的不同设备或不同原件都是冲突，不能成为另一轮执行。保存原期限，
重签或转发均不续期。

journal 保存 received、started、completed，以及已开始但未持久完成的待确认结果。
首个业务副作用前原子 claim received，仅赢家取得启动凭据。claim 后崩溃，即使无法
证明副作用已发生也视为待确认，不自动接管／重跑。复用 userTurnId／steer／fork 的业务
执行证据核对；同一业务操作关联 Meta 持久派发，不能绕开 journal。

特别是 `session/dispatch-turn` 当前从 offerRpcTurn 返回的只是交付 ACK，不是 agent
回合完成。建议 profile 中 accepted／queued 凭据属于 progress，关联原 userTurnId，
不能把执行 journal 标为 completed。实际 agent 启动门才 claim journal，业务完成才保存
最终结果。ACK 不能让持久 watcher 再启动一份。其他方法保留各自明确的完成语义。

业务结果先持久保存，再交付响应或做辅助清理。完成结果不可覆盖，丢响应或清理失败后
仍可查询。journal 错误只阻断依赖它的工作，保留文件与宿主诊断边界里的原始 cause；
I/O 恢复后下一调用可重开，不能把不可读当成空库。不能按超时抢占拥有权。

**首版回收规则：不自动回收。** expiresAt 已过不删除原件、结果或去重证据；显式确认
也不让 ID 可复用。后续容量／留存政策须在开放正文回收前明确结果消费、待确认操作、
持久退役 ID 证据及备份回滚。容量耗尽拒绝新工作，不驱逐证据。仍支持重传或精确冲突
比较时需要原件；精简墓碑政策尚未批准。presence 为临时状态，不进 journal 或历史。

presence 核对预期发送者、genesis、房间、epoch 和原 TTL。伪造、跨房间、过期、签发
时间在未来或超大的帧，在更新状态前丢弃。序号仅按发送者／incarnation 在其生命期内
保存；坏 presence 只影响该发送者状态，不暂停无关文档。

## 格式兼容性

**冻结点。** 账本 v1（记录版本号 1、`sig/v1` 和 `rec/v1` 签名域，以及[权限账本规范](e2ee/permission-ledger.zh.md)中的操作码）在生产部署第一次开放加密工作区创建时才成为永久格式，因为只有那时才会出现绝不能失效的账本。合入代码本身不会冻结格式。在此之前格式仍可修改，但须经所有者批准，并在同一改动中用独立生成器重新生成 `packages/e2ee-core/test/ledger-v1-vector.json`；此前在开发和测试环境创建的账本可能无法再通过验证。开放生产创建之前，必须先完成一次格式审查，确认记录结构、操作码、签名域，以及权限账本 §9 中的待定事项（恢复库与可信锚编码、自撤设备后的换代衔接、恢复设备的登记顺序），都不需要改变现有记录的编码或验证方式。冻结之后，样例永不重新生成。

**冻结的范围。** v1 在某个位置接受的每条记录，此后所有客户端都必须继续接受，字节、哈希和验证后的账本状态都不变。新增行为，包括放宽或扩展权限，只能通过能力声明之后的记录生效，绝不改变现有记录的验证结果。

账本只通过追加来演进：

- 新操作只有在同一账本更早的位置出现能力声明（操作标签 9）之后才合法。声明列出严格递增、非零的 u32 能力码，由 Owner 或 Admin 的个人设备签署，只增不减。不支持某项已声明能力的客户端，验证声明之前的记录，并在声明处以 `upgrade-required` 停止；不报告账本损坏，也不跳过这条记录。写入方和服务端拒绝自己不支持的声明，也拒绝使用此前未声明能力的操作。
- 更换密码套件或其他创世级参数时，新建一个带新创世记录的账本。旧账本永不改写，只在末尾通过一项能力追加指向新账本的链接记录，与 MLS ReInit 关联替代组的方式相同。

其余格式仍只支持当前格式。内容、日志、本地存储和快照格式都没有线上数据：每个入口仅支持当前格式；不增加旧格式解码、双读者、schema 升级、旧数据导入或兼容门面。快照总能从完整的 v1 历史重建，所以快照格式变化不会破坏账本兼容。不支持的格式直接失败且不改写输入。当前存储的正常重开、同一当前格式内的账本历史验证与代次密钥历史恢复仍须保留。这项范围决定不选择待定的新格式，也不批准生产启用。

## 保留的已验证状态（提议）

在空闲的桌面级机器上，全量重放每条记录约 5.4 毫秒（4,096 条需 22 秒）；在已有 view 上追加一条约 5 毫秒。因此每次请求都从创世重放，对服务端和客户端都不可行。本节提议在 core 中增加一个入口，让一方从**自己**此前验证过的状态继续。它不改变账本 v1 的记录格式。详见[提议 note](../.agents/notes/proposed/architecture/2026-10-19-e2ee-retained-ledger-state.zh.md)。

- **导出。** `exportVerifiedState(view)` 返回规范的状态编码（与快照正文使用同一种确定性编码，因此同一状态只有一种字节表示），以及创世、长度、头哈希和 `stateDigest`。摘要只在导出时计算一次。
- **恢复。** `restoreVerifiedState({ bytes, genesis, length, head, stateDigest? })` 按规范解码，对格式错误的输入返回带类型的错误。它不重新验证签名，也不重新校验密钥的曲线点：这些字节来自同一方自己的存储，该方本来就信任这份存储。调用方若传入与字节一起保存的 `stateDigest`，恢复会从字节重算摘要（一次 SHA-256，无需二次编码），不一致时以 `state-digest-mismatch` 失败。这能发现损坏或错配的行，但防不住能同时替换两者的写入方；不传摘要时行为不变。恢复出的 view 与导出时的 view 一样可以 `extendLedger`。
- **权限范围。** 保留状态只对导出它的一方、只对该方自己的决定有效（服务端的写入准入、客户端的本地视图），绝不接受来自另一方的保留状态。接收别人的状态仍然使用背书快照。
- **衔接。** 新记录从保留的长度之后读取，第一条必须指向保留的头哈希。不一致说明外部存储被回滚或出现分叉，直接失败关闭。这项检查针对的是不受信任的存储，不是保留状态本身。
- **完整性。** 保留状态必须包含验证下一条记录所需的全部重放事实，使结果与全量重放完全一致：所有曾登记的成员关系及其用户、所有曾登记的设备及其加密公钥和成员关系、当前角色与设备类型、已关闭的加入请求、epoch 状态、历史包，以及出现后的已声明能力。已用的密钥、成员 ID 和承诺就是这些表本身，每台曾登记的设备都保留历史作者。原始 epoch 发布记录不保留：恢复出的 view 报告其不可用，因此不能为恢复点之前发布的 epoch 暂存密钥。
- **统一状态编码。** 保留状态、背书快照和比对摘要共用同一种授权状态编码，因此三种来源（完整重放、合格快照导入、保留状态恢复）在同一位置的状态、摘要和每台设备的作者都一致。保留状态外层只多一项验证来源，往返后保持不变，也绝不升级；恢复点之前的已验证哈希不保留。布局与验收见[紧凑状态记录](../.agents/notes/proposed/architecture/2026-10-20-e2ee-compact-ledger-state.zh.md)。
- **摘要的用途。** `stateDigest` 用于跨方比对（comparison note）和后台审计。只有调用方提供时，恢复才校验它，代价是一次哈希，不做重新验证。
- **后台审计（暂缓）。** 从创世全量重放并与保留的摘要比对，可以发现程序错误或存储损坏。它是可选项，不在本次范围内，也可以放在服务端请求运行时之外（例如读取已存账本和保留摘要的独立 worker）。若日后加入，不一致即视为事故，在解决前停止该账本的写入。
- **格式。** 保留编码只支持当前格式，并带显式版本：保留状态外层版本 2、快照正文版本 2、摘要域 `snapshot-digest/v2`（版本 1 是紧凑布局之前的格式）。其他版本以 `unknown-version` 失败；此时丢弃保留状态，并对 v1 历史做一次全量重放来重建。编码变化时提升这些版本。
- **读取。** 服务端返回历史分页时无需在读路径上验证，客户端会验证收到的内容。服务端的验证属于写入准入。
- **本地存储。** 若采纳，客户端打开时可以恢复本地保留状态，而不必重新验证全部已存记录，这将取代下文所述的全量重新验证。

## 本地 epoch 保护边界

接收者须能重新打开已持久保留的安装密钥，不能要求原发送者一直有效。
可信 host composition 可初始化一次原生 protect/unprotect 能力；普通消费者
继续使用 opaque key。原生保护须将用途、Org genesis、接收者、epoch、commitment
与密钥一起绑定。被攻破的 host 可以复制明文；此契约不宣称操作系统隔离，
也不声称清零能追回这些副本。

安装报告须晚于持久保存、实际回读／解封和独立 commitment 校验。失败不得
宣称已报告安装。原生工作结束和临时清理须晚于取消请求、早于取消／Scope
完成。禁止明文降级或生产装配。原生适配器选择、恢复文件／包装／并发仍单独验收。
发布者窗口改用先暂存后提交；vault 与真实平台保管仍单独验收。本 Spec 修订保持 draft；边界方向已定和合成
测试通过，不代表整份修订获批或原生存钥通过验收。

## 定稿内容 v0 与快照继续位置

按用户决定采用 content v0 替代 v2，不保留 v2 读端。docEpoch 固定为 0；四种
文档 purpose 共用一把文档叶密钥，方便将来按文档授权；purpose 仍进入 AAD 与
签名，阻止跨用途篡改。更新帧不变，固定开销 143B。两种快照在签名公钥之后
加入 u16be 长度和 continuationOffset 原始 ASCII 字节，因此开销为
143 + 2 + offset 字节；整个头同时绑定进签名与 AAD。

SDK provider 头仅为 [4]，不再在 provider 头里编码 offset，无旧格式双读。内容
准入网关读取真实宿主记录边界，检查该位置存在且不超过真实 head，再将原密文
交给不感知内容的 Streams。读端认证并解密后，对比 SDK 给定的精确继续位置。
篡改、搬移、越过 head、非记录边界均失败，不推进文档/游标持久对。客户端不对
不透明 offset 做数值或字典序推断。宿主边界查询能力不等于快照信任来源。

通用 ASCII offset 使用 u16 长度界；已发布 SDK 的 4096B sealing-overhead
限制使适配器上限更小。真实 Loro/Flock 消费者用快照和后续增量 bootstrap。
以上方向已确定，修订稿仍为 draft，待用户审批，不代表产品启用。发布者密钥
可用性改用[先暂存后提交](e2ee/publisher-key-recoverability.zh.md)，不再保留旧 A/B 提案。

## 本地 SQLite 持久化

白皮书的威胁模型信任客户端及操作系统。当前格式的存储在创建或打开时检查
application/version 和固定 genesis/recipient 绑定，使用 WAL/FULL 与事务；打开
时重新验证已存账本记录。SQL 行不建立权威。每次操作保留第一份原件的目标行
读回及真实账本回滚 pin 比较；head/count 不变时不写 pin。不为检测其他本机进程
改库而逐次扫描旧行、触发器、schema 或本地写入计数。

快照发布仅为 current 和 Pending 保留密文正文。新快照成为 current 时，在同一
事务内清除旧 Accepted 正文，保留 offset、signer、SHA-256 摘要、原凭据时间窗口
和 phase。归档身份的同字节重试仍然幂等，同 offset 的不同字节冲突，旧身份
不能再次成为 current。容量预算只计算保留正文的行，不计算归档身份。

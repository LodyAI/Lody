# E2EE 基础模块边界

Status: draft
Translation: current

[English](e2ee-foundations.md)

客户端收到加密字节后，首先需要明确的格式，以及绑定到原本要打开的组织和文档的签名。
基础模块提供这一检查，但不启用加密工作区。

调用方提供独立可信的组织创世哈希、文档资源、密钥代次、用途和签名公钥。
不能因为字段出现在数据包或 URL 中就信任它。内容 v0 保持 `docEpoch = 0`，
拒绝不支持的版本和文档代次。更新帧字节排列不变：版本字节、u32be 组织代次、
u16be 文档代次、32 字节签名公钥、24 字节 nonce、密文及标签、64 字节签名。
文档上下文绑定创世哈希和资源；用途及可选外部绑定参与认证。
四种文档更新／快照用途共享密钥派生上下文，但不共享认证字节。

公有字节值复制输入输出。规范 CBOR 拒绝非规范编码、尾随数据和不支持的类型，
并限制总大小、嵌套深度和数组长度。严格 Ed25519 拒绝坏签名、非规范或带额外扭转分量的点、单位元公钥 A、单位元 nonce 点 R
以及 S ≥ L。纯实现和原生实现都先执行同样的前置检查，再验证签名方程，避免原生密码库
差异导致接受不同的记录集合。

签名有效只是一项前提。基础原语（`@lody/e2ee-core/protocol`）不验证当前成员身份、新鲜度、写权限、
快照历史或服务端接纳条件。独立 AEAD 原语使用 HKDF-SHA-256 派生绑定上下文的内容钥，
并按调用方提供的上下文、包头及外部绑定检查 XChaCha20-Poly1305 标签。
每次新加密必须取得 24 字节安全随机 nonce。标签有效本身不证明作者身份或权限。不提供签名、私钥导出、平台存储、传输或生产开关。
平台存钥和完整内容解密是后续工作。本草案不代表产品或全平台验收。

独立 HPKE 原语保留 Base X25519/HKDF-SHA-256/ChaCha20-Poly1305、
info `lody-e2ee/hpke-epoch/v1\0` 与账本规范四字段 AAD。只把 32 字节代次钥
封成 `enc32/ct48`，接收外部持有的设备密钥句柄，不提供投递或安装工作流。
封装必须取得宿主安全随机数；异步原生操作完成后清理临时副本，取消等待清理。
外层签名、当前双方资格与代次承诺仍由调用方验证；HPKE 有效不证明发送者身份。

## 格式兼容性

**冻结点。** 账本 v1（记录版本号 1、`sig/v1` 和 `rec/v1` 签名域，以及[权限账本规范](e2ee/permission-ledger.zh.md)中的操作码）在生产部署第一次开放加密工作区创建时才成为永久格式，因为只有那时才会出现绝不能失效的账本。合入代码本身不会冻结格式。在此之前格式仍可修改，但须经所有者批准，并在同一改动中用独立生成器重新生成 `packages/e2ee-core/test/ledger-v1-vector.json`；此前在开发和测试环境创建的账本可能无法再通过验证。开放生产创建之前，必须先完成一次格式审查，确认记录结构、操作码、签名域，以及权限账本 §9 中的待定事项（恢复库与可信锚编码、自撤设备后的换代衔接、恢复设备的登记顺序），都不需要改变现有记录的编码或验证方式。冻结之后，样例永不重新生成。

**冻结的范围。** v1 在某个位置接受的每条记录，此后所有客户端都必须继续接受，字节、哈希和验证后的账本状态都不变。新增行为，包括放宽或扩展权限，只能通过能力声明之后的记录生效，绝不改变现有记录的验证结果。

账本只通过追加来演进：

- 新操作只有在同一账本更早的位置出现能力声明（操作标签 9）之后才合法。声明列出严格递增、非零的 u32 能力码，由 Owner 或 Admin 的个人设备签署，只增不减。不支持某项已声明能力的客户端，验证声明之前的记录，并在声明处以 `upgrade-required` 停止；不报告账本损坏，也不跳过这条记录。写入方和服务端拒绝自己不支持的声明，也拒绝使用此前未声明能力的操作。
- 更换密码套件或其他创世级参数时，新建一个带新创世记录的账本。旧账本永不改写，只在末尾通过一项能力追加指向新账本的链接记录，与 MLS ReInit 关联替代组的方式相同。

其余格式仍只支持当前格式。内容、日志、本地存储和快照格式都没有线上数据：每个入口仅支持当前格式；不增加旧格式解码、双读者、schema 升级、旧数据导入或兼容门面。快照总能从完整的 v1 历史重建，所以快照格式变化不会破坏账本兼容。不支持的格式直接失败且不改写输入。当前存储的正常重开、同一当前格式内的账本历史验证与代次密钥历史恢复仍须保留。这项范围决定不选择待定的新格式，也不批准生产启用。

## 保留的已验证状态（提议）

在空闲的桌面级机器上，全量重放每条记录约 5.4 毫秒（4,096 条需 22 秒）；在已有 view 上追加一条约 5 毫秒。因此每次请求都从创世重放，对服务端和客户端都不可行。本节提议在 core 中增加一个入口，让一方从**自己**此前验证过的状态继续。它不改变账本 v1 的记录格式。详见[提议 note](../.agents/notes/proposed/architecture/2026-10-19-e2ee-retained-ledger-state.zh.md)。

- **导出。** `exportVerifiedState(view)` 返回规范的状态编码（与快照正文使用同一种确定性编码，因此同一状态只有一种字节表示），以及创世、长度、头哈希和 `stateDigest`。摘要只在导出时计算一次。
- **恢复。** `restoreVerifiedState({ bytes, genesis, length, head })` 按规范解码，对格式错误的输入返回带类型的错误。它不重新验证签名、不重新校验密钥的曲线点，也不重算摘要：这些字节来自同一方自己的存储，该方本来就信任这份存储，重算只增加成本，不增加保护。恢复出的 view 与导出时的 view 一样可以 `extendLedger`。
- **权限范围。** 保留状态只对导出它的一方、只对该方自己的决定有效（服务端的写入准入、客户端的本地视图），绝不接受来自另一方的保留状态。接收别人的状态仍然使用背书快照。
- **衔接。** 新记录从保留的长度之后读取，第一条必须指向保留的头哈希。不一致说明外部存储被回滚或出现分叉，直接失败关闭。这项检查针对的是不受信任的存储，不是保留状态本身。
- **完整性。** 保留状态必须包含验证下一条记录所需的全部重放事实，使结果与全量重放完全一致：成员、设备、角色、已用的签名/加密密钥与成员 ID、已关闭的加入请求、epoch 状态、历史包、已用的 epoch 承诺，以及出现后的已声明能力。已移除设备的历史作者归属和原始 epoch 发布记录不保留；恢复出的 view 报告其不可用，与来自背书快照的 view 相同。
- **摘要的用途。** `stateDigest` 用于跨方比对（comparison note）和后台审计，不在热路径上做自我校验。
- **后台审计（暂缓）。** 从创世全量重放并与保留的摘要比对，可以发现程序错误或存储损坏。它是可选项，不在本次范围内，也可以放在服务端请求运行时之外（例如读取已存账本和保留摘要的独立 worker）。若日后加入，不一致即视为事故，在解决前停止该账本的写入。
- **格式。** 保留编码只支持当前格式。编码变化后，丢弃保留状态，并对 v1 历史做一次全量重放来重建。
- **读取。** 服务端返回历史分页时无需在读路径上验证，客户端会验证收到的内容。服务端的验证属于写入准入。
- **本地存储。** 若采纳，客户端打开时可以恢复本地保留状态，而不必重新验证全部已存记录，这将取代下文所述的全量重新验证。

## 本地 epoch 保护边界

接收者须能重新打开已持久保留的安装密钥，不能要求原发送者一直有效。
可信 host composition 可初始化一次原生 protect/unprotect 能力；普通消费者
继续使用 opaque key。原生保护须将用途、Org genesis、接收者、epoch、commitment
与密钥一起绑定。被攻破的 host 可以复制明文；此契约不宣称操作系统隔离，
也不声称清零能追回这些副本。

安装报告须晚于持久保存、实际回读／解封和独立 commitment 校验。失败不得
宣称已报告安装。原生工作结束和临时清理须晚于取消请求、早于取消／Scope
完成。禁止明文降级或生产装配。原生适配器选择、恢复文件／包装／并发仍单独验收。
发布者窗口改用先暂存后提交；vault 与真实平台保管仍单独验收。本 Spec 修订保持 draft；边界方向已定和合成
测试通过，不代表整份修订获批或原生存钥通过验收。

## 定稿内容 v0 与快照继续位置

按用户决定采用 content v0 替代 v2，不保留 v2 读端。docEpoch 固定为 0；四种
文档 purpose 共用一把文档叶密钥，方便将来按文档授权；purpose 仍进入 AAD 与
签名，阻止跨用途篡改。更新帧不变，固定开销 143B。两种快照在签名公钥之后
加入 u16be 长度和 continuationOffset 原始 ASCII 字节，因此开销为
143 + 2 + offset 字节；整个头同时绑定进签名与 AAD。

SDK provider 头仅为 [4]，不再在 provider 头里编码 offset，无旧格式双读。内容
准入网关读取真实宿主记录边界，检查该位置存在且不超过真实 head，再将原密文
交给不感知内容的 Streams。读端认证并解密后，对比 SDK 给定的精确继续位置。
篡改、搬移、越过 head、非记录边界均失败，不推进文档/游标持久对。客户端不对
不透明 offset 做数值或字典序推断。宿主边界查询能力不等于快照信任来源。

通用 ASCII offset 使用 u16 长度界；已发布 SDK 的 4096B sealing-overhead
限制使适配器上限更小。真实 Loro/Flock 消费者用快照和后续增量 bootstrap。
以上方向已确定，修订稿仍为 draft，待用户审批，不代表产品启用。发布者密钥
可用性改用[先暂存后提交](e2ee/publisher-key-recoverability.zh.md)，不再保留旧 A/B 提案。

## 本地 SQLite 持久化

白皮书的威胁模型信任客户端及操作系统。当前格式的存储在创建或打开时检查
application/version 和固定 genesis/recipient 绑定，使用 WAL/FULL 与事务；打开
时重新验证已存账本记录。SQL 行不建立权威。每次操作保留第一份原件的目标行
读回及真实账本回滚 pin 比较；head/count 不变时不写 pin。不为检测其他本机进程
改库而逐次扫描旧行、触发器、schema 或本地写入计数。

快照发布仅为 current 和 Pending 保留密文正文。新快照成为 current 时，在同一
事务内清除旧 Accepted 正文，保留 offset、signer、SHA-256 摘要、原凭据时间窗口
和 phase。归档身份的同字节重试仍然幂等，同 offset 的不同字节冲突，旧身份
不能再次成为 current。容量预算只计算保留正文的行，不计算归档身份。

# Session file attachments in the CLI

Attachments choose their transport before authentication or source-byte reads. Native
same-machine ordinary files use durable local references; images use local files; remote targets and clients
without native provenance use the existing transfer boundary. The
[local-reference Spec](../../specs/local-attachment-references.md) explains the
ownership decision, while [attachment drafts](../../specs/session-files.md) owns
send-time preparation. A failed local preparation retains the complete draft and
never falls back to upload.

## Same-desktop images

New images use `SessionImagePayload` with `transport: 'local'`, a machine ID and
UUID `localImageId` equal to the initial `imageId`. The renderer prepares through Electron `prepareLocalImage`; the CLI persists the source reference before readiness. Existing source files are
used directly, while pathless image bytes are saved once. Preparation and dispatch do not wait for
cloud upload. Protected plaintext preparation is rejected.

`message-handler.ts` owns image backfill and restart recovery, using
`session-attachment-transfer.ts` for uploads. Publication requires the cloud
attachment-upload capability and an authorized bridge; local-only OSS composition
never acquires cloud access. It
retries with a capped delay until success or cancellation; generation fences
prevent retired work from publishing. Shutdown aborts and awaits owned tasks.
Publication changes transport to `r2` and supplies a cloud image ID while retaining
`localImageId`, machine and storage-session metadata. Durable receipts reconcile
history, frozen execution inputs and queued inputs through one promotion path, including references authored
after upload completes. Receipt adoption validates scoped metadata without reopening
the source file; only execution and a new upload read the bytes. Recovery
checks the receipt first, so completed uploads do not depend on local byte availability. Dispatch reconciles its target and current queue before
execution. Published inputs prefer the local file on its machine and can
use their uploaded bytes when the local file is unavailable.

Original-path preparation persists metadata without copying the image. Subsequent
local reads and uploads read current source bytes: edits are visible, and missing
or unreadable files fail. Cleanup never removes original source files.

Pathless image publication writes and flushes a private temporary file, then
atomically renames it before publishing metadata. These saved files stay under the
session-file quota without automatic retention GC because queued or frozen inputs
may still reference them. Storage pressure rejects admission. ACP receives image
bytes and a resource link to the local file; it does not create a workspace copy.

History, fullscreen and queued previews preserve the complete image metadata.
`resolveLocalImage` checks the scoped local reference before the renderer fetches
the host file resource. Published images retaining local identity try this path
first and use authenticated cloud downloads when local bytes are unavailable.
Pending local images never fall back to cloud URLs. Images without local identity
retain the legacy cloud image behavior. Existing image-shaped `local_attachment` records
use the local path flow below.

## Native local references

`session-attachment-routing.ts` selects the route. Original files immediately produce
`local_attachment` with `machineId`, `path`, `kind`, `fileName`, `mimeType` and
`sizeBytes`, without IPC or preparation reads. Generated bytes use the authenticated
local `session/attachment-prepare` RPC and are saved under
`<Lody data>/local-attachments` using a private, flushed temporary file and atomic
rename. There is no ID-to-path registry, registration binding, inheritance write or
resolve RPC. Managed files remain durable independently of Electron staging;
reclamation is not implemented.

Resend, fork and scheduled dispatch reuse the path payload. Actual readers check
the machine and resolve the current regular-file path. ACP local path reads additionally
require the frozen execution requester to be the machine owner; protected
workspaces reject this route. Images also supply visual bytes to ACP. Original
file edits remain visible, symlinks resolve at use time, and missing files fail.

## On-demand download from another device

Local owner downloads retain the existing bounded chunk format and 100 MiB limit.
Remote `file/download-chunk` requests use the existing authorized file reader and
its workspace containment, including for attachment paths. A path in conversation
content cannot grant access outside those roots. Generated files outside the
workspace therefore remain local-only. The existing `localAttachmentDownload`
capability gates the download request extension. Downloading does not upload,
rewrite or register the attachment. Offline and unavailable files report errors.

## Existing transferred attachments

The following lifecycle applies to legacy `file`/`image` inputs and remote
transfers, not to the `local_attachment` path flow.

## Ingest

`message-handler.ts` has two entry points: `handleSessionFileUpload` (cloud, and MCP
`lody_upload_files`) and `handleSessionFileSendLocal`. Local bytes live in
`session-file-blob-store.ts` under `~/.lody/session-files/<ws>/<sess>/<fileId>` and are
persisted as `transport:'local'`.

## Dispatch

`materializeSessionFileAttachments` copies or downloads the bytes to
`<workspace>/.lody/attachments/...` and sends ACP `resource_link` blocks with `file://`
URIs, so an agent can open the real file rather than a pasted excerpt.

Human image inputs keep their ACP `image` block for visual context and additionally
materialize the same bytes as a `resource_link`, so agents can echo or transform them
through a local file path.

## Backfill to the relay

`session-file-backfill.ts` uploads local blobs through the injected relay, flips
persisted blocks from `local` to `r2`, and rewrites `fileId` to the relay key. It is
triggered by dispatch, by opportunistic handoff, and by startup recovery.

Because the flip rewrites the fileId, a `.r2meta` sidecar recording `relayFileId` is
written BEFORE the flip. Restart recovery uses it to finalize a flip that committed but
was not marked, instead of retrying "not yet persisted" forever.

A blob with no history block, older than the draft retention window, is an abandoned
staged-but-never-sent draft and is reclaimed. File and image writes share quota admission and are serialized
process-wide so the quota check sees a consistent total.

Backfill commits (the marker write and the history flip) are gated by an authorization
generation plus an `AbortController` owned by `MessageHandler`. `disableRemoteBackfill`
(offline or revoke) aborts the in-flight relay upload and supersedes started tasks, so a
revoke landing mid-upload can never adopt the uploaded bytes — S5/D10, revocation must
prevent upload. Re-enabling opens a new generation and the pending blob backfills on the
next scan.

## Agent output

Agent-to-human ACP `image`, `resource` and `resource_link` output is materialized by
`acp-agent-attachments.ts` during the `message-handler.ts` ACP flush: upload to the
injected image/file capability, then append `image_group` / `file` history blocks. A
`resource_link file://...` is accepted only when it is contained in the session
workspace.

## CLI and MCP input

[CLI input attachments](../../specs/cli-session-attachments.md) adds a preparation
boundary before user history is authored. `session-input-attachments.ts` resolves
caller paths and snapshots all sources before any transfer. The shared
`session-attachment-transfer.ts` performs uploads for both this preparation and
MessageHandler's assistant output/backfill. Transport never appends history.

Create and chat write the same complete input blocks to user content and frozen
execution input. MCP acceptance persists references in `operation_inputs` with
fixed Session/Turn IDs; daemon recovery consumes these instead of source paths.

## Encrypted workspace attachments

The transfer selects the encrypted-file route only for an admitted encrypted workspace and obtains a short-lived attachment grant from its host-owned device credential. Paired machine ports receive the relay URL explicitly from cloud startup, without restoring an account CLI token. Files and images upload bounded opaque parts; the protected conversation stores the secret manifest. Downloads authenticate parts before materialization, and local backfill retains that manifest with its crash-recovery receipt. The [file-key decision](../notes/implemented/architecture/2026-10-28-encrypted-attachments.md) explains rotation, retention and failure trade-offs. Ordinary transfer paths remain unchanged.

### Local reference integration boundaries

Initial session prompts and subsequent turns use the attachment path directly.
Draft admission bypasses cloud attachment authorization only for a known native
same-machine target; remote drafts wait for workspace mode before queueing; prepared cloud references still require admission,
and protected-workspace restrictions remain in force. Local attachment cards open resolved
paths as canonical paths, preserving literal `#`, `?`, `%` and colon suffixes.

OSS-to-cloud export/migration rejects `local_attachment` references during local preflight,
including opaque legacy contents and removed turns retained in CRDT history. The migration
does not transfer files identified by machine-local paths, so these snapshots must not be published as complete.

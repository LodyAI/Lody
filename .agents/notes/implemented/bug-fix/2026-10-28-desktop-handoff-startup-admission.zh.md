# 桌面转交的启动准入

Status: implemented
Translation: current

[English](2026-10-28-desktop-handoff-startup-admission.md)

## 摘要

桌面通道可能在完成 Host 准入和应用导入之前就取得进程互斥租约。旧的转交路径允许这个
尚未就绪的持有者把深链接确认进一个无人消费的启动缓冲，于是随后因 Host 冲突退出的启动
会丢掉该链接。现在转交确认与启动处理器绑定对齐：正常慢启动期间链接保持等待，
被拒绝的启动明确拒收，持有者与客户端使用各自有界的等待。该改动由确定性的启动、租约和
准入测试覆盖；打包后的跨通道启动验收仍未完成。

## 问题与决策

桌面租约与消费启动的能力生命周期不同。`desktop-exclusion.ts` 负责端口，而 `index.ts`
仍可能在 Host 检查后拒绝启动，或在延迟加载应用模块时失败。取得租约时确认转交只能证明
端口所有权，不能证明链接会被处理。

`desktop-launch-admission.ts` 将两者分开。它从 pending 状态开始，仅在 `index.ts` 把既有
启动缓冲绑定到 `application.handleDesktopLaunch` 后才接受链接。拒绝 Host 准入、应用导入
失败或顶层启动失败会把本次进程的准入标记为 rejected；等待中和之后的转交都会收到明确的
否定响应。就绪后，链接进入既有启动缓冲和解析器，不建立第二条路由。

持有者最多等待准入五秒再回复，发送客户端等待六秒，从而能观察到持有者的拒绝而不是与之
竞速。若准入超过持有者期限但之后仍成功，链接仍会交付；发送方可能已显示冲突，但不会产生
虚假成功，也不会留下永久缓存的接受状态。socket 读取超时与准入超时分离：先及时读完请求，
之后由准入拥有下一个期限。

认证及其他云端回调仍不进入该转交，Host 独占不变，失败进程仍不加载凭据或业务模块。

## 备选方案

在 Host 准入后立即确认能避免大多数误报，但应用模块延迟导入失败时仍会确认无法消费的链接。
等 renderer 导航完成再确认会让发送方等待超过交付所有权所需的范围。移除缓冲则会复制既有
启动路径并丢失早期回调兼容。

## 证据与限制

`desktop-exclusion.test.mjs` 覆盖异步准入、拒绝和等待中的准入状态；
`desktop-startup.test.mjs` 覆盖 Host 冲突启动在竞争 daemon 停止前后均拒收、故障解除后新
持有者正常接收、正常转交、认证隔离和既有 Host 所有权。启动夹具使用已解决 Promise，不用
sleep。打包安装、真实系统分发和跨版本行为仍需发布验收；当前协议期限属于源码级行为。

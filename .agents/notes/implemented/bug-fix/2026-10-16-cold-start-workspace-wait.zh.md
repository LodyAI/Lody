# 冷启动延续启动画面，不再显示“正在切换工作区”

Status: implemented
Translation: current

[English](2026-10-16-cold-start-workspace-wait.md)

## 摘要

iOS 用户反馈，应用经常提示“正在切换工作区”，随后白屏刷新，正在输入的内容和正在查看的页面都没了。实际上并没有切换：
前端代码不会自行刷新页面，所以白屏是 WebView 被重新加载；每次重新加载都是一次冷启动，此时工作区数据 scope 还没有
就绪。这段等待原本总会挂载工作区布局，并在内容区显示“正在切换工作区”。现在冷启动会延续启动画面，直到 scope 就绪；
只有页面之前已经打开过另一个工作区时，才会提示正在切换。这次去掉的是误导性的界面，而不是刷新本身或输入丢失：
iOS WebView 为什么会被重新加载，这里没有查明。

## 问题

在乐观路径（本地有缓存 token）上，只要 `useResolvedWorkspaceScope()` 没有返回工作区 id，
`routes/$workspaceName/_auth.tsx` 就渲染同一个占位页。runtime 为当前路由的 slug 创建出来、并且首次 doc-metadata
扫描完成之前（`lib/workspace-data-scope.ts`），scope 都不会就绪，而每次启动都要经过这个过程。因此每次带缓存
token 的启动，都会在已挂载的布局里显示“正在切换工作区 / 正在完成工作区访问与权限校验”，尽管此前什么都没有打开。

关于刷新本身的依据：渲染进程里唯一会自动调用 `location.reload()` 的地方，是用户确认后的清除缓存
（`lib/clear-local-cache.ts`），错误边界也从不自动重置。所以“白屏后出现新页面”来自宿主，最可能是 iOS 的
WebContent 进程被终止、原生壳重新加载了页面。原生壳不在本仓库中，这一点也没有在真机上确认。

排查后排除的原因：`docMetaSubscriptionAtom` 会在异步 watch 回调中调用 `get`（`hasCachedDocMeta`）。在
jotai-effect 2.2.3 中，元数据缓存变化不会因此让 effect 重跑，所以正常的元数据更新不会重置 scope。

## 决定

`components/workspace-data-wait.tsx` 记住在已挂载的认证布局下、为哪个账号、上一个数据 scope 就绪的是哪个工作区；
布局卸载时（例如退出登录）就忘掉它，因为那时已经没有需要保留的布局。`_auth` 的等待据此选择：

| 情况                                                                   | 等待界面                                       |
| ---------------------------------------------------------------------- | ---------------------------------------------- |
| 当前布局和账号下还没有任何工作区就绪过（启动、宿主重新加载、重新登录） | 启动画面加“正在加载工作区”，同时预加载布局代码 |
| 同一个工作区再次变为未就绪                                             | 已挂载的布局内显示“正在加载工作区”             |
| 之前就绪的是另一个工作区                                               | 已挂载的布局内显示“正在切换工作区”，与原来相同 |

真正的切换仍然保持 `MainLayout` 挂载，侧边栏和工作区标识保持稳定。冷启动时没有需要保留的布局，而启动画面本身
已经预留了侧边栏一栏，所以延续它与第一帧在视觉上是连续的。所有情况仍然是 gate 为 `workspace_data` 的
`BlockingWaitPlaceholder`，30 秒恢复页和卡住上报都不变。

## 未采用的方案

- **只改文案。** 在布局里把冷启动的等待改叫“正在加载工作区”，启动画面之后仍然会多出一个加载界面。
- **在 scope 就绪前渲染工作区内容。** 依赖工作区 scope 的组件在就绪前会失败关闭、返回空数据，所以内容区只会显示
  空白或“找不到”，而不是等待界面。

## 取舍与局限

- 桌面端冷启动时，真正的侧边栏改为在数据就绪后才出现，而不是和内容区占位页一起出现。在那之前，它依赖 scope 的
  列表本来也是空的。
- 等待时长不变：仍然要等 runtime 打开、首次元数据扫描完成。
- 宿主重新加载 WebView 时，未发送的输入框内容仍然会丢失。保存这些内容，以及查明 iOS WebView 为什么被重新加载，
  是另外的工作。

## 验证

`tests/blocking-wait-placeholder.test.tsx` 覆盖六种情况：

- 冷启动渲染启动画面，不出现“正在切换工作区”；
- 另一个工作区就绪过之后再切换，内容区显示“正在切换工作区”；
- 同一工作区再次等待时留在内容区，也不提示切换；
- 另一个账号打开过的工作区按冷启动处理；
- 认证布局卸载（退出登录）之后的等待按冷启动处理；
- 一直没有就绪的冷启动仍然会进入恢复页。以上都没有在 iOS 真机上运行。

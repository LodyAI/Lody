# 保留 Codex 认证原始错误与可恢复的凭据清理

Status: implemented
Translation: current
PR: https://github.com/LodyAI/Lody/pull/1298

[English](2026-10-07-codex-credential-failure-recovery.md)

## 摘要

Codex API Key 保存或验证失败后，回滚删除再次抛错，会让调用方收到凭据删除错误，
掩盖最初的失败。现在失败处理尝试删除凭据，但保留原始错误，并留下未激活代次记录，
交由现有清理协调器处理。旧活动密钥仍可使用，重启后也能继续清理，无须新增队列或
回滚元数据。行为测试和消融实验支持这一更小的恢复路径；在 Nightly 产物中观察到的
另一处原生加载缺陷，仍须由产生该产物的构建修正。

## 原因与归属

[账号隔离决策](../../proposed/architecture/2026-09-26-codex-account-profiles.zh.md)和
[Spec 草案](../../../../specs/codex-account-profiles.zh.md)要求 API Key 代次由执行
主机的系统凭据库持有。提交 `df03b280c`
（[#1027](https://github.com/LodyAI/Lody/pull/1027)）引入了
[Profile Store](../../../../apps/cli/src/agent/codex-profile-store.ts)与凭据库。
暂存时先持久化候选名称，再保存密钥，但不改变活动代次或就绪状态。只有验证成功
才能激活候选代次。

此前的失败处理依次等待删除凭据、恢复旧元数据快照、重新抛出原始错误。删除失败
会覆盖原始错误；恢复元数据失败也可能覆盖原始错误。如果删除失败后仍恢复旧快照，
则会遗忘一个可能已经存入凭据库的密钥。

macOS arm64 Nightly 0.104.0-nightly.4 产物提供了真实的双重失败：打包后的
CommonJS keyring 包装器在 ESM chunk 内执行原生 `require` 调用，加载原因链包含
`require is not defined`，保存和回滚删除均返回通用凭据库错误。随包提供的
2.1.0 原生包在 Node 与应用主程序、Helper 运行时中直接加载正常；改用外部加载后，
合成凭据的保存、读取、删除、重复删除均成功。损坏的加载器没有执行到验证步骤。

公开源码的 [Vite 配置](../../../../apps/cli/vite.config.ts)已经将
`@napi-rs/keyring` 保持为外部依赖。检查包是否存在或 CLI 能否启动，无法覆盖
认证时才执行的延迟加载。这次源码修正保留失败恢复能力，但没有修复已安装产物，
也不能据此认定当前公开构建存在同样的打包缺陷。

## 恢复决策与简化

保留立即删除作为尽力清理，并始终抛回同一个原始错误对象，包括取消原因。即使
立即删除成功，也保留候选代次元数据：删除不存在的凭据是幂等操作，现有协调器
可以在后续扫描中完成记录清理。因此，失败或部分成功的凭据写入不会留下无法发现
的密钥。

暂存没有激活候选代次，所以无需回滚元数据。
[现有协调器](../../../../apps/cli/src/lib/provider-setup-manager.ts)已经扫描 Profile、
输出有限的待清理诊断，并在清理失败后安排再次扫描。直接复用这些行为，不新增
异常类型、重试字段、队列或服务。调查中使用的一次性产物布局解析器不进入长期
维护的补丁；可恢复清理的契约由回归测试负责。

## 验证与消融

[所属测试套件](../../../../apps/cli/src/agent/codex-profile-store.test.ts)现有
19 个行为用例。六个新增用例将保存、验证、取消失败分别与 pending、ready 状态
组合，同时令删除失败，检查原始错误、就绪状态与旧活动密钥、重启及协调清理失败
后的记录保留、最终清理，以及成功重试。保存夹具先存入合成密钥再抛错，覆盖部分
写入。另一个用例覆盖立即删除已经成功后的协调清理。

消融只在测试编译时替换失败分支，实验之间不修改源码；每组运行相同的 19 个用例。

| 变体 | 结果 | 可观察回归或决策 |
| --- | --- | --- |
| 最终恢复路径 | 19 通过 | 保留原始错误与重启清理能力。 |
| 去掉删除错误保护 | 6 失败，13 通过 | 清理失败覆盖原始错误。 |
| 删除失败也恢复旧元数据 | 7 失败，12 通过 | 遗忘待清理项，重启后无法协调候选清理。 |
| 去掉立即删除 | 2 失败，17 通过 | 被拒绝的密钥留到后续扫描才能删除。 |

较早版本对回滚错误提供保护并恢复元数据，其 19 个用例也通过；去掉恢复操作后仍
全部通过。最终套件直接验证了保留已删除候选记录的安全性。因此删去这次额外写入，
不再为一个不必要的操作增加错误保护。

所属套件、凭据 Broker 套件及 Provider Setup 套件一起通过，共 38 个用例。
提交前，全仓格式、类型及 lint 检查也通过；CLI 完整套件有 3,499 个通过、
4 个跳过。测试使用合成密钥、临时目录、注入失败与显式取消信号。

根 `pnpm check` 在 Node 26.10.0 下停于无关的启动画面存储不可用测试；在干净的
main `1417cf879` 中单独运行，也复现相同失败。单独运行的 i18n、导入、平台边界
及公开仓库边界检查均通过。文档检查有六个指向未就绪 Kimi/Pi 子模块的既有链接
错误。未执行 Windows/Linux 验证、完整桌面 UI 自动化或修复后的发布产物验证。

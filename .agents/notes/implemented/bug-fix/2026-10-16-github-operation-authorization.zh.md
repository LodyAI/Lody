# 将 GitHub 操作授权与登录绑定分开

Status: implemented
Translation: current

[English](2026-10-16-github-operation-authorization.md)

## 摘要

个人 GitHub 设置之前调用账号绑定，既会拒绝 GitHub 与应用邮箱不同的用户，也会新增登录身份。
现在改为通过云能力单独申请操作授权。浏览器保留 PKCE 验证凭据，并在当前登录用户下完成回调；
原生客户端继续跳转浏览器设置。本次修改仅涉及操作授权，现有 Git 提交作者选择策略仍然独立。

## 决策与职责

本次替代[授权入口修复](2026-10-11-github-personal-authorization-entry.zh.md)中的浏览器账号绑定部分。
共享 hook 调用独立的发起／完成操作，辅助模块在 sessionStorage 中保存一个待完成的验证凭据。
回调只消费一次，在发送完成请求前从历史记录移除临时数据。设置页不再通过社交登录或账号绑定获取操作权限。

桌面浏览器设置是聊天或会话上的弹窗，不能用当前地址作为 OAuth 回调目标。发起时构造标准 GitHub 设置地址；
设置路由打开弹窗并返回聊天页时保留授权 fragment。原生客户端继续打开浏览器设置，不通过 URL 传递 token 或应用登录凭据。

云实现必须将操作凭据与登录账号分开保存，并将完成操作绑定到发起用户、工作区和 PKCE 凭据。
公开客户端只声明操作 DTO 和能力描述。服务切换后，过去来源于登录账号的授权需要重新显式授权一次。
其他账号绑定的邮箱策略不放宽。

## 验证边界

确定性的浏览器凭据及设置测试覆盖匹配／无效回调、单次消费、原生跳转和本地能力门控。
后端测试覆盖不同邮箱、重放、用户／工作区／过期限制及凭据刷新代次。
真实 GitHub OAuth 和原生浏览器往返仍需在线冒烟验证；本文不代表已部署。

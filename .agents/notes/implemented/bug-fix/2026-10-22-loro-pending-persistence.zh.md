# 保留重启前已收到的 Loro 更新

Status: implemented
Translation: current

[English](2026-10-22-loro-pending-persistence.md)

## 摘要

远端更新缺少前驱时会暂存，不推进文档的已应用版本，也不触发变更事件。因此，现有 Promise Repo 持久化路径仅保存普通快照或已应用更新时，可能漏掉已收到的数据。接入 Loro 1.17.0 与 loro-repo 0.24.0，让这些更新经过现有 SQLite 保存、重新打开的边界后仍可恢复。这保障本地持久化，不证明用户夜间流量的根因，也不限制 Streams 的恢复下载量。

## 决策与职责

Loro 单独导出尚未应用的远端操作。Repo 负责观察导入、为仅有 pending 的变化安排保存、把收到的输入保留在现有更新日志中，并保留存储写入期间新收到的数据。内置存储适配器把日志与快照合并；只有操作仍可恢复时，正常压缩才能删除对应字节。Lody 通过工作区 catalog 和 CLI 的精确运行时依赖消费这些正式版本，不增加另一个持久化所有者，也不修改存储格式。

已应用版本和单次导入结果都不能查询全局 pending 状态。本地保存不表示缺失依赖已到达，不能据此上传被视为完整的远端快照，也不能推进另一个副本的 cursor。导出失败时保留上一份可恢复的 checkpoint；如果远端前驱永久缺失，仍需找回真实数据或使用可用的替代快照。

[流量调查](../../proposed/bug-fix/2026-10-22-desktop-network-amplification.zh.md) 保留原始证据及下载限额提案。保留 pending 比丢弃后从更早的 offset 重拉更可靠：后者依赖远端历史仍被保留，也可能反复下载大文件。网络恢复限额仍是独立工作。

## 验证与限制

CLI 回归使用真实 Repo 和 SQLite：保存 `base|`，先收到 B 而缺少 A，flush、关闭并重新打开同一数据库，补 A 后必须得到 `base|AB`。测试再重新打开一次确认最终结果，同时覆盖 `import` 和 `importBatch`。现有 registry 依赖下两例均得到错误的 `base|A`，无需服务器或用户数据即可证明持久化缺口。

冻结锁文件安装后，各运行域内使用同一个 Loro 1.17.0 实例。核心全部 41 个文件、Repo 全部 103 个文件均与已核对 SRI 的 npm 包一致，没有候选包 override；正式包下两项 SQLite 回归通过。仅用于测试的旧版 Loro CLI 保留独立的 1.16.3 override。

完整 `pnpm check`、格式化、文档检查和真实 CLI 构建通过。另从构建输出的 Core/Repo chunks 导入，完成 16 条 SQLite 恢复断言，包含第二次重新打开。快照测试在等待同步和清理时驱动当前时刻的零延迟任务，不推进显式控制的防抖时间。无变化的导入也可能在存储 I/O 后触发 Repo 已有的公平调度；冻结该计时器却等待同步屏障会卡住测试。这些验证不包含用户现场网络抓取、Nightly 安装验收或生产流量测量。

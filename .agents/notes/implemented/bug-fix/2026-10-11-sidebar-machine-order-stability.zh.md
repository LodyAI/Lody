# CLI 暂时不可用时保持侧栏设备顺序

Status: implemented
Translation: current
PR: [#1488](https://github.com/LodyAI/Lody/pull/1488)

[English](2026-10-11-sidebar-machine-order-stability.md)

## 摘要

侧栏原本使用实时 CLI 设备身份把桌面本机分组置顶。运行状态快照缺失时，分组退回按名称
排序；快照恢复后又移回顶部。现在独立的展示身份为排序保留最近确认的本机，
本地操作仍使用实时运行状态。关闭本地 Agent 会清除这项优先顺序；
CLI 报告新的设备身份时会替换原值。
探测追踪现在区分请求失败与恢复；原始探测失效的触发原因仍未确认。

## 决策与证据

`CliSupervisor.pollRuntimeState` 在探测连续失败后清空 `latestRuntimeState`，
Electron 的 `buildCliState` 随后发布不含 `runtime` 的状态。
`localProbeEffectAtom` 将这种缺失映射为 `localMachineIdAtom` 的空值。
侧栏于是把原来的本机分组移到其他设备中，原先这些分组只按所属用户和名称排序。
状态恢复后，该分组又回到顶部。
这是内部排序规则，不是可配置的排序选项。
逐帧检查反馈视频发现，3.862 秒和 7.172 秒发生整组换位，同时 iMac 的文件夹导入按钮
出现、消失。该按钮只在 `localSection` 渲染；按钮可见性和该分组位置都取决于实时本机身份。
第一次换位前后，选中的会话行没有改变。这将观测到的位移关联到本机分组身份变化，
而非已读状态或选中会话的排序。录制设备没有可关联的 CLI 日志，因此身份变化的上游原因
尚未核实。仅有 `reconnecting` 阶段不够：快照仍带有相同本机身份时，这个分组不会因此换位。

静态分析继续追踪了身份缺失的上游路径，未修改运行时代码。
[CLI reporter](../../../../apps/cli/src/lib/cli-runtime-state.ts) 在启动命令中接收一次设备 id，
此时本地探测服务尚未启动；连接状态变化不会清空它。Electron 观测的是可用性：
[supervisor](../../../../packages/cli-supervisor/src/supervisor.ts) 默认每 1,000 ms 探测一次，
请求超时为 800 ms，连续三次失败后丢弃快照。受管子进程可以在此期间始终存活，
恢复后仍返回同一个 id。PID 不匹配、所有权丢失和进程生命周期变化是其他清空快照的路径。
[主进程适配器](../../../../apps/electron/src/main/services/cli-service.ts) 将连接、超时、协议
等所有探测错误统一转成 `null`。它已经为 `getLocalMachineId` 保留 `cachedMachineId`，
但 `buildCliState` 只转发 supervisor 的实时快照。因此 CLI 无须改变设备 id，
渲染器就可能看到 `A → null → A`。

会话导航只改变路由，不重启 CLI，也不重新挂载应用级探测 effect。打开尚未缓存的会话
可能加入文档 room。探测 handler 与本地数据通道引擎运行在同一个 CLI 进程中；
[引擎](../../../../packages/shared/src/local-loro-data-plane-server.ts) 同步导出 Loro 增量
并编码数据。共享 scheduler 会在任务和帧之间让出事件循环，但无法抢占一次导出。
入站更新通过此 scheduler 之外的 Promise 链执行，重组文档增量后同步导入。
帧上限是 32 MiB；分片限制的是单个传输帧，并未限制完整导入或它的 CPU 耗时。
因此事件循环争用是探测超时的候选原因，并非原视频中已经测得的原因。
本地 room 的云端补齐限制为四项并发任务，不会激活 SessionDocument 包装器。
双通道模式下，已知远程会话 room 只挂载云端 transport，不能假设点击任意会话都会
触发本地 CLI 文档导入。
在双通道模式下，身份缺失还会改变 workspace target router 的本地/云端选择并调用
`refreshTransportRoutes`，身份恢复时再次调用。这可能增加同步工作，但尚未证明形成反馈循环。
普通后端重连本身不能解释身份缺失。

初始化阶段还有一处竞态：`localProbeEffectAtom` 接收首次 `getState` 结果与推送状态时
没有检查版本，首次读取拒绝也会在已有有效推送后清空实时身份。没有额外的重挂载或重新加载，
它无法解释反复点击会话时的波动。本次调查前，探测错误在主进程适配器中丢失分类。CLI 定时器延迟
警告和阻塞采样默认阈值分别为 5,000 ms 和 4,000 ms，所以没有这些日志也不能排除超过
800 ms 探测超时的较短延迟。确认原始触发原因需要录制设备上可关联的探测错误、耗时、PID
与生命周期证据。已经实现的改动稳定展示顺序，并未修复或确认上游探测失效。

检查可用的本地日志发现，后端重连期间仍保留运行快照；另有一段探测服务尚未监听时的启动空档。
这些日志没有证明录制设备上发生了反复快照缺失。已安装桌面的 renderer bundle 使用相同的
快照身份推导，但磁盘中的文件不能证明正在运行的进程加载了哪个版本，也不能证明录屏版本。

`CliService` 现在会在返回 `null` 前观察有类型的探测错误。
`createCliProbeTrace` 记录错误类型、请求耗时和超时设置、子进程 PID、适用时的 HTTP 状态，
以及连续请求失败次数。首次和第三次失败、错误类型变化时会记录；持续失败每 30 秒记录一次。
恢复时记录实际观测到的 PID 和是否存在非空设备 id。计数包括启动和 reconcile 请求，
并非 supervisor 的轮询失败计数。正常轮询不产生日志；不记录数据、cause、错误消息或实际
设备 id，追踪失败不能改变探测结果。Supervisor 状态追踪也增加了身份是否存在的标记。
这纠正了较早的[每日日志追踪记录](../feature/2026-09-25-daily-log-crash-and-stall-tracing.zh.md)
中将 reconnecting 一概归因于阻塞的推断。超时、路由和进程生命周期行为没有改变。

`lastKnownLocalMachineIdAtom` 在渲染器内存中保留已确认的身份。
`compareSidebarMachineOrder` 先按该身份排序，再按所属用户、名称和 id 排序。
它只影响分组位置：导入和删除操作、本机标签、本地请求路由及启动门控仍使用实时输入。
直接在断连时保留实时身份会影响这些其他消费者。首次确认身份时仍可能移动一次本机分组；
这项偏好不持久化。

本次修复保留了[侧栏分组记录](../feature/2026-09-25-deep-sea-palette-and-sidebar-groups.zh.md)
中本机优先的决策，并补充了[排序 Spec](../../../../specs/sidebar-project-ordering.zh.md)。

## 验证与限制

回归测试以合成 IPC 状态事件驱动真实探测 effect，比较在反复重连、离线、启动、致命失败
和停止状态下的设备顺序。同时检查实时路由身份仍会清空、显式关闭会重置优先顺序、
新身份会替换旧身份，以及首次 IPC 读取失败不会抹掉已推送的展示身份。
现有项目排序测试覆盖设备所属用户和同名时的确定性顺序。
探测、项目排序、键盘导航、本地项目行渲染和运行策略五个测试套件共 23 项测试通过。
全仓类型检查、`pnpm format` 和 `pnpm check:quick` 也通过。
`NODE_ENV=test pnpm check` 未通过：Components 套件有 4,887 项通过，
未修改的 boot-shell 存储不可用测试有一项失败，单独运行也能复现。
四个 CLI 套件最初因沙盒数据目录写入或继承的 Git 签名失败；为测试进程设置独立的
`LODY_DATA_DIR` 并关闭签名后，重跑的 171 项测试全部通过。
`pnpm run docs check` 仍报告未初始化的独立 Kimi/Pi 子模块导致的六处已有链接错误，
本次修改的文档没有错误。
Playwright 还并排录制了基准版本与修改后的真实侧栏组件，使用相同合成目录和注入的 IPC 状态。
两轮快照缺失、恢复使旧版 iMac 标题移动 200 px；修改后的标题和会话行位置始终不变，位移为 0 px。
连接正常及重连期间的真实侧栏点击都打开了预期路由。
第二组 Playwright 对照保持身份不变，连续点击三个会话，两版都没有移动。
接着不点击、不改变路由、名称或已读状态，只让身份消失、恢复，只有旧版发生换位；
两版的导入按钮仍跟随实时身份显示。这与反馈视频中的两个可见信号一致。两轮页面都没有异常。
目录 hooks 和选中会话的已读更新由夹具提供。这项浏览器渲染器验收未覆盖实际 Electron 进程，
也无法证明用户原视频发生过哪些 CLI 状态。录制及其夹具保留在被忽略的本地验收产物中。
现有 desktop-log 套件还使用注入时钟验证写入文件的探测错误分类、失败里程碑、30 秒汇总边界、
恢复和计数重置、私有数据字段不落盘，以及诊断写入失败时仍能继续。九项测试全部通过。
Electron 套件的回环端口租约测试最初因沙盒限制报 `listen EPERM`；在沙盒外重跑的
214 项测试全部通过。desktop-log 套件在负偏移时区下也通过，日志文件查找使用本地日期 helper。

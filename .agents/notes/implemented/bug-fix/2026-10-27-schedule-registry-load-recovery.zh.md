# 定时任务注册表加载失败排查

Status: implemented
Translation: current

[English](2026-10-27-schedule-registry-load-recovery.md)

PR: https://github.com/LodyAI/Lody/pull/1963

## 摘要

定时任务列表此前把本地文档读取失败和远端首次同步失败都显示为同一句加载错误，清空可读任务且没有重试入口。工作区 hook 现在保留可读列表并提示同步异常，在 1、3、10 秒后最多自动重试三次。网络恢复事件和手动重试也可重新获取订阅。空的本地扫描等待首次同步确认；底层网络故障原因和安装包恢复行为仍未验证。

## 证据与范围

以下为修复前版本 `51669978e28995629a33e01338fe16796caa3db9` 的行为。
[`useScheduleRegistrySync`](../../../../packages/components/src/hooks/use-schedules.ts)
打开工作区的 `:sr` Flock 文档，订阅并发布本地扫描结果，然后加入房间、等待
`firstSyncedWithRemote`。任一步拒绝都会把快照替换为空列表和
`REGISTRY_UNAVAILABLE`，原始错误被丢弃。
[`ScheduleListView`](../../../../packages/components/src/components/schedules/schedule-list.tsx)
随后隐藏列表并显示通用加载错误。

当时 hook 挂在工作区外壳上；runtime 身份不变时，重新进入列表不会重新启动它。
后续 Flock 更新可以清除错误，但当时 hook 不会主动重试失败的打开或首次同步。
这些是代码可确认的行为，不是对具体网络原因的证明。

即使本地文档可读，远端首次同步拒绝仍会进入同一通用加载错误分支。
另一个副本读取成功不能证明出错窗口的数据新鲜度或传输错误原因。
测试使用合成任务和受控失败，不包含捕获日志或账号标识。

## 恢复行为与验证

- 使用现有客户端诊断记录失败阶段（打开、扫描、加入、首次同步）、房间标识和
  脱敏错误，不记录任务内容。
- 区分本地读取失败与远端同步失败。保留可读列表并明确提示同步状态；未同步的
  空扫描不能表示确定没有任务。保留[机器级调度决策](../../implemented/feature/2026-09-24-machine-owned-scheduled-tasks.zh.md)
  中的执行和写入准入检查。
- 提供三次定时重试和显式重试入口，每个工作区 hook 同时只保留一次资源获取。
  清理旧订阅，工作区切换后忽略旧结果。首次加入失败可能需要重新加入，单纯
  reconnect 未必足够。
- 多传输房间的等待使用现有[就绪绑定选择器](../../../../packages/components/src/lib/room-readiness.ts)。
  这是另一处代码兼容性问题，不能当成已观察到的网络错误原因。
- 测试验证本地非空列表读出后首次同步拒绝、冷启动打开失败后重试成功、未同步的空列表、
  资源获取未完成时切换工作区。使用显式信号和假时钟驱动失败及恢复，安装包另行验证。

工作区外壳拥有资源获取过程，列表消费者只通过 atom 请求重试。
远端失败只释放房间，再安排下一次加入。可读的本地文档及其 Flock 订阅在
重试耗尽后仍保持活跃，因此成功的本地暂停、删除和新建仍会更新列表。
受控复现确认，同时释放两类订阅会让重试耗尽后成功的本地修改无法更新列表。
初次本地扫描失败仍释放不可用的观察
订阅，并在重试时重新打开。首次同步成功清除警告；单独的本地变化既不会清除警告，
也不会把未运行的重试标成运行中。工作区替换或卸载取消定时器并忽略旧结果，
包括取消在旧生命周期结束后才加入成功的房间。执行和写入准入检查保持原样。
React hook 继续使用普通 React 代码，不引入 Effect 服务或改变 runtime 所有权。

```text
工作区外壳 -> 打开并扫描本地 -> 加入并等待选定传输的首次同步 -> 持续更新
远端失败 -> 保留本地观察并提示 -> 释放房间 -> 重试加入
切换工作区或卸载 -> 取消定时器与订阅；忽略旧结果
```

行为测试覆盖自动恢复、重试耗尽后的本地暂停/删除/新建及手动恢复、
本地扫描失败及恢复、网络恢复、冷启动空扫描、
切换工作区后旧打开/加入/同步完成，以及保留列表和重试控件。
Storybook 包含空列表失败、已有任务同步失败和重试中状态。
安装包行为仍需单独验证，本次不代表发布或部署。

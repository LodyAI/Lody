# 历史文本的线性时间改写

Status: implemented
Translation: current

[English](2026-10-20-history-text-linear-rewrite.md)

## 摘要

有用户反馈切换 tab 时桌面端卡顿。他们的守护进程日志显示 CLI 主线程多次被阻塞 63 秒到 224 秒，profile 中 90% 以上的时间花在 `diffHistoryContainer` 调用的 `LoroText.update` 上。这个方法在 wasm 里执行不设上限的 Myers diff：追加很快，但长文本在中间被改写时要花几分钟。它运行期间，渲染端等待的所有 RPC 都会停住，所以切 tab、新建会话、读取运行时状态都会卡住。现在历史写入保留公共前缀和后缀，只替换中间部分，耗时与文本长度成线性。代价是大段改写会存成一次删除加一次插入，而不是最小 diff。

## 证据

`LoroText.update` 的耗时（loro-crdt 1.16.3，Node 24，Linux）：

| 原文本      | 改动                | `update` |
| ----------- | ------------------- | -------- |
| 2.3 万字符  | 末尾追加            | 7 ms     |
| 2.3 万字符  | 删掉开头 10% 并追加 | 0.8 s    |
| 9.3 万字符  | 删掉开头 10% 并追加 | 11 s     |
| 9.3 万字符  | 换成不相关内容      | 112 s    |
| 23.7 万字符 | 删掉开头 10% 并追加 | 70 s     |
| 23.7 万字符 | 换成不相关内容      | 456 s    |

`diffList` 在没有可以锚定的保留对象时按下标配对列表条目。两个约 2.7 万字符的文本条目、前面插入一个短条目时，直接调用 `diffHistoryContainer` 耗时 13 秒，因为每段已存储的文本都在和一段不相关的新文本做 diff。`HistoryWriter` 会保留未变条目的对象引用，所以它自己的更新路径能正确锚定。具体是哪一次写入触发了用户的阻塞还没确认：需要用户日志中阻塞前后的条目，以及 profile 里的调用方。

## 决策

`history-materializer.ts` 中的 `writeText` 替换了三处 `LoroText.update` 调用。它按 UTF-16 码元比较，保留公共前缀和后缀，不会拆开代理对（Loro 会拒绝这种拆分）。比较的基准是已存储的文本，而不是调用方给出的快照。

- 追加和集中在一处的修改产生的 op 与原来相同。向空 Text 写入是一次插入，所以与 Mirror 存储形态的等价性保持不变。
- 分散在长文本各处的改写变成一次删除加一次插入。如果另一个 peer 同时编辑同一段文本的中间部分，合并结果会比 Myers 粗糙。这些字段是只由 CLI 写入的 agent 输出，预计不会出现并发编辑。

## 备选方案

- `update(text, { timeoutMs })` 超时后直接抛出 `Update timeout`，不会自动换用别的算法，调用方仍然需要这种整段替换作为兜底。
- `updateByLine` 快得多，但仍是按行的 Myers diff（9.3 万字符换成不相关内容需要 366 ms），增长仍快于线性。
- 改进 `diffList` 的对齐方式（例如按 `toolCallId`）可以避免配对不相干的条目，但无法限制真正大段改写的开销，所以留作后续工作。

## 验证

`tests/history-writer.test.ts` 验证：通过 `HistoryWriter` 把文本改写成不相关内容时，恰好产生一次删除和一次插入，并且另一个 peer 能收敛到相同内容。旧实现对同一改动产生 600 个 op。另一个测试依次执行前缀或后缀边界落在代理对内部的修改；去掉边界调整后 Loro 会抛错。shared 测试套件以及 CLI 的 ACP 和历史测试套件全部通过。切 tab 卡顿本身没有在 Electron 中端到端复现。

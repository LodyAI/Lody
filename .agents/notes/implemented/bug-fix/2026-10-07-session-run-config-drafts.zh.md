# 会话运行配置草稿在切换标签后保留

Status: implemented
Translation: current

[English](2026-10-07-session-run-config-drafts.md)

## 摘要

已有 Codex 会话中的 Fast 修改尚未发送时，切换标签再返回会丢失，因为修改只保存在
输入组件的局部状态中。现将已有会话的运行配置修改保存在按会话隔离的应用状态中，
明确开启和关闭都会保留，也不会影响其他标签。最终配置仍由输入纯派生，只有新的逻辑
用户轮次才能确认已采纳的修改。这是内存草稿，不承诺应用重启后恢复，也没有新增同步
配置权威。

## 决策与证据

原选择钩子的 `useState` 边界在组件卸载时丢失，切换目标时也会清空。
`preserveUnsentUserEdits` 只保护同一次挂载内的修改。
[运行配置说明](../../../docs/sessions-run-config.md) 中的 Role 选择已经使用按会话隔离的
应用状态，其对应配置项也需要相同生命周期。新的 Jotai 原子仅保存用户修改与来源边界；
入口和新会话草稿仍使用独立的组件实例原子。

有效配置仍遵循用户修改、运行时基线、用户轮次偏好、能力默认值的优先级，绝不将解析后的
配置写回。受保护的 effect 只提交已消费的修改及已知来源标识；事件写入先推进同一个边界，
因此较晚的 effect 不会抹掉新选择。新逻辑轮次只清除它已采纳的字段，下一份草稿中的不同
选择继续保留。记录已观察的来源沿革，可避免将队列删除、重排、旧历史补载误判为新输入。
文档加载尚未就绪时既不记录来源，也不消费修改。旧标签的回调始终写入原会话的原子。

这保留了[附件等待发送决策](2026-09-30-composer-pending-send-config.zh.md)中的逻辑轮次
规则：等待发送转为历史记录时，不得消费下一份草稿中数值相同的明确修改。缓存完整解析
配置会与运行时权威冲突，并可能重现选择反馈循环；将未发送修改写入共享会话文档则会
过早发布私人草稿。

## 验证与限制

现有选择回归套件覆盖复用组件及重新挂载时的 A/B/A 导航、明确关闭 Fast、双标签隔离、
未就绪的文档加载、已采纳与不同的草稿修改、已知来源回退与历史补载、等待发送转为历史，
以及旧标签回调。用例采用合成数据和同步 React 提交，不依赖等待时间。
在 `1117f153` 基线上，完整 components 套件的 554 个文件、4,824 项测试全部通过，
工作区类型检查、带类型信息的 lint、国际化、边界检查、格式化和文档检查也均通过。

被拒绝、注入的代理环境及 WebRTC 限制；代表性失败在未修改的 `1117f153` 上也可复现。

# 压缩 Roost 渲染端变更记录，保留完整恢复证据

Status: implemented
Translation: current

[English](2026-10-21-roost-renderer-receipt-encoding.md)

## 摘要

渲染端变更日志在每个已验证的 Native 区间中重复保存 JSON 字段名、十六进制
scope、UUID 和十进制游标。v2 编码将固定宽度字段保存为字节，保留全部记录
和完整身份。owner 的 checkpoint 协议、完整性检查和写事务不变。实验性 v1
会话会被明确拒绝，不迁移、不删除。

## 决策与边界

`roost-history-change-codec.ts` 负责纯编码。每条值包含版本字节、标志位、两个
完整 u64 游标、完整的 256 位 owner/stream scope，以及完整的 128 位随机 nonce。
可选的结构位置用八字节保存，限制在 JavaScript 能精确表达的整数范围内。
规范小写 UUID 的 ID 列表保存数量及每个 ID 的十六字节；其余列表在同一 v2
格式中使用 JSON，不折叠大小写、不做 Unicode 规范化、不截断身份。这也保留
现有 ID 契约接受的空字符串和孤立代理项。

切换 generation 时，`before` 可能大于 `through`。编码保留这种重置证据，
顺序和覆盖范围继续由读取逻辑校验。错误版本、未知标志位、截断或数量不符的
记录、非法 UTF-8/JSON 和不安全的结构位置会报错，不会被当成记录缺失。

`lody_renderer_history_changes_v2` 替代 v1。现有的逐 stream 格式检查在初始化、
恢复及写入前额外探测旧渲染端 namespace，只在检查成功后缓存，缓存寿命不超过
stream handle。没有 v1 解码器、转换或清理。已有 v1 记录的会话需要新建测试
会话，同一数据库的其他 stream 不受影响。升级前需要停止旧 CLI owner，不支持
旧、新 owner 同时写同一数据库。

[增量恢复契约](2026-10-16-roost-incremental-history.zh.md) 仍要求相同的 scope、
nonce、完整游标链与重置证据。anchor CAS、Native 游标写入保护和所有记录保持
不变。不增减网络往返、正文读取、记录清理、写入批次或持久性设置。这和
[Agent 幂等凭据](2026-10-21-roost-agent-receipt-encoding.zh.md) 是两项独立优化。

Effect feature/fix 评估：本次只涉及纯编码以及现有 Promise Native owner 中的
一次有界探测。迁移 owner 会扩展到尚未完成的 Session 生命周期依赖，不能改善
本次编码，因此生命周期路线图和所有权边界保持不变。

## 证据

使用候选 Native addon 的四个所属测试套件共通过 105 项测试，覆盖完整 UUID 与
任意字符串身份、全宽游标、损坏记录、并发 anchor CAS、129 个区间跨分页与重启
恢复、区间缺失、错误 scope/nonce、重置证据、游标写入拒绝，以及旧格式和混合
格式在写入前被拒绝且不删除数据。既有本地恢复测试也改用生产 owner 的 SHA-256
scope 形状。

手动测量在 Linux x64、两颗 vCPU、可见内存 7.5 GiB、Node 24.22.0 上进行，
**两边**使用同一个 release Native addon：`60f6b160cfc0ec70039460a9f19b3ca8e65b733e`。
该 addon 已包含独立的 projection 和未使用 outbox 优化，本次不重复计算这些
收益。Lody 基线为 `ce653a2199e9b3ccebb33aa66d35104444244f13`，已经包含 Agent
凭据压缩。每档负载先丢弃一组预热，再交替进行六组基线/候选配对；每个样本均
使用新进程、新数据库。测量代码与数据保留在仓库及 CI 外，不使用真实对话。

固定合成会话有一条 `request` 用户消息、一条 `response` 助手消息、四十个完成
的工具结果（`synthetic-result-${i};` 重复四十次），随后写入 224 或 1024 条
`increment-${i};🙂` 文本通知，每个批次一条。会话 ID 固定为
`00000000-0000-4000-8000-000000000001`。每个 checkpoint 都由实际的 Loro history
writer 写入相同逻辑状态，导出增量给 peer，并通过 `SqliteRepoStore` 保存。
重新导入全部 Loro 更新可重建相同最终状态；Native 重开和最后一条通知重放也
保留原历史。这是相同状态的存储对比，不是历史 reducer 的独立正确性判定器。

| 中位数指标 | 224，优化前 → 后 | 1024，优化前 → 后 |
| --- | ---: | ---: |
| 渲染端记录数量 | 226 → 226 | 1026 → 1026 |
| 渲染端记录 KV 字节数 | 46,591 → 19,443 | 212,254 → 88,243 |
| SQLite 增长 | 248 → 212 KiB | 792 → 652 KiB |
| 完整流式写入耗时 | 4448.8 → 4336.4 ms | 19470.4 → 19725.0 ms |
| 单次写入 p95 | 25.65 → 25.84 ms | 25.07 → 24.68 ms |
| 读取遗漏变更 p50 | 8.01 → 7.77 ms | 29.79 → 25.44 ms |
| 重开并完整读取 | 93.38 → 93.36 ms | 88.67 → 104.32 ms |

SQLite 增长按 `page_count × page_size` 减去空 Native 数据库计算，不含 WAL/SHM、
身份库和 Loro 控制数据。长负载范围为优化前 784–792 KiB、优化后 644–652 KiB。
对应的 Loro SQLite 增长为 76/200 KiB，保留**所有**增量；其累计导出增量为
57,946/139,240 字节，最终逻辑 JSON 为 40,506/54,930 字节。Loro 不承担同一套
签名更新、事件日志及应用凭据契约。

记录 KV 减少 58.3%/58.4%，SQLite 总增长减少 14.5%/17.7%。签名更新数量及字节数
保持为 227/65,110 和 1027/162,734，因此收益来自本地索引，不是 Streams 流量。
长负载混合进程的总写入时间增加 1.3%，耗时范围重叠；重开耗时和混合进程 RSS
有波动，另用不运行 Loro 对照负载的 Lody 进程检查该信号。这些合成结果不能替代
原真实会话测量，也不能证明 CLI RSS 下降。

在不运行 Loro 对照的 1024 通知负载中，丢弃一组预热后的四组交替配对得到：
完整写入 19,281.9 → 19,217.8 ms，写入窗口的进程 CPU 时间
20,373.8 → 20,427.4 ms，写入 p95 为 24.13 → 24.42 ms，遗漏变更读取 p50
为 29.51 → 27.68 ms。在该样本规模下，写入速度基本持平。普通重开样本范围
分别为 86.85–128.02 ms 和 86.56–131.14 ms，中位数为 88.90/111.93 ms，
因此另用受控、重复重开测量检查这一差异。

最终编码还按基线、候选、候选、基线的顺序运行四个新进程，每个进程在显式 GC
之后重开八次，丢弃第一次，每个版本在两个进程中共计十四次观察。两边使用相同
方式测量 Native 调用。重开中位数为 110.38 → 110.17 ms，范围分别为
105.98–146.10 / 102.15–162.69 ms；首次获得 stream 前的时间为 67.66/67.38 ms，
Native 调用累计时间为 24.23/24.12 ms。新增渲染端格式探测的中位数为 0.20 ms。
此次没有复现稳定的重开速度回退；同进程内的重复观察不是独立实验，也不能据此
宣称普遍的冷启动加速。

使用锁定的已发布依赖，全仓 `pnpm check`、`pnpm format` 和 `pnpm run docs check`
通过。最终校验还拒绝末尾带换行的截短 scope 哈希，合法生产哈希的字节表示不变；
该边界用例已在候选 Native addon 的本地写入套件中通过。不增加依赖、发包、部署
或 CI 计时负载。

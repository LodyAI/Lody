# 从只能靠重装恢复的界面中恢复

Status: implemented
Translation: current
PR: https://github.com/LodyAI/Lody/pull/1531

[English](2026-10-13-workspace-open-recovery.md)

## 摘要

一些用户（主要是 iOS 上很久没打开应用的用户）每次启动都停在“正在切换工作区”，直到重装才恢复；在应用里清除缓存也无效。
根因还没有定位，而大约二十个路由界面都可能无限等待，或失败后没有任何出路。所以修复是结构性的：每个阻塞路由的
等待在 30 秒后变成恢复页，每个路由失败界面都提供重试和同一个恢复页。任何删除都不会自动执行，因为本地副本可能
含有尚未同步的编辑。清除缓存现在会校验实际删除了什么并记录下来；在桌面端重试一次没删干净的清除时，会重启进入
新进程执行。完全重置在宿主支持时使用文件层面的删除，这正是重装所做的事。iOS 原生壳在本仓库之外实现了这一清除
（`window.__LODY_NATIVE_RESET__`）。以上都还没有在真实卡住的用户上验证。

## 问题

在 iOS 上重装应用会删除 WebView 的整个数据目录、退出登录，并且无论卡在哪个界面都有效。应用内的选项三点都做不到：

- **到不了。** 出路只在设置页和崩溃页上。路由的等待（登录、加载工作区列表、等待当前组织、打开工作区数据）
  可能一直转圈，两者都进不去。还有几个路由失败界面让移动端用户“刷新页面”。
- **不校验。** 启动时的清除把删除报错当作成功，并且无论结果都会消费标记。如果存储后端打不开某个数据库（也就
  删不掉它），清除什么都没做，看起来却像执行过。桌面端的清除在渲染进程重新加载后执行，仍处在存储后端已经出错
  的同一个进程里。
- **不够彻底。** 所有应用内的清除都通过 Web 存储接口进行，只有宿主能删除文件。

另外还发现了两个具体的死路：

- **工作区数据 scope。** 首次 doc-metadata 扫描被拒绝（`doc_meta_scan_failed`），或 runtime 创建被拒绝，
  在整个页面生命周期内都会卡住；runtime 那种情况甚至显示成普通的 `runtime_missing` 等待。
- **工作区列表。** 失败 5 次（约 10 秒）后，`useOrganization` 在页面余下的生命周期里不再重试。清除缓存会删除
  slug→id 映射，而应用正是靠它才能在没有列表时打开工作区。于是清除缓存后，只要启动时的头几次请求失败，就会一直
  卡住——这与“清缓存也没用”相符。

## 决定

- **每个路由等待都有超时进入恢复页。** 三个路由文件都渲染 `BlockingWaitPlaceholder`，并用 `gate` 标明在等什么，
  不再直接使用 `LoadingPlaceholder` 或 `BootShell`。30 秒后显示恢复页：
  1. 重新加载；
  2. 清除本地缓存（与设置页相同的确认流程）；
  3. 复制诊断信息：gate、scope 卡住原因、错误名称、连接状态、启动前闲置时长、上次自动清除和启动时清除、构建、
     渲染轨迹；
  4. 清除全部本地数据并退出登录。

  超时是“等待”本身的属性，不是诊断，所以以后新增的门和尚未发现的原因也有出路。

- **每个路由失败都有出路。** `RouteMessage` 必须提供 `gate`。失败界面总会显示重试（调用方没有提供时就是重新加载）
  和“更多恢复方式”，后者打开同一个恢复页。`gate: null` 表示不是失败（例如移动端工作区数量上限），保持原有行为。
  把这个属性设为必填后，又在工作区路由之外发现了四个失败界面。
- **让 runtime 创建失败可见。** `RuntimeProvider` 记录 `workspaceRuntimeInitFailureAtom`
  （`{ workspaceSlug, errorType }`），scope 因此报告 `runtime_init_failed`。`describeErrorType` 只保留错误名称；
  它从任意对象上读取 `name`，因为并非每个引擎里的 `DOMException` 都是 `Error`。
- **终态失败立即显示恢复页，不会自动清除。** 遇到 `runtime_init_failed` 或 `doc_meta_scan_failed` 时，占位页
  立即变成恢复页，第一个选项是重新加载。它不删除任何东西：仓库副本可能含有尚未同步的编辑，而看起来是终态的失败
  （例如一次暂时的读取错误）可能重新加载后就好了。只有存储错误才会说本地数据可能已损坏：扫描失败，或 runtime
  以 IndexedDB 或 `RepoStorageError` 名称失败。其他 runtime 失败显示通用说明。
- **清除缓存只重新加载一个窗口，重启另有用途。** `restartIntoCacheClear` 设置启动标记并重新加载窗口，与设置页
  一直以来的做法相同。重启桌面端会退出内置 CLI，并停止正在运行的智能体，所以恢复页只在一种情况下请求重启：重试
  一次当天没删干净的清除。这种情况说明存储后端在当前进程中已经出错。重启会写入 `lody app reset-cache` 使用的
  一次性请求文件，并通过正常的退出屏障退出。`app.relaunch()` 只在 `will-quit` 时调用。如果退出被回答“留下”，
  或 CLI 清理失败，结果是 `cancelled`：请求文件会被撤回，调用方报告没有开始执行。
- **校验清除结果，重试交给用户决定。** 启动时的清除会记录每个删除的结果、重新枚举数据库，并把 `RuntimeProvider`
  额外传入的数据库的失败也计算在内。结果写入 `lody:lastLocalClear`，该记录不在删除名单里，完全清除后会重新写入。
  它不会自行重跑：重跑会再删一遍所有东西，完全重置后用户重新登录，又会被再次登出。当天有过没删干净的清除时，
  恢复页会提示；更早的记录会被忽略。
- **完全重置优先交给宿主。** `startHardReset` 撤销服务端会话后，先尝试由宿主在文件层面删除：
  - **桌面端：** 重启进入 CLI 已在使用的原生 `hard` 清除。
  - **移动端原生壳：** 调用 `window.__LODY_NATIVE_RESET__.resetAllData()`。

  只有在没有宿主清除或宿主拒绝时，才回退到 Web 层面的清除。这是同一步骤的更强版本，代价相同（退出登录、
  本地数据全部删除），不作为单独的第四个按钮。桌面端退出被回答“留下”时，什么都不删除。

- **工作区列表持续重试。** 重试用尽后，在 `online`、回到前台时，以及页面可见时每 30 秒再尝试一次。
- **说明是哪个请求失败。** 登录状态检查持续失败（离线、5xx、超时）时不会被当作登出，所以如果不加说明，页面会把
  服务器的问题说成本地数据的问题。登录检查、工作区列表、当前工作区和切换工作区这几个请求会记录最近一次错误。
  只要还有请求在失败，页面就会用通俗的话说明是哪个请求、带上 HTTP 状态码，并说明不是设备的问题；诊断信息和卡住
  上报里也会带上它。Better Auth 的 `get-session` 在会话缺失或过期时返回 `null`，在后端失败时（包括长期未用的会话
  需要的那次刷新写入）返回 HTTP 500 `FAILED_TO_GET_SESSION`；后端会把所有非 401 的认证错误记录为
  `better-auth error response`，可以据此确认这种情况是否真的发生。
- **上报写明 gate。** 同一个占位页可能先后代表几道门，所以它的 30 秒计时覆盖整个等待过程。每个占位页在出现
  恢复页时只发送一次 `workspace/boot_wait_stuck`，包含 gate、卡住原因、闲置时长和应用版本；
  闲置时长用于检验“很久没用”这一规律。启动时清除之后发送 `workspace/recovery_outcome`：工作区打开了是 `ready`，
  又出现恢复页是 `stuck_again`。据此可以判断清除缓存是否足够，还是需要宿主清除。
- **连接卡住提示条打开同一个恢复页。** 已知 id 的工作区即使 runtime 一直没有出现，也会渲染普通布局，
  屏幕上没有路由等待，唯一的出口是 45 秒 `loading` 提示条，而它只提供清除缓存。清除缓存会保留登录凭证，
  重装则会替换它。提示条现在打开恢复页，并以 gate `control_connection_loading` 上报一次
  `workspace/boot_wait_stuck`；连接恢复后页面自动关闭。

## 未采用的方案

- **终态时每天自动清除一次缓存。** 这是本改动的第一个版本。它会在用户没有同意的情况下删除尚未同步的本地编辑，
  而触发它的错误也许重新加载就能解决。与之配套的“把没删干净的清除留到之后几次启动重跑”，会在下次登录后再次
  执行完全重置。两者都在评审中移除。

- **逐个修复每道门。** 原因仍然未知，逐个修复会让下一道未知的门继续卡住。每道门仍会上报名称，供之后修复。
- **单独的第四个“原生重置”按钮，只在第三级无效后出现。** 宿主清除与 Web 清除代价相同且更彻底，所以 Web 清除
  只作为它的回退。
- **把 slug→id 映射移出删除名单。** 这样清除缓存后仍能离线启动。但删除名单是针对过期连接状态的明文规则，而持续
  重试的工作区列表已经不需要这样做。
- **扫描超时后自动清除。** 会在慢设备上清掉健康的缓存，而且被阻塞的打开操作本来也清除不了。
- **等待存储危机熔断（#438）。** 它说明配额耗尽和连接失效，并要求重启。它仍未合并，既不覆盖数据损坏，也不覆盖
  与存储无关的门。

## 已排查的原因：仓库存储升级

受影响的用户都是很久没用之后遇到卡死。最后一次打开早于 0.20.3（2026-09-27）的用户仍持有 schema v3 的仓库
数据库，下次启动会执行 v3→v4 的 IndexedDB 升级。

在 fake-indexeddb 下的实验排除了这一点：

- **写入：** 每个发布过的 loro-repo 版本（0.19.1、0.20.0、0.20.3、0.21.0–0.21.2、0.22.0）搭配当时的
  `loro-crdt` 和 Flock 版本，写入带修改和删除的会话与机器元数据，以及一个文档和一个 Flock 文档。其中一部分数据库
  正常关闭，另一部分不经过仓库关闭流程。
- **读取：** 0.22.0 用 runtime 的参数打开每个数据库，并运行真实的 `docMetaSubscriptionAtom` 扫描。
- **结果：** 所有数据库都升级到 v4 并进入就绪，值都符合预期，第二次启动也一样。0.19.1 写入的 3000 个会话约
  0.6 秒完成打开和扫描。
- **反向对照：** 损坏元数据快照后，`LoroRepo.create` 抛出 `Failed to hydrate metadata snapshot`，说明这套实验
  能发现不兼容。

局限：WebKit 的 IndexedDB 不同于 fake-indexeddb，也没有测从 Streams 导入的元数据。本地不兼容同样会被一次
有效的清除移除，这也是校验清除结果和宿主清除之所以重要的原因之一。

## 验证

- `tests/error-boundary-fallback.test.tsx`：重置 mock 遵循实际的 `Promise<boolean>` 契约；
  重置开始后确认框保持进行中，取消重置后关闭确认框并允许再次尝试。此前 CI 的所有断言虽然通过，
  但旧 mock 返回 `undefined`，调用 `.then()` 引发未捕获异常，导致整个测试分组失败。

- `tests/blocking-wait-placeholder.test.tsx`：
  - 终态失败立即显示恢复页，并且不设置任何清除；
  - 只有存储错误才显示“数据可能已损坏”的说明；
  - 工作区等待和非工作区等待都恰好在延迟到达时进入恢复页；
  - 跨越几道门的等待只上报一次；
  - 清除不完整的提示（桌面端带重启提醒），以及一天后不再提示；
  - 真实的启动时清除之后上报 `stuck_again`；
  - 诊断信息只在显示时才构建；
  - 有 gate 和无 gate 的 `RouteMessage`。
- `tests/clear-local-cache.test.ts`：
  - 清除缓存默认重新加载，只有明确请求时才重启；
  - 被取消的重启不设置任何清除；
  - 删除失败会被记录且不会重跑；
  - 报告成功但仍存在的数据库算作失败；
  - 完全清除失败时保留记录，但不再次设置；
  - 记录在一天后过期；
  - 原生桥接和桌面重启取代 Web 清除，回答“留下”时什么都不删除，桥接拒绝时回退到 Web 清除。
- `apps/electron` 的 `desktop-exclusion.test.mjs`：退出屏障在回答“留下”和清理失败时报告取消，正常退出时不报告。
- `tests/useOrganization.test.tsx`：重试用尽后，网络恢复时以及 30 秒重试时都能加载列表；页面隐藏时不轮询，
  一旦重新显示就立即重试。去掉 effect 中对应的部分后，相应测试都会失败。
- `tests/runtime-provider.test.tsx` 和 `tests/workspace-data-scope.test.ts`：`runtime_init_failed` 会被记录、
  在下次尝试时清空，并且只作用于目标 slug。
- 恢复页和 `RouteMessage` 已在 Storybook 中检查浅色、深色和 zh_CN。Electron 主进程测试和两个包的类型检查都通过。
- **未验证：**
  - 真实卡住的设备；
  - 桌面端重启清除的完整端到端流程；
  - iOS 宿主清除在真机上的效果。移动端原生壳在本仓库之外实现了 `window.__LODY_NATIVE_RESET__`；没有它的旧版原生壳会
    回退到 Web 清除，而 Web 清除删不掉存储后端拒绝打开的文件。
- **后续：** 等上报能说明卡在哪些门之后，修复它们的原因，例如 WebKit 上 v3→v4 升级本身的问题。

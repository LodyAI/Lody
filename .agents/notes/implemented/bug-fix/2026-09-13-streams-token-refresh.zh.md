# 隔离并合并 Streams token 刷新

Status: implemented
Translation: current

[English](2026-09-13-streams-token-refresh.md)

## 摘要

原先未授权回调会丢弃正在进行的刷新，导致多个 stream 放大 token 请求量。
Provider 现在共享刷新，并使用 SDK 提供的实际被拒绝 token，避免使替代 token 失效。
凭证变化同时隔离网络结果和异步缓存发布。协调只在 provider 内进行，托管签发端仍负责
授权与缓存隔离。

## 决策与证据

[草案规范](../../../../specs/streams-token-refresh.zh.md)定义契约。当前 Streams SDK
提供 `previousToken`，无需基于时间的猜测或重写传输层。没有引入全局 provider 池，
因为其身份和生命周期边界超出现有 provider。

持久缓存命名空间加入端点，密文仍绑定签发凭证。包括内存命中在内，无法解析当前登录时
拒绝返回 token。异步校验结束后、发布结果前必须立即同步检查代次：登录切换可能发生
在这两个微任务之间。

现有授权测试覆盖共享回调并发、迟到拒绝、凭证切换、旧请求完成、微任务发布竞争以及
端点和工作区隔离。托管缓存的实现和部署不属于公开仓库；可选的拒绝 token 字段向后兼容。

## 后续：拒绝信号必须穿过每一跳

对抗性复审发现该信号仍有两处丢失，现已修复，并有在缺少修复时会失败的测试覆盖。

eager-sync Worker 桥接把传输层的授权上下文压缩成只剩 `reason`，运行时又在每次调用时
新建 `createAuthCallback()`。既没有 `previousToken`，也没有最后 token 记忆，provider
无法把这次拒绝与缓存匹配，于是原样返回被拒绝的 JWT；Worker 的房间只能等前台传输恰好
刷新，或等 token 自然过期才能恢复。现在拒绝原因与被拒 token 跨越 Worker 协议，运行时按 provider
持有一个回调，并在丢弃 provider 的每个位置一并丢弃。

合并刷新在时间维度上造成同样的后果：拒绝到达时已在飞行的刷新，其请求体不含
`rejectedToken`，成功后却发布结果并清除标记。返回缓存版本的签发端因此重新装回被拒绝的
JWT，信号也永远到不了服务端。现在刷新会比较自己实际发送的值与当前标记，最多再发一次
携带拒绝的请求——该请求在同一个 promise 内，因此二十路回调扇出仍只多一次往返——并且在
JWT 仍处于被拒绝状态时既不清除标记也不写入持久缓存。

第二轮对抗性复审发现持久化写入仍未针对该标记设防。是否写入的判断发生在若干次异步
WebCrypto 调用之前，而紧邻 `setItem` 的同步闸门只重新检查代次——`reset('unauthorized')`
恰恰刻意不改变代次。落在这个窗口内的 401 会先清空存储，随后待完成的写入又把被拒绝的
JWT 写了回去，下一个进程便会在没有任何标记可供抑制的情况下加载它。现在该闸门也会重新
读取标记。标记只有一个槽位，因此在两个 token 之间循环的签发端仍可能重新持久化较早那个
被拒绝的 token；该情况会在下一次 401 时自愈，不值得为此引入无上限的逐 token 状态。

凭证隔离刻意保持原样。把轮换后的凭证当作身份可能未变，需要 provider 并不具备的身份信息，
因此轮换仍按登录变更重置：丢弃仍然有效的 Streams token，并让在飞请求以可重试错误失败。
这一代价是接受的，而不是用更弱的围栏去交换。

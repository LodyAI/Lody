# Roost 状态与批处理回执中的消息副本

Status: implemented
Type: bug-fix
Translation: current
Date: 2026-10-20

[English](2026-10-20-roost-message-storage-copies.md)

## 摘要

封存后的消息修正此前会把整条消息复制进状态和 SDK 命令回执。现在状态只记录相对指定已封存 primary 的操作，执行机器使用 Roost 的本地批处理恢复日志。含 432 KiB 不变正文、修正 32 次的合成用例，其保留更新由 889,477 字节降为 4,113 字节，同时保留 primary 签名、完整逻辑读取、旧状态读取和幂等恢复。消费者现在通过 #1735 的依赖更新使用正式 Roost 0.2.0，不迁移或重置更早的 SQLite 容器。

## 决策与范围

- 状态只记录变化的字段、文本及数组成员，绑定 primary Turn ID，读取时重建完整应用消息。在兼容容器内，已有整条消息状态继续可读，在下次正常修改时转为差量；不重写或裁剪已封存记录及保留更新。不增加 SQLite 容器迁移。写入差量后重开数据库需要当前或更新的适配器，RPC 读取仍返回完整逻辑消息。投影复用已解码的 primary，增量生成只转换操作偏移，不再次序列化累计文本或不变正文。
- SDK 在同一事务中准备本地命令计划与精简 pending 回执，再原子提交正文操作、发布信息、最终封存与计划退役。CLI 拥有整个数据库；Turn 导出同步已提交历史，迁移未完成的本地工作须携带包含恢复日志的完整数据库。其他宿主仍可使用 SDK 原有的可复制恢复默认模式。
- 本决策替换此前[写放大修复](2026-10-16-roost-storage-write-amplification.zh.md)的部分处理，不改变带条件校验的原生流式写入、不可变人类输入和分支事务。
- 通过 [#1735](https://github.com/LodyAI/Lody/pull/1735) 的依赖更新使用统一发布的 Roost 0.2.0，再合并 #1737。Native 0.2.0 要求 SQLite container v4。本改动不部署、不迁移或重置数据库、不清理历史、不截断 WAL、不合并 PR、不发包。

## 验收与故障边界

测试通过生产 SQLite 路径验证封存、封存后修正、后续流式输出、权限投影、关闭重开及原生回复丢失。大段不变文本不得出现在每条 state 更新和批处理回执中，测量保留更新字节而非 WAL 文件长度。验证 Unicode 偏移、字段删除、嵌套数组和错误基准/路径。错误状态继续使该历史读取报错，不切换后端、不重试写入。恢复日志的准备和应用故障由 SDK 处理，Lody 不另建恢复循环。

## 验证

消费者实现为 [Lody #1737](https://github.com/LodyAI/Lody/pull/1737)，SDK 实现为 [Roost #16](https://github.com/loro-dev/roost/pull/16)。分支已基于 [#1735](https://github.com/LodyAI/Lody/pull/1735) rebase，使用正式 SDK 与 Native 0.2.0，锁文件精确固定版本，没有本地覆盖。此前 SDK 0.1.3 的 `TS2554` 发布阻塞已通过依赖更新解决。

- 两个所属 CLI 测试文件在正式 Native SQLite v4 上 **82 项通过**。覆盖旧整条消息状态重开及转换、首次状态已提交但投影前丢失回复、后续输出、权限、分支和输入合同、Unicode、字段删除、错误基准/路径及 JSON 自有键。
- 此前的配对合成运行对照 Lody `7d6695c` + SDK 0.1.3，与本改动 + 拟发布 SDK。两边在封存 442,368 字节不变正文并修正 32 次后，均保留 **37 条更新**。更新 value 由 **889,477 降至 4,113 字节（99.54%）**，最大单条由 **443,344 降至 488 字节**。此口径不含初始 primary、outbox 副本、索引、WAL 和流传输封装。两边均保留旧帧、primary 不可变、逻辑内容及丢失回复后的重开。当前回归限制增长上界，不锁定协议精确字节数。
- 使用正式包的完整 `pnpm check` 通过，包含所有包类型检查、普通类型感知 lint、Effect lint、仓库测试、i18n 和边界检查。CLI 全量 **4,435 项通过、4 项原有跳过**。全仓格式及文档检查通过，文档无错误。
- 公开 CLI 在 **2 GiB 堆上限**内构建并通过发布包运行时及 Worker 探针。桌面 CLI staging 成功；真实 Electron 运行时通过 staged Native Worker 写入、校验并重新打开带签名的 SQLite 历史。四项 staging 测试覆盖六个平台的选择，其他平台用合成绑定，本机执行安装的真实绑定。这不代表本地 GUI E2E 或其他平台二进制的运行验收；正式 PR CI 已重跑。

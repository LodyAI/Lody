# 让云端同步重连退过 Convex 客户端的 16 秒封顶

Status: implemented
Translation: current

[English](2026-09-16-cloud-sync-reconnect-backoff.md)

## 摘要

一次持续两小时的代理/网络故障让守护进程发起了约 450 次云端同步 WebSocket 连接，
从第一分钟到最后一分钟都保持每 10 分钟约 40 次，原因是 Convex 客户端的重连退避把
封顶写死在 16 秒（±50% 抖动 → 8-24 秒），再久也不会继续增长。该客户端没有暴露这
些常量的开关，但接受 `webSocketConstructor`，因此新增的闸门（`cloud-sync-reconnect.ts`）
交给它一个会推迟真实连接的 socket：前六次失败不加任何延迟，之后从 15 秒翻倍到
5 分钟封顶，保留 ±20% 抖动。之所以敢退到分钟级，是因为封顶不是唯一的回来方式：
Streams 数据面恢复健康这一守护进程内既有的、未节流的"已上线"上升沿会立刻释放正在
等待的连接，并限制为每分钟最多强制一次，避免抖动的传输变成新的风暴。主要遗留限制
是：没有接入 Streams 传输的守护进程拿不到上线信号，只能依赖 5 分钟封顶。

## 问题与证据

`~/.lody/logs/2026-09-16.log.1`，04:50-06:50 UTC：

```
$ grep -c "Creating WebSocket" 2026-09-16.log.1
450
# 每 10 分钟分桶：15, 34, 38, 41, 39, 36, 37, 40, 40, 41, 40, 40, 4
# 相邻间隔：n=444 最小 0.76s 最大 23.99s 中位 15.18s，在 8-24s 间近似均匀
```

窗口之外同一行日志大约每小时出现一次，说明稳态没有问题。8-24 秒这个分布正是
`convex/browser/sync/web_socket_manager` 的指纹：`defaultInitialBackoff = 1s`、
`maxBackoff = 16e3`、`jitter = actualBackoff * (Math.random() - 0.5)`，而 `retries`
只有在收到"已同步过上次重连"的消息时才归零。socket 本身是 CLI 那个带代理的
`ProxiedWebSocket`（由 `lib/loro/doc.ts` 装到全局），所以尽管这条连接是 Convex 控制面
（`wss://…/api/1.33.0/sync`）而不是 Loro Streams，日志前缀仍是 `[loro:websocket]`。

同一时间窗、同一根因、不同模块：`[pr-poller] Initial meta sync not confirmed … within
60s; retrying in 60s` 重复了 345 次，PR 轮询整整两小时没能初始化。

## 决定了什么

**改在哪里。** `ConvexClient` 的退避字段是内部管理器的实例属性而非选项，要改就得伸手
去碰 `webSocketManager`。`webSocketConstructor` 才是受支持的接缝，在那里调节节奏是与
客户端自身的循环叠加而不是取代它：短暂抖动仍按客户端较快的基础延迟恢复，只有持续
失败才会走到新的封顶。

**曲线取值。** 前六次失败（约等于客户端自身曲线的 45 秒）不加延迟；此后从 15 秒翻倍
到 300 秒，抖动比例 ±20%，与 `computeLoroReconnectDelayMs` 保持一致。5 分钟封顶把这次
故障从约 450 次压到约 30 次，同时把"完全没有上线信号"的最坏情况限制在浪费一个 5 分钟
窗口。更短的封顶会让尝试次数仍停留在几百量级；更长则收益很小，因为剩下的代价主要是
那一个窗口，而不是尝试次数。

**不只是安静，还要能回来。** 这个改动带来的风险就是恢复变慢，因此 `notifyOnline`
会立刻释放正在等待的连接；`lody-fleet.ts` 把 `documentManager.onStreamsOnline` 接了
进去，正是那条已经用于释放搁置 Flock 工作的廉价上升沿。下限按**强制释放之间**计算，
而不是按尝试之间：早先的版本按任意尝试计时，会在真正的恢复信号距离触发等待的那次失败
不足一分钟时把它默默拒掉。信号刻意不清空失败计数——如果这次强制尝试也失败，退避会从
原处继续，而不是从基础延迟重来。

**信号会被锁存，不会白白花掉**（评审后的修正，见
[PR #757](https://github.com/LodyAI/Lody/pull/757)）。大多数信号到达时并没有东西可以
释放。最初落地的版本在这种情况下仍然消耗了节流令牌并清空了等待，这会分成两种结果：如果
Convex 客户端只是睡在自己的退避里，清空等待是有效的——它下一个 socket 会立即连接；但如果
当时已有一次尝试在途，就什么也没发生，而这次尝试失败后又会在被清空的位置装上一个封顶级
的新等待。此后 Streams 保持健康，不会再有第二个上升沿，于是恢复最多被丢掉五分钟——正好
落在本文声称要覆盖的那个风险上。因此，当下无法生效的信号会被锁存在 `onlineSignal` 里，
直到下一次连接请求；这也让下限变得诚实：只有在信号真的释放了一次连接时才计费，被下限挡
下的信号保持锁存而不是消失。任何真实尝试都会清掉锁存——已经跑过的尝试就是对该信号的回答
——所以锁存永远不会累积成可以重置风暴的口子。

**计数规则。** 连接必须稳定保持 5 秒才重置计数，这正是 `loro/connection-recovery.ts`
已有的防抖规则；窗口内就断掉的连接反而计入失败。任何时刻最多只有一个被推迟的连接：
Convex 客户端会在 60 秒服务端静默超时后**不调用 close** 就丢弃旧 socket 再建新的，若不
让新的顶掉旧的，这些被丢弃的推迟连接会在同一个截止时刻一起触发、形成突发。被顶掉的
socket 保持沉默；而对处于等待中的 socket 调用 `close()`（包括关机路径，那里 `dispose()`
先于 `subscriptionClient.close()` 执行）会补发客户端正在等待的 close 事件。

## 考虑过的其他方案

- **直接改 `client.webSocketManager` 的 `maxBackoff`。** 只要一行，但依赖的是已发布依赖包
  内部未导出的实例属性——`convex` 是 `apps/cli` 声明的普通 npm 依赖，通过 `convex/browser`
  使用，仓库里没有它的源码副本——升级后会悄无声息地失效，而失效形态就是重连风暴。
- **由闸门自己探测网络**（周期性向云端发 HTTP），而不是消费信号。它只是把 WebSocket
  尝试换成同样频率的 HTTP 尝试，证明力还更弱：Streams 的上升沿已经意味着真实流量成功。
- **把 CLI 每一次成功的 HTTP 响应**（`utils/http-transport.ts`）当作上线信号。这是最通用
  的信号，也能覆盖没有 Streams 传输的守护进程，但为了一个已被封顶兜住的情况，要在进程
  内每个请求上挂观察者。暂缓，不是否决。

## 暂缓：同一次故障中的上层重试

PR 轮询的首次同步等待是每个工作区固定 60 秒等待加固定 60 秒重试，所以两小时故障换来
345 行日志和零进展。它本身没有错，只是不知情：它按自己的时钟重试，而它等待的传输其实
知道自己离线。更贴合本仓库的形态是 `task-automation-workspace.ts` 与
`review-automation-workspace.ts` 已经在用的那种——把工作搁置、自己不装定时器、在
`onStreamsOnline` 时释放，后面再配一个较长的兜底间隔。该改动属于 `pr-poller/` 及其自己的
Spec（`specs/pr-status-reconciler.md`），本 PR 刻意不做；这是建议，不是决定。

## 验证与限制

`apps/cli/src/lib/cloud-sync-reconnect.test.ts` 在假定时器下按 Convex 客户端的方式驱动
闸门（同一时刻只有一个 socket，上一个关闭后才建下一个，连接在到达网络一秒后报告失败）：
模拟的两小时故障总尝试数低于 45 次且宽限期之后每个间隔都超过一分钟；等待途中的上线信号
在同一个 tick 内发起连接；落在在途尝试期间的信号，会在该尝试失败后按客户端自身的退避重连
（而不是等满封顶）；落在客户端重试睡眠期间的信号仍然立即连接；对着一个不断重连的客户端
每秒抖动一次、持续五分钟，最多只产生 6 次尝试；存活 1 秒的连接计入失败而存活 5 秒的连接
清零退避；被顶掉的推迟连接永远不会触网；`close()` 与 `dispose()` 都能了结一个处于等待中
的 socket。

每个机制都做了消融以确认测试能看见它：去掉锁存会让"在途信号"用例失败；让 `requestConnect`
不再消费锁存会让两个信号用例都失败；把强制重连下限设为 0 会让抖动用例失败。

未验证：没有针对真实故障的端到端运行，Convex 客户端自身的循环只通过测试替身所编码的模型
被间接覆盖。若上游改变构造 socket 的时机，先过期的会是这个替身，而不是生产代码。

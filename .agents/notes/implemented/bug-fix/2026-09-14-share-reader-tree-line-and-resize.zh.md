# 接上分享阅读页的树线，让高亮离开连接线，并允许调整树宽

Status: implemented
Translation: current

[English](2026-09-14-share-reader-tree-line-and-resize.md)

## 摘要

匿名分享阅读页的对话树复用了应用的行首槽位，却没有复用该槽位连接线所依据的行盒，
因此每个嵌套分组都渲染成一行一段的短划线——实测每个行边界有 5.57px 的缺口；选中行
的底色又横跨连接线所在的沟槽，在它穿过的地方第二次把线切断。现在行改用槽位的行盒
（30px 的行加列表的 1px `gap-px`），选中与悬停只绘制标题盒，深浅两种主题下缺口都
收敛为 0px，标记也不再压住线。侧边栏同时新增 `separator` 拖拽手柄：指针或方向键可
在 180px 到 480px 之间调整，并进一步收紧以保证正文至少保留 320px。连接线 ±8/9px 的
偏移现在被写成对调用方行盒的约定，因为类型系统拦不住下一个复用者重犯同样的错误。

## 决策

### 连接线编码的是"行"，不是"槽位"

`session-row-leading-slot.tsx` 在 14px 的槽位里绘制竖线，但它的长度是按槽位外的行
来定的：`-top-2` 与 `-bottom-[9px]` 向上 8px、向下 9px，正好覆盖一整行 30px 的侧边栏
行（1px 边框、`py-1`、20px 的标题行高），再加上应用列表在行之间放的 1px `gap-px`。
在这组数字下，一行的竖线恰好结束在下一行竖线开始的位置，一组被打开的 Session 才读
起来是一条连续的线。

分享阅读页复用了槽位，却自造了行：`text-[13px]` 的标题外包 `px-2 py-2`，列表没有
gap。这样的行约 37px 高，竖线漂在行中间，每个边界都露出缺口。在 Chromium 里把旧行盒
还原到实时页面上测得：上一段竖线的底边到下一段竖线的顶边相差 5.57px。树看起来像一
列互不相干的短横线，而不是一棵树。

修复方式不是新增几何量——给阅读页另写一套偏移，正是本包已经禁止的"第二套连接线实现"。
行改为采用槽位所依据的盒：`flex flex-col gap-px` 包住若干行，行内标题按钮带 `border`、
`py-1` 与 `text-sm`。现在浅色与深色下实测缺口都是 `0`，且在手柄允许的任意宽度下成立。

由于这些数字是约定而非细节，它们现在被写在复用者会遇到的地方：两个常量上的注释，以及
[侧边栏树文档](../../../docs/components-sidebar-session-tree.md)里的一节。

### 选中行不应盖住不属于它的线

阅读页原来用 `bg-foreground/10` 给整行（含沟槽）上色。竖线与拐角会穿过并不属于它们的
行的沟槽——连接两个子项的线正是从它们之间那一行穿过去的——所以整行宽的色块会在线的中
段压上一个带色的盒子，在原本的断裂之上再添一道。

现在选中与悬停只绘制标题按钮：行首槽位是它的兄弟节点，位于色块之外。在默认宽度下实测，
被标记行的背景从 x=34 开始，而拐角在 x=28 结束，标记与线不再有任何重叠。应用侧边栏仍然
给整行上色，这是对的——它的沟槽本来就在行自身的内边距盒内，把高亮内缩反而会破坏其
`AGENTS.md` 要求的平铺对齐。

这同时顺带修正了标记的高度：旧色块因为标题带 `py-2` 而有 37px 高，现在它就是一行。

### 树可以调整宽度，上限由正文决定

224px 的树会把多数标题截断（"Garbage collecti…"），想看全的读者却只有折叠开关可用。
树保留了该开关，并新增 `role="separator"` 手柄：跨在边框上的 12px 抓取区，可见部分是
2px 的细线；它绝对定位，因此两栏各自保留宽度，手柄本身不占布局空间。

范围是 180–480px，并且只要能量到布局，上限就收紧为 `容器宽度 - 320px`，这样在窄窗口
里拖动会停在正文仍可阅读的位置，而不是停在静态上限。窗口尺寸变化时会重新测量同一个上限
——否则先把树拉宽、再把浏览器缩窄的读者，就会留下一棵挤垮正文的树——手柄的
`aria-valuemax` 报告的也是它。Chromium 中验证：1280px 视口下拖到 x=1200 停在 480px；
700px 视口下同样的拖动停在 380px，正文正好剩 320px；420px 的树在窗口缩到 700px 时收到
380px。量不到尺寸时（jsdom、首次渲染）回退到静态上限，而不是把范围塌缩成最小值，这也
正是这段行为可测的原因。

方向键每次步进 16px，因此不用指针也能改变宽度。拖动期间去掉宽度过渡——每次指针移动都
做动画会让边缘拖在光标后面——拖完再恢复，所以折叠开关依然是滑动的（实测归零途中量到
75.47px），并且重新展开时回到读者选择的宽度而不是默认值。

宽度是组件状态，刻意不做持久化：阅读页被禁止把分享数据写入存储；布局偏好虽然不是分享
数据，但访客通常只读一次某个分享，为此增加一个存储键，要守的规则多、换来的收益少。

## 备选方案

保留整行高亮、把连接线提到高亮之上被否决：那样每个选中行仍会在线上留下一条带色横带
——诉求是高亮根本不要碰到线，而不仅是层级顺序——半透明色块穿过时仍会改变线的底色。

新增类似 `treeTrunkClassName` 的属性、让阅读页保留更高的行，同样被否决，理由与不许
复刻连接线一致：两个调用方各有一套几何，正是这个缺陷复发的方式。大家共用一个行盒，
是更便宜的约定。

把宽度持久化到 `localStorage`（与 `lody-language` 并列）考虑过并按上文延后。

## 证据与限制

`tests/session-share-page.test.tsx` 新增两个行为用例，原有十六个保留。调整宽度的用例用
指针事件驱动真实手柄（jsdom 没有 `PointerEvent`，因此该用例自带一个携带 `pointerId` 的
实现），断言树最终停下的宽度：拖到 304px、上下两个夹取、忽略第二个指针的移动、松开后不
再跟随、方向键 16px 步进、折叠时手柄消失、重新展开回到所选宽度。选中用例断言被标记的
元素不包含任一连接线元素，且连接线所在的行本身没有被标记。两者都能检出对应回归：把底色
改回整行会让后者以 `expected true to be false` 失败，去掉夹取会让前者以
`expected '4000px' to be '480px'` 失败。

jsdom 不计算布局，因此没有测试能看见这两条线。几何量在 Chromium 中针对
`Sharing/SessionShareReader` 故事测得：1280px 与 700px、浅色与深色，用
`getBoundingClientRect` 读取树自身的矩形——竖线缺口为 `0`，被标记标题的背景起点在拐角
终点右侧 6px 且解析为真实的 `oklab(… / 0.1)`，拖动与键盘宽度如上，且拖动经过正文时没有
产生文本选区。

`pnpm typecheck`、`oxlint`、`check-i18n`、三个边界守卫以及 `pnpm run docs check` 均通过。
`@lody/components` 套件 477 个文件中 474 个通过；`control-plane-mirror`、
`conversation-view-hooks` 与 `sidebar-share-only-menu` 在整套并行负载下因 5 秒默认超时失败，
单独运行通过，且三者都没有引入本次改动涉及的任何文件。没有验证任何托管分享——故事与测试
使用合成清单。

限制：窄视口的抽屉保持固定宽度，抽屉没有可拖的边框。窗口变化时的夹取是有损的——被缩小
的窗口压窄的树，在窗口重新变宽后仍保持窄，因为没有记录夹取前的宽度。320px 的正文下限是判断值，不是实测
的可读宽度。`packages/components/src/components/sharing/AGENTS.md` 原本距上限只剩 7 字节，
因此本次压缩了已有条目——保持语义、把理由移到本文与侧边栏树文档——以容纳两条新规则。

本文建立在[阅读页布局说明](../feature/2026-09-14-share-reader-navigation-and-foot.md)之上，
那次改动引入了本次修正的底色与折叠动画。

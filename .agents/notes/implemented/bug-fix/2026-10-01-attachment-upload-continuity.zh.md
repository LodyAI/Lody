# 附件上传到历史消息的显示连续性

Status: implemented
Translation: current

[English](2026-10-01-attachment-upload-continuity.md)

## 摘要

图片上传结束时，待发送预览先被丢弃，正式消息随后重新请求缩略图，因此再次出现加载占位。
待发送文件卡片也额外预留了进度行，且与正式卡片的边距不同。
现在准备阶段在释放源数据前写入已有图片缓存，待发送文件复用正式卡片布局，进度叠加在底边。
以最终附件布局为基准；缓存淘汰和页面重启后的图片仍走普通加载流程。

## 决策与归属

本次修复关闭了此前[原位发送决策](../architecture/2026-09-14-deferred-attachment-send.md#sending-in-place-2026-09-29)
记录的缩略图重复加载限制，并把其中预留的文件进度行改为叠加层。
当前意图见[附件 Spec](../../../../specs/session-files.zh.md#8-展示与离开保护)。

`SessionFileCardLayout` 统一外框、图标、名称、副标题和操作槽位；待发送文件与正式文件
使用同一个 `SessionFileCardList` 边距。上传进度与失败文案在该布局内部变化。
准备边界按工作区、会话和图片标识写入成功上传的图片字节，之后待发送队列才能清掉源数据。
浏览器支持时，发布前先解码新地址，避免本地首次解码带来的闪白。
待发送和正式图片同步读取这些字节；CSS 保留既有缩略图裁剪方式。
桌面上的长状态文案在一行元数据内截断，避免窄窗口中状态变化把附件推移。

复用原有 200 MiB 图片缓存，不引入第二套预览存储，也不在历史已经出现后继续保留待发送消息。
原生 iOS 在就绪前准备可安全长按分享的 data URL。缓存代次和取消信号阻止迟到的原生转换发布预览；
预览缓存失败不会把成功上传变为失败。传输选择、重试、取消、历史写入和可选云路由继续由现有模块负责。

## 证据与限制

准备、待发送行、正式文件卡片、图片缓存、图库和发送者身份套件共通过 55 项行为测试。
首帧测试在没有执行 effect 时直接渲染正式图片组件，覆盖完整、大缩略图和紧凑缩略图；
缓存测试覆盖标识隔离、原生 data URL、清理和取消。
交互式 `SessionPendingMessages.UploadToHistory` 故事先释放源数据，再切换为真实正式消息行，
提供桌面宽度和窄屏版本。

Playwright 驱动 Chrome，在 1280px 和 390px（强制移动布局）使用相同合成附件，
对比修改前 HEAD `93545f01b` 与修改后的真实组件。写入历史时暂缓缩略图响应，
复现原来的预览缺失与加载占位；随后释放响应，展示保持不变的最终布局。
修复后，两个宽度下的四个阶段均保持 168px 方形图片、62px 文件卡片高度和相同附件位置。
准备完成与正式消息复用同一个已解码地址，图片请求数为零。
桌面和窄屏前后对照截图覆盖上传、释放源数据、写入历史和最终成功。
根工作区格式化、改动范围内的 Oxlint 和 i18n 检查通过。
根工作区 `pnpm check` 在文档站缺失 `fumadocs-mdx` 依赖处停止；
组件类型检查仍受缺失的 Office 查看器依赖和无关依赖 API 不匹配阻塞。
文档与公开边界检查报告了未初始化 ACP 子模块中的缺失文件与清单。

尚未在打包 Electron 或实体原生设备上验收。
缓存中的源图片保留原始字节，不单独生成转换后的缩略图，直到原有缓存淘汰它们。
既有图片转本机文件的 fallback 仍可能改变附件类型；本次不修改该传输。

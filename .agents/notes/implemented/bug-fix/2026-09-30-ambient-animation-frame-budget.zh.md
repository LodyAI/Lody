# 窗口失焦时把氛围动画限制在 30 帧

Status: implemented
Translation: current

[English](2026-09-30-ambient-animation-frame-budget.md)

## 摘要

任何一个正在运行的无限动画（12px 的工作标记、转圈图标、状态扫光）都会让 Chromium
合成器每个 vsync 出一帧（ProMotion 上是 120 Hz），而可见的窗口从不会被节流，所以
agent 工作、用户在别的应用里时，Lody 会连续几个小时满帧绘制。现在窗口失焦时，所有
氛围动画都会在同一个刻度网格上量化为 30 帧；有焦点时保持流畅，而且不暂停任何动画，
因为放在副屏上的 Lody 仍然需要让人看到它在工作。在隔离的 Electron 43 基准测试里，
这让 renderer 加 GPU 进程的 CPU 大约减半；剩下的底线来自只要有动画在跑，合成器
仍会在每个 vsync 醒来。

## 压力

- 在 Electron 43 构建上实测，Lody 可见但不在最前，四个工作标记加两个转圈在跑：
  renderer 11.4%、GPU 进程 20.4%、WindowServer 46%；所有动画保持暂停时分别是
  2.2%、0.8%、8.0%。
- 一个动画的成本与十八个相当，600×600 的动画与 12px 的相当：成本取决于出帧数量，
  而不是像素或图层数。trace 显示合成动画每秒 120 个 `DrawFrame`，且没有主线程工作。
  [转圈说明](2026-09-13-spinner-off-svg-retina-composite.zh.md)把工作移出了主线程，
  但没有让运行中的动画变便宜。
- Electron 43 恢复的遮挡检测只对被完全盖住的窗口有效；最常见的情况（别的应用在最前，
  Lody 仍在屏幕上）报告的是 `visible`。

## 决定

`lib/ambient-motion.ts` 负责一个帧预算，由桌面端 renderer 安装一次。窗口 `blur`
时，它把每个无限动画的时序改写为 `steps(round(duration / tick))`，并把时长、延迟
和起始时间对齐到 33.3 ms 的刻度；`focus` 时恢复每个动画原本的缓动、时长和延迟。
一次性动画（进场、工作到未读的收拢）不受影响。失焦期间开始的 CSS 动画（包括伪元素）
通过 `animationstart` 加入；脚本创建的 Web Animations 不会触发这个事件，所以由
所有者调用 `adoptAmbientAnimations`——`WorkingGrid` 在创建方块后就这样做。它的周期
（1900、2700、3600 ms）、1 秒的转圈和 2.2 秒的扫光都是刻度的整数倍，所以没有任何
循环改变速度。

关键在于共享对齐：没有对齐的 `steps()` 动画会交错变化，合成器几乎每个 vsync 仍要
出帧。

## 备选方案

- **失焦时暂停。** 最省，但被否决：把 Lody 放在副屏上的用户会把暂停的标记当成应用卡死。
- **用 JS 定时器驱动指示器**（VS Code 的光标闪烁、Chrome 的 `views::Throbber`）。实测
  并不更好：10 Hz 定时器 3.4–3.6%，10 帧 `steps()` 3.3%；30 Hz 定时器和连续动画一样
  贵，因为每一拍都是一次主线程帧和提交。
- **有焦点时也始终降帧**（VS Code 的 codicon 转圈用 `steps(30)`/1.5 秒，约 20 帧；
  进度条在 10 秒后改为 `steps(100)`）。等产品评估过失焦时 30 帧的观感后再决定。
- **平台开关。** 屏幕上的窗口没有可用开关：`setFrameRate` 只用于离屏渲染，
  `--disable-frame-rate-limit` 是取消上限，Chromium 按内容降低显示刷新率的机制只在
  Android 上注册。

## 验证

隔离的 Electron 43.7.6 页面，窗口可见且无焦点，四个网格加两个转圈，统计 30 秒内
renderer 加 GPU 进程 CPU：连续动画 7.8–7.9%，30 帧 4.2–4.4%，20 帧 4.5%，10 帧
3.3–4.3%，无动画 0。把真实模块打包进该页面后，CSS `spin`、`::after` 扫光和 Web
Animations 都读到 `steps(n)`，起始时间都在整数刻度上，CPU 从 8.5% 降到 5.2%。
`tests/ambient-motion.test.ts` 用真实的波周期和相位检查每一个变化时刻都落在同一个
网格上；逐一去掉每个对齐步骤和两条接管路径做消融，都有测试失败。

## 局限

- 低于 30 帧后收益趋平：只要有动画在跑，合成器仍会在每个 vsync 醒来推进它，只有
  停下来才能去掉这条底线。
- 基准测试里无法单独测出 WindowServer 的部分；实测 A/B 显示它是最大的一块，所以
  产品层面的节省尚未测量。
- 预算只覆盖桌面端 renderer；浏览器组合没有安装它。

# 批量构建按需加载目录树

Status: implemented
Translation: current

[English](2026-10-18-lazy-directory-tree-construction.md)

## 摘要

文件面板的 provider 构树器在添加按需加载目录时反复查找、排序同级数组。合成的 10,000 个同级目录快照会占用主线程约三秒，而普通文件路径的构建很便宜。现在按每个同级数组建立目录索引，插入结束后只对有变化的数组排序一次。输出契约保持不变，包括目录身份、已有子项、修改标记、文件／目录路径冲突和最终顺序。性能与输入形状相关；5,000 文件与 5,000 目录的混合快照明显更便宜，本变更不宣称生产延迟分布。

## 决策与职责

`hooks/use-code-session.ts` 继续拥有纯 provider 条目转换与既有 Hook。普通文件仍由 `buildFileTreeFromPaths` 构建；lazy directory 保持相同的斜杠分段规范化，以及最后一个有效条目覆盖目录 id 的规则。每次调用的 WeakMap 只按完整路径索引目录子项，因此同路径文件仍是独立节点。记录新建目录所在的同级数组，最后用原比较器排序一次。不改变 provider 订阅、获取、发布、可见行虚拟化或消息时序。

```text
provider 快照
  → 构建普通文件树
  → 首次访问时索引同级目录
  → 添加 lazy 节点及身份
  → 对每个有变化的同级数组排序一次
  → 发布相同形状的树
```

原实现对每个路径段查找同级数组，每插入一个节点就排序。保留原算法或只虚拟化行，都无法消除渲染前的平方级工作。没有采用长期共享索引：新快照必须删除旧节点、标记和 id；构建期索引不需要缓存失效或新的生命周期。这里是纯计算，不引入 Effect 迁移单元或第二个数据权威。

## 正确性与证据

Owning provider-tree 套件覆盖已有文件与 lazy 祖先混合、目录 id 替换、重复／空路径段、空或缺失 id、文件与目录路径冲突、逆序宽目录快照，以及 provider 实时快照替换。既有文件树、虚拟行和视图状态套件保留修改标记传播及展开／选择覆盖。测试断言最终树和状态，不断言耗时阈值或排序调用次数。

此前隔离的生产浏览器审计中，逆序同级 lazy 目录 1,000 个耗时 31.4 ms，3,000 个为 286.5 ms，10,000 个为 3,017 ms。索引查找、批量排序原型的等价输出分别为 1.0、2.1、6.8 ms。这些数字定位算法问题，不是打包 Electron 或用户项目验收。Code Collab 默认扫描预算为 10,000 条，本地项目目录读取每层最多请求 1,000 个子项。不宣称所有大仓库都有这种形状。

使用最终 PR 实现的生产浏览器构建，对相同形状的 10,000 个合成目录测得 8.2 ms（单次观察，不代表延迟分布）。24 条 provider／文件树／视图状态针对性测试与根 `pnpm check` 通过，根 `pnpm format` 完成。`pnpm run docs check` 仅报告 6 个指向未初始化 Kimi/Pi 子模块的现有断链。

[文件界面文档](../../../docs/sessions-file-surfaces.md)拥有当前实现说明。产品回归与根检查结果记录在 PR 中，私人原始 trace 不进入变更。

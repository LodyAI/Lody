# 本地项目行的可点击性取决于可见性，而非机器归属

Status: implemented
Translation: current

[English](2026-09-15-shared-machine-project-navigation.md)

## 摘要

此前侧边栏中的本地项目行只有在所属机器属于当前登录用户时才能激活 chat landing，
因此团队成员共享的机器上的项目只呈现为不可点击的标签，也没有新建对话按钮；
而 landing 的输入区其实早已向同一位用户提供了同样的机器与项目。
现在该行的能力取决于项目可见性而非机器归属：侧边栏渲染出的每个项目都能在 landing
上切换到对应的机器与项目，并提供新建对话。删除仍然仅限机器所有者，因为删除请求要
派发到拥有该设备的一方。这没有扩大任何权限面：侧边栏与 landing 读取同一份可见项目
索引，其中只包含用户自己的机器，以及明确共享给工作区的项目。

## 决策与证据

`buildVisibleLocalProjectIndex` 是用户能否看到某个本地项目的唯一关口——要么来自
自己的机器，要么来自共享给团队的 Convex 访问记录。`chat-landing.tsx` 直接基于该
索引构建机器与项目选择器，只是在默认值上偏好自有机器的项目，并明确回退到共享项目。
侧边栏使用同一份索引，却又用 `machine.ownerUserId === userId` 二次设限，导致两个
界面对同一个项目给出相反结论：landing 接受它，侧边栏却不提供进入它的入口。

归属仍然决定删除。远程项目的删除是在该设备的 machine Flock 文档上排队的请求，只有
所有者可以发起，因此 `canRemoveProject` 保留归属判断，右键菜单的删除项也仍仅对
所有者出现。

去掉该关口后，`LocalProjectItem` 的 `canNavigateProject` 在所有调用点都恒为 true，
于是将其移除，而不是留下一个永远成立的条件。现在项目行不可点击的唯一原因是删除
正在进行中，因此该分支（`role`/`aria-disabled`、光标以及隐藏的新建对话按钮）依然
存在并被覆盖。

另一种方案是改为按机器可达性设限，已被否决：离线的自有机器项目在侧边栏中本来也保持
可点击，而机器当前能否运行任务应由 landing 而非该行来告知用户。

## 验证

新增的组件测试渲染了托管在团队成员机器上的项目行，并验证契约的两个方面：该行会带着
机器与项目 id 激活；新建对话按钮出现并开启新对话，且不会同时触发普通激活；处于删除
中的行保持不可点击且没有新建对话按钮。既有的 `LocalProjectItem` 测试与包类型检查通过。
验证停留在组件层面：承载原归属判断的侧边栏分组装配没有独立测试环境，因此防止该关口
被重新引入的保障是移除承载它的 prop，而非一条测试。

# 将 Roost 缓存恢复限制在实际变更与请求窗口内

Status: implemented
Type: bug-fix
PR: https://github.com/LodyAI/Lody/pull/1765
Translation: current
Date: 2026-10-21

[English](2026-10-21-roost-cache-recovery-network-cost.md)

## 摘要

checkpoint 与正文绑定修复把失去绑定的缓存导向串行全历史快照重建。在模拟 250 ms RTT / 2 Mbps 的网络下，恢复 2000 条缓存需要 41.00 秒、50 次请求；能力信息晚到也能在安静会话重开时触发它。缓存现在分别保存变更覆盖与补丁资格，通过完整变更回复校准受影响正文，原子提交后才恢复补丁。覆盖缺失或不属于当前 generation 时，只原子替换最新一致窗口，旧页按需读取。同一失去绑定的缓存场景现耗时 2.21 秒、1 次请求，并保留全部 2000 条缓存；真正 reset 会使旧缓存页失效，再次获取前无法离线使用这些旧页。

## 决策与正确性边界

- `checkpoint` 证明所有保留正文可以应用相对补丁。连续的无保护写入通过 `recoveryCheckpoint` 保留已验证的变更覆盖，且只允许完整回复。校准立即使用 `readChanges`，不等待空闲 watch；正文与重新绑定的 checkpoint 原子提交。两个游标字段都参与 compare-and-swap。
- 同 revision 的旧式分页保持已验证基准不变。不同 checkpoint 的部分保护分页不能证明未读取前缀有效，即使 revision 看起来连续也不行。保留原基准，通过 owner 验证完整区间，并允许 owner 拒绝不同 generation。
- reset 或覆盖缺失只读取一个最新窗口，原子提交正文、成员关系与 checkpoint。事务失败或被抢先推进时保留原 projection；晚到替换不能覆盖另一标签页推进的 head。普通刷新不再遍历旧页，也不因持续写入反复重启全量遍历。
- 失效旧行从活动缓存移除。缓存 cursor 已指明绝对边界：支持 checkpoint 的 owner 直接返回目标区间，不再从尾部一路翻到目标位置。旧 owner 沿用明确的旧 cursor 协议。搜索、事实与导出仍读取各自真正需要的数据；未读取的前缀不能冒充完整历史。
- 普通完整变更校准保留已缓存前缀。真正 reset 的离线可用性会变化：失效旧页必须重新向 owner 获取。Roost 权威历史和本地已接受输入不受影响。这是草案[历史契约](../../../../specs/session-history-writes.zh.md)明确记录的缓存策略取舍，不涉及数据库迁移。
- 沿用 v2 缓存命名空间隔离不安全的 v1 writer。没有增加新命名空间、Native 发包、线协议能力或补丁日志。保留 v1 仍是独立的浏览器存储成本。

本决策延续[正文绑定保护](2026-10-21-roost-cache-checkpoint-body-binding.zh.md)，替换其中的全缓存恢复选择。该保护必须保留；直接向未绑定正文应用相对操作会重新引入重复文字。

## 测量

本地受控环境为 Apple M4 / macOS arm64、Node 24.14.0、Chromium 145.0.7632.6。owner 使用生产 MessageHandler、Native Roost 0.2.0 和临时 SQLite；浏览器使用生产 bridge/cache 与真实 IndexedDB。准备数据和资源后，通过 Chrome CDP 对 HTTP 加延迟、限速。Roost 使用真实 AES-GCM RPC 封装。合成历史包含确定性的 2 KiB 前缀文本、一份不变的 352 KiB 工具结果与一次单字符追加。表中是单次样本，不是 p95，也不是 Linux/staging 实测；完成指一致缓存持久化，不是 DOM 绘制。

| 2000 条，250 ms RTT / 2 Mbps | 旧恢复 | 修复后 |
| --- | ---: | ---: |
| 正文失去绑定，但变更覆盖有效 | 40.998 秒 / 50 个回复 / 6,892,567 bytes | 2.207 秒 / 1 个回复 / 481,696 bytes |
| 正常增量追加 | 0.268 秒 | 0.275 秒 |

修复后的安静重开能力竞态耗时 2.979 秒、两个回复，并保留全部缓存。覆盖缺失时，最新 40 条恢复耗时 2.714 秒、一个回复；owner reset 需要 reset 回复再加一个窗口，合计 2.987 秒、两个回复。400 条时对应的有界恢复同样约 2.7–3.0 秒。这些窗口结果不能称为完整历史恢复。

在三秒内继续追加 29 次的场景中，同样 2000 条缓存的首次一致提交，在 100 ms / 10 Mbps 网络下耗时 0.513 秒，在慢网下耗时 2.200 秒。随后通过生产 watch 继续增量追赶，分别于 3.089 秒和 3.027 秒收敛到 owner 最终 checkpoint 与尾部正文，保留全部已缓存位置。慢网共使用一个完整变更回复与三个补丁回复，合计 487,773 响应 bytes，没有重新开始全历史遍历。

Loro 对照使用 1.16.3、生产领域 writer、`loro-repo` 0.23.3 SQLite/IndexedDB adapter、产品 zstd 快照压缩，以及 benchmark 的 AES-GCM 二进制封装。最终逻辑历史和持久化结果与 Native owner 核对。同样 2000 条慢网下，正常 Loro 增量耗时 0.280 秒、117 bytes；完整快照恢复耗时 27.957 秒、6,899,194 bytes。有效的 Loro 增量游标不需要该完整快照。两边都没有包含完整 Streams bootstrap、鉴权、SSE 协议或云端跳转。

只读矩阵中后端数据库与 WAL 文件大小未增长；这不能证明没有物理写 I/O。独立持久化浏览器 profile 中，v1 与已填充 v2 的文件合计在实际完整变更校准前为 17.83 MiB，校准后为 17.76 MiB。旧版全量重建测试为 15.48 → 26.16 MiB。LevelDB 压缩使这些观测值不能作为通用稳态倍率；本次去掉了重复改写前缀，但没有删除保留的 v1 缓存。

## 验证

所属 IndexedDB bridge/cache 测试覆盖晚到与不同 generation 的部分分页、完整校准后恢复相对补丁、有界 reset 发布、提交前保留旧状态、拒绝并行标签页中的过期替换，以及更新提示持续到来时的推进。真实 Native owner 回归覆盖 1 条和 2000 条已缓存历史：旧式正文刷新、能力晚到、一次完整变更区间，以及与权威完整历史一致，过程中不读取未变化分页。原有内容补丁、加密 RPC、结构修复和失败修复测试继续适用。

大规模 Native fixture 在单独限时 120 秒的准备钩子中导入并封存 1999 条未变化消息。恢复测试仍保留默认 30 秒期限及完整历史相等断言，避免真实 SQLite 历史的准备过程消耗恢复测试的时间预算。两个用例仍使用生产 owner 和缓存。

受控浏览器脚本与原始结果保留在本地 benchmark 产物中。它们验证列出的负载，不是任意存储损坏、跨版本应用行为或生产延迟分布的穷尽证明。

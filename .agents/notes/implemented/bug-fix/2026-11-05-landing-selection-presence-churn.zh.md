# 在 presence 抖动中保留落地页选择

Status: implemented
Translation: current

[English](2026-11-05-landing-selection-presence-churn.md)

## 摘要

聊天落地页上选中的远端机器会被本地机器取代，远端恢复后也不会变回去。这由两个问题叠加造成：presence 重启时，远端明明在线却推出了空快照；落地页又把“不在在线集合里”一律当作重新解析并持久化选择的理由。现在重启会保留上一份快照直到新房间 joined，在线状态只在启动时改动一次选择，且不写入存储的默认值。代价是真正离线的机器会一直保持选中，直到用户手动更换。

## 问题

`useChatLandingDefaults` 从 `selectableMachines` 重新解析，这个集合只包含本地机器和心跳新鲜的机器。它没有遵守[presence 通道预算](../architecture/2026-09-20-ephemeral-presence-channel-budget.md)里的三态规则：未同步的房间被读成离线。Web 在集合为空时没有可见症状，因为该 effect 在没有可选机器时直接返回；桌面端则总有本地机器可以回退。随后持久化 effect 覆盖了记住的目标，于是一帧空数据就造成永久改变。

SSE 原地回收会保留 store，从来不是原因。空帧来自 store 替换：看门狗在 `connecting` 或 `reconnecting` 持续 20 秒后重启，以及重连循环在 `error`、`disconnected` 或唤醒时发现陈旧后执行 `stop()` 再 `start()`。SDK 把读写合并成一个状态，所以 POST 失败也可能重启一个读通道正常的房间。此外，已同步房间里超过 TTL 的心跳也会移除单台机器，这条路径不涉及重启。

## 决策

- `WorkspacePresenceTransport` 在 `joined` 之前不交付替换 store 的快照。`stop({ retainSnapshot: true })` 只由两个重连循环使用，其余 stop 仍交付 `{}`，首次 `start()` 行为不变。
- 落地页挂载后在线状态一旦确定，已存在的选择不再仅因在线状态被替换。机器或其配置被移除时仍会重新解析。
- 启动时已同步房间报告存储的机器离线，只在当前视图回退。记住的目标保留在默认值里，可选时恢复，除非用户先选了别的。
- 只有明确的 `offline` 才阻止发送，`unknown` 继续并由机器自身的 deadline 兜底。

## 备选方案

- **继续跟随在线状态，恢复时切回。** owner 否决：已同步房间里的陈旧心跳仍会在用户输入时换掉目标，聊天可能在用户没注意到的情况下开在错误的机器上。
- **只在未同步时跳过回退。** 这样覆盖不到陈旧心跳路径。
- **只修落地页。** 侧边栏状态、会话状态和按机器的同步每次重启仍会闪烁，所以空帧必须从源头去掉。

## 后果

如果重启一直没有 join，保留的条目最多比房间多存活 90 秒 TTL。这与原地重连已有的表现一致，且同步状态保持 `connecting`，缺失的机器读作 `unknown`。报告场景里这个客户端为什么会重启房间尚未查明：没有现场 trace，所以此修复消除了症状，但没有证明触发原因。

## 验证

组件测试覆盖：看门狗和重连循环路径的快照连续性、终止时清空、云端与 dual 模式下重连循环接线的 `retainSnapshot` 参数、选择保留、启动回退及恢复，以及发送拦截状态。尚未在真实远端机器的桌面会话中验证。

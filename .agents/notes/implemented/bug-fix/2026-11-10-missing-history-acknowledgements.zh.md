# 缺失正文的失败确认保留每条输入身份

Status: implemented
Translation: current

[English](2026-11-10-missing-history-acknowledgements.md)

## 摘要

只有一个缺失正文标记时，下一次超时或生产者清理标记，会忘记之前失败的输入。迟到的正文或 RPC 随后可能让旧输入重新入选。Session 元数据现在保留执行主机维护、只增加条目的 `missingHistoryUserMsgIds`，并兼容旧标量。恢复投递使用新的输入 ID，其他消息仍可正常入选。

## 决策与所有权

同一会话串行的 dispatch watcher 是该映射的唯一写入者。下一次超时将旧标量记入映射，再加入本次失败的 ID。现有主机租约和旧进程退出约束排除两个执行主机同时写入；这里不证明多个主机并发替换整个 LWW 映射是安全的。生产者发布新激活时不再清除恢复确认。恢复期间出现新的激活，旧超时不能将它当作已经等待到期。

`isMissingHistoryUserTurn` 同时读取两种表示。待执行判断、正文/RPC 选择、优先输入退役、持久输入接纳、Roost 激活和界面均使用这个精确 ID 判断。每条迟到且尚未结束的消息仍可显示重新发送入口。没有读取到正文，不能证明消息已执行或处理，因此拒绝通过推进 `lastHandledUserMsgId` 解决问题；迟到的消息仍可能出现，因此也拒绝只记住最新失败。

这些是输入身份确认，不是诊断日志。每项只保存失败 ID 和 `true`，不复制正文，存储量随失败身份数量增长。任意按条数或年龄删除，会重新放行旧失败输入。它们跟随会话元数据保留和删除，不成为其他 ID 或会话的就绪条件。

Inbox 重试记录仍由原有 Effect scope 持有。每条失败保留原记录，继续尝试独立记录，最后返回合并后的 Cause。后台扫描报告错误后继续，批次准备也逐项隔离。中断仍结束 scope 内任务，没有新增运行时所有者或迁移链。

## 证据与限制

验证技能通过合成文档端口回放未改写的恢复与选择方法：两次失败都保留；迟到正文/RPC 仍被排除；清理旧标量不会复活输入；新 ID 仍能正常入选；旧超时不标记新的激活。删除映射写入后，同一检查失败。真实 Effect/SQLite fixture 检查独立重试、准备/诊断失败、未知结果不重放以及未来 Inbox 输入。没有运行真实多端同步、签名授权、主机租约生产者、原生 Provider 或完整界面。

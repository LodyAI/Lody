# Agent Note 作为持续维护的决策记忆

Status: implemented
Translation: current
Supersedes: [明确 Note 触发条件](../../archived/process/2026-09-07-explicit-agent-note-triggers.zh.md)

[English](2026-10-28-agent-note-memory-hygiene.md)

## 摘要

Agent Note 承担仓库的决策记忆，但过去只增不减：两个月写了 930 篇英文 note，只归档了
4 篇；活跃 note 写完即冻结，读者无法区分当前指导和过时历史。同时 `AGENTS.md` 的
8192 字节硬上限迫使 Agent 把规则压缩成残句。现在只为持久的决策依据写 note；每篇新
note 都要做取代检查并归档被它替代的记录；已实施的 note 跟随代码更新所引用的事实；
每篇新 note 都要从描述该代码现状的 README、文档或 Spec 链接过来；`AGENTS.md` 改为可以说明理由后上调的词数上限。双语 note 和测量证据保持不变；存量
note 尚未清理，一篇 note 是否值得写仍是任何检查都无法判断的取舍。

## 问题

在 2026-10-28 的 `main` 上，统计此前 500 个提交（2026-10-14 至 2026-10-28）和整个
note 目录：

| 信号                                                       | 数值            |
| ---------------------------------------------------------- | --------------- |
| 活跃英文 note（`proposed` + `implemented`）                | 1143            |
| 已归档 note                                                | 4               |
| 活跃 `bug-fix` note                                        | 450             |
| 500 个提交中新建 note 与更新已有 note                      | 577 对 210      |
| 改动任意 note 的提交                                       | 500 个中 392 个 |
| 改动任意 `AGENTS.md` 的提交                                | 500 个中 226 个 |
| 超过 8000 字节的 `AGENTS.md`                               | 95 个中 41 个   |
| `## Verification`/`Validation`/`Evidence` 占 note 正文比例 | 19.6%           |
| 记录通过数量的 note                                        | 159             |
| 引用了已不存在的仓库路径的活跃 note                        | 28              |
| 带 PR 链接的 `proposed` note                               | 107 篇中 63 篇  |
| 被 README、`AGENTS.md`、文档或 Spec 链接的活跃 note        | 925 篇中 337 篇 |

这些数字来自四个机制。"每个非简单改动"的触发条件让几乎每个修复都要写 note，而"先找
已有归属 note"的规则没有任何后果，于是新建远多于更新。已实施 note 保留写作时的历史
语境，文件移动或符号改名后它们就会悄悄失真，而归档又依赖没人去做的主观判断。验证段
记录的通过数和环境说明只对当次 PR 评审有用。字节上限不能上调，满载的 `AGENTS.md`
每加一条新规则，就得把已有规则缩短来腾地方；例如 `apps/cli/src/session/AGENTS.md`
在这 500 个提交中被改了 38 次，几乎每次增删行数相等。

抽查 Kimi 和 Grok 相关的 note，可以看出这些数字对读者意味着什么。其中的事实仍与代码
一致，最有用的是决策依据（为什么不预先创建 Kimi 的计划文件、为什么 Grok 通过私有方法
分叉）。但 Kimi 计划模式的行为分散在四篇带日期的 note 里，最新一篇修正了较早一篇的
假设，而且没有一篇被 Agent 修改 Kimi 代码前会读的文档链接。Grok 用量统计的 note 仍标
为 `proposed`，尽管对应 PR 六周前就已合并。真正起到记忆作用的是 Grok 运行时版本锁定
那篇：CLI agent README 的 managed runtime 一节链接了它，README 说明现状，note 说明原因。

[DeepSeek Harness](https://github.com/deepseek-ai/deepseek-harness) 采用相同的生命周期
目录和双语 note。约五个月后，它有 383 篇活跃 note、927 篇归档 note，其中活跃 `bug-fix`
只有 17 篇。造成差别的是：每篇新 note 都做取代检查；已实施 note 在归档前保持与现状
一致；写入门槛更窄，事故另走 postmortem；词数预算可以说明理由后上调。

## 决策

- **写入条件。** note 至少记录以下之一：被否决的方案、测试和类型无法强制的约束、
  测量结果、格式变化、归属边界。仅仅"修好了"的修复写在 PR 描述和回归测试里。得出
  实质结论的调研仍然需要 note，这保留了[原触发条件](../../archived/process/2026-09-07-explicit-agent-note-triggers.zh.md)
  的初衷：没有代码改动的设计结论不能丢。
- **写入时取代检查。** 每篇新 note 都在活跃 note 中搜索同一决策：有归属 note 就更新
  它而不重复新建；被完全替代的已实施 note 在同一个 PR 中归档，并列在新 note 的
  `Supersedes:` 中；部分替代则互相链接。[归档技能](../../../skills/archive-agent-notes/SKILL.md)
  给出流程和基于 Lody 实例的校准示例。
- **已实施即现状。** 已实施 note 使用现在时；改动移动或重命名了它引用的内容时，就地
  更新该事实。决策本身不改写，推翻决策要写新 note。归档 note 冻结。
- **归属文档链接。** 每篇活跃 note 都要从它的现状归属文档链接过来：描述该代码的
  README 小节、`.agents/docs/` 页面、`AGENTS.md` 规则或 Spec。归属文档用一句话写明当前
  行为，因此同一模块的多篇 note 读起来是一张清单。Agent 顺着这些链接找到 note，而不是
  在带日期的记录里搜索；来自其他 note 的链接不算。
- **读时维护。** 任务依赖的 note 如果过时、未被链接或生命周期不对，就在同一个 PR 中
  修正；实现某个提案的 PR 把它移到 `implemented/`。note 在被使用的地方得到修正，而不是
  依赖单独的清理计划。
- **保留证据，不记日志。** 测量、benchmark 表格及其条件留在 note 中。验证部分链接
  固定每个行为的测试，并写明尚未验证的内容。
- **词数上限。** [`agents-budgets.json`](../../../../scripts/docs/agents-budgets.json)
  为每个 `AGENTS.md` 设定 1200 词的默认上限，并允许按文件覆盖。超出时，挪出一个
  主题、在不丢规则的前提下精简，或在 PR 中说明理由后上调。默认值高于压缩最严重的
  文件（8 KiB 时约 1000 词）；`packages/ui/AGENTS.md` 已有 1251 词，因此一开始就有
  覆盖值；`.agents/notes/AGENTS.md` 设为 1400，因为它是本次扩展的 note 规则的唯一归属。

`pnpm run docs` 负责其中可机械判断的部分。`check` 在以下情况失败：超过词数上限、
`Supersedes` 目标未归档、新 note 没有归属文档链接、已实施 note 含有提案阶段标题（`## Plan`、`## Acceptance
criteria` 及其中文形式）。它在达到上限 90% 时和出现运行日志短语时给出警告。标题和
短语检查只作用于相对 `--base`（CI）或 `HEAD`（本地）改动过的 note，不会重新打开历史
记录；生命周期移动不算新 note。`status` 列出所引用的反引号仓库路径已不存在的活跃 note
（`staleReferences`），以及没有归属文档链接的活跃 note（`unlinkedNotes`，引入时 589 篇，
其中 309 篇是 `bug-fix`），作为读时维护和按主题审查的工作队列。

本决策部分取代了[按任务范围拆分 Agent 说明](2026-09-08-scoped-agent-instructions.zh.md)
中的字节度量：说明链成本仍然要度量，只是改用词数；该 note 的内容迁移决策继续有效。

## 备选方案

- **禁止超过警告线的文件净增长。** 被负责人否决：这会阻止加入必要的规则，并诱发
  同样的压缩。
- **Agent note 改为单语。** 否决：双语是产品要求，体量问题通过少写、少留来解决。
- **把 benchmark 数据移出 note。** 否决：测量结果是未来决策需要的证据，只去掉运行
  日志。
- **按路径召回，以及 `Paths:`/`Verified:` 元数据和漂移检测。** 暂缓。note 与代码同
  提交，使 `git log` 按路径成为可用的召回索引（430 个代码提交中 314 个带 note），但
  一个 CLI session 文件就关联到 82 篇 note，大多是噪声。归属文档链接利用 Agent 本来就
  会读的文档，不需要新元数据；活跃集变小后再考虑召回。
- **定期全量审查。** 未作为主要机制：不设配额地审查 925 篇 note 工作量大，而且很快又会
  过时。读时维护把精力花在真正被用到的 note 上；归档技能仍支持按主题审查。
- **整体照搬 DeepSeek Harness**，包括哈希封存的归档、逐行对齐的翻译 sidecar 和独立
  的 postmortem 层。未采用：每项都带来工具成本，而上述四个机制已经对应了测得的原因。

## 影响

写入的 note 会减少，留下的 note 在其引用的代码移动时必须维护。写一篇 note 现在还意味
着要改它的归属文档，这让 note 的主题更明确，但多了一处编辑。贡献者不能再靠追加一篇
新的带日期记录来满足 note 规则。上调上限从"不可能"变成一次可见、经评审的决定。运行
日志检测基于中英文短语，会漏掉换种说法的表述，也会误报引用的测试名，因此只给警告。

## 验证限制

[`main.test.mjs`](../../../../scripts/docs/main.test.mjs) 覆盖了词数上限与覆盖值、
格式错误的清单、被列入预算但已不存在的文件、仅针对改动 note 的提案标题和运行日志
短语、未归档的 `Supersedes` 目标、失效引用队列，以及归属文档链接（拒绝仅来自 note 的
链接、接受指向任一语言的链接、存量 note 只排队、生命周期移动豁免）。没有检查能判断一篇 note 是否
值得写，或取代检查是否搜索充分；链接也只能证明归属文档提到了这篇 note，不能证明那句
现状描述准确。本次改动不清理现有的 1143 篇活跃 note，那需要按主题
逐批应用归档技能。本 note 归档了它所替代的触发条件 note。

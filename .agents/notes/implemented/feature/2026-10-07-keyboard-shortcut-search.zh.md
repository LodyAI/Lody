# 快捷键设置搜索

Status: implemented
Translation: current

[English](2026-10-07-keyboard-shortcut-search.md)

## 摘要

快捷键设置页列出全部命令，但无法查找某个命令，也无法回答"这个按键绑定了什么"。现在列表上方新增一个搜索框，默认按名称筛选；打开框内右端的键盘开关后改为按按键筛选，两种模式互斥。只要某行当前任一绑定与录制按键的规范形式相同即视为匹配，因此别名、修饰键顺序和次要绑定都能命中。测试随改动一并编写，但撰写时尚未运行。

## 决策

- **一个输入框，两种模式。** 开关是位于输入框尾部插槽的图标按钮（带 `aria-pressed`，关闭时为次要灰色，打开时为强调色）。打开时清空文本查询，关闭时清除按键筛选，因此同一时间只有一个筛选生效；纯函数匹配器仍支持两者同时存在。
- **名称模式。** 对显示的（已翻译）标签、未翻译的 `title` 或命令 id 做不区分大小写的子串匹配，因此界面为中文时仍可用英文名或 id 找到对应行。查询会去除首尾空白，仅含空白时不筛选。在输入框中按 Escape 会清空非空查询。
- **按键模式。** 输入框变为同一外观下的只读显示（`@lody/ui/input` 的 `InputShell`）：先显示占位提示，按住按键时实时预览，松开后以按键标签显示录到的组合。录制复用各行重新绑定所用的 `useKeyCapture`，因此命令分发和系统全局快捷键保持暂停，且只有一个录制器在监听。每个新组合直接替换上一个而不退出模式：`onCapture` 返回 `false`，使捕获（及暂停）持续。
- **退出按键模式。** 单独按 Escape 与点击开关效果相同，退出模式。其他取消——某行开始自己的录制，或窗口失去焦点——保留模式和筛选，因为用户可能正在重新绑定筛选出的行；点击或聚焦输入框即恢复监听。为区分这些情况，`useKeyCapture` 的 `onCancel` 现在会收到原因（`escape`、`blur`、`superseded`、`manual`），现有调用方忽略该参数。
- **匹配规则。** 双方都经过 `canonicalizeBinding`；比较 `commands.getKeybindingsFor` 返回的全部绑定，而非仅行中显示的主绑定。全局快捷键行按其实际生效的绑定匹配。未绑定的行永远不匹配按键筛选。
- **布局。** 没有匹配行的分类以及为空的全局分区会被隐藏；全部不匹配时页面显示一条"没有匹配的快捷键"提示。
- 匹配逻辑是 `packages/components/src/components/settings/keyboard-shortcuts-filter.ts` 中的纯函数，可在不渲染的情况下测试其规则。

## 备选方案

- 在输入框旁放按键标签加清除按钮，以及单独的录制按钮：已改为框内开关，使其保持一个控件、一条边框。
- 像命令面板一样使用模糊匹配：本页列表较短，子串匹配结果更可预期，故未采用。
- 为搜索单独实现捕获逻辑：没有必要。现有 hook 已能接受 Enter 等不带修饰键的单键。Escape 保留用于退出模式，所以无法通过按键搜索单独的 Escape，可改用名称搜索。

## 限制

- 按键筛选生效时重新绑定某行，可能导致该行因不再匹配而消失，这是可接受的。
- 按键模式监听期间所有按键都交给捕获，Tab 不会把焦点移出输入框；键盘用户用 Escape 退出。
- 单元测试（`packages/components/tests/keyboard-shortcuts-filter.test.ts`）、jsdom 渲染测试（`packages/components/tests/keyboard-shortcuts-setting-search.test.tsx`）和 `@lody/ui` 字段测试随改动编写；它们、类型检查和 Storybook 均未在撰写环境中运行。

# 移动端首跑引导把安装动作交给电脑，而不是在手机上打开下载页

Status: implemented
Translation: current

[English](2026-09-23-mobile-first-run-connect-machine.md)

## 摘要

移动端主页的首跑界面（workspace 内既没有机器也没有会话时展示）此前只有
「Lody 运行在你的电脑上」加一枚在手机浏览器里打开下载页的按钮——那个
页面会转而推荐用户刚刚装好的这个手机 App，而且无论点什么都无法把东西装
到真正需要它的机器上。现在这张卡变成了「连接机器」引导，围绕手机唯一能
递给另一台设备的两样东西构建：CLI 路径是可复制的
`npx lody daemon start` 命令胶囊；命令和本地化下载链接都可以通过「发送到
电脑」系统分享面板（AirDrop / 信息 / 邮件）递过去，剪贴板复制作为通用
兜底。手机本身不再打开下载页。底部三步预览（机器出现 → 添加项目文件夹 →
选 Agent）完成闭环。有意取舍：所有新文案字段都是可选的、带中文兜底，因此
只传原来三个字符串的旧宿主也能渲染出完整引导——代价是组件里存在中文兜底
文案，移动端宿主应通过 i18n 覆盖。

## 决策

### 升级现有空态，不新增路由

最先考察的替代方案是独立 onboarding 页面——移动端新路由或 `site-docs`
公开页面。两者都被否决：

- 独立路由会复制一个已经存在、且已经持有触发条件
  （`showChatOnboarding`：无机器且无会话且不在加载中）的界面；第二个界面
  需要自带一套触发逻辑，并会随时间与它本该解释的真实空态漂移。
- 公开站点页面只能在离开 App 后到达，而用户需要引导的时刻恰恰是盯着空白
  Chat 页的那一刻。
- 公开下载页已经持有平台探测和发版元数据。引导只把它当作*可分享的 URL*
  引用（`onboardingDownloadUrl`，与桌面空态共用 `getDownloadPageUrl`），
  因此发版通道变化不会让引导过期。

### 为什么手机端不应打开下载页

第一版保留了「下载 Lody」按钮，在外部浏览器打开
`getDownloadPageUrl`——与桌面端无机器提示共用同一 handler。两个事实说明
在这个界面上那是错的：

- `site-docs/components/download-page.tsx` 按 UA 检测平台并给命中的卡片加
  「Detected platform」徽章。在 iPhone/Android 上命中的是*移动端*卡片——
  页面重点推荐的正是用户已经装好的 App，桌面端下载要往下滚一屏才看得到。
- 就算用户在手机上点到了桌面端下载，`.dmg`/`.exe` 也只是落在手机的文件
  App 里，到不了电脑。这个点击从未跨越设备边界。

按钮背后的真实任务是一次跨设备交接，而引导的设计基于一个认识：手机无法
传输任何东西——它只能*展示*用户自己带过去的内容。因此两张卡都把制品以
可敲字的 mono 胶囊作为主体：

- **命令卡**——大字号 mono 胶囊展示 `npx lody daemon start`。走到机器前
  照敲是基准路径（22 个字符，好记）；点胶囊复制（覆盖贴进 Termius/Blink
  这类手机 SSH 客户端的场景），胶囊右缘挂一个纯图标的分享按钮，把
  「命令 + 链接」打包在一个 `text` 字段里发出。
- **桌面卡**——分享面板就是交互本身：一个全宽带文案的「发送到电脑」
  按钮发送 `{ url }`，AirDrop 会直接落在 Mac 浏览器里打开；右缘钉一
  个纯图标复制按钮——与命令胶囊同一套「主操作 + 尾随加速器」的行
  布局，只是主次角色互换。URL 本身不再展示——链接的归宿是浏览器
  标签页，把它当可敲制品展示只是噪音；只有在 `navigator.share` 缺失
  时，胶囊（显示去 scheme、复制带 `https://`）才作为兜底路径出现。
  `onDownloadClient` 已从组件和 `MobileHomeScreen` 中整体移除——一个
  唯一职责是「打开页面」的回调在这个界面上不再有调用方。

机制层级跟着制品走：命令是要敲的东西，所以胶囊领衔、分享是尾随
加速器；链接是要打开的东西，所以分享领衔、复制是尾随加速器——
同一行结构，角色互换。QR 码方案被考虑过并否决：它解决的是
电脑→手机方向（手机扫屏幕），与我们需要的方向相反。入场动效
（错落弹簧 + 图标后的雷达 ping）曾实现过，评审后被有意移除——
引导静态渲染，这个界面克制比可爱更合适。

### 命令是主路径，桌面端是次路径

文档和 CLI 自己的预检（`apps/cli/src/commands/daemon-auth-preflight.ts`）
对真实旅程的描述一致：`npx lody daemon start` 校验凭据、在可见终端里发起
设备授权、打开或打印登录链接并等待——所以没有浏览器的远程服务器打印出的
链接，可以直接在显示着引导的这台手机上打开，而手机端本身已经登录。桌面端
只在自己的电脑上才是更友好的路径。排序由此而来：命令卡在前，因为它覆盖
所有机器类型（服务器、虚拟机、SSH 主机、个人电脑）；桌面卡只覆盖一种。

命令胶囊通过 `writeTextToClipboard`（`src/lib/clipboard.ts`）复制，这个
共享工具已经处理了非安全上下文和 Clipboard API 缺失时的隐藏 textarea
兜底——`src/ui/copy-button.tsx` 里现有的 `CopyButton` 没有这些处理，因此
有意没有使用它。

### 「机器上线之后」闭环

三条编号步骤与文档中的 quickstart 对应，用来回答首跑用户的第二个问题：
「这个手机 App 之后会变得有用吗？」它们是预览文案而非追踪状态，没有引入
打卡式 checklist 机制。

## 验证

`tests/mobile-home-onboarding.test.tsx` 在 jsdom 中渲染组件并断言可观察
行为：命令胶囊通过桩化的 `navigator.clipboard` 复制
`npx lody daemon start` 并切换到已复制标签；整个引导不渲染任何外跳
`<a href>`（手机端不链接出去）；命令覆盖值原样渲染；桩化
`navigator.share` 后两个分享按钮发出正确的载荷（命令路径的 `text` 含命令
与链接，桌面路径为 `{ url }`）；URL 胶囊显示去 scheme 的短链但复制完整的
`https://` 链接。`pnpm lint:i18n` 覆盖两个 locale 文件；包级
`tsgo --noEmit` 干净。

视觉验收：临时 Storybook story 把改动前卡片（从 git HEAD 逐字复制的 JSX）
与新引导并排渲染在两个手机框里，Playwright 截图
（worktree 根目录 `mobile-onboarding-before-after.png`）在各版迭代中都
确认了布局。该 story 与截图脚本已在取图后移除。

未验证：真实 Capacitor 构建里的分享面板（桩只证明了开关逻辑和载荷）；
`navigator.share` 与剪贴板 API 同时缺失的极端 WebView 上是否仍有可用路径
（`writeTextToClipboard` 有 `execCommand` 兜底，覆盖了现实中的其余情形）。

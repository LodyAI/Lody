# 对话分享卡片改为单一固定模板

Status: implemented
Translation: current

[English](2026-09-14-chat-share-card-fixed-template.md)

## 摘要

对话分享卡片此前是一个外观编辑器：六种背景、五种页脚布局、三档外框内边距、三选一
的明暗、四个开关，外加一个折叠代码块的数字输入框，可达的组合接近一千种，而其中值得
发出去的只有少数几种。这些控件还掩盖了两个缺陷——默认页脚只打印 Agent 名称，整张图
上没有任何 Lody 标识；默认的二维码永远编码产品首页而不是这段对话。现在卡片是一个固
定模板，只保留四个改不了版面的选择——卡片多大、底露出多少、用哪个底、用哪种配色——尺寸
分聊天版和帖子版；所有区块
共用同一个水平内边距，消息一律左对齐并靠不均等的纵向节奏分组，而不再把用户消息挂在
右边；预览界面也回到"预览 + 两个动作"，不再是控制面板。卡片仍然不限高，选得多就会得
到一张很长的图——这是刻意保留的：省略用户选中的消息会让图片与用户的选择不一致，而供
人阅读的完整对话本来就应该走分享链接。

## 决策

卡片有两个尺寸：`chat` 宽 360pt，`post` 宽 560pt。两者只在行宽和内部尺度上不同——字号
是共享的，并且是固定值而不是读取用户的对话字号设置——因此聊天卡片和帖子卡片会以同样的
字号排同样的文字。

尺寸问的是"这张图要发到哪里"，因为答案取决于这个，而导出者也正好知道这个。它决定的是
行宽：一行能放多少正文、一行代码会不会被折断。两个答案就够了，所以它是一个开关，不是
一个需要微调的量。

这个轴一开始是设备：由 `useIsMobile()` 挑宽度，理由是"你在哪台设备上导出"可以代表
"这张图要发到哪里"。它代表不了。在电脑上往群聊里发卡片的人拿到的是宽版，在手机上发
帖的人拿到的是窄版，而且谁都没法纠正。现在设备只负责给一个初始猜测，一下点击就能改
掉，除此之外不再决定图片的任何事——只决定这个界面是对话框还是抽屉。

两种卡片的全部尺寸集中在一张 `LAYOUT` 表里，而不是散落在标签上，"帖子比消息更舒展"因
此是一个决定而不是许多处。标题区、对话区和署名区共用同一个 `gutter` 值——这正是旧卡片做
不到的：它在不同区块之间混用 `px-5` 与 `px-6`，又把用户消息贴到右边，于是卡片里没有
任何东西共享同一条左边界。现在所有消息左对齐——一张分享出去的图，没有哪个读者的"我"
在右边——用户提问是一块浅色底的块，回复是普通正文。原先靠对齐承担的分组信息移到了纵
向节奏上：两轮问答之间的间距，是提问与它的回复之间间距的两倍。这正是卡片可以不加
说话人标签的原因。

出处信息留在旧设计已经做对的那条相机式说明栏里——Runtime、模型、token 估算、绝对日期
——而 Lody 署名移出卡片，印在下方的背景上：它不再占用对话的高度，也不会被读成记录的
一部分。缺失品牌标识的缺陷因此一并解决，且没有为第二个标识多花卡片高度。

二维码是被移除而不是被修好的。没有任何调用方传过 `shareUrl`，所以每一张导出的卡片编
码的都是 `https://lody.ai`；一行可读的 `lody.ai` 文字用十分之一的面积说了同一件事。
移除它也移除了它带来的异步资源——导出不再需要 `assetsReady` 门禁，因为剩下的资源只有
字体和一张打包图片，而截图管线本来就会等待它们。

背景保留为可选，这一条是更正：本次改动的第一版删掉了全部六种背景、把签名渐变写死，
理由是"一个不能让卡片变好的选择只是噪音"。这个理由对其中一种是错的。`welcome` 是开
场动画浅水场景的可导出静帧，是手工搭出来的——实景是 WebGL shader，DOM 截图序列化不
了——而且它在产品里没有第二个去处，所以删掉它是销毁了一份资产，不是移除了一个选项。
它同时也是唯一的浅色底，签名现在必须为它反向用墨。`aurora`、`ocean`、`sunset` 无论
如何都还活在用量卡片里。真正成立的分界是：改变卡片**怎么读**的选择（页脚版式、内边
距、消息挂在哪一边）是这次要删掉的编辑器；只改变它**读在什么之上**的选择是审美，属
于用户。`none` 留在这一组里，签名落到说明栏左列的第二行——和用量卡片已经写明的回退方
式一致——而不是另起一条独立的横栏。

留白是一个以像素为单位的滑块，也是这个界面上唯一一处问"量"而不是问"意图"的地方。之前
有两版在这件事上判断错了，而且错的方向相反，两次都做了更正。

第一版直接删掉控件、让留白由卡片尺寸推导，理由是"没人能判断 32pt 和 56pt 的差别"。这
个理由描述的是一张设置表单。在有实时预览的地方它不成立：用户根本不读那个数字，他拖、
他看，这比任何命名给出的答案都好。直接操纵恰恰是应该把量暴露出来的场景，在这里把一个
连续量切成几个有名字的档位，等于替一个已经能看见结果的人做决定。

中间那一版把留白绑死在尺寸上，还声称"560pt 的卡片配薄边、360pt 的卡片配厚框，这两种
组合都没人想要"。那是一句断言，而且两半都是错的：宽卡片贴边正是贴进 README 或文档想要
的，窄卡片配厚框正是手机发帖想要的。宽度和留白是真正独立的两个自由度——一个是关于行宽
的内容决定，一个是关于画框的呈现决定——所以它们是两个控件。尺寸会给留白一个该尺寸下的
常规初值，这正是让两者读起来像"先挑一个起点，再微调"而不是两个互不相干的旋钮的原因。

选尺寸总是会重置留白，背后没有"用户有没有动过滑块"的标记。一个有时保留、有时不保留的
隐藏位，比一个永远重置的预设更难预测，而且无论哪种，预览都会立刻显示结果。

零是可达的。低于 `MIN_SIGN_OFF_MAT` 时，底就不再是一条边距了，于是签名落回说明栏——和
完全没有底的卡片走同一条回退路径——卡片的投影也一并去掉，因为投影需要一个落得下的地面。

代码软换行改为无条件生效。图片没有横向滚动条，一行不换行就等于读者看不到的一行；这
是媒介的属性，不是偏好。要让这句话真正成立需要两条声明而不是一条，而第二条直到 review
才被发现：fenced `diff` 走的是 `MarkdownDiffBlock`，它的 `pre` 设了
`width: max-content`，好让宽 patch 在 App 里横向滚动。只放开 `min-width` 会把那个
`width` 留在原地，而 `pre-wrap` 下的 `max-content` 仍然是最宽的那一行——于是 diff 块保
持完整的未换行宽度，顶出卡片的固定边界，被卡片自己的 `overflow-hidden` 裁掉。也就是
说，"代码永远不会溢出分享卡片"这句话在写下的时候，对其中一种 fence 是假的。现在 Story
在两种尺寸下都带了一个 `diff` fence；此前一个都没有，这正是截图没能发现它的原因。配套的 `collapseAfter` 控件随之删除，同时删掉的还有一个
`MutationObserver`——它在每次渲染后改写 Shiki 的代码 DOM 来裁剪过高的代码块并注入
"+N 行"药丸标签，等于在和渲染器争夺并不属于它的节点。

无条件换行暴露了三件被选项矩阵掩盖的事，它们都是靠对 Story 截图发现的，而不是靠读
diff。代码块的语言标签是一块停在右上角的不透明遮罩，在 App 里可行是因为过长的首行会横
向滚动到它下面；换行之后的首行永远不滚动，于是永远被遮住。把这段让位空间放在 `pre` 而
不是代码块 body 上不是风格取舍：App 的代码样式写在 `@layer components` 里，而层内的
important 声明优先级高于未分层的 important 声明，所以组件内联 `<style>` 根本盖不掉
body 上那条 important 的 `padding-block`——但能盖掉它的普通声明。代码块的复制按钮在预
览里也是完全不透明的，会被一起拍进图片，因此卡片把它隐藏。最后，预览区的高度用的是百
分比，而百分比在 flex 子项上并不成立，滚动容器因此没有上界，长卡片会直接画到操作栏上面
——现在改为 `flex-1` 加 `min-h-0`。

`ui/slider.tsx` 是新增的，而且用的是原生 range input 而不是库：平台已经提供了键盘步
进、Home/End、正确的 ARIA role 与 value，以及符合系统预期的触摸目标，我们只负责轨道和
滑块本身。`tailwind/index.css` 里有两条全局规则必须手工绕开，已记在
[该 primitive 的规则](../../../../packages/components/src/ui/AGENTS.md)里——"Pro focus
style" 会把整个控件框起来，而 `*:focus-visible` 的重置会通过继承的自定义属性让 `ring-*`
工具类在滑块上失效。

两个动作按钮在对话框里用 `sm` 尺寸，在抽屉里保持默认尺寸。`sm` 同时也是 `text-xs`，
而那一栏里其他控件本来就都用 `text-xs`——所以默认尺寸下这两个按钮是整栏唯一的
`text-sm`。手机上它们是主要的触摸目标，`h-9` 本来就已经低于 44pt 的建议值，不该再缩。
不要为了"一致"把两者统一：这处不一致正是有意为之。

分享完成即结束整个流程：预览关闭，聊天里的选中态也一并撤掉——把一个用户已经办完的事情
留在那儿继续武装着，只是让他多一步手动收拾。手动关掉预览仍然**保留**选中态，那正是"想
回去改一下选择"的场景，所以两者是靠一个完成回调区分的，而不是 `onOpenChange`——后者分
不出这两种情况。

这件事顺带暴露了 `exportShareImage` 的一个缺陷：它把"用户取消了保存对话框"吞掉了，解析
结果和成功保存完全一样。那么"导出 resolved 就关闭"会把只是退出了文件选择器的人的流程
一起拆掉，而这正违反 Spec 已经给出的保证。现在它返回 `{ saved }`。浏览器下载没有取消
信号可读，因此那条路径永远报告已保存——这是诚实的：从点击那一刻起，传输就归浏览器管了。

完成回调会带上是哪个动作完成的，因为两者身后留下的反馈不同。保存有原生对话框或浏览器
自己的下载界面；复制在预览消失之后什么都没有，所以宿主只为复制弹一次 toast。

预览界面照此收敛：一个明暗开关，`复制图片` 与 `导出 PNG`。它以 App 当前的外观打开，
重置写在渲染阶段的分支里而不是 effect 里，因此重新打开的对话框不会有一帧显示上一次
的配色或结果提示。在手机上，同样的预览与动作渲染在底部抽屉而不是对话框里——这是两端
在外壳上唯一的差别。

已移除控件对应的 21 个文案键在两种语言里一并删除。`chatShareCard.qrAlt` 保留：用量卡
片仍然会画二维码。

## 备选方案

给卡片设置最大高度、超出部分渐隐并标注"还有 N 条"，这一方案被提出并由需求方否决：一
张悄悄丢掉用户已选消息的图片，陈述的内容与用户的选择不一致，而产品本来就能把完整对
话发布为静态分享链接。只做一种卡片尺寸、由外围界面按设备适配的方案同样被否决，最终
选择两种图片形态，理由是贴进手机聊天窗的卡片和贴进帖子的卡片会在不同宽度下被阅读。用
导出设备去推断该用哪一种，实现过之后被更正：那只是对去处的猜测，而去处直接问就行。

给留白起名字而不是让它可量——"紧凑 / 常规 / 宽松"，或者干脆折进尺寸预设里——实现过两
次，也回退过两次。两种形式在设置界面上都说得通，但在实时预览面前都站不住：预览回答
"多少"这个问题，比任何一套词汇都准。

把背景固定成一种、由亮/暗开关挑选签名渐变，这一版实现过，随后按需求方的判断回退。它
规则上更干净，还能自动做到浅卡配浅底，但代价仍然是删掉五种背景、其中一种不可恢复，
只为省下一排色块那么宽的一个控件。

## 证据与限制

[规格草案](../../../../specs/chat-share-image.md)承载意图，已在同一改动中更新；
[用量卡片规格](../../../../specs/usage-share-image.md)里那句"对话卡片的内容形态不
可预测，因而需要大量外观控件"的过时表述也一并修正。Story 覆盖两种尺寸 × 两种配色、留白滑块的两端、每一种需要单独
判断的底（浅色底配两种卡片配色、一种高饱和底、无底配两种卡片配色）、无标题卡片，以及
一个签名行远宽于两种卡片的代码块。

工作区类型检查、lint、i18n 键检查，以及 Code Collab、平台与公开边界三项守卫全部通过。
`@lody/components` 测试套件 476 个文件中 474 个通过；失败的两个是
`control-plane-mirror` 与 `conversation-view-hooks`，都依赖时序，单独重跑都通过，且
从本次改动触及的任何文件都到不了它们。本次改动没有自己的单元测试，也没有新增：卡
片是纯展示组件，它喂给的导出管线没有变化且仍由
[导出测试](../../../../packages/components/tests/share-image-export.test.ts)覆盖，
而断言 class 字符串或 jsdom 量出的几何值的测试并不能发现视觉回归。留白的三种状态改为
在真实浏览器里核对：0 时签名在说明栏里、卡片没有投影，56 和 96 时签名在底上、投影存
在，且任何一种情况下签名都恰好只有一处。验证方式是对卡片各
Story 以及对话框在桌面与手机视口下的 Storybook 截图，另外在浏览器里实测了标签让位空间
和被隐藏的复制按钮。没有建立像素基线，抽屉形态也没有在真机上验证过。本记录扩展
[最初的功能记录](2026-09-08-chat-share-image.md)与
[剪贴板后续记录](2026-09-08-chat-share-image-clipboard.md)，二者均未被取代——消息选
择、元数据与截图管线都没有改变。

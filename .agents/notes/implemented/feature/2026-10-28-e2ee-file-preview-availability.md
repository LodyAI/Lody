# Encrypted workspace file and preview availability

Status: implemented
Translation: current

[中文](2026-10-28-e2ee-file-preview-availability.zh.md)

## Abstract

Encrypted workspaces can use Code Collab and remote preview through the existing workspace keys, signatures and same-member machine authority. Code Collab v2 synchronizes file-index and signal Flocks; its file text, saves, diffs and LSP results travel over RPC rather than synced text documents. Those Flocks now use the normal protected document provider, including snapshots. The file and preview RPC methods use the existing encrypted request/response wire and journal. Public-link sharing publishes a server-readable static copy outside workspace membership after the [explicit encrypted-workspace confirmation](2026-10-28-e2ee-share-plaintext-consent.md).

## Decisions

The owner approved reuse of the existing remote-preview behavior and device-local export rather than a new ledger or permission model. Feature RPC admits only the existing Code Collab methods, restricted `file/preview`, and preview create/status/revoke. It cannot invoke `file/resolve-local`, local endpoint controls or unrelated machine operations. The native sender resolves the target machine signer from the verified ledger; the receiver reuses fresh same-member machine authorization and checks workspace/machine and claimed human identity before the existing handlers. Missing native capabilities never select ordinary RPC.

An ordinary workspace retains its existing RPC, owner-session envelopes, Flock rooms and preview proofs. Encrypted previews reuse the capability-checked Quick Tunnel and loopback proxy. Page bytes stream through that tunnel with `no-store`; no application server content store is added. This does not describe the preview tunnel as end-to-end encrypted: the tunnel service terminates its transport. Preview control results and visual comments remain in the protected RPC/document paths.

Feature requests and results keep each existing signed content frame below 1 MiB. A feature request splits its canonical JSON into 256 KiB chunks, with big-endian uint32 index/count before each chunk in the existing method-body params. Each frame carries the same request ID, method and expiry. The host retains the complete ordered original as length-prefixed ciphertext frames before transmission; response digests bind that exact aggregate. Results share the native assembler and strict binary page metadata with [machine read queries](../architecture/2026-10-28-e2ee-read-queries.md): uint32 totalPages/totalBytes, then at most 256 KiB of LocalMachineRpcResponse JSON; sequence and progress/success mark position. Signer, routing, epoch, method, count, exact lengths, request digest and sequence are checked before a complete DTO crosses IPC. Requests remain bounded to 32 MiB; results are bounded to 16 MiB and return an explicit size error above it. Incomplete request retention has a shared 32 MiB/32-request bound and expires on later intake or owner close. No second read-query format exists.

The channel extends [encrypted dispatch](../architecture/2026-10-28-e2ee-streams-dispatch.md); its dispatch originals and execution claims remain unchanged. The renderer shares one response reader with encrypted dispatch. Its runtime close aborts transport and joins that reader before token disposal. The CLI listener retains its four bounded intake handlers. Read and write tasks have independent 32-slot owners and drain admitted raw work before close. The ten audited pure reads use fresh read authority and originals without an execution claim; diffs, saves, index publication and preview controls require write authority. Its journal claims a feature request before a save, retains every encrypted response before publication, and replays only those originals after publication failure. An uncertain started request cannot execute its save again. Storage failure affects that request, with a bounded retained response owner; it cannot switch a sibling to plaintext. No ledger, key format, or schema migration changes.

### Browser and mobile consumers

Browser and mobile surfaces reuse the same facade, provider and signed feature channel as the desktop; they add no file transport, cache or Electron service tree. Only a runtime whose host implements the feature ports receives the encrypted sender. Otherwise every remote file entry point returns a non-retryable unavailable result rather than a transient error that invites retry, and ordinary RPC stays closed.

The file role for display comes from the verified ledger `memberRole` delivered with each host status, not the organization listing. Owner, admin and member map to write, while Guest, unknown and closed or removed bindings map to read. The receiver silently drops a request its fresh authority rejects, so that request would only surface as a timeout. For that reason, a non-writer is refused before signing any request outside the closed read list, with copy that names the read-only role. That list excludes save, both diff kinds, turn diff and lazy directory initialization. This client refusal is a display gate and never an authorization; the receiving machine's check is still final. A demotion takes effect at the next operation, and the role view notifies the UI. Responses are not rebound to the requested path on the client: project-root routing legitimately returns a root-relative path, and correlation to the exact signed request digest already rejects another request's response.

## Evidence and limits

Synthetic real-key and SQLite tests exercise large request/result chunks, out-of-order request assembly, wrong-request responses, immutable originals across reopen, publication-failure replay, and revocation. Production provider/preload tests cover host forwarding; runtime tests open the actual Repo-backed file-index and comment stores; host tests cover protected updates and snapshots for those rooms. Facade/provider tests drive the non-Electron path against a synthetic machine: save then reread on a second device, stale-digest conflict without overwrite, Guest refusal before signing, and unavailable hosts. These checks do not establish installed desktop, live-cloud, native keystore, or all-platform acceptance. Device-local export is a separate independent change in [PR #2011](https://github.com/LodyAI/Lody/pull/2011).

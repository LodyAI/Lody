# 会话头部只用一个对话访问控件

Status: implemented
Translation: current

[English](2026-09-14-session-header-share-control.md)

## 摘要

把对话发布成公开链接，此前只能从会话头部的「…」菜单进入，而且任何位置都不会
说明一个对话是否已经发布过——也就是说，唯一一条影响范围会越出工作区的事实，恰
恰是头部从来不显示的那条。现在头部原本的私密/团队药丸控件（`SessionAccessControl`）
同时承载两条访问轴：团队可见性决定形态，已发布的静态链接决定文案，而发布编辑
器由对话页统一持有，药丸和菜单打开的是同一个。要知道「是否已共享」，代价是每
个打开的对话多一条控制面订阅；这是为了让头部能说出这件事而刻意付出的成本，而
且这次读取受能力开关约束，本地开源版不会发出任何请求，也不会出现任何分享入口。
仍未回答的是一个既有缺口：一个对话可能通过以*另一个*对话为根的分享而可读，这个
控件同样不会提示。

## 决策

### 一个控件，两条轴

读者对头部只会问一个问题——谁能看到这个对话——所以两条轴的答案应该出现在同一个
控件里，而不是让两个药丸去争同一个角落。

团队可见性决定**形态**。私密对话保留原有的下拉菜单，因为它的私密状态是从机器和
项目继承来的，必须先解释清楚，才谈得上提供任何一种分享动作。其余情况——团队可见，
或者单人工作区根本解析不出可见性——没有什么要解释的，就是一个普通按钮。

已发布的静态链接决定**文案**，两种形态都一样。一条谁都能转发的链接，比「仅限你的
工作区内部」是更大范围的披露，因此它才是值得一眼看到的状态，药丸上的「私密对话」
会被「已共享」取代。取代的只是文案，不是事实：私密范围仍然是菜单里的第一块内容，
链接自身的披露紧随其后。团队可见的对话上，按钮写着「分享对话」，状态确定后就地
变成「已共享」——同一个药丸、同一个图标，只换了一个词——所以状态解析过程中不会有
任何元素凭空出现或消失。

于是 `SessionAccessControl` 的 `state`（单人工作区没有）和 `publicShare`（没有云
的构建没有）都是可选的，只有两者都缺席时才什么都不渲染。最后那种情况就是本地开
源桌面版，它的行为没有变化。

### 如何知道「已共享」

`useSessionShareStatus` 是 `useSessionShareManagement` 的只读同伴：读同一条
`sessionSharing:getManagement` 记录，不做候选发现，也不做任何写入。「控制面还没
回答」和「这个构建没有云」都返回 `unknown`，而头部把 `unknown` 当作尚未共享，因此
文案只会就地升级。

这是真实的成本：以前没有订阅的地方，现在每个挂载的对话多一条；而且分享子系统自
己的规则是「关闭的编辑器不得发起云查询」。那条规则说的是编辑器，它依然只在打开
时挂载；头部是第二个、有意为之的读取方，而区分两者的不变量——只读管理记录，绝不
读源文档——记录在
[`components/AGENTS.md`](../../../../packages/components/src/components/AGENTS.md)。

这个状态的范围是**以本对话为根**的分享，也就是编辑器所管理的那一个。作为别人分享
的子对话被发布出去的对话，在这里显示为未共享。这与 Q12 已经记录在案的、关于对话
框移除「其他分享来源」列表的缺口是同一个；本控件既没有扩大它，也没有修复它。

### 编辑器归页面所有

`SessionShareDialog` 及其开关状态原本由 `SessionHeaderMenu` 持有。有了两个入口之后
这样行不通，因此对话框上移到 `SessionChatInterface`，菜单改为接收
`onOpenPublicShare` 回调，回调是否存在决定菜单项是否渲染。状态仍然按 session id
存放而不是布尔值：一个在编辑器打开时切换了内容的 Tab，不能让编辑器改指向新显示的
对话。

「…」菜单里的入口保留。需求说的是在菜单**之外**再加上头部，而菜单仍然是桌面端唯一
一处把全部会话操作列在一起的地方。

### 药丸文案的垂直居中

在图标旁边加上文字，暴露了一个此前被纯图标状态掩盖的缺陷：药丸共用样式里写了
`leading-none`，而 `items-center` 居中的是文案的**行盒**，不是字形本身。行盒比字体
自身的行盒矮时，字形的墨迹会比旁边的图标高出约 1.2px——在 8 倍设备像素下从渲染结果
逐像素测量，文案墨迹中心比按钮中心高 1.25px，而图标中心正好落在按钮中心上。现在这
套样式改用 `line-height: normal`，此时 half-leading 为零，墨迹落在字体设计的位置；
同样的测量读数变为 0.13–0.25px，在一个设备像素之内。选 `normal` 而不是固定行高，是
因为界面字体可以由用户切换，这项修正必须跟随实际使用的字体。修改落在共用常量上，
因此「已归档」药丸也一并修好。

## 考虑过的替代方案

**两个药丸——保留「私密对话」，旁边再加一个「已共享」。** 它不丢失任何信息，被否
决的理由是头部的空间预算而非正确性：桌面工具栏已经有启动器分栏按钮、PR 徽标、归档
药丸和「…」菜单，再加一个状态药丸会把标题在窄窗口里挤成省略号。收敛成一个文案的
代价，是已发布的私密对话失去了一眼可见的私密信号，所以菜单第一块仍然写着它。

**文案保留「私密对话」，只在菜单项上标注「已共享」。** 这样私密信号得以保留，但它
恰恰把披露藏到了最需要披露的那类对话的一次点击之后——而需求明确要求：已经共享出去
的对话，无论是否私密都要说出来。

**用 `sessionSharing:list` 按工作区读一次，而不是按对话读。** 订阅数从 N 降到 1，
但该列表是分页的，而且按角色分范围（成员只看到自己的分享，管理员看到工作区清单），
于是头部为了回答关于单个对话的问题，需要翻整份清单，而且对它看不见的分享会给出错
误答案。这被当作一个披着性能外衣的正确性问题而否决。

**打开编辑器去看。** 直接否决：那会让答案的代价变成打开一个具备抓取能力的界面，而
这条披露恰恰是不应该要求进入发布流程才能看到的。

## 证据与限制

`session-access-control.test.tsx` 覆盖了该控件真正的义务：私密对话仍然显示药丸与菜
单；非私密对话得到一个没有 `aria-haspopup` 的直接按钮并能打开编辑器；团队可见性尚
未解析时按钮已经存在；`shared` 显示「已共享」而 `unknown` 不会；私密对话的菜单里两
种分享动作都在；已发布的私密对话显示「已共享」，而菜单里依然写明私密范围和链接披
露。`use-session-share-management.test.tsx` 增加了状态钩子：active 读作 `shared`，
不存在以及 `draft`/`revoked` 读作 `none`，未作答的查询保持 `unknown`，没有工作区时
无论控制面持有什么都读作 `none`。这两个文件，连同既有的头部菜单、分享管理器和移动
端菜单套件，全部通过。

布局通过 `Sessions/SessionAccessControl` 在明暗两种主题下的 Storybook 渲染截图审
阅，覆盖普通分享按钮、已共享文案，以及在有/没有已发布链接两种情况下的私密菜单。

限制：没有连接任何托管后端，因此 `getManagement` 只通过其被 mock 的契约得到验证——
每对话一条订阅的成本是推断出来的，而不是对着部署实测的。该控件只在桌面端；移动端
保留 `SessionInfoBar` 里既有的私密标签和 `SessionShareMobileMenu` 里独立的分享入口，
本次改动没有统一它们。发布流程本身、它的确认与凭据处理都未改动，参见
[对话框与读取页布局笔记](2026-09-09-session-share-dialog-and-reader-layout.zh.md)
和[静态对话分享](2026-09-09-session-sharing.zh.md)。

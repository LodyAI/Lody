# 将超长输入框粘贴内容转换为文本附件

Status: implemented
Translation: current

[English](2026-09-28-oversized-paste-text-file.md)

## 摘要

以前超过输入框现有 500 KiB UTF-8 上限的粘贴会直接被拒绝，尽管产品已经有完整的文件附件链路。现在两个输入框入口都会把这段剪贴板文本保存在不可编辑的 `text/plain` 文件 `pasted-text.txt` 中，并沿用普通附件草稿流程。较短的粘贴继续使用原有行内或折叠行为；剪贴板文件筛选、文件数量与大小校验、上传、重试和持久化仍由现有附件逻辑统一负责。

## 决策与证据

- `createPastedTextFile` 保留剪贴板原始字符串，包括原始换行符以及首尾空白。500 KiB 判断仍使用原有的规范化并去首尾空白后的 UTF-8 体积，因此只有以前会被拒绝的内容才进入这条路径。
- 新对话 landing 和已有会话的粘贴处理器都会先生成文本文件，再与 `selectPastedClipboardFiles` 筛选出的文件合并后调用一次附件添加逻辑。这样仍保持 Word/PowerPoint 渲染截图让位于文本、真实剪贴板文件继续作为附件的规则。
- 生成文件沿用普通文件草稿和发送链路，因此继承当前单文件 100 MiB、单条消息 8 个文件的限制；没有新增上传状态、协议字段或文本编辑器。
- 这项决定取代了[2026-09-14 上限记录](2026-09-14-composer-paste-size-ceiling.md)中“超限即拒绝”的当前结论，但不改写那份历史记录。此前可编辑文本文件实验因回归而撤回，原因仍记录在[上下文兜底记录](2026-09-09-conversation-context-fallback.md)中。

## 验证与限制

- 已有会话输入框的渲染测试验证超限粘贴会生成 `pasted-text.txt` 卡片，文件字节、MIME 和原始内容都正确，不再触发超限错误 toast，并能在同一次粘贴中合并真实剪贴板文件。
- 同一套测试保留闭区间边界：恰好 500 KiB 的内容仍是折叠粘贴文本胶囊；纯 helper 测试覆盖文件名、MIME、字节长度和原始文本保留。
- landing 入口复用了相同 helper 与附件筛选逻辑，但本次没有通过完整渲染 landing 页面测试；打包桌面端的真实剪贴板往返仍未验证。

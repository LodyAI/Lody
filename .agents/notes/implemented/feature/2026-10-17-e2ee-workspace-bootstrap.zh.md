# E2EE 工作区的开发者创建与账本预览

Status: implemented
Translation: current

[English](2026-10-17-e2ee-workspace-bootstrap.md)

## 摘要

核心库已合入，但产品缺少可识别的加密工作区和初始化入口。本批接入开发者选项、桌面受保护的设备初始化、独立云端创建接口和可读的完整账本页。创建先落本地密钥，再按固定请求提交创世记录；已知加密空间不能进入旧明文运行时。这个交付仅开放控制操作，不代表聊天、附件、恢复登记、全平台保管或生产上线完成。

## 决策与责任

用户要求先完成工作区模式、开发者入口、独立云端标识、首次设备密钥与账本追踪。[实施导读](../../../docs/e2ee-workspace-bootstrap.zh.md)记录代码入口和数据流。普通工作区不转换；云端工作区 ID 与 genesis 一对一绑定，设备私钥不进入云端或渲染进程。

设备初始化由桌面主进程持有，使用既有保管适配器、真实签名与 SQLite 原请求记录。关闭或取消需要等原生操作结束；未知结果保留，不生成替代身份。云端适配器校验账号归属与回执；页面按账号和请求分别保存待确认工作，成功后固定创世哈希。账本读取使用 core 的完整与增量验证，不把服务端 JSON 投影当作权限事实。

原本只靠远端模式查询会破坏离线启动，也无法阻止已固定加密身份被降为明文。因此保留不可变的账号/工作区模式证明，并优先执行本地加密约束。未登记模式的旧缓存需首次在线验证，这是保留不降级保证的限制。独立窗口不能共享可覆盖的唯一 pending 槽位。

本批不自动迁移明文，不开放缺少密钥适配器的平台创建，不连接尚未加密的数据通道。[现有核心边界](../architecture/2026-10-15-e2ee-current-decisions.zh.md)与 draft 协议仍适用；此记录不批准协议或全平台 Beta。

## 验证与限制

验证覆盖真实加密/SQLite 重启、未知创建结果、账号切换、账本篡改与分页，以及真实本地控制服务的创建、并发重试和清理。独立复核发现的多窗口请求覆盖、模式降级和明文离线回归在本批修复并加入行为覆盖。具体命令和最终结果随交付记录列出。合成保护提供者不证明用户系统密钥库、签名安装包或实际部署行为；未读取用户钥匙串或生产数据。

本批目标验证：前端 77 项、云端组合 7 项、桌面保管/初始化 26 项与 IPC 2 项通过；私有后端 726 项及真实本地 Convex 18 项通过。新的独立复核运行相关三套 36 项测试并确认源码一致，未发现剩余可证 P0/P1。浏览器验证了合成账本和创建页的桌面/手机布局。完整仓库检查及部署结果单独记录，不由这些数字推定。

仓库验证：类型检查、类型感知 lint、Effect lint、格式与文档检查通过。完整 `pnpm check` 没有全绿：未改动的 CLI 测试受到注入的 Git 环境和 macOS 进程探针期限影响。隔离到原生 Git 后 24/24 通过；Inbox 套件曾独立 60/60 通过，但重复隔离运行仍触发既有探针期限。这些是保留的验证限制，没有绕过，也不记为完整检查成功。机械 lint 调整后的最终桌面保管/初始化测试为 26/26 通过。

## 运行时稳定性修正

后续审查复现了普通工作区在认证恢复期间启动失败、无关缓存变化导致运行时被替换，以及 localStorage 配额耗尽导致启动被拒绝的问题。本次修正在保留严格准入的同时，分开处理认证就绪、可选离线缓存和运行时所有权。初始化等待同一账号认证，在异步边界重新检查账号；即使认证已经恢复，也会重试本地产生的认证不可用错误。切换工作区会取消认证订阅并忽略旧读取结果，不会声称取消底层 I/O，也不让新的工作区等待旧的只读请求。准入完成后，认证刷新和无关缓存事件保留当前 Repo 与待发送内容；当前工作区的证据变化仍会触发重新验证。

只有已验证的普通或 legacy 模式缓存写入可以降级；加密信任锚、损坏证据和降级冲突仍然阻止启动。捕获所有准入错误会削弱模式保护，而强制每次缓存写入成功造成了已确认的配额回归。行为测试覆盖这些区别、待发送内容、预热窗口认领、同 ID 确认、取消和账号/认证切换时序。这些是组件与适配器测试，不代表已安装 Electron 的验收。

Effect 迁移评估保留 React 初始化作为所有者，以及现有平台 observable store/Promise 接口边界。这些修复无需迁移尚未完成的运行时依赖链；新增的唯一订阅在就绪、账号不匹配或取消时明确释放。本次不宣称完成原生生命周期迁移。

## 桌面依赖安装

本次接入新增生产依赖链 Electron → platform → cloud-api → E2EE core → SQLite。在同一锁定依赖树上，真实 `@electron/rebuild@4.0.4` 发现器使用基线 `fb4d565` 的工作区声明时没有原生候选，使用 `ba794186` 声明时则选中了 `better-sqlite3@13.0.3`。重建因 `node-abi@4.26.0` 无法映射 Electron `44.7.0` 而失败；这是本次接入触发的安装回归，不是无关的基线失败。

Postinstall 删除了通用 `install-app-deps` 命令，因为该命令不遵循已有的 `npmRebuild: false` 打包设置。SQLite 和 node-pty 保留 Node-API 预编译产物，Electron 自己的二进制安装器和 macOS Sparkle 专用构建保持不变。打包仍按目标准备二进制并运行探针。运行时版本与 [Node-API 下限](../bug-fix/2026-09-09-node-api-runtime-floor.md)均未改变。

子进程回归测试在旧脚本上失败、修复后通过；允许既有打包夹具访问 npm 后，原生依赖准备与 Sparkle 的 11 项测试全部通过。真实 macOS arm64 postinstall 已完成，包括 Sparkle 原生构建。同一 SQLite 预编译产物在 Node 和 Electron `44.7.0` 下完成内存数据库读写，node-pty 也在两者中加载成功。这些检查不证明 Windows/Linux 执行、其他架构打包、签名安装包或部署。

## 私有 Streams 账本调整

用户确认让 Streams 在 Convex 背后保存原始账本。共享组合层改用 action 创建和读取历史，describe 仍为 query，公开 DTO 不变。私有宿主负责签名和权限验证、条件追加、固定待处理请求以及跨服务删除恢复。客户端独立验证和仅开放控制功能的运行时边界保持不变。上文测试数量属于前一批改动；本批存储和 action 接线验证在交付时单独报告，不据此声称已部署或完成全栈 Beta 验收。

本次 action 接线验证：使用原生 Git 环境的公共仓库完整 `pnpm check`、格式与文档检查已通过；独立与组合环境的云组合测试均为 8/8。对应私有宿主的完整 affected 检查通过，最终后端测试 750/750，真实本地 Convex/SQLite Streams 联调 19/19（18 个场景及父测试）。新一轮独立对抗审查未发现有证据的 P0/P1。上文早期本地检查失败属于历史记录，并非本次结果；这些验证不证明生产网关、安装后的密钥保管或部署已验收。

## 首次准入可用性跟进

对公开 PR #1625 和私有 PR #3794 的只读复核指出，首次在线查询的可用性成本比此前记录更广：所有尚未保存模式证明的云工作区都需要实时认证及后端 `describe`，与开发者选项是否开启无关。安全决策保持不变；缓存工作区 ID 不能证明其是明文。本次跟进把首次 ID、认证和模式等待限制为 15 秒，说明失败原因并提供原地重试。认证或联网恢复后可重试失败的准入；超时或被替换的旧读取不能用迟到结果准入，也不能重建已正常运行的运行时。存储配额耗尽仍会阻止下次离线启动保存新的普通模式证明。

同一复核还发现私有账本的发布阻断：外部写入结果未知且读回为空时，当前 Streams 网关不能证明旧 PUT 不会在删除后重建同一 URL，因此不能安全释放写入所有权或完成账号删除。单加运维 mutation 或手动改库无法提供这个证明。Streams 必须先在同一提交边界提供持久栅栏和墓碑，Convex 才能安全恢复该写入；两个 PR 在协议和延迟请求联调完成前保持草稿。上文旧测试数字仅属于各自描述的增量，不是本次跟进的验证结果。

本次代码提交 `bafa14a97` 在已初始化的隔离 checkout 中通过 38/38 项运行时定向测试、组件类型检查、`pnpm format` 和使用原生 Git 的公共仓库完整 `pnpm check`。作者 checkout 的 `docs check` 与开始时一样保留 82 条缺失 ACP 子模块链接错误，没有新增错误。没有本地登录令牌时，外层登录/权限关卡可能先显示原有恢复界面；15 秒提示只属于可见的模式关卡。CI 与安装后客户端验收仍需分别确认。

## 账本兼容性与救援跟进

所有者决定账本 v1 永久可验证，而不是把预览工作区当成可丢弃的。对照 MLS（RFC 9420：每个组的版本、密码套件和组 ID 固定；ReInit 新建关联的替代组；`required_capabilities` 控制扩展）和 Keyhive（根公钥即组 ID，创建时不记录版本）后，没有发现 v1 创世记录必须补充的字段。v1 缺的是让旧客户端识别未来记录的方式，因此在出现任何线上账本之前加入了标签 9 的能力声明：只允许 Owner 或 Admin 的个人设备签署（所有者同意 Admin 也可签），只增不减，对不支持的能力码报告 `upgrade-required` 而非损坏。创世级变更会新建一个相关联的账本。独立生成的样例冻结了 v1 的字节、哈希和状态。

救援按失败类型区分，而不是统一报错：身份冲突永远不提供客户端重置；进度冲突提供需确认的单工作区重置；只删除无法读取的可选缓存。诊断信息不含账号 ID、密钥和记录正文。列表中的锁图标只用于展示。所有者决定在 Streams 墓碑上线前不开放用户删除入口，并选择默认关闭、按白名单开放的服务端创建开关（私有后端）。运维救援函数、创建开关和账本恢复设计位于私有服务端。

本次跟进的验证：e2ee-core 22 个文件 / 411 项测试，含固定样例和能力声明测试；受影响的组件测试（28 个文件 / 387 项）和新的控制页渲染测试；组件类型检查。变异检查确认：去掉存储重读后，原地重试测试会失败。完整 `pnpm check`、CI 和安装后客户端验收另行报告。

随后所有者澄清：合入不等于冻结。账本 v1 在生产部署第一次开放创建时才成为永久格式，此前须对权限账本中的待定事项（恢复库与可信锚编码、自撤设备后的换代衔接、恢复设备的登记顺序）做格式审查。在此之前，经批准的格式修改可以重新生成样例。冻结范围包括验证后的账本状态，因此新增或放宽的权限只能在能力声明之后生效。

## 与 main 的运行时所有权合并

合并保留了 main 按工作区回收 Repo 的规则，也保留了模式准入的取消规则。被替换的只读模式查询会中止；它没有占用 Repo 存储，因此不进入回收表，也不拖住其他工作区。开始创建数据层之后，清理操作登记在该工作区 ID 下；再次打开同一工作区必须等待所有旧清理完成，失败时继续阻止重建并允许下次重试。其他工作区可以独立启动。即使 React 所有者已替换、旧运行时随后才创建完成，也走同一清理路径。既有运行时测试覆盖迟到的模式结果和同工作区清理失败；合并后的套件本地 41/41 通过。 main 之后用 #1713 回滚了按工作区回收 Repo 的机制，改为每次初始化都等待的单条关闭链；2026-10-20 的合并采用了这一做法。被取代的模式查询仍会很快结束，因为它的 describe 调用会随初始化信号一起被中止，所以关闭链不会等待它。

## 已保存创建请求的可用性跟进

一次 review 发现，一个永远无法成功的加密工作区创建请求会被一直保存。创建页会保留每一个失败的请求，自动选中它，强制使用加密，并锁定名称和标识字段；只有实验开关提供了绕开的入口，而且无法丢弃该请求。服务器的发布开关默认关闭，因此只要尝试一次，用户关掉开关后，这台设备就无法再创建任何工作区，包括第一个工作区。保留请求的规则假设"早先的尝试可能已被预留"，但服务器是在同一事务中确认该请求 ID 没有任何预留之后，才检查开关的。

现在，当服务器证明请求未被预留且结果已确定时（`e2ee_creation_not_enabled`、`e2ee_creation_deleted`、`e2ee_genesis_already_bound`、`workspace_slug_taken`），客户端会移除已保存的请求，并原样抛出原始拒绝。结果未知的情况，以及 `e2ee_creation_conflict`（请求已被预留但内容不同），仍保留请求并保持锁定，以便原样重试。开关关闭时，已保存的请求可以先搁置：它仍留在列表中、可以继续，用户则可以创建普通工作区。账号没有任何工作区时，页面不再清掉创建失败的提示。收到已校验的回执后，工作区列表刷新失败现在只记为警告，不再视为创建失败。被移除请求在桌面端保留的准备材料从未发布；目前还没有原生的丢弃接口。路由级测试通过真实页面覆盖了"先搁置"、"未开放时移除"和"结果未知时保留"三种情况；变异检查确认每个测试在去掉对应修复后都会失败。

## 启用前不可见修正

下文原有的可用性取舍属于历史决定。本地先打开的行为保留；把未知工作区视为可以走普通出站路径的部分，由[未知模式出站准入](../bug-fix/2026-10-29-unknown-workspace-egress.zh.md)替代。服务端拒绝不能保护请求中已经发送的原文。现在的临时运行时保留本地访问，正文出口和发送接受则等待已认证分类。

对 #1625 的复查发现，E2EE 对普通用户可见，并且损害了他们的可用性。每次加载云端工作区都会显示“正在确认工作区加密模式…”。模式确定之前的任何失败都显示成加密失败，包括上一个运行时关闭失败。没有已保存证明的工作区要等待最多 15 秒的已认证 `describe`，随后失败，因此升级后第一次离线打开无法访问本地数据。超时以外的 `describe` 错误直接失败，不重试。每次重启运行时都会清除模式并卸载工作区界面。引导页即使对当前已激活的工作区也要验证，并在提示中显示原始错误码。无法读取的已保存创建请求会阻止创建普通工作区。

所有者提出的要求是：现阶段 E2EE 对普通用户不可见，明文工作区不出现 E2EE 文案、延迟或失败，普通工作区的行为与 #1625 之前一致。所有者明确选择的取舍是：默认按明文处理，在后台验证，失败时关闭并退役运行时。只有当本账号在本机有该工作区的加密证据，或列表把它标记为加密时，才需要在任何数据通道之前取得权威准入。证据包括创世 pin、已知加密模式、加密证明、无法读取的模式记录，以及 slug 相同且未完成的加密创建请求。其他没有已保存证明的工作区，通过 #1625 之前的 `resolveEffectiveWorkspaceId` 路径以临时准入（`descriptor: null`）打开，`describe` 随后在后台执行，没有时限并会重试。返回加密时先退役运行时，再记录仅控制准入；返回更新的、格式错误的、ID 不符或与本地证据矛盾的结果时，同样退役并失败关闭；不描述任何模式的失败则保留运行时。

这改变了什么：对本机从未见过的加密工作区，客户端不再保证绝不创建明文运行时。对于本机未知、列表未标记（或尚未加载）的工作区，在验证返回之前，由后端准入负责拦截：它拒绝加密工作区的普通 Streams、令牌、分享和执行入口。这段时间内的本地写入会留在该工作区的明文本地 Repo 中。加密工作区目前没有内容（仅控制），因此不会暴露加密内容。已排除的替代方案：保留阻塞式查询会保留离线回退问题；只信任列表无法离线工作。凡有本地证据、pin 或加密列表标记的工作区，原有保证不变。

配套修改。模式证明按账号和工作区 ID 匹配，按旧 slug 保存的证明被接受并改写。登录确认后，按顺序为列表中其他未标记加密的工作区预取证明。未认证的 Convex 响应、不透明的查询服务端错误和网络失败按 `getConvexAuthRecoveryDelayMs` 重试。同一账号和工作区重启时保留上一次已验证的模式。路由关卡（`components/workspace-admission-gate.tsx`）显示普通的加载和打开失败文案；只有模式准入失败（失败记录带 `modeAdmission`）且工作区已知为加密，或开发者打开了加密创建时，才显示加密文案。引导页恢复对当前工作区的直接继续，只对列表标记加密或有本地证据的工作区检查模式，失败使用通用的切换失败文案。加密创建关闭时，创建页把无法读取的已保存请求视为没有请求。开发者模式开关不变；按所有者决定，没有增加客户端账号权限开关。

后续复查发现，后台返回被拒结果时没有保存任何记录，重试或任何重新初始化都会再次打开明文运行时。现在被拒结果会写入持久的 `lody-e2ee-rejected-mode` 标记（存储拒绝时只在本次会话内保留），让该工作区必须先取得准入；其文案保持通用，除非开发者打开了加密创建。后台返回加密时，退役后立即同步记录该模式，消除了重新初始化再次打开明文的窗口；加密标记写入失败会走被拒路径并显示失败。列表存储每次启动都从 `loading` 开始，因此没有本地证据、但列表标记为加密的工作区，在列表到达前仍会临时打开。

Effect 迁移评估与运行时稳定性修正时相同：React 初始化仍是所有者，本次不迁移尚未完成的运行时依赖链。后台验证由初始化的中止信号管理。

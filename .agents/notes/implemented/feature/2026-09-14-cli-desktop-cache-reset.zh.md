# 从 CLI 重置桌面端的本地缓存

Status: implemented
Translation: current
PR: https://github.com/LodyAI/Lody/pull/704

[English](2026-09-14-cli-desktop-cache-reset.md)

## 摘要

桌面端修复本地状态的两条路径——设置 → 清空缓存，以及崩溃页的整体清除——都在渲染进程内部，因此渲染
进程卡死的用户根本点不到它们；而如果卡死的原因正是应用每次启动都会重新加载的本地数据，那么重启也无法
摆脱。`lody app reset-cache` 让这两个级别可以从终端预约：CLI 把一次性请求写入该安装的数据目录，
Electron 主进程在任何窗口加载之前消费它。缓存级别仍然由渲染进程执行，因为只有它能保住 Shortcut
发件箱以及清理时必须保留的那些 localStorage 键，这也意味着该级别需要渲染进程能启动；`--hard` 由主
进程原生执行，因此它才是渲染进程完全跑不起来时仍然有效的级别。

## 压力

`packages/components/src/lib/clear-local-cache.ts` 已经把两个修复级别做得不错：缓存清理会保留登录
状态、偏好设置和离线的 Shortcut 草稿，硬重置则不留任何痕迹。它唯一做不到的是在没有渲染进程的情况下
启动：两个入口都是按钮，而它们写入的启动标记位于渲染进程的 localStorage，其他进程无法写入。

这个缺口之所以重要，是因为现实中的卡死更多是数据形态的，而不是一次性的——例如某个被污染的文档会在
workspace 运行时把它物化时挂住——于是每次启动都会复现。应用重新打开同样的本地存储，卡在同样的位置，
用户没有任何入口。

## 决策

CLI 把 `desktop-local-reset.json` 写入 `getLodyDataDir()`，这是 CLI 与桌面端已经按安装 profile
以相同方式推导出的同一路径。格式、原子写入、取消以及消费式读取全部集中在一个共享模块
（`packages/shared/src/node/desktop-local-reset.ts`），使写入方与读取方无法在形状或位置上产生分歧。
不需要登录、不需要 daemon，也不走 deep link：deep link 是攻击者可达的——任何网页都能让操作系统跳转到
已注册的协议——因此清除动作绝不能由它触发。

主进程在 `app.whenReady()` 流程中、`openMainWindow` 之前消费该请求，并且这次读取会在执行之前先删除
文件。这个顺序正是关键：一个无法解析、已过期或执行到一半的请求不能在之后每次启动时被重新评估，否则就
是一个永远都在清空本地状态的启动循环。

两个级别按"谁有能力完成这件事"来划分：

- `hard` 在这里原生执行（对默认 session 调用 `clearStorageData` + `clearCache`）。它不需要渲染
  进程，这正是它作为真正逃生出口的原因；它也会清掉渲染进程保存在 localStorage 里的 Better Auth
  token，所以应用回来时处于登出状态。
- `cache` 通过新增的一次性 `app.consumePendingLocalClear` IPC 交给正在启动的渲染进程，
  `runPendingClearOnBoot` 会像处理应用内标记一样处理它。主进程无法正确执行这个级别：那里的 Chromium
  存储 API 只能按存储类型整体清除，原生版本会连带删除 prompt-shortcut 发件箱数据库——其中可能保存着
  离线保存的唯一副本——并且无法删除缓存修复必须清掉的那些具体 localStorage 键（Streams JWT/网关、
  workspace-info 映射、cursor-bypass 标记）。

是一次性的，而不是常驻的：渲染进程的启动路径在每次 reload 时都会重新执行，如果这个模式一直可读，
每次 reload 都会重新清空整个本地副本。因此主进程只交出一次。渲染进程这侧的探询有 2 秒上限，因为它
现在每次桌面端启动都会执行；一个永不回答的主进程只能延迟首屏，而不能阻止它。

始终未被执行的请求会在一天后过期，两个时钟方向都算，这样被遗忘的 `--hard` 不会在很久以后把用户登出
而对方完全无法把它和某个动作联系起来，时钟被往回校正也不会让请求永久有效。

## 考虑过的替代方案

**从 CLI 直接删除 Chromium 的存储目录。** 无需改动桌面端，但只在应用未运行时可行，而且无法表达缓存
级别：保留 `Local Storage` 会留下过期的连接缓存，删除它又会让用户登出。它还会把 Chromium 的磁盘布局
写死。

**通过本地 CLI host lease 直接连上运行中的主进程。** 主进程本来就在提供那个 socket，而且在渲染进程
卡死时它恰好是健康的，因此重置可以不重启就生效。暂不采用：该 lease 的关闭通道用桌面端并未公开的 token
做认证，扩展它会触及 local-agent 归属规则，而用户本来就要做的那次重启是更便宜的契约。

**通过 preload `additionalArguments` 注入模式。** 可以省掉每次启动的那次 IPC，但这些参数在窗口生命
周期内固定不变，因此除非再在 localStorage 里加一个"已消费 nonce"标记，reload 就会重放清理。相比主
进程里的一次性状态，这是更多的活动部件，而收益只有一次 IPC 往返。

## 验证

- `packages/shared`：围绕预约/消费/取消新增 9 个用例——只执行一次、被拒绝时同样退休该文件（非法
  JSON、未知版本、未知模式、数组、缺字段）、两个时钟方向的过期、恰好在边界上仍然执行，以及
  cloud/local 请求文件路径互不相同。
- `packages/components`：新增 4 个用例——CLI 预约的 `cache` 清理在没有 localStorage 标记的情况下
  执行精确清理并保留 auth token、应用内标记优先且不去询问桌面端、"没有预约"时什么也不清、桥接没有
  回答时在假定时器上放弃而不是拖住启动。把新增的读取消融掉会让第一个用例失败。
- `apps/cli`：`--hard`/`--cancel` 的解析，包括同时传入两者时的拒绝。
- 手工：构建 dev CLI 并执行预约、`--hard`、`--cancel`、双 flag 拒绝（退出码 1），以及各自的
  `--json`，检查写出的请求，并确认 `lody app [path]` 仍然可以解析。`--json` 最初被 `app` 自身的
  选项吃掉而没有到达子命令；`appCommand.enablePositionalOptions()` 修正了这一点，并保持既有的每种
  `lody app` 写法可用，包括结尾的 `--json`。

## 限制

没有在真实的打包桌面端启动中验证过：原生的 `hard` 清除以及主进程到渲染进程的移交只有单元测试和手工
CLI 覆盖，两者都不在 E2E 套件中。该命令也无法报告桌面端是否真的执行了重置——用户要通过重新打开应用
才知道。

重置仍然需要用户自己退出应用。如果将来确有必要做到不重启即生效，上面的 host lease 方案就是那条路，
而且它不需要改动本文件格式。

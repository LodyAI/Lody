# 会话启动自动重试临时性系统失败

Status: implemented
Translation: current

[English](2026-10-16-session-start-transient-retry.md)

## 摘要

在一台高负载机器上，有两次恢复因为系统拒绝 fork，在 20 毫秒内以 `spawnSync /usr/bin/git EAGAIN` 失败。用户只能重发，而重发成功了。现在，当错误链中带有 `EAGAIN`、`EMFILE`、`ENFILE` 或 `ENOMEM` 时，会话启动会自己重新开始：最多尝试三次，依次等待 1 秒和 3 秒，并且只在 Agent 还没有产生任何输出之前进行。同一次启动中，worktree setup 脚本绝不会运行两次：在脚本运行期间失败的启动不会重试；已经跑过脚本的启动会以 resume 的方式重试，从而跳过脚本。其他所有失败，包括认证和续接失败，第一次出现就结束这个回合。重试范围刻意保持很窄，只有在观察到某类失败重发就能解决时才会扩大。

## 问题

在这次改动之前，失败处理只有一种自动恢复：ACP 续接失败时回退到历史回放，其余所有启动错误都直接成为终态。扫描一周的 daemon 日志，共有 4 次启动失败，其中 3 次是临时性的环境状况，每次重发都成功了。两次 `EAGAIN` 都发生在任何持久工作开始之前。第三次是 worktree 就绪之后的锁释放超时，已由[文件锁持有者释放](../architecture/2026-10-16-file-lock-holder-release.zh.md)在其所有者处修复，不需要重试。[启动失败归属](../bug-fix/2026-10-16-session-start-failure-attribution.zh.md)提供了这里用来判断的步骤信息。

## 决策

- **什么会重试。** 只有在 `cause` 或 `AggregateError` 链中任何位置的 `code` 为 `EAGAIN`、`EMFILE`、`ENFILE` 或 `ENOMEM` 的错误。它们表示系统暂时用尽了进程、文件描述符或内存，资源释放后同样的请求可以成功。锁竞争超时不在其中：一个持有锁超过时限（worktree 是 120 秒）的持有者，不太可能在重试窗口内释放，再等一个完整时限也会逼近初始化预算。
- **怎样重试。** `sessionStartRetryMode` 读取失败启动所处的步骤：
  - `worktree-setup` 永不重试。只有 setup 脚本真正开始运行时才会上报这一步，之后的 `sandbox` 步骤以 resume 方式重试。因此，没有配置脚本的启动不会被误当成运行过脚本。
  - 恢复原样重试，因为它的 worktree 已经存在，setup 会被跳过。
  - 新会话如果在 setup 之前失败，原样重试。
  - 新会话如果在 setup 之后失败，以 `resume = true` 重试，这只会跳过 setup 脚本。worktree、分支和凭据与任何一次 resume 一样，重新创建或复用。
- **上限。** 最多三次尝试，延迟依次为 1 秒和 3 秒（`SESSION_START_RETRY_DELAYS_MS`），每次延迟在其后半段随机抖动。每次尝试都重新调用 `createSession`，它的去重条目也已移除，所以是全新的工作。
- **整体稳定性优先于单个回合的坚持重试。** 临时性系统失败通常影响整台机器。固定且同步的延迟会让所有失败的回合在同一时刻重试，恰好在机器资源耗尽时把 spawn 压力放大到三倍。所以延迟加了抖动，并且整个服务共享一个预算：所有会话合计每分钟最多重试 6 次，超出后第一次出错就直接失败。
- **清理确认后才重试。** 如果失败的尝试没能终止它的 agent 或释放凭据，`SessionManager` 会给原始错误打上标记（用 WeakSet 记录，错误对象本身不变），这次启动就不再重试。否则每次重试都会在泄漏的资源上再叠加一次新的尝试。初始化卡死看门狗仍然生效，发布 `Retrying after a temporary system error` 也算作进度。
- **Stop 与卡死。** 回合一旦被取消或判定为卡死，就不再重试。Stop 会中断等待，回合在等待结束后也会再检查一次是否已取消。
- **报告。** 每次重试都以 warn 级别记录当时的步骤和错误。最后一次失败的记录方式与没有重试时完全相同。

## 行为契约

| 问题     | 回答                                                                                         |
| -------- | -------------------------------------------------------------------------------------------- |
| 触发     | 在会话绑定到回合之前，`createSession` 以列表中的系统错误码失败。                             |
| 所有者   | 可见回合的执行 fiber 负责重试循环和等待。`SessionManager` 负责每次尝试及其清理。             |
| 取消     | Stop 或卡死会中断等待，之后不再开始新的尝试。                                                |
| 交接     | 只有在上一次尝试已经失败返回之后，才开始下一次。此时它创建的部分会话已被终止，凭据也已释放。 |
| 失败恢复 | 最后一次尝试的错误走普通的恢复失败或 prompt 前失败路径。                                     |

## 备选方案

- **对所有启动失败都重试一次。** 不采用。认证、缺少 Git 可执行文件、配置和续接错误重试后只会以同样方式失败，而盲目重试还会重复非幂等的工作。
- **在 `SessionManager` 内部重试。** 不采用。取消、卡死标记和 presence 发布都由回合负责，而且一次尝试不能在 Stop 之后还继续运行。
- **在资源紧张时做准入控制。** 对 `EAGAIN` 更完整的解决办法，是把同步 spawn 移出 daemon 主线程，并根据进程余量来决定是否接纳新的回合。那是另一项工作。这里的重试只覆盖资源一时紧张的情况。

## 限制

- 只覆盖会话启动。会话绑定之后的临时性失败（例如应用运行配置时）仍会让回合失败。
- 这个错误码集合的证据只有那两次 `EAGAIN`。其他几个错误码被纳入，是因为它们同样表示"系统暂时用尽某种资源"，而不是因为实际观察到过。
- 延迟是固定值，不会自适应。如果资源持续耗尽，三次尝试都会失败，回合报告最后一次的错误，与以前相同。

## 验证

`tests/session-execution-service.test.ts` 使用 fake timers 和真实的执行服务：

- 一次恢复先因 `EAGAIN` 失败两次、再因普通错误失败，共尝试三次，报告带步骤的普通错误。三次都是 `EAGAIN` 时也尝试三次，报告最后一次。
- 在 `worktree-setup` 期间失败的恢复或新会话只尝试一次。所有已有的非临时性 prompt 前失败用例也都恰好尝试一次。
- 在 `agent-start` 失败的新会话，重试时设置了 `resume`，而第一次尝试没有设置。
- 等待期间点击 Stop，不会有第二次尝试，也不会记录失败。

消融实验：去掉"切换为 resume"后，resume 用例失败。在 Stop 用例里，等待之后的那次取消检查与中断机制是重复的：有没有它，测试都能通过。

# 重做会话分享对话框与阅读端布局

Status: implemented
Translation: current

[English](2026-09-09-session-share-dialog-and-reader-layout.md)

## 摘要

分享对话框此前要求作者逐项审阅候选会话清单，然后再勾选一个把正上方告知内容重述一遍的同意框，而这
一切都挤在同一个滚动列中，操作按钮可能被挤出手机屏幕。对话框现在是固定头部 + 单一滚动主体 + 固定
操作行，子会话收敛为一个开关，单独的确认勾选也被移除——链接卡片上的告知就是通知。由于存储的授权仍是
一份显式 id 集合，该开关只能意味着「当前存在且已就绪的子会话」，文案也正是这么写的，而不是暗示后来的
会话会自动加入；代价是无法再表达部分子集。匿名阅读端去掉了常驻的「只读 · 实时更新」一行，改为一个
复用应用自身 `ThemeProvider`、默认值与存储 key 的外观控件，其限制是 `localStorage` 按 origin 隔离，
因此托管的分享域名无法继承在应用域名上做出的选择，而是记住自己的。

## 决策

### 对话框

`SessionShareDialogFrame` 不再作为单个盒子整体滚动。它渲染一个固定头部与一个滚动主体，而
`useKeyboardAwareScrollIntoView` 现在观察的是那个主体——真正滚动的元素——这正是该 hook 文档所述的契约。
`SessionShareManager` 把操作行放进该主体内的 `sticky bottom-0` 容器中。

组成控件是一个开关「包含子会话」，取代逐候选项的清单。作者只做一个决定，而不是审阅列表；而最常见的
情形——没有后代的会话——根本不渲染开关，留下的对话框只有链接、一句告知与操作。候选搜索框随它所过滤的
列表一起消失。

该开关是对同一份显式 id 集合的投影，服务端仍逐目标校验；wire 契约没有变化。打开它会选中根以及当前所有
符合条件的后代，上限为 `SESSION_SHARE_MAX_TARGETS`，触及上限时会显示一行说明。不符合条件的后代只是
不被选中，而辅助文案——「分享当前已就绪的 N 个子会话。之后新增的不会自动加入。」——承载了裸布尔值无法
表达的两个事实：未就绪的目标被排除，且该授权不会自行扩张。若某份授权仍列着一个此后变得不可用的目标，
开关会显示为打开状态，因此关闭开关正是修复它的方式。

单独的确认勾选框已移除，也不再是变更操作的闸门。链接卡片上的告知就是通知；它陈述了用户无法自行推断的
四件事——原始文档、历史与附件、后续更新，以及链接可被转发且非端到端加密。

对话框也不再列出包含本会话的其他授权。那一节回答的问题（「还有哪些链接能读到它？」）读者并不会意识到
它说的是**其他**会话的链接，而它在一个以「一个决定」为核心的对话框中花掉了一个标题、一行说明以及每份
授权一行。`sources` 数据仍会拉取——`copyableShareIds` 需要它——只是那一节没有了。

此前仅仅「置灰」的两处现在会自我解释：尚未同步完成的根会在操作区上方说明原因，而不是让「创建」毫无理由
地失效；「保存」只有在确有改动时才渲染，而不是永远灰着。

### 阅读端

头部是一个容器：第一行是工作区名称、访客标签与外观控件，然后是占满宽度的会话标题一行，再是目标导航。
把访客标签放到工作区那一行，正是 390px 宽的手机能显示可用标题而非省略号的原因。常驻的「只读 · 实时
更新」状态已移除——该界面不提供输入框、编辑、重试或审批能力，因此在构造上就是只读——状态区域现在只渲染
中断信息（暂停、加载中），为空时收起。

`ShareThemeToggle` 复用应用 `theme-provider` 中的 `nextCycledTheme` 与 `useTheme`，让阅读端获得与产品
相同的 浅色 → 深色 → 跟随系统 循环、相同的 `system` 默认值以及相同的 VS Code 主题应用方式。私有宿主
不再覆盖 `storageKey`，因此它使用应用的 key：从应用 origin 提供 `/s` 时，访客既有的选择现在会带过来。

## 考虑过的替代方案

在分享多个目标时隐藏 `h1`，本可消除标题与所选导航项之间的重复，但那会让构建页套件中既有的标题断言对着
一个 1px 元素通过，而不是读者真正能看到的东西。取而代之的是给 tab 设上限，使第二个目标总能露出一角，
让这一行读起来像导航。

仅供阅读端的明暗开关被否决：它会引入与应用竞争的第二个默认值与第二个缓存 key，而这正是此前
`lody-share-theme` 覆盖已经造成的问题。

单一开关取代了本记录最初记载的逐项选择，也取代了「作者逐个挑选目标」的第一阶段指引；相关文档已在同一
改动中更新。授权模型未被触碰——授权仍是显式 id 列表，每个目标仍单独校验，之后的会话仍不会自行加入。
被放弃的是表达部分子集的能力：想要部分而非全部后代的作者无法再表达，而把开关关掉再打开，会把一份遗留的
部分授权扩展为当前所有已就绪的目标。这个取舍是刻意接受的，以换取「一个决定」而非一份清单。

隐藏其他授权列表是第二个刻意留下的缺口，而且更尖锐。`docs/session-sharing.md` 中的 Q12 要求管理界面展示
每一个仍然有效的分享来源，正是为了避免把「撤销一条链接」误当成「本会话不再被任何地方分享」。该节消失后，
撤销此处所示链接的作者，仍可能通过一份以其他会话为根的授权被读到，而对话框里没有任何提示。该要求并未被
重新解释掉：它被记录为那份文档中的一个未决缺口，预期该节会以更清晰的形式回归，而不是就此缺席。

## 证据与限制

`session-share-manager.test.tsx` 覆盖该开关真正的义务：新链接无需额外确认即可创建且不会自我扩张；打开
开关会加入每个已就绪的后代并排除不可用的那个；关闭则回到仅根；无可包含内容时开关缺席，变更进行中时被
冻结；不可分享的根会被解释而不是仅仅置灰。管理员与授权过期的用例保留既有断言。私有 Web 宿主中的构建页
套件针对真实的 `dist-share` 产物新增两个测试——阅读端在未设置偏好时通过 `system` 解析，并把选定模式存在
应用的 `vite-ui-theme` key 下；以及该 origin 上缓存的值会覆盖系统偏好。全部十二个构建页测试通过。

布局是通过渲染截图评审的，而非阅读 CSS：管理器 story 在 1200px 与 390px、两种主题以及中文下，构建后的
阅读端在 1280px 与 390px、两种主题下。正是这次评审发现了窄屏手机上状态文本被自身按钮截断为「Link …」，
以及阅读端标题被访客标签挤压。开关取代清单之后，整个对话框在 390px 视口下无需滚动即可容纳。

限制：该入口是客户端渲染的 SPA，因此缓存的主题是在阅读端挂载时应用，而非首帧之前。跨 origin 共享主题不
可能，也未尝试——`localStorage` 按 origin 隔离，因此 `share.lody.ai` 与应用域名各自保留选择，这正是页内
控件存在的原因。截图使用合成 fixture；未使用任何已部署的后端。

# New chat page: the last seven days

Status: implemented
Translation: current

[中文](2026-10-16-home-week-tiles.zh.md)

## Abstract

The desktop new-chat page was a large title above a docked composer. It now keeps the composer at the bottom and puts five flat tiles in an uneven bento above it, aligned to the composer's own column: code shipped in the last seven days (a big tile with a daily bar chart and its change against the week before), the selected provider's plan usage with when each window resets, merged pull requests, the agents that did the work, and the most-used repository. The page shows only what is worth a glance: the first design had nine tiles and was cut after review. Session metadata and the machine's rate limits are already held by the client, so the tiles add no query or write; the one network request is the Codex reset forecast, which loads when the page mounts. Two later changes made it say less: the active streak is gone from the page, and a "now" with nothing happening says one quiet phrase instead of three zeros. Nothing here has been rendered or type-checked in the authoring sandbox.

## Decision and ownership

The [week model](../../../../packages/components/src/lib/home-week.ts) reads the signed-in user's root sessions on the local calendar. A session's lines changed and merged pull requests count on the day it was last active, and a session counts as started on its creation day. The stored metadata keeps only those two moments and the cumulative lines, so this is close, not exact: a long session's lines land on its last day, and a pull request counts when its session was active, not when GitHub merged it. The most-used repository is the one most sessions started in (its share is of all the week's sessions, so sessions without a repository lower it). A week with no sessions and no changed lines shows the same tiles at zero rather than hiding them, and so does the short moment before session metadata has loaded; the numbers then roll up once real data arrives. A [derived atom](../../../../packages/components/src/atoms/home-week.ts) reduces the session cache to the few rows the page needs and keeps its previous reference while they are unchanged, because a running agent rewrites its session metadata constantly.

The plan usage is the entry the composer's usage popover already reads: the landing resolves the selected provider's rate limits for the selected model ([`buildHomeWeekUsage`](../../../../packages/components/src/lib/home-week-usage.ts)) and shows its shortest window (the 5-hour one when there is one) with percent used and the provider's own reset time; the provider's other windows are not shown (a second meter beside it only crowded the tile, so the page merges them into the one that resets next). It is local data (the machine's rate limits). The tile says whose plan it is in an outlined selector listing every provider on the selected machine that reports one; it starts on the composer's provider and keeps the user's pick for the visit, and with a single provider the same outline appears without a menu. When no provider reports a plan (another agent, an API key) the wide tile shows the session count instead. A Codex reset that the forecast knows about, forecast or scheduled, has a tile of its own (titled as a Codex reset, with its chance and when it is expected) beside the usage; a small mark by its title says in a tooltip that the data is a third-party forecast from `codex-resets.com`, loaded when the page opens. Squeezing the forecast into the usage tile beside two meters truncated every label, and squeezing it beside one meter was still a cramped half tile, so it is a separate cell. A provider with no 5-hour limit shows whichever window is shortest, and without a forecast the usage tile spans both columns on its own. The forecast comes from the third-party `codex-resets.com`; the owner chose to load it when the page mounts, which reverses the earlier rule that nothing loads on mount, so [that rule](../../../../packages/components/src/components/codex-reset/AGENTS.md) now names this page as the third loading surface. The shared store still coalesces and revalidates, and a non-Codex provider makes no request.

The [tiles](../../../../packages/components/src/components/chat/home/week-bento.tsx) are a pure picture of their props; a [host](../../../../packages/components/src/components/chat/home/home-dashboard-host.tsx) supplies the atoms, the clock, the forecast and agent display names and marks. They are placed explicitly, never by auto-flow: code shipped is two columns by two rows on the left; beside it the repository takes the top right that the plan usage used to hold (the usage moved to the "now" board, below), with merged PRs under it, and the agents run across the bottom row. A three-row code tile beside a stack of three tiles was tried first and left an empty band above the wall, since its content is shorter than the stack; the right side now adds up to about its height. The bento keeps its four columns; see [the streak is gone](#the-streak-is-gone-and-a-quiet-now-2026-10-22). The chart in the code-shipped tile is an activity wall in the style of a contribution graph: fourteen weeks of plump rounded cells at the right of the tile, level with the figures (thirty weeks of sharp small squares read as full, and eighteen weeks beside the figures left too little width: the change pill and its comparison broke onto two lines each), a column per week and a row per workday from Monday to Friday (weekends are left off: seven rows read as full, and the two weekend rows were the sparsest; the streak tile still counts weekends), one small square per day, shaded in four solid blue steps (quarters of the busiest day) over a solid neutral gray for quiet days (a translucent first step over a translucent well read as the same colour, so blue now means only activity), the last week stopping at today. Seven solid bars across the tile (each about a hundred pixels wide with square corners) read as wide and rough on review; a short row of narrow bars then left the tile empty, and a wall of cells grouped by day read as seven bars made of cells. The owner asked for the contribution-graph form, so it returns despite the earlier rejection of a half-year calendar tile, now small and inside the tile rather than a tile of its own. What it shows is session activity, not lines: the metadata keeps lines only for the last two weeks, but every session's created and last-active day is held, so the page counts those events per day (`activity`, falling back to one per active day) and the wall carries a label saying so. Above the wall the number is the one large figure in the card (the title role; everything else is a step down), and its change against the week before is a soft pill with the comparison as quiet text beside it: green only when it is up, a neutral pill when it is down, since a quieter week is not a failure. The seven-day lines per day (`daily`) are still computed and tested but no longer drawn. The grid was also made smaller: rows are minimums that grow with their content, and the tile padding is 10px. They use the design system's recessed background with no shadow, medium-weight numbers and hairline charts, so they read as part of the page and the composer remains the one raised object. The only motion is the numbers rolling up from zero the first time the page is shown and the wall fading in; both are off under `prefers-reduced-motion`.

Two follow-ups after review of the empty-plan state. The session-count tile had been placed in one column only, leaving the top-right cell blank whenever no provider reported a plan and no reset was known; it now spans both columns like a usage tile with no reset beside it, as the placement comment always said. And the wall had only a static `title` on its container, so no day could be inspected: each cell now carries its local day and event count (`HomeWeekWallCell`, from `buildWall`), and pointing at a cell opens one shared tooltip anchored to that cell ("Fri, Oct 16, 2026 · 3 session events", or "No activity"). One tooltip is mounted for the whole wall rather than one per cell (about a hundred and fifty at the widest), and the `title` is removed so the browser's tooltip does not stack on it. It is pointer-only: the wall is a single labelled image for assistive technology and the cells are not focusable, and on touch the tip closes when the finger lifts.

This replaced three earlier attempts at the same page, all rejected on review: a year-long square-per-day activity chart (it duplicated the usage calendar in Settings and was not liked), a list of sessions to pick back up, and heavier Bento tiles with a large tinted hero, a donut, a gauge and a half-year calendar (too large and rough). The nine-tile revision that followed was regular and had too much on it: its start-hour chart with the night-owl share, the longest conversation, the busiest day and the stand-alone session count were removed as trivia. Cost is deliberately absent: it comes from the hosted backend, which the open-source desktop does not call. There is no time-range switch and no share action; those were declined.

## Now and the week

Review then asked what a coding-agent product's first screen is for: not how many lines were written, but which tasks are running, which need the person, which just finished, and which are worth picking back up. The page now has two boards under one line, and opens on **now**; the seven days above are the **week** board. This deliberately reverses the earlier rejection of "a list of sessions to pick back up": that list stood alone, while this one is sorted by what each session needs and sits beside what is running and what finished. The owner chose it with the retrospective kept one press away.

The [now model](../../../../packages/components/src/lib/home-now.ts) reads the signed-in user's open root sessions through a [derived atom](../../../../packages/components/src/atoms/home-now.ts): live state from presence (a child tab's running or waiting agent counts for its parent, as in the sidebar), unread output, and the latest pull request's draft state, CI rollup and readiness, all already synced. Each session lands in one list by its first reason: waiting on the person, running, CI failed, finished but unread, draft, ready to merge, open pull request, active in the last three days. A running agent is never listed as needing the person even when its CI is red, since it may be fixing exactly that. The lists are **needs you** (waiting, CI failed, drafts), **running**, **just finished** and **worth continuing**, each showing its first few with a count of the rest. A first version drew all four always and said so inside an empty one; on a quiet afternoon that was a wall of empty boxes, and under load it failed the other way: fixed caps hid the rest behind a count that led nowhere, and lists placed two to a row stretched a short list to the height of a long neighbour. [The layout](../../../../packages/components/src/lib/home-now-layout.ts) now spends the board's height in two steps. A row budget (twelve in all): every list with something gets one row, then the rest goes by priority up to each list's cap (six, four, three, three), so when it is busy the lower lists give way first and what needs the person never does. Then two columns kept level: the usage starts the right one and each list goes, in priority order, to whichever column is shorter so far, so tiles are as tall as what they show. A list with nothing is not drawn, and a lone list takes the whole board. Whatever a list does not show is one press away: "Show all" opens the whole list in the board's own frame (see [fitting the window](#fitting-the-window-2026-10-18)). With nothing going on at all, one calm "All quiet" tile stays on the left while usage and its reset stay on the right. A row opens its session through the sidebar's route. The plan usage lives on this board, because running out is something to act on; its Codex reset forecast is requested only while this board is shown.

[The line](../../../../packages/components/src/components/chat/home/home-dashboard.tsx) has one segment per board and a control at its end. The other segment swaps the boards; the open segment, or the control, folds the board into the line, where both segments show their summaries (how many need you, run and finished; seven pebbles and the line count) and the line centres under the heading. The control unfolds the board that was open last. An earlier round of this review made every tile fold separately from a dog-eared corner into a shelf of chips; once the page had two boards that was more interaction than anyone needed, and it was replaced by this single switch. The move is one quiet View Transition. A first version flew the open board into its segment's summary as a shared element; on review it read as flashy, so nothing is scaled or flown any more. A second version still flickered: the old board finished fading before the new one was in, leaving a see-through gap, and the browser cross-faded the whole page. The transition is now typed (`home-board`) so its rules touch nothing else, the page does not cross-fade, and only three things move: the board's area eases to its new height while the two boards cross-fade in full overlap with the browser's additive blend (no dip between them), the open segment's pill glides to the other segment, and the heading glides as the stage re-centres, on one curve in about a quarter second. There is no per-frame script, and under reduced motion (or without the API) the change is simply made. The open board is a device-local view preference under `lody:homeBoard` (`none` when folded), not on the cache-clear list.

Tile text was also too faint: labels, units, notes and the comparison used `tertiaryLabel`, about 2.6:1 on the tile's well in light mode. They now use `secondaryLabel` (about 4.6:1) and the percent used takes `label`. The wall's shades were reworked at the same time (see the wall above); the chip's seven pebbles use the same shades.

The heading and the boards are centred in the stage above the docked composer, not on the whole
page (`web-chat-landing-screen.tsx`): the band between the window's top edge and the composer is
its own box, so the group reads a touch above the page's middle. An earlier cut split the stage's
free space 3:2, and then 5:3, above and below the group, and (folded) measured the composer to
re-centre the group on the whole page; on review that read too low once the boards sat under the
heading, and both were replaced by an even split of the stage itself (see
[vertical placement](#vertical-placement-2026-10-19)).

## Transition layering correction (2026-10-18)

Frame-by-frame inspection and a Chromium reproduction showed that the independently named pill covered the switch's text during a board change. The pill's DOM `z-index: -1` does not order its extracted View Transition snapshot below text left in the root snapshot. Meanwhile the unnamed switch jumped to the new vertical position as the stage re-centred, leaving the pill to travel diagonally after it.

The segments, their persistent labels and the fold control now have separate snapshot names. All geometry follows the board and heading's 240ms curve. Explicit overlay ordering puts the pill below the segments and the labels above both. Segment snapshots cross-fade their changing summaries at natural size and clip to their animated width; labels retain their natural size and stay visible while their position moves. The board snapshot group does not clip: switching drifts each picture 20–28px outside that group, and clipping it visibly sheared the leading card edge until the picture arrived. Keeping the browser transition preserves the existing board cross-fade and height easing without adding an animation loop or replacing the layout system.

## Pill rides the fold, rows come with the frame (2026-10-18)

Reviewing the motion again surfaced two readings that the first cut got wrong. Unfolding the board, the pill appeared settled at the open segment's place from the first frame while the board, segments and heading were still travelling, because the pill is only in the DOM once the board is open: its `home-pill` snapshot had no old side, so the browser faded the new bitmap in place instead of moving anything. Folding, the other cut: the pill faded away wherever the open board had been rather than leaving with its segment. Fixing both is one rule: the pill is named only while it continues across a transition — a board change has it on both sides, so its snapshot glides between the segments as before — and on unfold or fold it is unnamed, riding the segment's own snapshot, which already follows the board's geometry. Folding additionally takes the name off the live DOM before the old capture (`show(null)` in `home-dashboard.tsx`), because the previous render had named it and its deletion alone cannot stop the old side from snapshotting.

The same review read the "Show all" opening as draggy: the rows a tile had hidden and the way back waited 140ms plus 18ms per row after the frame's spring had begun, so the opened list sat visibly empty for a fifth of a second. The late rows now enter at 30ms plus 14ms per row over 200ms, which lands with the frame instead of after it; the few-rows-at-a-time stagger itself stays.

The [landing story](../../../../packages/components/src/stories/HomeDashboard.stories.tsx) uses the real stage, so changes in board height exercise vertical re-centring. The [browser regression suite](../../../../packages/components/tests/e2e/home-dashboard.spec.ts) pauses animations at explicit times and checks screenshot pixels for label ink, as DOM visibility alone cannot detect a snapshot covering text. It also checks the initial label position, both switch directions, folding/unfolding, interruption and reduced motion. Four browser tests passed in local Chrome at 1180px and 720px; the existing dashboard and week component suites passed all 21 tests. Package type checking remains blocked by existing errors in `loro-sidebar.tsx` and `home-week-usage.ts`, outside this correction.

## Fitting the window (2026-10-18)

Review showed the "now" board breaking under load in a short window: with every list long and "Show all" pressed on worth continuing, that tile grew by ten rows in place, the right column ran about nine rows past the left, the left ended in an empty band, and the board pushed the heading against the top of the window while its last rows slid under the composer. Three things caused it, and all three changed.

- **The budget follows the window without filling it.** The landing stage hands what sits in its group the stage and the group (`LandingStageContext`, [`landing-stage.ts`](../../../../packages/components/src/components/chat/landing-stage.ts)). The dashboard's room is the stage's height less the rest of the group and 24px of breathing space; this difference does not depend on the dashboard's own height, so fitting settles at once rather than chasing its own measurement. The line and the gap under it are a fixed 34px, so the board's room is the same folded or open (measuring the board itself would give a folded board the gap and fold it again). The room becomes rows a column may hold (a row is 1.9em of the footnote size and 1px; a tile's title is about two rows) and [`layoutHomeNow`](../../../../packages/components/src/lib/home-now-layout.ts) shrinks its budget until the taller column fits, down to one row per list, lower lists first. Once the minimum busy layout fits, a compact stage keeps up to two additional rows of room unused instead of turning every spare pixel into another session row; twelve rows still hold the usage tile and one row from every non-empty list, so this reserve never makes that worst-case layout fold. Taller stages still reach the same natural budget. The row arithmetic is close, not exact, so after layout a board still measured taller than its room takes back one more row at a time for that room.
- **Columns ended where they happened to.** After placing, the shorter column now shows more of its own lists, row by row from its lowest list, until it reaches the taller one or has nothing left. The space is spent on real rows, not by stretching a tile, so the earlier rejection of a short list stretched to a long neighbour's height still holds. A list's last hidden row costs nothing, since its "Show all" line goes with it. The levelling may exceed a list's cap; caps only order who gives way.
- **"Show all" grew a tile in place.** It now opens the whole list over the board, in the board's own box, its rows running down the board's two columns (one for a tile that spanned the board), scrolling inside. Nothing around it moves, and no column can outgrow the other. A control at the head's end, Escape, or opening a session returns to the board, and focus returns to the "Show all" that opened it.

The motion went through three rounds on review. Cross-fading the board into the list (the boards' View Transition) read as strange: two full pictures ghosting through each other, with no link to what was pressed. A sideways slide was started and dropped for the owner's direction: the pressed tile grows and the rest step back, with a little depth. A fixed 280ms curve then read as too fast, after the cross-fade had read as draggy. The cause was not the number: everything moved at once at one speed, a large area change took as long as a small one, and the way back was the opening reversed, so an ease-out became a slow start. [`focus-motion.ts`](../../../../packages/components/src/components/chat/home/focus-motion.ts) now choreographs it on real elements with the Web Animations API (no snapshots, so the list is live while it moves and a press midway turns it around from where it is). Opening: the rest of the board scales toward the pressed tile and dims out while the list's frame grows from the tile's clip to the board's, its content travelling from the tile's corner so the first frame is the tile itself; nothing is scaled, so no text stretches. The rows the tile hid and the way back rise in after the frame is mostly open, eight rows one after another, so it reads as more of the same list coming out. Closing is its own motion: the list scrolls home, the extra rows go first, the frame lands in its tile without overshoot, and the board comes forward as it lands.

A first cut of that motion ended visibly off and made the whole board flicker. The frame was a clipped full-board picture translated into place, so at the tile's size it was not the tile: its count had faded out, it had no "Show all", its balanced columns could put a different row first, and the board's step back skewed the measured client rect. And the motion was cancelled before React removed the frame, so the unclipped frame painted for a frame over the board. Now both ends of the motion are the tile itself. The frame's own box (its insets) moves between the tile's and the board's, so its head (title, the way back, then the count in the tile's corner) lays out at every size; its rows hold the board's width while it moves, laid in an explicit grid whose first column holds at least the tile's rows at exactly a half-board tile's width (an 18px column gap: two tiles' padding and the board's 6px gap, less the 4px the rows overhang each side), so they never reflow; a stand-in for "Show all" sits under the tile's last row and is there only at the tile's size; the tile is measured by offsets, which ignore the board's transform, and measured again when closing, after the list scrolls back to its top. Settling removes the frame and shows the tile in one synchronous commit, and only then lets the motion go. Timing is springs written as CSS `linear()` easings (open: response 0.5s, damping 0.86, about 95% there at 300ms; close: response 0.4s, critically damped), falling back to an ease-out where `linear()` is unsupported. Storybook's `ShowAllMotion` exposes the spring constants, the depth and a slow-motion factor so the owner can tune them by eye; under reduced motion it simply changes.

When even one row per list does not fit, the board shows folded into the line (`data-auto-folded`) without changing the remembered board, and unfolds itself when the window grows. Opening it from the line in that state shows it anyway and lets the stage scroll, since the person asked for it. Without a landing stage (stories, tests) nothing limits the board. The week board is a fixed picture and is not fitted.

The pure suite covers the shrinking budget, the levelled columns, the fit report and that every column stays within its room for all list sizes. The jsdom suite covers opening and closing a whole list (back, Escape, focus return, opening a row), fitting a reported stage, the compact-stage reserve and the automatic fold with its override. Storybook has a 620px and a 380px landing. The compact 620px landing was checked in Chromium after the reserve was added; the two-column whole-list motion remains outside that check.

## Vertical placement (2026-10-19)

Review read the greeting group as too low. Two things had put it there: the expanded stage split
its free space 5:3 (documented as 3:2) above and below, and, with the board folded, the screen
measured the docked composer and padded the stage by it so the small group centred on the whole
page. Both were dropped. The group now centres in the stage — the band above the composer — with
an even split, so the heading and boards sit a little above the page's geometric middle in both
the folded and open states, and the composer's height is no longer measured at all (the
`ambientExpanded` prop went with it). The trade-off is that folding no longer holds the group at
the exact spot it had when open; the heading's View Transition still glides the small move. The
change is a layout constant, not exercised in a real window here: the exact reading at tall and
short windows, and dark mode, remain visually unverified.

## The tile opens too (2026-10-19)

Review asked why a press on a "now" tile did nothing while its "Show all" worked: the card is
the thing the eye sees first. A list tile now opens its whole list too, the same `open` path as
"Show all", while it hides rows (`total > shown`); with everything shown it stays inert, so the
openable state is exactly the state the toggle line exists in. A pressed row still opens the
session, judged at the tile by the nearest `data-session` or `data-show-all` ancestor of the
click target, so no nested control is swallowed and no second "Show all" is mounted; the
keyboard path and the focus return remain the toggle button. The affordance is the pointer
cursor only, chosen over a tile-level hover fill because the rows' own hover already answers a
point and a second hover layer read as noisy. `Tile` in `tiles.tsx` gained an optional `onPress`
plus `pressProps` for the cursor; the week board's tiles take neither. jsdom coverage adds
the tile press opening, a row press not expanding, and a fully-shown tile staying shut. In a
real window the press-over-a-row target judgement and the cursor affordance remain visually
unreviewed.

## Controls stay put (2026-10-20)

Review asked for fewer moving targets: switching boards moved the switch, a tile's "Show all" sat wherever its rows ended, and its way back was a separate icon in another corner. The rule now is that what the pointer presses does not move with the content; content changes only inside fixed frames.

- **The line.** It is one phrase centred under the heading, open or folded. Both segments always carry their summaries (the open one too, like a tab's badge), and the "now" summary shows its three counts with zeros faded; see [the streak is gone](#the-streak-is-gone-and-a-quiet-now-2026-10-22) for the quiet case, which replaces the three zeros with one phrase. The fold control always keeps its place after the segments and remains visible. A brief trial hid its ink until the dashboard was hovered, but the owner preferred the persistent affordance and reverted it.
- **The slot.** An open board sits in a slot of the board's own height: it is measured, not reserved, so an expanded board is exactly as tall as what it shows. The slot used to reserve the tallest "now" board any lists can make (`HOME_NOW_TALLEST_COLUMN`, seventeen rows), and that reserved space was empty under a board showing less — a band of nothing between the tiles and the composer, with the heading pushed up by it. The rows are still capped by the room the stage has (`useLandingRoom`), so the board never grows past what the window can hold, and the hang (`hangPx` in `home-dashboard.tsx`) still takes the board's height back with a negative bottom margin so the group does not travel as far. A first cut kept the slot while folded as well; on a real window that left a band of nothing under a one-line page with the control stranded at the far edge, and keeping none made folding re-centre the group by half the slot (about 190px at the default size), which read as far too much travel; keeping half of it only halved that. Hanging all of the open board below the folded line, so that nothing but the board moved, sat it too low against the composer. Now most of an open board (`HOME_BOARD_HANG_SHARE`, 0.7) hangs below what the stage centres, its height taken back with a negative bottom margin (`hangPx` in `home-dashboard.tsx`; `useLandingRoom` adds that margin back when it measures), and the rest lifts the heading and the line a short way, about 65px at the default size. That share alone still sank the board in a window of middling height: it hung until the group's bottom met the breathing space, leaving every spare pixel above the heading (about 340px above against 110px under the board in the owner's screenshot). The hang is now also capped by balance (`HOME_BOARD_MAX_TILT`): the space above the heading is at most 1.5 times the space under the board. In a tall window the share still decides and the heading lifts little (about 70px on a 2000px stage at the default size); in a middling one the board stays nearly centred and the heading travels further (about 200px on a 700px stage). Balance and travel pull against each other here; balance wins where they conflict. Folded, the heading and the line sit a little above the stage's middle (`HOME_FOLDED_LIFT`, 3% of the stage's free space, about 17px on a 700px stage): space twice that is kept, unseen, under the folded line as a positive bottom margin, the same mechanism the hang uses, which also shortens the travel on opening. With the folded page lifted, a 1.5 limit still carried the open heading well above it, so the limit is now 2.5 (`HOME_BOARD_MAX_TILT`): the open board sits a little lower, and opening travels less. The hang is also never more than leaves the open heading where the folded one is: in a tall window the folded lift would otherwise exceed what the board lifts, and opening would move the heading down. There opening now moves nothing but the board, or nearly. Both the lift (from 6%) and the limit (from 2) were then eased a step, the owner finding both states a touch high; at a 1000px stage the heading lifts about 95px on opening, at 700px about 165px. The folded page stays centred as on 2026-10-19; raising the whole stage instead (a 3:4 split) was the wrong reading and was reverted. The cost is some space under a short "now" board in a tall window.
- **Fixed columns.** Each list has one place: needs you over just finished on the left, the usage over running over worth continuing on the right. The two longest lists sit in different columns, so a busy board spends both. A list with nothing is its title with a quiet zero instead of disappearing, and the "All quiet" tile is gone, since it changed the whole board's shape at the first running agent. (That card is back; see [the quiet card is back](#the-quiet-card-is-back-2026-10-22).) The row budget, fitting and level bottoms are unchanged; only "whichever column is shorter" was removed, because it moved tiles between columns as counts changed.
- **"Show all" where the list ends.** A tile that hides rows ends with a row-wide "Show all 12": a chevron in the place a row has its mark and the quiet label colour, so it reads as an action. Three earlier versions were each turned down: a small caption under the rows was easy to miss; the count in the head's corner ("12 ⤢", which also rode out to be the way back) was far from where the eye finishes reading; and a fading preview of the next session with "+N" read as a session row that would open that session. The way back is "Show less" at the foot of the opened list, where "Show all" was pressed; Escape, opening a session and pressing the tile still work. An opened list covers only its own column, growing from its tile to the column's height while the rest of that column steps back; the other column stays as it was and in reach, and the rows run down one column at the tile's width, so they never reflow (opening over both columns moved the eye across the whole board). The list scrolls in the app's own `ScrollArea` with its overlay scrollbar, hidden while the frame moves; since the frame keeps its column's width, the motion no longer holds the rows' width or touches the scroller's overflow. Closing is now one motion: the frame lands and the column comes forward at once, and the rows the tile does not show are clipped by the shrinking frame and fade over its first third; letting them leave first, with the frame and the board following on 40ms and 100ms delays, read as things leaving one after another and the pace dropping.

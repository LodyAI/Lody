# E2EE 共享成员的派生工作

Status: implemented
Translation: current

[English](2026-10-31-e2ee-shared-member-derivation.md)

## 摘要

在加密机器上，共享成员的轮次可以驱动 MCP 工作：子会话、chat、Role、续跑和 agent 控制。这些派生输入由机器签名，
看起来像所有者本人的工作，以前因此绕过了共享与项目检查。所以 #2149 改为失败封闭。2026-10-31 owner 决定恢复这项
能力，并复用签名原件链，不新增令牌。现在派生输入在已签名的行内记录来源；在同一台机器上，它只能以来源成员的权限
启动。共享成员的跨机器派生尚未决定，因此失败封闭。尚未在真实后端或设备上运行。

## 决定

以下各点由 owner 于 2026-10-31 拍板，经 E2EE 总调度转达。

- **证明。** 派生输入在其历史行里携带 `derivedFrom: { sessionId, userTurnId }`。签名原件校验覆盖该字段（与
  `scheduleRun` 相同），所以事后改写或删除它，原件就无法通过验证。
  - 只有这台机器能写出这种输入。
  - 启动时，机器自己验证来源行。根来源必须是人类本人签名的轮次：不是派生的、不是定时任务、也不是机器写的。
- **授权。** 派生输入按来源成员授权：该成员当前的权限、所有者的共享策略，以及该输入涉及的每个项目。沿用现有
  "已知撤销即拒、未知不超过 15 分钟"的新鲜度闸门。
- **期限。**
  - 只能在当前驱动轮次活跃期间创建。写入时，daemon 先检查活跃的运行时，再验证已签名的来源。
  - 自 owner 2026-11-10 决定起，派生输入没有开始期限，只剩"来源轮次进行中"和每个来源的数量上限。
    机器在同一次提交里对派生输入（含 `derivedFrom`）签名（[签名的执行意图](../../implemented/architecture/2026-11-10-e2ee-signed-execution-intent.zh.md)）。
- **深度与数量。**
  - 多级委派直接继承同一个根来源。已领取的后续轮次提供根请求者身份，用于继续委派和 agent 控制；中间机器签名不能替代人的权限。
  - 共享成员的所有后续轮次共用每个人类根来源的 20 次持久启动额度，与单次 Agent 批量的最大目标数（20）一致。写入预约在根权限和目标校验通过后进行，按目标机器／输入 ID 去重；重试复用名额，拒绝目标不扣额度。Owner 启动不占用这项配额。
- **跨机器。** owner 于 2026-10-31 决定第一版不做跨机器派生。指向其他机器的成员派生在写入时被拒
  （`e2ee_derivation_cross_machine_unsupported`）。扩展点是 `decideEncryptedDerivation`。
- **agent 控制。** 成员轮次发起的 iOS 控制，需要该成员对本轮次所涉项目拥有权限。预览归属仅限所有者。
- **所有者工作。** 人类签名的同机委派保留根来源并重验签名者，不限次数，也可 steer 正在运行的轮次。已验证主体与来源信息分别传递，避免根引用静默禁用 Owner steer。跨机 Owner 委派在发送侧重验根权限，再使用原有机器签名路径，不携带仅本机可验的 `derivedFrom`；目标验证机器签名及本机当前授权。收到的机器签名 Owner 输入，只有其签名设备当前仍被授权为 Owner，才可继续本机／跨机委派或恢复 Operation；它不附带人类根引用，由接收机器自己签名下一跳。机器签名输入仍不可作为 `derivedFrom` 根。机器自身输入保留独立授权。Owner 驱动轮次结束后的操作恢复仍可使用。

## 共享成员跨机器派生（未来）

这是 owner 倾向的方向，不是已批准的设计，留待后续 Spec 讨论。

- agent 想在另一台机器上派生工作时，向发起用户发出审批请求。
- 用户在自己的个人设备上批准后，由该设备完成签名。签名绑定工作区、genesis、来源轮次、目标机器、目标操作和期限。
- 目标机器验证该签名，并按"发起成员权限 ∩ 目标机器共享策略 ∩ 项目范围"授权。
- 目标机器不需要读取来源会话。

## 备选方案

- _由成员客户端预签的委托令牌。_ owner 已否决。这是新的线格式，桌面、Web、移动端都要改。
- _从 `author` 或其他未签名字段取来源。_ 否决。成员可以改写这些字段而不影响签名校验。
- _在 MCP 与 Operation 各层之间传递标志。_ 否决。任何一层丢掉标志，都会悄悄得到所有者权限。改为在写入行的地方
  直接判定。

## 后果与局限

- 根轮次配额凭据保存在控制 SQLite 库，按 genesis、工作区、根会话和根轮次隔离。控制库从 v1 扩展到 v2，保留请求退役证据；主 journal 仍是 schema 3。独占事务先提交去重配额预约，再领取启动。崩溃或启动失败可能占用额度，但不会返还额度；同一请求重试复用凭据，执行日志重置也保留凭据。
- 写入分类、请求者解析和启动准入都通过既有账本与共享策略 gate 重验根签名者。已知成员移除、设备撤销或共享关闭会拒绝新的同机派生与尚未启动的轮次。成员所有层级跨重启共享 20 次预约；真实 SQLite 与签名账本测试覆盖这些边界。
- 控制库 schema v2 需要新版 runtime，旧二进制会拒绝打开。
- RPC 分派快路径不再验证这台机器自己写的输入，因为只有已签名的行能携带 `derivedFrom`。
- 签名账本与 SQLite 测试覆盖 Owner 跨机验签和启动、22 次 Owner 派生、成员配额／重试隔离和 steer 策略。成员跨机派生、托管后端检查和真机行为仍未验证。

# Fork Virtua 并按 key 管理行

Status: implemented
Translation: current

[English](2026-09-24-virtua-keyed-fork.md)

## 摘要

在长对话中向上滚动时，读者正在看的内容会一次移动几百像素。对话会在读者接近时加载较早的回合，
于是视口上方的一个占位行会变成多行；而 Virtua 以下标数组保存条目尺寸，只补偿列表开头的插入。
Lody 现在内置 Virtua 0.52.7 的 fork（`packages/virtua`，`@lody/virtua`）：`keyed` 列表按 React key
保存尺寸、按 key 恢复快照，并在列表变化时保持视口起点的条目不动。在同一个 100 行对话和同样的输入下，
可见跳动从 1,370px（本分支早期）和 294–318px（中间修复之后）降为零；代价是 fork 需要手动与上游同步。

## 问题

测量方式（逐帧行位置、带调用方的滚动写入、行尺寸变化、真实滚轮输入、本地生产构建；详见
[跟随模式 note](2026-09-23-conversation-follow-modes.zh.md)）：

- 读者上方的占位行展开：314px 和 902px 的跳动。`shift={false}` 保持像素偏移，所以读者眼前换成了别的行；
  尺寸按下标存储时，之后的每个尺寸都对应到错误的行，直到重新测量。
- 插入到视口内的行在插入后才测量（先估计尺寸，再真实尺寸）：−88/+128px 成对出现。
- 0.49 中同一帧内的多次补偿会互相覆盖（上游 0.52 改用 `scrollBy` 修复，上游 #898）。

上游 0.52.7 仍按下标保存尺寸（`fill` 只在末尾或开头追加），`shift` 也只覆盖列表开头。

## 决策

从 `0.52.7` 标签引入 `src/core` 和 `src/react`，并加入以下改动（均以 `Lody:` 标记）：

- `Virtualizer` 的 `keyed` 属性：条目以 React key 标识。
- 列表布局按 key 记住所有测量过的尺寸（包括已不在列表中的 key），key 变化时重新映射；
  `CacheSnapshot` 带上 key，不论条目数量都按 key 恢复。
- store 动作 `ACTION_ITEMS_KEYS_CHANGE`：变化前记录第一个可见条目（以及之后的可见条目，以防它被移除）
  和视口在其中的偏移，变化后在绘制前施加把它放回原处的跳转。

对话列表启用 `keyed`，两个非消息行使用固定 key。本分支早先在 hook 层加入的阅读锚点已删除，
列表变化时只有 Virtua 一个写入者。快照缓存在行数变化后仍保留 keyed 快照。

## 备选方案

- 继续给发布版打补丁：按下标的缓存是结构性问题，不是改一行能解决的。
- TanStack Virtual（按 key 的尺寸缓存、可定制补偿）：迁移量大（选区 `keepMounted`、快照缓存、大纲计算），
  而且同样不会为列表中间的插入做锚定。
- 每个回合一个 Virtua 条目：插入问题消失，但长回合会变成一个巨大条目，违背按部分拆行的设计。
- 在 sticky-scroll hook 里加第二个滚动写入者（先尝试过）：程序跳转的 scroll 事件尚未到达时，它可能撤销该跳转。

## 验证与限制

- `@lody/virtua`：上游 core 测试（237 个）加上 keyed 的布局、store 和 React 测试；去掉 `keyed` 时
  React 测试失败（视口停在 500 而不是 700）。
- 组件测试全部通过。本地生产构建上，两次在 100 行对话中向上滚动以及底部附近的来回滚动都没有可见跳动；
  切走再切回时，同一行恢复到同样的位置。
- 未引入上游依赖真实 sleep 的 jsdom 快照测试和浏览器测试；`src/` 不参与仓库 lint，以便贴近上游。
- 与上游同步需手动进行（`packages/virtua/README.md`）。
- 从未测量过的行仍以估计尺寸开始；只有本次会话中见过的行才会以真实尺寸开始。尺寸只在页面生命周期内保存在内存中。

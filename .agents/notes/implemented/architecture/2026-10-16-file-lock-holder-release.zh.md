# 文件锁释放变慢时，持有者保留自己的结果

Status: implemented
Translation: current

[English](2026-10-16-file-lock-holder-release.md)

## 摘要

在高负载的 daemon 上，会话启动会在 worktree 已经就绪之后失败。原因是仓库级文件锁连续两次各等 5 秒，都没能确认锁文件和临时目录已经删除，而这个清理失败覆盖了 body 已经成功的结果。锁服务本来就会保留未完成的删除，并把后继者挡在外面直到删除完成，所以让持有者失败并没有带来额外的安全性。现在持有者最多只等一次 5 秒，并保留 body 的结果。缓慢或失败的删除继续由锁服务持有：下一个本地持有者在自己的获取时限内等待它完成，服务 dispose 时仍会报告没解决的删除。只有锁文件已被另一代替换时，持有者才会失败，错误为 `LockOwnershipLost`。一次很小的 unlink 为什么会超过 5 秒，目前仍未查明。

## 问题

2026-10-16，同一台 Linux daemon 上有三个 turn 以这种方式失败。每份日志都是先在 `createWorktree` 内部记录 `Worktree ready` 或 `Worktree already exists`，然后 14 到 19 秒没有任何输出，接着 `SessionManager.createSessionInner` 内的 `squashFileLockFailure` 抛出 `FileLockCleanupFailed`。新会话报的是 `turn_pre_prompt_failed`，恢复中的会话报的是 `session_restore_failed`。每次重发同一条消息都成功了。当时运行的构建早于[准备清理诊断](../bug-fix/2026-10-16-preparation-cleanup-diagnostics.zh.md)，所以用户看到的失败原因是空的。那份 note 在准备态回收中记录了同样的"两次等待"特征，但把这里要回答的问题留作待决。

旧契约把释放放在 body 的 finalizer 里执行。锁文件和临时目录各有一个清理租约，各自最多等 5 秒。超时会变成 `LockReleaseFailed`，`acquireUseRelease` 再把它和 body 的退出结果合并，于是成功的 body 变成失败，返回值被丢弃。三次失败里有两次正好碰上日志记录的 5 到 7 秒事件循环卡顿。在这样的主机上，5 秒定时器可能先于已经完成的 unlink 回调触发，但日志无法证明是这个顺序。

这个失败并没有保护任何东西：原始的删除操作仍在租约下继续执行，服务登记表保留着它，下一个本地持有者在运行 body 之前会先等它完成。其他进程看到的是一个属于存活进程的锁，会自行退避。

## 决策

- **持有者。** body 结束后，持有者在同一个共享的 5 秒上限内等待锁文件和临时目录的删除。上限用完时如果还有删除没完成，持有者只查询一次当前状态，不再安排新的定时器。超时或失败的删除继续登记在服务里。持有者原样返回 body 的退出结果。
- **后继者。** 本地后继者在自己的获取时限内（即 `timeout`，从本地准入时开始计时）等待所有被保留的删除完成，不再使用单独的 5 秒上限。同一个时限接着也覆盖跨进程竞争。已经确定失败的删除会在 body 运行前重试一次。只有当删除到时限时仍未完成、或者重试再次失败时，后继者才会以 `LockReleaseFailed` 失败。
- **一次卡住的删除只等一次。** 这个时限记在删除尝试上，而不是记在每个后继者上。否则在 FIFO 准入下，一次卡住的 unlink 会让队列里的每个持有者（也就是同一仓库的所有会话启动）依次各等满一个时限，还会把失败归到不相关的会话头上。只要已经有一个后继者为一次仍未完成的删除等满了整个时限，之后的后继者就只查询一次状态并立即失败，直到开始新的删除尝试。已经确定失败的删除不算卡住，仍可由下一个持有者重试。
- **所有权丢失。** 释放时先读取锁文件，再决定是否删除。如果锁已经被另一代替换，那就没有属于我们的东西需要删除。持有者以 `LockOwnershipLost` 失败，因为它的 body 并不是在互斥条件下运行的。这个租约随即结束，后续调用方会正常地与新持有者竞争，而不是被一个永远不可能成功的重试挡住。以前在替换者消失之前，后续每个调用方都会以 `LockReleaseFailed` 失败。
- **Dispose。** 保持不变：仍以 5 秒上限等待被保留的租约，然后以携带恢复租约的 `FileLockCleanupFailed` 失败。
- **Legacy 调用方。** worktree manager 原样抛出 `LockOwnershipLost`，并像对待 `LockReleaseFailed` 那样，不让它被 fallback 分支吞掉。

## 行为契约

| 问题     | 回答                                                                                                                     |
| -------- | ------------------------------------------------------------------------------------------------------------------------ |
| 触发     | 持有锁期间，body 结束、失败或被中断。                                                                                    |
| 所有者   | `FileLocks` 服务实例通过租约和登记表持有每个原始删除操作。持有者只拥有自己那次有界等待。                                 |
| 取消     | 中断持有者只会结束它的等待。被屏蔽中断的原始删除仍在租约下继续执行。                                                     |
| 交接     | 本地后继者要等所有被保留的删除完成之后才运行 body。其他进程要等锁文件消失，或者按现有的 stale 规则接管，之后才能获取锁。 |
| 失败恢复 | 由下一个本地持有者重试已确定失败的删除。Dispose 时报告剩余的删除，并附上恢复租约。没有后台重试机制。                     |

## 备选方案

- **仍让持有者失败，然后重试整个会话启动。** 不作为修复方案采用。工作本身已经成功了，而且其中一次失败的尝试为了等仓库锁和创建 worktree 已经花了 3 分钟。重试启动应该留给真正的临时性错误。
- **持有者完全不等待释放。** 不采用。正常的快速返回会让锁文件和临时目录短暂残留，短生命周期的命令可能在 unlink 完成前就退出。有界等待让常见情况保持干净，只是把慢的情况延后处理。
- **调大 5 秒上限。** 不采用。这只是挪动了阈值，并没有改变失败由谁负责。卡顿时间足够长时，已经完成的操作仍然会失败。

## 取舍与限制

- 持有者返回时锁文件可能仍然存在，但这只发生在删除超过上限的情况下。本地后继者会等待它，其他进程会退避。如果进程恰好在这个窗口内退出，会留下一个属于已死亡进程的锁文件，由现有的回收机制清理。
- 被保留的失败会在下一个持有者或 dispose 时才暴露，而不是在原始调用处。持续存在的权限错误仍会让下一个持有者失败，直到问题修复，这一点和以前相同。没有后台机制去重试它。
- `LocalWorktreePreparation` 在本地项目的准备态已经发布之后，如果临时目录清理超时，仍然会让操作失败。这是同一类问题，但属于另一个所有者，这次没有改动。
- 这次改动既没有找出、也没有消除删除变慢的原因。目前首要的推测是 daemon 主线程上的同步工作导致事件循环被饿死。

## 验证

`packages/shared/tests/file-lock.test.ts`（29 个用例）使用真实文件、注入的时钟和显式的就绪信号：

- 锁文件和临时目录的删除都卡住时，持有者在一次 5 秒上限后返回自己的值。排队的后继者要等原始 unlink 在它自己的时限内完成后才运行。
- 被中断的持有者返回中断。如果 unlink 在后继者的时限到达时仍未完成，后继者以携带原始租约的 `LockReleaseFailed` 失败，而且这个租约永远不会删除后来那一代的锁文件。
- 释放失败时持有者保留 body 的值，下一个持有者在运行 body 之前失败，允许删除之后就恢复正常。临时目录的失败表现相同。
- 失败的 body 以它自己的错误到达原生和 Legacy 边界，被保留的删除由下一个持有者重试。
- 锁文件被另一代替换时返回 `LockOwnershipLost`，不会动替换后的文件。替换文件消失后，下一个持有者可以成功获取。
- Dispose 时仍会报告未完成的删除，并附带恢复租约。

消融实验：恢复"`LockReleaseFailed` 时让持有者失败"后，有 5 个用例失败，其中包括这次事故的回归用例。给临时目录单独的 5 秒等待后，事故回归用例失败。以上只在 Linux 上验证，没有覆盖其他平台，也没有在真实的事件循环饿死场景下运行。

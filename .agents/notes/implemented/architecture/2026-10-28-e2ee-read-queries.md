# Encrypted machine read queries

Status: implemented
Translation: current

[中文](2026-10-28-e2ee-read-queries.zh.md)

## Abstract

Encrypted workspaces previously stopped machine reads at the ordinary RPC gate, so remote files, diffs and history were unavailable. A closed set of machine state and file reads now reuses the signed Streams frames and shared response reader, with native read authorization and the existing method handlers. Diff/history and external provider discovery remain unavailable because their existing handlers can start processes, initialize storage or flush writes. They never claim the execution journal. Large JSON outcomes use signed pages, and a separate RPC-only token lets Guests send queries without receiving document write permissions. Packaged two-device acceptance and backend deployment remain separate from these local checks.

## Decision and boundaries

This extends the [dispatch channel](2026-10-28-e2ee-streams-dispatch.md), preserving its execution claim and durable fallback. It does not supersede that decision: read results have no business execution to claim or replay. A separate encrypted transport implementation would duplicate target binding, framing, correlation and cleanup; the existing channel instead accepts typed inputs/results and keeps one response reader for both operations.

On the baseline, `getMachineRpcClient` rejects protected workspaces through the common `rpc` feature gate; `e2ee_rpc_unavailable` also guards missing host preparation capabilities. The production chain is cloud provider → inferred IPC proxy → preload allowlist → account/window-bound host → native preparation/response verification. Both host operations and `rpcOnly` token selection pass through that chain. No signing key crosses it.

The allowlist admits ten method names: machine status/ping/binary status, session live status, file preview/download, text open/refresh and the two existing LSP queries. Binary status only inspects cache metadata; absent/incompatible runtimes remain absent/incompatible. LSP returns its existing `lsp_not_wired` result without launching a server. Text reads use the service's read-only mode, suppressing watchers, reconciliation and publication.

Method names alone are not evidence of read-only behavior. Pi discovery installs and scans the runtime; memory list runs a provider command; local-project probes/Git state start Git; history read/watch opens a backend and flushes writes; diff reads can start Git/workers or initialize SQLite. All nine names are refused by client preparation, native receiving and the server read entry. This applies to every reader role, including old signed requests. They require a separate side-effect-free reader before admission. Saves, history writes, index publication, preview leases, installation/authentication and execution remain closed too.

Encrypted file resolution checks durable session/parent/machine ownership before observing an existing resident path through `Session.peekHostWorkdir`, or deriving an existing chat/project/worktree path. A temporary `WorktreeManager` computes and stats paths only; no global manager, checkout, fetch or initialization is acquired. Project registrations come only from the machine sync owner's already-open Flock; unavailable registrations produce an unavailable result. The getter neither opens a Flock nor requests a sync. Even the SDK's detached Flock read was rejected here: SQLite `loadFlockDoc` may compact and write storage on a cold load. Project member resolution disables link repair. Missing directories, links and registrations stay missing. The `file/preview` Markdown discovery variant is explicitly unsupported: its shared resolver runs `git worktree list`; returning only the current-root candidate would hide ambiguity. Explicit file paths remain readable. Ordinary resolution keeps its original path. The [PR's method audit](https://github.com/LodyAI/Lody/pull/2013) records all nineteen original call chains.

Read authorization reuses the host's authenticated latest-ledger refresh and its bounded in-memory freshness lifetime, then checks active non-recovery membership and the target machine's same-member binding. Guest is a valid reader; execution still separately requires write authority. The realtime crypto binding admits active readers, while the host's closed method/action entry decides what they may request. Read queries enter neither receipt nor actual-start execution journals. Their incoming signed originals are retained in the ciphertext originals store, rejecting different bytes under the same signer/request ID. New coordination stays native Effect; existing method handlers and Repo remain Promise adapters, without claiming a migration of those services.

## JSON paging and original retention

Purpose 8 retains the existing request body and method. Params are explicit UTF-8 JSON `{queryId, params}`, with the existing method params codec inside; owner-session encrypted envelopes and validation remain unchanged. The host generates the secure 16-byte request ID and a 60-second deadline. The exact signed request is saved before transmission; changed intent under a retained query ID is refused.

Successful method outcomes are UTF-8 JSON `{result}`. Each purpose-9 payload is JSON `{version:0,totalPages,totalBytes,data}`, with canonical padded base64 `data` containing at most 512 KiB of those original JSON bytes. The body sequence is the zero-based page index; only the last page has kind `success`, earlier pages are `progress`. Counts, byte lengths, signer, epoch, ID and full-request digest are verified. A missing page keeps the result incomplete, even if the last page arrived first; conflicting sequence bytes cannot replace saved pages. Reassembly decodes JSON only after all pages exist. Errors use the approved nested error body with an explicit safe method DTO.

A result is bounded to 32 pages / 16 MiB before base64. Larger outcomes return `e2ee_query_too_large` with `truncated:true`, total bytes and the limit; no partial payload masquerades as success. Bounded file chunks remain the application recovery path; excluded history/diff methods are never retried through ordinary plaintext RPC. The native response owner seals all pages and saves them atomically before publishing the first. An uncertain local write retains those sealed pages for retry; reopened committed outcomes reuse identical frames. No automatic collection or execution-result migration is introduced.

## Ownership and containment

A signed query starts a workspace-scoped read task, capped at 32 independently of dispatch intake. Identical active requests share the first response; retained responses replay without rerunning the handler. Reads have a 45-second work budget intersected with request expiry. Timeout/close aborts the raw handler and drains its actual settlement before releasing custody; a raw operation that ignores cancellation retains only its own slot. Authorization is checked again before publication, and incompatible epochs or revocation refuse affected sends.

Network failures, a bad response, an outbox fault or an expired read fail that query, leaving document sync, other requests and workspace startup available. Scope close drains the shared reader and admitted read tasks before releasing RPC token ownership. Retained ciphertext and public routing live in the existing originals store; the execution journal is unrelated.

RPC tokens use the existing credential-authenticated content-token operation with `rpcOnly:true`, isolated in cache identity by their restricted scope. They allow read/create/append only under the encrypted bucket's `<workspace>:e2ee-rpc:` prefix. Document tokens retain their previous Guest read-only behavior, and neither token grants snapshot writes to Guests. Current credential/role/epoch checks and the 15-minute absolute token bound remain backend responsibilities. The matching private change is independently reviewable and never changes the public gitlink.

## Verification limits

The [host tests](../../../../packages/loro-streams-rpc/tests/e2ee-native.test.ts) pin request retention, paged exact response reuse and incomplete out-of-order delivery. The [query integration](../../../../apps/cli/src/lib/e2ee/realtime-rpc.test.ts) traverses real method serialization, encrypted Streams correlation, target signature checks and the real server read entry. [Production provider/preload coverage](../../../../packages/components/tests/cloud-platform-provider.test.tsx) pins both query operations and token purpose forwarding; [runtime authorization](../../../../apps/cli/tests/e2ee-runtime.test.ts) checks a demoted Guest on its admitted machine against execution and foreign-machine denial. The [assembled Guest query regression](../../../../apps/cli/tests/message-handler-file-preview.test.ts) traverses real Guest-signed preparation, native receiving, MessageHandler callbacks and signed responses for every admitted method, comparing machine files and injected process state. A real installer with a synthetic archive pins Pi denial before download/installation/scanning; subprocess execution is an in-memory boundary. Missing active directories, missing/stale member links and unavailable project catalogs remain unchanged. The Markdown variant is refused before Git discovery. The [catalog observation regression](../../../../apps/cli/src/lib/loro/machine-flock-sync-coordinator.test.ts) permits no storage or transport acquisition from the read path. These synthetic, deterministic boundaries do not establish WAN latency, a deployed backend or packaged two-device behavior.

# 分离附件准备与消息提交

Status: implemented
Translation: current

[English](2026-10-10-cli-input-attachments.md)

## 摘要

运行时已有附件输入能力，但 CLI 创建和继续会话仍然只写纯文本。新增输入准备层冻结
调用方文件，与 agent 输出共用字节传输服务，再把引用交给现有消息写入层。
MCP Operation 原子保存这些引用用于恢复，不重新读取可变源文件。
确定性本地测试覆盖了这些边界。Staging 跨两台 Mac 的创建和续聊验收也已通过：
远端工具读取完整的 39,052 字节测试文件，返回的随机后缀和 SHA-256 均匹配；
文件与图片混合续聊也正确识别图片。MCP 恢复的部署环境验收仍未执行。

## 职责

```text
CLI 路径 / MCP 调用会话目录内路径
  -> 输入准备：校验 + 私有快照
  -> 传输：中转或本地附件库
  -> 完整输入引用
  -> 命令写入：历史 + 冻结执行输入 + 激活
  -> 现有 daemon：附件落盘 + 调用 agent

MCP 接受 -> Operation 输入副表 -> 恢复时使用同一消息写入路径
```

既有 assistant 上传工具继续追加 assistant 输出。复用它们的历史写入会造成用户附件
归属错误，因此只从 MessageHandler 抽取字节传输。将源路径传给目标会读错机器；
恢复时重新打开路径则可能读到不同内容。

`operation_inputs` 将生成的引用与命令重试指纹、严格的旧 Operation 行分开。
操作接受与副表写入共享事务。能力协商防止新 MCP 调用方把恢复工作交给会忽略附件
的旧 daemon。并发竞争失败方可能留下中转对象，由既有保留清理机制处理。

真实历史读取测试发现，空提示词和 undefined 字段会被规范化。重试比较因此使用
共享输入配置规范化函数和序列化内容，同时检查每个附件。

本方案扩展[延后附件准备](2026-09-14-deferred-attachment-send.md)，
保留[冻结执行输入](2026-10-08-frozen-turn-execution-input.zh.md)。
行为与限制见 [Spec](../../../../specs/cli-session-attachments.zh.md)。

## 真实验证限制

纯附件创建也返回了预期随机值，稍后的独立查询确认会话已经完成，但该次 CLI
`--wait` 超过 180 秒。此次 staging 验证还出现工作区路由发现和 Streams 同步确认
超时。这证明了附件内容送达，尚不能证明这些条件下完成回执的可靠性。没有执行
真实 MCP 持久操作恢复及大型分片文件验收。

# The ledger user ID is the account ID

Status: implemented
Translation: current

[中文](2026-11-06-e2ee-ledger-user-id.zh.md)

## Abstract

The ledger's 32-byte user ID used to be a random public value the service allocated per account, which added a registry, a client cache and a network call before signing, and protected nothing: the service assigned it, and it never proved an account owns a signing key. The owner decided on 2026-11-06 that the field holds the account ID itself. `accountUserId` encodes the ID reversibly, clients compute it locally, and the service only checks that a signed value names the authenticated account. The field keeps its 32 bytes, so the ledger format and its v1 vector are unchanged, but the encoding is frozen once production enables encrypted workspace creation. This does not change authority, which still comes from signatures, the verified ledger and signed policy.

## Decision

The user-level field stays. One current membership per user and recognizing a person across a rejoin both need a value that outlives a membership, and neither a device key nor a membership ID can supply it. Only the value changes.

`accountUserId` in `packages/e2ee-core/src/internal/foundation/account-user-id.ts` defines the layout. Byte 0 is the character count, 1 to 49. The characters of the lowercase Crockford base32 alphabet `0123456789abcdefghjkmnpqrstvwxyz` follow as 5-bit values, most significant bit first. Every remaining bit is zero. Anything else is refused, never normalized, and `accountIdFromUserId` refuses bytes the encoder cannot produce.

Hosted account IDs are Convex document IDs: 19 to 23 bytes, written as 31 to 37 base32 characters. They do not fit the field as text and do fit decoded. The rule packs characters and counts characters, so it never interprets a Convex table number or checksum. It relies on the published alphabet and length only, and the bits it stores are the ID's own binary form. Core stays independent of any account system.

Creation and member requests sign the value locally, with no pre-signing network call. The service recomputes it from the authenticated account before reserving a write and refuses a mismatch with the existing `e2ee_account_identity_conflict`, which the renderer already treats as an unreserved refusal. That is an ownership check, not a permission. The member directory keeps its `cryptoUserId` field, which now carries this encoding.

## Alternatives

- **Keep the random value.** It needed a registry table and an immutable client file, and its one effect was hiding the account ID from members, who already see it in plaintext presence. See the [rejected proposal](../../rejected/architecture/2026-10-26-e2ee-account-global-identity.md).
- **A SHA-256 derivation of the account ID.** This also removes the registry and keeps the raw ID out of the permanent ledger. The owner chose the raw, reversible ID: a reader of the ledger gets the account directly.
- **Remove the field.** That changes genesis and JoinRequest records and loses the duplicate-member and rejoin rules.

## Consequences

Each record that names a member permanently holds the account ID, and members of a workspace can read it. Replacing the account system requires keeping the old IDs as stable subjects, because existing ledgers name them. A future account ID outside the alphabet or over 49 characters is refused at signing; extending the rule needs a new ledger capability or a new field meaning, not a change to this layout.

## Verification

`packages/e2ee-core/test/foundation.test.ts` pins two fixed vectors generated by Python's RFC 4648 base32, round trips, refusals and non-canonical bytes. `apps/electron/src/main/services/e2ee-bootstrap.test.mjs` and `e2ee-runtime.test.mjs` cover one account across workspaces and a rejoin keeping its user ID. `packages/e2ee-client/test/account-requester.test.ts` covers local membership lookup. No test runs against a real Convex deployment's IDs; the alphabet and lengths come from the public convex-backend source (`crates/value/src/base32.rs`, `id_v6.rs`).

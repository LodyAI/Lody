# 内置个人记忆：独立包架构

Status: proposed
Translation: current

[English](2026-10-26-builtin-personal-memory.md)

## 摘要

Lody 现有 Provider 只绑定外部身份，不存储个人 Role 知识。
独立的 `@lody/memory` 包在单份个人 LoroDoc 上实现同步文档服务，宿主保留授权、持久化和传输所有权。
文档现采用相对 Markdown 路径 key 和 mergeable 容器，使同路径并发创建对应同一份文档。
代价是不再保留独立于改名的文档身份，换取更简单的路径模型。
本地宿主接入已落地，生产加密同步仍不可用；本说明不表示整体归属与存储规范获批。

## 本地宿主接入

已接入独立 SQLite/Renderer IndexedDB、Role 配置、Agent 提示及 MCP 工具。
逻辑作用域为工作区、可信当前用户和记忆体 ID；不同工作区不合并。
实际访问读取冻结 turn、当前本地 Role 配置与记忆体目录；停用、改关联、删除 Role 或删除记忆体都会撤销后续访问。
当前宿主不允许其他用户借用机器所有者的个人记忆，不宣称抹除历史上下文。

个人仓库不加入工作区 meta 或 Streams。Renderer 自行编辑并复用本地 Loro 数据通道；
界面及运行时在连接前要求 `builtinMemory: 1`，避免旧 daemon 将个人房间作为普通工作区数据接收。
普通清理缓存保留个人 IndexedDB，显式完整重置仍可删除本地副本。

Effect 采用小型 scoped layer 管理延迟打开及关闭。现有本地传输和房间解析依赖 Promise Repo，
本次不扩大为整个数据面的 native Repo 迁移；包的 `./repo` 适配器保留该依赖边界。
生产跨设备同步仍关闭，等待个人资源授权及现有设备、密钥与 E2EE 数据面接入，不另造协议。

使用固定 Loro 1.17.0 / Repo 0.25.0、真实 SQLite、MCP 注册及本地数据通道验证。
隔离环境下核心、宿主、Provider、Role 和 turn 冻结共 91 项行为测试及局部类型检查通过；
完整工作区检查依赖缺失的工具及 ACP 包，缓存清理原有套件未在隔离环境运行，
尚未进行打包桌面或真实 Agent 端到端验证。具体行为以包 README 为准，本提案不代表批准。

## 决策与职责

[包 README](../../../../packages/memory/README.md)维护实际布局、接口、限制和待完成接入。
[记忆规范](../../../../specs/agent-role-memory.zh.md)继续保持 draft；
[Nowledge 决策](../../implemented/feature/2026-10-04-agent-role-memory.zh.md)及外部 Provider 数据不变。

同一可信个人与记忆体 ID 跨机器对应一份记忆；Role 通过 `lody` 绑定关联记忆体，多个 Role 可共用。
Role/模型名称、机器 ID 和工作目录不参与分区。此前按 Role 隐式对应一份记忆（`lody/role`），
现改为具名记忆体，使用户能像 Nowledge 一样命名、描述和复用记忆；代价是复制 Role 会共用已关联的记忆，
而不是得到空记忆。名称和描述写在各自 `MEMORY.md` 的 front matter，所有者目录 Doc 只列 ID，避免资料出现第二份可写副本。
历史差异复用 Loro 历史，而不是在来源记录里保存正文快照：每次修改的提交信息带上它的 change ID，
使其成为不被合并的独立 change，其依赖与最后一个 op 界定了前后两个版本。
未采用逐条保存快照，因为每次按键编辑都会复制最多 64 KiB 的正文。
只实现个人归属；共享归属、账号和设备授权属于后续宿主接入。
Role 切换、会话内容披露和宿主文件系统隔离不在收敛后的包实现范围内。

宿主传入已授权 Doc，负责导入准入、保持绑定和实际访问时的权限检查。
身份只在打开时验证，唯一来源 change ID 由宿主生成。
不增加跨进程代写、平行持久化源、网络客户端、Git 流程或密码协议。
内存 commit 不代表保存成功，生产同步仍关闭。

## 路径身份与 mergeable 容器

确认后的路径模型替代此前独立文档 ID 设计。当前布局将相对 Markdown 路径直接作为根 documents Map 的 key。
每篇使用 ensureMergeableMap(path)，正文使用 ensureMergeableText('body')，
来源使用 ensureMergeableMap('changes')，没有重复 path 字段或 ID/路径索引。
[Loro API](https://www.loro.dev/docs/concepts/container)由父容器、key 和类型确定此类容器身份；
真实 1.17.0 副本测试验证同路径并发创建合并双方正文与来源。
标量元数据遵循 Loro Map 的冲突解决；CRDT 合并不负责判断知识矛盾。

创建向 ensure 后的路径写入指定内容，包括已有路径。
更新缺失路径返回 not_found。删除隐藏 mergeable 状态，离线子容器编辑不重新激活父键。
显式创建可重新激活原容器及保留来源，并以新传入的正文、描述作为当前内容。

改名使用 newPath：迁移可见元数据、正文及来源，记录移动，再删除源键。
这是内容迁移，不是保持身份的 CRDT 移动。已可见目标通过直接 key 查询拒绝覆盖；
并发到达相同新路径则合并。离线源路径编辑保留于隐藏历史，并发移到不同目标可能产生两份文档。
其他正文中的链接不自动改写。这些是接受路径身份后的语义。

该包尚未发布，路径布局保持格式 1，开发过程中的设计调整不升级版本或添加迁移层。

## 服务边界与证据

服务直接操作实时 Loro 状态，不增加哈希、修订校验、墓碑或快照分页游标。
分页使用有界数值偏移；目录不读正文，路径解析直接查 Map。
搜索直接匹配路径 key，并对描述、正文执行固定字面量 JSONPath。
描述改善排序但不排除正文命中。内部结构损坏抛出不含正文的错误，输入错误返回结构化结果。

行为测试使用真实副本与快照，覆盖同路径并发初始化、独立新增、编辑、改名、
删除重连重建、路径搜索与转义、来源、配额和个人作用域隔离。
类型与格式检查使用隔离环境中的锁定直接依赖，当前 checkout 缺少根依赖和 ACP 子模块。
文档及公开边界检查仍受已有子模块缺失问题影响；这些检查不证明宿主持久化或生产同步/E2EE。

下面的实验早于路径 key 布局，使用原始 ID-keyed 合成数据。
它们比较 Loro 操作和布局规模，不是新服务的延迟或内存测量；保留原始证据而不重新标记结果。

## JSONPath 搜索实验（2026-10-27）

仓库锁定 `loro-crdt` 1.17.0。隔离实验使用此版本 npm 包，环境为 Linux x64、
Node 24.22.1，未修改仓库依赖。每篇文档是包含路径和 LoroText 正文的嵌套 LoroMap。
正文含 32,768 个字符的重复中英文文本，每十六篇在末尾追加 `needle测试`。
四种方式返回的匹配路径完全一致。预热十次、查询八十次的中位耗时（毫秒）：

| 文档数 | JSONPath contains | JS 读取容器后搜索 | 全量 toJSON 后搜索 | 缓存 JS 字符串搜索 |
| ------ | ----------------- | ----------------- | ------------------ | ------------------ |
| 32     | 0.552             | 4.093             | 4.107              | 0.925              |
| 256    | 4.866             | 29.759            | 32.887             | 7.964              |

查询为 `$.documents[?(@.body contains "needle测试")].path`。
另行构建 JS 字符串缓存分别约耗时 8 和 49 毫秒。
这是合成数据的热态子串匹配实验，不是生产延迟保证、排序测试、倒排索引对比，
也不证明这是所有方式中最快的方案。加载、增量更新、摘要生成和分页未计入测量。
单独测试 JSONPath `search()` 时触发 WASM panic；应使用已支持的 `contains`。

首版优先选择有界 JSONPath 子串查询，不预设需要额外文本索引。
Lody 对查询字面量校验、转义并构造表达式；Agent 只提供关键词，不提供任意 JSONPath。
打开 Doc 前完成作用域限制。增加索引前再用真实工作负载测量。
参见[官方 JSONPath 文档](https://loro.dev/docs/advanced/jsonpath)。

## 单 Doc 与十个 Doc 对比（2026-10-27）

第二组实验使用十篇各 4,000 个汉字的记忆文档，总计 120,000 UTF-8 字节，
分别放入一个 LoroDoc 或十个 LoroDoc。两组均采用嵌套 LoroMap 和 LoroText、
相同的确定性合成正文以及 JSONPath `contains` 查询，两篇文档命中。
每种情况在五个独立 Node 进程中运行，下表取中位数。
正文长度和预期搜索结果断言全部通过。环境：Loro 1.17.0、Node 24.22.1、
Linux x64、Intel Xeon 2.20 GHz。

| 操作，毫秒                            | 单 Doc | 十个 Doc |
| ------------------------------------- | ------ | -------- |
| 冷进程导入全部快照字节                | 19.57  | 23.83    |
| 读过一篇后的首次全库搜索              | 12.13  | 12.54    |
| 热态全库搜索                          | 0.126  | 0.410    |
| 修改一篇的四个字并 commit             | 0.042  | 0.040    |
| 修改全部十篇的各四个字，逐 Doc commit | 0.296  | 0.324    |

热搜索预热十次，每进程测一百次；更新测一百次，正文长度不变。
冷操作包含 WASM/JIT 首次执行成本，不含文件读取或 fsync。
快照字节在计时和内存基线采样前读取，不包含 Streams、加密、持久化适配器、UI 或网络。

为减少一次性运行时开销对内存结论的影响，另测同时驻留一百份独立逻辑记忆，
每份均执行全库搜索。显式 GC 后，进程 RSS 增量分别为 61.19 MiB 和 97.24 MiB，
即每份逻辑记忆约 0.612 和 0.972 MiB，包含摊销的运行时开销。
一百份记忆的 WASM 线性内存容量增量分别为 49.81 和 80.00 MiB。
容量不等于存活对象的实际分配量，也不能与 RSS 相加。
只加载一份记忆并首次搜索时，RSS 增量为 7.67 和 8.88 MiB，
因此不能把这两个数解释成纯粹的每份记忆存储占用。

另一个历史样本在导出快照前对十篇正文各更新一百轮，共一千次四字替换。
一百份逻辑记忆加载并搜索后的 RSS 增量为 63.18 和 105.56 MiB；
单份热搜索仍为 0.125 和 0.413 毫秒。这种局部编辑历史不能代表多年编辑、
大量删除或多 peer 场景。

仅访问一篇时，内存优势反转：单 Doc 导入完整快照，分 Doc 只导入第零篇的快照。
一百份逻辑记忆读取该篇后，RSS 增量为 34.71 和 14.40 MiB。
此时分 Doc 的另外九篇从未打开，也不执行全库搜索。
这是拆分按需加载的实际收益，不代表全部文档都要搜索时仍有收益。

本实验中显式释放 Doc 后，RSS 和 WASM 容量没有立即下降。
释放所有权允许分配器复用空间，不证明立即归还内存给操作系统。
在本次规模下，建议为简单全库搜索和更新保留单 Doc；
后续规模或以少量主题访问为主的负载证明有需要时，再考虑拆分及相应搜索索引。

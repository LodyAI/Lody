# Machine pairing originals and frontend admission

Status: proposed
Translation: current

[中文](2026-10-26-e2ee-machine-pairing-journal.zh.md)

## Abstract

Machine preparation previously recreated public proofs on retry, and activation checked the machine key without remembering which personal frontend approved it. The existing same-user socket now carries the main process's frontend key and pairing session through preparation and activation. A scoped local journal retains exact context, proofs and the accepted ledger record; core authenticates the complete record chain before the receiver can install a key. This is preparation for remote pairing, not a remote command or credential protocol: independent authentication of a future command, service credentials and location policy remain unresolved.

## Responsibility and lifecycle

`pairing-journal.ts` is a native Effect owner used directly by `prepareCliE2eeMachineLegacy` and the activation/active-owner paths in `workspace-legacy.ts`. Its separate SQLite mutex excludes concurrent signing and durable readback within one workspace; no network call runs while held. Scope release closes SQLite and custody only after native preparation settles. Context and public proofs are journaled before the response can leave the host. Interruption or an unknown result never deletes an original. There is no cancellation or retirement endpoint pretending to know whether a frontend has signed an admission.

The pin comes from `e2ee-local-pairing.mts`, where Electron main exports its own signer key over the existing same-OS-user socket. This is the authenticated input boundary; merely supplying expected values through a future remote API would not establish trust. Strict prepare/activate schemas require the frontend key, and activation also requires the original session; a partial upgrade fails closed. The fixed core possession and credential-binding signature formats are unchanged.

Activation first loads the original account/machine/workspace/genesis/member/frontend/session context and both machine keys plus credential hash. It audits retained full ledger originals to the runtime's verified endpoint, finds the machine admission matching a retained preparation of its actual signing frontend, compares any saved admission bytes, and checks current membership/device state. If that frontend was interrupted after admission but before first activation, another active personal frontend of the same member may continue through the existing same-user socket. Its current session, keys and credential remain fixed; the original admission signer and bytes remain unchanged. The current frontend must be active and same-member, the original preparation must match the account/machine/workspace/genesis/member, machine keys, credential hash and possession proof, and only the newest prepared session may activate. A new frontend session requires explicit user confirmation even when the machine is already admitted; retries in that confirmed session can reuse consent. No transferable remote proof is implied by this authenticated local context. Only then may the receiver fetch/install an envelope and activation be marked. Ledger-only pending owners cannot receive keys. A valid global ledger update is distinct from successful personal pairing; a wrong frontend can leave valid control history advanced while installing no key and publishing no activation marker.

Fleet shares an activation only for an identical immutable intent. A different intent receives a conflict. Local journal preflight precedes ownership changes. An already-running matching identity uses that owner's genuine evidence and the same guard before refresh; a failed retry leaves the healthy owner available. A genuinely different identity still drains its old owner before installation. No global account lock waits for network I/O.

## Originals and recovery

Same-session retries reopen their exact machine and credential originals. Missing credentials, damaged protection, wrong permissions or a changed context cannot generate replacements. The existing M2 recovery contract remains: a fresh trusted local session can prepare a new candidate after strictly missing machine custody, followed by fresh explicit frontend approval and verified admission/key installation. Old journal rows and runtime directories remain. Later sessions follow the current protected identity rather than the first historical proof. Before generating a replacement, the journal durably marks that session as owning the preparation generation. If device/credential creation, signing or material publication fails, the same session can resume its core originals. A fresh trusted session of the same account, machine, workspace, genesis bytes and member can also take over an unpublished generation; its frontend and session may change. One transaction sets the prior `creating` integer to `-1` (superseded) and the successor to `1`, without changing context, material, admission, keys or credentials. This uses the existing schema version 3; no migration is added. The successor inherits the unfinished generation rather than comparing replacement originals with an older published generation. Superseded sessions fail before custody and again at material publication, including a late signer in the same owner; they cannot retake or overwrite the current identity. Cross-process exclusion remains the SQLite mutex. Completed material is not eligible for takeover. Completed older rows remain unchanged. A singleton current-identity pointer publishes atomically with material, independently of session insertion order; pointer-write failure cannot leave half-published material. Earlier unpublished experimental database layouts remain intact and are explicitly rejected rather than guessed during migration. A leftover credential bound to the lost key causes rejection before creating a device, and is never deleted or overwritten to force recovery. The missing-original checks use core node-custody's existing `${genesis}.machine.device` and `device-credential-${genesis}.sealed` paths; the recovery tests bind these integration assumptions.

Rejected alternatives were returning only newly generated proofs (loses request originals), accepting an installed key as proof of the expected frontend (wrong session can succeed), and stopping every live owner before validation (a failed acknowledgement retry would disconnect healthy work). No new cipher, signature domain, token scope or machine-sharing permission is introduced.

## Verification and limits

Synthetic real crypto/storage tests cover first and replacement-generation takeover, same-scope checks, atomic takeover rollback, late signing after takeover, cross-process mutex exclusion and process exit after an explicit custody-retained IPC signal, exact retries, context substitution, missing credentials and machine originals, preserved recovery with a fresh session, explicit failures before/after credential publication, signing and SQLite material publication followed by native-scope reopen, partial custody loss without device creation, wrong activation targets, interrupted first activation continued by a second same-member frontend without replacing keys or credentials, rejected foreign/revoked frontend and late sessions, explicit new-session confirmation, admission-journal write failure followed by normal-call recovery, damaged saved admissions, cursor checkpoints across 67 records, partial-upgrade rejection, exact-intent concurrency and healthy-owner recovery. The owning suites and build results accompany the review handoff. Real keychains, remote transport, one-time credential issuance/cancellation, location lookup, deployment and M5 execution are outside this change. The one-time pairing credential must not be adapted from the legacy flow that promotes account API keys.

The CLI context keeps machine pairing in its own section so the dormant M5 journal instructions can compose independently. This moves context only: machine preparation/activation does not authenticate a realtime request, the journal does not authorize execution, and neither supplies the pending shared epoch/freshness barrier.

The same-user control reply `prepare-superseded` is emitted only for an exact retained context whose generation is -1. Main first checks machine/session, current account and reader, then atomically archives only an all-null unsigned desktop attempt. A subsequent explicit retry prepares a fresh session and still requires approval. Generic errors/timeouts, changed sessions and staged or signed attempts never reset; retirement failure retains the original receipt and cleanup cause for retry. The CLI keeps old context/originals. Native A/B/A and strict socket tests cover B stopping after prepare, failed archive rollback, stale replies and signed-state rejection.

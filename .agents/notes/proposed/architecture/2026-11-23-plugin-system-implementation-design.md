# Plugin system implementation design and stacked PR plan

Status: proposed
Translation: current

[简体中文](2026-11-23-plugin-system-implementation-design.zh.md)

## Abstract

This note translates the normative [Lody Plugin System Spec](../../../../specs/plugin-system.md) and the boundary rationale in [Plugin architecture convergence and E2EE workspace boundaries](2026-11-22-plugin-architecture-and-e2ee-boundaries.md) into a concrete repository implementation blueprint across `@lody/plugin-sdk`, `@lody/shared`, `apps/cli`, `@lody/components`, `apps/electron`, and `apps/mobile-capacitor`. Every daemon-side OS subprocess (`PluginHost` and `DevPluginCompiler`) routes exclusively through the generic Effect process boundary in [`packages/shared/src/node/process.ts`](../../../../packages/shared/src/node/process.ts) under native Effect v4 (`4.0.2`) `Scope` ownership, while client rendering, raw snapshot reads, permanent `SessionCreationReceipt` idempotency, and E2EE signing reuse existing `ai-gui`, `sidebar-surface`, `vscode-theme`, Loro/Flock, `sessionData`/Roost, and `e2ee-execution-intent` owners with zero parallel stores. Delivery splits into four dependency-ordered stacked pull requests (`PR-1` through `PR-4`), where `PR-2` already closes a complete end-to-end interactive plugin loop across Desktop Electron and Web and `PR-3` layers raw snapshots, machine workflows, and rooted E2EE derivation. For current implementation evidence, see [Spec §17.4](../../../../specs/plugin-system.md#174-repository-evidence--current-implementation-status).

## 2. Native Effect v4 lifecycle & failure-containment contract

Per [`packages/shared/src/node/AGENTS.md`](../../../../packages/shared/src/node/AGENTS.md) and [`scripts/check-cli-process-boundary.mjs`](../../../../scripts/check-cli-process-boundary.mjs), `apps/cli` MUST NOT import `node:child_process` or call `process.kill` / `child.kill` directly. Instead, `NodeProcessApi` in [`packages/shared/src/node/process.ts`](../../../../packages/shared/src/node/process.ts) gains `spawnIpcChild` (modeled identically in `process-testing.ts`), returning a scoped Effect handle `{ pid, send, messages: Stream<unknown, ProcessIpcError>, exit, ringBuffer }`. **`process.ts` owns zero plugin business protocol:** its `Scope` finalizer executes only generic OS process-tree termination (`terminateTree`: `SIGTERM -> 2000 ms waitUntilGone -> SIGKILL -> zombie-excluded OS table verification` + `ProcessReleaseFailed` recovery lease), while `PluginHost` owns the application-level `{ type: "shutdown", graceMs: 2000 }` IPC frame before closing the child `Scope`.

`PluginHost` and `DevPluginCompiler` are authored as native Effect `4.0.2` services (`Context.Service`, `Layer.effect`, `Effect.fn`, `Schema.TaggedError`, `PubSub`, `Deferred`, `Ref`, `Clock`) satisfying [`cli-effect-ts.md#behavior-contract`](../../../docs/cli-effect-ts.md) and [`failure-containment.md`](../../../docs/failure-containment.md):

| Contract Dimension                                                     | `PluginHost` (`apps/cli/src/plugins/workflow/plugin-host.ts`)                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               | `DevPluginCompiler` (`apps/cli/src/plugins/workflow/dev-plugin-compiler.ts`)                                                                                                                                                                                                                   |
| ---------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **1. Trigger**                                                         | Daemon startup (for enabled plugins unless `--safe-mode`), explicit CLI/RPC `enable` / `reload` / `disable` / `remove`, or `--dev` rebuilds whose `machine.js` or `manifest` changed.                                                                                                                                                                                                                                                                                                                                                                                                                                                       | Explicit `lody plugin link --dev`, `pack`, or debounced (`150 ms`) source file change under watched plugin directories.                                                                                                                                                                        |
| **2. Owner & FIFO Serialization**                                      | Daemon root `Scope` owns `PluginHost`; each running `machine` plugin owns a child `Scope.Closeable`. Because Effect `4.0.2` `Semaphore` does not preserve FIFO on immediate reacquisition, per-`pluginId` lifecycle transitions use an **owned `Ref`/`Deferred` FIFO turn queue** that coalesces redundant pending `--dev` `reload` requests to the latest trailing build while keeping `disable` / `remove` strictly ordered.                                                                                                                                                                                                              | `PluginHost` child `Scope` owns an on-demand compiler worker lease. A `Clock`-backed idle timer (`1000 ms`, deterministic under `TestClock`) closes the compiler `Scope` when no build is queued or running, dropping resident compiler memory to `0 B`.                                       |
| **3. Cancellation & Protocol-Clean Teardown**                          | Before closing a plugin's child `Scope`, `PluginHost` aborts its host `AbortController`, sends `{ type: "shutdown", graceMs: 2000 }` over `handle.send` (without `child.disconnect()`), and races `handle.exit` against a `2000 ms` `Clock` timer; if still alive, closing the child `Scope` delegates `SIGTERM -> 2000 ms -> SIGKILL -> waitUntilGone` to `process.ts` `terminateTree`. Daemon shutdown bounds total plugin teardown so uncooperative children never hang exit.                                                                                                                                                            | Canceling or superseding a `--dev` build interrupts the in-flight compile fiber; if the `esbuild` subprocess stops responding, closing its `Scope` reaps the tree via `terminateTree`.                                                                                                         |
| **4. Handoff, `clientDigest` vs `instanceId`, & Drain-Before-Respawn** | `instanceId` identifies a **`MachinePluginInstance` subprocess generation** and increments **only** when `PluginHost` spawns a new `machine` OS process. Client-only edits (`client.tsx`, themes, CSS) update `clientDigest` and hot-swap clients **without** restarting the `machine` subprocess or rotating `instanceId`. When `machine` respawn is required, `PluginHost` **never** spawns a replacement PID until the prior PID is gone; if `Scope.close` surfaces `ProcessReleaseFailed`, `PluginHost` retains its recovery lease and blocks successor `enable` / `reload` on `lease.retryTermination` until `waitUntilGone` succeeds. | Writes compiled outputs to a staging directory and atomically commits updated `clientDigest` + bundle artifacts only after compile succeeds (never owning or mutating `instanceId`); compile errors preserve the prior active bundle and publish structured diagnostics to `Plugin Inspector`. |
| **5. Normative Deadlines & `0` Auto-Retry**                            | Enforces exact Spec §9.3 deadlines: `init -> ready`: **`10_000 ms`**; `start` (`machine.onStart`), `query`, `mutation`, `attachment-*`, and `event`: **`30_000 ms`**; `defineTool`: **`600_000 ms` (`10 min`)**. Handshake timeout, uncaught exit, or protocol violation transitions to `Faulted` with **`0` automatic retries** and **never caches a failed startup fiber**. Crash or timeout settles in-flight `mutation` / `tool` calls as `PluginCallError { code: "outcome_unknown" }` and fails `query` calls without re-dispatch.                                                                                                    | Compiler crash or syntax/bundle error fails the single build attempt with structured file/line diagnostics; the file watcher stays alive in the daemon so saving a fix triggers the next build cleanly.                                                                                        |
| **6. Containment**                                                     | Client-only, theme, skill-only, and `sound-effects` plugins spawn `0` subprocesses. A crash, infinite CPU loop, or `--max-old-space-size=256` V8 OOM in plugin `A` affects only `A`'s PID, leaving the daemon, ACP sessions, and plugin `B` untouched.                                                                                                                                                                                                                                                                                                                                                                                      | `esbuild` runs out-of-daemon in `DevPluginCompiler`'s child process; native bundler panics or OOMs never touch the daemon heap.                                                                                                                                                                |

## 3. Data plane, UI mount stability, bundle streaming & E2EE gate wiring

### 3.1 Shared `lodyCommands` registry, zero-parallel-store `lodyQueries`, permanent `SessionCreationReceipt`, & gapless `onStart`

- **Shared Typed Host Command Registry (`lodyCommands` — zero duplicate command system):** Instead of maintaining ad-hoc mutation methods or trapping domain writes inside React hooks, Lody extracts canonical `LodyCommandDescriptor<S, TInput, TOutput>` definitions into `packages/shared/src/commands/host-commands.ts` (`lodyCommands`: Session execution `sessionCreate` / `sessionSend` / `sessionRespondInteraction` / `sessionStop` / `sessionArchive` / `sessionRestore` / `sessionFork`, Status/Focus triage `sessionSetPinned` / `sessionSnooze` / `sessionSettle` / `sessionMoveToFocus` / `sessionMoveOrder` / `sessionUpdateTitle` / `sessionMarkRead` / `sessionMarkUnread` over [`status-view/command.ts`](../../../../packages/shared/src/status-view/command.ts), `pinSection*`, and `schedule*`). [`use-session-actions.ts`](../../../../packages/components/src/hooks/use-session-actions.ts) and plugin `lody.execute` / `useLodyCommand` / `ctx.lody.execute` delegate to the **same** `workspace-command-executor.ts` / `daemon-command-executor.ts` pipeline (with `sessions.*` kept as thin aliases over `lodyCommands.session*`), binding an unforgeable host `ActorContext` on every call (signed-in client user; authenticated RPC member on `plugin/query` & `plugin/mutate`; owning/signing `SessionMeta.userId` / verified `originTurn` on `defineTool` & `machine.events`; and separately authorized workflow principal for new post-turn work on `machine.onStart`, which rejects un-attributed `prefer` writes such as `sessionMarkRead` with `forbidden`) and enforcing Lody's existing first-party `prefer` vs `manage` session guards ([`use-session-management-guard.ts`](../../../../packages/components/src/hooks/use-session-management-guard.ts)), E2EE `MachineSharing` / `e2eeIntent` gates, and `ui.command.invoked` emission — never granting a daemon plugin ambient cross-member privileges merely because it runs on the machine owner's host.

- **Typed queries (`lodyQueries`) & lazy detached snapshots (`useLodySnapshot` / `readSnapshot`):** `ClientPluginHost` and `PluginHost` resolve all 18 typed descriptors directly against existing workspace Loro/Flock room readers and [`packages/shared/src/session-data`](../../../../packages/shared/src/session-data/AGENTS.md) / Roost narrow query indices (including `sessionIds`, `agentRoleId`, and inclusive `updatedAfter` filters on `sessions`, plus `userTurnId` / `stopReason` on `sessionTurns`) with zero parallel Domain Store. Snapshot subscriptions attach ref-counted narrow listeners and mark dirty revisions lazily; `structuredClone` + recursive `Object.freeze` + secret/foreign-`businessKey` redaction runs **only when a caller reads a dirty slice**.
- **Permanent `SessionCreationReceipt` (No TTL):** `SessionCreationReceiptStore` persists `(workspace_id, caller_user_id, canonical_target_key, plugin_id, request_id) -> { payload_sha256, session_id, business_key? }` **permanently without TTL** in the custody-scoped daemon SQLite store (~250 bytes/row; ~25 MiB across 100,000 creations, removed only on E2EE custody wipe or explicit `lody plugin remove --purge-data`). Replaying the identical normalized payload returns the original `SessionRef` even after Session archive or multi-day restarts; modified payloads reject with `idempotency_conflict`; archiving a Session releases `businessKey` uniqueness for new `requestId`s while retaining the historical `requestId` receipt forever (Spec §7.3).
- **Gapless Startup Event Buffering (`ready -> buffer -> onStart -> drain -> live`):** To prevent missing a `session.turn.completed` event that fires after `machine.onStart` scans history but before live event delivery opens (without a Durable Event Broker), `PluginHost` attaches the instance's `subscribedEvents` listener into an **in-memory startup buffer immediately upon receiving `ready`**, dispatches `start` (`machine.onStart(ctx)`, `30_000 ms` deadline) to reconcile `ctx.dataDir` journals + `lodyQueries.sessions({ updatedAfter })` / `sessionTurns`, and once `onStart` resolves, drains buffered events in arrival order before switching atomically to live pass-through. Overlap between `onStart` and buffered events deduplicates idempotently via plugin journal keys and permanent `SessionCreationReceipt` rows.

### 3.2 Client UI integration, normative 3-layer `sidebar`, & `blockId` stability

- **Three-layer Client Identity (`Installation Key` / `Bundle Key` / `Per-Installation Module Evaluation`) & `Trusted Dev Session`:** Per Spec §8.5, `ClientPluginHost` distinguishes three layers: (1) **Installation Key** `(workspace_id, source_key, plugin_id)` (`source_key = "machine:<machine_id>" | "local"`) owning `ClientPluginInstance`, RPC routing, `config`, `events`, and `query_cache`; (2) **Bundle Key** `(plugin_id, clientDigest)` deduplicating `plugin/bundle-chunk` downloads, SHA-256 verification, custody cache storage, and immutable `assets/*`; and (3) **Per-Installation Module Evaluation** `(workspace_id, source_key, plugin_id, clientDigest)` minting a dedicated ephemeral Blob/module URL per installation (revoked on disable/HMR while sharing externalized host `react` / `zod` / `@lody/ui` / `@lody/plugin-sdk/*` singletons) so module-level `let` state inside `client.tsx` never bleeds across two machines running the same plugin. `DevPluginCompiler` bundles `client.tsx` as browser ESM with `react`, `react/jsx-runtime`, `zod`, `@lody/ui`, and `@lody/plugin-sdk/*` externalized onto a host-frozen module map. On remote Web/Desktop connections, release plugins require per-`(workspace_id, plugin_id, clientDigest)` trust, whereas `devMode: true` plugins expose an explicit **"Trust Dev Session"** toggle binding `(workspace_id, machine_id, plugin_id, devSessionNonce)` in ephemeral tab memory / `sessionStorage` (with a persistent **"Dev Session Active · Revoke"** badge and automatic invalidation on `devSessionNonce` rotation or manifest capability escalation).
- **Stateful `messages.renderBlock` & universal `tools.matchRender`:** [`markdown-renderer.tsx`](../../../../packages/components/src/components/ai-gui/markdown-renderer.tsx) assigns each fenced code block its deterministic turn-scoped `blockId = "${turnId}:block:${ordinal}"` and renders `PluginMessageBlockSurface` keyed by `${sessionId}:${blockId}:${winner.pluginId}:${winner.id}`. Streaming token appends and `streaming: true -> false` fence closure update `code` and `streaming` props **in place** without unmounting the component instance, preserving form/zoom/selection state while omitting `searchBlockId` per [`ai-gui/AGENTS.md`](../../../../packages/components/src/components/ai-gui/AGENTS.md). Both `PluginMessageBlockSurface` and `PluginToolCallSurface` (wrapping [`tool-call-detail.tsx`](../../../../packages/components/src/components/ai-gui/tool-call-detail.tsx)) render a non-spoofable host header toggle (`"View Raw Markdown"` / `"View Raw Output"`) and `SurfaceErrorBoundary` fallback.
- **Normative three-layer orthogonal `sidebar` & two-tier `themes` / `styles`:** [`loro-app-sidebar.tsx`](../../../../packages/components/src/components/loro-app-sidebar.tsx) composes the exact Spec §6.3 layers over [`sidebar-surface.ts`](../../../../packages/components/src/components/sidebar-surface.ts): (1) `sidebar.sessionRow.decorate` (composable `trailing` badges and `hoverCard` popovers sorted by `(plugin_id, decorator_id)`, automatically composed whenever `<SessionRow />` renders — including inside custom sidebar views), (2) `sidebar.headerItems.add` / `sidebar.footerItems.add` (`<SidebarRow />` navigation items paired with `screens.add`), and (3) `sidebar.views.add` (selectable sidebar bodies alongside Lody's built-in `"Default"` view, reverting immediately to `"Default"` if the active plugin view disables or faults). `themes` feed [`vscode-theme-dom.ts`](../../../../packages/components/src/lib/vscode-theme/vscode-theme-dom.ts) and `styles` mount `<style data-lody-plugin="<plugin_id>">` nodes removed atomically on disable/HMR.

### 3.3 Five E2EE runtime gates

1. **Non-Guest execution gate:** In [`packages/shared/src/e2ee-rpc.ts`](../../../../packages/shared/src/e2ee-rpc.ts), `isE2eeFeatureMethod` adds `method.startsWith('plugin/')`, while `E2EE_READ_QUERY_METHODS` stays unchanged so `plugin/query`, `plugin/mutate`, and `plugin/attachment-*` enforce non-Guest `authorizeExecution` (`< 15 min` ledger freshness).
2. **Owner vs `MachineSharing` scope gate:** Daemon RPC dispatch consults [`@lody/e2ee-machine-sharing`](../../../../packages/e2ee-machine-sharing/AGENTS.md): `machine`-scoped handlers, plugin lifecycle/config writes, `devSessionNonce`, and `acpProviders` require machine-owner identity; collaborators may invoke `project` / `session` handlers only while `MachineSharing` grants the machine and all bound projects.
3. **`SignedTurnOrigin` & `e2eeIntent` derivation:** Client execution-bearing `lodyCommands` (`sessionCreate`, `sessionSend`, `sessionRespondInteraction`, `sessionFork`, `scheduleRunNow`, plus `sessions.*` aliases) sign `E2EE_INTENT_KIND.memberInput` (`1`) via [`e2ee-execution-intent.ts`](../../../../packages/shared/src/e2ee-execution-intent.ts). At write time the daemon must verify that the driving turn is active in the live runtime and that `originTurn: { session, userTurnId }` matches its human-signed `memberInput` in local `sessionData`. Shared-member `derivedFrom` `machineInput` (`kind = 2`) requires active member/project `MachineSharing`, the same machine, and a maximum of 20 derivations. An already signed input may start after restart without a start deadline, subject to current authorization. History establishes provenance, not authority to sign another input. Once the turn is inactive, new workflow work requires a separately verified machine-owner activation covering that operation on that machine; it runs as the declared workflow, never as an elevated member. Unrooted queries and mutations return `forbidden`.
4. **Iroh frame sizing:** `plugin/query` and `plugin/mutate` cap serialized payloads at `256 KiB` (one `1 MiB` `purpose 8` frame); `plugin/bundle-chunk` streams `<= 4 MiB` client bundles in `256 KiB` `purpose 9` pages and verifies SHA-256 against `clientDigest` before custody caching or `import()`.
5. **Custody directory binding & static share fallback:** Daemon `ctx.dataDir`, permanent `SessionCreationReceiptStore`, and client remote bundle caches live under `<account>/<workspace>/<genesis>/<signing-key>/plugins/` and wipe on E2EE member removal or device revocation; static plaintext share viewers disable `ClientPluginHost` script execution and render built-in raw fallbacks.

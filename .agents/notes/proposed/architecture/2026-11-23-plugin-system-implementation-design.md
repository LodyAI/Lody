# Plugin system implementation design and stacked PR plan

Status: proposed
Translation: current

[简体中文](2026-11-23-plugin-system-implementation-design.zh.md)

## Abstract

This note translates the normative [Lody Plugin System Spec](../../../../specs/plugin-system.md) and the boundary rationale in [Plugin architecture convergence and E2EE workspace boundaries](2026-11-22-plugin-architecture-and-e2ee-boundaries.md) into a concrete repository implementation blueprint across `@lody/plugin-sdk`, `@lody/shared`, `apps/cli`, `@lody/components`, `apps/electron`, and `apps/mobile-capacitor`. Every daemon-side OS subprocess (`PluginHost` and `DevPluginCompiler`) routes exclusively through the generic Effect process boundary in [`packages/shared/src/node/process.ts`](../../../../packages/shared/src/node/process.ts) under native Effect v4 (`4.0.2`) `Scope` ownership, while client rendering, raw snapshot reads, permanent `SessionCreationReceipt` idempotency, and E2EE signing reuse existing `ai-gui`, `sidebar-surface`, `vscode-theme`, Loro/Flock, `sessionData`/Roost, and `e2ee-execution-intent` owners with zero parallel stores. Delivery splits into four dependency-ordered stacked pull requests (`PR-1` through `PR-4`), where `PR-2` already closes a complete end-to-end interactive plugin loop across Desktop Electron and Web and `PR-3` layers raw snapshots, machine workflows, and rooted E2EE derivation. For current implementation evidence, see [Spec §17.4](../../../../specs/plugin-system.md#174-repository-evidence--current-implementation-status).

## 2. Native Effect v4 lifecycle & failure-containment contract

Per [`packages/shared/src/node/AGENTS.md`](../../../../packages/shared/src/node/AGENTS.md) and [`scripts/check-cli-process-boundary.mjs`](../../../../scripts/check-cli-process-boundary.mjs), `apps/cli` MUST NOT import `node:child_process` or call `process.kill` / `child.kill` directly. Instead, `NodeProcessApi` in [`packages/shared/src/node/process.ts`](../../../../packages/shared/src/node/process.ts) gains `spawnIpcChild` (modeled identically in `process-testing.ts`), returning a scoped Effect handle `{ pid, send, messages: Stream<unknown, ProcessIpcError>, exit, ringBuffer }`. **`process.ts` owns zero plugin business protocol:** its `Scope` finalizer executes only generic OS process-tree termination (`terminateTree`: `SIGTERM -> 2000 ms waitUntilGone -> SIGKILL -> zombie-excluded OS table verification` + `ProcessReleaseFailed` recovery lease), while `PluginHost` owns the application-level `{ type: "shutdown", graceMs: 2000 }` IPC frame before closing the child `Scope`.

`PluginHost` and `DevPluginCompiler` are authored as native Effect `4.0.2` services (`Context.Service`, `Layer.effect`, `Effect.fn`, `Schema.TaggedError`, `PubSub`, `Deferred`, `Ref`, `Clock`) satisfying [`cli-effect-ts.md#behavior-contract`](../../../docs/cli-effect-ts.md) and [`failure-containment.md`](../../../docs/failure-containment.md):

| Contract Dimension                                                     | `PluginHost` (`apps/cli/src/plugins/workflow/plugin-host.ts`)                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               | `DevPluginCompiler` (`apps/cli/src/plugins/workflow/dev-plugin-compiler.ts`)                                                                                                                                                                                                                   |
| ---------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **1. Trigger**                                                         | Daemon startup (for enabled plugins unless `--safe-mode`), explicit CLI/RPC `enable` / `reload` / `disable` / `remove`, or `--dev` rebuilds whose `machine.js` or `manifest` changed.                                                                                                                                                                                                                                                                                                                                                                                                                                                       | Explicit `lody plugin link --dev`, `pack`, or debounced (`150 ms`) source file change under watched plugin directories.                                                                                                                                                                        |
| **2. Owner & FIFO Serialization**                                      | Daemon root `Scope` owns `PluginHost`; each running `machine` plugin owns a child `Scope.Closeable`. Because Effect `4.0.2` `Semaphore` does not preserve FIFO on immediate reacquisition, per-`pluginId` lifecycle transitions use an **owned `Ref`/`Deferred` FIFO turn queue** that coalesces redundant pending `--dev` `reload` requests to the latest trailing build while keeping `disable` / `remove` strictly ordered.                                                                                                                                                                                                              | `PluginHost` child `Scope` owns an on-demand compiler worker lease. A `Clock`-backed idle timer (bounded implementation-defined window, e.g. `30 s` default, deterministic under `TestClock`) closes the compiler `Scope` when no build is queued or running, dropping resident compiler memory to `0 B`. |
| **3. Cancellation & Protocol-Clean Teardown**                          | Before closing a plugin's child `Scope`, `PluginHost` aborts its host `AbortController`, sends `{ type: "shutdown", graceMs: 2000 }` over `handle.send` (without `child.disconnect()`), and races `handle.exit` against a `2000 ms` `Clock` timer; if still alive, closing the child `Scope` delegates `SIGTERM -> 2000 ms -> SIGKILL -> waitUntilGone` to `process.ts` `terminateTree`. Daemon shutdown bounds total plugin teardown so uncooperative children never hang exit.                                                                                                                                                            | Canceling or superseding a `--dev` build interrupts the in-flight compile fiber; if the `esbuild` subprocess stops responding, closing its `Scope` reaps the tree via `terminateTree`.                                                                                                         |
| **4. Handoff, `clientDigest` vs `instanceId`, & Drain-Before-Respawn** | `instanceId` identifies a **`MachinePluginInstance` subprocess generation** and increments **only** when `PluginHost` spawns a new `machine` OS process. Client-only edits (`client.tsx`, themes, CSS) update `clientDigest` and hot-swap clients **without** restarting the `machine` subprocess or rotating `instanceId`. When `machine` respawn is required, `PluginHost` **never** spawns a replacement PID until the prior PID is gone; if `Scope.close` surfaces `ProcessReleaseFailed`, `PluginHost` retains its recovery lease and blocks successor `enable` / `reload` on `lease.retryTermination` until `waitUntilGone` succeeds. | Writes compiled outputs to a staging directory and atomically commits updated `clientDigest` + bundle artifacts only after compile succeeds (never owning or mutating `instanceId`); compile errors preserve the prior active bundle and publish structured diagnostics to `Plugin Inspector`. |
| **5. Normative Deadlines & `0` Auto-Retry**                            | Enforces exact Spec §9.3 deadlines: `init -> ready`: **`10_000 ms`**; `start` (`machine.onStart`), `query`, `mutation`, `attachment-*`, and `event`: **`30_000 ms`**; `defineTool`: **`600_000 ms` (`10 min`)**. Handshake timeout, uncaught exit, or protocol violation transitions to `Faulted` with **`0` automatic retries** and **never caches a failed startup fiber**. Crash or timeout settles in-flight `mutation` / `tool` calls as `PluginCallError { code: "outcome_unknown" }` and fails `query` calls without re-dispatch.                                                                                                    | Compiler crash or syntax/bundle error fails the single build attempt with structured file/line diagnostics; the file watcher stays alive in the daemon so saving a fix triggers the next build cleanly.                                                                                        |
| **6. Containment**                                                     | Client-only, theme, skill-only, and `sound-effects` plugins spawn `0` subprocesses. A crash, infinite CPU loop, or `--max-old-space-size=256` V8 OOM in plugin `A` affects only `A`'s PID, leaving the daemon, ACP sessions, and plugin `B` untouched.                                                                                                                                                                                                                                                                                                                                                                                      | `esbuild` runs out-of-daemon in `DevPluginCompiler`'s child process; native bundler panics or OOMs never touch the daemon heap.                                                                                                                                                                |

## 3. Data plane, UI mount stability, bundle streaming & E2EE gate wiring

### 3.1 Shared `lodyCommands` registry, Two-Tier Reads, Scoped Storage, Event Cursor & `machine.service`

- **Shared Typed Host Command Registry (`lodyCommands`, stability-tiered):** Canonical `LodyCommandDescriptor<S, TInput, TOutput>` definitions live in `packages/shared/src/commands/host-commands.ts` (Tier-1 core session/annotation/schedule commands plus shell-coupled/experimental sidebar triage commands over [`status-view/command.ts`](../../../../packages/shared/src/status-view/command.ts)). First-party UI ([`use-session-actions.ts`](../../../../packages/components/src/hooks/use-session-actions.ts)) and plugin `lody.execute` / `useLodyCommand` / `ctx.lody.execute` share `workspace-command-executor.ts` / `daemon-command-executor.ts`, routing `sessions.*` SDK aliases over the single `lody.execute` wire op. Every `host_call` carries `contextId` (`callId` / `eventId` / `"start"` / `"service"`) so the daemon binds the originating `ActorContext` (signed-in/RPC member, active `ToolExecutionContext` owner, or verified `DeclaredWorkflowGrant` workflow principal — rejecting un-attributed personal `prefer` writes such as `sessionMarkRead` with `forbidden`) and checks `manifest.permissions` (`sessions.write`, `sessions.approve`, `workflow.autonomous`, `unstable.rawState`).
- **Two-Tier Read Model (`lodyQueries` + `annotations` / Tier-2 `lody.unstable.readSnapshot`):** Tier-1 normalized `lodyQueries` and synced `<= 4 KiB` entity `annotations` (`sessionSetAnnotation` / `projectSetAnnotation`) bind directly to Loro/Flock and [`session-data`](../../../../packages/shared/src/session-data/AGENTS.md) / Roost with zero parallel Domain Store. Tier-2 `lody.unstable.readSnapshot` / `useUnstableLodySnapshot` requires `manifest.permissions: ["unstable.rawState"]`, exposes only allowlist-projected top-level domain collections (never denylist-filtered internal CRDT docs), requires explicit `collection`/`path` or bounded `turnIds`/`limit` slicing, and caps serialized slices at `512 KiB`.
- **Host-Managed Scoped Storage (`storage`), Local Event Cursor, Permanent `SessionCreationReceipt` & Long-Lived `machine.service`:**
  - `ctx.storage` (SQLite-backed on daemon) and `lody.storage` (user/workspace preferences on client) provide atomic `get` / `set` / `delete` / CAS `update` inside the E2EE custody scope, eliminating hand-rolled `.tmp` file-locking boilerplate.
  - `SessionCreationReceiptStore` persists `(workspace_id, caller_user_id, canonical_target_key, plugin_id, request_id) -> { payload_sha256, session_id, business_key? }` permanently without TTL; archiving releases `businessKey` uniqueness while retaining `requestId` history.
  - `PluginHost` records canonical `MachineHostEventMap` envelopes (including `session.archived` and `session.interaction.resolved`) into a bounded local SQLite sequence log so `{ resumeFromCursor: true }` replays missed events after restart without `onStart` full-history scan timeouts; `onStart` stays non-blocking for read queries; `machine.service(ctx)` runs with a plugin-lifetime `AbortSignal` until `shutdown` for Slack/Telegram/Feishu bridges and webhooks. Oversized `defineTool` outputs (`16 KiB .. 2 MiB`) auto-spill to host-managed turn artifact storage with an inline summary.

### 3.2 Workspace-vs-Machine Client Ownership, High-Leverage UI Slots & `blockId` stability

- **Workspace-vs-Machine Client Ownership & Multi-Machine Deduplication:** Client-only plugins (`source_key = "workspace"`) mount once per workspace, persist non-secret `scope: "client"` config in user/workspace preferences, and stay active even when individual machines sleep. Machine-bound companion installations (`source_key = "machine:<machine_id>"`) deduplicate workspace-wide client contributions (`events.on`, `commands`, `composer.slashCommands`, `composer.beforeSend`, `tools.matchRender`, `messages.renderBlock`, `sidebar.*`, `screens`, `themes`, `styles`) onto one deterministic primary instance (highest SemVer, tie-broken by `source_key ASC`). Remote Web/Desktop connections enforce per-release `clientDigest` trust and opt-in revocable `Trusted Dev Session` leases for `--dev` (re-prompting on any new `manifest.permissions` or capability class).
- **Commands, Pre-Sign `beforeSend`, Additive `enhance` Matchers & Stateful `blockId`:** Adds `commands.register`, `composer.slashCommands.add`, client pre-signing `composer.beforeSend` (visible personal-device prompt augmentation before `memberInput` signing), `lody.ui` (`toast`, `confirm`, `openExternalUrl`, `copyToClipboard`), and lightweight `session.headerActions` / `messages.actions` / `statusBar.items` slots. [`markdown-renderer.tsx`](../../../../packages/components/src/components/ai-gui/markdown-renderer.tsx) preserves mounted `PluginMessageBlockSurface` state via `${sessionId}:${blockId}:${winner.pluginId}:${winner.id}`. [`tool-call-detail.tsx`](../../../../packages/components/src/components/ai-gui/tool-call-detail.tsx) separates `"replace"` winner selection (with host `"View Raw Output"` toggle) from additive `"enhance"` renderers. Managed stylesheets mount inside `@layer lody-plugin`.

### 3.3 Five E2EE runtime gates

1. **Non-Guest execution gate:** In [`packages/shared/src/e2ee-rpc.ts`](../../../../packages/shared/src/e2ee-rpc.ts), `isE2eeFeatureMethod` includes `method.startsWith('plugin/')`, while `E2EE_READ_QUERY_METHODS` stays unchanged so `plugin/query`, `plugin/mutate`, and `plugin/attachment-*` enforce non-Guest `authorizeExecution` (`< 15 min` ledger freshness).
2. **Machine owner vs `MachineSharing` scope gate:** Daemon RPC dispatch consults [`@lody/e2ee-machine-sharing`](../../../../packages/e2ee-machine-sharing/AGENTS.md): `machine`-scoped handlers, plugin lifecycle/config writes, `DeclaredWorkflowGrant` issuance/revocation, `devSessionNonce`, and `acpProviders` require machine-owner identity; collaborators may invoke `project` / `session` handlers only while `MachineSharing` grants the machine and all bound projects.
3. **Dual-Model `e2eeIntent` (`SignedTurnOrigin` vs `DeclaredWorkflowGrant`):** Client interactive writes (`sessionCreate`, `sessionSend`, `sessionRespondInteraction`, `sessionFork`, `scheduleRunNow`) sign `E2EE_INTENT_KIND.memberInput` (`1`) after any client `composer.beforeSend` hook. **Model A (`ToolExecutionContext`):** At write time the daemon verifies the driving turn is live and matches stored `originTurn` in local `sessionData`, signing `derivedFrom` `machineInput` (`kind = 2`, active `MachineSharing`, same machine, 20-derivation cap); inactive historical turns never authorize new member derivations. **Model B (`machine_event` / `machine_startup` / `machine_service`):** Requires `manifest.permissions` (`workflow.autonomous` + `sessions.write`/`sessions.approve`) AND a verified, unrevoked, machine-owner-signed `DeclaredWorkflowGrant` covering `(workspace_id, machine_id, plugin_id, op, target_project_id, role_id)`, executing as the declared workflow principal. Un-rooted queries/mutations return `forbidden`.
4. **Iroh frame sizing:** `plugin/query` and `plugin/mutate` cap serialized payloads at `256 KiB` (one `1 MiB` `purpose 8` frame); `plugin/bundle-chunk` streams `<= 4 MiB` client bundles in `256 KiB` `purpose 9` pages and verifies SHA-256 against `clientDigest` before custody caching or `import()`.
5. **Custody directory binding, allowlist projection & static share fallback:** Daemon `ctx.dataDir`, `ctx.storage`, `SessionCreationReceiptStore`, `DeclaredWorkflowGrant` store, local event cursor ring, and client remote bundle caches live under `<account>/<workspace>/<genesis>/<signing-key>/plugins/` and wipe on E2EE member removal or device revocation; Tier-2 snapshots use allowlist-only domain projection; static plaintext share viewers disable `ClientPluginHost` script execution and render built-in raw fallbacks.

## 摘要

千条消息、万次追加的累计 CPU 与 Loro 接近，不能用历史选择加速解释过去。当前
Roost 的原子提交全部命中，但一万个追加仍产生 151,003 次串行 Native 请求，其中
五万次是返回空页的事件检查。诊断中实际 Native 写请求占进程追加 CPU 约 19%，
主线程约 49%；后者包含 SDK 提交证明复制、协议编解码和控制文档发布。该范围没有
看到全历史扫描复活，问题是单片段仍跨越过多独立的检查/发布边界。本次调查完成，
随后用户授权了隔离优化，已完成下文的本地实现和验收；Loro 实现保持固定。

## 执行与测量方法

保留同一合成用例：500 个用户/助手来回、1,000 条消息、10,000×256 B 追加，每条
助手含 16 KiB 工具载荷。FULL/WAL、每动作持久化、增量消费、完整校验和重试不变。
Loro 不重跑或改动，参照使用此前未修改适配器的完整样本。

诊断只修改仓库外的 Native JS 包副本和临时 harness。Rust addon 不变。主线程
记录每个实际追加区间及线程 CPU；Native Worker 在每次同步请求周围记录线程 CPU、
时间、方法和 JSON 字节数。主线程 V8 profile 使用 500 μs 采样，并按单调时钟
过滤至真正追加区间；消息创建、读消费者、窗口诊断及最后全量导出不纳入追加样本。
调用清单只留方法、键/表标识及少量合成调用栈，不提交捕获对话。

Native 各请求区间无重叠，可核对串行往返；没有把嵌套时长加成 CPU。进程 CPU
包含全部线程，线程计数则只覆盖主线程及 Native 请求函数，因此余项仍未完全归因。
V8 百分比是 8,350 个非 idle 追加样本的占比，不是整个进程精确 CPU 百分比。

首次诊断把 profiler 启动放进了最终校验循环，收尾时得到 `Session is not connected`；
保留为 `attempt-1`，不能当有效性能样本。修正到写循环前后，仅重跑一次新副本，
`attempt-2` 写入/重开/分页全部通过。堆 1,536 MiB、RSS 2 GiB、阶段前磁盘 4 GiB
预算不变。磁盘不足时，仅对两个已完成的合成 Roost 旧对照副本做可恢复归档，
读回 SHA-256 逐文件比对后再移除原 DB；JSON、失败库、种子和 Loro 副本均保留。

## 一万次追加到底做了什么

| Native 请求                   | 次数   | 每次追加平均次数 | Native 请求内 CPU s |
| ----------------------------- | ------ | ---------------- | ------------------- |
| 正文/收据/派生索引 writeBatch | 10,000 | 1.0              | 2.178               |
| indexRead                     | 91,000 | 9.1              | 0.646               |
| eventsAfter                   | 50,000 | 5.0              | 0.403               |
| 初次格式检查 indexScan        | 3      | 0.0003           | <0.001              |

总计 151,003 个请求，常规追加 15 次，新消息首次及初次格式检查最多 20 次。
10,000 个写结果的 `metadataAttached` / `derivedIndexesApplied` 全为 true；
因此没有退回“每片段四个写事务”的旧路径。50,000 个事件响应都为 23 字节，
对应当前 Native 紧凑回复 `{"ok":true,"result":[]}`：检查全是空页，并非重放历史。

主线程向 Worker 发送 67.40 MiB JSON、接收 6.86 MiB，合计约 74.25 MiB，服务于
2.44 MiB 新增文本及其证明/收据/进度。它是**本地线程协议**，不是网络流量、
Loro Stream offset 或落盘总字节。单次 writeBatch 已平均发送约 4.45 KiB JSON。

前 1,000 次 / 接着 4,000 次 / 最后 5,000 次追加，平均进程 CPU 为
1.451 / 1.121 / 1.082 ms，Native 请求数约每片段 15.1。该测试范围支持“单片段
固定开销很高”的判断，不支持历史线性扫描复活；不能因此推断所有更长历史规模。

## CPU 拆分与结构原因

| 插桩追加期间 CPU                   | 秒    | 占本轮进程 CPU |
| ---------------------------------- | ----- | -------------- |
| 主线程整体                         | 5.551 | 48.9%          |
| Native Worker 的 writeBatch 请求   | 2.178 | 19.2%          |
| Native Worker 的索引/事件读请求    | 1.049 | 9.2%           |
| 其他线程/请求外围/插桩等未归因余项 | 2.565 | 22.6%          |

主线程的互斥采样类别为控制 CRDT/持久化 21.84%、Native JS 协议/传输 21.04%、
SDK `structuredClone` 12.48%、GC 2.74%、其余/未知 41.89%。这只描述主线程
非 idle 样本，不能与上表 Native CPU 百分比相加；其余项不能一律认定可删除。

三个已确认的结构成本：

1. **一次追加没有形成一个完整的命令边界。** 应用层 resolve/checkpoint、收据查找、
   SDK catch-up、generation guard、提交后状态投影、operation cursor 与发布 cursor
   分别独立观察。一般命中路径共 9 个索引读、5 个空事件检查、1 个写请求，所有
   往返串行。合并写事务降低了写成本，却没有合并这些读取与观察边界。
2. **提交证明重复构造和复制。** `NodeLodyHistory.commitContentBatch` 先拥有
   writes/options，再复制给 host 的 expected/derived rows，提交后又复制缓存 plan；
   命中路径有三处 `structuredClone`。profile 的调用栈明确落在此 SDK 方法，不是
   再次复制整段旧正文。输入隔离和私有证明不可被 host 修改是正确性约束，不能
   直接删掉复制；需要改变拥有关系/提交计划表示来减少重复。
3. **Roost 控制面仍逐片段经过 Loro 文档更新。** `setRoostHistoryCursor` 的 mirror
   更新及自动持久化参与 `applyAgentBatch` 内部/等待时段。末尾额外
   `persistDocNow` 很短，只能说明该 barrier 的剩余工作小；它不说明控制库成本为零。
   本次没有修改 Loro，也不能通过静默降低通知频率或延迟持久化规避这项成本。

调用栈还确认，提交后 `refreshTurnProjections` 会清掉目标的 state cache，再经
`projectMessages → readState → lookup` 重新检查状态记录；即使命中 staged primary
也会走无状态记录查找。紧凑 agent 收据未命中后，`lookupOperation` 还查询通用
publication 收据。通用路径仍服务现有复杂写入，不能仅按“旧格式兼容”删掉。
这些是具体的重复观察机会，但每处都需保留远端事件、分支切换和重试的正确性。

```mermaid
flowchart LR
  A[256 B 流片段] --> B[应用层与 SDK 分别读取/检查]
  B --> C[复制命令与提交证明]
  C --> D[Native 原子正文/收据/索引提交]
  D --> E[状态投影与游标再次查询]
  E --> F[控制文档发布与持久化]
```

## 待讨论的优化方向

应先收拢 **Roost 专属的准备快照 → 原子提交 → 权威结果安装** 边界。将同一追加
所需的索引/事件观察合并在一致快照中，把必须持续成立的条件放进 Native 事务
比较；提交后直接使用已验证的 cursor/seq/覆盖区间推进投影，不在相邻层重新查证
同一事实。SDK 命令/证明的字节拥有关系要清楚，减少重复对象复制并保留 host
不可篡改私有证明的保证。纯 Loro 路径和控制通知语义保持不变。

这不是删除 14 个检查的授权，也不能只把它们并行跑：跨步观察可能混入远端事件。
需要配套并发/远端事件、stale、lost reply、分支切换、重试、调用方修改输入、host
修改提交参数等行为验收。它涉及 Roost SDK/Native 与 Lody 的 Roost 接入边界，
具体接口和可行收益还未验证；不能承诺消除全部差距或报出未测的加速倍数。

## 本地优化验收完成（2026-10-23）

本轮只改 Roost Node SDK 和 Lody 的 Roost 接入。代际指针与正文/收据在同一事务
比较；只有完整的本地提交证明才能安装状态（包括确认没有 overlay）并推进块间
游标；发布前仍读取新事件。goal 缓存绑定同一 Host 与新鲜游标；出错即失效。SDK
首次把证明与 Host 索引结果/参数分离，随后保留私有证明和每次给 Host 的副本，
去除成功后重复的第三次复制。所有 Native CAS 条件保留。Rust、Native 协议、
存储格式、纯 Loro、通知时机和每动作持久化均未变。

万次追加实测总请求 **151,003 → 71,503，减少 52.6%**。9,500 次普通追加为
**15 → 7** 次，其余 500 次初始化消息证明/goal。新计数为索引读 31,500、事件读
30,000、写批次 10,000、格式扫描 3 次。万次提交的派生索引和元数据均命中。
当前通用收据恢复查询继续保留，不能作为旧格式兼容删除；控制发布的 Loro 文档
成本也仍在。单独的计数运行不用于时延/CPU/RSS 结论。

同机 Apple M4/32 GiB、Node 24.22.1、堆 1536 MiB/RSS 2 GiB，SQLite WAL/FULL、
每动作持久化、同业务内容/操作身份/增量消费者和窗口诊断，原 harness 未变。
Roost 按旧→新→新→旧各两轮；另重跑未修改的 Loro 各两轮参照。两个 SDK 版本
使用同一个绝对包路径；原 Loro 103 个文件逐一核对。CPU 为实际追加的进程
user+system；不含创建、结束、窗口诊断与导出。RSS 为整个进程，增长从 backend
open 起算。数据库为控制库+历史库相对空库增量，不含 WAL/SHM；WAL 是采样分配
大小，不是累计写入字节。

累计追加 CPU 降低 13.5%–28.0%，追加 p95 降低 12.1%–45.2%；RSS/磁盘没有实质
下降。短消息和混合更新仍比 Loro 费 CPU；1 MiB 回复更快，千条消息万次追加只有
适度的累计 CPU 优势。千条/万条前缀的 20 次追加 p50 约增加 0.09/0.10 ms，冷首
追加及 CPU 未显示明显退化，不能说所有热追加都更快。本轮改善比例只用本轮配对基线，不能拿前文较老的绝对数当分母。
小样本包含 JIT/GC，万次
累计才反映持续写入。混合 tool/plan/text 未分别隔离，独立 thought/tool/plan
时延仍未测。1 MiB 完整导出有一个 183.99 ms 离群值，其余新样本 23.04–24.65 ms；
双方各加两次新进程重开后该格 n=4，原离群值仍列入范围，没有把原因归到 GC。

#### 结论与证据

当前实现的命令与发布职责没有收拢，不能据此认定单 owner、封存 Turn 的模型失效。此前确实已将正文、本地收据、元数据和符合条件的派生索引合进一个 Native 写事务；事务周围的观察与控制文档发布仍分属各层。复用提交凭据降低了成本，没有消除这个架构边界。

新增诊断仅运行 20 次合成的 256-byte 追加及独立进程重开，使用当前 SDK 和同字节的共享正文 Native。19 次普通追加各有 7 个请求，首次初始化 13 个；每次随后都调用一次控制文档发布。普通路径是：

1. 读取 generation/epoch，再检查新事件。
2. 查询紧凑操作收据；未命中后，仍有效的通用收据恢复路径再次检查事件并读取 binding。
3. 提交一个原子 writeBatch；发布前再检查新事件。
4. 更新 Loro 控制文档，完成原有持久化屏障。

这 7 个 Native 请求串行执行。所检查的普通样本为 256 字节正文传递 5,832 字节请求 JSON，其中 writeBatch 4,649 字节：14 项索引前置条件占 2,884 字节，6 项派生写入占 729 字节。这是本地 Worker 协议，不是网络或 Stream 字节。现有分层需要这些条件，包含不发事件的 generation/发布索引变动；直接删除检查或全部替换为 event cursor 会出错。让 owner 接受完整命令、以统一且受事务保护的版本校验，是待设计方案，尚未实现或测得加速。所有相关写入者必须在事务内共同推进这个版本；收据与摘要冲突恢复仍须保留。

体积还有另一组结构问题。既有逐字节审计使用已完成 CPU 优化、尚未删除可选 operationId 的共享正文基线；两后端业务内容一致。以下是一轮归因样本的写入阶段**绝对**分配量，排除 WAL/SHM：

控制文档当前 246 字节，却形成 12,001 条增量和 38,504 个 CRDT 操作。cursor/count/change 与权威 Native 提交元数据有所重叠，但当前发布游标屏障与跨 owner 唤醒依赖控制文档，不能直接删掉。即使假设整个控制库免费，Native 单库仍为该样本 Loro 整库的 1.46 倍；这是账面假设，不是可实现收益。因此 Native 布局也要审查：23,000 条 projection 记录，以及 binding、publication、branch、dispatch 索引分别支撑不同访问路径；没有证据说每个索引都可删除。重复身份与细粒度记录的表示有实在成本。普通 KV 压缩和 namespace 编号已经存在；热索引打包与页尺寸实验未通过速度/体积验收，不能再次当成新的架构修复。

此前的完整正文重复已消除：投影引用不可变帧片段。普通指定目标的文本追加处理当前消息及最近 40 条分支窗口，不加载全部旧正文。这保留了按需打开的结构优势，但不能用于替累计 CPU 或体积放大辩护。全历史导入、替换及未绑定目标的操作是另外的路径，本次普通追加跟踪没有覆盖它们。

建议的下一条边界是：正文、收据、发布进度和持久变更共用 Native 提交权威，订阅者从已提交日志首次连接和断线续读；Loro 继续承载其他协作元数据，不修改 Loro 或通用持久化。Native 存储收拢是第二项协调设计：保留精确导出/同步字节和有界查询/范围读取，同时减少稳定身份和逐记录开销。冷热分离只是一种候选，seal 时延、冷追加及完整/部分恢复代价尚未验证；不能承诺文件必然达到 Loro 大小或所有写入都更快。

实现前必须证明崩溃/丢回复恢复、摘要冲突、不发事件的 generation/分支竞争、发布顺序、订阅首次连接/重连不丢唤醒，以及待接纳远端工作。保持 FULL 与每动作完成语义；最近窗口读取、原始 wire 字节和签名/seq/owner 检查均不可退步。删收据、丢原操作或延迟持久化不属于建议方案。

原始诊断位于外部 `shared-body-validation/architecture-boundary-audit/`：请求跟踪、summary、harness/协调器及执行/恢复清单。写入、重开内容与 SQLite quick/FK 检查通过；948 个运行时/SDK/Rust 源码文件、固定 addon、103 个原 Loro 包文件、原 harness 与依赖链接核对未变。诊断时延不是新的 CPU/RSS 验收样本。本轮架构审查没有修改产品运行时、PR、发布或部署。

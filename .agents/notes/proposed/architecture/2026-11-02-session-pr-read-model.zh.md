# 会话 PR 统一读取模型

Status: proposed
Translation: current

[English](2026-11-02-session-pr-read-model.md)

## 摘要

托管版会话的 Info Bar PR 状态（开/关/合并）和 CI 摘要明显慢于侧边栏，且两者可能不一致：侧边栏读会话元数据，Info Bar 用自己从 GitHub 拉取的详情无条件覆盖元数据，而这次拉取不参与已有的按提供方修订比较，失效触发的重读还会命中浏览器 HTTP 缓存（GitHub 返回 `max-age=60`）。另外"当前 PR"的选取规则有三份实现，多仓库会话中两处可能显示不同 PR。本提案让会话元数据成为 PR 摘要的唯一来源，由 `@lody/shared` 中一个返回该会话全部 PR 视图的纯函数统一读取，所有界面只经由它取值；打开会话的提速依靠机器 PR 协调器已有的"正在查看"高频档。该函数为日后显式订阅/退订 PR 预留唯一的合并点。未验证：托管 CI 的最坏延迟从客户端 15 秒轮询变为协调器 20 秒高频档。

## 问题与证据

- `session-chat-interface.tsx` 中 `effectivePrStatus` 在 `activePrData` 存在时取 `derivePrStatusFromDetails`，`session-info-chips.tsx` 中存在实时 check runs 时忽略元数据 `s`；操作可用性也混用两种来源（`liveCiFailed`）。
- `use-github-pr-details.ts` 中由 `serverVersions` 触发的失效重读和挂载时重读调用 `fetchSlice(slice)` 时不带 `cache: 'reload'`，读到缓存后仍把 `*FetchedAt` 记为当前时间，于是这次失效不会再重读；只有 15 秒（公开仓库 300 秒）的兜底轮询会绕过缓存。
- 当前 PR 选取逻辑在 `session-list-rows.ts`、`session-tasklist-mapping.ts`、`session-github-state.ts` 各有一份；只有后者按多仓库成员仓库过滤。
- 元数据已经支持多个 PR：`pullRequests` 是协调器唯一写入的关联列表（每个仓库取最后一项为当前 PR），状态由 `resolveSessionPullRequests` 按机器/webhook 两个生命周期寄存器的提供方修订解析，CI/合并状态在 `pullRequestState[url]`。

## 决定

1. **唯一来源**：PR 状态、CI、合并状态、就绪度的摘要只来自会话元数据。客户端从 GitHub 拉取的数据只用于 PR 标签页和 CI run 明细，不再覆盖摘要，也不进入操作可用性判断。
2. **统一读取**：在 `packages/shared/src/session-pull-requests.ts` 新增 `resolveSessionPullRequestViews(meta)`，返回关联顺序的完整列表，每项含 URL、仓库、编号、解析后的状态、`ci`、`merge`、`readiness`，以及是否为该仓库的当前 PR。另提供一个主 PR 选择函数：给定仓库时取该仓库当前 PR，未给定时保留现有规则（存在旧 `reportedAt` 时按其排序，否则取最后一项）。三份重复实现删除，侧边栏、任务列表、移动端、Info Bar 及其操作状态都改用它。
3. **多仓库一致**：侧边栏对多仓库会话使用 Info Bar 未选择成员时的同一个默认成员仓库。
4. **订阅预留**：函数签名为日后的"显式订阅 ∪ 发现 − 退订"留出输入位置，本次不新增字段、不改存储，也不实现订阅。
5. **Info Bar 仍只显示主 PR**；多 PR 展示是后续工作。
6. **CI 悬浮卡片**：顶部摘要取元数据，下方 run 明细取实时拉取。
7. **提速**：打开会话会发布查看状态，协调器把该会话放入高频档，到期即在约 1 秒防抖后查询，之后每 20 秒一次；托管 webhook 几乎即时写入生命周期寄存器。本次不新增档位，不改协调器配置。
8. **拉取 hook 修正**：失效触发和挂载时的重读改为绕过 HTTP 缓存，使 PR 标签页与明细同样及时。
9. **操作后的一致性**：合并、标记 ready、关闭等成功后，按钮保持进行中，直到统一视图反映目标状态或超过 15 秒，避免按钮和状态点短暂矛盾。

## 备选方案

- **客户端观察存储与元数据按新旧合并**（被否决）：实时拉取结果写入内存存储，与元数据按修订合并，侧边栏也读它。生命周期有提供方修订可比，但 CI 的 `t` 是机器侧"上次变化"时间而非提供方修订，只能按观察时间猜新旧；一致性也仅限同一窗口，且多 PR 时客户端需要逐个拉取。
- **渲染端把实时观察写回元数据**（被否决）：需要第三个生命周期来源和规格变更，增加同步开销，且违反"渲染端不持久化详情读取结果"的现有约束。

## 影响与限制

- 一致性由结构保证：所有摘要来自同一份同步数据。
- 托管 CI 最坏延迟由客户端 15 秒轮询变为协调器 20 秒高频档；状态变化有 webhook 时基本不变。
- 机器离线时 CI 摘要不再由客户端补充，按主路径优先原则不在本次范围。
- PR 标签页的状态行仍用实时详情，可能短暂领先于摘要。

## 验证计划

- 共享纯函数单测：多仓库、旧 `reportedAt` 排序、生命周期寄存器胜出、缺失 `pullRequestState`。
- Info Bar 与侧边栏对同一份元数据渲染同一状态和 CI 的组件测试，包括实时详情与元数据矛盾的情况。
- `use-github-pr-details` 失效触发重读使用 `cache: 'reload'` 的测试（假 fetch，断言请求选项与结果状态）。
- 操作挂起直到视图更新或超时的测试，使用假时钟。

# E2EE 账号级个人设备配对

Status: proposed
Translation: current

[English](2026-11-01-e2ee-account-personal-pairing.md)

## 摘要

反复手动交换配对信息使第二台设备加入工作区过于繁琐。原 128 位秘密交换协议已实现；用户现在选择自动申请、两端核验码以及一次批准，仅授予当前工作区。自动实现增加带承诺的临时通道，保留已有入账日志、MAC 和密钥托管。约 20 位的目视比较与原手动协议有不同安全边界，因此协议增量仍为草案，原生部署验收与夹具验证分开记录。2026-11-12 owner 决定的扫码即加入：电脑在请求到达时直接显示二维码，免去再次确认即签名，代价是任何看到所显示二维码的人都能让设备加入。

## 问题

- **信任锚。** [现有流程](2026-10-26-e2ee-personal-desktop-join.zh.md)通过配对码传递 genesis 和背书者 pin；新设备正是靠这条
  带外通道才信任它收到的第一个快照。
  - 替代方案仍必须双向认证：既向批准方认证新设备的密钥，也向新设备认证批准方的密钥，同时让转发的服务端无法替换任何一方。
- **可用性。** 用户要为每个工作区处理一个码、比对完整公钥、手动点"检查"，而且新设备会停在账本页上。

## 决定（owner，2026-11-01）

### 配对字符串

- **秘密。** `S` 为 128 bit，来自平台的安全随机源。由显示码的一方生成：默认是新设备 N，反方向时是批准设备 A。
- **编码。**
  - 2 bit 版本号（`00`）加上 `S`，共 130 bit，写成 26 个 Crockford base32 字符。
  - 再加两个校验字符，取 `SHA-256("lody-e2ee/pair-check/v1\0" || 版本 || S)` 的高 10 bit。
  - 合计 28 个字符，每 4 个一组、共 7 组显示，例如 `7K2M-9QXD-4HTR-...`。
- **解析。**
  - 忽略大小写、空格和短横线；`O` 读作 `0`，`I`、`L` 读作 `1`。
  - 长度不对时提示"码共 28 个字符"。
  - 校验位不符时提示"有一个字符看起来不对，请检查"；随机错误漏检的概率为 2⁻¹⁰。
  - 两项检查都在任何网络请求之前完成。
- **二维码。** 二维码内容为 `lody://pair/<28 个字符>`。凡是接受二维码的地方，也接受纯字符串。

### 派生值

每个值都是以 `S` 为输入、salt 为 `"lody-e2ee/pair/v1\0"`、各用自己标签的 HKDF-SHA256：

- `lookupId`：16 字节，标签 `"lookup"`。这是服务端唯一能看到的值，用于在已认证账号下索引请求。
- `requestKey`：标签 `"request-mac"`。`requestTag` 为 `HMAC-SHA256(requestKey, 规范请求)`。规范请求涵盖：
  - 账号、`lookupId`、方向、显示名称和过期时间；
  - 每一行 `(genesis, 签名公钥, 加密公钥, 持有证明, 凭据哈希)`。
- `approvalKey`：标签 `"approval-mac"`。`approvalTag` 为
  `HMAC-SHA256(approvalKey, requestDigest || A 的签名公钥 || 每个工作区的 (genesis, 接纳记录哈希, 邀请摘要))`。

### 流程

1. N 提交带 `requestTag` 的请求。
2. A 通过扫码或粘贴拿到 `S` 并派生出 `lookupId`，然后取回请求，校验 `requestTag` 之后才显示任何内容。
3. 批准后，A 把 `approvalTag` 与签名接纳记录、快照邀请一起发布。
4. N 校验 `approvalTag` 之后，才固定 genesis 和 A 的背书公钥。

## 安全论证

- **替换。** 服务端要改动任何公钥、行、名称或过期时间，就必须在一把由它从未见过的 128 bit 秘密派生的密钥下伪造 HMAC。
  向 N 伪造批准也是同样的界。成功概率约为 2⁻¹²⁸。
  - 不同的 HKDF 标签把请求标签和批准标签分开，所以一种用途的标签不能被反射成另一种用途来用。
- **离线攻击。** `lookupId` 是 HKDF 的输出，不泄露关于 `S` 的任何可用信息。128 bit 秘密无法暴力枚举，因此不需要管理在线尝试次数。
- **重放与过期由客户端执行。** 不信任服务端报告的请求状态。恶意服务端可以返回一个 MAC 正确的旧请求，并谎称它仍待批准。
  - 请求原始的过期时间（最长 10 分钟）被 `requestTag` 覆盖。A 在签名前检查它，N 在接受批准前也检查它。
  - 双方都持久保存已知的终态（已批准、已拒绝、已过期）以及每个已使用的 `S`。重启或重试既不能续期，也不能让请求复活；
    N 用过 `S` 后即销毁。
  - N 只接受针对自己当前请求摘要的批准。旧的 `approvalTag` 绑定的是旧摘要，会被拒绝。
  - **剩余局限。** 如果另一台批准设备已经拒绝或消费了该请求，而服务端瞒着不说，MAC 无法发现这一点。全局一次性只在
    本地状态加 10 分钟期限的范围内成立，泄露的 `S` 也只在这个窗口内有用。不另外引入新机制。
- **社会工程（"幽灵配对"）。** 知道账号密码的攻击者，可以在自己的设备上生成一个真实请求，再诱导用户在用户自己的设备上
  扫描或粘贴它的码。这时每个 MAC 都能通过，服务端也无需作恶。持有 `S` 的一方无法把这台设备与用户自己的设备区分开。
  - 签名前，批准方显示固定警告：只扫描或粘贴你本人另一台设备上正在显示的码，不要输入任何人发给你的码；批准将授予所选
    工作区及其全部历史内容。
  - 确认步骤指明目标设备，列出要加入的工作区（每个都可取消勾选），并把设备名称标注为"由请求设备提供"、位置标注为
    "大致位置，由服务器估算"。
  - 批准后，所有已批准设备和账号邮箱都会收到"新设备已加入"的通知，并附带撤销入口。
  - 这些措施能降低风险并在事后暴露它，与 Signal 关联设备的警示相同，但无法阻止它。
- **账号绑定。** 服务端只把请求返回给同一个已认证账号。这只是纵深防御，完整性从不依赖它。
- **泄露。** `S` 是一个短时有效的持有者秘密。只有既看到它、又控制转发通道的人，才可能在 10 分钟窗口内替换密钥。没有服务端
  配合的旁观者，无法读取或改动别的账号的请求。
  - 缓解措施：码只显示在发起请求的屏幕上；只能使用一次；会过期；粘贴后 Lody 会尽力清除自己写入剪贴板的副本。
- **出处。** Signal 的关联设备二维码直接携带新设备的公钥；这样的内容太长，无法粘贴，而 Lody 还要覆盖多个工作区。Keybase kex2
  用共享秘密短语认证信道。本方案沿用 kex2 的共享秘密 MAC 思路，形式更短。

## 其他决定（手动流程）

- **发起请求。** 桌面端和移动端自动发起。网页端只有在用户点"请求访问"后才发起，因为浏览器常常是公共或共享的；
  [客户端保管 Spec](../../../../specs/e2ee/client-custody.zh.md) 有对应的待批准增量。
- **批准方。** 同一用户的任意一台活跃个人设备都可以批准；机器和恢复设备不可以。
- **位置。** 大致位置按 IP 估算，标注"大致位置，仅供参考"。
- **手动配对**使用同一个字符串。
- **范围。** 一次批准覆盖账号下的所有加密工作区，可以取消勾选。
- **Member 批准方。** Member 无法签名快照邀请。按[历史增量](../../../../specs/e2ee-foundations.zh.md#member-批准方以历史代替快照已批准增量)，它的批准行不带邀请，新设备改为验证完整历史。

## 被否决的方案

- **CPace + 在新设备上输入 6 位码。** 没有经过审计的 JavaScript CPace 实现，而且它引入了一套需要单独审查的协议。
- **在两块屏幕上比对短认证串**（配合承诺-揭示）。需要额外的安全论证和交互，而且比对很容易被直接点过去。
- **输入短认证串。** 短码必须配合 PAKE 或承诺协议才安全，同样多出交互。
- **像 Signal 那样把完整公钥放进二维码。** 太长，无法粘贴；而且 Lody 每个工作区都需要一套密钥。
- **所有工作区共用一把设备密钥，或新增账号级账本操作。** 两者都会无谓地改变按 genesis 划分的保管或账本。

## 批量签名与失败

- **写日志。** A 在任何网络步骤之前，把每个工作区的精确 `AdmitDevice` 原件和请求 ID 写入日志。
- **重试。** A 重试同样的字节，按原件对账未知结果，从不重新签名；崩溃后继续处理剩余的工作区。
- **每个工作区的状态。** 每个工作区只会处于三种状态之一：已接纳且密钥已送达、已接纳等待送达、未接纳。
- **新设备的身份。** N 在提交前就保留了每个工作区的身份。之后的请求会复用它们，N 绝不在其上重新生成身份。

## 中继契约

公开的中继 DTO 位于 [`packages/cloud-api`](../../../../packages/cloud-api/src/e2ee-account-pairing.ts)
的 `e2eeAccountPairing` 下：提交、待处理列表、按查找 ID 读取、拒绝、发布和领取。

- **权威字节。** 客户端只信任规范的请求字节、批准字节及其标签。状态、设备名、过期时间、位置和工作区路由列表都只是建议性副本，用于路由、限流和通知。
- **多个批准者。** 领取会返回所有已发布的批准，因为每个批准者只覆盖自己能签名的工作区。
- **接纳记录。** 接纳记录走现有的账本追加路径。每条邀请行都带上批准者在该工作区的设备访问凭据。

## 客户端界面

宿主端口是 [`packages/platform`](../../../../packages/platform/src/e2ee-account-pairing.ts)
中可选的 `E2eeAccountPairingRuntime`。页面在 [`e2ee-account-pairing.tsx`](../../../../packages/components/src/components/pages/e2ee-account-pairing.tsx)。按 owner 2026-11-04 的决定默认显示，不需要开发者模式，也没有客户端开关。紧急关闭由服务端返回 `e2ee_account_pairing_disabled` 实现，页面会说明原因；单台设备上的本地设置无法在全局范围关闭该流程，因此不再保留。

- **职责归属。** `S`、每个标签的校验、有效期检查、终态记录和签名都由宿主负责。界面在本地校验输入的配对码，只是为了在发出任何网络请求之前指出输入错误；解码出的字节随即清零。
- **何时显示。** 宿主没有实现这些方法时，界面什么都不显示，原有的按工作区配对仍保留在下方。桌面端通过 IPC 实现这些方法；可移植 host 能审批，原生请求端通过验证历史接入，浏览器请求端按真实能力显示。

## 验证局限

- 字符串格式、密钥派生、规范的请求与批准字节以及两个标签都由 `packages/e2ee-core/test/pairing-vector.json` 固定。该向量由一个只用标准库的独立 Python 生成器（`test/generate-pairing-vector.py`）产生。
- 账号配对后端在私有仓，默认开启并保留紧急关闭。自动发现遵守同一开关；应用挂起时的推送与位置估计不在此次验证范围。
- 有一个端到端测试，跑在真实的桌面 custody、bootstrap、账本宿主和 SQLite 上，中继是内存实现。还没有打包、原生或真实后端的运行。

## 桌面宿主

共享的流程位于 [`@lody/e2ee-client/account-pairing`](../../../../packages/e2ee-client/src/account-pairing.ts)，持久状态通过 `AccountPairingStore` 端口存取。[`e2ee-account-pairing.mts`](../../../../apps/electron/src/main/services/e2ee-account-pairing.mts) 是桌面端的 SQLite 存储与组装。[`e2ee-account-pairing-host.mts`](../../../../apps/electron/src/main/services/e2ee-account-pairing-host.mts) 把它接到按工作区的宿主上，`E2eeIpc` 再把它暴露给 #2196 定义的宿主接口。

- **工作区列表。** 渲染进程把自己的加密工作区列表作为路由提示传入。宿主会用该工作区自己的账本或请求标签，校验每一个 genesis。
- **新设备。** 新设备为已验证历史中分配给本账号 crypto user 的那个成员身份提供持有证明。accept 时，它按受标签认证的账本哈希找到接纳记录，把该记录的签名者当作背书者，再通过现有的按工作区加入日志安装邀请。
- **Member 批准方。** Member 的邀请端口返回 `null`，因此批准行的邀请摘要为全零（中继正文是一字节占位）。新设备从标签认证的创世记录验证完整签名历史，按认证的记录哈希找到自己的接纳记录，以其签名者为背书方，经按工作区的历史路径安装。带邀请的行仍走快照路径。线格式和中继格式都不变。
- **安装之后。** 新设备会打开工作区、刷新，并用自己的凭据跑一轮密钥安装，做法与按工作区的 claim 相同。这一步尽力而为：之后打开工作区时还会再执行一次。
- **运行时条目。** 流程打开的每个运行时条目，如果没有窗口在读该工作区，用完后都会关闭。
- **未完成的按工作区配对。** 如果有一个无关、未完成的按工作区配对，它的日志行会保留。对应工作区显示为 `blocked`，界面会写出它的名字；完成或取消那次配对后，请求会继续。
- **密钥。** `S` 只保存在内存里，从不写入磁盘。重启会在本地结束这个请求，之后设备会用同一批保留的身份发起新请求。
- **终态。** 已批准、已拒绝、已过期和已取消，按 lookup ID 记录在本地 SQLite 中。第一个写入的终态生效，之后不再改变，也不会因为中继报告的状态而复活。
- **批准方。** 批准方先用标签认证请求，并按自己的时钟检查过期时间；每次签名前都会立即重新检查这两项。
  - 每个工作区签好的准入原件在任何网络步骤之前写入日志，之后原样重试，重启后也一样。
  - 日志按工作区和新设备的签名公钥记录，而不是按请求记录。如果请求在准入之后、送达之前过期，同一个保留身份发起的下一个请求会复用那份原件，所以同一个工作区绝不会被签名两次。
  - 配对操作逐个串行执行，保证检查、签名和写日志是原子的。
  - 无论以何种方式结束，包括失败和中断，密钥和派生密钥都会被清零。
  - 只有本设备自己校验过批准标签后，批准才会发布。它的 `approverSigningPublicKey` 取按 genesis 排序后第一行的签名者；每一行的记录哈希绑定了该工作区实际的签名者。
- **新设备。** 只有同时满足四个条件，新设备才会安装邀请：批准标签校验通过；批准绑定的是自己的请求摘要；自己的过期时间还没到；邀请摘要一致。中继给出的其他内容一律忽略。
- **解码。** 中继传来的字节由 core 的严格 `decodePairingRequest` 和 `decodePairingApproval` 解码，只接受规范编码。

## 便携宿主

[`account-requester.ts`](../../../../packages/e2ee-client/src/account-requester.ts) 是手机端和 Web 端的新设备一侧，由个人设备宿主实现。

- **固定 offer。** 便携身份的凭据包绑定一个 offer，但账号级流程是在还不知道批准方的时候就生成身份的。所以每个工作区使用一份固定的账号 offer：包含它的 genesis 记录和成员身份、一个占位背书者（`00…`），以及由工作区 ID 派生的 `pairingSessionId`。之后的每次请求和重新打开都能找到同一个身份和同一份日志，本地凭据格式也不需要改动。
- **真实背书者。** 批准标签认证了某条准入记录的账本哈希，这条记录的签名者就是真实背书者。它和批准原件一起保存，快照校验和账本起点都用它代替占位值。
- **身份保护。** 身份保护仍由各平台的 custody 负责：手机端用 Keychain 或 Keystore，Web 端用 web-crypto。
- **已知限制。** 便携宿主目前还不会报告未完成的按工作区配对，所以这种工作区不会显示为 blocked。

## 当前工作区自动核验（2026-11-10）

用户在 `318781d5` 会话批准 Ryugi 流程：手机打开工作区即显示核验码，已有设备一次授权后手机自动继续。只授予当前工作区；“稍后”保留数量入口和原请求。这是 UI 批准，不是独立密码学审查，foundations 的自动协议增量仍为草案。原手动协议和单工作区邀请保留。早期拒绝 SAS 的原因仍成立：需要单独安全论证，而且用户可能跳过比较；本次 UI 选择重新权衡了操作成本。

带承诺的 P-256 ECDH 绑定账号、工作区、genesis、请求 ID、设备名和原期限。响应方得知请求端公钥前，先承诺带域标识的规范上下文、随机 peer ID、公钥和 256 位随机 nonce 的 SHA-256。双方固定对端第一条消息，再通过共享密钥及完整 transcript 的 HKDF-SHA256 分别导出比较码和 128 位配对秘密。relay 只传公开消息，现有请求／批准 HMAC 仍认证入账。批准端不显示自身的码，而是让用户输入新设备上显示的六位码，本地一致才签名；连续输错三次即作废本次请求（owner 于 2026-11-11 在设计审核 `5b3fb2d9` 后决定，避免一次误点就接纳攻击者设备）。比较强度约 20 位，不继承原手动交换的 128 位带外认证。承诺顺序阻止响应方看到请求端公钥后再挑选密钥或 nonce。这不是 PAKE，也不表示完成了独立审计。

响应前必须读到本地已验证的个人身份；元数据和 relay 的 approved 状态不授予权限。原生准备和重开使用固定账号 offer、占位 endorser 和从工作区派生的 session ID，实际签名者保存在已认证批准描述中。批准后换掉日志键会导致重开找不到原身份。原生请求端现在通过已验证历史接入；可移植 host 可审批，浏览器请求端仍按实际能力显示。私有账号配对 relay 已默认开启，保留显式紧急关闭。

## 扫码即加入（2026-11-12）

owner 要求手机扫完码就能直接加入、不再有额外步骤（会话 `207baaf6`，2026-11-12）。反向配对时，批准方设备在自己显示的码下验证到请求后，立即为所列全部工作区签名，并列出它无法批准的工作区。最初版本只在点击后显示该码，以免掌握账号密码者发起请求就能让持有者秘密出现在屏幕上。owner 审阅这一取舍后选择直接显示：电脑在请求到达时直接在批准窗口中显示，控制台“添加设备”操作立即显示，手机只在用户要求时显示（手机通常是扫码方）。接受的代价是所显示秘密的暴露：十分钟内通过屏幕共享或摄像头拍到它的人可以让自己的设备加入。窗口会说明两种方式的范围：扫码把手机加入此设备上的加密工作区，输入六位码只批准当前工作区。每个码最多批准一次，窗口隐藏时暂停。新设备在扫码加入报告 joined 之前不结束自动发现记录；扫码加入被取消或失败时结束自己的请求；若其他工作区已加入而批准方无法解锁当前工作区，则停止并说明原因。这一判断来自协议状态而非计时：请求按工作区报告已验证批准的覆盖情况（`waiting`、`approved`、`omitted`），批准方只有在其接纳的每个工作区都有邀请后才发布批准，因此 `omitted` 是确定的，已批准工作区的缓慢安装不会被中止。批准方锁定已验证的请求，每次轮询都继续同一批准直至送达：`awaiting-delivery` 和临时故障保留该码，只有带类型的拒绝才结束。自动配对的 relay 调用都有时限；取消先在本地落定并分离请求，再发送 relay 通知，因此离线 relay 不会阻塞新请求。

新电脑还会在六位核验码旁显示 `lody://auto-pair?id=…&code=…` 二维码。批准该请求的手机扫码即可代替手动输入；扫到其他请求的码不发送任何内容，匹配的码进入同一本地比较与输错计数。用手机系统相机扫到的同样链接会交给收件箱或加入页。手机和平板负责扫码、电脑负责显示，角色取决于设备而不是窗口宽度。

`packages/components/tests/e2ee-account-pairing.test.tsx` 中的组件测试覆盖窗口中直接显示的二维码及范围说明、无需点击的单次批准、扫码加入后的延后处理、保持发现记录的扫码加入、取消与部分加入、请求 ID 校验、系统相机链接以及桌面/手机布局。iOS/Android 真机摄像头解码、原生链接投递和打包应用中的行为尚未验证。

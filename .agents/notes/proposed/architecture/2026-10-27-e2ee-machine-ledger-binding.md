# Machine identity in the permission ledger

Status: proposed
Translation: current

[中文](2026-10-27-e2ee-machine-ledger-binding.zh.md)

## Abstract

Realtime authorization needs an authenticated relation between a product machine ID and its device signing key; a machine directory cannot supply that authority. The owner has approved extending the existing machine AdmitDevice record before ledger v1 freezes, including atomic replacement of the old key for that same machine ID. Replacement keeps historical identities and requires epoch rotation before new content is sealed. Machine possession covers the same strict UTF-8 ID; the existing credential-binding proof rejects reuse across pairing sessions. The implementation and independent vector reflect these approved pre-freeze choices, while deployment, remote pairing and the complete rotation barrier remain outside this draft.

## Approved boundary

The approving device signs machineId together with the new device keys and an explicit old signing key for replacement, or no replacement. There is no new operation, capability code or tag9 declaration. At most one currently active device may own a machineId within one workspace. Replacement must name that exact active machine, have the same machineId and membership, and use the existing personal-device admission/revocation authority. Owner/Admin status does not grant cross-member machine takeover. Signing and encryption keys remain permanently non-reusable.

The old device leaves current state and the new device enters it in one transition. Every validation precedes either mutation. History retains the old identity; revocation or member removal releases only the active machineId binding. Atomic replacement sets rotationRequired. Admission must never clear an already pending rotation, and new sealing stays blocked until the normal epoch publication completes. This does not implement the PR20 sending barrier.

Clients obtain machineId-to-key bindings exclusively from a genuine verified ledger view. Backend projections only reflect the result of that verification. Projection, credentials and checkpoint remain one completion transaction on create, append and recovery. Any deterministic storage-readiness check also runs before reservation/CAS; a successful external append must not acquire a new unfinishable policy check at settlement.

## Format and rollout

This is an explicitly owner-approved, pre-freeze change to existing tag4. Old development machine records are current-only failures: recreate those workspaces rather than adding a legacy decoder or migration. Snapshot state, retained state and the state-digest format/domain advance together to version 3. Their packed device table keeps historical kind and active status, and their machine table keeps every historical binding; restoration rebuilds the active-only index. The independent Python/PyNaCl v1 vector was regenerated with machine admission and atomic replacement coverage. The owner has also approved binding machineId in the machine possession message, signed by the machine itself and reconstructed from the admission record at verification. Personal-device possession bytes remain unchanged. CLI preparation must produce the new machine proof. Session replay remains the responsibility of the existing bindingSignature, which binds the complete pairing exchange to its session. Session IDs are one-time pairing context and must not be added to possession or permanent ledger records. The regression boundary is the combined possession and bindingSignature material: it must fail when reused in another session. Separately, verification must reject a modified machineId, a mismatch between the machineId signed by possession and the admission record, and reuse in another workspace. Personal-device possession remains byte-for-byte unchanged.

The owner-approved representation is a strict UTF-8 byte string of 1..256 bytes without normalization. Encoding rejects lone UTF-16 surrogates rather than repairing them; decoding rejects malformed or noncanonical UTF-8 and retains a leading BOM as identity data. Valid strings compare exactly because strict UTF-8 is injective. The local socket applies this machine-specific byte limit without changing account/workspace identifier limits. A new machine record is `[4,1,signingKey,encryptionKey,possessionSignature,machineIdBytes,replacedSigningKeyOrNull]`; its possess/v2 tuple appends the identical machineIdBytes. Personal/recovery records and proof tuples remain unchanged.

Public core must be adopted before the corresponding backend can deploy. The backend feature branch must not include a private gitlink change; any local combination validation must name its separate core candidate. Current-only rollout must account for old developer workspaces and unresolved original writers before adopting the incompatible codec. It must not skip verification, delete an uncertain writer or silently treat an old machine as an unbound new device.

The CLI instruction scope retains all binding rules and moves explanations to this note. The Fleet PR poller owns hosted GitHub ports independently of the workspace cloud port, so the latter cannot prevent repository/branch disclosure on its own. Old catalog v1 schemas discard `contentMode`; caching unknown modes could reopen them as plaintext offline. Native SQLite recovery can change physical files before application validation, even for rejected formats. The accepted file-global clock floor can expire new requests across workspaces and restarts until time catches up after a forward jump. These remain the existing contracts; compacting instructions changes no product behavior.

## Verification so far

Core regression covers strict UTF-8 bounds/BOM/no normalization, proof substitution, old-format rejection, same-member atomic replacement, branch isolation, historical key non-reuse, all three view sources, corrupted/duplicate snapshot bindings, and asynchronous signing-input capture. CLI and Electron regressions retain original bytes, reject cross-session material, preserve interrupted A-to-B activation and compare verified machine IDs. Backend tests exercise normal/lost-ACK replacement settlement and reject invalid candidates before CAS; old credentials remain recorded but fail immediately after settlement.

The real Lab workflow exposed a command-capture omission: WorkspaceControl copied only the old fields. It now owns machineId and the replaced key before waiting, and the actual SDK/SQLite consumer tests both initial admission and atomic replacement, including rotationRequired. Components consuming the frozen vector now assert its new record positions, heads and active machine count without relaxing endpoint checks. The jsdom consumer also verifies that encoder output is owned in the current realm before strict validation; malformed UTF-8 and all size/equality restrictions remain unchanged. Validation counts and final candidate fingerprints are recorded in the handoff. These results are not gateway, keychain, installer or product acceptance.

The original author's ACP lock alignment is now present in main. After a non-overlapping rebase, frozen installation succeeds without this feature changing any dependency manifest, lockfile, ACP source or gitlink. The rebase preserves the reviewed product patch; affected-scope verification and remaining CI results are tracked in [PR #1940](https://github.com/LodyAI/Lody/pull/1940). The owner authorizes reuse of exact-tree focused evidence and independent reviews; complete suites belong to CI, and the stopped local full run is not a passing gate. Draft publication does not authorize ready state, merge or deployment.

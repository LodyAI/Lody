# 会话切换成本与初始历史就绪

Status: proposed
Translation: current

[English](2026-10-17-session-switch-rendering-cost.md)

## 摘要

真实浏览器测量将会话切换的同步工作与等待可读历史分开：24 次切换的点击到绘制为 104–314ms，独立视觉采样则确认一次首次观察的会话约第四秒才从骨架变为可读。已实施的小修正去掉初始 Roost 页自身推进观察 epoch 时产生的一次多余 owner 往返。确定性的生产 reader 回归与受控浏览器对照验证了该依赖，正常首次打开和缓存命中对照基本不变。更广泛的渲染优化仍是提议，此修复和已录制的 10.84 秒内容候选都不能证明托管页面数秒等待的原因或已被消除。

## 范围与职责

用户要求先审计会话切换，再对已证明的大头做小范围优化。合成测量和首版实现使用 `4cc74cae8` 及其已有无关改动；真实录制使用 Chrome 155 中已经打开的托管页面，部署源码版本未知。PR 只把初始页修正迁到 main `450595e07`，保留其增量历史与首次打开被取代后的恢复。

渲染端 bridge 负责 owner 读取、只读 IndexedDB 投影和通知顺序，ConversationView 负责目录与租用正文，React 和滚动引擎负责显示窗口。owner 接受、持久 checkpoint 覆盖和命令仍是独立职责。意图见[历史显示读取](../../../../specs/session-history-writes.md#backend-selection-and-display-reads)。后续 main 的[增量恢复决策](../../implemented/bug-fix/2026-10-16-roost-incremental-history.md)已经替代早期全量刷新调查，不能用旧审计把这些已修复机制重新报成缺陷。

此处只保留匿名汇总，私人对话、原始 trace 和截图留在仓库之外；所有回归与浏览器实验历史均为合成数据。

## 决定优先级的证据

四段原生控制的 Chrome Performance 录制覆盖两组托管负载的 24 次真实侧栏点击，没有重载、清存储或人为 CPU／网络限速。DevTools 独立成窗以保留页面宽度，开启 JS 采样和截图。录制开销和小样本不支持延迟分位数或所有设备的保证。

| 负载／终点                 | 观测结果                                                | 解释                             |
| -------------------------- | ------------------------------------------------------- | -------------------------------- |
| 首组公式较多会话的重复返回 | 点击到下一次绘制 191–262ms，处理器 167–214ms            | 热数据下也有同步成本。           |
| 慢工作区十次重复访问       | 点击到下一次绘制 184–314ms                              | 重复切换有独立的响应成本。       |
| 三个首次观察目标           | 最后软导航内容候选为 1.36–1.57 秒                       | 首次绘制不等于可读内容已就绪。   |
| 另一个首次观察目标         | 最后内容候选 10.84 秒，处理器约 124ms                   | 晚指标本身不能定位首次可读帧。   |
| 独立连续视觉样本           | 3.866–4.105 秒截图仍为骨架，下一张 4.106–4.320 秒已可读 | 一次访问确有约四秒用户可见等待。 |

10.84 秒案例在 bootstrap 之后的 8.9 秒区间内约有 8.5 秒被采样为主线程空闲，较晚历史缓存回调之后才有 168.6ms 主线程任务。80 次 `readTurn` 成功回调集中在末尾，没有覆盖先前的空闲间隔，不能据此归因成十秒 Markdown CPU 或八十次慢 IndexedDB 串行往返。owner 执行、传输与就绪等待仍需对应操作的关联证据。

录制的截图预算在该交互之前耗尽，无法重建它的首次可读帧。之后一次返回的首张截图结束于 2.073 秒且已经可读，那只是另一次热访问的上界；另一个视觉样本存在辅助功能快照造成的采样缺口，也无法细化首次可读时间。不能把这些观察合并成一个延迟。

一个 214ms 处理器内，React 同步 flush 包含式采样约 168ms，Markdown／KaTeX 约 21ms，滚动 `afterCommit` 约 32ms；这些路径重叠，不能相加或归给单一组件，实际大纲只有 13 条刻度。另一次首开在 SDK `loadDoc` 中采样约 102ms，含 import／export CPU，并非 I/O 延迟。

独立生产版 Storybook 移除大纲的对照证明另一种负载的成本：两个已热加载的 3000 条消息区各有 1500 条刻度，移除后子树重挂载就绪中位数从 71.1 降为 14.9ms，CPU ×4 时从 281.5 降为 58.9ms，DOM 从 5437 降至 932。这排除了路由、store 和文档准备，不能解释托管公式会话或异步等待。生产 Hook 探针只为消息流打开 40 条正文，完整事实消费者最终通过 75 个逆向页覆盖全部 3000 条；热重挂载不新增正文读取，仍有按历史规模的索引遍历。这些是规模候选，没有证明每个隐藏消费者都会阻挡首屏。

## 已实施的初始页修正

旧协议／非 checkpoint 初始化记录 `observedDirectoryEpoch`，读取最新页、排空通知，再在 epoch 改变时重试。已校验 owner 响应自身也会通过 `notifyChanged` 或首次确认 owner 推进 epoch。旧持久快照无法服务较新观察时，把这次自身通知当成失效，就会在返回已校验页之前再次请求 owner。

修正让页携带对应的 epoch：缓存页保留读取前隔离；普通 owner 页只有在响应版本仍为当前版本时才采用读取后 epoch；一致的增量 checkpoint 保留 main 允许其暂落后于较新提示的行为；排空通知后仅在目录 epoch 仍匹配时返回。

后续结构通知仍要求重试，普通过期响应继续走 main 既有恢复。协商的一致 checkpoint 不必追上每个新控制提示后才能可读。游标兼容、缓存接收、原子替换和命令接受路径保持原职责，不能把不完整替换发布成完整快照。

回归使用真实 bridge、缓存和组合 ConversationView，配合 fake IndexedDB 与显式 Promise 信号：revision 1 尾部缓存保留，未缓存读取观察 owner revision 3，首个最新页报告 revision 5。修复前阻塞重复最新页请求会阻挡初始就绪，修复后 reader 与生产视图均能拿到已校验页及当前尾部正文。并发控制推进覆盖旧协议重试到新正文，以及一致增量快照落后于新提示时的正常进展。

生命周期评估：观察启动初始等待者，bridge 拥有共享请求、缓存和通知队列，释放一个观察者不会取消另一消费者的原始工作，dispose 保留既有发布隔离。交接仍要求已校验页和目录 epoch，真正失败仍由现有恢复负责。补丁只增加结果元数据，不增加资源、重试 owner 或确认等待。transport、缓存和通知仍有未迁移的 Promise 依赖，只包装等待者不能完成生命周期单元，故暂缓原生 Effect 迁移，迁移账本事实不变。

## 受控浏览器对照

临时生产版 Storybook 同时包含 `4cc74cae8` 审计工作区的基线与修正版 bridge，其余构建相同。两侧各有独立缓存／会话及 120 条合成历史，在内置浏览器默认 1280 × 720 视口中实际运行 IndexedDB、ConversationView、消息 Hook、Markdown 与滚动引擎，只模拟 owner 响应及等待，不测真实传输或 owner 存储。

两侧从合成缓存／owner 前置准备完成后计时。requestAnimationFrame 探针要求真实 Markdown 目标段落与消息视口相交，且初始布局已就绪；这是绘制前 DOM／布局终点。排除一组预热后，十六组成对对照不同时采样截图：

| 初始状态           | 每请求注入等待 | 组数 | 修复前首次可读帧中位数 | 修复后首次可读帧中位数 |
| ------------------ | -------------: | ---: | ---------------------: | ---------------------: |
| 旧缓存／较新 owner |          800ms |    5 |               1640.9ms |                835.4ms |
| 旧缓存／较新 owner |          300ms |    5 |                654.5ms |                329.2ms |
| 正常打开，无缓存   |          800ms |    3 |                858.4ms |                844.3ms |
| 当前缓存直接可读   |          800ms |    3 |                 31.3ms |                 36.0ms |

触发场景可读之前的最新页响应由两次变为一次；无缓存对照两侧均一次，当前缓存对照均零次。这支持该路径少一次往返，不能代表所有切换提速 50%，也不能把对照的微小差异视为明确收益。另一次每请求等待 1500ms 的视觉对照保留 67 张未修改截图，DOM／布局终点分别为 3049.7 和 1540.4ms。自动化点击之后 2.157–2.255 秒的截图中，旧侧仍是骨架，新侧已能读答案与表格。截图起点含输入／准备开销，与 DOM 探针起点不同。

该浏览器构建早于迁移到当前 main，没有测量迁移后 main 的新构建。它不含路由／运行时／store 启动、控制文档 bootstrap、完整 SessionChatInterface 消费者、真实 RPC／owner 延迟或私人托管负载；当前 main 的确定性验证单独报告，不能据此推算托管页面四秒等待能去掉多少。

## 暂缓工作与保留契约

增加通用渲染机制前，先关联一个前台历史操作。源码已优先读一致的本地页；骨架只是空消息流占位，状态计时器不会阻挡已存在列表，另加通用缓存或缩短骨架计时不是已证明的修复。

长大纲实测负载可单独做固定间距刻度窗口化，保留导航、焦点、悬停和跳转。未访问子消息区懒挂载、增量投影应分片测量，保留待完成 fork 就绪和完整业务事实。不能延后 SessionDetail 身份边界，URL、输入框和发送／归档／重命名目标必须一起切换；不能统一删除 `flushSync` 或几何读取，锚点、覆盖修正和重新显示仍需正确测量。Markdown AST 缓存、Worker 迁移和滚动引擎重构仍是提议，不属于本补丁。

# 不依赖历史后端的本地发送接纳

Status: proposed
Type: architecture
Translation: current

[English](2026-10-13-backend-independent-send-acceptance.md)

## 摘要

Roost 就绪消息原先等待所属机器的历史 IPC/RPC 后才发布写入通知，发送交互因此暴露了
网络和存储延迟。已实现的方案在本地接纳一份冻结输入，独立保存，再通过原子、不可变
的所属机器回执完成交接。普通消息复用原有用户内容渲染器，不增加状态标签；执行仍须
等待所属机器确认历史。行为测试覆盖请求中断、保留的存储代、取消，以及输入与队列的
混合排序。使用已发布 SDK 的 Cloud 打包 App 还验证了本机恢复与远程重试：所属机器
暂停时消息先显示，恢复后收敛到一份所属历史记录。这些设备样本验证时序，不承诺延迟
指标，首次显示也不证明已经持久化。

## 决策与替代方案

Loro 的本地历史文档已承担本地接纳，以及异步 Repo 持久化和同步。Roost 渲染适配器
没有等价的可写副本：所属机器仍负责历史签名与存储。因此发送端保留就绪输入，不建立
第二份历史文档或签名 writer。维护者要求采用这个本地接纳方向并沿用原有展示。

仅增加内存气泡会失去已保存输入的恢复能力；完整的可写 Roost 副本则涉及签名、所有权
与同步，超出本次范围。旧的[发送日志删除决策](../../implemented/simplification/2026-09-29-remove-session-send-journal.zh.md)
仍提供历史约束：未准备好的 Blob 只在内存中，结果不明的 guide 不重放。新保留记录
只包含不可变的就绪 Roost 输入及最终附件引用。

## 职责与生命周期

1. 接纳时冻结账号/workspace、用户、目标、会话和 turn 身份、内容、输入配置及投递
   意图。新会话先本地提交路由元数据，再允许界面获取历史 store。消息先显示，所属
   机器的工作随后完成；本地持久化在后台完成。
2. IndexedDB 按账号/workspace 隔离，按接纳顺序保留就绪输入。保存新输入时，先用
   `parseHistoryWrite` 规范化 entry，再做存储校验，让包含 `text: undefined` 的
   图片/文件数据与普通历史写入保持一致。已持久化记录仍严格解码，同一 ID 的内容
   冲突仍会报错。保存失败时，投影刷新
   仍保留唯一的内存副本，并阻止同会话后续消息越过它、保留离开确认。普通缓存恢复
   保留这份用户数据库；明确的完整重置可以删除它。
3. workspace 的原生发送资源 scope 持有真实存储、会话 Web Lock、store 借用及所属
   机器/控制面 I/O。Promise 协调器不声称完成了文档/RPC 生命周期的原生迁移。
   跨窗口 worker 在共享锁内重读存储。控制队列继续使用 Loro writer，但同一锁内
   等待先前输入；后续输入不会成为前置条件。合并投影保留本窗口接纳顺序及持久化的
   其他窗口顺序，也保证最新暂存输入的运行配置不会被旧输入覆盖。
   附件准备将输入交给持久化 owner 后，即使暂存队列仍在等待，重试也发给该 owner。
   仅发生在准备阶段的失败继续走暂存队列的重试路径。
4. `sessionInputAcceptance` v1 独立协商 `accept_input` 与只读 `inputAcceptance`
   查询。旧目标或已改变目标明确报错，不回退后端。获取到的渲染端 port 必须绑定到
   冻结的目标，不能只信可变元数据。原有身份/访问检查及 RPC 拒绝回执继续生效。
5. SDK 在写历史的同一事务内绑定操作身份与不可变内容指纹。查询缺失仍是未知结果；
   重试完全相同的接纳操作可以和晚到的原请求安全收敛。当前及保留的旧存储代回执
   优先于分支位置。改变输入会冲突，已删除输入不会被重建；不可读历史表示观测失败，
   不能当作已经删除。
6. 执行边界是所属机器的历史/回执原子提交，不是发送端已经观察到回复。回复丢失时，
   daemon 仍可能启动已提交的 pending 历史，沿用 Loro/历史的原有契约。发送端仅在
   观察到接纳后写激活或发起 guide；本地投影本身不能执行。guide 发起前记录防重放
   标记，中断后不再
   发起同一次 guide。确认历史不等于 Agent 已执行。本地消息保留到权威 view 包含
   同一 ID，界面不同时显示两份。
7. 取消、归档、删除不依赖本窗口快照，而是找出共享存储中的记录，先持久化取消，
   再等待本地真实工作和相关会话锁。其他窗口投递前检查该标记。取消不能撤销远端
   历史写入。关闭时等待已启动 I/O，已保存的未知输入按原身份恢复。

## 验证与剩余验收

发送端所属测试通过 fake-indexeddb 验证真实 IndexedDB 事务行为，使用原生发送资源、
真实 Loro 控制面/所属历史文档及实际 workspace writer。显式 gate 覆盖立即显示、输入
冻结、确认丢失/缺失、存储恢复和顺序、重启及账号隔离、历史删除、忽略 abort 的 I/O、
快照落后的窗口取消、guide 不重放，以及一个或两个窗口中的控制队列。UI 测试验证普通
消息外观及没有附件草稿时已就绪图片/文件的显示。

生产接收端测试使用已固定的原生 SQLite 包，覆盖回执和内容冲突、历史推进、重新打开、
旧存储代删除、投影不可读，以及重试或原请求先完成、期间发生存储代替换的竞争。
浏览器及 Node SDK 的分支测试验证相同的原子回执边界。这些合成测试验证相应边界，
不证明原线上事件的起因或真实设备延迟。

Cloud 打包测试发现了本机传输的一处遗漏：Zod 协议包含 `accept_input`，Node 的轻量
请求/回执守卫却没有接受它，桌面因此在所属机器执行之前拒绝请求。TS 守卫现已接受
该操作，CJS 镜像也补齐历史契约；所属的声明操作测试同时检查 schema 的每一种操作，
防止未来新增操作时漏掉任一方向。测试还覆盖不可变回执查询和无效回复。

同一轮发行包恢复测试还发现，本机身份探测尚未确定所属机器时选中的传输通道会被
缓存。历史桥接现在每次操作都解析同一所属机器当前使用的平面，让已有 store 随
本机身份变化使用正确通道，不改变历史后端或收件机器。所属桥接测试覆盖跨越这些
变化的回执查询、接纳、历史读取及已保留回执。

Lody 固定使用已发布的 TypeScript SDK `@loro-dev/roost@0.1.3`，原生
`@loro-dev/roost-node@0.1.2` 依赖图不变。使用全新缓存下载的 registry 包与已测试
tarball、依赖锁的完整性一致，安装后的 57 个文件也与下载包逐一相同。
[会话文件草案](../../../../specs/session-files.zh.md#7-提交身份与本地写入)
继续区分本地接纳、同步与执行，不增加已获批准的声明。

最终 `pnpm check` 通过，包含 11,724 个 Vitest package 用例，以及脚本和 Electron
测试、类型、lint、i18n、public/local/Effect 边界检查。31 个定向用例覆盖最终附件
修复，包括准备失败、重试、所属机器拒绝、按原 ID 再次重试，断言所属历史恰好一条、
没有重复上传且 IndexedDB 记录已清除，并覆盖直接就绪的图片和文件输入。撤回对应
修复时，每项回归测试都会失败。CLI 发行 bundle、Storybook 构建及使用已固定 SQLite
的 7 个不可变回执用例在最终附件修改前通过。

在最终附件修改前，macOS arm64 Cloud 打包 App 通过内置 CLI/原生组件 smoke 检查。
设备测试沿用已有已登录的 Nightly profile，覆盖：

- 本机已保存输入在传输修复后以原 ID 恢复；所属历史只有一条用户输入及一条助手
  回复。接着发送的输入在内置所属 worker 暂停时先显示，恢复后收到回复；所属历史
  共四条记录，本地待发送记录已清除。
- 旧版远程 CLI 明确拒绝输入，没有改变 Roost 后端。把同一 Docker 机器更新到本次
  构建的 CLI 后，重试沿用原输入 ID，产生一条用户输入及一条助手回复，并清除本地
  待发送记录。
- 接着发送的远程输入在 Docker daemon 暂停时先显示，恢复后收到回复。读取远端
  所属机器的实际 transcript，恰好包含两条用户输入及各自的两条助手回复。
- App 重启后仍保留本机及远程输入与回复，没有重复。随后新建本机会话，首次输入
  正常接纳并收到一条助手回复；所属历史恰好只有这两条记录。

暂停 worker 时的 DOM 样本本机约 20 毫秒、远程约 16 毫秒；观测期间两个 worker 都
无法确认输入。这是单次时序检查，不是性能基准。检查使用禁用更新、采用 ad-hoc
签名的本地产物；没有测试公证、发布和更新流程。
最终附件路径由上述确定性的集成测试验证，没有为这些修改重新执行打包设备测试。

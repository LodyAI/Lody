# 不依赖历史后端的本地发送接纳

Status: proposed
Type: architecture
Translation: current
PR: https://github.com/LodyAI/Lody/pull/1546

[English](2026-10-13-backend-independent-send-acceptance.md)

## 摘要

Roost 就绪消息原先等待所属机器的历史 IPC/RPC 后才发布写入通知，发送交互因此暴露了
网络和存储延迟。已实现的方案在本地接纳一份冻结输入，独立保存，再通过原子、不可变
的所属机器回执完成交接。普通消息复用原有用户内容渲染器，不增加状态标签；执行仍须
等待所属机器确认历史。首次显示不代表已经本地持久化、被所属机器接纳或执行。
后续测量发现所属机器处理为毫秒级，但 Roost 还有额外的发送端协调和历史反馈等待。
普通输入现在通过一次协商后的请求完成所属机器接纳与激活，并用其回执反馈送达；
线上端到端延迟仍未测量。

## 决策与替代方案

Loro 的本地历史文档已承担本地接纳，以及异步 Repo 持久化和同步。Roost 渲染适配器
没有等价的可写副本：所属机器仍负责历史签名与存储。因此发送端保留就绪输入，不建立
第二份历史文档或签名 writer。
[会话文件草案](../../../../specs/session-files.zh.md#7-提交身份与本地写入)
定义了本地接纳、同步与执行的区别。

仅增加内存气泡会失去已保存输入的恢复能力；完整的可写 Roost 副本则涉及签名、所有权
与同步，超出本次范围。旧的[发送日志删除决策](../../implemented/simplification/2026-09-29-remove-session-send-journal.zh.md)
仍提供历史约束：未准备好的 Blob 只在内存中，结果不明的 guide 不重放。新保留记录
只包含不可变的就绪 Roost 输入及最终附件引用。

## 职责与生命周期

1. 接纳时冻结账号/workspace、用户、目标、会话和 turn 身份、内容、输入配置及投递
   意图。新会话先本地提交路由元数据，再允许界面获取历史 store。消息先显示，所属
   机器的工作随后完成；本地持久化在后台完成。
   路由准备不获取历史 store。后台投递先提交可信的 `humanInputReceipts` 控制记录，
   再调用所属机器接纳；普通 Loro 写入和控制队列也保持先记用户来源、后激活的顺序。
   回执查询保持只读，缓慢的 store 获取不阻塞本地接纳。
2. IndexedDB 按账号/workspace 隔离，按接纳顺序保留就绪输入。保存新输入时，先用
   `parseHistoryWrite` 规范化 entry，再做存储校验，让包含 `text: undefined` 的
   图片/文件数据与普通历史写入保持一致。已持久化记录仍严格解码，同一 ID 的内容
   冲突仍会报错。保存失败时，投影刷新仍保留唯一的内存副本，并阻止同会话后续消息
   越过它、保留离开确认。普通缓存恢复
   保留这份用户数据库；明确的完整重置可以删除它。
3. workspace 的原生发送资源 scope 持有真实存储、会话 Web Lock、store 借用及所属
   机器/控制面 I/O。Promise 协调器不声称完成了文档/RPC 生命周期的原生迁移。
   跨窗口 worker 在共享锁内重读存储。控制队列继续使用 Loro writer，但同一锁内
   等待先前输入；后续输入不会成为前置条件。合并投影保留本窗口接纳顺序及持久化的
   其他窗口顺序，也保证最新暂存输入的运行配置不会被旧输入覆盖。
   附件准备将输入交给持久化 owner 后，即使暂存队列仍在等待，重试也发给该 owner。
   仅发生在准备阶段的失败继续走暂存队列的重试路径。
4. `sessionInputAcceptance` v1 独立协商 `accept_input` 与只读 `inputAcceptance`
   查询。旧目标或已改变目标明确报错，不回退后端。获取到的渲染端 port 必须绑定到
   冻结的目标，不能只信可变元数据。原有身份/访问检查及 RPC 拒绝回执继续生效。
5. SDK 在写历史的同一事务内绑定操作身份与不可变内容指纹。查询缺失仍是未知结果；
   重试完全相同的接纳操作可以和晚到的原请求安全收敛。当前及保留的旧存储代回执
   优先于分支位置。改变输入会冲突，已删除输入不会被重建；不可读历史表示观测失败，
   不能当作已经删除。
6. 执行边界是所属机器的历史/回执原子提交，不是发送端已经观察到回复。回复丢失时，
   daemon 仍可能启动已提交的 pending 历史，沿用 Loro/历史的原有契约。发送端仅在
   观察到接纳后发起 guide；普通输入则在同一次接纳请求内由所属机器发布激活。
   本地投影本身不能执行。guide 发起前记录防重放
   标记，中断后不再发起同一次 guide。确认历史不等于 Agent 已执行。本地消息保留到
   权威 view 包含
   同一 ID，界面不同时显示两份。
7. 取消、归档、删除不依赖本窗口快照，而是找出共享存储中的记录，先持久化取消，
   再等待本地真实工作和相关会话锁。其他窗口投递前检查该标记。取消不能撤销远端
   历史写入。关闭时等待已启动 I/O，已保存的未知输入按原身份恢复。

## 投递标记的连续显示

#1546 的实现复用了普通消息内容，但省略了就绪本地输入的元数据投递标记。因此气泡
立即出现时没有圆圈，只有同一 turn 进入权威历史后，才显示圆圈或对勾。第一条消息
和后续消息都使用 `PendingMessageRow`，所以两种情况都会出现这段显示空缺。

就绪本地输入在保存和等待所属机器时保留原有的中性发送圆圈。所属机器确认输入仍在
活动历史中后，就会在发送端确认事务完成前更新原有送达覆盖层。本地行和权威行都
使用它，因此向 pending 历史交接时仍保留对勾，没有新增接纳文案或修改历史状态。
仅有已保存的发送端状态不能显示对勾。guide 的历史接纳仍与应用结果分开，不发布
这个确认。

气泡旁转动的加载圈是普通用户行的另一部分，位于 `UserChatBubble` 外面。仅复用气泡
并补上元数据圆圈，并不会在 Roost 本地输入阶段显示加载圈，因此确认较慢时仍会显得
没有反馈。就绪输入现在复用普通行的 500 毫秒加载 hook 和原有旋转图标，也保留
520 px 容器的显示阈值。等待由真实所属机器回执驱动，而非控制文档同步。错误会停止
加载，重试会重新计时，收到回执则立即取消加载。这修正了等待反馈，不表示所属机器
或网络延迟已经改善。

```mermaid
flowchart LR
  local["本地输入 · ○"] --> receipt["活动历史的所属机器回执 · ✓"] --> history["权威行 · 同一送达覆盖层 · ✓"]
```

## 送达延迟对比

[合成发送基准](../../../../apps/cli/benchmarks/roost-send.mts)使用生产环境的
`SessionDocument` 后端，分别测量接纳及所属机器观察器标记 `seen` 的耗时。
2026-10-14 在 macOS arm64 / Node 24.14.0 上，每个后端预热两个会话，再测量
九个会话，得到以下中位数：

| 输入               | Loro 接纳 | Roost 接纳 | Loro `seen` | Roost `seen` |
| ------------------ | --------- | ---------- | ----------- | ------------ |
| 打开完成后首条输入 | 0.70 ms   | 9.45 ms    | 0.66 ms     | 17.07 ms     |
| 后续输入           | 0.42 ms   | 15.10 ms   | 0.39 ms     | 22.84 ms     |

每个后端有九个首条输入及 27 个后续输入样本，每个会话包含四条简短合成输入。
Roost 包含原生 SQLite 写入及签名；Loro 使用没有持久化的内存 Repo，因此测量的是
持久化保证不同的现有所属机器路径。后端打开在首条输入前单独测量，中位数为
Loro 0.24 ms、Roost 18.81 ms。热缓存和短历史不代表冷启动或长会话。
`seen` 表示所属机器已观察到输入，不表示 Agent 已执行。

后续基准的 `BENCH_DISPATCH=1` 模式为两个后端预先准备路由元数据，并包含 Roost
所属机器激活。另一次九会话测量得到 Roost 接纳/激活中位数：首条 9.19 ms、后续
12.40 ms；`seen` 中位数为 16.16/19.29 ms。这些本地观测没有测量网络节省，
也不构成改动前后耗时改善的因果证据；门控发送端测试证明了串行请求/回读依赖已移除。

基线确定性发送端实验使用显式的接纳/回读门控、真实 Loro 控制与历史文档及 workspace
writer。普通 Loro 门面将成功的 dispatch 回复传给 UI 的已送达回调。就绪 Roost
输入在保留期间绕过这个门面，先等待所属机器接纳，再等待权威 `readTurn`，才发起
dispatch。缓存未命中时可能多一次所属机器往返；一致缓存或并发刷新可能免去该请求。
后台 helper 没有传入已送达回调，因此成功的 dispatch 回复也不会更新 UI 的确认
覆盖层。本地投影行还须等待权威历史交接，才能显示对勾。

这些发送端等待并不全都延迟实际送达：所属机器可以在回复到达发送端前，自行启动
已提交的 pending 历史。如果回读已经显示无需启动的状态，协调器便跳过 dispatch。
因此代码不意味着每次发送都有固定次数的网络往返。对比证明了额外的发送端屏障和
较慢的确认反馈路径，没有证明线上报告的 1–3 秒延迟由哪一段造成、各占多少。
基准和实验都没有测量真实传输、渲染器 IndexedDB、React/绘制或执行启动。
仅这次测量没有改变发送协议或确认行为；下面的后续实现移除了这些发送端等待。
基准和门控发送端实验均成功完成；基准还通过了包含生产依赖的 TypeScript 检查和
范围内 lint。文档检查仍报告原先六个失效链接。

## 传输与兼容性

### 普通输入只需一次所属机器请求

`sessionInputDispatch` v1 独立协商 `accept_input_and_dispatch` 和可选的
`inputAcceptance.acceptAndDispatch` 端口。普通发送在消耗草稿或创建路由元数据前
拒绝旧 owner；恢复的输入也重新检查冻结的所属机器和协议能力。仅写历史和 guide
保持原有 v1 协议，不回退后端或传输。

现有原生 writer 队列先检查不可变回执身份，在接纳前记录显式的人类来源，再签名/
存储历史、检查当前历史和元数据，最后发布激活。只有最新且等待启动的用户输入能
推进指针；重试不会把它移回较早输入。已移除/已结束输入、已归档/删除元数据及
缺失历史墓碑不会重新激活。host 唤醒现有历史 dispatcher，不等待 Agent 执行或
远端同步，也不增加 Loro RPC 内容暂存副本。

正常发送端投递使用这一次写入回执，不再回读权威历史或发送第二个 dispatch 请求。
历史观察器仍可能独立读取。回复丢失时查询不可变回执，再重做同一个组合操作以恢复
激活。历史提交后的失败不会追加另一条输入；每次重试都检查当前状态和活动成员身份。
guide 交接继续保留持久化防重放标记和应用语义。

投递所有权在 runtime 生命周期内保留到可见行交接或取消之后，dispatch/guide 门面
不能在行消失后重新接管已接纳输入。它在原完成记录中增加投递意图，不把所有权
当作 daemon 已收到输入的证据。

workspace 发送资源 scope 和顺序租约仍拥有发送端存储及真实请求。关闭/取消会等待
已启动工作并抑制迟到的发送端反馈，但不能撤销所属机器已提交的历史或已接受的激活。
所属机器复用现有 writer 队列和 dispatcher 所有权。已评估并延后原生 Effect 迁移：
SessionDocuments/历史和 dispatcher 仍依赖上游 Promise 编排。此次没有新增锁或
runtime，也不声称迁移完成。

每次历史操作都通过 workspace router 解析固定所属机器当前使用的传输通道。store
不能缓存本机身份探测时的初始路由，也不能在通道不可用时更换收件机器。Node IPC
的两份守卫实现都必须接受已声明的历史请求/回执契约。

不可变接纳使用 `@loro-dev/roost@0.1.3`；原生
`@loro-dev/roost-node@0.1.2` 依赖图不变。

## 验证与限制

确定性发送端测试使用 IndexedDB 事务、原生发送资源、真实 Loro 文档及 workspace
writer，覆盖立即显示、不可变重试、恢复与排序、账号隔离、跨窗口取消、附件交接、
guide 防重放，以及所属机器接纳前的用户来源记录。接收端测试使用已固定的原生
SQLite 包，覆盖回执冲突、晚到的原请求、重新打开、保留的存储代和不可读历史。
桥接及 IPC 测试覆盖路由变化、全部已声明的历史操作和无效回复。

macOS Cloud 打包测试覆盖本机及远端所属进程暂停时的发送、重启后按原 ID 恢复、
不支持协议的目标明确拒绝。最终附件修改及 operation-inbox 集成通过了确定性测试
和 `pnpm check`，没有为这些修改重新执行打包测试。这些检查验证所覆盖的行为，
不证明原线上事件的起因，也不构成延迟保证或发布/签名验证。

投递标记的后续修复基于 main `08a58d6f3` 调查。确定性 DOM 回归测试在该版本上因
本地气泡没有发送圆圈而失败，再验证所有本地输入状态及向 pending、已送达权威历史
行交接时的标记。这证明了呈现缺陷，没有测量所属机器确认的延迟。
气泡旁加载圈的回归使用假时钟比较实际 Loro 行和 Roost 本地行：499 毫秒时都不加载，
500 毫秒时都开始加载，真实所属机器回执到达后停止加载，交接到历史行后仍保留对勾。
修复前 Loro 用例通过、Roost 用例失败；另一用例覆盖错误、重试，以及重试计时结束前
收到回执。这两个所属测试套件通过 48 项测试，浏览器渲染也确认等待故事中有可见的
16 px 加载圈，已确认故事中没有加载圈。这是合成呈现证据，没有测量线上端到端耗时。
最初仅呈现修复的相关测试通过 84 项；components 类型检查、范围内 lint 和格式检查通过。仓库文档
检查仍被 subagent-events 笔记中六个既有 Kimi/Pi 链接阻断。此次呈现修改没有执行
完整 workspace 检查或测量打包应用的确认耗时。

组合请求的后续实现通过 296 项相关测试：115 项发送端/UI、123 项 CLI 后端/
dispatcher/注册（包含原生提交顺序用例），以及 58 项协议/IPC。恢复旧的
接纳/回读/dispatch 路径后，新会话和后续消息的回归用例都会失败。显式门控验证
发送端确认事务之前的反馈、无发送端回读依赖、原生来源/激活顺序、部分激活失败
后的恢复，以及交接或取消后门面不重新接管投递。components、shared、CLI 和基准

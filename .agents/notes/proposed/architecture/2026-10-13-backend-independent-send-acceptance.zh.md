# 不依赖历史后端的本地发送接纳

Status: proposed
Type: architecture
Translation: current
PR: https://github.com/LodyAI/Lody/pull/1546

[English](2026-10-13-backend-independent-send-acceptance.md)

## 摘要

Roost 就绪消息原先等待所属机器的历史 IPC/RPC 后才发布写入通知，发送交互因此暴露了
网络和存储延迟。已实现的方案在本地接纳一份冻结输入，独立保存，再通过原子、不可变
的所属机器回执完成交接。普通消息复用原有用户内容渲染器，不增加状态标签；执行仍须
等待所属机器确认历史。首次显示不代表已经本地持久化、被所属机器接纳或执行。

## 决策与替代方案

Loro 的本地历史文档已承担本地接纳，以及异步 Repo 持久化和同步。Roost 渲染适配器
没有等价的可写副本：所属机器仍负责历史签名与存储。因此发送端保留就绪输入，不建立
第二份历史文档或签名 writer。
[会话文件草案](../../../../specs/session-files.zh.md#7-提交身份与本地写入)
定义了本地接纳、同步与执行的区别。

仅增加内存气泡会失去已保存输入的恢复能力；完整的可写 Roost 副本则涉及签名、所有权
与同步，超出本次范围。旧的[发送日志删除决策](../../implemented/simplification/2026-09-29-remove-session-send-journal.zh.md)
仍提供历史约束：未准备好的 Blob 只在内存中，结果不明的 guide 不重放。新保留记录
只包含不可变的就绪 Roost 输入及最终附件引用。

## 职责与生命周期

1. 接纳时冻结账号/workspace、用户、目标、会话和 turn 身份、内容、输入配置及投递
   意图。新会话先本地提交路由元数据，再允许界面获取历史 store。消息先显示，所属
   机器的工作随后完成；本地持久化在后台完成。
   路由准备不获取历史 store。后台投递先提交可信的 `humanInputReceipts` 控制记录，
   再调用所属机器接纳；普通 Loro 写入和控制队列也保持先记用户来源、后激活的顺序。
   回执查询保持只读，缓慢的 store 获取不阻塞本地接纳。
2. IndexedDB 按账号/workspace 隔离，按接纳顺序保留就绪输入。保存新输入时，先用
   `parseHistoryWrite` 规范化 entry，再做存储校验，让包含 `text: undefined` 的
   图片/文件数据与普通历史写入保持一致。已持久化记录仍严格解码，同一 ID 的内容
   冲突仍会报错。保存失败时，投影刷新仍保留唯一的内存副本，并阻止同会话后续消息
   越过它、保留离开确认。普通缓存恢复
   保留这份用户数据库；明确的完整重置可以删除它。
3. workspace 的原生发送资源 scope 持有真实存储、会话 Web Lock、store 借用及所属
   机器/控制面 I/O。Promise 协调器不声称完成了文档/RPC 生命周期的原生迁移。
   跨窗口 worker 在共享锁内重读存储。控制队列继续使用 Loro writer，但同一锁内
   等待先前输入；后续输入不会成为前置条件。合并投影保留本窗口接纳顺序及持久化的
   其他窗口顺序，也保证最新暂存输入的运行配置不会被旧输入覆盖。
   附件准备将输入交给持久化 owner 后，即使暂存队列仍在等待，重试也发给该 owner。
   仅发生在准备阶段的失败继续走暂存队列的重试路径。
4. `sessionInputAcceptance` v1 独立协商 `accept_input` 与只读 `inputAcceptance`
   查询。旧目标或已改变目标明确报错，不回退后端。获取到的渲染端 port 必须绑定到
   冻结的目标，不能只信可变元数据。原有身份/访问检查及 RPC 拒绝回执继续生效。
5. SDK 在写历史的同一事务内绑定操作身份与不可变内容指纹。查询缺失仍是未知结果；
   重试完全相同的接纳操作可以和晚到的原请求安全收敛。当前及保留的旧存储代回执
   优先于分支位置。改变输入会冲突，已删除输入不会被重建；不可读历史表示观测失败，
   不能当作已经删除。
6. 执行边界是所属机器的历史/回执原子提交，不是发送端已经观察到回复。回复丢失时，
   daemon 仍可能启动已提交的 pending 历史，沿用 Loro/历史的原有契约。发送端仅在
   观察到接纳后写激活或发起 guide；本地投影本身不能执行。guide 发起前记录防重放
   标记，中断后不再发起同一次 guide。确认历史不等于 Agent 已执行。本地消息保留到
   权威 view 包含
   同一 ID，界面不同时显示两份。
7. 取消、归档、删除不依赖本窗口快照，而是找出共享存储中的记录，先持久化取消，
   再等待本地真实工作和相关会话锁。其他窗口投递前检查该标记。取消不能撤销远端
   历史写入。关闭时等待已启动 I/O，已保存的未知输入按原身份恢复。

## 传输与兼容性

每次历史操作都通过 workspace router 解析固定所属机器当前使用的传输通道。store
不能缓存本机身份探测时的初始路由，也不能在通道不可用时更换收件机器。Node IPC
的两份守卫实现都必须接受已声明的历史请求/回执契约。

不可变接纳使用 `@loro-dev/roost@0.1.3`；原生
`@loro-dev/roost-node@0.1.2` 依赖图不变。

## 验证与限制

确定性发送端测试使用 IndexedDB 事务、原生发送资源、真实 Loro 文档及 workspace
writer，覆盖立即显示、不可变重试、恢复与排序、账号隔离、跨窗口取消、附件交接、
guide 防重放，以及所属机器接纳前的用户来源记录。接收端测试使用已固定的原生
SQLite 包，覆盖回执冲突、晚到的原请求、重新打开、保留的存储代和不可读历史。
桥接及 IPC 测试覆盖路由变化、全部已声明的历史操作和无效回复。

macOS Cloud 打包测试覆盖本机及远端所属进程暂停时的发送、重启后按原 ID 恢复、
不支持协议的目标明确拒绝。最终附件修改及 operation-inbox 集成通过了确定性测试
和 `pnpm check`，没有为这些修改重新执行打包测试。这些检查验证所覆盖的行为，
不证明原线上事件的起因，也不构成延迟保证或发布/签名验证。

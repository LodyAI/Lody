# E2EE 账本验证使用 WebAssembly 严格 Ed25519

Status: proposed
Translation: current

[English](2026-10-20-e2ee-wasm-ed25519.md)

PRs：本改动（叠在 [LodyAI/Lody#1733](https://github.com/LodyAI/Lody/pull/1733) 之上）

## 摘要

账本重放慢，是因为椭圆曲线运算用纯 JS 实现，协议本身并不慢。core 现在用一个由 Rust 编译成 WebAssembly 的小模块做 Ed25519 验签，规则与现有严格规则完全相同，全量重放快了 7–13 倍。差分测试证明，包括对抗性输入在内，该模块与纯 JS 路径接受的密钥和签名完全一致。没有 WebAssembly 时，core 回退到纯 JS，结果相同。在本地 Convex 部署中，该模块在 query、mutation 和 action 里都能运行。

## 问题与证据

对全量重放做 profile，约 70% 的时间花在 noble 的曲线运算上。每个签名要执行以下严格步骤（单次耗时；8 核 2.2 GHz Xeon，有负载）：

| 步骤 | 纯 JS |
|---|---|
| noble `verify`（zip215: false） | 3.4 ms |
| R 的质数阶子群检查（`isTorsionFree`） | 1.9 ms |
| A 的子群检查（只缓存 256 个密钥） | 1.9 ms |
| Web Crypto 验签（只能替换第一行） | 0.36 ms |

子群检查不能省：各 Ed25519 实现对带小阶分量的点判定不一致，而每个客户端和宿主必须对每条记录得出相同结论。因此 Web Crypto 最多只能快一倍。

## 做法

- **crate：** `packages/e2ee-core/wasm/ed25519-strict`，基于 curve25519-dalek 4.1.3 和 sha2。
  - A 和 R 必须是规范编码、非零、位于质数阶子群；A 不能是小阶点；S < L；带余因子等式成立。这与 noble 的 `zip215: false` 加上 core 的子群检查完全一致。
  - 输入都是公开数据，所以全部使用可变时间乘法；`[L]P` 按 `[L−1]P + P` 计算。
  - 使用 32 位域运算后端；在 WebAssembly 中实测比 64 位后端快。
- **无胶水代码：** 不用 wasm-bindgen。原始导出（`input`、`key_ok`、`verify`）用普通 `WebAssembly.Instance` 即可调用。模块 74 KB，以 base64 连同其 SHA-256 嵌入 core。
- **固定后端，不可注入：** `foundation/ed25519-wasm.ts` 首次使用时同步实例化。若 WebAssembly 不存在或实例化被拒绝，每次调用都返回 `undefined`，core 改走纯 JS 路径。`signingPublicKey` 和两个验签入口都优先使用该模块。
- **已校验的密钥：** `verifySignature` 一直先通过带缓存的 `signingPublicKey` 校验 A。现在它把这一点告知模块，模块据此跳过 A 的子群检查；A 仍会做规范解码。
- **可复现构建：** `node wasm/ed25519-strict/build.mjs` 运行 `cargo build --locked`，并重新生成 `ed25519-wasm.generated.ts`。两次重建得到相同哈希。CI 不构建 Rust；有测试核对嵌入字节与记录的哈希一致。
- **许可证：** 编译进模块的 crate 已登记在 `THIRD_PARTY_NOTICES.md`，许可证原文放在 `wasm/ed25519-strict/licenses/`。

## 证据

差分测试（`test/ed25519-wasm.test.ts`）：
- **输入：**
  - 50 个有效密钥和 500 个随机密钥；
  - 全部 8 个小阶点；
  - 混合阶密钥；
  - 所有非规范编码；
  - 有效、被篡改以及 S+L 的签名；
  - R 带挠分量且满足带余因子等式的签名（测试断言它们能通过 noble 原始 `verify`）；
  - 0 到 20,000 字节的消息。
- **结果：** 模块与纯 JS 参考实现对每个输入的判定都一致；core 在开启和关闭 WebAssembly 时返回相同的结果和错误码。
- **变异检查：**
  - 去掉 R 的子群检查，测试会失败；
  - 去掉规范编码检查，任何输入都无法察觉，因为不存在具有非规范编码的质数阶点；测试断言了这一事实。

core 全套测试在默认开启 WebAssembly 时 411/411 通过；Web Crypto 回退路径的测试会显式关闭它。

真实密钥和签名、全量重放、同一主机同一负载下的性能：

| 账本 | 记录数 | 纯 JS | WebAssembly | 加速 |
|---|---|---|---|---|
| 4,096 次换代 | 4,097 | 27.1 s | 4.0 s | 6.8× |
| 1k 成员 + 1k 设备 + 2k 次换代 | 4,001 | 43.2 s | 5.6 s | 7.7× |
| 4k 成员 + 4k 设备 | 8,001 | 156.9 s | 12.4 s | 12.7× |

- **单个签名：** WebAssembly 0.42 ms，原生 Rust 0.15 ms。
- **重放的其余开销：** 主要在 JS 侧，包括 CBOR 解码、哈希和生成器。

Convex：在本地 Convex 后端（容器中运行，放宽了本地时间限制）部署了一个探针，模块在 query、mutation 和 action 中都能实例化，每处都接受有效签名、拒绝被篡改的签名。action 中实测每次验签 0.65 ms。

## 后续：JS 侧开销

开启 WebAssembly 后，对 1k/1k/2k 账本做 profile，42% 的时间在模块之外。CBOR 占 1.04 s：用 dag-cbor 解码后再重新编码以确认规范形式，并且每次编码后都回读解码一次。此外，256 项、按先进先出淘汰的已校验签名公钥缓存，把账本里最常用的签名者 Owner 挤掉了，导致约 1,000 次重复的公钥校验。

- **CBOR 快路径。** 单遍解码器和编码器只覆盖朴素的规范子集：最短编码头的非负安全整数、不超过编解码器上限的字节串（账本记录为 256 字节；快照和保留状态为各自的总预算，因为其状态就是几张字节串表）、定长数组、false、true 和 null，深度和数组上限与原来相同。其余输入一律交给 dag-cbor 路径，由它单独负责拒绝和选择错误码，因此拒绝结果和错误码在构造上保持不变。
  - `test/cbor-fast-path.test.ts` 把快路径与参考路径对比：覆盖三种预算下的 6,000 个生成值，以及 16,000 多个有效、变异、截断、追加、边界和随机输入；要求结果字节或值相同，或错误码相同。
  - 五种变异（非最短编码头、超长字节串、尾随字节、嵌套上限、编码器的编码头边界）各自都会让测试失败。
- **公钥缓存。** 改为按最近最少使用淘汰，容量 4,096 个。

没有选择把这些搬进 WebAssembly：解码结果必须回到 JS 交给策略代码，跨越边界的开销会吃掉大部分收益。SHA-256 只占 1.5%，保留在 JS。

结果（同一主机）：

| 账本 | 之前 | 之后 | 加速 |
|---|---|---|---|
| 4,096 次换代 | 4.0 s | 2.9 s | 1.38× |
| 1k 成员 + 1k 设备 + 2k 次换代 | 5.6 s | 3.9 s | 1.44× |
| 4k 成员 + 4k 设备 | 12.4 s | 10.9 s | 1.14× |

相对纯 JS，分别为 9.3×、11.1× 和 14.4×。在 1k/1k/2k 账本上，模块现在占 65% 的时间，也就是必须验证的 6,001 个签名；CBOR 占 9%。

## 运行环境

使用打包后的加载器测量（`ms/verify` 为预热后的值）：

| 运行环境 | 是否用上模块 | 结果正确 | ms/verify |
|---|---|---|---|
| Node.js 24 | 是 | 是 | 0.5 |
| Chromium 145 主线程与 Web Worker（Electron） | 是 | 是 | 0.44 |
| WebKit 26 主线程与 Worker | 是 | 是 | 0.66–0.74 |
| Firefox 146（Playwright 构建）主线程与 Worker | 是 | 是 | 3.4 |
| Convex query、mutation、action（本地后端） | 是 | 是 | 0.65（action） |
| Cloudflare workerd，普通导入 | 否：禁止运行时编译 | 是（纯 JS） | 纯 JS 速度 |
| Cloudflare workerd + `@lody/e2ee-core/cloudflare`（wrangler 打包） | 是 | 是 | 0.64 |

- **Cloudflare 入口。** workerd 拒绝 `new WebAssembly.Module(bytes)`（"Wasm code generation disallowed by embedder"）。`./cloudflare` 入口导入包内的 `wasm/ed25519-strict/ed25519_strict.wasm`，由 wrangler 在部署时编译，再把该模块交给 core。该文件与嵌入字节由同一次构建生成，哈希必须相同。
- **已知答案检查。** 无论模块从哪条路径加载，core 都要先用一组已知答案向量检查，全部通过才会使用：有效签名、被篡改的消息、R 带挠分量但满足带余因子等式的签名、小阶密钥、非规范密钥。手工拼出的"全部接受"模块会被拒绝；去掉该检查后它会被放行，测试能发现这一点。
- **Firefox。** 在 Playwright 的 Firefox 构建中，同步编译和异步编译都是 3.4 ms。需要在正式版 Firefox 上复测；即便是 3.4 ms 也比纯 JS 快。

## 限制

- **没有 WebAssembly 的平台**仍是纯 JS 速度。Lody 的客户端都不属于这种情况：移动端是 Capacitor，运行在 WKWebView 或 Android WebView 中。
- **内容安全策略（CSP）。** 如果 `script-src` 中没有 `'wasm-unsafe-eval'`，core 会悄悄回退到纯 JS。在 Electron 渲染进程的 CSP 下运行 Vite 生产构建，WebAssembly 启用时每次验签 0.41 ms；去掉该来源后为 4.26 ms，并出现一条 `script-src wasm-eval` 违规记录。渲染进程的 CSP 测试（公开仓库）和托管应用的 CSP 测试（私有仓库）现在都要求包含它。移动端没有设置 CSP。
- **浏览器主线程：** 同步编译大模块可能被拒；本模块 74 KB，在通常的限制以内，被拒时也会回退到纯 JS。
- **测量环境：** 只在一台有负载的主机和本地 Convex 后端上测过，没有在线上 Convex 或真机上测过。

## 考虑过的其他方案

- **只用 Web Crypto：** 约 2 倍，因为子群检查仍在 JS 中。
- **原生 N-API 插件：** 约 40 倍，但每个平台都要单独的二进制，而且 Convex 默认运行时和浏览器都用不了。
- **去掉子群检查：** 否决。这会改变哪些账本能通过验证，破坏各实现之间的一致性。

# 用户侧 Codex 账户与端点凭据

Status: proposed
Translation: current

[English](2026-09-26-codex-account-profiles.md)

## 摘要

Codex 多账户不能交换全局认证文件，也不能把 API Key 写入共享提供商环境变量。
实现采用不可变的宿主账户绑定、ChatGPT 原生系统密钥库及系统凭据库内的 API 密钥代次，
保留现有本地和远程交互。固定版本原生程序在同主机 HTTPS 降级至 HTTP 时转发
Authorization，因此自定义 API 必须经过拒绝重定向的用户侧凭据转发器。
同一 ChatGPT 账户保留多个原生进程并发；确认刷新竞争后保留共享凭据，允许一次
新进程启动重试，但不串行原生刷新。

## 决策

[草案 Spec](../../../../specs/codex-account-profiles.zh.md)拥有产品契约。账户位于执行
机器的 Lody 数据目录，非秘密元数据绑定工作区、机器、提供商、账户、方式及地址。
OAuth 刷新仍由 Codex 负责；Lody 用 `@napi-rs/keyring` 2.1.0 暂存 API 密钥代次。
Linux 明确要求持久化 Secret Service，不回退到临时 keyutils。渲染进程不能读回已有
密钥；远程输入复用现有与上下文绑定的加密交互，而非另建凭据通道。

每次启动的回环转发器固定地址及密钥代次。原生进程仅收到随机访问令牌；上游请求拒绝
全部重定向，不回显供应商错误正文，仅接受模型和 Responses 操作。尽管最初倾向原生
直连，实验已证明这个本地边界不可省略。凭据验证不能运行通用代码代理，仅经转发器
发送没有工具的合成文本。

全局认证交换、名为加密却明文落盘的方案、把密钥放进 `AgentConfig.env` 以及托管代理
均违背隔离、存储或部署边界。重定向实验后否决原生 API 环境变量注入；不另建 OAuth
快照和刷新实现，因为凭据仍归 Codex 所有。

初版实现错误地因未证实的刷新风险引入运行期独占租约；现改为独立的每进程使用记录。
启动先登记，再确认账户未移除；删除先持久化墓碑，再等待所有记录证明原生进程已退出。
未知进程只延迟凭据清理。迟到的退出证明仅写入宿主生成的自身 token 对应记录，不影响
其他进程。现有登录操作串行规则不变。

原生 0.156.0 会在刷新前重读共享凭据，但只在进程内串行。可控的双进程实验确认：
两个进程可能在新凭据写入前提交同一旧 refresh token。adapter 旧有的会话打开
错误处理会把败者报错中的“log out”当作删除共享凭据的依据，可能连胜者一起影响。
现在托管 ChatGPT 账户只上报错误，不自动退出登录；旧模式行为保留。这只阻止
破坏性后果，不协调原生刷新。托管 ChatGPT 刷新错误分类覆盖新建、恢复、分叉和
稳定版加载会话，均不自动退出登录。此前稳定版加载绕过分类，导致已保存会话恢复时
丢失重试标记；旧模式加载仍原样抛错，不进入旧有退出登录处理。宿主只在会话启动阶段
识别 adapter 标记的结构化重复刷新错误：清理失败进程，等待 750 毫秒，重新核验实时
Provider，再启动一次新进程；第二次失败即终止。该有界恢复在胜者已保存凭据时复用它，不串行会话，
也不在 Codex 之外实现 OAuth 刷新。已删除或变更的 Provider 不能授权重试。
跨进程刷新串行应由原生凭据所有者负责，不能靠
启动时租约或宿主另写一套 OAuth 刷新完成。
adapter 的缓解措施另见
[acp-extension-codex PR #58](https://github.com/LodyAI/acp-extension-codex/pull/58)。
adapter 合并到 `main` 的 squash 提交还依赖 `acp-extension-core` 0.1.9 的增量子代理
事件契约。宿主同时固定两个已合并提交，而不是已删除的 adapter PR 分支。Lody
未声明这项新的客户端能力，因此配套升级不会启用子代理事件。

恢复的会话可能携带旧格式的 `codexAuth`。这个值只能验证历史身份，不能授权启动新的
原生进程；启动现在要求实时 Provider 保留相同的托管账户绑定。本地删除协调是异步的，
不能代替这项检查。新会话不写入逐会话启动配置，普通恢复在 Provider 缺失时原本已被
阻止，但旧格式绑定的恢复仍有缺口。通用编辑弹窗的重新登录按钮也与 ChatGPT 绑定
不可变的规则冲突：守护进程会有意拒绝已就绪账户再次登录。编辑这类 Provider 现在
说明切换账户需添加新 Provider；创建时的首次登录及 API Key 更新仍保留各自入口。

旧守护进程忽略未知账户字段，因此持久化配置包含带 NUL 字符的
`runtimeOverrides.codexPath`，使旧版启动和登录在访问原生认证前失败。
支持该功能的 Flock 读取方只移除完全匹配的标记，保留账户契约供宿主验证。
普通运行时覆盖仍被禁止；该标记不是秘密，也不是用户可编辑的运行时设置。

## 证据与限制

实验使用精确的 Codex 0.156.0 macOS arm64 托管包，SHA-256 为
`27a4c6ad8d63ab0988eb2a6699fb092d999b78845c75edad1eef674064a026de`。
固定源码按规范化 CODEX_HOME 生成原生密钥库账户键，但刷新锁仅在进程内有效。
手动植入凭据的刷新实验被跨应用钥匙串 ACL 阻挡，不代表原生刷新成功或失败。
后续[合成刷新实验](../../../../packages/acp-extension-codex/scripts/probe-refresh-contention.mjs)
让两个固定版本的真实原生 app-server 进程共用隔离的文件凭据目录和带屏障的本地
刷新端点。两者均提交相同旧 token；一次成功及一次模拟 `refresh_token_reused` 后，
只有胜者报告可用 token；新启动的第三个进程读到了胜者保存的 token。实验未涉及
真实账户、密钥库刷新或既有凭据。

已执行的隔离实验仅用合成凭据：系统凭据增读删、无 auth.json 的真实原生 Responses
完成、跨端口重定向移除密钥、同端口 HTTPS 降级泄漏、转发器保护下完成及阻断降级、
通过测试 HTTPS CONNECT 服务执行两次真实原生设备登录、状态查询和退出。
macOS 需保留系统 HOME 才能访问默认钥匙串，应隔离 CODEX_HOME、Lody 数据和 Electron
userData。未查看真实账户或既有凭据。

行为测试覆盖代次回滚和取消、重启、不可变绑定、凭据库锁定、独立目录、符号链接、
并发/活跃/未知/已退出原生进程使用记录、旧进程迟到证明、删除协调、冻结地址提交及恢复身份。
真实 OSS 桌面通过合成 API 登录和模型回复、两个真实原生设备登录及独立回复、登录 B
后恢复 A、替换失败保留可用旧密钥，以及界面删除清理凭据库。
[可复现录制器](../../../../e2e/scripts/acceptance-codex-profiles.mts)保留视频并检查各账户
没有写入 `auth.json`；外部协议模拟不使用真实账户。

有界重试加入前，账户实现通过 `pnpm check`、格式化、公开边界、文档及 E2E 套件检查。
本次重试通过 32 项定向 CLI 测试、825 项 adapter 测试（含稳定版加载刷新及旧模式
行为）、8 项 Core 契约测试、类型检查、格式化、文档及边界检查。当前修订的本地完整
`pnpm check` 尚未通过：工作树起初缺少 Electron 二进制；
补齐后，一个无关 Git 测试仅在并发执行时失败，隔离运行则通过。单独执行的完整 CLI
套件另有无关 worktree 凭据转发测试超时。完整套件仍以托管 CI 为准。现有加密 RPC
测试通过，但尚未执行远程桌面全链路。Windows/Linux 凭据后端与真实账户密钥库刷新
竞争仍未验证。
合成原生刷新竞争已复现；adapter 防自动登出和宿主有界启动重试只缓解用户影响，
不阻止原生竞争，也不能恢复所有永久失效的凭据。录制器以显式到达
屏障持有同账户两条请求，验证原生执行重叠，不代表刷新竞争验证。未知孤儿进程仅延迟
删除清理，不阻止启动。旧外部历史目录不会聚合
所有托管账户，绑定历史回放在提供商缺失时拒绝
回退。新目录刻意不复制原生全局配置和历史；现有 Lody 项目、MCP 与技能沿用正常启动
流程。独立交付审查完成前保留 proposed；Spec 保持 draft。

# E2EE M2 产品接入

Status: proposed
Translation: current

- 日期：2026-10-22
- English: [English](2026-10-22-e2ee-m2-product-integration.md)

## 摘要

加密工作区需要完整的桌面到机器执行路径，单独的加密适配器不能证明产品可用。本次实现让设备与文档密钥留在宿主，以独立设备凭证调用云端控制面，并在打开本地数据时不等待网络认证。普通工作区保留原来的组装路径。owner 已在第二轮 M2 方案中明确接入契约；本文仍不表示 M2 已验收，端到端和真实平台证据需分别完成。

## 边界

下文的快照限制描述 M2。[PR-17 MVP](2026-10-27-e2ee-native-content-snapshots.zh.md) 取代这一部分，启用带签名的原生内容快照，并明确回放及历史清理后的恢复路径。

- 账号级 E2EE 运行时按需创建。普通工作区不打开其保管，也不创建 E2EE 云客户端。
- 离线身份只是在原有认证存储中保存 token 哈希与账号的绑定，没有时间过期；明确拒绝或主动登出时删除，网络不确定时保留。平台状态仍为未登录，仅附加网络不确定标记，只有 E2EE 会据此尝试主进程身份，避免七天快照过期阻断本地打开；普通工作区行为不变。它只选本地数据，不授予云端访问或账本权限。
- 设备凭证是独立随机的 32 字节访问秘密，以独立 KEK 用途域、genesis 与签名公钥绑定保存。创建重试时公开哈希不变，设备与 epoch 密钥格式不变。没有凭证的旧开发者工作区需重新创建，不做迁移。
- 主进程负责签名和内容加密。渲染进程只能按房间 seal/open，不能任意签名或导出文档密钥。Meta 实际为 Flock；只启用会话文档、`wf` 与 `mf:*`。读取只接受加密帧，快照上传继续关闭。
- 房间 provider 固定写入 epoch。换代后旧 provider 停止写入，不静默切换。纪元变化或需要换代时，停止新发送、本地编辑保持持久化、界面提示更新密钥；完整的排空与重建交接明确延后到 M3 PR-20。
- 账号和宿主锁只覆盖本地、原生操作；token、账本读取和信箱网络调用在释放锁后进行。工作区关闭时先停止接收、取消本工作区的 HTTP 请求，再等待完整密钥轮次结束后释放存储；等待发生在两个锁之外。账号关闭还会取消共享客户端。core 继续持有已开始的原生工作直到真实结束。
- 窄客户端只开放固定的 E2EE 方法，校验返回形状，关闭 SDK 日志，不自动重发结果不确定的写入。提交方必须先保存原签名字节。
- 每个工作区的密钥轮次有限且合并触发，复用 core 的 journal 和工作流；触发来自启动、本地已验证账本刷新与重连，服务端提示不是权限依据。

## 未加密出口

M2 使用 Loro 历史和持久派发指针。定时任务文档与工作区注册表使用同一受保护 CRDT 传输；定时任务在交接前与共用实际启动 claim 中，都通过现有机器访问检查验证原始定义 signer；显示用的归属字段和机器派生签名都不授予这份权限。加密工作区关闭云端 RPC、presence、快照上传、云附件、Shortcuts、Code Collab 索引、分享、远程预览、导出与通知正文；后台 PR 观察、托管 GitHub 凭据和云端关联也关闭，避免仓库名与分支旁路泄漏。同系统用户的可信本地 IPC 可承载必要控制，但不得回落网络 RPC。Loro 的授权结果已经写入受保护的会话文档。文件保管仅限机器设备，必须在明确批准配对前告知用户。

## 证据与限制

测试覆盖凭证持久保存与原样重试、主进程按房间加密和坏帧隔离、离线身份、并发补尾，以及慢信箱不阻塞本地状态。Canary 测试使用真实 Loro/Flock 对端和 Riverrun，并能抓到故意泄漏的原文及编码标记；这不等同于整款产品验收。

隔离的 Electron 44.7.0 实测：16 KiB 加密、签名和 IPC，300 个样本 p95 为 0.70 ms（macOS arm64）。真实 HTTP/SDK/IPC/Loro/IndexedDB 首次同步测得普通模式中位数 44.30 ms、加密模式 71.60 ms（1.6163×），低于 owner 确认的 M2 上限 1.75×；两组都没有服务端快照。实际 IPC、序列化及排队开销为 2.221 ms（3.1%），不触发约 20% 的批量优化条件；CRDT 导入 4.90 ms。验签、作者检查与 AEAD 的代表性重复测量使用同一 SDK 密文帧和主进程内的密钥；这些不可直接累加的数字及测量边界见[基准说明](../../../../apps/electron/scripts/e2ee-ipc-benchmark.md)。PR-17 加密快照完成后须重新测量 1.5× 目标。这些数字不含 React 和工作区目录组装，也不替代整款产品同步与发送延迟验收。合成宿主测试不证明真实钥匙串、Windows ACL 或打包应用验收。

CLI 打包把运行时及 worker、ACP 适配入口分到两个 Vite 进程，保留 source map、原生顶层 await、外部依赖和同一个平铺输出目录。按进程限制转换源码与 map 的驻留量，不再依赖应用 chunk 循环导入，原来的 handler/execution 分块已移除。适配入口这一步保留运行时输出，依赖 chunk 使用内容哈希；默认模式（含 `build:watch`）仍构建原来的全部入口。公开仓独立 frozen install、与 main 的实际合并树、Node 22.23.4 下，完整 Electron `build:cli` 在 1792 MiB 和规定的 2048 MiB 都通过。2048 MiB 下运行时为 3189 个模块、7.44 秒，适配入口为 233 个模块、2.21 秒。发布运行时及 worker 检查、构建产物 `--help` 均通过；十二个入口的 map 均保留，209 份 vendor map 不含应用源码。E2EE 仍按需导入，隔离普通工作区。这些构建与启动检查不等于打包聊天验收。

## 第二轮已定接入契约

1. 信箱按 core 的资格、安装上下文与本地发布规则执行，只去掉服务端验签。写入时原子投影有效成员、设备、当前纪元与承诺、包含 genesis 的每代发布记录。发钥方可以读回本人发送的信封并查询接收者状态。
2. 凭证绑定采用固定域 `lody-e2ee/device-credential-binding/v1\0`，后接 genesis（32 字节）、配对会话（16）、新设备签名公钥（32）和凭证哈希（32）。主进程生成本机会话，用 core 严格验签后保存公共材料。CLI 的独立持钥证明绑定加密公钥与成员。用户明确批准后才签接纳记录；请求和签名字节在 HTTP 前持久保存，重启也只重发原件。文件保管在确认框说明；发钥或本机激活暂时不可用，不推翻已经入账的结果。
3. CLI 只有准备好的绑定时不能构造内容传输。激活先核对实际账本和当前已安装密钥，关闭临时原生所有者后，才发布启动提示并启动内容运行时。启动提示不授予账本权限。
4. JWT 设备声明明确延后到 PR-16；内容 token 继续严格限制独立 bucket、角色和不超过 15 分钟的有效期。
5. M2 只实现停止发送的安全兜底，完整换代交接属于 PR-20。首次同步上限为 1.75×，附耗时拆分；文档密钥始终不进渲染进程。

新后端接口先部署，再合入依赖它的客户端；私有指针更新单独进行。相关 Spec 仍为 draft，等待 owner 批准。提交前仍须完成可用性清单和独立对抗审阅。

真实本地后端与产品模块的集成脚本已通过主进程宿主、渲染/CLI 传输和实际 SessionDispatchWatcher 交换加密回合；两个工作区在子进程注入八天时钟后离线重开，排队消息重连后执行。系统保管、账号身份及模型执行仍是合成边界；同一子进程内重开全部宿主和存储，不等于打包应用进程重启。该链路还复现了 token 读取任务启动前取消、Effect 内的 finalizer 未执行而残留登记的问题，现改为真实 Exit 后的完成观察器移除登记，producer、lease 和原始清理失败的所有权保持原样。

## 审查后的恢复边界

本机终端入口保留普通 running/degraded 状态的行为。全局重连时，只有本地 agent 已启动、原生启动完成且当前工作区出现在运行时快照里，才能创建终端；其他工作区的重试不再禁用它。目标运行时缺失、进程不可用及启动未完成仍阻断，原生会话授权不变。组件测试通过实际 daemon hook 和 dock，把 CLI 状态 IPC 连到终端打开 IPC，并验证目标工作区恢复时无需重挂载。

CLI 明确选择接收加密工作区；已发布客户端继续只收到普通工作区，避免污染持久目录。设备访问凭证留在主进程，IPC 只返回是否可用；缺少凭证时隐藏本机审批，原生准备也在接触 CLI 前拒绝。未签名的配对材料可以替换；已签名材料必须等已验证原始历史证明原记录落账，或同一 parent 被另一条记录占用，才能开启新会话。retained 重开仍检查持久化的已验证前缀。新会话使旧审批失效，需要重新确认。机器保管丢失后，本地运行时按设备公钥隔离，保留旧证据；只有新设备完成入账验证并装好当前密钥，才能更新同一 genesis 的激活提示。等待配对不产生启动告警、全局离线状态或重试定时器，列表刷新也不重试。只有打开激活、绑定文件或已批准设备原件时明确返回 ENOENT 才进入等待；其他打开错误保留原件并沿用 Fleet 重试，文件访问恢复后无需重新激活或重启。符号链接、文件损坏及 genesis 检查继续拒绝不安全状态。测试在真实已安装密钥的运行时注入文件打开失败并验证恢复后重开；Fleet 的假时钟测试验证重试能启动运行时。激活绑定本次已验证批准的公钥；先释放身份不同的旧运行时，再安装新设备。旧清理暂时失败时，下次激活通过原有恢复路径重试清理，释放完成前不启动新工作。本地提示不授予云端或账本权限。

机器启动在打开保管前检查已批准设备的原件。原件丢失时等待配对，不探测钥匙串，也不启动 Fleet 重试；损坏及其他 I/O 失败保留原始错误。普通 catalog 继续使用版本 1 文件；加密条目放在独立且绑定账号、机器的文件中，已发布客户端读不到它。加密缓存失败时保留文件和原始诊断，普通工作区发现、远端授权更新与撤销继续进行；持久缓存标记阻止离线采用旧加密条目，直到正常对账修复缓存。

桌面换 token 时透传被拒 token，以淘汰对应的服务端缓存。配对以验证后的读回结果为准：已经确认落账时，追加确认丢失不推翻成功；读回也失败时，主进程在本地保留两个原始错误，IPC 只返回不带 cause 的稳定错误。本机 agent 调用有界超时后显示待确认，可明确重试，不声称已取消或激活成功。

本地账本的暂时存储失败通过既有合并刷新恢复，在 SDK 重试待发数据时触发，不依赖网络重连。签名、pin 和 epoch 失败继续阻止发送。本地编辑仍持久保存，清理失败的责任继续留在原所有者。

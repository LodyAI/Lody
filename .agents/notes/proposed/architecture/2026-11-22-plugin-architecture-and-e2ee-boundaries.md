# Plugin architecture convergence and E2EE workspace boundaries

Status: proposed
Translation: current

[简体中文](2026-11-22-plugin-architecture-and-e2ee-boundaries.zh.md)

## Abstract

An adversarial review of the initial [Lody Plugin System Spec](../../../../specs/plugin-system.md) against Paseo's production plugin runtime showed that sharing a single `PluginWorker` per machine manufactured cascading complexity — collateral crashes across plugins, canary fault-reproduction workers, silent read-only auto-retries, and a tri-digest (`clientDigest` / `machineDigest` / `revision`) state machine — while stacking peripheral loopback servers and multi-Agent blueprints before shipping a real Phase 1 runtime. This note proposes converging on **one dedicated subprocess per enabled `machine` plugin, serialized drain-before-respawn (`shutdown → 2s SIGTERM → 2s SIGKILL`), Fail-Stop with zero auto-retry, and `clientDigest` + runtime `instanceId`**, while preserving Lody's raw reactive data SDK (`lodyQueries`), three-layer orthogonal sidebars, Obsidian-style two-tier themes and host-managed custom CSS (stable `--*` token contract + disposable local `styles`), and six E2EE security boundaries. This trade-off spends roughly `30–45 MiB` per enabled `machine` plugin in exchange for OS-level fault attribution and deterministic teardown, while forbidding Guest dynamic plugin queries and restricting `'machine'` scope to the machine owner in E2EE workspaces. Only the TypeScript SDK contracts and `ctx.dataDir` atomic-persistence fixtures are verified today; daemon and client runtime hosts and real subprocess/browser E2E suites remain unimplemented.

## Core convergence decisions from adversarial review

### 1. Replace shared `PluginWorker` + Canary attribution + read-only auto-retry with per-plugin subprocesses + Fail-Stop

The earlier draft shared a single `PluginWorker` per machine to minimize baseline memory, but any synchronous infinite loop or V8 heap OOM killed every co-hosted plugin without stack attribution — forcing the design to invent short-lived canary workers, silent `defineQuery` retries, and Automation error-threshold exemptions. Aligned with [`.agents/docs/failure-containment.md`](../../../../.agents/docs/failure-containment.md) and Paseo's external subprocess model:

- **One dedicated `child_process.fork` subprocess per enabled `machine` plugin** (`0` backend processes for client-only, theme, or skill-only plugins): every crash, hang, or OOM maps unambiguously to one `pluginId`, eliminating canary fault-reproduction workers.
- **Drain-Before-Respawn and serialized lifecycle queue:** All `start` / `reload` / `stop` / `remove` transitions per `pluginId` run through one async queue; stopping an instance enforces `shutdown` → `2s SIGTERM` → `2s SIGKILL` (without premature `child.disconnect()` so `close` reliably fires), and **never spawns a replacement subprocess until the old OS process has exited**, preventing concurrent `ctx.dataDir` corruption.
- **Idle-reaped `--dev` compiler subprocess:** Development `esbuild` bundling runs in an on-demand child process that exits after `1s` idle, keeping bundler state out of the daemon heap and leaving zero orphaned `esbuild` processes on daemon shutdown.
- **Single-layer flat IPC and Fail-Stop (zero silent retry):** Host and subprocess exchange flat typed IPC messages directly; unexpected exit or timeout immediately rejects all pending calls (`outcome_unknown` for `defineMutation` / `defineTool`, direct error for `defineQuery`, `0` automatic retries for both) and marks the plugin `plugin_faulted` until explicit user `reload`.

_Deliberate departures from Paseo:_ (1) Lody omits Paseo's in-process `InternalPluginChild` fast path so built-in migrated plugins run under the exact same subprocess isolation contract rather than risking main-daemon crashes; and (2) Lody omits Paseo's nested WebSocket-over-IPC tunnel in favor of single-layer IPC messages.

### 2. Replace tri-digest and `revision_mismatch` with `clientDigest` + runtime `instanceId`

The earlier draft invented `machineDigest` alongside `revision` and `clientDigest` so UI edits in `--dev` would not break running Agent Turns frozen on a whole-package `revision`. Separating client and daemon lifecycles removes both `machineDigest` and `revision_mismatch`:

- `ClientPluginHost` tracks only `clientDigest = SHA-256(client.js + assets/)`: if a `--dev` rebuild leaves `clientDigest` unchanged, the mounted plugin instance, its `AbortController`, and its query cache stay intact; when `clientDigest` changes, the host runs cleanup, aborts subscriptions, removes managed `<style>` tags, and mounts the replacement.
- `PluginHost` assigns each spawned `machine` subprocess a monotonic runtime `instanceId`: editing `client.tsx`, themes, or `skills/` never restarts the `machine` subprocess or disturbs in-flight Agent Turns, while Zod `safeParse` guards wire payloads on both ends.

### 3. Preserve raw data SDK, three-layer sidebars, and Obsidian-style two-tier themes + managed CSS

- **Thin component props and three orthogonal sidebar layers:** Surface components receive only capability references and route `params`, pulling [`SessionMeta`](../../../../packages/shared/src/schema.ts) (`openedBySessionId`, `openedByRootSessionId`, `agentRoleId`, `pendingInteraction`) and machine/Git state on demand via `lodyQueries` + `useLodyQuery`. Backed by [`sidebar-surface.ts`](../../../../packages/components/src/components/sidebar-surface.ts), sidebars split into `sidebar.sessionRow.decorate` (paired with `lody.sessions.answerQuestion` over [`ask-user-question.ts`](../../../../packages/shared/src/acp/ask-user-question.ts) and [`use-permission-response.ts`](../../../../packages/components/src/hooks/use-permission-response.ts) while keeping tool `permission` approvals kernel-owned), `headerItems`/`footerItems` + `<SidebarRow />` + `screens.add`, and selectable `sidebar.views.add` (`<SessionRow />` automatically composes active row decorators).
- **Why keep two-tier `themes` + host-managed `styles` rather than banning custom CSS:** Because client plugins run as trusted, unsandboxed JS in the main renderer realm, `client.js` already has full `document` access — deleting `styles` provides zero sandbox security and merely pushes authors to append untracked `<style>` elements that leak across disablement. The real architectural boundary is **contract stability**: Tier 1 (`manifest.themes`, `lody.themes.add`, `lody.themes.activate` with `PluginThemeSeedColors` plus typography/radius/`density` `PluginThemeTokens`) derives root `--*` CSS variables via [`vscode-theme-dom.ts`](../../../../packages/components/src/lib/vscode-theme/vscode-theme-dom.ts) and [`vscode-theme-css.ts`](../../../../packages/components/src/lib/vscode-theme/vscode-theme-css.ts) as a **SemVer-stable contract**; Tier 2 (`manifest.styles`, `lody.styles.add`) provides a host-tracked local opt-in escape hatch (disposed on disablement/HMR, bypassed by `lody --safe-mode`, never auto-propagated to collaborators) whose **stability guarantee covers documented `--*` variables without freezing internal React DOM hierarchy**.

### 4. Remove hazardous/speculative hooks and narrow Phase 1 scope

- **Removed outright:** (1) `machine.beforeSessionTurn` (appending unsigned prompt markdown on the machine after personal-device verification undermines E2EE `memberInput` prompt integrity; context belongs in explicit `defineAttachmentSource` or `defineTool` outputs); (2) `ctx.sessionDataDir` (collapsed into installation `ctx.dataDir` keyed by immutable `toolCallId`, eliminating `session/fork` coupling); (3) `lody plugin propose` chat cards (replaced by a hard invariant: plugin install/enable/reload is never exposed on Agent MCP tools); and (4) pre-release aliases (`useHost`, `hostQueries`, `HostActions`) plus `results.add({ mimeType })`, which has no backing entity in [`history-apply.ts`](../../../../packages/shared/src/acp/history-apply.ts).
- **Deferred beyond Phase 1:** `createLodyClient()` loopback server, `manifest.agentRoles` / `roleTarget`, `manifest.settings` / `usePluginSettings`, `defineObservation` + `waitCondition`, `machine.onSessionEvent`, `businessKeyScope: 'project'`, bundled `acpProviders` / `mcpServers`, `workspace.pages.add`, and global `shell.*` / `commands.add`.

## Encrypted (E2EE) workspace boundaries

In E2EE workspaces ([`specs/e2ee-foundations.md`](../../../../specs/e2ee-foundations.md)), plugins enforce five architectural boundaries:

1. **Guest (`read`) vs Writer RPC separation:** Following [`e2ee-rpc.ts`](../../../../packages/shared/src/e2ee-rpc.ts) and [E2EE read queries](../../implemented/architecture/2026-10-28-e2ee-read-queries.md) (_"a method name cannot prove read-only"_), subprocess-executed `plugin/query`, `plugin/mutate`, and `plugin/attachment-*` never enter `E2EE_READ_QUERY_METHODS` and require non-Guest `authorizeExecution` (`<15 min` ledger freshness); Guest `useQuery` calls resolve cleanly to `{ status: 'unavailable', reason: 'forbidden' }`, leaving inline ≤16 KiB history snapshots and host-owned `useLodyQuery` reads available.
2. **Machine owner vs per-project `MachineSharing`:** Per [`specs/e2ee/machine-sharing.md`](../../../../specs/e2ee/machine-sharing.md) and [`packages/e2ee-machine-sharing/AGENTS.md`](../../../../packages/e2ee-machine-sharing/AGENTS.md), plugin install/enable/disable, `binding: 'installation'` settings, `ctx.env` secrets, and `'machine'`-scoped calls remain **machine-owner-only**; collaborators may invoke `'project'`- and `'session'`-scoped handlers only while `MachineSharing` actively shares both the machine and every bound project.
3. **Signed `e2eeIntent` provenance and 20-derivation cap:** Per [`e2ee-execution-intent.ts`](../../../../packages/shared/src/e2ee-execution-intent.ts), [signed execution intent](../../implemented/architecture/2026-11-10-e2ee-signed-execution-intent.md), and [shared-member derivation](../../implemented/architecture/2026-10-31-e2ee-shared-member-derivation.md), client `useLody().sessions.create` / `send` signs `memberInput` (`kind = 1`) on the personal device; on the daemon, only `ToolExecutionContext` inside an active human root Turn may sign `derivedFrom` `machineInput` (`kind = 2`, inheriting the 20-derivation cap and single-machine rule), while un-rooted `MachineContext` rejects `create` / `send` with `forbidden`.
4. **256 KiB single-frame Iroh fast path and 4 MiB bundle ceiling:** Per [E2EE Iroh transport](../../implemented/architecture/2026-11-10-e2ee-iroh-transport.md), `MAX_PLUGIN_RPC_REQUEST_BYTES` (256 KiB) keeps direct Desktop↔Machine calls inside one 1 MiB `purpose 8` Iroh frame, while `MAX_PACKED_CLIENT_BUNDLE_BYTES` (4 MiB) reuses existing 256 KiB `purpose 9` paged reads when Phase 2 remote bundle distribution ships.
5. **Custody isolation, redaction, and plaintext share fallback:** E2EE daemon `ctx.dataDir` lives under the identity-scoped `<account>/<workspace>/<genesis>/<signing-key>` custody root ([`apps/cli/src/lib/e2ee/AGENTS.md`](../../../../apps/cli/src/lib/e2ee/AGENTS.md)); Phase 2 client bundle and trust caches bind to the same custody tuple ([`specs/e2ee/client-custody.md`](../../../../specs/e2ee/client-custody.md), [`specs/e2ee/desktop-custody.md`](../../../../specs/e2ee/desktop-custody.md)), stay gated while workspace E2EE mode is `unknown`, and wipe on confirmed member removal or device revocation. Presence and telemetry strip all plugin identifiers and stack traces, and explicit plaintext shares ([plaintext share consent](../../implemented/feature/2026-10-28-e2ee-share-plaintext-consent.md)) export only inline ≤16 KiB history payloads using Lody's built-in fallback viewer without uploading `ctx.dataDir` or executing third-party `client.js`.

## Rejected alternatives

1. **Single shared `PluginWorker` per machine + canary fault workers + silent read-only retries:** Rejected because co-hosting plugins in one Node process forces speculative canary replay for unattributed infinite loops and OOMs, while auto-retrying arbitrary `defineQuery` code violates deterministic failure containment; per-plugin subprocesses isolate faults at the OS boundary.
2. **Tri-digest (`clientDigest` + `machineDigest` + `revision`) coordination:** Rejected because tracking `clientDigest` on the client and a runtime `instanceId` per `machine` subprocess already lets UI edits hot-swap without restarting backend subprocesses or interrupting running Agent Turns.
3. **`machine.beforeSessionTurn` post-verification prompt mutation:** Rejected because silently appending unsigned prompt text on the machine after personal-device `memberInput` signing erodes end-to-end prompt integrity and auditability.
4. **Banning host-managed custom CSS (`styles`) under a sandbox rationale:** Rejected because unsandboxed `client.js` already runs in the main DOM realm; banning `styles` creates no security boundary and forfeits host lifecycle cleanup and `--safe-mode` bypass over `<style>` elements. Separating SemVer-stable `--*` theme tokens from non-DOM-freezing host-managed `styles` preserves both rich theming and host refactoring freedom.
5. **Hardcoding a `swarm` entity in core or using a singleton `sidebar.replace`:** Rejected because publishing `lodyQueries` alongside three orthogonal sidebar layers reuses existing `SessionMeta` lineage/role fields without multi-plugin collisions.
6. **Exposing `plugin/query` to E2EE `read` Guests or letting un-rooted `MachineContext` sign `machineInput`:** Rejected because the former triggers arbitrary code execution from read-only Guest credentials and the latter turns the daemon into an un-rooted execution-signing oracle.

## Consequences and open limits

- **Pay-per-enabled-machine-plugin subprocess footprint:** Only enabled plugins declaring a `machine` entry spawn a Node subprocess (`0` subprocesses for client-only, theme, and skill plugins), trading modest RAM per active backend plugin for zero collateral crashes and deterministic `SIGKILL` recovery.
- **Honest E2EE Guest and un-rooted daemon limits:** E2EE Guests view inline ≤16 KiB history cards and `useLodyQuery` catalog state while dynamic plugin `useQuery` calls resolve to `forbidden`; background daemon handlers without an active human root Turn cannot originate new E2EE Session prompts.
- **Mobile native surfaces remain open:** `apps/mobile` continues to use built-in structured fallbacks rather than evaluating `client.js` bundles.

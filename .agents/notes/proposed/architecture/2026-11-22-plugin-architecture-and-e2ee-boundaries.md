# Plugin architecture convergence and E2EE workspace boundaries

Status: proposed
Translation: current

[简体中文](2026-11-22-plugin-architecture-and-e2ee-boundaries.zh.md)

## Abstract

Reviewing the [Lody Plugin System Spec](../../../../specs/plugin-system.md) across both runtime failure containment (against Paseo's production plugin host) and Agent Workspace product plasticity revealed two orthogonal failure modes: (1) sharing a single `PluginWorker` per machine manufactured cascading runtime complexity (collateral crashes, canary reproduction workers, silent read-only retries, and tri-digest coordination), while (2) over-pruning product extensibility risked reducing Lody to a static React-slot + RPC plugin system unable to express Sound Effect plugins, cross-provider Tool/Output renderers, Sorbet-class Workflow plugins, raw workspace state dashboards, Agent-assisted plugin authoring, or unified Desktop + Web experience. This note converges on **a lean, fail-stop per-plugin subprocess runtime (`child_process.fork`, Drain-Before-Respawn, zero auto-retry, `clientDigest` + `instanceId`) paired with full no-fork Agent Workspace extensibility**: canonical Client + Machine Host Events, universal `tools.matchRender` and `messages.renderBlock` contributions with mandatory `"View Raw Output"` host toggles, complete Workflow composition (`agentRoles`, `skills`, out-of-daemon `mcpServers`, and `acpProviders`), expanded `lodyQueries` plus detached read-only raw document snapshots (`useLodySnapshot` / `readSnapshot`), declarative `manifest.config` + first-run `onboarding`, Agent-assisted `lody_plugin` `propose_*` approval cards, unified Electron + Web `Core Conformance` bundle streaming (with Mobile Capacitor inline cards/config + `useHostCapabilities()` negotiation), and E2EE signing/custody gates.

## Core convergence decisions

### 1. Keep the runtime engine lean: per-plugin subprocesses, Drain-Before-Respawn, and Fail-Stop

Aligned with [`.agents/docs/failure-containment.md`](../../../../.agents/docs/failure-containment.md) and Paseo's external subprocess boundary:

- **One dedicated `child_process.fork` subprocess per enabled `machine` plugin** (`0` subprocesses for client-only, sound, theme, or skill-only plugins): every crash, hang, or V8 OOM attributes unambiguously to one `pluginId`, eliminating canary workers.
- **Drain-Before-Respawn and serialized lifecycle queue:** All `enable` / `reload` / `disable` / `remove` transitions per `pluginId` execute serially; stopping enforces `shutdown → 2s SIGTERM → 2s SIGKILL` and **never spawns a replacement PID until the old OS PID emits `close`**, preventing `ctx.dataDir` races.
- **Idle-reaped `--dev` compiler subprocess & `clientDigest` + `instanceId`:** Development `esbuild` runs in an on-demand child process reaped after `1s` idle; `ClientPluginHost` reconciles solely by `clientDigest = SHA-256(client.js + assets/)` while `PluginHost` tracks a monotonic runtime `instanceId`, eliminating `machineDigest` and `revision_mismatch`.
- **Single-layer flat IPC and zero automatic retry:** Unexpected exit or timeout settles in-flight `mutation` / `tool` calls as `outcome_unknown` and `query` calls as errors with `0` automatic retries, quarantining the plugin in `Faulted` until explicit `reload`.

### 2. Restore full Agent Workspace plasticity without re-bloating the runtime

Simplifying process management does not justify cutting platform extensibility:

- **Canonical Host Events (`lody.events.on` & `machine.events.on`) + Orthogonal Asset & Lifecycle Primitives (`lody.assets.url`, `lody.signal`):** Plugins subscribe to typed Session/Turn/Tool transitions and local UI interaction events (`ui.message.submitted`, `ui.session.switched`, `ui.interaction.resolved`, `ui.command.invoked`) without DOM scraping or polling, composing standard Web Audio + `assets.url` + `signal` for zero-process Sound Effect plugins without bespoke `audio` SDK slots and event-driven workflow orchestrators (with `machine.onStart(ctx)` reconciling unfinished journaled workflow steps across Daemon restarts).
- **Universal Tool Call Matchers & Message Block Renderers:** Alongside own-tool `tools.render`, `tools.matchRender` matches built-in, ACP (Claude, Codex, Antigravity, custom ACP), and MCP tool calls by name/kind/command predicate with deterministic priority, and `messages.renderBlock` renders custom fenced code blocks / structured artifacts. A non-spoofable host header toggle (`"View Raw Output"` / `"View Raw Markdown"`) plus `SurfaceErrorBoundary` guarantees plugins can never trap ground-truth output or violate [`ai-gui`](../../../../packages/components/src/components/ai-gui/AGENTS.md) search/folding rules.
- **Complete Workflow Composition (`agentRoles`, `skills`, `mcpServers`, `acpProviders`):** Workflow plugins (such as Sorbet Super Assistant) package Roles, Skills, out-of-daemon MCP servers ([`apps/cli/src/agent/AGENTS.md`](../../../../apps/cli/src/agent/AGENTS.md)), and custom ACP Agent runtimes (`Workflow Provider Conformance Profile`, launched via `acp-session-start-gate.ts`) under one manifest.
- **Typed `lodyQueries` + Detached Read-Only Raw Snapshots (`useLodySnapshot` / `readSnapshot`):** Beyond 18 typed descriptors (including `sessionTurns`, `subagentRun`, `agentConfigs`, `automations`, `plugins`), power dashboards read deeply frozen (`Object.freeze`), secret-redacted raw workspace/session/transcript snapshots lazily materialized on demand over Lody's existing Loro/Flock and [`session-data`](../../../../packages/shared/src/session-data/AGENTS.md) / Roost readers (zero parallel Domain Store, zero whole-tree rebuilds per commit/token), while `HistoryWriter` and Kernel commands remain the sole write path.
- **Two-tier Appearance (`themes` + host-managed `styles`) & Three-layer Sidebars:** Preserves SemVer-stable `--*` theme tokens ([`vscode-theme-dom.ts`](../../../../packages/components/src/lib/vscode-theme/vscode-theme-dom.ts), [`vscode-theme-css.ts`](../../../../packages/components/src/lib/vscode-theme/vscode-theme-css.ts)) alongside disposable `<style>` sheets and composable sidebars ([`sidebar-surface.ts`](../../../../packages/components/src/components/sidebar-surface.ts)).

### 3. First-class DX, UX, Propose-Confirm Agent authoring, and Cross-Device Core parity

- **Unified Electron + Web in `Core Conformance`, Adaptive Mobile Capacitor:** Remote `client.js` bundle streaming (`<= 4 MiB` paged chunks + `clientDigest` trust gate) is promoted into `Core Conformance` so Web shares exact plugin parity with Desktop Electron. [`apps/mobile-capacitor`](../../../../apps/mobile-capacitor/AGENTS.md) supports inline tool/message cards, client events, and declarative config in Core while negotiating 1:1 shell `containers` (`sidebarViews`, `sessionPanels`, `screens`, `projectPages`) via `useHostCapabilities()`.
- **Declarative `manifest.config` + `onboarding`:** Generates native Settings forms and First-Run Setup Sheets automatically without custom React boilerplate, storing secrets exclusively in daemon keychain custody.
- **Agent-Assisted Authoring via Propose-Confirm (`lody_plugin` MCP):** Modeled on [`schedules/AGENTS.md`](../../../../apps/cli/src/lib/schedules/AGENTS.md) (`schedule_proposal.ts`) and `lody_agent_role`, Agents can scaffold plugins and call `propose_install` / `propose_enable` / `propose_reload` to publish an idempotent in-chat approval card, while executable activation remains strictly gated on human confirmation (`LODY_AGENT_SESSION_ID` cleared on human terminals).

## Encrypted (E2EE) workspace boundaries

In E2EE workspaces ([`specs/e2ee-foundations.md`](../../../../specs/e2ee-foundations.md)), plugins enforce five architectural boundaries:

1. **Guest (`read`) vs Non-Guest execution gate:** Per [`e2ee-rpc.ts`](../../../../packages/shared/src/e2ee-rpc.ts) and [E2EE read queries](../../implemented/architecture/2026-10-28-e2ee-read-queries.md), `plugin/query`, `plugin/mutate`, and `plugin/attachment-*` stay outside `E2EE_READ_QUERY_METHODS` and require non-Guest `authorizeExecution` (`<15 min` ledger freshness).
2. **Machine owner vs per-project `MachineSharing`:** Per [`specs/e2ee/machine-sharing.md`](../../../../specs/e2ee/machine-sharing.md) and [`packages/e2ee-machine-sharing/AGENTS.md`](../../../../packages/e2ee-machine-sharing/AGENTS.md), plugin lifecycle, `machine`-scoped secrets/calls, and workflow provider configuration remain machine-owner-only; collaborators invoke `'project'` / `'session'` handlers only while `MachineSharing` grants the machine and all bound projects.
3. **Signed `e2eeIntent` across Interactive, Tool, and Rooted Workflow Events:** Per [`e2ee-execution-intent.ts`](../../../../packages/shared/src/e2ee-execution-intent.ts), [signed execution intent](../../implemented/architecture/2026-11-10-e2ee-signed-execution-intent.md), and [shared-member derivation](../../implemented/architecture/2026-10-31-e2ee-shared-member-derivation.md), client actions (`create` / `send` / `respondInteraction`) sign `memberInput` (`kind = 1`), and rooted machine handlers (`ToolExecutionContext` / `MachineEventContext` / `MachineStartupContext`) symmetrically support `create` / `send` / `respondInteraction`; daemon `ToolExecutionContext` and `machine.events.on` handlers triggered by an event carrying a verified `userTurnId` (or a human-signed workflow declaration on that machine) sign `derivedFrom` `machineInput` (`kind = 2`, 20-derivation cap, single-machine rule), whereas un-rooted queries/mutations reject `create` / `send` with `forbidden`.
4. **256 KiB single-frame Iroh fast path and Core 4 MiB paged Web bundles:** Per [E2EE Iroh transport](../../implemented/architecture/2026-11-10-e2ee-iroh-transport.md), `MAX_PLUGIN_RPC_REQUEST_BYTES` (`256 KiB`) fits one 1 MiB `purpose 8` frame and `MAX_PACKED_CLIENT_BUNDLE_BYTES` (`4 MiB`) pages over `256 KiB` `purpose 9` chunks.
5. **Custody isolation, snapshot redaction, and plaintext share fallback:** Daemon `ctx.dataDir` and Core Web/Desktop remote bundle caches bind to `<account>/<workspace>/<genesis>/<signing-key>` ([`apps/cli/src/lib/e2ee/AGENTS.md`](../../../../apps/cli/src/lib/e2ee/AGENTS.md), [`specs/e2ee/client-custody.md`](../../../../specs/e2ee/client-custody.md), [`specs/e2ee/desktop-custody.md`](../../../../specs/e2ee/desktop-custody.md)) and wipe on member removal or device revocation; raw snapshots strip secrets and foreign `businessKey`s; static plaintext shares ([plaintext share consent](../../implemented/feature/2026-10-28-e2ee-share-plaintext-consent.md)) render built-in fallbacks without uploading `ctx.dataDir` or executing third-party `client.js`.

## Rejected alternatives

1. **Shared `PluginWorker` + canary fault workers + silent read-only retries:** Rejected in favor of OS subprocess isolation and deterministic Fail-Stop.
2. **Restricting `tools.render` to plugin-owned tools or omitting Host Events / Workflow Roles & Providers:** Rejected because it forces DOM scraping/polling for interactive plugins (e.g. Sound Effects) and prevents no-fork workflow extensions (e.g. Sorbet Super Assistant) and cross-tool result customization.
3. **Relegating Web remote plugin UI to an optional Extension or banning Agent plugin proposals outright:** Rejected because Web is a core Lody client surface, and `propose_*` + human-confirmed approval cards preserve human execution authority without breaking Agent-assisted plugin authoring.
4. **`machine.beforeSessionTurn` silent prompt mutation or mutable CRDT handle exposure:** Rejected because post-signing prompt mutation breaks E2EE `memberInput` integrity, while detached `Object.freeze` snapshots provide full read freedom without bypassing `HistoryWriter` invariants.

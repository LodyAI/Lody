## Abstract

The product removal path must revoke access without waiting for a new encryption key. Native member controls submit ordinary records and reuse the existing settings key-update entry. A credential-confirmed whole-member removal stops and drains that workspace before automatically deleting its managed local data. Exact device checks and durable receipts protect a later rejoin from an old response; this is honest-client cleanup, not secure erasure or proof of production acceptance.

## Decision and responsibilities

The owner decision of 2026-10-27 permits Owner/Admin removal, forbids Admin removal of Owner/Admin, and forbids removing the Owner. Only Owner changes Admin roles. UI affordances follow these rules; native verified-ledger policy remains authority. Member and key commands share the existing `host.manage` entry, signer and SQLite submission journal. Only an explicit `rotate` resumes an uncommitted epoch candidate; staging failures cannot gate independent removal or revocation. Unknown CAS outcomes must first reconcile the exact original bytes and acknowledge persisted verified history. An old committed result satisfies the new request only when operation type, membership ID and role (or device target) all match. Capability 1 is declared before tag 10. The existing atomic tag 8 API stays separate.

Removal preserves epoch/commitment and makes rotationRequired advisory. Remaining members keep their retained epoch; an administrator finishes the key update in settings. Failed rotation does not undo removal or gate sending. The settings entry/red dot belongs to the existing key-update implementation; this PR adds no second rotation workflow.

The credential endpoint distinguishes whole-member removal from individual-device revocation. A generic directory/history denial or network failure cannot delete data. The host first compares the originating account, workspace, genesis, signing key and credential against the installed identity and persists a terminal marker. It stops native admission and drains the workspace outside network locks. The account coordinator closes its isolated owner and takes the existing exclusive identity lease before deletion; a busy process lease retains the receipt for retry. A newer identity is spared. No renderer can request arbitrary filesystem deletion or export keys.

Admitted member history uses the host-owned bounded ingest loop, never reacquiring the account lock while logout/close waits for that operation. The renderer retires its own runtime, then independently deletes the original account/workspace/genesis/signing-key instance’s data. Repo/cursors and high-water add the window scope; pending inputs, cross-window locks and broadcasts use the identity instance. A saved public locator lets a cold open that immediately learns removal find only the previously installed instance. Missing or mismatched locators cannot authorize broad deletion. It keeps a cleanup marker and one scoped retry receipt until all independent stores succeed. Deletion is excluded from the global runtime-drain receipt; a blocked or failed delete cannot fail the next unrelated workspace, while a successor using those exact databases joins its cleanup. Another account or newly invited device has a different namespace, including after a renderer restart. CLI removal fences content and first verifies the original identity and persists its terminal receipt. Close waits for this short local phase after draining history/snapshot diagnosis and before releasing custody; it does not await the full deletion task that calls back into parent close. A persistence failure remains observable, still stops the execution owner and releases custody/leases through the terminal close path; full erasure is skipped. The regression checks exclusive lease reacquisition even when the parent never calls close. After execution/document owners drain, the identity lease and pairing mutex protect erasure of custody, runtime and only `content/<genesis>/<signing-key>` inside that account/workspace directory. LoroDocumentManager opens that same path while its native owner holds the shared identity lease; ordinary workspace paths are unchanged. User project directories and other workspaces remain. A new invitation/membership generates new device keys; old membership pairing is refused. Public pins and tiny cleanup receipts remain. Offline copies can only be cleared after the client learns the removal; other stopped window namespaces clean themselves when opened. This does not reclaim malicious copies, backups or prior external side effects.

## Alternatives and integration

Waiting for epoch publication would violate removal availability. Deleting by workspace ID alone could erase a later rejoin. Treating every unauthorized response as removal would erase data after an individual-device revoke or account/network failure. That rejection still holds; the exact authenticated device-revocation code later received its own device-scoped cleanup in [desktop device revocation](2026-10-30-e2ee-desktop-device-revocation.md). Separate member journals would allow concurrent uncertain submissions by the same signer. The shared ordinary journal settles pending CAS originals; an unsubmitted rotation candidate remains independent.

This independent branch merges public main `281f40a7`, including [24-A](https://github.com/LodyAI/Lody/pull/1979) and the pending-publication recovery fix [#1987](https://github.com/LodyAI/Lody/pull/1987). Validation uses that merged code directly; no core overlay remains. The publisher is unchanged from main, and the native regression exercises both device revocation and member removal through the shared management entry. Private adoption [#3880](https://github.com/loro-dev/lody/pull/3880) and backend removal [#3876](https://github.com/loro-dev/lody/pull/3876) are merged; this establishes source composition, not deployed product acceptance. The branch composes the settings implementation already merged in [#1980](https://github.com/LodyAI/Lody/pull/1980); verified management state sees the removal hint and a single management owner drains all admitted commands. Shared join glue still needs composition review. Specs remain draft: the old mandatory atomic-removal and paused-send text is replaced with the explicit MVP decision, not marked approved.

## Evidence and limits

Behavior tests use real crypto, native SQLite, deterministic injected failures and explicit completion signals. They cover ordinary role/removal records, retained old epoch, staging outage versus unknown publication CAS across reopen, full recovered-intent matching, lost-ACK native-owner reopen with identical bytes, exact-incarnation cleanup, credential-only deletion signaling, exclusive-lease retry, shutdown during member history and blocked IndexedDB deletion with sibling availability, machine execution-owner drain, fresh-member keys, scoped IndexedDB deletion, confirmation and terminal UI. New native management/cleanup tests were RED against the base, then GREEN with this implementation; final composition is validated against merged main without an overlay. The former workspace-global CLI database allowed delayed old-account cleanup to delete another account’s open store; a concurrent close could also release custody before the removal receipt existed. Both regressions are RED on the previous head and GREEN with real SQLite snapshots and explicit signals. The equivalent renderer cross-restart namespace case is covered with IndexedDB. The short-phase wait remains in the registered Legacy facade: published Promise Repo and parent lifecycle callbacks remain dependencies, so no complete native migration is claimed. The unified management entry was RED before implementation; dropping full intent matching makes all three intent regressions RED. The unknown-CAS regression requires an actual retry with the original record bytes while staging remains unavailable, then verifies the member is absent and rotation remains advisory. Temporarily restoring pre-#1987 publisher recovery makes both revoke and remove regressions RED; the unchanged main publisher makes both GREEN. A built desktop smoke run also exposed an eager import of the cloud client through the removal error class, failing startup with ERR_PACKAGE_PATH_NOT_EXPORTED before boot. The error brand now lives in a small host-only module so IPC can classify removal without loading cloud transport. The existing first-run smoke explicitly cold-restarts a profile without a cloud account while retaining another encrypted identity’s valid cleanup receipt and IndexedDB content. The ordinary workspace keeps its plaintext cache namespace and editable composer, and the foreign receipt/content remain unchanged. Restoring the two old static imports reproduces the same pre-boot error and makes this scenario RED; restoring the original fixed source and build makes it GREEN. Final affected-suite counts and static checks are recorded in the PR.

Existing content tokens expire within their current lifetime (at most 15 minutes). Active invalidation/disconnection of already issued tokens and long connections is deferred. Real keychains, Windows ACL/native ABI, installed app restart, two physical members/devices, live cloud/gateway token behavior and M5 execution acceptance remain unverified. No merge, deployment, gitlink adoption or release is implied.

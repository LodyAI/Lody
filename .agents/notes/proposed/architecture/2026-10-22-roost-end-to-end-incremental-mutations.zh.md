# Roost 端到端增量变更

Status: proposed
Translation: current

[English](2026-10-22-roost-end-to-end-incremental-mutations.md)

## 摘要

Native 文本追加已经是增量的，但 Lody 在提交前后仍复制完整消息或状态正文，
并重新读取已加载的历史。本次将共享语义层的变更计划贯穿验证、Native 内容操作和
私有投影安装，并使用 SDK 证明过的目录转换。范围包括标签、工具、结束动作和恢复
后的状态更新，也包括普通文本追加。公开读取的所有权、持久化确认和权威恢复保持
原有约束。产品调度仍存在全历史读取，下文工作负载未证明端到端工作量不随历史增长。

## 问题与决策

本次接续[原子检查点工作](2026-10-22-roost-atomic-content-checkpoints.zh.md)和
[此前的投影优化](2026-10-22-roost-owner-incremental-projection.zh.md)。
独立合成探针中，旧文本为 0/256 KiB/1 MiB 时，Native 追加 p50 分别为
0.178/0.167/0.172 ms，而应用路径从 1.621 增长到 4.770 ms。Native 单独测量不含
收据、索引、控制文档持久化和消费者，只用于定位重复的应用工作，不能作为可达延迟承诺。

初版只优化了 primary 的文本后缀修改和本地目录创建，没有完成复杂操作与恢复状态的
投影复用。本次完成后的消费者在这些路径上遵守同一套语义与持久化约束：

- 共享 reducer 和动作规划器在私有写时复制草稿上记录修改路径，持有新输入并保留
  未修改的存储值。写入验证仍有决定权：路径只用于选择**经过验证的顶层子树**，
  不直接采用 Immer patch 的值。验证可能规范化该字段内的兄弟值，只选择叶子会漏写。
- 精确文本后缀提示避免反复扫描普通追加。真正改写已有文本时仍生成紧凑、按 Unicode
  标量索引的 splice。未闭合的 thinking/plan 块在结束标记完整出现前不运行全文解析，
  有界尾部分析识别跨片段标记。原有解析器、重叠/快照去重、逐事件顺序及坏标量的
  修复或拒绝行为继续共用。
- 私有暂存覆盖 `set`、`remove`、`appendText`、`spliceText`、`spliceArray`，
  同时维护应用值与 SDK 无损表示，只复制修改路径的祖先和新值。新增键遵循 Native
  的规范顺序，自有键检查与 Unicode 标量偏移通过真实 Native 边界核对。
- 只有 Native 元数据、完整事件区间、owner generation 和未变化的窗口均匹配，才安装
  暂存结果。状态层还要求派生索引组实际生效。修改并封存时只读取权威的小型 header/hash。
  不确定结果、外来事件或不支持的转换沿用权威正文读取；最终检查点发布继续验证事件覆盖。
- 恢复后的状态只与最后一个相关追加操作合并；其他修改按受影响字段重建相对 primary
  的差异，保持操作顺序且不无限积累程序。投影按路径复制，不再深复制不可变 primary；
  精确的私有 SDK 快照保留解码值。公开读取和模型摘要仍脱离私有对象。命令借用只发生在
  串行写队列内部，队列外的输入回执查询继续使用正式读取器。

检查点和分支证据由 Roost 持有。每次事务仍原子比较保留的全部检查点证明行；只有
Native 确认没有写入的 stale，才刷新一次。目录转换只证明已确认的本地线性追加成员关系，
不证明旧正文的新鲜度。分叉、远端穿插、不完整页面和不确定结果继续走恢复流程。

本次不修改 Rust/Native 运行时、存储或线协议、签名、保留策略与持久化保证，也不增加
兼容读取器、迁移、发包或部署。这是纯规划/投影工作，不涉及 Effect 生命周期迁移。
如出现无法保持可观察行为或保证的改动，必须停止并讨论。

## 验证与测量边界

[统一验证流程](../../../docs/roost-validation.md)管理准备、所属测试、固定手动负载和
失败处理。持久化基准及配置保存在 `apps/cli/benchmarks`，不进入默认 CI；现在也覆盖
混合标签、工具、计划更新，以及结束/重新打开后继续流式输出。

### 缺测项与源码解释

本次未测：固定 1,000/10,000 条消息前缀、独立的相邻游标页延迟、user/assistant
各自创建时间、独立工具/计划/thought 操作、首次和后续恢复追加、释放后或强制 GC 后
内存、Native 独占保留量、逐层事务/Worker 耗时、WAL/SHM 峰值、等价的 Loro 增量
交付、网络 HTTP/Stream offset 字节，以及 renderer 可见延迟。已有结果不能证明
预期的超长历史优势。

源码审查说明此前的总括结论为什么不充分：

- Loro 的[Agent 写入器](../../../../apps/cli/src/lib/loro/session-agent-writes.ts)
  已通过 `HistoryWriter.updateTail` 选择目标尾部/条目窗口。锁定的 `loro-repo`
  0.23.3 `persistDocUpdate` 从上次持久化版本导出增量，普通追加并不每次序列化完整历史。
  因此，热的尾部写入延迟本身不能区分全文驻留与 Roost 分页设计。
- [Roost 接入层](../../../../apps/cli/src/session/roost-node-session.ts)对未缓存的
  绝对位置范围或 ID 查询，通过 `readRangeEntries`/`scanPages` 从尾部逐页扫描并投影
  中间正文。因此，当前跳到最老页的探针会物化中间页面并可能填满正文缓存，不能标为
  一次相邻翻页，也不能代表只驻留最新窗口的内存。`readTurnOutput` 也明确读取完整
  entries；本次没有测量其实际调用频率和成本。
- 进一步源码审查发现了此手动基准未包含的真实产品调用者：[调度器](../../../../apps/cli/src/session/session-dispatch-watcher.ts)
  在首次调度检查，以及等待历史期间收到再次检查请求时，调用 `checkHistoryAndQueue`，
  其中直接调用 `backend.readHistory`。Roost 后端经 `readAll`/`readCompleteEntries`，
  缓存未命中时遍历完整活动分支、投影全部正文并保留完整快照；即使命中缓存也复制全部
  条目。因此，这条路径仍有随整段历史正文增长的工作，没有使用有界最新页接口。
  当前写入/读取基准没有测其实际调用频率和端到端耗时。不能简单替换为只查最新页：
  更老的待处理输入、终态修复证据、队列顺序和 RPC 去重都必须保持权威。

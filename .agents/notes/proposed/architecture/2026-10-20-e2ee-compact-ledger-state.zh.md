# 带完整设备历史的紧凑账本授权状态

Status: proposed
Translation: current

[English](2026-10-20-e2ee-compact-ledger-state.md)

PRs：本次改动（叠在 [LodyAI/Lody#1625](https://github.com/LodyAI/Lody/pull/1625) 之上），细化[保留验证状态](2026-10-19-e2ee-retained-ledger-state.zh.md)。

## 摘要

保留状态、背书快照和比对摘要共用的授权状态，大部分事实存了两遍，还会丢失历史。已用的签名公钥、加密公钥和成员 ID 是独立的集合，又把当前设备和成员重复了一遍。撤销和移除之后，退役设备当时用的是哪把加密公钥、属于哪个成员关系，都不再保留。因此，恢复或从快照导入的视图无法确定退役设备所写内容的作者，也无法把收到的状态原样重新导出。现在状态里有两张只追加的历史表：所有曾登记的成员关系及其用户，所有曾登记的设备及其加密公钥和成员关系。它们只编码一次，采用定长行。各来源因此在状态、摘要和每台设备的作者上完全一致。实测账本缩小 18%，在一台机器上恢复耗时从 24 ms 降到约 15 ms。原始 epoch 发布记录仍不保留。

## 问题

- **事实存两遍。** 状态数组有 11 个字段。已用的签名公钥、加密公钥和成员 ID 是排好序的集合，又把每台当前设备和每个当前成员存了一遍。在下文的实测账本里，这部分加上逐项的 CBOR 头，总共 165,581 字节。
- **撤销后丢历史。** `revokeDevice` 和 `removeMemberAndPublishEpoch` 会删除当前行，之后只剩 `contentAuthors`（签名公钥 → 用户、成员关系）；`usedEncKeys` 是独立的集合。两台设备都退役后，从 {S1, S2} 和 {E1, E2} 推不出哪把加密公钥对应哪把签名公钥。
- **快照和保留状态的作者。** 导入时只为当前设备重建作者，所以快照或恢复点之前已退役的设备一律打开为 `device-only`，状态也无法原样重新导出。一个连同全部设备一起被移除的成员，导入后它的用户 ID 无处保存。

## 决定

### 状态模型

当前视图 `members` 和 `devices` 仍只含当前对象，所有按存在性判断的授权检查都不变。新增的持久事实：

| 字段 | 内容 | 写入时机 |
|---|---|---|
| `membershipUsers` | 所有曾登记的成员关系 → 用户 ID | 创世、接纳成员；永不删除 |
| `deviceHistory` | 所有曾登记的签名公钥 → 加密公钥、成员关系 | 创世、接纳成员、接纳设备；永不删除 |

撤销和移除只修改当前视图。派生索引在各路径中重建或增量维护，不编码：
- `usedEncKeys` 即 `deviceHistory` 里的加密公钥；
- `usedCommitments` 即 `historyPackets` 里的承诺；
- `memberUsers` 是当前成员的用户集合，供重新接纳时查重，不是历史表。

`usedSigningKeys`、`usedMembershipIds` 和 `contentAuthors` 被删除，因为历史表本身就是这些集合。

### 信任决定：采信背书携带的历史（所有者决定）

合格背书快照携带完整的设备历史，导入时为其中每台设备（包括已退役的）建立作者身份。这是所有者的明确决定：合格背书者伪造历史归属不在威胁模型内。

其他约束都不放宽：
- 背书者仍需通过独立的角色和位置资格校验；
- 任意有效签名仍不能产生可信视图；
- 背书视图仍报告 `endorsed-snapshot`，绝不升级为 `full-history`。

因此 `historicalContentIdentity` 总是返回 `kind: 'member'`，`device-only` / `missing-history-context` 这个变体被删除。

### 编码

外层结构不变，版本号和摘要域升到 2（见[格式版本](#格式版本)）：

```
保留状态   [2, 创世(32), 长度, head(32), S, 验证方式（0 完整历史，1 背书快照）]
快照正文   [2, 创世, 长度, head, 签名者, S]
状态摘要   sha256("lody-e2ee/snapshot-digest/v2\0" ‖ [2, 创世, 长度, head, S])
```

`S` 是 6 个元素的 CBOR 数组：5 个由定长行拼接成的字节串，加一个布尔值。

| # | 表，行顺序 | 行 |
|---|---|---|
| 0 | 成员关系，按成员 ID | ID (16) · 用户 ID (32) · 角色 (1)：0 已移除，1 所有者，2 管理员，3 成员，4 访客 |
| 1 | 设备，按签名公钥 | 签名公钥 (32) · 加密公钥 (32) · 成员关系序号 (u32 BE) · 状态 (1)：0 已退役，1 个人，2 机器，3 恢复 |
| 2 | 加入请求，按设备序号 | 设备序号 (u32 BE) · 请求 ID (16) |
| 3 | epoch 承诺 0..n | 32 |
| 4 | 历史包 1..n | 72 |
| 5 | 需要轮换 | 布尔值 |

以下内容不存储，都能从表中推出：
- 所有者（角色 1）；
- epoch 号（承诺数 − 1）和当前承诺（最后一个）；
- 已用的密钥、成员 ID 和承诺；
- 已关闭的加入请求（设备公钥加请求 ID）；
- 每台设备的作者（设备所属的成员关系，及该成员关系的用户）。

摘要仍对去掉最后一个元素的保留字节计算，不需要再编码一次。这要求摘要正文与保留状态外层使用同一个版本号。

### 格式版本

紧凑 `S` 最初沿用了旧版本号。现在两种布局的版本 1 字节都会被拒绝：

- 保留状态外层和快照正文都是版本 2。摘要域改为 `snapshot-digest/v2`，因为它哈希的内容与 v1 不同。
- 解码器只接受当前版本。其他版本以 `unknown-version` 失败。宿主本来就把它当作“全量重放重建”，所以过期的保留行重放一次即可恢复。
- `snapshot/v1` 和 `head-attest/v1` 签名域不变。版本号在被签名的正文中，所以版本 1 的正文无法当作版本 2 通过验证。
- 账本 v1 记录和 `test/ledger-v1-vector.json` 不变。
- 以后改动 `S` 或任一外层时，三者一起升级。

### 恢复时的摘要校验

`restoreVerifiedState` 接受可选的 `stateDigest`，即 `exportVerifiedState` 返回、并由宿主与字节一起保存的值：

- 传入时，恢复先解码字节，再从字节重算摘要（一次 SHA-256），不一致时以新错误码 `state-digest-mismatch` 失败。先解码，是为了让旧行仍报告 `unknown-version`，而不是摘要不一致。
- 不传时，行为不变。
- 范围：它能发现损坏、截断或错配的行，但防不住能同时替换字节和摘要的写入方。签名和曲线点仍不重新检查。
- 摘要覆盖位置和 `S`，不覆盖最后的验证方式字节。单独翻转该字节不会被发现。

### WebAssembly 可观测性

`@lody/e2ee-core/protocol` 也导出 `ed25519WasmActive()`，让无法打包 `./cloudflare` 的宿主（如 Convex）上报严格 Ed25519 是否在 WebAssembly 中运行。它只读状态，不能借此注入、替换或关闭任何验证后端。

快照和保留状态的 CBOR 现在允许单个字节串达到各自的总预算（2 MiB 和 16 MiB），因为一张表就是一个字节串；账本记录仍限 256 字节。它们的数组长度上限降为记录的 32，因为 `S` 只有 6 个元素。

### 规范性解码

出现以下任一情况即拒绝：
- 字段数、类型或行宽不对，或历史包数不等于承诺数 − 1；
- 成员 ID 不严格升序、角色不在 0–4、所有者不恰好一个，或两个当前成员共用同一用户；
- 签名公钥不严格升序、加密公钥重复、成员关系序号越界，或状态不在 0–3；
- 当前设备属于已移除的成员关系、某成员关系没有设备，或所有者没有当前的非机器设备；
- 加入请求的设备序号不严格升序、请求数不等于成员关系数 − 1，或两个请求指向同一成员关系的设备；
- 承诺重复；
- 不满足现有的、相对账本长度的上界，包括长度为 1 时必须是创世形态。

快照导入会对每把签名公钥做曲线校验；保留状态恢复跳过这一步，因为字节来自调用方自己的存储。

### 各来源的重建规则

| | 完整重放 | 合格快照导入 | 保留状态恢复 |
|---|---|---|---|
| 持久事实 | 由记录写入 | 从 `S` 解码 | 从 `S` 解码 |
| 作者 | 每台设备 | `S` 中每台设备 | `S` 中每台设备 |
| `verification` | `full-history` | `endorsed-snapshot` | 沿用导出时的值 |
| 已验证哈希 | 全部 | 只有 head（`historyStart` = 长度 − 1） | 只有 head |
| `epochPublications` | 所有重放过的发布 | 无 | 无 |

## 验收（"相同"的含义）

- **与来源无关。** 在同一位置，完整重放、合格快照导入、任一来源的保留状态恢复，`S` 逐字节相同，比对摘要和 `ledgerStateDigest` 相同，每台曾登记设备的作者也相同；追加同样的记录后依然如此。
- **同来源往返。** 恢复后的视图再导出，保留字节完全一致，包括来源字节。先恢复再追加，与原视图直接追加的结果相同。不同来源只在最后的验证方式字节上不同。
- **行为等价。** 下一条记录的接受/拒绝及错误码都与完整重放相同。覆盖的情形有：退役设备的签名公钥、退役设备的加密公钥配新签名公钥、已移除的成员 ID、连同全部设备一起被移除的成员关系、当前用户的第二个成员关系、已用承诺，以及撤销已退役的设备。
- **有意的差异。** 恢复点之前的已验证哈希不保留，`hasVerifiedRecordHash` 对它们返回 false。恢复点之前发布的 epoch，`epochPublicationRecord` 会失败，因此恢复或导入的视图无法为这些 epoch 用 `getCommittedEpochStagingKey` 暂存密钥。`verification` 跟随来源。

测试先在账本里构造以下事件，再第一次导出：
- 多台设备退役；
- 一个成员被移除；
- 一个成员连同全部设备一起被移除；
- 同一用户以新的成员关系重新加入；
- 五个 epoch。

测试还会交换两台退役设备的加密公钥，检查摘要随之改变。两次故意引入的回归都被测试抓到：解码时丢弃退役行，以及撤销时删除历史。

## 实测

账本共 1,301 条记录：150 个成员关系（其中 50 个已移除）、301 台设备、1,000 次轮换，使用真实的密钥和签名。耗时为一台开发机上的单次运行。

| | 之前 | 之后 |
|---|---|---|
| 保留字节 | 165,581 | 135,293（−18%） |
| 恢复 | 24.0 ms | 14.8 ms |

逐行的精确开销：一个带一台设备的成员 138 字节，每台额外设备 69 字节，每次轮换 104 字节。移除和撤销只改一个字节，状态不会变小。一个 900 KiB 分块可容纳约 6,600 个单设备成员或 8,800 次轮换，之前分别是 3,300 和 8,200。2 MiB 的快照上限现在能容纳约 15,000 个单设备成员，之前约 5,000。

剩下的字节几乎都是随机数据：每台设备 64 字节的公钥，以及 72 字节的历史包。压缩没有帮助。

## 备选方案

- **在保留状态外层为快照来源的状态单独记一份作者列表。** 只在不采信背书历史时才需要；所有者做出决定后已删除。
- **退役设备的加密公钥只存截断哈希**（每台退役设备约省 16 字节）。误匹配只会拒绝一把新公钥，但设备表就不再是统一的行结构。
- **把历史包移出 `S`。** 它们占四分之一的字节，但快照和摘要都绑定了它们；这是协议改动，需要单独决定。

## 限制与后续

- 不做兼容：目前没有已部署的状态。旧编码不再读取，其版本 1 以 `unknown-version` 拒绝。
- 未改变：恢复或导入的视图仍无法为恢复点之前发布的 epoch 暂存密钥；候选修复是按位置从账本读取原始发布记录。
- 未验证：私有后端的分块存储在新字节下的表现。它把这些字节当作不透明数据，但需要升级到这版核心库。

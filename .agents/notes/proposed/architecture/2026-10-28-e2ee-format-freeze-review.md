## Abstract

Ledger v1 becomes a permanent verification contract when production encrypted workspace creation first opens. This review recommends **not freezing yet**: the owner must resolve the recovery admission and trust-anchor questions against the actual v1 record shapes, and approve the remaining unapproved protocol fields. The independent ledger vector already covers capability declaration and independent removal. Other formats are current-only under the existing compatibility decision, but preserved data must not be rolled back; current-only is not a license to destroy it. This is a source review at `b6882f13f12ec0144ccb6d1a1d0707af3a6ed663`, not production or device acceptance.

## Decisions before freeze, highest impact first

1. **Needs decision, potentially changes v1:** [permission ledger §3, §9](../../../../specs/e2ee/permission-ledger.zh.md) leaves recovery-device proof fields, recovery vault/trust-anchor encoding, self-revocation rotation, and enrollment ordering unapproved. [Records](../../../../packages/e2ee-core/src/internal/ledger/records.ts) already encode recovery admission as tag 4, and possession as `lody-e2ee/possess/v2\0`. Owner must explicitly decide whether that existing record and proof contain all identity, membership and key bindings required by the intended recovery protocol. If not, approve the exact pre-freeze change and regenerate the independent vector; after freeze, introduce new behavior as a new capability-gated operation and retain old verification. Decide whether trust-anchor material must occur in genesis or an existing record; external vault encoding can otherwise be decided independently. The current code does not establish that either answer has been approved.
2. **Needs reconciliation before approval:** [whitepaper §6](../../../../specs/e2ee/whitepaper.md#6-backup-and-recovery) describes `vault-v1` and a detailed setup, while the approved ledger Spec explicitly excludes its unresolved fields and §9; [vault Spec](../../../../specs/e2ee/recovery-vault.md) is draft. This is a status/intent conflict, not proof that the draft bytes are approved. After the recovery format decision, align the whitepaper with the recovery-vault Spec in the same review round; do not silently promote the draft to approval. The vault and PRF wrapping can be decided later only if they do not change accepted v1 records or genesis.
3. **Approved by owner on 2026-10-28:** tag 9, capability 1 and tag 10 retain the existing implementation, including 1–16 strictly ordered codes, limits and `upgrade-required` on an unsupported declaration. This approval does not settle recovery or authorize production. The separate approval documentation PR records it.
4. **Can defer with a boundary:** optional offline export, Web/mobile custody, backup publication thresholds, product rollout, lost-owner account deletion and capacity/retention policy can be decided separately if they do not alter existing record verification. A new ledger operation requires a prior supported capability; a genesis parameter change requires a new linked ledger. Self-revocation rotation and enrollment sequencing may likewise be deferred only after confirming that existing tag 4/5/7 and their proof fields suffice; sequencing and recoverability must still be reviewed before enabling recovery.

## Proposed recovery format for owner review

**Recommendation: keep the existing tag 4 and `possess/v2` bytes; change no genesis or ledger record field.** This is a proposal, not an implementation or approval. Freeze only after the owner accepts this allocation and the private package format is specified and tested. It uses the preceding verified state to supply the fields that the record does not repeat:

```text
record = CBOR([ [previousHash32, approvingPersonalEd25519Public32,
                 [4, 2, R_ed25519Public32, R_x25519Public32, R_possessionSignature64]],
                approvingPersonalSignature64 ])
R_possessionSignature = Ed25519_R("lody-e2ee/possess/v2\0" ||
  CBOR([genesisHash32, membershipId16, R_ed25519Public32, R_x25519Public32, 2]))
approvingPersonalSignature = Ed25519_D("lody-e2ee/sig/v1\0" || CBOR(record body))
```

Canonical bounded ledger CBOR and the existing 8192-byte record / 256-byte byte-string limits apply. `previousHash` binds exact position and existing chain; the active personal signer binds user authorization and derives `membershipId` from the immediately preceding verified state, not a server claim. The proof binds the pinned genesis, member instance, both R public keys and kind 2, preventing cross-workspace/member/key substitution; outer signature and chain bind the approval to its predecessor. Signing-key proof **does not prove X25519 private-key possession**. Before calling setup recoverable, import both private keys, derive and compare both public keys, decrypt a fresh current-epoch envelope addressed to R, and check the ledger epoch commitment; this is an operational acceptance gate, not a new ledger proof. Ledger verification uses strict Ed25519 checks; its X25519 field check currently requires exactly 32 nonzero bytes and does not reject every low-order input. Successful HPKE decrypt and key-pair comparison are separate acceptance checks, not stronger ledger parsing. Revocation does not invalidate old signed records.

It is a concurrency/version label, not epoch, ledger authority or a key-reuse exception. Same-generation competing first setups adopt the winning package; different replacement candidates conflict rather than silently merge. | Existing [vault package](../../../../packages/e2ee-core/src/internal/recovery/vault.ts) already stores generation; no tag 4 or proof field added. Propose explicitly specifying overflow as failure and generation reset on a new membership. |
| Trust and ledger source | In the **encrypted package**, store canonical CBOR object fields `genesis` (lowercase 64 hex), `membershipId` (lowercase 32 hex), `generation`, `signingPublic`/`encryptionPublic` (32-byte bstr each), `signingPrivate`/`encryptionPrivate` (PKCS#8 DER bstr, 32–256 bytes), and `trust: {source, genesisRecord, head, length}`. `source` is a bounded nonempty locator/label, never an authority; `genesisRecord` is original canonical signed bytes ≤8192, `head` is lowercase 64 hex and `length` a positive safe integer. The encrypted index binds genesis/member/generation, immutable entry ID and ciphertext digest. Package and index are bounded to 256 KiB and reject noncanonical CBOR. The [host DTO](../../../../packages/e2ee-core/src/host/recovery-vault.ts) carries only entry ID, revision and opaque ciphertext, not these plaintext identity or trust fields. | Existing implementation already has these fields; no ledger change. Add a **`formatVersion: 1` package field**, reject other versions, and specify the exact PKCS#8 algorithm/DER validation and source interpretation in the recovery Spec and implementation before using this proposal. Do not accept an unsupported version or silently rewrite originals. |

**Trust bootstrapping:** The package must originate from a vault entry selected and authenticated by the user's recovery capability and the previously verified setup, and its genesis must equal an independently pinned or previously authenticated workspace identity. Verify that hashing `genesisRecord` gives the pinned genesis and verify its signature. Check a fetched full ledger from that genesis against a separately qualified endpoint, and prove that the saved head/length is a prefix before accepting later state. A stored head/length is a rollback checkpoint only if captured from an actually verified view; package encryption and the `source` string do not prove that provenance or a globally latest head. If independent anchor or endpoint qualification is unavailable, stop and request trusted confirmation; do not promote a server URL, self-signed genesis or fresh server response into trust. A server can still withhold newer records; freshness/availability are separate assumptions. Current [workspace workflow](../../../../packages/e2ee-core/src/internal/recovery/workspace.ts) validates the genesis record against caller-supplied genesis, but the package's source/head/length are not themselves a demonstrated independent trust or freshness check.

**Why no anchor in genesis or tag 4:** a genesis cannot authenticate its own selection, and a service locator or saved checkpoint can change independently of membership. Adding them to permanent public ledger bytes would expose or hard-code mutable recovery storage without proving its trust. Keep the signed genesis and previously verified checkpoint inside the encrypted package with independently qualified provenance; an independently authenticated lookup locates the rest of the chain. If an owner instead requires publicly verifiable recovery-generation or publicly committed anchor provenance, that is a different requirement and needs an explicitly approved pre-freeze record design and regenerated vector; do not infer it from the private vault counter.

**Ordering and self-revocation:** generate R and upload/read back/decrypt its immutable private package; select the winner through index CAS; active personal D signs tag 4 with R proof; persist exact record and position, submit/reconcile, then verify admission; finally publish/read/decrypt a current-epoch envelope and check its commitment before marking recoverable. Ordinary replacement verifies the new R before revoking old; compromise may revoke first. If D self-revokes, its already-signed tag 5 is reconciled as original bytes and another eligible personal signer must perform any later tag 7 rotation; an R may admit a new personal device but may not rotate. If no eligible manager remains, no rotation can be promised. Revocation sets advisory rotation-required; it does not block honest content seals. These are ordering and availability rules, not changes to existing tag 4/5/7 encoding; no cross-store atomicity is claimed.

**Owner decision requested:** (1) approve unchanged tag 4/`possess/v2`, with private generation and externally qualified trust rather than a public ledger field; (2) approve the proposed private package version and the trust/possession acceptance gates, or identify any additional recovery data that must be permanently verifiable in the ledger. Package-vault formats and production recovery remain draft until their own review. Add fixed independent vectors for recovery tag 4 and proof, wrong genesis/member/kind/key, private package/index version, replacement/CAS, invalid PKCS#8, unmatched X25519 key and trusted checkpoint mismatch before freezing. No test was run to establish that these proposed gates already exist.

## Vector and domain review

Keep the existing independent ledger generator and committed bytes immutable after freeze. Before freeze add or verify fixed expected bytes, hashes, signatures and resulting state for each tag and permitted device kind, recovery admission, machine initial/replacement, capability-before-use, unknown capability, rejected tag 2, malformed/noncanonical CBOR and exact boundary lengths. Include wrong signer, cross-domain and cross-genesis negatives. For non-ledger formats, add independent fixtures for v4 state/snapshot, purposes 7/8/9 and RPC resource Unicode/BOM/max length, policy v2 generation transitions, attachment AAD/chunk boundaries, schedule fingerprint and custody blob. Tests for truncation, unknown version/tag and re-encoding must check rejection without changing retained originals.

The inspected ledger, content, policy, attachment and custody domains above are distinct literal namespaces; no collision was established by this review. Schedule hashes have no dedicated domain or explicit version, which makes future semantic evolution ambiguous; this observation is not a demonstrated cross-protocol collision. RPC resource encoding produces unpadded base64url; this review did not establish a separate parser accepting padded aliases. No unfixed ledger size bound or noncanonical accepted ledger encoding was established from the inspected codec.

## Evidence and limits

Supersession search found existing ledger, compact-state, sharing, attachment and journal notes owning their respective mechanisms; this proposal does not replace them. The review inspected source and fixed fixtures, not deployed backend, real-device behavior, all local formats or a formal proof of domain disjointness. It does not approve any Spec or grant production activation. Open questions above remain owner decisions; no format change is implemented here.

# E2EE pre-freeze format review

Status: proposed
Translation: current

[中文](2026-10-28-e2ee-format-freeze-review.zh.md)

## Abstract

Ledger v1 becomes a permanent verification contract when production encrypted workspace creation first opens. This review recommends **not freezing yet**: the owner must resolve the recovery admission and trust-anchor questions against the actual v1 record shapes, and approve the remaining unapproved protocol fields. The independent ledger vector already covers capability declaration and independent removal. Other formats are current-only under the existing compatibility decision, but preserved data must not be rolled back; current-only is not a license to destroy it. This is a source review at `b6882f13f12ec0144ccb6d1a1d0707af3a6ed663`, not production or device acceptance.

## Decisions before freeze, highest impact first

1. **Needs decision, potentially changes v1:** [permission ledger §3, §9](../../../../specs/e2ee/permission-ledger.zh.md) leaves recovery-device proof fields, recovery vault/trust-anchor encoding, self-revocation rotation, and enrollment ordering unapproved. [Records](../../../../packages/e2ee-core/src/internal/ledger/records.ts) already encode recovery admission as tag 4, and possession as `lody-e2ee/possess/v2\0`. Owner must explicitly decide whether that existing record and proof contain all identity, membership and key bindings required by the intended recovery protocol. If not, approve the exact pre-freeze change and regenerate the independent vector; after freeze, introduce new behavior as a new capability-gated operation and retain old verification. Decide whether trust-anchor material must occur in genesis or an existing record; external vault encoding can otherwise be decided independently. The current code does not establish that either answer has been approved.
2. **Needs reconciliation before approval:** [whitepaper §6](../../../../specs/e2ee/whitepaper.md#6-backup-and-recovery) describes `vault-v1` and a detailed setup, while the approved ledger Spec explicitly excludes its unresolved fields and §9; [vault Spec](../../../../specs/e2ee/recovery-vault.md) is draft. This is a status/intent conflict, not proof that the draft bytes are approved. Review the exact revision and choose its owner; do not silently promote the whitepaper to approval. The vault and PRF wrapping can be decided later only if they do not change accepted v1 records or genesis.
3. **Needs decision:** §4.5 is marked pending review, although foundations and code define tag 9 and capability 1/tag 10. Approve the exact permanent declaration and stop-on-unknown semantics, including whether all intended v1 authority rules and size limits are final. Fix any intended change before freeze; merely merging the code is not approval.
4. **Can defer with a boundary:** optional offline export, Web/mobile custody, backup publication thresholds, product rollout, lost-owner account deletion and capacity/retention policy can be decided separately if they do not alter existing record verification. A new ledger operation requires a prior supported capability; a genesis parameter change requires a new linked ledger. Self-revocation rotation and enrollment sequencing may likewise be deferred only after confirming that existing tag 4/5/7 and their proof fields suffice; sequencing and recoverability must still be reviewed before enabling recovery.

## Vector and domain review

Keep the existing independent ledger generator and committed bytes immutable after freeze. Before freeze add or verify fixed expected bytes, hashes, signatures and resulting state for each tag and permitted device kind, recovery admission, machine initial/replacement, capability-before-use, unknown capability, rejected tag 2, malformed/noncanonical CBOR and exact boundary lengths. Include wrong signer, cross-domain and cross-genesis negatives. For non-ledger formats, add independent fixtures for v4 state/snapshot, purposes 7/8/9 and RPC resource Unicode/BOM/max length, policy v2 generation transitions, attachment AAD/chunk boundaries, schedule fingerprint and custody blob. Tests for truncation, unknown version/tag and re-encoding must check rejection without changing retained originals.

The inspected ledger, content, policy, attachment and custody domains above are distinct literal namespaces; no collision was established by this review. Schedule hashes have no dedicated domain or explicit version, which makes future semantic evolution ambiguous; this observation is not a demonstrated cross-protocol collision. RPC resource encoding produces unpadded base64url; this review did not establish a separate parser accepting padded aliases. No unfixed ledger size bound or noncanonical accepted ledger encoding was established from the inspected codec.

## Evidence and limits

Supersession search found existing ledger, compact-state, sharing, attachment and journal notes owning their respective mechanisms; this proposal does not replace them. The review inspected source and fixed fixtures, not deployed backend, real-device behavior, all local formats or a formal proof of domain disjointness. It does not approve any Spec or grant production activation. Open questions above remain owner decisions; no format change is implemented here.

# E2EE 控制面只在接受账本记录时验签

Status: proposed
Translation: current

[English](2026-10-22-e2ee-control-plane-verification-scope.md)

## 摘要

按原设计，服务端要在多处验签：签发访问 token 前做一次性持钥挑战，信箱、暂存、加入申请也要逐条验证签名。但访问 token 大约每 15 分钟续一次，这样的验签成本落在热路径上，而它防住的情况，接收端本来就会自己验签拒绝。Owner 于 2026-10-21 决定：账本、密钥投递、访问凭证与加入申请这几项控制面服务，只在接受账本记录时验证签名；其余请求改为用入账时绑定的设备访问凭证识别设备，并查服务端在接受账本记录时同步维护的设备状态。同时确认：机器设备没有系统钥匙串时用只有本用户可读的文件保存密钥，并在配对批准时告知用户。本记录只修订 Spec 和后端指南，相应的服务端实现尚未开始。

## 背景与问题

- 白皮书原文要求宿主在以下场合验证签名：签发和续签 JWT 时用一次性挑战核验持钥；写入信封前验证发送设备签名；网关核验信封签名；先核验加入申请签名。
- 访问 token 的有效期约 15 分钟。如果每次续签都做持钥挑战，再读账本状态并验证新记录，这些成本都落在每台活跃设备的热路径上。
- 只有账本必须由服务端在写入前拦住坏记录：账本只能追加，一条坏记录写进去之后，所有客户端都会停在那里，工作区的控制面会被永久卡死。信封、安装报告、暂存组、加入申请即使是坏的，接收端在使用前也会验签、核对承诺并拒绝。

## 决定

1. **控制面只在接受账本记录时验签。** 创建、追加和恢复写入时仍然完整验证；其他控制面请求不做服务端密码学验证。
2. **设备访问凭证。** 设备入账时生成随机凭证，服务端只保存它的哈希，绑定到（工作区, 设备签名公钥）。绑定有两个时机：创建请求，以及提交 `admitDevice` 记录时。新设备对"配对会话 ‖ 凭证哈希"的签名由审批端在本地验证，防止别人把自己的凭证挂到别人的公钥上。
3. **设备状态投影。** 服务端在接受账本记录的同一个事务里，同步更新"设备是否有效、种类、角色"。签发 token、处理信箱和暂存请求时只查这张表，撤销在写入账本时立即生效。
4. **信箱与暂存的结构检查。** 发送者必须等于凭证对应的设备；收件人必须是当前有效设备；纪元必须是当前纪元；字节不可变；每个发送者有数量上限。需要更强保证的宿主仍可调用 `@lody/e2ee-core/host` 的验签辅助函数（后端指南中的"可选层"）。
5. **机器文件保管。** 机器设备第一次创建保管时，如果系统钥匙串的写入、读回测试失败，就选择文件保护，之后不再自动切换；个人设备只用系统安全存储；配对批准界面必须告知用户。实现见 [M1 运行时边界](../../implemented/architecture/2026-10-21-e2ee-m1-runtime-boundaries.zh.md)。

## 考虑过的方案

- **每次签发 token 前做持钥挑战**（原 Spec）：每次续签都要两次往返，并读取账本状态，成本高。它额外防住的只是凭证被盗用的情况，而凭证被盗等同于设备被攻破，按撤销加换代处理即可。
- **用链式 nonce 降低往返次数**：仍然需要服务端验签和 nonce 状态，复杂度没有省掉。
- **所有控制面请求都在服务端验签**：成本最高。接收端反正要再验一遍，服务端多验一次只能挡住一台已认证设备往自己的槽位里写垃圾。

## 取舍与限制

- **作恶空间：** 一台已认证设备最多能往自己发出的信封和自己的槽位里写无效内容，受数量上限约束，可以追溯到具体设备；接收端会拒绝并发起修复。它不能冒充别的设备，也拿不到密钥。
- **凭证泄露：** 等同于设备被攻破，处理方式是撤销设备并换代。凭证不轮换。
- **作用范围：** 内容写入准入不在本决定范围内，仍由白皮书 §4.2 和未定的写入准入方案负责。
- **审批：** 本记录对应的 Spec 修订仍是草稿，需要 owner 批准。设备访问凭证、投影、信箱、暂存的服务端实现尚未开始。

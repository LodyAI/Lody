## 摘要

本文将规范性文档 [Lody 插件系统规范](../../../../specs/plugin-system.zh.md) 以及 [插件架构收敛与 E2EE 工作区边界](2026-11-22-plugin-architecture-and-e2ee-boundaries.zh.md) 中的架构边界决策，转化为覆盖 `@lody/plugin-sdk`、`@lody/shared`、`apps/cli`、`@lody/components`、`apps/electron` 与 `apps/mobile-capacitor` 的仓库级工程实施蓝图。守护进程侧的所有 OS 子进程（`PluginHost` 与 `DevPluginCompiler`）均严格收敛至通用 Effect 进程边界 [`packages/shared/src/node/process.ts`](../../../../packages/shared/src/node/process.ts) 并由原生 Effect v4（`4.0.2`）`Scope` 托管；客户端渲染、原始状态快照读取、永久保留的 `SessionCreationReceipt` 幂等回执与 E2EE 执行签名则直接复用现有的 `ai-gui`、`sidebar-surface`、`vscode-theme`、Loro/Flock、`sessionData`/Roost 与 `e2ee-execution-intent` 模块所有者，不引入任何平行状态存储。整体交付按依赖顺序拆解为四个纵向闭环的 Stacked PR（`PR-1` 至 `PR-4`）：其中 `PR-2` 即跑通覆盖 Desktop Electron 与 Web 的完整交互插件纵向闭环，`PR-3` 在此之上叠加原始快照、机器侧工作流与有根 E2EE 派生。当前实施证据见[规范 §17.4](../../../../specs/plugin-system.zh.md)。

## 2. 原生 Effect v4 生命周期与故障隔离契约

遵循 [`packages/shared/src/node/AGENTS.md`](../../../../packages/shared/src/node/AGENTS.md) 与 [`scripts/check-cli-process-boundary.mjs`](../../../../scripts/check-cli-process-boundary.mjs)，`apps/cli` 严禁直接导入 `node:child_process` 或调用 `process.kill` / `child.kill`。为此，在 [`packages/shared/src/node/process.ts`](../../../../packages/shared/src/node/process.ts) 的 `NodeProcessApi` 中新增 `spawnIpcChild`（并在 `process-testing.ts` 的内存进程表中提供等价桩实现），返回受 `Scope` 约束的句柄 `{ pid, send, messages: Stream<unknown, ProcessIpcError>, exit, ringBuffer }`。**通用 `process.ts` 完全不感知任何插件业务协议：** 其 `Scope` 终结器仅执行纯粹的 OS 进程树终止（`terminateTree`：`SIGTERM -> 2000 ms waitUntilGone -> SIGKILL -> 剔除僵尸进程的 OS 进程表核验` + `ProcessReleaseFailed` 恢复租约）；应用层的 `{ type: "shutdown", graceMs: 2000 }` IPC 帧完全由上层 `PluginHost` 在关闭子 `Scope` 前自行发送。

`PluginHost` 与 `DevPluginCompiler` 均采用原生 Effect `4.0.2` 服务编写（`Context.Service`、`Layer.effect`、`Effect.fn`、`Schema.TaggedError`、`PubSub`、`Deferred`、`Ref`、`Clock`），逐项落实 [`cli-effect-ts.md#behavior-contract`](../../../docs/cli-effect-ts.md) 与 [`failure-containment.md`](../../../docs/failure-containment.md)：

| 契约维度                                                          | `PluginHost`（`apps/cli/src/plugins/workflow/plugin-host.ts`）                                                                                                                                                                                                                                                                                                                                                                                                                                                           | `DevPluginCompiler`（`apps/cli/src/plugins/workflow/dev-plugin-compiler.ts`）                                                                                                        |
| ----------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **1. 触发源（Trigger）**                                          | 守护进程启动（非 `--safe-mode` 下自动拉起已启用插件）、显式 CLI/RPC `enable` / `reload` / `disable` / `remove`，或 `machine.js` / `manifest` 发生变更的 `--dev` 重编译。                                                                                                                                                                                                                                                                                                                                                 | 显式执行 `lody plugin link --dev`、`pack`，或受监听插件源码目录触发去抖（`150 ms`）文件变更。                                                                                        |
| **2. 所有权与 FIFO 串行化**                                       | 守护进程根 `Scope` 持有 `PluginHost`；每个运行中的 `machine` 插件独占一个子 `Scope.Closeable`。鉴于 Effect `4.0.2` 的 `Semaphore` 在立即重入时不保证 FIFO，按 `pluginId` 隔离的生命周期变迁采用**自管 `Ref`/`Deferred` FIFO 队列**，在严格保序执行 `disable` / `remove` 的同时将积压的重复 `--dev` `reload` 合并为最新一次构建。                                                                                                                                                                                         | `PluginHost` 子 `Scope` 按需持有编译子进程租约。基于 `Clock` 的空闲计时器（`1000 ms`，支持 `TestClock` 确定性推进）在无排队/运行中构建时自动关闭编译 `Scope`，使常驻编译器内存归零。 |
| **3. 取消与协议分层回收**                                         | 关闭插件子 `Scope` 前，`PluginHost` 先中止宿主 `AbortController`，经 `handle.send` 发送 `{ type: "shutdown", graceMs: 2000 }`（不提前调用 `child.disconnect()`），并将 `handle.exit` 与 `2000 ms` `Clock` 计时器竞速；若超时仍未退出，关闭子 `Scope` 交由 `process.ts` 的 `terminateTree`（`SIGTERM -> 2000 ms -> SIGKILL -> waitUntilGone`）强制回收。守护进程退出时对全部插件回收施加总超时上限，杜绝失控子进程阻塞退出。                                                                                              | 取消或被新构建取代时立即中断当前编译 Fiber；若 `esbuild` 子进程无响应，关闭其 `Scope` 即经 `terminateTree` 强制清理整棵进程树。                                                      |
| **4. `clientDigest` 与 `instanceId` 解耦及 Drain-Before-Respawn** | `instanceId` 专用于标识 **`MachinePluginInstance` 子进程运行代次**，**唯有当 `PluginHost` 实际派生新的 `machine` OS 子进程时才递增**。仅修改 `client.tsx`、主题或 CSS 只会更新 `clientDigest` 并热替换各客户端，**绝不重启 `machine` 子进程或轮换 `instanceId`**。当确实需要重派生 `machine` 子进程时，旧 OS PID 存活期间绝不启动替代进程；若 `Scope.close` 抛出 `ProcessReleaseFailed`，`PluginHost` 保留其恢复租约并令后续 `enable` / `reload` 等待 `lease.retryTermination` 直至 `waitUntilGone` 确认旧进程彻底消失。 | 编译产物先写入临时目录，仅在编译成功后原子提交新 `clientDigest` 与产物目录（绝不持有或修改 `instanceId`）；编译失败保留旧有效产物并将结构化诊断推送至 `Plugin Inspector`。           |
| **5. 规范超时上限与零自动重试**                                   | 严格执行规范第 9.3 节时限：`init -> ready` 为 **`10_000 ms`（`10 s`）**；`start`（`machine.onStart`）、`query`、`mutation`、`attachment-*` 与 `event` 均为 **`30_000 ms`（`30 s`）**；`defineTool` 为 **`600_000 ms`（`10 min`）**。握手超时、异常退出或协议违规直接置为 `Faulted`，**自动重试次数为 `0`** 且**绝不缓存失败的启动 Fiber**。崩溃或超时将未决 `mutation` / `tool` 结算为 `PluginCallError { code: "outcome_unknown" }`，未决 `query` 立即报错且不重放。                                                    | 编译器崩溃或语法/打包错误直接令当次构建失败并返回文件/行号诊断；守护进程侧文件监听器保持存活，开发者保存修复后即可触发下一轮编译。                                                   |
| **6. 爆炸半径隔离**                                               | 纯客户端、主题、纯 Skill 与 `sound-effects` 插件占用 `0` 个后端子进程。插件 `A` 的崩溃、CPU 死循环或 `--max-old-space-size=256` V8 OOM 仅终结 `A` 自身 PID，守护进程、活跃 ACP 会话与插件 `B` 零受累。                                                                                                                                                                                                                                                                                                                   | `esbuild` 运行在 `DevPluginCompiler` 独立子进程内，原生打包器崩溃或内存溢出绝不污染守护进程堆空间。                                                                                  |

## 3. 数据面、UI 挂载稳定性、产物分发与 E2EE 门禁接线

### 3.1 共享 `lodyCommands` 命令注册表、零平行存储 `lodyQueries`、永久 `SessionCreationReceipt` 与无窗口 `onStart`

- **第一方与插件共用的类型化宿主命令注册表（`lodyCommands`，零平行命令系统）：** Lody 不重复发明另一套插件专属命令系统，而是将现有宿主业务写操作提炼为 `packages/shared/src/commands/host-commands.ts` 中的类型化 `LodyCommandDescriptor<S, TInput, TOutput>` 注册表 `lodyCommands`（完整涵盖会话执行 `sessionCreate` / `sessionSend` / `sessionRespondInteraction` / `sessionStop` / `sessionArchive` / `sessionRestore` / `sessionFork`、基于 [`status-view/command.ts`](../../../../packages/shared/src/status-view/command.ts) 的状态分流命令 `sessionSetPinned` / `sessionSnooze` / `sessionSettle` / `sessionMoveToFocus` / `sessionMoveOrder` / `sessionUpdateTitle` / `sessionMarkRead` / `sessionMarkUnread`、置顶分组 `pinSection*` 及定时任务控制 `schedule*`）。[`use-session-actions.ts`](../../../../packages/components/src/hooks/use-session-actions.ts) 第一方 UI 与插件 `lody.execute` / `useLodyCommand` / `ctx.lody.execute` 统一委派至同一套 `workspace-command-executor.ts` / `daemon-command-executor.ts` 执行管线（`sessions.*` 仅保留为指向 `lodyCommands.session*` 的轻量语义别名）：每次调用均绑定不可伪造的宿主 `ActorContext`（客户端绑定当前登录用户；机器侧 `plugin/query` 与 `plugin/mutate` 绑定发起 RPC 的已认证成员；`defineTool` 与 `machine.events` 绑定所属会话/回合的 `SessionMeta.userId` / 经核验 `originTurn` 签名人；`machine.onStart` 对回合结束后的新工作使用独立授权的工作流主体，并对无明确用户主体的个人偏好命令如 `sessionMarkRead` 直接拒绝 `forbidden`），直接复用第一方 `prefer` 与 `manage` 分级守卫（[`use-session-management-guard.ts`](../../../../packages/components/src/hooks/use-session-management-guard.ts)）、E2EE `MachineSharing` / `e2eeIntent` 门禁及 `ui.command.invoked` 广播，绝不因插件安装在机器所有者 Daemon 上就赋予跨成员代理修改偏好或审批的越权能力。

- **类型化查询（`lodyQueries`）与按需脱离句柄快照（`useLodySnapshot` / `readSnapshot`）：** `ClientPluginHost` 与 `PluginHost` 直接在现有工作区 Loro/Flock 文档读取器及 [`packages/shared/src/session-data`](../../../../packages/shared/src/session-data/AGENTS.md) / Roost 窄查询索引上解析全部 18 个描述符（含 `sessions` 上的 `sessionIds`、`agentRoleId`、包含边界 `updatedAfter` 过滤，以及 `sessionTurns` 上的 `userTurnId` / `stopReason`），零平行 Domain Store。快照订阅仅挂载引用计数窄监听器并做脏版本标记；**唯有调用方实际读取脏分片时**才执行 `structuredClone` + 递归 `Object.freeze` + 密钥与外部插件 `businessKey` 剥离。
- **永久保留的 `SessionCreationReceipt`（无 TTL 过期）：** `SessionCreationReceiptStore` 在托管作用域 SQLite 库中**永久持久化** `(workspace_id, caller_user_id, canonical_target_key, plugin_id, request_id) -> { payload_sha256, session_id, business_key? }`，不设任何 TTL（单行约 250 字节，累计 10 万次派生仅约 25 MiB，仅在 E2EE 托管擦除或显式执行 `lody plugin remove --purge-data` 时清理）。即便原会话已归档或设备离线数天后重启，重放相同归一化载荷仍返回原 `SessionRef`；篡改载荷返回 `idempotency_conflict`；会话归档后释放 `businessKey` 供新 `requestId` 复用，同时永久保留历史 `requestId` 幂等回执（严格对齐规范第 7.3 节）。
- **无间隙启动事件暂存与对账（`ready -> buffer -> onStart -> drain -> live`）：** 为在不引入 Durable Event Broker 的前提下彻底消除“历史对账扫描刚读完、实时订阅尚未打开之间恰好完成一个 Turn”的漏单窗口，`PluginHost` **在收到 `ready` 的同一时刻即将该实例的 `subscribedEvents` 监听器接入内存启动暂存队列**，随后下发 `start` 执行 `machine.onStart(ctx)`（`30_000 ms` 时限）完成 `ctx.dataDir` 日志与 `lodyQueries.sessions({ updatedAfter })` / `sessionTurns` 历史对账，待 `onStart` 返回后按到达顺序排空暂存事件再原子切换至实时直通。对账与暂存队列的重叠事件经插件日志键与永久 `SessionCreationReceipt` 自动幂等去重。

### 3.2 客户端 UI 挂载、规范三层 `sidebar` 与 `blockId` 状态保护

- **三层客户端身份模型（`Installation Key` / `Bundle Key` / `按安装实例隔离的模块求值`）与 `Trusted Dev Session`：** 对齐规范第 8.5 节，`ClientPluginHost` 严格区分三层身份：（1）**安装实例键 `(workspace_id, source_key, plugin_id)`**（`source_key = "machine:<machine_id>" | "local"`），决定实例归属、来源机器路由、`config`、`events` 与 `query_cache`；（2）**不可变产物键 `(plugin_id, clientDigest)`**，仅用于共享去重 `plugin/bundle-chunk` 下载、SHA-256 校验、托管缓存落盘与静态 `assets/*`；（3）**按安装实例隔离的模块求值 `(workspace_id, source_key, plugin_id, clientDigest)`**，为每个 Installation 分配独立且在停用/HMR 时吊销的临时 Blob/Module URL（同时共享宿主外置的 `react` / `zod` / `@lody/ui` / `@lody/plugin-sdk/*` 单例），确保两台机器运行同一插件时 `client.tsx` 顶层的模块级可变状态也彻底物理隔离、绝不串台。`DevPluginCompiler` 将 `client.tsx` 打包为浏览器标准 ESM，并将 `react`、`react/jsx-runtime`、`zod`、`@lody/ui` 与 `@lody/plugin-sdk/*` 外置映射到宿主冻结模块表。远程 Web/Desktop 连接对发布态插件按 `(workspace_id, plugin_id, clientDigest)` 逐版本确认信任；对 `devMode: true` 插件提供显式 **“Trust Dev Session”** 开关，在标签页内存 / `sessionStorage` 中绑定 `(workspace_id, machine_id, plugin_id, devSessionNonce)`（顶部常驻 **“Dev Session Active · Revoke”** 撤销徽章，且在 `devSessionNonce` 轮换或清单权限扩容时立即失效重询）。
- **保态流式 `messages.renderBlock` 与通用 `tools.matchRender`：** [`markdown-renderer.tsx`](../../../../packages/components/src/components/ai-gui/markdown-renderer.tsx) 为回合内每个围栏代码块分配确定性 `blockId = "${turnId}:block:${ordinal}"`，并以 `${sessionId}:${blockId}:${winner.pluginId}:${winner.id}` 为 key 渲染 `PluginMessageBlockSurface`。流式分片追加与 `streaming: true -> false` 围栏闭合均**原位更新** `code` 与 `streaming` 属性而不卸载组件实例，完整保留表单、图表缩放与选中状态，同时遵循 [`ai-gui/AGENTS.md`](../../../../packages/components/src/components/ai-gui/AGENTS.md) 不注入 `searchBlockId`。`PluginMessageBlockSurface` 与包裹 [`tool-call-detail.tsx`](../../../../packages/components/src/components/ai-gui/tool-call-detail.tsx) 的 `PluginToolCallSurface` 均在宿主头部渲染不可伪造的 `"View Raw Markdown"` / `"View Raw Output"` 逃生开关与 `SurfaceErrorBoundary` 兜底。

### 3.3 五道 E2EE 运行时安全门禁接线

1. **非访客执行门禁：** 在 [`packages/shared/src/e2ee-rpc.ts`](../../../../packages/shared/src/e2ee-rpc.ts) 中将 `method.startsWith('plugin/')` 纳入 `isE2eeFeatureMethod`，同时保持 `E2EE_READ_QUERY_METHODS` 不变，使 `plugin/query`、`plugin/mutate` 与 `plugin/attachment-*` 强制走非 Guest `authorizeExecution`（`< 15 min` 账本新鲜度）。
2. **机器所有者与 `MachineSharing` 作用域门禁：** 守护进程 RPC 分发接入 [`@lody/e2ee-machine-sharing`](../../../../packages/e2ee-machine-sharing/AGENTS.md)：`machine` 级处理器、插件生命周期/配置写入、`devSessionNonce` 与 `acpProviders` 限定本机所有者；协作者仅在 `MachineSharing` 同时授权该机器及全部绑定项目时可调用 `project` / `session` 处理器。
3. **`SignedTurnOrigin` 与 `e2eeIntent` 派生签名：** 客户端触发执行的 `lodyCommands`（`sessionCreate`、`sessionSend`、`sessionRespondInteraction`、`sessionFork`、`scheduleRunNow` 及其 `sessions.*` 别名）经 [`e2ee-execution-intent.ts`](../../../../packages/shared/src/e2ee-execution-intent.ts) 签发 `E2EE_INTENT_KIND.memberInput`（`1`）。守护进程必须在写入时确认驱动回合在运行时仍活跃，并在本地 `sessionData` 核验 `originTurn: { session, userTurnId }` 对应该回合的人类签名 `memberInput`。共享成员派生 `derivedFrom` `machineInput`（`kind = 2`）须有有效的成员/项目 `MachineSharing`，限同一机器，最多派生 20 次。已签名输入无启动期限，重启后仍可在通过当前授权检查后启动。历史记录只能证明来源，不能授权签发新输入。回合结束后，新工作必须由另行核验的机器所有者工作流激活声明授权，且仅限声明覆盖的机器和操作；执行主体是该工作流，不得提升成员权限。 无根查询与变更处理器返回 `forbidden`。
4. **Iroh 传输帧预算：** `plugin/query` 与 `plugin/mutate` 限制序列化载荷 `<= 256 KiB`（单帧 `1 MiB` `purpose 8`）；`plugin/bundle-chunk` 以 `256 KiB` `purpose 9` 分页流式传输 `<= 4 MiB` 客户端产物，并在写入托管缓存或执行 `import()` 前校验完整 `clientDigest` SHA-256。
5. **托管目录绑定与静态明文分享兜底：** 守护进程 `ctx.dataDir`、永久 `SessionCreationReceiptStore` 与客户端远程产物缓存统一挂载在 `<account>/<workspace>/<genesis>/<signing-key>/plugins/` 下并随成员移除或设备吊销原子擦除；静态明文分享页面禁用 `ClientPluginHost` 脚本执行，仅渲染内置原始输出兜底卡片。

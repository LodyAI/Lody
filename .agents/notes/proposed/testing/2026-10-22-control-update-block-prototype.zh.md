# 控制更新有界打包的隔离原型

Status: proposed
Type: testing
Translation: current
Owner: Codex

[English](2026-10-22-control-update-block-prototype.md)

## 摘要

共享正文优化后的短 Roost 用例仍有 80 KiB 控制库增长，来自逐次发布的 Loro 游标
更新。隔离原型在通用 SQLite 适配器中无损打包这些更新，保留立即持久化与通知行为。
短用例总增量实测 242→192 KiB，但千条流式历史的追加 CPU 增约 20%、p95 增约
38%，RSS 没有一致改善。本地试验已完成，格式仍为提案；这版不满足速度不退化的
采纳条件，建议不合入。产品源码、现有 PR 和部署未改变。

## 责任与格式边界

后续范围已固定：Loro 实现保持原样，作为固定参照。进一步优化仅限 Roost 本体
或 Roost 专属接入；通用适配器原型停止推进。下文的打包 Loro 行只保留为已完成
实验的诊断证据，不是可采纳候选，也不能代替固定的 Loro 基线。

用户授权的是一次隔离实现及对比。复制已安装的 `loro-repo@0.23.3`，不编辑原安装包。
改动仅在副本的文档更新存储；Roost 共享正文 Native、Lody 运行时代码与既有测试
harness 不变。通用适配器也服务纯 Loro，因此两个后端均测试原布局和打包布局。

每块保留精确更新字节、全局递增 ID 与时间戳，最多 7,936 原始字节 / 64 条；超大
更新单独不压缩。使用 Node 自带同步 Zstd level 1，压缩更小时才保留，并限制解码
大小。序号与追加同一 IMMEDIATE 事务，或复用外层事务；批次失败全部回滚。清理
只删已覆盖块并改写边界块。不跨事务缓存，不延迟落盘，不减少游标发布。小追加
不会读取前一个超大单条正文。

新表加持久序号计数器，空库固定增加 4 KiB。新旧 schema 双向拒绝；没有旧格式
兼容读取器或产品迁移。已准备历史仅在关闭的合成副本中离线转换，保留所有更新
字节、ID、时间戳和计数器；原种子不变。原型仅实现 ESM，CommonJS 明确拒绝。
这不是可直接发布的通用依赖修改。

追加需要读取并解码尾块、重新编码/压缩，以及持久序号 SQL。它们是额外工作的
明确来源；本次未用 profiler 将 CPU 回归逐项归因，不能只归咎于 Zstd。原型没有
在发现回归后悄悄放松持久化、增加缓存或删掉通知以换取速度。

`56b737124db34a1dba137856582f5c1809a696bc30ebb22ee49bedea85adb0e2`.

使用全部既有 PR 集成栈和 #27 共享正文运行时，不是只测 npm 0.2.0。流程归属：
[Roost 验证指南](../../../docs/roost-validation.md)；前序验收：
[共享正文联合报告](2026-10-22-roost-pr-stack-integration.zh.md)。

首批 24 个短阶段的原布局来自原安装路径，原型来自副本；打开存储前 RSS 已差约
60 MiB，模块图是混杂因素。该批保留但不用于性能结论。下表使用同一个绝对包路径
切换原字节/原型字节，启动 RSS 因而对齐。RSS 是 Vitest、JS、WASM、Native 整体，

相对空库增量，不含 WAL/SHM 与不变的身份库。CPU 为进程 user+system，追加 CPU
只包通知+持久化；整写阶段另列。所有箭头均为原布局→打包，中位数来自两轮。

## 追加与历史选择：固定参照复核

本次复核仅重读既有原布局样本，没有新跑 benchmark 或改运行时。被测构建已含
语义增量变更、Native 正文/检查点原子组、标量调度索引及 #27 共享正文，并不是
优化前的旧版。

图中的历史追加 CPU，是**从空库增长到 1,000 条消息的 10,000 个通知批次**之和：
Roost 10.874 s，对未修改 Loro 为 10.808 s。计时包住 `applyAgentBatch` 与
`persistDocNow`，不含调度选择或长会话恢复；包括接入/Native 工作和立即控制库
持久化。进程 CPU 计数器不能分出 Roost 独占成本。已停止原型的 13.085/7.865 s
不能替换这组固定参照。

2.628/82.694 ms。最新窗口→选择后 RSS 为 447.5→447.9 MiB 与

已有分段计时进一步限定了耗时调查范围：`applyAgentBatch` 确认 p50 为 Roost
2.519 ms、Loro 0.226 ms，随后显式 `persistDocNow` 的 p50 为
0.007/0.081 ms。这些是分别统计的轮内分位数，不能相加当阶段百分比。Roost
追加的大部分观测时延发生在后端确认之前；这不排除控制库工作已在其中或异步发生，
也不是 CPU 热点 profile。

之前去掉全历史调度读取的优化仍然有效。带目标 ID 的普通写入也保留语义追加提示，
并通过一个条件 Native 提交组处理正文/收据/派生索引。源码确认追加路径仍有游标
检查、收据查找、发布和控制库落盘，但**此前只读复核没有剖析其各自 CPU 占比**；存在这些
调用或旧 profile 都不能证明它们就是当前最大热点。这些边界上的追加 CPU/时延
仍更慢或接近，因此不能用选择收益推导整体长会话领先。下一步若优化追加，先取得
当前分段归因，再选改动，Loro 始终固定。
后续已完成[流式追加结构调查](../architecture/2026-10-23-roost-append-cpu-structure.zh.md)，
提供当前请求轨迹、线程 CPU 与按追加区间过滤的 profile；它不授权实施所提重构。

## 正确性证据、预算失败与限制

真实适配器边界 9/9 通过：精确字节/ID/时间戳与超大记录重开、前缀清理、真实
Loro 快照压缩及后续更新、批次失败回滚（含序号/兄弟文档）、损坏块拒绝、表前缀/
多文档/原写者隔离、两个独立进程共 80 次写入、明确 IPC 信号后提交/未提交
SIGKILL 恢复，以及新旧 schema 双向拒绝。未使用睡眠决定崩溃时间。

四负载 96 个阶段全部完成；已准备历史 44 个成功、1 个 RSS 预算失败、3 个未执行。
总计 140 个成功阶段、212 次 SQLite quick/foreign-key 检查；完整内容摘要、跨后端
业务摘要、重开、重试、分页和成功的 dispatch/verify 配对一致。不能把此次总结写成
“全部测试通过”。初次续跑前还曾被 4 GiB 磁盘预检阻止，未启动测试进程。
已完成的合成库逐文件 SHA-256 校验归档，读回比对后才移除原副本；种子、失败库、
原始 JSON/日志与归档 manifest 保留。

本轮没有重跑整个 Lody/Rust CI；9 个边界测试及实际端到端矩阵用于隔离取舍，
不能移用前序 #27 CI 宣称这个新存储可发布。未验证 CJS、六平台打包、网络同步、
浏览器通知、ACP 全链路恢复与累计磁盘写入。原型保持 proposed，当前实现不满足
“正确性和速度均不退化”的采纳要求。建议保留试验证据，不将此版合入现有 PR。

# 加密工作区页面的账本核验码

Status: proposed
Translation: current

[English](2026-10-20-e2ee-ledger-verification-code.md)

PRs: [LodyAI/Lody#1625](https://github.com/LodyAI/Lody/pull/1625)

## 摘要

加密工作区的成员原本无法确认 Lody 服务器给每个人看到的是同一本权限账本；服务器若替换公钥或分叉账本，没有人能发现。控制页现在提供类似安全码的核验码和二维码，成员可通过复制、朗读或扫码在带外比对。核验码是核心库的比对摘要，绑定协议、创世、版本、head 和实际权限状态，因为白皮书明确不允许只比较 head 哈希。一致只证明双方在该版本持有同一本账本；成员的真实身份仍需双方自行确认，比对结果也尚未持久保存。

## 决定

- **核验码是什么。** 核心库的 `ledgerStateDigest(view)` 返回 `comparisonNote` 已在计算的摘要，即 `sha256("snapshot-digest/v2" ‖ CBOR[2, 创世, 长度, head, 授权状态])`，但不要求账本中的设备作为签名者。控制页不持有设备密钥，无法调用 `comparisonNote`。[白皮书](../../../../specs/e2ee/whitepaper.zh.md)要求安全码绑定实际状态：仅有 head 时，状态可能是错的，例如通过快照初始化的客户端。
- **版本**即已验证记录数。二维码内容为 `lody-ledger:1:<版本>:<head>:<摘要>`；复制的文本是一行带版本的标题，加上分成 16 组、每组 4 位的摘要。
- **比对规则**（`e2ee-ledger-verification.ts`）：
  - 版本和摘要相同（有 head 时 head 也相同）：一致；
  - 版本相同但摘要或 head 不同：不一致；
  - 对方版本较早，且 head 等于本账本该位置的记录：同一历史，对方落后；
  - 对方版本较早，但 head 不同：不一致；
  - 对方版本较新：先刷新；
  - 粘贴的摘要没有版本且不同：暂无法判断。
  
  按白皮书要求，位置不同绝不直接判定为攻击。
- **扫码**使用 `getUserMedia` 加 `jsqr`（Apache-2.0）。只在用户按下摄像头按钮后启动，识别到第一帧即释放摄像头；粘贴始终可用。macOS 构建增加摄像头 entitlement 和 `NSCameraUsageDescription`。
- **姓名和头像**是展示数据，不是账本事实。账本里的用户 ID 是随机值，目前也没有成员资料接口。页面接受 `you` 和 `memberProfiles` 两个参数；路由只提供 `you`，且仅在本机持有创建时的 pin 时对应到创世成员，其他成员显示“成员 N”。提示文案请用户当面确认对方是哪位成员。

## 备选方案

- **只比 head 哈希**：更简单，对完整重放的客户端也够用；但白皮书禁止，并且快照初始化上线后会悄悄变弱。
- **数字安全码（WhatsApp 风格）**：更便于朗读。暂缓，因为十六进制分组与现有比对摘要一致、便于复制；改变显示方式不影响摘要本身。
- **`BarcodeDetector`**：Windows 和 Linux 上的 Chromium 不支持，仍然需要纯 JS 解码器。

## 验证与限制

- 核心库测试：不需签名者的摘要与比对记录的摘要相同，对完整历史视图和快照验证视图都成立；伪造视图会被拒绝。
- 单元测试覆盖解析（包括带版本的复制标题）和每一种比对结果。
- 页面测试确认显示的核验码等于该摘要，且账号资料只在有 pin 时才对应到创世成员。
- 在无头 Chromium 中，用生成的二维码作为假摄像头画面，分别得到一致、旧副本和分叉（head 正确但状态不同）的判断；复制后粘贴也判为一致。
- 尚未验证：
  - 带新 entitlement 的真实 macOS 签名；
  - iOS/Android 外壳，它们需要在私有应用里配置各自的摄像头权限说明。
- 比对结果不保存。白皮书中“已在此位置独立核对”的状态，以及 `confirmIndependentComparison`，均未接入。
- 其他成员的姓名需要后端按成员关系提供资料目录；这些数据仍只用于展示。

# 团队成员加入的桌面原生流程

Status: proposed
Translation: current

[English](2026-10-28-e2ee-team-joining-native.md)

## 摘要

个人设备配对不足以让另一个账号加入加密工作区。本改动在桌面主进程中增加独立的成员签名申请，绑定账号加密身份和独立传递的 genesis 固定值。当前个人 Owner/Admin 设备签入 Member 后，沿用信箱机制发送保留的密钥历史。待处理申请、已签名尝试和已验证历史可跨重启恢复；对端不可用时只影响正在加入的成员，已有工作区继续可用。

## 边界与决定

- 可选公开接口只传邀请固定值、签名申请与进度。凭据和私钥留在按账号隔离的原生主进程。普通工作区和本地构建不会启动此流程。
- 邮箱邀请与加入链接保留不同来源。仅已接受的定向邮箱邀请允许自动批准；链接申请必须显式批准。云端负责账号归属和席位预约，真实权限仍由签名账本授予。
- 加入设备在提交前保存完整原始 KeyPackage。批准设备在网络请求前保存每次原始签名记录。结果不明时重用原件；只有验证到占用原父节点的竞争记录，才允许针对新父节点重新签名，并保留旧尝试。
- 换用新邀请前，先向已认证服务对账旧申请。只有已取消、已过期且未预约、或已拒绝的申请才能退役本地待处理意图；正在签入或已提交的申请继续恢复。安装和清理不会删除已安装的来源。
- 新设备从独立保存的 genesis 开始，完整验证有大小上限的权限历史页。服务端角色或未验证快照不能建立本地身份。当前和保留 epoch 的密钥沿用现有信箱发放。
- 已加入的 Member 可以批准同账号的其他个人设备；不能借此加入另一个账号、机器或恢复身份。服务端另外核验发布者属于同一当前成员。
- 成员角色调整复用配套 #1982 的 `setMemberRole` 和管理日志。加入运行时不再保留单独的升权命令、端口或日志。
- 每次异步成员操作捕获已认证账号和实际原生 owner 实例。后台借用的 reader 携带临时归属标记；迟到的清理不能释放后来替换的 namespace，同账号重置也一样。

## 证据与限制

所属运行时测试使用真实密码学、SQLite 和合成的已认证 safeStorage，覆盖不同账号、原始申请恢复、篡改凭据绑定拒绝、真实历史验证、双向加密数据、额外个人设备及离线重开。真实 IPC 边界测试覆盖账号、namespace 替换和 reader 归属；preload 测试覆盖 renderer 的显式允许列表。后端邀请政策和产品 UI 分开审查，不编译进本公开主进程 PR。

尚未验证已安装桌面、真实系统钥匙串、生产服务、邮件、Stripe 或跨平台验收。完整历史启动限制为 256 页、32 MiB；超过上限需另行审查启动方案。本 PR 不改变已保存的签名账本格式，也不实现移除成员或换代 UI。

## 移除和重新加入的组合

本分支合并当前 main，包含[成员管理与本地清理 #1982](https://github.com/LodyAI/Lody/pull/1982)。Owner 升 Admin 沿用它唯一的 `setMemberRole` 端口、原生签名实现和管理日志。加入流程不另造角色命令、账本状态字段或快照版本；能力状态和快照、保留状态、摘要 v4 仍由 #1979 负责。

已认证移除继续比较原账号、工作区、genesis、签名公钥和 credential，停止并排空原生 owner 后删除该实例。清理现已覆盖 `member_joins` 和 `personal_join_histories`，避免已安装来源阻塞或污染新邀请。凭据认证的邀请接口沿用统一移除错误分类和终态清理。旧凭据的迟到响应不能通过当前身份比较，因此不会删除新实例。

`acceptMemberJoin`、`acceptPersonalHistory` 和 `acceptPersonalJoin` 共用移除标记完成规则：先验证签名接纳或历史及其与本地设备的绑定，再仅为同 genesis、不同签名公钥清除标记。准备申请和安装失败都保留标记。旧实例清理后，新邀请生成新设备和凭据；同一未决申请的重试继续使用原件。

渲染器沿用 #1982 唯一的本地数据定位：账号、工作区、genesis、签名公钥，正文命名空间再区分窗口。加入成功后进入现有加密运行时接纳流程，在打开正文前保存新定位，不能选择旧的仅按工作区命名的缓存或复活被移除实例。

三条真实密码学和 SQLite 回归覆盖三个安装入口的移除后新邀请、不同成员实例与 key/credential、安装失败保留标记、Owner 升 Admin、旧凭据迟到保护、发钥与离线重开。真实 IPC 测试覆盖邀请管理接口触发的终态清理；渲染器回归验证新公钥选择并保留新的本地实例。这些是自动组合验证，不表示已安装设备或真实服务验收完成。

## 协议归属

公开邀请 DTO 只有 `packages/cloud-api/src/e2ee-members.ts` 一处声明，平台和 UI 复用。`E2eeWorkspaceRuntime` 保留已合入的签名公钥、成员实例、角色和 `setMemberRole`，并加入本 PR 的临时 reader 所有权标识。原生配套可先合入，产品邀请与设置界面由 #1986 提供。两个独立分支不互相叠栈，也不保留临时 core overlay。

## 准入后的派钥

过去审批要等完整的 `refresh()` 结束才返回，其中包含最多四遍的 key round。在打包版的 B④ 运行里，中继已经提交了准入，审批桌面却又多等了 30 秒。这段时间管理员的审批卡一直是禁用状态，没有任何进度提示，邮件 worker 的调用也一直挂着。现在 `approveMemberJoin` 只做一次 ledger 摄入（`installKeys: false`），读取中继结果后就返回 `admitted`，同时带上 `keyDelivery: 'pending'`。派钥结果无法撤销准入。加入方设备本来就要等自己装好当前密钥后才显示"就绪"，所以不会出现显示已加入、却打不开工作区的情况。

派钥归主进程的 `E2eeIpc` 服务所有，不再依附于某个渲染端请求。每个账户和工作区同时只跑一轮，这一轮由主进程自己持有的 host reader 承载，所以即使关掉所有窗口也不会中断。host 原有的 key round 单飞和锁规则保持不变，派发对象也仍然只限于 ledger 中已验证的成员。每一轮都先在这个 reader 下 ingest 中继历史。只有这一轮成功、并且本地 verified ledger 把被准入的设备列为派发目标时，请求才会标为 `delivered`；判定规则与 `KeyDistributor` 相同，即有效成员名下已准入的设备。设备公钥取自已验证的 KeyPackage，不用中继给的标签。不满足时，请求保持可重试，原因码为 `e2ee_admission_not_ingested`。失败时只记录公开的 `e2ee_*` 原因码，不记录密钥字节、token 或错误原因，同时保留 `pairingFailure`。之后按退避等待：从 10 秒开始，每失败一次翻倍，上限 5 分钟。到期后由下一次 `memberJoinRequests` 或 `memberKeyDeliveries` 调用触发重试；邮件 worker 和团队设置页每 10 秒都会轮询这两个接口。不另设定时器或循环。显式重试会跳过退避。成员被移除、设备被吊销、绑定缺失、工作区已关闭都属于终态：直接清掉 slot，不再重试。这些原因即使嵌套在 `WorkspaceKeyRoundFailure` 的阶段 Result 里也能识别，识别发生在公开投影把它们压平成通用失败之前。团队设置页在派钥成功前显示"已加入 · 正在发送密钥"，失败时提供重试按钮。加入页补充说明：需要管理员的桌面端在线。

影响范围：触发条件是 key round 期间中继、mailbox 或 staging 请求变慢或失败。影响只落在这一轮所覆盖成员的派钥状态上，审批、请求列表和其他工作区都照常工作。恢复由服务实例负责，生命周期与应用一致；每个账户和工作区最多保留 32 条记录。退出、登出或切换账户时会关闭 owner，正在进行的一轮会以 `closed` 或 `account_mismatch` 失败，这条记录也不会显示给另一个账户。状态只保存在内存里。重启后，未完成的派发要等本设备下一次完整的 key round 时，由 core journal 重新发现，而不是靠这里的记录。这个缺口在本次改动之前就存在。

# 从输入框预约发送消息

Status: proposed
Translation: current

[English](2026-10-27-scheduled-messages.md)

## 摘要

已有对话在统一的 `+` 菜单中提供“定时发送”。用户选择未来时间，继续在当前输入框编辑，然后确认预约。
复用机器拥有的 Schedule 系统，持久保存完整消息块和本次运行配置，按时间发送一次。新建对话页面不提供此功能。

## 决策

- 输入框拥有发送前的草稿状态：发送按钮旁显示一个次级动作“发送定时消息 · 时间”，点击后编辑时间或取消定时；取消定时保留消息。信息栏不再显示任何定时消息条目。编辑器沿用日期时间输入，预选 30 分钟、1 小时和 5 小时。2026-10-27 UI 评审后修订，原“信息栏图标”决策作废。
- 按目标机器时区解释快捷选项和手动输入，旧机器缺少时区时使用设备时区。机器离线或睡眠后补发一次，
  保留现有重试期限和次数。目标对话忙碌时等待，不中断当前任务。
- 按账号、工作区、对话保存草稿时间和预约身份。正文、附件草稿仍沿用现有内存生命周期。
  移除时间不会清空草稿；只保存草稿时间不代表已经接受预约。
- Schedule 文档新增 `message.payload`，严格解析的 definition 新增 `messageVersion: 1`。
  冻结普通输入块、MCP 选择、Role 信息和前缀，以及 Agent、模型、权限和配置。Registry 只保存消息标记，
  不保存内容。旧文字任务指纹不变，继续支持 schedules v2；完整消息需要 v3。严格版本标记防止旧端
  把完整消息编辑或执行成仅有文字的版本。
- 复用[现有 Schedule 所有者](../../implemented/feature/2026-09-24-machine-owned-scheduled-tasks.md)、
  执行指纹和 SQLite 账本。附件通过现有工作区 `sendResources` 准备，完成后再次检查时间，才发布预约。
  保存失败保留已成功传输的凭据。已经发布的预约会保留本地附件，即使还没有对话历史；读取预约不完整时不能据此回收附件。
- 切换页面取消附件准备。已经开始的持久写入仍可能完成，因此重试保留预约和操作身份。
  仅在接受后清理同一代草稿。到点后由现有 prepared-input 流程交接完整输入块和配置，重试、重启沿用相同消息身份。
- 队列的独立“定时消息”分区可在行内修改发送时间，并从行上打开 Schedule 详情或取消；预约不进入可执行 `mq`。
  完整消息详情固定一次发送到当前对话，编辑完整内容；不提供通用立即运行和恢复操作。继续检查所有权、机器协议和工作区能力。
  取消会禁用预约；目标机器确认前显示等待。若发送已经提交则显示已发送，否则在跳过交接前工作后确认取消。
  已发送仅指消息已交给对话，Agent 的执行结果另行展示。

## 当前流程审计（2026-10-27）

在这次跟进之前，已发布路径仍是入队前的界面：发送后由 `ScheduledMessagesSummary` 在信息栏下方
显示一行弱化文本，点击进入通用 Schedule 详情页。队列展示已经接受定时行，但生产只传入 `mq`；
Storybook 预览通过伪造 `MessageQueueItem` 表达预约，因此不构成可发布的数据路径。送达后的用户
消息也丢失了来源：合成“Scheduled task…” 系统条目被对话渲染器过滤，用户轮次看起来与手动输入相同。

跟进后，发送前的状态由输入框的次级动作承载，信息栏不再出现任何定时消息条目；发送后的预约作为
只读行进入队列的独立“定时消息”分区，由单独的视图模型提供。次级动作的语义已经确定：它是状态
编辑器，主 Send 负责按定时提交。仍待定的是时间编辑器的形态、送达轮次的弱化来源标记，以及行内
编辑/取消；后者仍依赖下文的回执协议。

## 终态回收

执行端每次就绪评估都会运行回收扫描。完整的一次性消息进入终态
（`sent`、`cancelled` 或 `failed`）后，如果 runtime row 的 `updatedAt`
已超过 `SCHEDULED_MESSAGE_RETENTION_MS`（七天），执行端会清除
`schedule-<id>` 文档，删除 Registry 的 schedule／runtime／manual 行，并留下
tombstone。计时从终态投影开始，而不是创建时间。文档仍被占用（详情页打开中或
同步未完成）时跳过，留到下一次评估重试。

Pending／活动中的预约以及普通周期任务不在回收范围内。这是执行端本地清理：
tombstone 会拒绝离线旧写入，但不声称已经压缩 Loro 历史或远端副本。

## 同步健壮性审计（2026-10-27）

当前承诺是复制收敛加执行端 15 秒唤醒循环，不是确认回执。到点时 daemon 已停止的，重启后按当时
重新 plan；`run_once` 会补发，`plannedAt` 也是当时，因此不存在“从计划时间起 24 小时”的过期。
daemon 在运行但没有完成同步的，会停在同步门槛，恢复后再 plan。已经 plan 但持续无法派发的 run，
会从 `plannedAt` 起按 24 小时或 5 次尝试过期；对话一直忙碌则每 30 秒重试，同样受 24 小时窗口限制。

两个结构性缺口：Registry row 是唯一发现和执行门槛，执行端没有从 Schedule 文档做修复扫描；
客户端本地 flush 后没有 owner 回执或重试。因此 Registry row 丢失时预约既不可见也不可执行；
只到本地、没有到达 owner 的预约可能永远停在 Pending。失败模式矩阵在评审画布中；本次审计没有
改变生产行为。

## 队列展示与同步提案

复用队列展示和正文编辑器，但定时预约不进入 Session 的 `mq`。真实组件 Storybook 仍只是界面提案。
普通队列读取端直接选择队首，不检查截止时间；新增一个旧端不认识的时间字段，会导致旧 CLI 立即发送。
展示层用 `queued` / `scheduled` 两类数据合并列表，不把预约复制进可执行队列。
定时行的编辑、删除分别调用 Schedule 修改、取消操作；普通拖动排序和 steer 不适用于定时行。

完整内容与配置继续放在 Schedule Loro 文档，发现与执行发布使用工作区 Schedule Registry Flock，
执行恢复使用所属机器的 SQLite 账本。沿用 Repo 传输和工作区能力限制，不新增云服务或页面计时器。
Registry 有记录但完整内容尚未到齐、指纹不匹配时不能执行。附件准备完成后才发布，并保留到交接结束。
持久时间使用绝对时刻，选择器按执行机器时区解释。

当前 Repository 先 flush 文档，再发布指纹；这只证明本地持久化，不证明执行端已经收到或接受。
引擎已有指纹检查、当前连接同步门槛和稳定的 prepared-input 身份，可以复用；但没有带确认的串行修改、取消协议。
当前 `save` 没有预期版本检查，CRDT 收敛本身不能决定哪次操作获得执行资格。

建议为定时消息增加持久、幂等的创建／修改／取消请求，携带请求 ID、预约 ID，修改／取消还需携带预期的已接受版本。
请求沿用工作区复制层同步，只有执行机器可以接受。该机器按顺序处理请求接受和到点交接，持久记录接受版本与结果，
再把回执同步到其他设备。重复请求返回同一结果。两个设备基于同一版本编辑时，一次成功，另一次提示冲突并保留草稿。
请求的内容快照不可变，只有完整内容到齐且指纹匹配才接受。这是 Schedule 所有权的扩展，不是第二套调度器，
需要显式能力／版本门槛，旧写入端不能绕过这类预约的接受版本路径。

取消对同一预约 ID 是终态，旧编辑不能使其复活。执行端先核对持久派发证据：先接受取消则阻止交接，
先提交派发则返回已发送。离线客户端可以保存取消请求，但不能保证已生效；此前已接受的版本仍可能发送。
同样，未确认的改时间请求不会替换旧截止时间。执行机器离线会推迟确认和发送；云同步工作区继续要求当前连接同步就绪。

状态分成同步与发送两层：

| 层次       | 建议值／含义                                                               |
| ---------- | -------------------------------------------------------------------------- |
| 本地请求   | 准备中、本机已保存、等待执行机器确认、被拒绝／版本冲突                     |
| 执行端回执 | 请求 ID、已接受版本／指纹、结果、回执序号                                  |
| 发送       | 等待指定时间、等待条件（忙碌／离线／同步）、正在交接、已发送、已取消、失败 |

发送状态由执行机器更新。离线是可用性提示，不是持久终态。客户端时钟经过截止时间只能说明时间已到，不能推断正在发送或已发送。
旧回执不能确认新编辑：按预约、请求／版本、机器和单调回执序号匹配。修改或取消尚未确认时，仍显示上次已接受的时间。
已发送指消息持久交给 Session，Provider 的完成／失败另行表达。
交接后按稳定 user-turn 身份对齐定时行和历史消息，使其从待发送列表移除并成为普通对话消息。

到点后沿用现有 prepared-input 交接，忙碌时等待；不为了复用 UI 而插入 `mq`。
与普通队列的竞争仍需明确、公平的规则；建议优先已有普通排队消息，到期预约按截止时间、ID 排序。
未来预约不阻塞普通消息，不提供跨类型拖动排序或隐式立即发送。

实现验收需要覆盖：两端编辑同一版本、离线取消撞上派发、迟到／过时回执、内容未同步完整、派发提交前后崩溃、
执行端重启、旧客户端能力拒绝、附件保留及忙碌对话的调度顺序。
本次是依据源码的设计研究，没有增加运行时代码或新的端到端验证。
现有 `messageState`、`queueState`、`observedDefinitionFingerprint` 可作为投影基础，但不等于上述完整回执协议。

## 队列展示（2026-10-28）

队列是一张列表，共用 16px 行首槽：折叠箭头、队列序号和“定时消息”分区标题对齐，所有行的正文从同一列开始。
行改为带悬停底色的内嵌块，去掉行间与标题下的分割线。队列正文使用 subheadline（默认界面字号下 13/18）。
桌面端的编辑／移除及定时行的详情／取消在悬停或聚焦时出现，触屏及无悬停指针始终可见；Steer 以浅色胶囊常驻。
定时行末尾是发送时间胶囊，点击打开时间编辑器；发送失败时胶囊改为警示色并带提示图标，无障碍标签为“未发送”，
不另设状态列。相对时间首字母大写（如“Tomorrow 9:00 AM”）。

触屏行使用三列网格（行首槽、内容、44px“更多”）。普通行保留序号并单行截断。定时行将标题与发送时间上下排列，
整体是一个打开时间编辑器的按钮；“更多”菜单提供修改发送时间、编辑（详情）和取消。两类“更多”按钮都是真实的
44px 盒子，此前基于 Button 的触发器实际只有 32px。本次只改展示；数据路径、排序与回调不变。

展示顺序已明确：普通行保留手动顺序，本地附件准备行跟在其后，定时行始终位于最后，按发送时刻升序排列；相同时间保留原有顺序。修改时间会重新排序。定时行不进入可拖动 ID 列表，也不能作为拖动来源／目标，不提供置顶或 steer。展示组件通过明确的发送时间读取函数分类，不从文案推断，也不将预约写入持久 mq。组件测试覆盖排序、时间修改及定时行无拖动入口。此队列提案的后台预约同步仍独立且尚未接入。

## 生命周期与 Effect 评估

触发来自用户确认预约和现有机器时钟。附件准备由工作区 send-resource scope 持有，接受后由 Schedule 文档与账本持有。
页面切换取消准备，显式取消阻止后续交接，已提交的发送继续归普通 Session 所有。
恢复依赖稳定预约身份、已准备附件凭据、冻结账本载荷和持久发送证据。运行状态从账本恢复。

没有新建调度器、历史写者或 Effect runtime。Schedule 的 Repo/Session 编排仍是未完成的 Promise 依赖链，
本次不扩大原生迁移范围；附件复用现有原生 scope。

## 验证与限制

测试使用合成数据、注入时钟和临时 SQLite，覆盖真实输入框接受、失败、取消定时模式、引用、机器时区快捷选项、
跨副本持久化与幂等、完整载荷指纹、仅附件消息、补发、重启恢复以及取消与已提交发送竞争。
原有普通发送、任务表单/列表和持久 Session 交接测试保持回归边界。Storybook 渲染真实组件，检查桌面、窄屏和深色模式。
不声称已验证生产云端预约、真实 Provider 执行或打包 Electron。

## 发送身份与并发创建

完整消息一旦可靠提交发送，其 Schedule ID 就已被消费，后续 activation 不能再次发送。
执行机器在计划和处理待执行任务前检查 SQLite 的发送历史；旧客户端编辑后，
按账本投影为已发送，不创建第二次发送。发布运行状态只能在同一 activation 内
继承旧回执；完整消息跨 activation 的已发送状态来自账本，而非旧 Flock 行。
这并未实现执行端确认编辑：本地保存的修改仍可能被执行端的已发送回执覆盖。
更换执行机器和破坏性丢失账本不在该保证内。

完整消息以原子 input blocks 作为正文来源，旧 LoroText prompt 仅保留为兼容投影，
并发创建不会拼接实际执行正文。一次性触发时间同时作为 activation 的起点，
不受各写入设备时钟影响；展示用的创建、更新时间仍保留。完整消息读取时按活动 ID
去重，普通纯 prompt Schedule 的语义保持不变。

真实双副本测试覆盖不同创建时间、发布指纹匹配和保存结果不确定后的重试。
SQLite 引擎测试覆盖已发送之后旧客户端修改 activation，以及引擎重启。
info bar 测试显式固定设备时区，并分别在 UTC、Asia/Shanghai 下验证。
此次不改变生命周期或传输所有权；修复集中在现有账本和纯读取归一化，
暂不扩展为原生 Effect 迁移。

## 发送范围隔离

完整消息不占用或恢复按 Agent 配置划分的执行 slot。这层 slot 继续约束通用定时任务；
完整消息只等待自己的目标会话，以及同一 Schedule 的先前任务。因此其他会话中的
长任务或定时消息不会再将它阻塞至发送期限过期。所有权、指纹、activation、
消息账本去重和 SESSION_BUSY 检查保持不变。账本仍跟踪目标 turn 完成，但不持有
Agent slot。消息的 release 调用保持按 owner key 的安全空操作，不会释放其他任务的 slot。

新增四个行为回归在修复前失败、修复后通过：消息到消息、通用任务到消息、
消息到通用任务（包含 worker 重启），以及其他通用 slot 被占用时目标会话从忙碌
恢复为空闲。原有通用任务等待测试保持通过。目标会话自身长期忙碌时的过期预算
保持不变；本次只移除跨会话阻塞，不改变重试策略，也不引入新的并发管理者。

# Native team membership admission

Status: proposed
Translation: current

[中文](2026-10-28-e2ee-team-joining-native.zh.md)

## Abstract

Personal-device pairing alone cannot admit another account to an encrypted workspace. This change gives the desktop host a separate signed member request, tied to its account crypto identity and independently transferred genesis pin. A current personal Owner/Admin device signs the Member admission; normal mailbox delivery then gives the new device the retained key history. Pending requests, signed attempts and verified history survive restarts; unavailable peers affect the joining member while the existing workspace remains usable.

## Boundaries and decisions

- The optional public port exposes invitation pins, signed requests and progress. Credentials and private keys remain in the account-bound native host. Ordinary/local composition never starts this workflow.
- Email and shared-link requests have distinct sources. Automatic approval is limited to email invitations whose endorser signature, current endorser role, expiry and single token-derived request id the approver verifies itself (`source` is only a label); link requests require an explicit approval invocation. The authenticated cloud relay reserves account ownership and seats, while the real permission ledger grants membership.
- A joining desktop retains one exact KeyPackage before submitting. An approver retains each exact signed append before network I/O. Unknown outcomes reuse those bytes. Only verified competing ledger bytes permit a new parent; every prior attempt remains retained.
- A replacement invitation first reconciles the old request with the authenticated relay. Only a cancelled, expired unreserved, or rejected request can retire the local pending intent; an admitting/committed request remains recoverable. Installation and cleanup never erase an installed origin.
- Admission starts from the independently saved genesis and fully verifies bounded permission-history pages. No server-only role or unverified snapshot establishes a local identity. The existing mailbox supplies current and retained epoch keys.
- An admitted Member can approve another personal device of the same account. This does not admit another account or a machine/recovery identity; the server separately binds the publisher to that same current membership.
- Member role changes use companion #1982's `setMemberRole` and management journal. The joining runtime has no separate promotion command, port or journal.
- Each asynchronous member operation captures the authenticated account and the actual native owner instance. Background readers carry an ephemeral ownership cookie; delayed cleanup cannot release a replacement namespace, including a reset under the same account.

## Evidence and limits

The owning runtime test uses real crypto, SQLite and synthetic authenticated safeStorage. It checks different accounts, immutable request recovery, modified credential binding rejection, genuine history verification, bidirectional encrypted payloads, an additional personal device, and offline reopen. Actual IPC boundary tests cover account/namespace replacement and reader ownership; preload tests cover the explicit renderer allowlist. Backend invitation policy and product UI are separately reviewed changes; they do not compile into this public host PR.

No installed desktop, real OS keychain, production relay, email, Stripe, or cross-platform acceptance is claimed. Full history bootstrap is bounded at 256 pages and 32 MiB; a workspace beyond that budget needs a reviewed bootstrap extension. This PR does not change the saved signed-ledger format or implement member removal/rotation UI.

## Removal and rejoin composition

This branch merges current main, including [member controls and local removal #1982](https://github.com/LodyAI/Lody/pull/1982). Its single `setMemberRole` port, native signing implementation and management journal supply Owner promotion. Joining adds no parallel role command, ledger state field or snapshot version; #1979 owns capability state and snapshot/retained/digest v4.

Authenticated removal still compares the originating account, workspace, genesis, signing key and credential, drains the native owner, then erases that incarnation. Cleanup now includes `member_joins` and `personal_join_histories`; otherwise installed origins would block or contaminate a new invitation. Credential-authenticated invitation calls use the existing shared removal classifier and terminal cleanup. A late old-credential response fails the identity comparison and cannot erase its replacement.

`acceptMemberJoin`, `acceptPersonalHistory` and `acceptPersonalJoin` share the marker completion rule: first verify the signed admission/history and its binding to the retained device, then clear a same-genesis removed marker only for a different signing key. Preparation and failed installation retain the marker. After cleanup, a fresh invitation generates a fresh device and credential; retries of the same unresolved request retain their exact originals. If the erase after a recorded removal receipt failed (a busy lease or an unavailable key store), preparing a new invitation resumes that erase from the receipt before it prepares the new join. A removed workspace is no longer listed, so nothing else reopens it, and without this the new invitation would stay refused until someone opened the lost workspace.

The renderer continues using #1982's single local-data locator: account + workspace + genesis + signing key, with window-specific content namespaces. Successful joining enters the ordinary encrypted runtime admission path, which persists the new locator before opening content. It cannot select the old workspace-only cache or resurrect a removed instance.

Three real crypto/SQLite regressions cover removal followed by a new invitation through each installation entry, distinct membership/key/credential, failed install marker retention, Owner promotion, late old-credential protection, key delivery and offline reopen. The real IPC suite covers terminal cleanup from invitation-management endpoints; the renderer regression verifies that a replacement key selects and retains the replacement local instance. These are automated composition evidence, not installed-device or live-service acceptance.

## Protocol ownership

Public invitation DTOs have one declaration path, `packages/cloud-api/src/e2ee-members.ts`; platform and UI consume those types. The optional `E2eeWorkspaceRuntime` retains the merged signing-key/membership/role fields and `setMemberRole`, plus this PR's ephemeral reader ownership cookie. The native companion can be merged first; product invitation/settings surfaces are supplied by #1986. Neither independent branch stacks the other, and no temporary core overlay remains.

## Key delivery after admission

An approval used to return only after a complete `refresh()`, including a key round of up to four passes. On the packaged B④ run the relay had committed the admission while the approving desktop waited another 30 s. The admin card stayed disabled with no progress shown, and the email worker's call stayed in flight. `approveMemberJoin` now ingests the ledger once (`installKeys: false`), reads the relay result and returns `admitted` with `keyDelivery: 'pending'`. Delivery cannot undo admission. The joining device already gates "ready" on its own installed current key, so it never shows a joined workspace it cannot open.

Delivery belongs to the main-process `E2eeIpc` service, not to a renderer request (see the due timer below for retries without a poll). Each account/workspace has one in-flight round under a main-owned host reader, so closing every window does not stop it. The host keeps its own key-round single-flight and lock rules, and distribution still targets only verified ledger members. Each round first ingests relay history under that reader. A request becomes `delivered` only on positive evidence: the mailbox holds an envelope for the admitted device at the current epoch (`EnvelopeStored` or `InstallationReported`). That is the check `KeyDistributor` itself uses before recording `Observed`. A successful round is not evidence: an ineligible sender, a blocked target, a missing current key or joining another caller's round all end in success. Each such case stays retryable with its own code: `e2ee_admission_not_ingested`, `e2ee_key_sender_ineligible`, `e2ee_key_unavailable`, `e2ee_key_not_sent`, `e2ee_key_epoch_changed`, `e2ee_key_recipient_ineligible` or `e2ee_key_status_unavailable`. The local checks run under the host lock; the mailbox status read runs after it is released. The device key comes from the verified KeyPackage, not a relay label. A failure records a public `e2ee_*` code (never key bytes, tokens or causes) and keeps `pairingFailure`. It then waits out the shared `KEY_DELIVERY_RETRY_DELAYS` backoff (500 ms, 1.5 s, 4 s, 10 s, 40 s, 160 s, then 5 min twice), which `services/e2ee-key-delivery.mts` owns for `E2eeIpc`. The next due `memberJoinRequests` or `memberKeyDeliveries` call retries it; the email worker and team settings poll these every 10 s. There is no separate timer or loop. An explicit retry skips the backoff. Only permanent causes are terminal: member removal, device revocation, a missing binding and `restart-required`. A terminal cause drops the slot, which is never retried. A closed workspace is retryable, because the next round reopens it. Terminal causes are found inside `WorkspaceKeyRoundFailure` phase Results as well, before the public projection would flatten them to a generic failure. Team settings show "Joined · sending key" until delivery succeeds and a retry action on failure. The join page adds that an administrator desktop must be online.

Account-wide pairing (`approveAccountPairing`) uses the same delivery. Its admission carries a signed snapshot invitation but no epoch key, and the approver's account-pairing host only ingested the ledger after `append`. So the new device joined and then reported "current epoch key not installed" indefinitely, because no envelope was ever sent to it (M2, 2026-11-04). The shared workflow now calls the approver port `deliverKeys(device, requestId)` once `append` confirms the admission in the verified ledger. It names only the device from the authenticated request row, under the journaled `account-device-*` admission id, and never for a lost or unconfirmed admission. The desktop host maps that call to `trackKeyDelivery`, and `retryMemberKeyDelivery` accepts that id form. The portable approver (`makePortableAccountPairingApprover`, used by the phone) implements the port with the approving session's own key round, through the purpose-limited `keyRound` and `keyDeliveryEvidence` added to `E2eeAccountApprovalSession`.

- Each attempt ends with the same mailbox evidence the desktop uses. A finished round is not evidence: a refused envelope store still finishes.
- Anything short of `delivered` is retried on the same shared backoff as the desktop (eight retries). Each retry asks for the session again, so sign-out ends the delivery.
- The delivery is bound to the approving session's device key. If another account signs in and opens the same workspace, the lookup returns a session with a different device; the delivery then ends (`e2ee_key_delivery_owner_changed`) without calling it. The desktop timer likewise compares the slot's original account with the signed-in one.
- `onKeyDelivery` reports `running`, `retrying` (with code), `delivered` or `ended`.
- The core distribution journal stores the same id and bytes on each retry.

Security review of #2302 found that a failed first delivery was retried only by `memberJoinRequests`/`memberKeyDeliveries` polls. Those polls run only in an owner/admin's team settings or email worker, so a Member approver, or a workspace that is not active, left the new device keyless. `E2eeIpc` now also schedules a main-owned due timer for every delivery slot:

- the timer fires at the earliest retryable `retryAt`, for at most eight timer-driven retries after the last new request or explicit retry;
- it is cleared on delivery, terminal causes and slot removal, and is unref'd so it never holds the process;
- when it fires, it re-checks the signed-in account and drops the slot if the account changed.

Polls and explicit retries still work after the bound. A request admitted during a run's last pass is still `pending` when the run ends; the timer treats it as due at once.

Reopening rule: a delivery may reopen a workspace that no window is reading, because main's reader (desktop) or the per-attempt approval session (portable) is held only while one attempt runs, so the workspace still drains between attempts. A delivery never reopens a workspace after it was removed, revoked or reset: those paths drop its slot and timer. It also never continues after sign-out or an account change, or when the portable runtime retired. `runtime.accountApproval` counts holders of the `account-approval` reader it opens, and the last `release()` closes that reader. The workflow releases the sessions it listed when inspect or approve ends. Sessions opened before a later workspace fails to list are released too. A release whose close failed rejects and stays retryable, and background release failures go to diagnostics. Dropping a desktop slot also aborts a round already in flight before it opens the workspace or sends. The desktop also drops and aborts a slot at the start of a pass, or after a failed round, when the signed-in account is no longer the slot's (opening was already fenced by the member scope's identity check). A workflow release that fails is kept and retried at the start of each later inspect or approve, at most three attempts and sixteen holders, each failure recorded. Effect v4 `onError` also runs on interruption, so an interrupted listing releases its opened sessions; a test keeps that assumption. Delivery state remains in memory: after a restart, the device's next full key round resumes pending deliveries from the core journal.

Blast radius: the trigger is a slow or failing relay, mailbox or staging request during a key round. It reaches only the delivery state of the members that round covers. Approval, the request list and other workspaces continue. Recovery is owned by the service instance for the app's lifetime, and retained records are capped at 32 per account/workspace. Quit, sign-out and account changes close the owner. A round in flight then fails `closed` or `account_mismatch`, and the record is not shown to another account. State is in memory only. After a restart, unfinished distribution is rediscovered by the core journals on the next full key round on this device, not by this record. That gap existed before this change.

### Time to ready (R16 B run)

After the early return, the packaged B run still timed out waiting 60 s for the member's ready claim. On two real accounts over a synthetic relay and reference mailbox, the chain is functionally complete: one claim after delivery installs the key. The problem is serial cost. At about 2.3 s per relay call (a fresh Convex token plus the call), approver delivery took 14 calls and each member claim another 14, because every claim ran a full key round including distribution. The member's 10 s claim cadence could then miss a delivery by a whole cycle. The member claim now runs a receive-only round under the same single-flight: staged group or mailbox, then its installation report. Ready still requires a current key the native host installed itself. Distribution and repair stay with later full rounds; a full round waits out a receive-only one. While committed but not ready, the join page claims every 3 s for at most two minutes, then every 10 s. The owning test counts 24 serial calls (about 58 s) from the approval result to ready, down from 28 (about 67 s). Delivery transitions (`pending`, `delivering`, `delivered`, `failed` with code, `ended`) and claim phases are logged under a 12-hex request hash, never the request id. Reusing Convex tokens across calls is a separate auth follow-up, and core distributor/receiver call counts are unchanged.

### Critical path under 30 s

The owning test measures the critical path from the approval result with a warmed approver. That path is the approver's calls until its envelope `put`, one member retry that just missed it plus the 3 s cadence, and the claim that installs. It was 6 + 3 + 10 calls (about 46.7 s at 2.3 s per call including a token mint). It is now 5 + 2 + 6 calls. With Convex token reuse each call costs about 1.9 s and the path pays at most one 0.4 s mint, about 28.1 s in total; at 2.3 s per call it would be 32.9 s. Core protocol checks are unchanged:

- Approver delivery runs a distribute-only round under the keyRound single-flight. A caller joins a running round of its own mode or a full round, and otherwise waits it out.
- A claim for a join already accepted locally for the same request skips the relay claim, full history and accept. It still ingests the relay history suffix after its local checkpoint before receiving, so a rotation or a lagging local ledger can never yield ready with an old epoch key. If that catch-up fails, or relay history still pages after 256 pages (`e2ee_history_not_caught_up`, not terminal), the claim is not ready. A refused catch-up is checked through this device's credential, and confirmed access loss removes the local workspace as on every other path.
- The receive-only round no longer flushes reports. After ready, main takes over the workspace with its own reader and runs one full round, which flushes the installation report and does distribution and repair, then releases the reader.
- The cloud client reuses an unexpired Convex JWT within its owner and renews it 60 s before `exp`. The owner belongs to one account and closes on account change and sign-out, which drops the token. Any failed call drops it too, and so does a call ended by the 30 s deadline or a cancellation.
- After the two-minute fast window the join page says the member is still waiting for an administrator's device, and Retry restarts the fast cadence.

### Concurrent recipients (B on-site J07, 2026-11-05)

J07/continue still missed the 60 s window at about 63 s: the approver's full key round took 47.7 s for 36 serial mailbox calls at about 1.3 s each under whole-host CPU contention. JWKS, the TLS proxy and Convex's concurrency limit were ruled out. The owner chose to cut serial calls in the product rather than enlarge the test machine or widen the window. On real hosts after a rotation with five recipients, the round was 28 calls, all serial. It is now 10 round trips on the critical path (26 calls):

- `KeyDistributor` schedules and delivers different recipients concurrently, at most eight at once. Each recipient's hint, put, read-back and status stay in order. Outcomes are checked in the original target/page order; a blocked recipient never blocks the others; storage damage still fails the batch, after concurrently started siblings finish their idempotent step.
- `KeyReceiver` asks the mailbox revision once per step, immediately before a report is queued or sent. This replaces the earlier note that kept all four installation `status` calls: the removed queries were each followed, with only local signing or a key read in between, by another revision query before the report was queued or sent. Every verified ledger check remains.
- The owning test derives round trips from fiber fork/join structure, not wall-clock time. Recipients beyond eight, or a backend batch status call, are follow-ups only if a larger team needs them.

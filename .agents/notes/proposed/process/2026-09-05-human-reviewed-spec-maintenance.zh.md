# 人类复核的 Spec 与增量文档维护

Status: proposed
Translation: current

[English](2026-09-05-human-reviewed-spec-maintenance.md) | 中文

## 摘要

文档容易随代码变化而过期，但要求每次小修复都补齐记录和翻译，又会增加贡献者负担。本提案用人工复核的 Spec 表达人类意图，用 Agent Notes 保存重要取舍，并通过关键代码块的 SHA 检查提醒定向复核。普通小修复不强制写 note，双语可异步补齐；这降低了日常维护成本，但仍需人类判断说明是否准确。维护规则和检查工具已完成初步实现，整体方案仍待评审，正式保护范围尚未登记。

## 问题

贡献者需要理解系统意图和重要设计理由，但文档可能随实现过期。要求每次小改动都补全过程记录、双语和文件 hash，会制造额外负担。

## 决定与发现

notes 按生命周期和决策类型归档，本篇属于待 review 的 process 提案；不要求普通小修复写 note。

本次引入 [公开文档维护流程](../../../README.md)，从 [通讯架构草案](../../../../specs/communication-architecture.zh.md) 试点。Spec 由人类复核，agent 提供实现证据和开放问题；重要工作写 note，普通局部修复不强制。双语异步补齐；重点文档和关键代码引入有范围的 SHA 复核保护，普通引用不强制。本次增加开工、收尾和领域巡检工作流，以及状态汇总、分类/链接检查和定向 SHA 工具；正式范围与基线仍待登记，不进行全量迁移。

当前仓库用根目录 `specs/` 收录允许公开的客户端行为、架构和协议意图；维护流程放在 `.agents/`，跨模块说明放在 `.agents/docs/`，单个目录的实现导航放在所属模块的 README。不设根目录 `docs/`：`site-docs/` 已经拥有 `lody.ai/docs` 的用户文档，再开一个根 `docs/` 对浏览仓库的人是歧义；`docs/` 因此仍是公开边界的禁止路径。公开边界检查继续检查私有路径、内部绝对路径和部署信息。通讯草案区分本仓库证据与维护者确认的云端意图。

Invariants 已通过就近 `AGENTS.md` 维护。本次保留这一来源，agent 从历史归纳风险时先查已有规则：区分约束缺失与实现违反约束，再提出必要修改。note 记录发现和理由，不复制 invariants。

## 考虑过的方案与取舍

- **所有引用绑定 SHA 并强制复核**：文件级无关变化和多分支元数据更新会扩大工作量。选择人类确认的小范围 SHA 保护：保存完整内容 hash，短值仅供展示；变化后定向复核并显式刷新。代码改用 AfterRay 式声明块锚点，同文件其他声明的改动不触发复核；文档仍接受文件级复核成本，避免全库连锁失效。
- **靠最后编辑时间判断正确性**：只能安排巡检，改错字并不代表复核实现。
- **Spec 精确复述全部代码**：丢失人类意图并增加认知负担。选择简洁场景、模块层次和重要保证；省略细节，未知明确列出。
- **所有行为改动都写 note、合并前必须双语**：对普通修复和社区作者负担过重。按重要性记录、后续补译；代价是需要显式暴露翻译欠账。
- **新建 invariants 候选体系**：与现有 `AGENTS.md` 重复。沿用原机制，让风险发现成为维护输入。

## 工具选择

复核基线只记录已提交内容，diff 直接通过 blob hash 恢复内容，revision 仅作溯源；代价是先提交代码/文档，再提交确认记录。只要 blob 仍可取得，squash/rebase 不影响 diff；浅克隆仍可能需要补取含旧 blob 的历史。维护步骤直接写在 `.agents/README.md`，SHA 细节单独链接；这些是仓库常规约定，不包装成需要选择调用的 skill；SHA 记录放在所属文档旁的 `.anchors.json`，借鉴 DSH 的就近 sidecar 组织，但扩展为重点 Spec/代码复核。采用独立文件和动态状态汇总，避免全局索引冲突。没有选定范围时不宣称 SHA 保护已覆盖任何产品模块。

## review 与验证

本变更等待人类充分 review，通讯 Spec 未批准。规则和草案不代表产品行为已通过运行验证。已检查本次文档的本地链接目标、指令文件大小、符号链接和 diff 空白；这些不证明产品行为正确。公共边界检查未通过：当前 checkout 的 ACP 子模块未初始化，已有 workspace 依赖无法解析；检查未报告新文档违规。未运行产品测试、未验证后端或线上行为。

PR：尚未创建，创建后补充链接。本示例 note 已补齐双语，其余文档补译与全库巡检仍待完成；工具测试使用合成 Git 仓库，未替代产品行为验证。PR 模板直接嵌入完整 ShowMe 说明，外部贡献者无需安装 skill。

## 代码块复核的具体选择

借鉴 AfterRay 的源码 `@dec:` 标记、文档旁 `.anchors.json` 和双向关联检查。Lody 用 TypeScript 解析器定位完整声明，避免括号扫描误截 TS 返回类型、模板字符串或 TSX；用文档相对路径作为主题，避免 slug 重名。依赖清单仅在 sidecar 中保存，正文不重复维护 Anchors 列表。hash 记录完整值，仅忽略代码行尾空白，不自动追踪块外调用依赖；这部分依赖仍需明确选定。

保留指定主题的理由/证据确认和已提交基线，不采用 AfterRay 的全量 `--write`。当前支持 JS/TS 声明块及文件级文档，尚不支持 Rust/Swift 或章节级保护；未登记正式产品主题。合成测试覆盖块内与块外变化、双向引用缺口、标记移除、TSX/模板字符串和语法失败。

## 完整流程核验

在合成 checkout 中通过真实 CLI 验证初次待复核、确认、代码变化、只读 diff 与再次确认，整个过程 Spec 状态始终保持 draft。核验同时发现并修复了摘要未被检查、仅删除部分声明时源码 diff 漏展示的问题。这些检查验证维护工具，不证明产品行为正确或人工复核质量。

## 长期累积的保护措施

watch 两侧统一排除 symlink；基于 blob 的 diff 不再依赖 PR commit 可达。单个 topic 出错仍保留健康记录和文档队列。门禁检查全仓 Markdown 链接（含归档）、双语 Status 一致性与 8 KiB 指令上限；严格字段与可追溯的范围确认引用用于发现配置错误。经复核的退役保留记录、停止新鲜度检查，并要求移除仍存活的代码标记。

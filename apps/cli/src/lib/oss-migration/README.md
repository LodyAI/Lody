# OSS to cloud record migration

The cloud CLI exposes `lody migrate --from-oss`. It asks the human to choose an
existing workspace and confirm the account, source, target and snapshot. It never
creates a workspace. `--workspace <id|slug|name>` selects explicitly; automation
also requires `--yes`. `--source <directory>` overrides the default OSS data root.
The OSS CLI does not expose this command and rejects programmatic invocation.

Close the OSS desktop and stop its CLI after local sync finishes. Migration takes
the OSS host lease while creating a consistent SQLite backup and freezing referenced
attachments. It neither stops an application nor modifies its database. Cloud
conversations can remain present and other clients may keep editing. Migration requires
the Streams `append-cas` extension and checks it before any upload; an older deployment
fails closed. Conflicting row changes are detected on the server, not just in a local lock.

## Supported records and boundaries

- Full Loro session operation history, including archived sessions, opaque history
  entries and unknown document roots; preview comments, legacy task documents and
  disabled schedules retain their document history.
- Local file attachments from current and historical versions (including removed
  messages and overwritten references) are frozen and hash-checked before upload.
  Descriptor replacements are scanned at map-write run boundaries, including
  commits coalesced by Loro. Every recovered descriptor must match its immutable
  blob; disk contents never select a trusted historical hash. Current references
  also pass integrity checks independently.
  Current references are rewritten through HistoryWriter. The HEAD document's
  `ossMigrationAttachments` map preserves original descriptors and cloud descriptors
  for historical-only files: resolve an old-frontier reference against this HEAD
  archive with `resolveArchivedAttachment`, never rewrite immutable past operations.
  Upload receipts survive restart. A fork's `storageSessionId` is honored even when
  its original session was deleted. Missing historical bytes stop preflight.
- Needed project/provider/legacy launch rows (including their configured environment) are merged individually; conflicting
  values or tombstones stop migration. Cloud workspace settings, MCP/Role catalogs,
  installation login/keychain credentials, machine command queues and schedule runtime/manual requests are not
  replaced or copied. Transient Code Collab indexes are regenerated by their owner.
- Roost history, shallow Loro snapshots, unknown document kinds and cloud image/file
  references or legacy attachment references in an OSS source fail preflight. No unsupported record is silently
  omitted. This is not yet a universal import for every OSS release.
- Source code directories, Git worktrees, native agent state and host credentials
  are not moved. This imports records on the same computer; it is not a machine
  relocation tool. A resumed conversation may require provider/project setup.
- Session IDs are preserved. Equal titles are fine. An unrelated existing ID,
  including a deletion tombstone, is a conflict. A 32-byte migration identifier in
  metadata and a source checksum in the document distinguish recovery from collision.
- Imported sessions are collaboration-stopped, dispatch pointers/queues are cleared,
  and schedules are disabled. The complete source snapshot remains in the backup;
  pending queues are not automatically replayed.

## Recovery and publication

`<cloud data root>/migrations/<migration id>` contains the frozen source SQLite,
manifest, original/prepared full-history snapshots, referenced blobs and an atomic
journal. The migration identity binds deployment, account, workspace and OSS workspace;
the manifest additionally binds source path and machine identities. Keep this directory
until the migration has been verified. It contains private conversation data.

Before remote writes, check every source body/attachment, target document ID and
shared index row. Create each document stream with its ownership receipt in the
initial request. Creation and ownership are atomic; a lost response is recovered
from the receipt on the next run. Unrelated or empty streams are never adopted. Sync all imported authors through the Streams
initial full-delta path, then independently read back and compare version vectors.
Only after all bodies pass do index rows and stopped session metadata get published.
Each index batch and its per-row receipts use one server-conditional append against
the offset of the replica that was checked. A mismatch discards that tentative
replica and reads a fresh one before rechecking; no ordinary append fallback exists.
Row receipts live in their owning sub-Flock, not the workspace meta. They distinguish
completed rows from new collisions, even if users subsequently edit/delete a row or
the successful append response was lost. Metadata publication uses the same CAS
protocol, so concurrent tombstones are not resurrected.
There is no workspace-wide atomic publication, so an interrupted final publication
may expose a verified subset, never an unverified empty shell.

Run the same command with the same source and target to resume. Prepared bytes are
reused exactly; completed records are not overwritten or resurrected. A completed
journal describes its original frozen snapshot, not ongoing synchronization of later
OSS edits. Manifest/journal version 2 is required; scratch artifacts from the
unreleased version 1 prototype are rejected rather than reused without historical
attachments or server receipts. Source data is never deleted.

The command handles SIGINT/SIGTERM with a scoped abort signal and holds the migration
lock until the interrupted callback and target cleanup finish. Signal listeners are
removed on every exit. Network steps propagate cancellation to both attachment fetches and Streams requests,
and have a five-minute deadline. Interruption awaits Promise settlement, with a
five-second cleanup bound for broken adapters. Aborted uploads cannot publish a
receipt or prepared document. Local journal writes use fsync and atomic rename.

## Files

- `model.ts`: persisted manifest/journal validation, identity and control transforms.
- `source.ts`: read-only source backup, frozen blobs, source/index preflight.
- `attachments.ts`: historical reference scan, HEAD archive/resolution, integrity checks and HistoryWriter edits.
- `target.ts`: atomic owned creation, isolated replicas, CAS index receipts/publication and verification.
- `engine.ts`: Effect-owned sequential checkpoints, publication order, cancellable I/O
  and bounded cleanup.
- `../../commands/migrate.ts`: interactive selection, cloud auth, OSS host lease and
  cross-process migration lock. Existing Promise auth/transport adapters remain at
  this boundary; the feature does not migrate the daemon lifecycle.

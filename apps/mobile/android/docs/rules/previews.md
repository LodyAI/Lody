# Remote previews (Android)

Read before changing the conversation's web preview, iOS Simulator or Android Emulator preview, their runtime commands, the preview-token broker or the viewer host WebView. These rules bind every caller of the area, not only files in its directory.

- Previews use the shared runtime's calls unchanged: `sessionPreview` (`create` / `revoke`), `iosSimulatorControl` and `androidEmulatorControl` (`list` / `start` / `status` / `stop`). The bridge exposes them as `sessionPreview`, `iosSimulatorControl` and `androidEmulatorControl` with the verified identity, and `CloudRuntime` carries them as `RuntimeCommand.SessionPreview` and `RuntimeCommand.DeviceControl`. Native deadlines (340 s and 110 s) stay above the bridge's (335 s and 105 s), which stay above the runtime's own budgets (330 s and 100 s). Failures arrive in band as an error code with the computer's message; start, stop, create and revoke are never retried.

- Every preview proof asks the host for a request token through `shareRequest` with operation `previewToken`. The contract bridge forwards only that operation, only for the current workspace and an intent naming that workspace, to native as a `previewToken` event, and answers each request exactly once through `previewTokenReply` (60-second JS fallback). `ReadOnlyCloudRuntime` mints the token under `AccountController.withVerifiedAccount` with `cloud/PreviewTokens`, a one-shot POST of the intent to `${site}/api/session-preview/request-token` with the account bearer, within 55 seconds. An HTTP refusal returns its status; a reply whose `requesterUserId` is not the scope's account is a failure. Every other share-request operation stays `unsupported_method`.

- The session snapshot's `preview` (`label`, `active`) offers "Open preview" in the conversation's More menu, plus "Stop preview" while a link is open. A returned link opens only when it is HTTPS on a `*.trycloudflare.com` tunnel without credentials or port (`PreviewUrls`). The in-app page loads only that origin; a tapped link elsewhere opens in the browser, and no native bridge is exposed to the previewed page.

- Device previews have no More-menu entries. Each platform gets a capsule leading the action bar (`DevicePreviewChip`) when the catalog offers it on the computer (`machineSimulators` `available` for darwin computers, `machineEmulators`; both cached with the catalog) and either the agent requested a preview or one is running on this page. The request is the main conversation's `iosSimulatorPreviewRequestId` / `androidEmulatorPreviewRequestId` (live catalog only, never cached), because the CLI records starts from a Tab on the conversation that owns the device. Tapping a capsule opens the device page.

- `DevicePreviewSession` holds one platform's state for one conversation page and runs on that page's coroutine scope; pages never create a runtime. Opening resumes a running preview through `status`, otherwise lists devices for the picker (occupancy and unavailable reasons shown, other-session devices disabled). Start polls `status` each second, at most 180 times, while the device prepares. Leaving the page stops polling but not the device; Stop ends it and lists devices again. A newer action fences an older reply. Android quality (Data saver / Balanced / Clear, Balanced by default) restarts the same device with the chosen preset.

- The viewer page must have a real parent window, so `DeviceViewerWebView` loads a bundled host page from `https://appassets.androidplatform.net` (WebViewAssetLoader) that frames the viewer with `sandbox="allow-scripts allow-same-origin"`. After each frame load it sends `lody:ios-simulator:init` to the viewer's exact origin, and it accepts state and control results only from that frame, that origin and that operation, as web `IosSimulatorViewer` does. Native talks to the host page only through the `LodyPreview` web message listener restricted to the host origin. Main-frame navigation away from the host page is blocked, and frame requests are allowed only to the viewer's origin. Controls go through `lody:ios-simulator:control`, one at a time, bounded at 15 seconds; lifecycle visibility follows the page's STARTED state. File and content access are disabled and media plays without a gesture.

- Android controls are Back, Home, Recents, rotate left or right, Light or Dark appearance and Paste text. iOS controls are Home, App switcher, Lock, Volume up or down, rotate, Shake, appearance, text and Open URL, with web's text and URL limits. Bezel artwork and screenshots are not implemented on Android; the screen is drawn as a plain rounded rectangle sized from the viewer's reported dimensions.

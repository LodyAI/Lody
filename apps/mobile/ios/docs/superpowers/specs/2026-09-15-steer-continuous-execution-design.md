# Steer 连续执行与统一过程折叠

日期：2026-09-15\
更新：2026-09-16（用户引导消息保留在折叠区域外）\
状态：产品交互已确认；实现设计待落地。本文不表示相关功能已经实现。

## 决定

**一次连续执行对应一个 AI 过程折叠区域。无论中间发生多少次成功的 steer，所有阶段性 AI 内容均合并到该区域；原始用户任务与所有引导消息按顺序排列在区域上方，最终回答独立展示在区域下方。**

- 执行期间按顺序展示内容，steer 不触发完成态折叠。
- 整次执行正常完成后，统一收起过程。
- 展开后 AI 过程保持原始顺序，用户消息继续保留在区域外，不重复插入过程。用户附件随气泡保留，AI 过程附件及工具详情入口随过程展开。
- 底层 assistant 记录可以拆分；展示分组不能直接以单条记录的 `finished` 为完成依据。

## 问题与依据

| 问题                   | 当前实现                                                                                                             | 影响                                     |
| ---------------------- | -------------------------------------------------------------------------------------------------------------------- | ---------------------------------------- |
| 气泡进入正文后返回队列 | `data-runtime/project.ts` 将带 steer 标记、处于 `pending_apply / pending / seen` 且没有关联回复的消息投影为 `queued` | 等待投递确认与等待执行混淆               |
| 两种入口行为不同       | 队列 Steer 预写 `_lodyDeliveryKind: steer`；直接 Guide 的写入路径不同                                                | 同一投递语义可能产生不同展示             |
| steer 后旧过程折叠     | 上游交接时封存旧 assistant；`ChatTranscript` 对 `finished` 记录应用完成态折叠                                        | 仍在执行的工作被表现为已经完成           |
| 投递结果不明确         | `useSessionControl` 未展示正常返回的 `not_applied` 及原因                                                            | 用户无法区分拒绝、普通后续调度与确认丢失 |

上游核对基线：`LodyAI/Lody`，`a769db8b2165623bfe84893c9e903eb6be9b3e15`。

- 上游 `apps/cli/src/session/session-execution-service.ts` 在 steer 被接受后交接执行归属，封存旧 assistant 并创建新记录。记录封存不代表底层 Agent 停止后重新执行。
- 上游 `packages/components/src/components/ai-gui/view.tsx` 对没有可见结果尾部的已结束记录保留展开，但不足以表达跨多次 steer 的统一执行过程。
- 本地代码审查确认上述风险；特定用户操作的回退原因仍需通过 RPC 结果与同步时序验证，不能用动画完成代替投递证据。

## 术语与边界

| 概念           | 定义                                                                             |
| -------------- | -------------------------------------------------------------------------------- |
| 连续执行       | 原始任务开始后，经零次或多次已接受的 steer，直到真正完成、停止或失败的一条执行链 |
| assistant 分段 | 上游为了交接输出和取消操作归属而创建的独立 assistant 记录                        |
| steer 消息     | 被确认注入当前执行的用户补充指令                                                 |
| 普通后续消息   | 队列消息，或确认未注入而转为普通调度的消息；启动新的执行组                       |
| 过程           | 最终结果之外的 AI 阶段性文字、思考、工具操作、计划及附件；不包含用户消息         |

同一会话不等于同一次连续执行。正常完成后的新消息、Stop 后启动的队列消息、明确未注入的后续消息均不得合并到前一组。

## 展示契约

### 执行中

```text
用户：原始任务

AI：初始阶段的文字、思考与工具操作
用户：第一次引导
AI：后续过程
用户：第二次引导
AI：继续执行……
```

- 原生发送动画沿用现有交接机制；同一消息 ID 从乐观气泡过渡到服务端历史气泡。
- steer 插入时不收起此前阶段，不清除用户已有的展开状态。
- 可继续使用现有局部工具摘要；不因 assistant 分段结束而新增整段完成摘要。
- 用户引导消息保留用户身份、内容及附件；等待确认时在原位显示投递状态。

### 正常完成

```text
用户：原始任务
用户：第一次引导
用户：第二次引导

▸ 执行过程 · 2 次引导

AI：最终回答
```

展开后的逻辑顺序：

```text
用户：原始任务
用户：第一次引导
用户：第二次引导

▾ 执行过程 · 2 次引导
  AI：初始阶段的文字、思考与工具操作
  AI：后续过程
  AI：最后阶段的过程

AI：最终回答
```

- 只有一个顶层过程摘要；不为每次 steer 留一个独立的完成摘要。
- 所有已接受的 steer 气泡位于过程摘要上方，按引导顺序接在原始任务之后；各条消息保留独立身份及附件，不合并为一个用户气泡。
- 用户消息不进入 AI 过程区域；展开或收起过程均不改变这些气泡的位置及数量。
- 最终回答及其明确关联的结果附件始终位于过程区域下方。
- 执行期间仍按交错时序展示；正常完成时才切换为“用户消息序列 → AI 过程 → 最终回答”。这是展示重排，原始历史顺序与因果关联保持不变。
- 前面各 assistant 分段的最后一段文字也是过程，不因其处于分段末尾而成为最终回答。
- 最终回答允许由多个连续内容块组成，不能机械地只保留最后一个 text item。
- 引导次数只统计确认接受的 steer；普通排队、拒绝与确认未知不计入。
- 展开采用当前聊天过程入口支持的原生交互；上图表达内容归属，不要求新增第二套弹层。若复用过程页，应以执行组为参数展示全部 AI 过程，不能继续只接收单一 assistant ID，也不重复渲染用户消息。

### 自动折叠与异常结束

| 状态                                            | 行为                                                     |
| ----------------------------------------------- | -------------------------------------------------------- |
| 正在运行或等待权限                              | 保持过程展示，不自动进入完成态                           |
| steer 交接中，旧记录已 finished、新记录尚未同步 | 保持执行组未完成，避免短暂折叠再展开                     |
| 已正常完成且最终结果可确定                      | 默认统一折叠一次                                         |
| 用户主动展开后收到补充同步                      | 保留展开选择，不重复自动收起                             |
| Stop、失败或缺少可确定的最终结果                | 保留过程可见，展示真实结束状态；不伪造最终回答或成功摘要 |
| 断线、缓存不完整或确认未知                      | 不因暂时缺少活动分段判定完成                             |

过程总耗时属于执行组。若展示耗时，从根任务执行起点计至执行链终点，排除已知权限等待；不得简单累加可能重叠的分段耗时。

## 投递状态契约

展示位置与投递确认分别建模。飞行动画完成不代表 Agent 接受，历史写入成功也不代表 steer 生效。

| 事件 / 证据                         | 展示                               | 分组                           |
| ----------------------------------- | ---------------------------------- | ------------------------------ |
| 普通队列写入成功                    | 输入区上方队列                     | 未加入活动执行组               |
| 用户提交 Guide 或点击队列 Steer     | 正文气泡显示“正在确认引导”         | 暂存目标关联，不作为已接受成员 |
| `applied` 确认，历史状态尚未同步    | 同一气泡原位确认，不回退队列       | 加入目标执行组                 |
| ACK 丢失或 RPC 超时，无法证明未投递 | 原位显示确认未知；继续同步         | 不推断成功，不自动重放         |
| 明确未注入，且已转为普通调度        | 同一正文气泡显示“等待当前回复结束” | 成为后续独立执行的根消息       |
| 明确未注入，且未转为普通调度        | 原位展示未投递状态及适用的恢复操作 | 不加入活动执行组               |

- 已进入正文的引导气泡不因等待状态而自动退回队列；真正的普通队列消息维持现有位置。
- RPC 的“未确认”不能一律解释为“确定未投递”。按机器提供的 disposition 和历史证据判断；无法区分时保留未知。
- 成功确认应覆盖较旧的投影状态，直到服务端持久证据接管。页面卸载不能丢失这项事实；恢复时不能重放写入。
- 直接 Guide 与队列 Steer 使用同一状态转换及分组判定。
- 不支持 acknowledged steer 时现有 Stop + FIFO 路径属于普通后续执行，不作为成功 steer 合并。

## 数据模型与实现所有权

### 分组所需信息

下列为本地投影的语义要求，名称可在实现时按现有模型调整；不是已经存在的上游协议字段。

| 信息                         | 用途                                               |
| ---------------------------- | -------------------------------------------------- |
| 稳定的执行组 ID              | 由根用户任务确定；新增 steer 不改变组身份          |
| 用户消息的投递方式与确认状态 | 区分普通任务、待确认引导、已接受引导和普通调度回退 |
| 已接受 steer 的前驱关联      | 确认它延续哪一个活动 assistant / 执行组            |
| assistant 的因果用户 ID      | 关联回复分段，保留现有 `userTurnId` 信息           |
| 分段结束原因与执行链终态     | 区分交接、正常完成、取消和失败                     |
| 最终结果范围                 | 区分最后执行分段的过程与真正结果                   |

约束：

1. 不使用时间邻近、数组相邻或“最后一条用户消息”单独推断 steer 关联。
2. `_lodyDeliveryKind: steer` 不能单独证明已经接受：本地队列入口也会预写该标记。
3. 不把原始 CRDT 记录物理拼接、删除或改写为一个 assistant；组合发生在投影与渲染层。
4. 保留原始 entry/item ID，用于工具详情、附件、差异与错误恢复操作。组 ID 只承担展示身份。
   执行组成员与可折叠内容分别建模：已接受的 steer 属于执行组，但其用户气泡不属于可折叠内容。
5. 交接中的未确认关联可阻止过早折叠，但只有明确接受后才成为持久成员。
6. 冷启动、历史重载和另一设备读取应得到一致的分组；仅存于当前 React 页面内的关联不足以交付本设计。

### 上游兼容边界

实现前应验证现有历史数据能否提供持久、无歧义的交接关系及终态。RPC 请求中的 `expectedTurnId` 可作为本机暂存关联，但不能独自解决其他设备或历史重载。

- 已有数据足以证明的关联：由 `data-runtime` 生成执行组投影。
- 旧历史缺少证据：保留现有分段结构，不误合并；不声称完整支持历史统一折叠。
- 若现有协议无法满足上述持久性要求：明确提出最小上游契约扩展（交接前驱、结束原因等），再实现完整能力。不得静默写入未经确认的私有服务端字段。
- 此兼容限制不阻止先修复投递位置回退，但仅修复位置不能视为本 spec 全部完成。

## 滚动与可访问性

- 完成态重排及折叠时保留可见内容锚点并补偿偏移。用户气泡作为锚点时保持其稳定 ID；AI 过程锚点将被收起时，映射到过程摘要，不能在隐藏行上继续计算滚动位置。
- 用户已向上阅读时，不因 steer、新分段或完成态强制滚到底部。
- 跟随输出时，继续保持最终结果可见；展开过程不重新播放发送动画。
- 每条消息只有一个可见实例。连续快照、ACK 与历史接管不得造成气泡闪现或重复。
- VoiceOver 能识别摘要的展开状态和引导次数；区域外气泡保留用户身份，展开内容保留工具操作标签，阅读顺序与完成态布局一致。
- 使用 UIKit 语义颜色、至少 44 pt 点击区域，支持 Reduce Motion；不以动画是否播放影响状态正确性。

## 验收

### 行为检查

| 场景                                          | 必须成立                                                                                 |
| --------------------------------------------- | ---------------------------------------------------------------------------------------- |
| 单次 steer                                    | 执行中不折叠；完成后原始任务与引导气泡在摘要上方，摘要仅包含前后 AI 过程，最终结果在下方 |
| 连续至少三次 steer                            | 一个稳定执行组；所有引导气泡按顺序位于摘要上方，展开后也只出现一次                       |
| 完成态重排与展开                              | 用户气泡及其附件保持稳定 ID；展开不将用户消息移回过程，不重播发送动画，滚动锚点不跳变    |
| 前段以文字结束 / 工具中途交接                 | 两者均归过程，不把前段文字提升为最终结果                                                 |
| 多块最终文字及结果附件                        | 完整结果留在摘要外，过程附件可在展开后访问                                               |
| 队列 Steer 与直接 Guide                       | 相同投递语义，无正文→队列回退                                                            |
| ACK 先于历史，旧快照随后到达                  | 已接受状态不回退，气泡和组身份稳定                                                       |
| 旧 assistant finished 先到、新 assistant 后到 | 不闪现已完成折叠                                                                         |
| ACK 丢失但历史证实已接受                      | 无二次 RPC / append 重放，按证据完成归组                                                 |
| 拒绝并转普通调度                              | 原位显示等待，后续回复建立新组                                                           |
| 明确未投递但未转调度                          | 展示真实结果，无无限“正在确认”                                                           |
| Stop / 失败 / 等待权限 / 断线                 | 不错误进入成功折叠态，操作入口仍可用                                                     |
| 完成后新发普通消息                            | 与前组分离                                                                               |
| 离开再进入、冷启动、从历史恢复                | 有持久关联的数据分组一致；缺证据的旧数据不误合并                                         |
| 用户展开后迟到同步                            | 保留展开选择；无重复摘要                                                                 |

### 验证方式

- 运行时测试覆盖真实投影与合成 RPC/CRDT 时序；不能仅用 UI 桩直接设置最终状态。
- 原生检查验证分组内容、最终结果、行身份、工具与附件详情目标。
- 在 Debug 增加可独立重置的离线连续 steer 场景；复用生产组件，不使用账户、云服务或真实机器。
- 更新 `verification/ui`：截图验证完成与展开内容，视频验证发送落点、交接中间态及折叠滚动。截图不能替代时序验证。
- 实现交付运行 `pnpm check`、`pnpm bundle`；原生改动生成 runtime assets 后使用正常签名的模拟器构建，并按仓库租赁流程运行 UI 检查。

## 范围

本次覆盖 steer 投递展示、连续执行归组、统一折叠与相关回归验证。不修改 Agent 的执行策略，不自动重放不确定写入，不新增 Android 能力，不以客户端猜测替代缺失的协议证据。

## 实现记录（2026-09-16）

- 当前上游已提供 `acpTurnId`。首版仅在多个 assistant 具有相同非空 provider 回合 ID、各自具备明确 `userTurnId`，且后续用户消息带 steer 标记并已进入 `processing / handled` 时生成执行组。不能仅凭 steer 标记归组。
- Grok 的兼容路径通过取消当前执行后消费 FIFO 队列实现引导。客户端在取消前将消息 ID、目标回复 ID 与 `interrupt` 模式写入独立的 `lodySteerLinks` 会话 CRDT 元数据；上游会过滤自定义输入配置，因此归组读取独立元数据。后续历史同时具备此关联、前驱用户状态 `canceled` 和对应 assistant 时才归组。普通 Stop 不写关联，取消失败后自然消费的普通队列不误合并。
- 缺少 provider 回合 ID 或上述明确取消关联的数据保持原分段；不通过时间相邻推断。
- 本机 RPC 的目标关联用于阻止交接空隙中的过早折叠；成功 ACK 的显示状态覆盖暂时落后的历史状态。历史中的持久状态接管投递确认。
- 展开复用现有过程页，按执行组呈现 AI 内容，并保持原始 entry/item ID；用户消息不在过程页重复出现。

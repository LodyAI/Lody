# Settings (iOS)

Read before changing Settings pages or their caches. These rules bind every caller of the area, not only files in its directory.

- Settings has no Machines entry. Agent uses `AgentProvidersController`: a machine sheet picker followed by providers, with management through `agentProviders` and subscription quotas from the existing catalog usage projection. Keep Roles separate and preserve machine details and execution-machine selection elsewhere. Provider list DTOs and caches must exclude credentials and environment values. Detail editors read environment keys only, omit untouched fields, encode explicit removal separately, and clear submitted secrets. ACP sign-in and provider operations use the public runtime contracts; Sorbet encrypted connection/store management remains explicitly unavailable without its native transport.

- Preferences groups its rows under General (language, notifications), Chat Behavior (queued messages) and Appearance (app icon, the last row); rows carry no hint copy and there is no notification group label. Do not restore Appearance, MCP-server management, Memory management, Published shares or the Agent conversation sync (project history) pages; conversation MCP selection and Role memory bindings remain independent.

- Agent providers, Agent Roles and prompt shortcuts restore account/workspace-scoped `SettingsSnapshotStore` lists before the live read, persist only accepted reads, and enable writes only after a live read. Saves and deletes update the list at once and roll back on failure. Settings list reads use an incremental per-runtime stream cache (cleared when the account or workspace changes; writes and turn-time reads bootstrap fresh) and lists providers from the synced workspace replicas, online and own computers first; new providers come from the page's "+" for the selected computer.

- Settings › Projects lists the local project catalog at once and overlays team visibility from the cloud registrations (the last accepted `SettingsSnapshotStore` list first, then a live read). The read also lists the user's own machines (`machines:listVisibleMachines`): as on desktop, a project on an owned machine without a registration is private and may be shared, and an unregistered project on another member's machine is hidden. Before any registration read, or when the machine read fails, unregistered projects show as unknown and read only; a failed or empty read never blanks the list. Only a live read enables sharing changes. The read passes the catalog's account id to `WorkspaceSettingsCloud.run`, which then skips the `get-session` lookup.

- Settings › GitHub (`GitHubSettingsController`) shows personal identity, then Manage GitHub App (owners and admins), then the workspace repositories with owner logos and native switches, filtered by a stacked navigation search. It shows the last complete read from `SettingsSnapshotStore` at once and refreshes behind it; because the list rarely changes, its switches work from the cached read (each native write re-reads the role and repositories and reads back), and a write supersedes an in-flight refresh. A flipped switch shows its new value until the write reads back; a failed or unknown write returns it to the last read value and locks writes until a fresh read. Members see disabled switches.

- Prompt shortcuts favour speed over freshness. A shortcut row opens its sheet at once and fills the body when the read returns, with Save off until then. The runtime (`prompt-shortcuts.ts`) keeps per workspace and account: the access directory for 30 s, stream grants until shortly before expiry, and bodies keyed by their exact index entry (a published body is immutable), and it prefetches listed bodies one at a time. The Settings page lists with `fresh`, and saves always re-read the directory; opening, composer choice and send-time expansion may miss a revocation until the next directory read. Native `GitHubCloud.call` reuses the Convex JWT until a minute before its `exp` and re-mints once on a 401.

- GitHub installation entry points (Settings and Add Project) re-read personal operation authorization before minting installation state. Missing or expired grants offer the existing Web authorization settings; network or malformed reads remain failures. The browser uses the configured backend’s neutral installation callback to resolve its Web origin, and the user signs into the same Lody account, authorizes, then returns and retries. This does not enable the personal operation preference; backend installation and repository authorization remains final.

# Core OTA

Standalone Node ESM publisher for the [Core OTA intent](../../../../specs/portable-desktop-ota.zh.md).
Requires a Node version with native `node:zlib` zstd support and the repository's supported security floor.

| Entry               | Contract                                                                              |
| ------------------- | ------------------------------------------------------------------------------------- |
| `protocol.mjs`      | Canonical serialization, SHA-256, strict schema validation and Ed25519 authentication |
| `build.mjs`         | Streaming snapshot publisher with signed manifests and immutable packs                |
| `protocol.test.mjs` | Real crypto, filesystem and zstd boundary tests                                       |
| `download.mjs`      | Measured Range planning, disk spooling, streamed decoding and snapshot staging        |
| `activation.mjs`    | ABI-scoped release adoption, durable pointers and attempt-bound health                |
| `bootstrap.mjs`     | Installed metadata admission and verified external entry selection                    |

Run from the repository root:

```sh
node apps/electron/scripts/core-ota/build.mjs --input /build/core --output /build/release --release r5 --seq 5 --channel nightly --platform darwin --arch arm64 --host-abi abi1 --key-file /secure/signing.pem
node --test apps/electron/scripts/core-ota/protocol.test.mjs
```

The output directory must be outside input. New files are created exclusively; retries accept identical bytes and reject conflicting artifacts. A failed write can leave unpublished pack files. No upload, feed advancement or network operation occurs. Keep input immutable while building; concurrent modification is unsupported. The caller owns release-ID immutability, sequence allocation and publication ordering.

`buildRelease({input, output, release, seq, channel, platform, arch, hostAbi, keyFile})` returns `{manifest, packs}`; each returned pack is `{path, bytes: Buffer}` by default. With `returnPackBytes: false`, pack entries contain `path` and an undefined `bytes`; immutable bytes are written to the output directory without retaining earlier pack buffers. The CLI uses this disk mode. Library callers may supply an Ed25519 `privateKey` instead of `keyFile`. CLI keys are PEM files. Diagnostics never print key material.

The schema has exactly `schemaVersion: 1`, `releaseId`, `seq`, `channel`, `platform`, `arch`, `hostAbi`, `tree`, `packs`, `objects`, `patches`, and `signature`. Tree entries are `{path, sha256, size}`; packs are `{sha256, path, size}`; objects are keyed by uncompressed SHA-256 and contain `{packSha256, offset, length, compressedSha256}`. Patch entries add `fromSha256` and `toSha256` to those frame fields. Their fixed schema semantics are zstd with the exact verified source bytes as dictionary. The builder optionally generates dictionary patches using native Node zstd. Every target hash has a full frame regardless of patches.

`canonicalJson(value)` returns a string: object keys use JavaScript UTF-16 lexical order, arrays preserve order, strings use JSON escaping, integers use decimal notation. Only safe integers are supported; negative zero is rejected. `sha256(bytes)` returns lowercase hex. `validateManifest(manifest)` returns the original object or throws. `signManifest(unsigned, privateKey)` returns a validated signed copy. `verifyManifest(manifest, publicKey)` validates and returns the original object or throws. Keys may be Node KeyObjects or PEM inputs. Signature is canonical Base64 Ed25519 over UTF-8 canonical JSON with only the top-level signature removed. Verification does not normalize paths, insert defaults or reorder arrays.

Wire readers must reject duplicate JSON keys before converting to an object; these object APIs cannot recover duplicates discarded by JSON.parse. Readers must bound raw manifest bytes before parsing. Unknown fields are rejected. Paths must be relative NFC, without Windows device names, traversal, backslashes, controls, forbidden Windows characters or trailing dot/space. Case-folded duplicates and file/ancestor conflicts are rejected. Symlinks and special files are unsupported. Mode bits are not represented; Core content must not depend on executable permission preservation.

Limits are 100,000 files/patches, 256 MiB per target/frame, 64 packs, 8 GiB per pack and 32 GiB logical tree. Sequence and offsets are safe integers; ranges must fit their pack and cannot overlap. The publisher hashes files incrementally, streams compression and pack writes through disk, and splits packs at frame boundaries under `maxPackBytes`. An individual frame above the budget or more than 64 packs fails. Dictionary generation retains at most one bounded previous file; dictionary replay streams and verifies the target. `returnPackBytes: true` additionally retains every returned pack in memory, so production publishers use `false`. The default pack limit is 256 MiB; `maxPackBytes` may raise it up to the wire limit. Stable input and Node/zstd toolchain produce deterministic output; compression across toolchain versions is not promised.

Consumers must authenticate before use, enforce channel/platform/architecture/exact Host ABI and sequence policy, verify compressed hash before bounded decompression, then target size/hash. Full-pack downloads additionally verify pack hash. Signature validity alone does not provide freshness, anti-rollback persistence, safe staging or activation. HTTP Range, installation, rollback and signed installer behavior belong to the runtime and are not verified by these publisher tests.

Optional `--previous-input /build/previous` (`previousInput` in the library) compares matching relative paths. Changed targets use streamed native zstd compression with the verified previous file as dictionary; patches are retained only when they save more than 256 bytes and bounded streaming replay matches the target size and hash. Missing previous files omit that patch. Invalid previous file types and escaping links fail the build. All target objects retain dictionary-free full frames. Identical existing output bytes are accepted on retry; different bytes fail rather than overwrite immutable artifacts.

## Transfer and activation

`stageRelease({manifest, publicKey, hostAbi, channel, platform, arch, baseUrl, storeRoot, localRoots, fetchImpl, signal})` authenticates applicability before work and returns `{directory, manifest, stats}`. The directory contains only target files; the manifest is returned separately.

The transfer planner compares mixed dictionary/object ranges, complete-object ranges and full packs using compressed bytes and request latency. Local content is hashed before reuse. Each downloaded frame and decoded object is verified; HTTP 200 fallback verifies the full pack. Verified objects persist under `storeRoot/.objects` via synced temporary files and atomic rename. Transfers retain object paths, reverify disk size/hash before reuse and snapshot output, and load dictionary bytes only on demand. A failed transfer retains completed objects; retries fetch only missing or corrupt objects. Partial compressed frames are not resumed.

Responses spool to disk under `maxSpoolBytes` (8 GiB by default); decoding and snapshot assembly stream from disk. Dictionary reads are bounded at 256 MiB. Cached responses are evicted when no remaining target needs them or before another response would exceed the disk budget. Decoded bytes are rejected as soon as they exceed the signed object size. Temporary transfer files are removed on success, cancellation and failure. The next exclusively owned transfer removes abandoned module-generated download/staging directories left by a killed process. A 32-entry LRU retains per-origin measured request latency and body throughput; the next uncached request replans using those measurements. Statistics include requested, received, useful and wasted bytes, request count, selected plan modes, peak spool bytes, elapsed time and process CPU usage. `processLifetimePeakRssBytes` reports the process lifetime high-water mark rather than pretending to isolate one update.

`cacheBytes` defaults to 512 MiB. Cache GC removes only digest-named regular files in `.objects`, never release directories. Before transfer it protects target and dictionary hashes; after snapshot publication or a caught staging failure it trims cache bytes to budget. Eviction uses oldest verified use time (file mtime), with digest order breaking ties. Valid object reads refresh mtime. Active references may temporarily exceed the cache budget; an abruptly killed process is trimmed on the next transfer. Same-store calls are serialized within this module instance; callers must provide exclusive store ownership across processes. Cache publication syncs file bytes; power-loss durability of directory metadata is not established.

`openActivation({root, installed, publicKey, lease})` requires the installed Host's exclusive process lease. `adoptStaged({directory, manifest})` verifies the source, copies and verifies the complete snapshot, flushes and seals it, publishes it, and persists `staged`. `begin()` promotes only on the next launch and records an attempt before external execution. `acknowledge({releaseId, attemptId})` accepts only that attempt. A later process rejects an interrupted attempt and verifies the retained candidate before using it; builtin remains the final fallback. Pointer replacement syncs both file and directory. Filesystem flush guarantees still depend on the platform.

The namespace includes product, channel, platform, architecture and Host ABI. The owner is the installed application's single-instance lock, not a PID file or time-based takeover. These modules assume a same-user store; permissions and repeated verification do not isolate downloaded code from another malicious process with the same user rights.

Run the owning behavioral suites:

```sh
node --test apps/electron/scripts/core-ota/*.test.mjs
```

They exercise signed dictionary replay, real loopback HTTP ranges, skipped releases, content reuse, tampering, cancellation, concurrent snapshot publication, durable process restart and stale health rejection. They do not establish packaged Electron execution, signed installer behavior, production publication, power-loss recovery or complete specification conformance.

## Installed desktop integration

Package with `pnpm --dir apps/electron run package -- --core-ota-config /path/to/public-config.json` and the existing explicit publish-policy arguments. The JSON contains only `{product, channel, platform, arch, publicKey, feedUrl}`: product is `lody-oss`, channel matches the packaged stable/nightly version, platform and architecture match the build, publicKey is an Ed25519 PEM public key, and feedUrl is HTTPS without credentials. The packager computes hostAbi from the installed build, dependency lock, public configuration and Host modules after native staging. The resulting `resources/core-ota-host.json` is part of the signed installation. Signing private keys belong only to the artifact publisher.

The feed URL serves the signed manifest. Upload digest-named packs before advancing that manifest. The publisher must assemble Core input containing the complete emitted module closure rooted at `out/main/application.js`, including nested emitted dependency modules, plus `out/preload` and `out/renderer`, preserving their build-relative layout. The main build uses `preserveModules: true`, `preserveModulesRoot: src/main` and strict entry signatures in [electron.vite.config.ts](../../electron.vite.config.ts); copying only top-level main files is insufficient. Exclude modules exclusive to the installed Host closure, while retaining every shared emitted module reachable from Core. `buildRelease` recursively snapshots the supplied input; it neither assembles nor validates that module closure. `buildDesktopRelease({buildOutput, ...options})` calls [assembleCoreSnapshot](../assemble-core-snapshot.mjs) into a temporary `<snapshot>/out`, then signs `buildRelease({input: snapshot, ...options})`; temporary input is removed on success or failure. The CLI selects this path with `--build-output /build/out` instead of `--input`. The assembler uses `main/core-artifacts.json` emitted by the build boundary plugin, so only the recorded Core main closure is copied. Bundled dependency chunks use `dependencies/` paths without `node_modules` directory segments, avoiding electron-builder's dependency filtering. After packaging, the ASAR reader checks every recorded Core main file before native probes. To assemble separately from the repository root, run `node apps/electron/scripts/assemble-core-snapshot.mjs /build/out /build/core/out`, then pass `--input /build/core` to the publisher. The destination must be new; its parent must already exist. `previousInput`, when supplied, remains a previously assembled snapshot root containing `out/`. Read hostAbi from the installation's metadata for publication.

Core updates use relaunch through the current unload/CLI quit barrier. The installed index keeps identity, single-instance admission and startup custody. Desktop logging shares its process-owned state across Host/Core module copies, preventing lost direct logs and duplicate lifecycle installation. A scoped Node loader hook resolves external packages from the installed Host while relative Core imports stay in the verified release.

Health commitment requires completed main initialization, resolved route content, matching workspace readiness, restored session content when a session is selected, and a main-window mainFrame IPC probe through preload. Loading shells cannot acknowledge health. Login, onboarding, empty workspaces and the existing session-not-found recovery view have explicit readiness paths. The probe reads live local Execution Host state with a bounded timeout and rejects starting or fatal states; degraded/offline operation remains valid. Explicit control-only mode skips the local Host probe. The main window, frame and navigation are checked again after the probe. Health acknowledgement and timeout share one decision owner, so a late ACK cannot overwrite recovery and shutdown waits for an admitted pointer write.

Initial health has a sixty-second deadline; import failure, synchronous startup failure, asynchronous main initialization failure or timeout persists rejection and verified fallback before requesting a clean process relaunch. Before automatic CLI startup, application registers an early failure cleanup that stops CLI startup admission and begins CLI/shell teardown before the activation write; Host relaunch waits for both release receipts. Once application teardown is installed, rescue uses the existing unload/CLI quit barrier with an observed fifteen-second wait budget; an unconfirmed quit is reported rather than forcibly bypassed. If renderer persistence remains unconfirmed after execution owners release, the terminal exit records that state and preserves the OTA recovery relaunch; ordinary restart cancellation retains its existing behavior. Deliberate pre-health shutdown clears the attempt without permanently rejecting the release. Failure to write that shutdown state is logged without skipping independent teardown. Missing metadata, absent releases and incompatible Host targets leave the native full updater available.

The integration suite is `node --test apps/electron/src/main/services/core-updater-service.test.mjs`. It loads signed synthetic application modules, including a CommonJS relative chunk using a Host-only package in a subprocess, and checks retained content reuse across publications. These are Node boundary tests; actual Vite artifacts, Electron's ASAR resolution, native addons and renderer/preload startup require packaged probes on supported architectures. Publisher assembly and signing are covered with synthetic emitted artifacts, including nested shared modules and an excluded Host artifact. The [artifact boundary fixture](../main-artifact-boundary.test.mjs) exercises exact entry paths, ownership refusal without business evaluation, an executable assembled Core without the Host entry, coherent preload/renderer output, and rejection of eager stores and undeclared externals. The product build and `desktop-startup.test.mjs` validate the real emitted ownership closure. The resource verifier runs after product builds and during desktop publication to require the fixed window entry, renderer pages, recovery and preload files.

In-place renderer reload, release-retention GC, rollout policy, data-schema rollback coordination, production publication automation and native installer delta chains remain separate specification work. Cache GC is independent of release retention.

On macOS arm64, an electron-builder directory package verifies the complete Core main closure, window/preload/renderer resources, main E2EE SQLite and encrypted custody, Roost Worker storage and embedded CLI native bindings. The final emitted Core also passes signed publication, staging, adoption and external loading using temporary fixture trust, the package's actual Host ABI and its Electron runtime; native bindings resolve from the Host ASAR. Formal signing, notarization, installer execution, complete application startup, renderer/preload interaction and OS-specific process relaunch remain unverified. No production feed is enabled by default.
